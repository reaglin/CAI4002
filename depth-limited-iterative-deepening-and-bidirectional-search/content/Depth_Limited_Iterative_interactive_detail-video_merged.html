Depth-Limited Search

1

Depth-Limited Search

▶

Depth-limited search (DLS) is the smallest useful repair to depth-first search (DFS). It changes one thing only: it refuses to expand any node that lies at or beyond a chosen cutoff depth l. That single parameter converts an algorithm that may wander forever down an infinite branch into one that always terminates, while preserving DFS's greatest virtue — its tiny, linear memory footprint. The price is a new kind of failure: the search may terminate without finding a goal and without having proved that no goal exists. Understanding that third outcome, the cutoff, is the heart of this topic.

Motivation: taming depth-first search. Plain DFS always expands the deepest node on the frontier. In a finite, acyclic, tree-shaped state space this is harmless: every branch eventually bottoms out, the search backtracks, and the whole tree is enumerated. Real state spaces rarely behave so politely. Consider route-finding on a road map modelled as a search tree: from Arad you may go to Sibiu, from Sibiu back to Arad, from Arad back to Sibiu, and so on forever. The state space has only twenty or so cities, but the search tree generated from it is infinite because the same cycle can be traversed indefinitely. DFS following the path Arad → Sibiu → Arad → Sibiu … never terminates and never reports anything. The same failure occurs in genuinely infinite spaces — for example, a state space whose states are integers with successor functions n ↦ n+1 and n ↦ n−1, or a block-stacking domain where you may always add another block.

DLS repairs this by supplying a depth bound. Every node carries (explicitly or implicitly, via the recursion stack) the number of actions taken from the root to reach it. When the algorithm reaches a node whose depth equals l, it simply does not generate that node's successors. Formally, nodes at depth l are treated as though they had no successors at all — the search behaves exactly as if the state space ended there. The algorithmic change is tiny: take any DFS implementation, add a depth counter, and add one comparison. Because the modified tree has finite depth and finite branching factor, it contains at most 1 + b + b² + … + b^l nodes, so the search must terminate. Termination is now guaranteed even in an infinite state space, and even when cycles are present, because a cycle can only be followed l times before the limit intervenes.

How the algorithm works. Node ordering is untouched: the frontier is still last-in-first-out, so DLS expands the most recently generated node, exactly as DFS does. When it arrives at depth l it tests for goalhood (a node at the limit is still checked — it is only its children that are suppressed), then backtracks to the shallowest unexplored sibling and continues. A recursive formulation makes the structure obvious:

function DEPTH-LIMITED-SEARCH(problem, l) returns a solution, or failure, or cutoff
    return RECURSIVE-DLS(MAKE-NODE(problem.INITIAL-STATE), problem, l)

function RECURSIVE-DLS(node, problem, limit) returns a solution, or failure, or cutoff
    if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
    else if limit = 0 then return cutoff
    else
        cutoff_occurred? <- false
        for each action in problem.ACTIONS(node.STATE) do
            child <- CHILD-NODE(problem, node, action)
            result <- RECURSIVE-DLS(child, problem, limit - 1)
            if result = cutoff then cutoff_occurred? <- true
            else if result != failure then return result
        if cutoff_occurred? then return cutoff else return failure

Three return values, not two, are the defining feature of this algorithm:

  • solution — a goal node was reached at some depth ≤ l; the path to it is returned immediately and the remaining search is abandoned.
  • cutoff — no goal was found, and at least one branch was truncated by the limit. Somewhere in the tree there are unexamined descendants; the question "does a solution exist?" remains open.
  • failure — no goal was found and nothing was truncated. Every branch terminated naturally in a dead end before reaching depth l. This is a genuine proof that the state space reachable from the start contains no goal at all.

Notice how the cutoff_occurred? flag propagates upward: a parent returns cutoff if any of its children did, because a single truncated branch anywhere is enough to invalidate a claim of exhaustiveness. This is precisely the signal that distinguishes "no solution exists" from "no solution found yet" — and it is the information that makes iterative deepening possible, since a cutoff result is an invitation to try again with a larger limit, whereas failure means retrying would be pointless.

Completeness and the choice of limit. Let d be the depth of the shallowest goal. DLS is complete if and only if l ≥ d. The two ways to get the limit wrong are asymmetric but both costly:

  • Limit too small (l < d). The goal lies strictly below the frontier of exploration and is never generated. The algorithm returns cutoff, having done potentially enormous work for nothing. The goal is missed entirely — not approximated, not partially found.
  • Limit too large (l ≫ d). Completeness is preserved, but effort is squandered. Because DFS plunges depth-first, it may descend l levels down an irrelevant leftmost branch, generating b^l nodes, before ever touching the subtree containing a goal at depth d. In route-finding with l = 100, the search can wander through hundred-step tours of the map before considering the three-step route.

The uncomfortable conclusion is that completeness depends on knowledge the searcher usually does not possess: you must already know something about how deep the answer is in order to guarantee finding it. This is why the cutoff return value matters so much in practice — it is an explicit warning to the user that a deeper limit might succeed, turning a silent failure into an actionable one. A system that returned only "failure" in both cases would mislead its user into concluding the problem is unsolvable.

Optimality concerns. DLS is not optimal. It returns the first goal it happens to encounter, which depends entirely on the order in which successors are generated. Consider a root with two children: the left child leads down a chain to a goal at depth 6, while the right child is itself a goal at depth 1. With l = 6 and left-to-right expansion, DLS dives into the left branch, finds the depth-6 goal, and returns it immediately — never discovering that a one-step solution existed on the very next branch. A deeper goal on an early branch is routinely returned in preference to a shallower goal on a later branch.

With non-uniform step costs the situation is worse still: there is no cost guarantee of any kind. Even if DLS returned the shallowest goal, "fewest actions" need not mean "cheapest", because a two-step route of 500 km beats neither a three-step route of 150 km in cost nor any sensible notion of quality. To obtain an optimal answer, DLS would have to abandon its early exit and instead explore all branches down to the limit, record every goal found, and compare their path costs — which sacrifices the early-termination saving and still only guarantees optimality among solutions of depth ≤ l. Breadth-first search (with uniform costs) or uniform-cost search are the appropriate tools when optimality is required.

Complexity and memory profile. The analysis follows directly from the shape of the truncated tree. With branching factor b and limit l, the number of nodes that can be generated is 1 + b + b² + … + b^l = O(b^l), so time complexity is exponential in the limit, not in the goal depth. Space is where DLS shines: at any instant the algorithm stores only the nodes on the current root-to-node path, together with the unexpanded siblings at each level of that path — at most l levels × b nodes, giving O(b·l).

Breadth-first search must hold roughly 1012 nodes — hundreds of terabytes — whereas DLS with l = 12 holds about 120 nodes, a few kilobytes. Memory stays linear in the limit, and this is DLS's decisive advantage over breadth-first search.

An important corollary: raising l costs time exponentially but costs memory only linearly. Setting l too high therefore reintroduces large time costs without any memory penalty. If you can afford the time, a generous limit is the safer error; if you cannot, a generous limit may mean the search never terminates in practice even though it terminates in theory.

Choosing a limit in practice. Several sources of a defensible bound exist, ordered roughly from tightest to loosest:

  • Problem-specific knowledge. Domain constraints often pin the answer down exactly. Rubik's Cube is solvable from any configuration in at most 20 quarter-turn-metric... in at most 20 face turns ("God's number"), so l = 20 is a provably sufficient and tight limit. The 8-puzzle requires at most 31 moves. A chess engine searching for a forced mate in three sets l = 5 plies.
  • The diameter of the state space — the longest of all the shortest paths between any two states. Since the goal is some state, and the shortest path to it cannot exceed the diameter, setting l to the diameter guarantees l ≥ d. In the classic Romania route-finding problem there are 20 cities and any city is reachable from any other in at most 9 steps, so l = 9 is both sufficient and far tighter than the number of cities. The catch is that computing a diameter is often as hard as solving the original problem; it is usable only when the domain hands it to you (grid worlds, small graphs, structured puzzles).
  • Number of states minus one. Any shortest path visits no state twice, so it has at most |S| − 1 edges. This is a safe upper bound but typically a catastrophically loose one: for Romania it gives l = 19, roughly doubling the depth and hence squaring the worst-case node count relative to l = 9. For most real problems |S| is astronomical, making the bound useless in practice.
  • No sensible limit available. This is the common case. The natural response is to hedge: run DLS with l = 0; if the result is cutoff, run it again with l = 1; then l = 2, and so on, stopping on solution or failure. That procedure is exactly iterative deepening search, and it inherits DLS's O(b·l) memory while recovering breadth-first search's guarantee of finding the shallowest goal. The apparent waste of regenerating shallow nodes on every pass turns out to be asymptotically negligible, because the bottom level of an exponential tree dominates the total.

In short, DLS should be understood less as a finished algorithm than as a disciplined building block: it converts DFS's unbounded risk into a bounded, well-reported computation, and its three-valued result is the control signal on which more powerful uninformed strategies are constructed.

Depth-first search is attractive because it uses very little memory, but it has a serious weakness: on graphs with very deep or infinite branches, it can follow a single path forever and never return. Depth-limited search (DLS) is the simple fix. It runs depth-first search but refuses to expand any node past a chosen cutoff depth L, treating nodes at depth L as if they had no successors.

That one change gives the algorithm three possible outcomes instead of two: it can return a solution, it can report plain failure (no goal exists within the limit), or it can report cutoff (the search was truncated, so a goal might still exist deeper). The choice of L is therefore everything. If L is smaller than the depth of the shallowest goal, DLS is incomplete and will miss the solution; if L is larger, DLS may still return a goal that is not the shallowest one, so it is not optimal. Its time complexity is O(b^L) and its space complexity is O(bL), inheriting DFS's memory advantage.

Second, what does the algorithm return when the limit is hit but no goal is found — and how is that different from genuine failure? Third, how would someone pick L for a real problem, for example using problem knowledge such as a known graph diameter or a bound on solution depth? These questions lead directly into iterative deepening, which is covered later in this module.

Iterative Deepening Search

1

Iterative Deepening Search

▶

Iterative deepening search (IDS), sometimes written as iterative deepening depth-first search (IDDFS), is the uninformed strategy that resolves the central dilemma of blind search. Breadth-first search (BFS) is complete and, for uniform step costs, optimal — but it must hold an entire frontier in memory, which grows as O(b^d) and exhausts RAM long before it exhausts patience. Depth-first search (DFS) needs only a single path in memory, but it is neither complete (it can dive forever down an infinite branch) nor optimal (it returns the first goal it stumbles upon, however deep). Depth-limited search (DLS) repairs DFS's infinite-descent problem by refusing to expand nodes below a cutoff depth ℓ, but it introduces a new problem: you must choose ℓ correctly. Choose too small and you miss the goal entirely; choose too large and you re-admit much of DFS's wasted effort and lose optimality. Iterative deepening sidesteps the choice altogether by trying every limit in increasing order until one succeeds.

What iterative deepening search is. IDS is a loop around depth-limited search. It runs DLS with limit 0, then limit 1, then limit 2, and so on, without any predetermined upper bound. Each iteration is a complete, self-contained depth-limited search launched afresh from the initial state; if that iteration does not find a goal, everything it built — its stack, its path, its generated nodes — is discarded, and the next iteration starts from zero with a limit one greater. This sounds profligate, and it is the feature most students object to on first encounter, but as the complexity analysis below shows, the duplicated work is asymptotically negligible.

Two properties follow immediately from this structure. First, IDS never requires you to guess a depth limit in advance, which is precisely the weakness that makes plain depth-limited search awkward to deploy on unfamiliar problems. Second, because the limits are tried in strictly increasing order starting at 0, the first iteration that returns a solution must be the iteration whose limit equals the depth of the shallowest goal. If a goal existed at some depth k, the iteration with limit k would have found it; so when the goal is first found at limit d, no goal exists at any depth less than d. The process terminates the moment it reaches the shallowest goal depth — it never searches deeper than necessary.

How the algorithm works, step by step. The control loop is remarkably short, and its correctness rests entirely on depth-limited search returning three distinguishable outcomes rather than two:

  • Solution — a goal node was reached within the limit; IDS stops and returns the solution path.
  • Cutoff — no goal was found, but at least one branch was truncated because it hit the depth limit. There may still be a goal further down, so IDS increments the limit and tries again.
  • Failure — no goal was found and no branch was truncated. The entire reachable state space was explored and found to contain no goal, so IDS terminates and reports failure.

Without the distinction between cutoff and failure, iterative deepening could not know when to stop on a finite state space with no solution — it would loop forever, raising the limit past the depth of the deepest reachable node. The pseudocode is:

function ITERATIVE-DEEPENING-SEARCH(problem) returns a solution, or failure
    for limit = 0 to infinity do
        result <- DEPTH-LIMITED-SEARCH(problem, limit)
        if result != cutoff then return result     // solution or failure
    end for

function DEPTH-LIMITED-SEARCH(problem, limit) returns solution / failure / cutoff
    return RECURSIVE-DLS(MAKE-NODE(problem.INITIAL-STATE), problem, limit)

function RECURSIVE-DLS(node, problem, limit) returns solution / failure / cutoff
    if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
    else if limit = 0 then return cutoff
    else
        cutoff_occurred? <- false
        for each action in problem.ACTIONS(node.STATE) do
            child <- CHILD-NODE(problem, node, action)
            if child.STATE is on the path from the root to node then continue   // cycle check
            result <- RECURSIVE-DLS(child, problem, limit - 1)
            if result = cutoff then cutoff_occurred? <- true
            else if result != failure then return result
        end for
        if cutoff_occurred? then return cutoff else return failure

Note the memory behaviour. Because RECURSIVE-DLS is a depth-first recursion, the only nodes alive at any instant are those on the current root-to-node path, plus the unexpanded siblings of each node on that path. When an iteration ends, its entire recursion stack unwinds and the memory is reclaimed before the next iteration begins. At no point does IDS hold two iterations' worth of data simultaneously — only one path at a time is ever stored.

Completeness and optimality. IDS inherits the good properties of breadth-first search:

  • Complete on any state space with a finite branching factor, even if the space is infinitely deep. Any goal at finite depth d will be reached on iteration d at the latest, because iteration d exhaustively examines every node at depth ≤ d, and there are only finitely many such nodes when b is finite. This is exactly what plain DFS cannot promise: DFS may commit to an infinite branch and never return.
  • Optimal when all step costs are equal (or, more generally, when path cost is a non-decreasing function of depth). Since limits are tried in increasing order and iteration d is the first that can possibly succeed, the goal returned is a shallowest goal, and with uniform costs shallowest means cheapest.
  • Not optimal with varying step costs. If moving from A to C costs 100 and a three-step route costs 3, IDS will still return the shallower, more expensive solution. Depth is simply the wrong quantity to minimise when edges have different weights. The correct responses are uniform-cost search (a best-first search ordered by g(n), which is optimal but pays the BFS-style memory penalty) or iterative lengthening search, described below.
  • Cannot be trapped on an infinite path, because every iteration imposes a hard finite cutoff and then unwinds. An unbounded descent simply triggers the cutoff signal and causes the next, slightly deeper, iteration.

The O(bd) figure counts the d nodes on the current path plus the up-to-b siblings stored at each of those levels while the recursion iterates over them; implementations that generate successors lazily can reduce this to O(d).

The practical significance is hard to overstate. For b = 10 and d = 12, BFS would need to store on the order of 1012 nodes — terabytes of memory, which is why memory, not time, is almost always the binding constraint on large blind searches. IDS needs storage for roughly 120 nodes. Both do about 1012 node generations, so both are slow; but IDS will actually run, while BFS will crash. This is why iterative deepening is the preferred uninformed strategy whenever the search space is large and the solution depth is unknown.

Why repeated node regeneration costs little. The objection to IDS is obvious: the root is expanded d + 1 times, level 1 is generated d times, and so on. Surely that is enormously wasteful? It is not, and the reason is the geometry of exponential trees: in a tree with branching factor b > 1, the bottom level contains roughly as many nodes as all shallower levels combined. Level d has bd nodes while levels 0 through d−1 together hold (bd − 1)/(b − 1). The nodes that get regenerated most often are exactly the ones that are least numerous.

Counting precisely: a node at depth i is generated once in each iteration whose limit is at least i, i.e. in iterations i, i+1, …, d — that is d − i + 1 times. So the total node generations are

Real AI search problems tend to have substantial branching factors — the 8-puzzle has an effective b near 2.8 after excluding the reverse move, chess around 35, Rubik's Cube around 13.3 — so in the regime where blind search is most painful, iterative deepening's overhead is smallest. The one genuinely unfavourable case is a near-unary tree (b close to 1), where the bottom level is not dominant and the repetition is no longer amortised; there, plain DFS or BFS is preferable.

Variants and practical use. The "restart with a looser bound" idea generalises well beyond depth limits:

  • Iterative lengthening search replaces the depth cutoff with a path-cost cutoff. Each iteration performs a cost-limited DFS that prunes any node with g(n) > limit; if that iteration fails, the limit is raised to the smallest g-value that exceeded the previous limit. This restores optimality for varying step costs while retaining linear space — a memory-light stand-in for uniform-cost search. Its drawback is substantial overhead: with many distinct path costs, the number of iterations can be far larger than d, since each iteration may admit only one extra node.
  • IDA* (Iterative-Deepening A*) applies the same cutoff-and-restart scheme to heuristic search, bounding on f(n) = g(n) + h(n) instead of depth. Each iteration is a DFS that prunes nodes whose f-cost exceeds the current threshold; the next threshold is the minimum f-value that was pruned. With an admissible heuristic, IDA* returns optimal solutions using memory linear in the solution depth, whereas A* must store the whole frontier and explored set. IDA* was the method that first produced optimal solutions to the 15-puzzle and remains standard for memory-constrained optimal search.
  • Standard practice for large uninformed searches. When the goal depth is unknown and the space is too large to hold in memory, IDS (or IDA* if a heuristic is available) is the default recommendation. Game-playing programs use a closely related form of iterative deepening over minimax search depth, both to respect a clock — the deepest completed iteration is always available as an answer — and because the move ordering learned at depth k dramatically improves alpha-beta pruning at depth k + 1, often making the extra iterations pay for themselves.
  • Cycle and duplicate handling. Because IDS is depth-first inside each iteration, it has no global explored set to detect repeated states, so a graph containing cycles can send one iteration spiralling around a loop until the limit is consumed — wasting effort and bloating the branching factor. The cheap, standard remedy is a cycle check along the current path: before expanding a child, verify its state does not already appear among the ancestors on the root-to-node path. This costs O(d) per node (or O(1) with a hash set keyed on the current path) and preserves the linear space bound. A full transposition table can catch more duplicates, but it reintroduces memory growth and so is used selectively, often with a bounded-size cache.

Putting it together. Iterative deepening is best understood not as a compromise between BFS and DFS but as a way of getting almost all of BFS's guarantees at DFS's memory cost. It uses depth-first expansion to keep memory linear, while the outer loop over increasing limits imposes a breadth-first ordering on the order in which depths are first explored, which is where completeness and shallowest-goal optimality come from. The price is re-generating shallow nodes, and the geometry of exponential trees makes that price a small constant factor rather than an asymptotic penalty. For a large state space with unit step costs, an unknown goal depth, and no usable heuristic, it is the strategy of choice; add an admissible heuristic and its descendant IDA* takes over; replace the depth bound with a cost bound and iterative lengthening handles non-uniform costs.

Iterative deepening search (IDS) is the standard answer to a practical dilemma in uninformed search: breadth-first search finds the shallowest goal but stores an exponential number of nodes, while depth-first search uses very little memory but can wander down a deep or infinite branch and miss a nearby solution. IDS resolves this by running depth-limited search over and over, with the limit set to 0, then 1, then 2, and so on, until a goal is found. Each pass behaves like DFS in memory terms, but the sequence of passes explores the tree in order of increasing depth, like BFS.

This matters in the course because IDS is usually the default choice when the search space is large, the branching factor is finite, and you have no heuristic information. It is complete, it is optimal when every step costs the same, and it needs only O(bd) space. The surprising part — and the part worth understanding carefully — is that regenerating the shallow nodes on every pass is cheap: because the number of nodes in a tree grows geometrically with depth, the deepest level dominates the total count, so the repeated work adds only a constant-factor overhead.

Bidirectional Search

1

Bidirectional Search

▶

Every uninformed search strategy considered so far grows a single tree outward from the initial state until a goal is encountered. The cost of that growth is dominated by the exponential term b^d, where b is the branching factor and d is the depth of the shallowest solution. Bidirectional search attacks this exponent directly. Instead of one search that must travel the full distance d, it runs two searches simultaneously — one growing forward from the initial state and one growing backward from the goal state — and stops as soon as the two frontiers touch. Because each search only has to cover about half the distance, the dominant cost becomes b^(d/2) rather than b^d. This is not a constant-factor trick: it is a genuine reduction of the exponent, and it is the single largest speedup available to an uninformed strategy. The price is a set of structural requirements on the problem — the ability to generate predecessors, an explicitly known goal state, and an efficient way of testing whether the frontiers have intersected — that many problems simply cannot satisfy.

The core idea. Picture the state space as a graph. The forward search begins at the initial state s and repeatedly applies the problem's successor function: from a node n it generates every state reachable by one legal action. This is ordinary search in the normal direction of time. The backward search begins at the goal state g and repeatedly applies a predecessor function: from a node n it generates every state m such that some legal action transforms m into n. The backward search is therefore reasoning about "what could have come immediately before this?" rather than "what can happen next?". The two searches grow two balls of explored states, one centred on s and one centred on g. Since any solution path runs from s to g, the two balls must eventually overlap, and the first node that appears in both frontiers — the meeting node m — lies on a path connecting them.

Recovering the actual solution is a matter of splicing. The forward search holds a path s → … → m built from parent pointers back to the start. The backward search holds a path g → … → m, also built from parent pointers, but its arcs point in the wrong direction: each "parent" link in the backward tree represents an action travelling towards the goal. Reversing that chain gives m → … → g. Concatenating the two, and taking care not to duplicate the meeting node itself, yields the complete solution:

forward path  : s → a → b → m
backward path : g → z → y → m   (as stored, rooted at g)
reversed      : m → y → z → g
solution      : s → a → b → m → y → z → g

Note the implicit assumption: reversing the backward chain only produces a valid plan if each backward link corresponds to a real action in the forward direction. This is automatic when the predecessor function is defined correctly, because the predecessor relation is the inverse of the successor relation by definition. What is not automatic is that such a function is computable, which is the subject of a later point.

Why each half only travels d/2. If the shallowest solution has length d, then in the best case the two searches, growing at the same rate, will meet near the midpoint of that path. A forward breadth-first search that has completed layer k contains every state at distance k from s; a backward breadth-first search that has completed layer k contains every state at distance k from g. The node at distance d/2 along an optimal path belongs to both sets once both searches have completed layer ⌈d/2⌉. So neither search ever needs to go deeper than roughly half the solution depth. Visually, two balls of radius d/2 touch exactly where one ball of radius d would have had to reach — but two small balls contain vastly fewer states than one large one.

The complexity advantage, quantified. A breadth-first search to depth d generates O(b^d) nodes. Each half of a bidirectional breadth-first search generates O(b^(d/2)) nodes, so the total is O(2·b^(d/2)) = O(b^(d/2)) in asymptotic terms. Space behaves the same way: breadth-first search must retain its frontier, which is the largest layer, so bidirectional search needs O(b^(d/2)) memory — and in fact at least one of the two frontiers must be held in memory in its entirety, because that is what the intersection test is performed against. Requirement: generating predecessors. The backward search cannot start unless we can answer the question "which states have n as a successor?" Formally, Pred(n) = { m | n ∈ Succ(m) }. When every action is reversible and the action set is symmetric, this is trivial: the predecessors of n are exactly its successors, and the backward search is identical in form to the forward one. Examples:

  • Route finding on a two-way road network. The predecessors of a city are the cities joined to it by a road; the successor and predecessor functions coincide. Bidirectional search is a classic and highly effective technique here, and is used in production route planners.
  • The 8-puzzle / 15-puzzle. Sliding the blank left can always be undone by sliding it right. Pred = Succ, so the backward search is just an ordinary search rooted at the goal configuration.
  • Rubik's Cube. Every quarter-turn has an inverse quarter-turn. The goal (solved cube) is a single explicit state, making this an almost ideal candidate; the famous "God's number = 20" computations rely heavily on meeting-in-the-middle ideas.

Now consider the failures:

  • Irreversible actions. In a chemical synthesis planner, mixing two reagents cannot be undone. In a robot that drops an object off a ledge, the action has no inverse. Backward reasoning must then ask "what situation could have produced this?", which may have no computable answer.
  • Many-to-one actions. Suppose an action is "set variable x to 0". Every state that differs only in x is a predecessor of the result. The predecessor set is huge, or even infinite, and the effective backward branching factor explodes — possibly exceeding b by orders of magnitude, which destroys the b^(d/2) analysis. A similar problem arises with lossy or information-destroying operations such as integer division, truncation, or sorting.
  • Simulation-defined transitions. If successors are produced by running a black-box physics engine or an external program, inverting it may be impossible even in principle.

The rule is blunt: if predecessors cannot be computed efficiently and with a modest branching factor, bidirectional search is simply not applicable. Note also that the backward branching factor b_back need not equal the forward one. If they differ, the two searches should not be grown at equal depth; the balanced strategy is to expand whichever frontier is currently smaller, so that the total work is minimised rather than the two depths equalised.

Requirement: explicit and few goal states. The backward search needs somewhere to start, and that means we need the goal state, not merely a goal test. The ideal case is a single, concretely specified configuration: the solved Rubik's Cube, the ordered 15-puzzle tile arrangement, the destination city. Several situations degrade from there:

  • A small, enumerable set of goals. If there are, say, five acceptable final states, the standard device is to introduce a dummy goal node G* whose predecessors are defined to be exactly those five real goal states (joined by zero-cost pseudo-actions). The backward search is then rooted at the single node G*, expands immediately into all five real goals, and proceeds normally. The solution found is simply the path up to whichever real goal was involved.
  • Goals described by a property. Consider the 8-queens problem, where the goal test is "no two queens attack each other". We cannot root a backward search at "the" goal, and enumerating all solutions in advance defeats the purpose — finding one is the problem. Similarly, in a theorem prover the goal might be "any state in which the formula is proved", and in a planning problem it might be a partial description such as "the robot is holding a cup and the door is closed", which is satisfied by astronomically many complete world states.
  • Abstract goal descriptions. A goal description that leaves k binary features unconstrained corresponds to 2^k concrete states. A backward search that must begin by enumerating all of them has already lost the exponential battle before expanding a single node. In such cases the backward frontier is larger at depth 0 than the forward frontier will be at depth d/2.

There is a partial remedy for the last case: search backwards over sets of states (regression planning) rather than individual states, where a backward "node" is a partial description that is weakened as actions are regressed through it. But this is no longer plain state-space search, and the clean b^(d/2) analysis no longer applies directly.

Testing for frontier intersection. The termination condition of bidirectional search is "a node appears in both frontiers", and this test is executed every time a node is generated. If it were implemented as a linear scan it would cost O(b^(d/2)) per check and completely negate the savings. The standard implementation stores at least one frontier (and usually both, along with their explored sets) in a hash table keyed on the state, so that membership testing is expected constant time. Each newly generated node from one direction is looked up in the opposite direction's table before being added to its own.

function BIDIRECTIONAL-BFS(problem) returns a solution, or failure
  if problem.INITIAL = problem.GOAL then return empty path
  frontierF ← FIFO queue containing INITIAL
  frontierB ← FIFO queue containing GOAL
  reachedF  ← hash table { INITIAL : node }      // state → node, for path recovery
  reachedB  ← hash table { GOAL    : node }

  while frontierF and frontierB are both non-empty do
    // expand whichever side is currently cheaper
    if |frontierF| ≤ |frontierB| then
       dir ← FORWARD; expand frontierF using SUCCESSORS, test against reachedB
    else
       dir ← BACKWARD; expand frontierB using PREDECESSORS, test against reachedF

    for each child generated in this expansion do
       if child.STATE is in the opposite table then
            return JOIN(forward-part, reverse(backward-part))
       if child.STATE not in own table then
            add child to own table and own frontier
  return failure

The subtle point is the word first. The first intersection discovered yields a solution, but not necessarily an optimal one, even when both halves run breadth-first. The reason is that the meeting is detected at generation time, and the two searches are at specific, possibly unequal, depths when it happens. A classic illustration: suppose the forward search has completed depth 2 and the backward search depth 2, and while generating depth-3 forward nodes we find a node already in the backward depth-2 set. That gives a path of length 5. But there might exist a different node, not yet generated, that joins the forward depth-2 layer to the backward depth-2 layer for a total of 4. Because node generation within a layer happens in an arbitrary order, we may stumble on the length-5 meeting first.

The standard fixes are:

  • Do not return immediately. Record the best solution found so far, keep expanding, and terminate only when the sum of the two frontiers' minimum depths (or minimum path costs g-values) is at least as large as the best solution cost recorded. At that point no undiscovered meeting can beat it.
  • Finish the current layer. With uniform step costs, complete the layer in which the first meeting occurred and keep the cheapest join found during it.
  • Use a cost-aware termination rule. Modern front-to-end algorithms such as MM ("meet in the middle") are designed so that the two searches provably meet near the midpoint and so that the termination test guarantees optimality for non-uniform step costs.

The key insight behind this table is that bidirectional search needs at least one side to maintain a broad, stored, systematically grown frontier, because that frontier is the "net" that the other side must hit. Breadth-first growth guarantees the net is complete out to a known radius. Depth-first search in both directions is attractive on memory grounds — it would reduce space to O(bd) — but it is useless in practice: two depth-first searches explore long, narrow paths through an enormous space and will almost never intersect, so the method loses both completeness and its reason for existing. Mixed strategies are legal but make the analysis awkward: if one side is iterative-deepening and the other breadth-first, you can no longer say "the meeting occurs at depth d/2 on each side", and establishing that the first meeting is the shallowest becomes considerably harder.

Practical limitations, and when to reach for it. Summarising the constraints:

  • Memory remains exponential. O(b^(d/2)) is far better than O(b^d), but it is still exponential, and in real systems memory — not time — is usually the binding constraint. Bidirectional search raises the depth you can reach before running out of RAM to roughly double, which is a large but finite win. It does not convert an intractable problem into a linear-space one the way iterative deepening does for time-bounded depth-first search.
  • Implementation complexity. You must maintain two frontiers, two explored sets, a predecessor function, a balanced expansion policy, a correct intersection test, a path-splicing routine, and a termination rule that does not sacrifice optimality. This is substantially more machinery than a plain breadth-first search, and more places for bugs to hide.
  • Structural preconditions. Irreversible actions, many-to-one actions with huge predecessor sets, and implicit or abstract goal descriptions each individually rule the technique out.
  • Poor payoff on shallow problems. At d = 2 or 3 the constant factors and extra bookkeeping may make bidirectional search slower than the single-direction version.

Conversely, the profile of an ideal candidate is: a large branching factor, a substantial solution depth, fully reversible (or at least easily invertible) actions, and one explicit goal state. Puzzle domains such as the 15-puzzle and Rubik's Cube fit perfectly; so does point-to-point route planning on a road network, where bidirectional Dijkstra is standard practice and typically halves or better the explored region. A worked sense of the payoff: for the 15-puzzle, b ≈ 2.13 and typical optimal solutions run to d ≈ 53. Unidirectional breadth-first search is hopeless; a bidirectional search needs to reach only depth ~27 from each end, cutting the node count from roughly 2.13^53 ≈ 10^17 to roughly 2 × 2.13^26.5 ≈ 10^9 — the difference between impossible and merely expensive.

When its preconditions hold, bidirectional search delivers the largest single improvement available within the uninformed family. It should be considered the default recommendation for problems with a known, unique goal state and reversible actions — and discarded immediately, without further analysis, for problems whose goals are defined only by a predicate or whose actions cannot be run backwards.

Comparing Uninformed Search Strategies

1

Comparing Uninformed Search Strategies

▶

Uninformed (or "blind") search strategies all share the same limited information: they know the initial state, the actions available in each state, the cost of each action, and a test that recognises a goal. None of them has any estimate of how far a given state lies from a goal. What distinguishes them is purely the order in which they expand the frontier. That single design choice — expand the shallowest node, the cheapest node, the deepest node, or expand from both ends at once — produces dramatically different behaviour in terms of whether a solution is found at all, whether it is the best solution, how long the search takes, and how much memory it consumes. Comparing these strategies systematically is therefore one of the most practically useful exercises in search: it turns a collection of superficially similar algorithms into a decision procedure for choosing one.

The comparison below is carried out on tree search formulations unless stated otherwise, because that is where the asymptotic bounds are cleanest. Adding a closed/explored set (graph search) changes some of the completeness claims — notably, it rescues depth-first search on finite state spaces — but it also changes the space complexity, so the distinctions are flagged where they matter.

Four Criteria for Evaluating Search Strategies

Every search algorithm in this family is judged against the same four questions. They are deliberately orthogonal: an algorithm can score well on one and badly on another, and the art of selecting a strategy lies in knowing which criterion your application actually cares about.

  • Completeness asks: if a solution exists anywhere in the state space, is the algorithm guaranteed to find one in finite time? Note the precision of the claim. Completeness is not "usually finds a solution"; it is a guarantee. An algorithm fails completeness if there is even one reachable configuration in which it loops forever, or descends an infinite branch, or terminates reporting failure while a goal still sits unexplored. Depth-first search on a state space with cycles — a robot that can move north then south then north again — is the standard example of incompleteness.
  • Optimality asks: when a solution is returned, is it guaranteed to be a lowest-cost solution? Where every action costs the same, "lowest cost" collapses to "shallowest", and the question becomes whether the algorithm returns a solution with the fewest actions. Optimality is strictly stronger than completeness: an algorithm can be complete but habitually return a wasteful 40-move solution when a 7-move solution exists. Depth-first search again illustrates this — it returns the first goal it happens to stumble into, which may lie at the bottom of a very deep branch.
  • Time complexity measures how long the search takes, expressed not in seconds but in the number of nodes generated (or, in some texts, expanded) before termination. Counting nodes rather than seconds keeps the analysis machine-independent. In search problems the state space is typically characterised not by the number of vertices and edges — which is often astronomically large or implicit — but by the branching factor and the depth of a solution, so complexity is expressed in those terms.
  • Space complexity measures the maximum number of nodes held in memory simultaneously at any point during the search. This counts the frontier (the open list), plus the explored set if one is maintained, plus whatever path information must be retained to reconstruct the solution.

A point that students often meet with surprise: in practice, memory is almost always the binding constraint, and it binds long before time does. Consider a machine that can generate 10 million nodes per second and stores each node in 1,000 bytes. A search that generates 1010 nodes will take about 1,000 seconds — roughly 17 minutes, which is tedious but entirely survivable. Storing those same 1010 nodes would require about 10 terabytes of RAM, which is not survivable on ordinary hardware. The breadth-first search simply crashes with an out-of-memory error after a few minutes, having never reached its time limit. This asymmetry is the single most important practical fact in the whole comparison, and it is the reason iterative deepening — which is slower by a constant factor but uses linear memory — is the default recommendation rather than breadth-first search.

Notation Used in the Comparison

All the complexity results that follow use a small, fixed vocabulary. Being precise about these symbols is essential, because bounds that look similar differ enormously depending on whether the exponent is d, m, l, or d/2.

  • b — the branching factor. The maximum number of successors generated by any node. In the 8-puzzle the blank tile can move in two, three, or four directions depending on its position, giving an average branching factor of about 3 (or 1.7 if one avoids immediately undoing the previous move). On a chessboard mid-game b is around 35. In route-finding across a road network b is the average number of roads leaving a junction, perhaps 3 or 4. Because complexity is exponential in depth with base b, even modest reductions in the effective branching factor pay off handsomely.
  • d — the depth of the shallowest goal node. Not any goal, but the closest one, measured in number of actions from the root. This is the quantity that bounds breadth-first search, because breadth-first search cannot possibly expand past level d.
  • m — the maximum depth of the state space. The length of the longest path from the root that the algorithm might follow. Critically, m may be infinite: in any state space with a reversible action and no repeated-state checking, a tree-search algorithm can generate paths of unbounded length (north, south, north, south, …). Where a goal exists, m ≥ d, and m can be vastly greater than d. This gap is exactly why depth-first search behaves so badly in the worst case despite its attractive memory profile.
  • l — the depth limit. A user-supplied integer at which depth-limited search refuses to expand any further. It is a parameter of the algorithm, not a property of the problem, and supplying a good value requires knowledge the searcher does not otherwise have.
  • C* — the cost of the optimal solution, and ε — the smallest positive action cost in the problem. These appear only in the analysis of uniform-cost search, where the algorithm's progress is measured in units of cost rather than levels of depth. The quantity C*/ε is the "effective depth" in cost terms: it is the greatest number of actions that could possibly make up a path still worth considering. If ε is allowed to be zero — a free action — uniform-cost search can be trapped forever on a zero-cost cycle, which is precisely why the condition ε > 0 appears in its completeness guarantee.

Breadth-First and Uniform-Cost Search

Breadth-first search expands the shallowest unexpanded node, managing the frontier as a FIFO queue. Because it expands all nodes at depth 0, then all at depth 1, then all at depth 2, and so on, it sweeps the state space in concentric shells around the start state.

Completeness. Breadth-first search is complete provided b is finite. The argument is simple and worth internalising: if a goal lies at depth d, then after finitely many expansions the algorithm will have exhausted levels 0 through d−1 (there are at most 1 + b + … + bd−1 such nodes, a finite number when b is finite) and must therefore reach the goal. Infinite branches are harmless because breadth-first search never commits to one. This is a stronger guarantee than depth-first search offers, and it holds even when m is infinite.

Optimality. Breadth-first search returns the shallowest goal. If all step costs are identical, shallowest equals cheapest, and the search is optimal. If step costs differ, it is not optimal: a two-action path costing 100 will be returned in preference to a three-action path costing 3. Consider a route-finding problem where one road from the start leads directly to the destination along a 400 km motorway detour, while a three-hop sequence of local roads covers 25 km. Breadth-first search returns the 400 km path and stops. More subtly, breadth-first search is optimal only in the weaker sense of "fewest actions" even in the uniform-cost case; it makes no claim about minimising anything else.

Time and space. With the goal test applied at generation time, breadth-first search generates b + b2 + … + bd = O(bd) nodes. (Applying the goal test at expansion time instead, as some textbook formulations do, generates nearly a whole extra level — O(bd+1) — which for b = 10 means a tenfold waste; test at generation.) Space complexity is also O(bd), because at the moment just before the goal is found, the entire last level sits in the queue simultaneously. This is the crucial observation: breadth-first search's space complexity has the same exponent as its time complexity. Every node generated must be kept, either on the frontier or in the explored set, so memory grows as fast as work does. Referring back to the table above, this is why breadth-first search is the classic victim of out-of-memory failure.

Uniform-cost search generalises breadth-first search by expanding the node with the lowest path cost g(n), using a priority queue ordered by g. Two implementation details make it correct rather than merely plausible: the goal test is applied when a node is selected for expansion, not when generated (because a cheaper route to the same goal may still be sitting in the queue), and a node on the frontier is replaced if a cheaper path to the same state is discovered.

Completeness and optimality. Uniform-cost search is complete and optimal for any set of non-negative step costs, provided every step costs at least some ε > 0. The optimality argument is that the algorithm expands nodes in non-decreasing order of g, so the first goal selected for expansion must be a cheapest goal. The role of ε is to guarantee termination: without it, an infinite sequence of zero-cost actions would have total cost 0 and the algorithm could expand forever without the frontier's minimum cost ever rising.

Complexity. Uniform-cost search is not bounded by d, because depth is irrelevant to it; it is bounded by cost. Every node whose path cost is less than C* must be expanded before the optimal goal is selected. Since the cheapest action costs ε, a path of cost below C* can contain at most ⌊C*/ε⌋ actions, giving a bound of O(b1 + ⌊C*/ε⌋). When all costs are equal, say all equal to 1, this reduces to O(bd+1) — slightly worse than breadth-first search because of the deferred goal test. When costs are highly non-uniform, the bound can be enormously worse. Example: edges cost either 1 or 1,000,000, and the optimal solution costs 1,000,000 with a single action. Then C*/ε = 106, and uniform-cost search must grind through every path of up to a million unit-cost actions before it will consider that single expensive edge. Space complexity matches the time bound for the same reason it does in breadth-first search — the frontier holds everything.

Depth-First and Depth-Limited Search

Depth-first search expands the deepest unexpanded node, managing the frontier as a LIFO stack (or equivalently, by recursion). It plunges to the bottom of one branch, and only on failure backs up to the shallowest unexplored alternative.

Completeness. Depth-first tree search is not complete, and fails in two distinct ways. First, if the state space contains cycles, the algorithm can regenerate the same state endlessly along an ever-lengthening path — A → B → A → B → … — and never terminate. Second, even on an acyclic space, if some branch is infinitely deep (consider a state "integer n" with the single action "add 1"), depth-first search will follow it forever while a goal sits one node to the right of the root. Depth-first graph search, which maintains an explored set, is complete on finite state spaces because it cannot revisit a state — but that fix sacrifices the memory advantage that was the whole point of using depth-first search, since the explored set can grow to the size of the state space.

Optimality. Depth-first search is not optimal. It returns the first goal it encounters, which is determined entirely by the arbitrary order in which successors happen to be generated. A goal at depth 20 may be returned while a goal at depth 2 sits unvisited in a sibling subtree.

Time. In the worst case depth-first search explores the entire tree down to the maximum depth, giving O(bm). When m is much larger than d this is catastrophically worse than breadth-first search; when m is infinite it never terminates. Conversely, when solutions are dense in the tree, depth-first search can be much faster than breadth-first search, because it may dive straight onto a goal without expanding the exponentially many shallow nodes first.

Space. Here is the redeeming feature. Depth-first search needs to store only the nodes along the current path from root to the deepest node, plus the unexpanded siblings of each node on that path. That is at most b nodes per level across m levels: O(bm) — linear, not exponential. For b = 10 and m = 16, depth-first search needs on the order of 156 nodes, about 156 kilobytes, where breadth-first search at depth 16 would need roughly 10 exabytes. That is a factor of about 1014. A recursive variant, backtracking search, improves this further to O(m) by generating one successor at a time and modifying the state in place rather than copying it.

Depth-limited search is the obvious remedy for the infinite-branch failure: run depth-first search but treat nodes at depth l as having no successors. The algorithm must distinguish two kinds of non-success, which is what makes its interface slightly unusual.

function DEPTH-LIMITED-SEARCH(problem, l) returns solution | failure | cutoff
    return RECURSIVE-DLS(MAKE-NODE(problem.INITIAL-STATE), problem, l)

function RECURSIVE-DLS(node, problem, l) returns solution | failure | cutoff
    if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
    else if l = 0 then return cutoff
    else
        cutoff_occurred? <- false
        for each action in problem.ACTIONS(node.STATE) do
            child <- CHILD-NODE(problem, node, action)
            result <- RECURSIVE-DLS(child, problem, l - 1)
            if result = cutoff then cutoff_occurred? <- true
            else if result != failure then return result
        if cutoff_occurred? then return cutoff else return failure

The three possible return values matter. A solution means a goal was found. failure means no solution exists anywhere in the searched region and no branch was truncated — the space below this node was fully explored. cutoff means no solution was found but at least one branch was chopped off at the limit, so a solution may still exist deeper. Collapsing cutoff and failure into a single "no" would be a serious bug, because it would license the caller to conclude the problem is unsolvable when in fact the limit was merely too small. It is also the signal iterative deepening uses to decide whether another, deeper round is worthwhile.

Properties. Depth-limited search always terminates, in O(bl) time and O(bl) space. It is incomplete whenever l < d: the goal is simply out of reach and the algorithm reports cutoff. It is also non-optimal, and non-optimal even when l ≥ d: because the underlying traversal is still depth-first, it will return a deep goal it meets first rather than the shallowest goal. Choosing l too large reintroduces wasted work; choosing it too small loses the solution.

Choosing l requires problem knowledge. Sometimes the knowledge is available. In a map of the 20 cities of Romania, any city is reachable from any other in at most 9 steps — the diameter of the state space — so l = 19 is certainly safe and l = 9 is exactly right. For Rubik's Cube it is now proved that any configuration is solvable in at most 20 quarter-turn-metric moves ("God's number"), so l = 20 is both sound and tight. But such facts are hard-won; usually the diameter is unknown, and any guess risks either an incomplete search or an unnecessarily expensive one. This dilemma is precisely what iterative deepening dissolves.

Iterative Deepening and Bidirectional Search

Iterative deepening depth-first search (IDS) runs depth-limited search repeatedly with l = 0, 1, 2, 3, …, stopping as soon as a round returns a solution. If a round returns failure rather than cutoff, the whole state space has been exhausted and IDS can correctly report that no solution exists.

function ITERATIVE-DEEPENING-SEARCH(problem) returns solution | failure
    for depth = 0 to infinity do
        result <- DEPTH-LIMITED-SEARCH(problem, depth)
        if result != cutoff then return result

Completeness and optimality. Because the limit eventually reaches d, and because every round terminates, IDS is complete whenever b is finite — infinite branches no longer trap it, since each round truncates them. It is optimal when step costs are uniform, because the rounds are tried in increasing depth order, so no goal at a depth greater than the shallowest can be returned before the shallowest is found. In effect IDS delivers breadth-first search's guarantees using depth-first search's memory discipline.

Space. At any instant only one depth-limited search is running, so the memory requirement is O(bd) — linear. The results of earlier rounds are discarded entirely; nothing accumulates.

Time, and why the repetition is cheap. The obvious objection is that IDS regenerates the shallow part of the tree over and over. The objection is correct but quantitatively unimportant, and the reason lies in the geometry of exponential trees: the overwhelming majority of nodes live on the bottom level. In a tree with branching factor b, level d alone contains bd nodes while all levels above it together contain only about bd/(b−1) — a fraction that shrinks as b grows. Repeating the cheap upper levels therefore costs little, while the expensive bottom level is generated exactly once.

Counting precisely: in the final round the deepest level is generated once, the level above it twice, the level above that three times, and so on up to the root, which is generated d + 1 times. The total number of nodes generated is

N(IDS) = (d)b + (d-1)b^2 + (d-2)b^3 + ... + (2)b^(d-1) + (1)b^d

compared with breadth-first search's N(BFS) = b + b2 + … + bd. Both sums are dominated by their last term, so both are O(bd); the repetition changes only the constant factor, and the constant is b/(b−1) in the limit. Numerically, with b = 10 and d = 5:

An 11% overhead in exchange for reducing memory from 100,000 nodes to roughly 50 nodes is an extraordinary bargain. The overhead falls as b rises: at b = 2 IDS generates about twice as many nodes as BFS, at b = 10 about 11% more, at b = 35 (chess) under 3% more. The intuition to retain is that re-searching an exponential tree's shallow levels is asymptotically free, because an exponential tree is almost entirely bottom level. Note also that in some formulations IDS is actually faster than BFS, because BFS with a goal test at expansion generates O(bd+1) nodes while IDS tests at generation within each round.

The same idea extends to non-uniform costs as iterative lengthening search, which iterates on a cost bound rather than a depth bound and mimics uniform-cost search in linear space, though its overhead is typically larger because the number of distinct cost contours can be much greater than the number of depth levels.

Bidirectional search attacks the problem from a different angle: instead of economising on memory, it reduces the exponent. It runs two simultaneous searches — one forward from the initial state, one backward from the goal — and stops when the two frontiers intersect. The motivation is purely arithmetic: bd/2 + bd/2 is dramatically smaller than bd. For b = 10 and d = 6, a single-direction search generates about 1,111,110 nodes, while two searches each to depth 3 generate about 1,110 each, 2,220 in total — a saving of roughly 500-fold. For b = 10, d = 12 the saving is about 50,000-fold.

Completeness and optimality. When both halves are breadth-first searches and all step costs are uniform, bidirectional search is complete and optimal. Optimality needs a little care: the first intersection discovered is not automatically the cheapest meeting point, so a correct implementation continues until it can prove no cheaper joining path remains, rather than halting at the first touch. If one half is depth-first, both guarantees are lost.

Complexity. Time and space are both O(bd/2). The space figure deserves emphasis: at least one of the two frontiers must be held in memory in a form that supports membership testing, so bidirectional search is still exponential in space — just with half the exponent. This makes it a far weaker memory story than iterative deepening, and the two ideas can be combined (a breadth-first forward search meeting an iterative-deepening backward search, for instance).

Preconditions. Bidirectional search is not universally applicable, and its requirements are restrictive:

  • An explicitly defined goal state. You cannot search backwards from a description. "Checkmate" or "all eight queens are non-attacking" names a large and implicitly specified set of states; there is no single node from which to begin the reverse search. If there are only a handful of goal states, one can add a dummy goal node whose predecessors are all of them, but if the goal set is huge or defined by a property, the technique fails.
  • Efficiently computable predecessors. The backward search needs, for each state, the set of states from which it can be reached in one action. When actions are reversible — sliding a tile, moving between cities, turning a Rubik's Cube face — predecessors are just successors under inverse actions, and the requirement is free. When actions are irreversible or many-to-one (a state with thousands of possible predecessors, or an action that destroys information), computing predecessors is expensive or produces an unmanageable backward branching factor.
  • Efficient frontier-intersection testing. Every newly generated node must be checked against the opposite frontier, and this check happens once per node generated. If it costs more than roughly constant time — a hash table lookup — the saving evaporates. Hashing the state representation is the usual solution.
  • A manageable backward branching factor. If the reverse branching factor is much larger than the forward one, the backward search is slower than the arithmetic above assumes and the advantage shrinks.

A concrete success case: finding the shortest chain of acquaintances between two named people in a social network. Both endpoints are explicit, the "knows" relation is symmetric so predecessors are free, states are hashable, and the branching factor is large — the ideal profile. A concrete failure case: the 8-queens problem, where goal states are characterised by a property and the start state is empty, so there is no sensible node to search backward from.

The Core Trade-Off: Memory Versus Guarantees

Stepping back, the six algorithms arrange themselves along a single axis, and the organising question is how much of the search tree does the algorithm retain?

  • Store the whole frontier, buy guarantees with exponential memory. Breadth-first and uniform-cost search keep every node they have generated but not yet expanded. Retaining the frontier is exactly what lets them expand in a globally principled order — shallowest first, or cheapest first — which is in turn exactly what delivers completeness and optimality. The price is that space complexity carries the same exponent as time complexity, so memory exhausts first.
  • Store one path, buy linear memory by surrendering guarantees. Depth-first and depth-limited search keep only the current root-to-leaf path and its unexpanded siblings, giving O(bm) or O(bl). Because they have forgotten the alternatives they passed over, they cannot order their expansions globally; they commit to whatever branch is in front of them. That forgetfulness is simultaneously the source of the memory saving and the cause of the lost completeness and optimality. The two properties are not coincidentally linked — they are the same fact described twice.
  • Re-search instead of remembering. Iterative deepening refuses the trade-off by regenerating what it has forgotten. It pays in time — a constant factor of roughly b/(b−1) — rather than in space, and because the payment is a constant factor on an exponential quantity, it does not change the asymptotic time class at all. This is the general principle of trading recomputation for storage, and it recurs throughout algorithm design.
  • Attack the exponent, not the constant. Bidirectional search is categorically different from the other three: it does not rearrange when nodes are stored, it halves d in the exponent. That is a far bigger win than any constant factor — but it is available only when the restrictive preconditions above are met, and it leaves space complexity exponential.

The practical upshot is that, aside from bidirectional search, all of these strategies are in the same exponential time class: O(bd) or O(bm) or O(bl), differing by constant factors and by which exponent appears. They are not in the same space class — O(bd) versus O(bd) is a difference of many orders of magnitude at realistic depths. Since the algorithms are hard to separate on time but easy to separate on space, and since memory is the resource that actually runs out, space is normally the deciding criterion.

Guidance for Selecting a Strategy

The table turns into a decision procedure once you ask three questions about your problem: Are step costs uniform? Do I know roughly how deep the solution is? And is a reverse search possible?

  • Breadth-first search — when the solution is known to be shallow and memory is plentiful. If d is small (say bd comfortably fits in RAM) and all actions cost the same, breadth-first search is the simplest correct choice and avoids iterative deepening's repeated work. Example: finding the shortest sequence of three or four moves in a puzzle, or computing all states within k steps of the start. If bd exceeds memory, do not use it — it will not fail gracefully, it will crash.
  • Uniform-cost search — when step costs vary and genuine cost-optimality is required. Route planning with distances or travel times, scheduling with unequal action durations, and network routing all fall here; breadth-first search would return the wrong answer because fewest-actions is not cheapest. Check that ε > 0, and be wary when the ratio C*/ε is enormous, because the bound O(b1+⌊C*/ε⌋) is then far worse than O(bd).
  • Iterative deepening — when the search depth is unknown and memory is limited. This is the usual default. It is the preferred uninformed strategy whenever the state space is large, costs are uniform, and you cannot bound d in advance. You get breadth-first search's completeness and optimality at depth-first search's memory cost, for a time overhead that is a small constant factor and shrinks as b grows. Unless you have a specific reason to pick something else, pick this.
  • Depth-limited search — when a reliable bound on solution depth is known in advance. The bound must come from problem knowledge: the diameter of the state space, a regulation limiting the number of moves, a domain fact such as God's number for Rubik's Cube, or a business rule ("no supply chain may exceed six hops"). It is also the right choice when you deliberately want a bounded-effort search — a quick attempt that is guaranteed to terminate — and are willing to accept a cutoff report. Remember that it remains non-optimal even when it succeeds.
  • Bidirectional search — when the goal state is explicit, actions are reversible, and the branching factor is large. All three conditions must hold, plus constant-time frontier intersection testing. The payoff grows with both b and d, so it is most attractive precisely where other methods are most hopeless: large-branching, moderately deep problems such as word ladders, social-network shortest paths, or sliding-tile puzzles with a single specified target configuration.
  • Depth-first search — when the state space is finite and shallow, solutions are dense, or memory is critically scarce and guarantees are not needed. It is also the right engine underneath constraint-satisfaction solvers and in situations where any solution will do and all branches have similar depth. Never use plain depth-first tree search on a space with cycles or unbounded depth without either a depth limit or a repeated-state check.

Two closing cautions. First, these bounds assume tree search; adding an explored set to make graph search prevents cycle-induced non-termination and can collapse an exponential tree into a much smaller graph, but it raises space complexity to the order of the number of distinct reachable states, which negates the linear-memory advantage of depth-first and iterative deepening. Iterative deepening with a cycle check only along the current path is a common compromise: it costs O(d) extra work per node and catches the most damaging loops without storing the whole explored set. Second, every strategy here is exponential, and no amount of reordering changes that. Escaping exponential growth in practice requires information about which direction the goal lies in — that is, a heuristic — which is the subject of informed search.

Selecting an Appropriate Strategy

1

Selecting an Appropriate Strategy

▶

Uninformed (blind) search strategies all explore the same state space and all are built from the same skeleton: maintain a frontier of unexpanded nodes, pop one, test it for the goal, and push its successors. What distinguishes breadth-first search, uniform-cost search, depth-first search, depth-limited search, iterative deepening search and bidirectional search is only the order in which the frontier is drained — yet that single design decision determines whether a search finishes in seconds or exhausts memory, whether it returns the cheapest solution or merely the first one found, and whether it terminates at all. Selecting a strategy is therefore not a matter of taste: it is an engineering decision driven by measurable properties of the problem. This topic sets out how to characterise a problem in those terms, how each property narrows the field of candidate algorithms, and how to combine the resulting constraints into a defensible recommendation.

Four criteria are used throughout to evaluate any candidate strategy. Completeness asks whether the algorithm is guaranteed to find a solution when one exists. Optimality asks whether the solution it returns is guaranteed to have the lowest path cost. Time complexity counts the number of nodes generated, and space complexity counts the maximum number of nodes held in memory at once. For uninformed search these are expressed in terms of three structural parameters of the problem — the branching factor b, the depth of the shallowest solution d, and the maximum depth of the state space m — plus, where costs vary, the optimal solution cost C* and the minimum step cost ε.

Start by characterising the problem. Before any algorithm is named, five questions should be answered, because each one eliminates or promotes whole families of strategies.

  • What is the branching factor b? This is the average number of successors generated per state. In the 8-puzzle the blank tile can move in two, three or four directions depending on whether it sits in a corner, an edge or the centre, giving an average branching factor of about 3 (and about 2.13 once the move that undoes the previous move is suppressed). In chess the effective branching factor is roughly 35; in the Rubik's cube with quarter-turn metric it is about 13.3 after removing redundant moves. The significance of b is that it is the base of an exponential: every unit increase in depth multiplies the frontier by b. Estimating b empirically by expanding a sample of states and averaging their successor counts is usually quick and is well worth doing before committing to a strategy.
  • What is the solution depth d, and what is the maximum depth m? These are different quantities and confusing them is a common error. d is how far down the shallowest goal lies; m is how deep the search tree can get before paths terminate — and in a state space with loops and no repeated-state checking, m can be infinite even when d is small. For the 8-puzzle, d is at most 31 moves in the quarter-turn sense but m is unbounded on the tree because the blank can shuffle back and forth forever. Depth-first search's complexity is governed by m, breadth-first search's by d, and the gap between the two is precisely the risk you take by going depth-first.
  • Are step costs uniform or varying? If every action costs the same (say, one move), then the shallowest solution is automatically the cheapest, and any strategy that finds the shallowest goal is optimal. If costs differ — road distances, fuel consumption, monetary tolls, time taken — then depth and cost come apart, and a shallow solution may be an expensive one. This single question decides whether breadth-first-style strategies can claim optimality or whether uniform-cost search is required.
  • What is the hard memory ceiling? Memory, not time, is almost always the binding constraint in uninformed search. A practical rule of thumb: a modern machine generating a million nodes per second with 100 bytes per node consumes 100 MB per second of search. A 10 GB memory budget is exhausted in roughly 100 seconds of breadth-first search — long before a patient user's time budget runs out. Determine the real ceiling (physical RAM minus operating system and application overhead, with a safety margin) and convert it into a node count by dividing by the per-node size of your representation.
  • Is the goal explicitly known, and are actions reversible? A goal may be given as a concrete state ("the tiles in order with the blank bottom-right", "Bucharest") or as an abstract test ("a configuration in which no queen attacks another", "a checkmate position"). Only the first kind supports searching backwards from the goal. Reversibility asks whether, given a state, you can compute the states that could have led to it. These two questions jointly decide whether bidirectional search is even on the table.

Choosing when memory is the binding constraint. Read the space column of that table and a stark pattern emerges: breadth-first search and uniform-cost search both store the entire frontier, which at depth d contains on the order of b^d nodes. For b = 10 and d = 10, that is roughly 1010 nodes — at 100 bytes each, about a terabyte. The arithmetic rules these strategies out long before the clock does. A useful discipline is to compute b^d against the memory ceiling identified during characterisation: if the product exceeds available memory by even one order of magnitude, breadth-first and uniform-cost search are not viable and no amount of implementation tuning will rescue them.

Depth-first search sits at the other extreme. Because it expands the deepest node first and discards a branch once it has been fully explored, it needs to retain only the nodes on the current path plus their unexpanded siblings: O(bm) space, which is linear rather than exponential. For b = 10 and m = 10, that is around a hundred nodes instead of ten billion. The price is severe. Depth-first tree search is not complete: if the state space contains a loop or an infinite branch, the search can descend forever and never return, even though a goal sits one step from the start down a different branch. It is also not optimal: it returns the first goal it stumbles upon, which may be arbitrarily deep and arbitrarily expensive.

Depth-limited search is the direct remedy for the non-termination problem. It is depth-first search with a predetermined cutoff ℓ: nodes at depth ℓ are treated as having no successors, so no path can descend further. The search can no longer run forever in an unbounded space, and its space cost falls to O(bℓ). What it returns is now three-valued rather than two-valued: a solution, a cutoff indication meaning "no solution was found within depth ℓ, but unexpanded nodes were truncated at the limit", or failure meaning "the space below the start node was exhausted within the limit and contains no goal". A schematic implementation makes the three-way result explicit:

function DEPTH-LIMITED-SEARCH(problem, limit) returns solution | cutoff | failure
    return RECURSIVE-DLS(MAKE-NODE(problem.INITIAL-STATE), problem, limit)

function RECURSIVE-DLS(node, problem, limit) returns solution | cutoff | failure
    if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
    else if limit = 0 then return cutoff
    else
        cutoff_occurred? <- false
        for each action in problem.ACTIONS(node.STATE) do
            child  <- CHILD-NODE(problem, node, action)
            result <- RECURSIVE-DLS(child, problem, limit - 1)
            if result = cutoff then cutoff_occurred? <- true
            else if result != failure then return result
        if cutoff_occurred? then return cutoff else return failure

Iterative deepening search resolves the dilemma of having to guess ℓ by simply trying every value: run depth-limited search with limit 0, then 1, then 2, and so on, until a solution is found. Each individual iteration is depth-first and therefore costs only O(bd) space, yet because the limits increase one level at a time the first goal found is the shallowest one, so the strategy inherits breadth-first search's completeness and (under uniform step costs) its optimality. This combination — breadth-first guarantees at depth-first memory cost — is why iterative deepening is the default uninformed strategy for large state spaces where the solution depth is unknown.

The obvious objection is that iterative deepening regenerates the shallow nodes many times: the root is generated at every iteration, the depth-1 nodes at every iteration but the first, and so on. The objection sounds damaging and is in fact almost irrelevant, because in a tree with branching factor b > 1 the overwhelming majority of nodes lie at the deepest level, and that level is generated only once. Counting generations, the nodes at depth d are generated once, those at depth d−1 twice, and in general those at depth d−k are generated k+1 times, giving

N(IDS) = (d)b + (d-1)b^2 + ... + (2)b^(d-1) + (1)b^d

whereas breadth-first search generates N(BFS) = b + b^2 + ... + b^d. For b = 10 and d = 5, iterative deepening generates 123,450 nodes against breadth-first search's 111,110 — about 11% more. For b = 10 and d = 6 the overhead falls further, and in general the ratio tends to b/(b−1), so the overhead shrinks as the branching factor grows: roughly 11% at b = 10, about 3% at b = 35. Both strategies are O(b^d) in time, and iterative deepening is exponentially better in space. The repeated work is a constant-factor tax, not a change of complexity class. The one case where the overhead genuinely matters is a very small branching factor — at b = 2 the asymptotic overhead is a factor of 2, which is still only a constant.

Choosing based on step costs and optimality needs. The second axis of the decision is the cost model. When every action costs the same, depth and cost are interchangeable: the shallowest solution is by definition the cheapest, so breadth-first search and iterative deepening both return optimal solutions, and you should pick between them on memory grounds alone. When step costs vary, this equivalence breaks. Consider a route-finding problem where a direct road from A to B is 200 km while a two-hop route A–C–B totals 120 km: breadth-first search finds the one-step, 200 km route first and declares victory, which is shallowest but not cheapest.

Uniform-cost search repairs this by expanding the node with the lowest path cost g(n) rather than the shallowest node, using a priority queue keyed on g. Because it expands nodes in non-decreasing order of path cost, the first time it selects a goal node for expansion it has already proved that no cheaper path to any goal exists. Two implementation details matter for correctness: the goal test must be applied when a node is selected for expansion, not when it is generated (otherwise a suboptimal goal found early would be returned), and a newly discovered cheaper path to a node already on the frontier must replace the existing entry. Uniform-cost search is therefore the correct uninformed choice whenever costs vary and optimality is required.

Its completeness carries a precondition that is easy to overlook: there must be a positive lower bound ε on step costs. If a problem admits zero-cost or vanishingly small actions, the search can get trapped expanding an infinite sequence of cheap steps — for instance a self-loop costing zero — and never make progress towards the goal, even though a finite-cost solution exists. Its complexity reflects this too: O(b^(1+⌊C*/ε⌋)), which can be considerably worse than O(b^d) when many small-cost steps are possible, since the effective depth is measured in units of ε rather than in actions.

The converse situation is equally important. If any solution is acceptable — a satisficing problem such as placing n queens, finding some valid configuration, or generating a feasible schedule — and the state space is deep or unbounded, depth-first or depth-limited search is often the fastest route to an answer and uses negligible memory. Depth-first search plunges towards a solution instead of methodically clearing each level, and in spaces where solutions are plentiful and spread throughout the tree it typically finds one after exploring a tiny fraction of the space. Spending breadth-first effort to guarantee the shallowest solution is simply wasted when the shallowest solution is no better than any other.

Deciding whether bidirectional search applies. Bidirectional search runs two simultaneous searches — one forward from the start, one backward from the goal — and stops when the two frontiers intersect. Its appeal is purely arithmetical: two searches of depth d/2 generate about 2b^(d/2) nodes, which for b = 10 and d = 6 is 2,000 instead of 1,000,000. That is the single largest speed-up available within uninformed search. But it is applicable only when a conjunction of preconditions holds, and each must be checked explicitly.

  • The goal must be explicitly and uniquely specified. You cannot search backwards from a goal you can only recognise, as opposed to one you can write down. "Bucharest" and "the solved cube" are explicit states. "A checkmate position" or "an assignment in which no two queens attack each other" are abstract tests satisfied by enormous, implicitly defined sets of states; there is no single node from which to start the backward search.
  • Actions must be reversible so that predecessors can be generated. The backward search needs a function PREDECESSORS(s) returning every state from which s can be reached in one action. In the 8-puzzle this is easy, because sliding a tile is its own inverse. In many planning or physical domains it is not: if an action irreversibly consumes a resource, destroys information, or merges many distinct states into one (a "many-to-one" action such as setting a variable to a constant), computing predecessors may be expensive or impossible.
  • The number of goal states must be small. If the goal is described by a predicate satisfied by thousands of states, the backward search must be seeded with all of them, and the backward frontier explodes immediately — destroying exactly the advantage you were seeking.
  • An efficient intersection test is required. At each expansion the algorithm must check whether the newly generated node already appears in the opposite frontier. Done naively by scanning, this costs O(b^(d/2)) per node and dominates the runtime; done with a hash table keyed on the state representation, it costs expected constant time. Bidirectional search therefore presupposes that states can be hashed or indexed cheaply, which in turn presupposes a canonical state representation.
  • Memory for at least one frontier must be available. Intersection testing requires at least one of the two frontiers to be held in memory in its entirety, so space remains O(b^(d/2)). This is a dramatic improvement over O(b^d) — for b = 10, d = 10 it is 105 instead of 1010 — but it is still exponential, and for deep problems it can still exceed the memory ceiling.

A further subtlety: with varying step costs, naively stopping at the first frontier intersection does not guarantee optimality, since a later, cheaper meeting point may exist. Guaranteeing optimality requires continuing until the combined cost of the best known meeting path cannot be beaten, which complicates the implementation. In practice bidirectional search is most comfortably applied to uniform-cost problems with a single explicit goal, such as sliding-tile puzzles, Rubik's cube, and point-to-point route finding on a road network.

Setting a depth limit sensibly. If depth-limited search is chosen, the limit becomes a parameter whose value determines whether the search is useful or useless, so it should be derived from problem knowledge rather than guessed. The most reliable source is the diameter of the state space — the greatest shortest-path distance between any two states — because no solution can be deeper than the diameter. The classic example is route finding across the 20 cities of Romania: although the map has 20 nodes, any city is reachable from any other in at most 9 steps, so ℓ = 19 is a safe but loose bound while ℓ = 9 is both safe and tight. Similar published diameters exist for many puzzles: 31 quarter-turn moves for the 8-puzzle's hardest instance, 80 moves for the 15-puzzle, 20 face-turn moves ("God's number") for the Rubik's cube. Where no exact diameter is known, domain reasoning can often yield an upper bound — for example, a bound on the number of items to be placed, the number of variables to be assigned, or the number of jobs to be scheduled.

The two ways of getting the limit wrong fail in opposite directions:

  • A limit below the true solution depth makes the search incomplete. If ℓ < d, every branch is truncated before any goal is reached and the search reports cutoff, even though a solution exists. The danger is that this result is easily misread as proof that the problem is unsolvable.
  • A limit far above the solution depth is sound but wasteful. Because depth-first ordering drives the search to the bottom of the first branch before considering alternatives, a generous limit can send it exploring vast irrelevant subtrees at depths well beyond where the goal lies. Since the cost is O(b^ℓ), every extra level of slack multiplies the worst-case work by b.

Because of this double-edged sensitivity, interpreting the result correctly matters as much as choosing the limit. Cutoff and failure must never be conflated. Cutoff means "no solution within this limit; a deeper search might succeed" and licenses retrying with a larger ℓ — which, applied systematically, is precisely iterative deepening. Failure means "the reachable space was exhausted within the limit and contained no goal"; if the limit was at least the diameter, failure is a genuine proof that the problem has no solution. Collapsing the two values into a single boolean destroys this distinction and is a frequent source of incorrect conclusions about solvability. It is also the reason iterative deepening is preferable whenever d is unknown: it needs no estimate at all, and only pays a constant-factor premium for the privilege.

A practical decision heuristic. The considerations above can be condensed into an ordered checklist. Apply the tests in sequence and take the first that matches; the ordering reflects which constraints are hardest to work around.

  • If step costs vary and optimality matters, choose uniform-cost search. No other uninformed strategy returns a least-cost solution under non-uniform costs. Verify that step costs have a positive lower bound, and budget for O(b^(1+⌊C*/ε⌋)) space.
  • If the goal is explicit and actions are reversible, consider bidirectional search. It offers the largest speed-up of any uninformed strategy, reducing O(b^d) to O(b^(d/2)). Confirm first that the goal states are few, that predecessors can be computed cheaply, and that frontier intersection can be tested in roughly constant time by hashing.
  • If memory is limited and the solution depth is unknown, choose iterative deepening search. It is complete, optimal under uniform step costs, needs only O(bd) space, and requires no estimate of d in advance. This is the standard default for large state spaces and the safe answer when the problem description leaves the depth open.
  • If the solution depth is known and bounded, choose depth-limited search. Setting ℓ to a justified bound such as the state-space diameter, or to a known exact depth, avoids the repeated shallow iterations that iterative deepening performs and delivers the answer in a single depth-first pass at O(bℓ) space.
  • If any solution suffices, memory is scarce, and the space is finite, plain depth-first search is adequate. With no infinite branches to fall into and no optimality requirement, depth-first search's weaknesses do not bite, and its linear memory use and low constant-factor overhead make it the simplest effective choice. Add cycle detection along the current path if the space contains loops.

Two worked applications show the checklist in use. Route finding between two named cities on a road network with distances in kilometres. Step costs vary (road lengths differ) and the shortest route is wanted, so the first test fires and uniform-cost search is the correct uninformed answer; distances are strictly positive, so completeness holds. Had the question been "find any route" rather than "find the shortest", the second test would apply instead, because the goal city is an explicit state and roads are traversable in both directions, making bidirectional search attractive.

Solving a 15-puzzle instance of unknown difficulty with a few hundred megabytes of memory. Here b ≈ 2.13 after pruning reverse moves, d is unknown and may be as large as 80, and all moves cost one. Breadth-first search is ruled out immediately: 2.13^40 nodes cannot be stored. The goal configuration is explicit and moves are reversible, so bidirectional search qualifies on preconditions — but at d ≈ 50 even b^(d/2) is around 2.1325, tens of millions of nodes, which strains the stated budget. Depth-limited search is unattractive because d is unknown and a limit of 80 would be hopelessly loose. Iterative deepening therefore wins: it is complete, returns the shortest move sequence, runs in O(bd) memory, and pays only the small constant-factor premium for regeneration. (With a heuristic available, IDA* would be the natural next step — but that lies outside uninformed search.)

Finally, note that these decisions interact with the choice between tree search and graph search. Adding a closed set of explored states eliminates repeated states and makes depth-first search complete in finite spaces, but it reintroduces memory proportional to the number of distinct states visited, which can silently undo the space advantage that motivated choosing depth-first or iterative deepening in the first place. In memory-critical settings the usual compromise is to keep only the current path for cycle checking — cheap, O(d) extra space — and accept some redundant work on re-converging paths.

Once you know how breadth-first, uniform-cost, depth-first, depth-limited, iterative deepening, and bidirectional search each behave, the practical question becomes: which one should you actually use? This topic gives you a procedure for answering that. You start by characterising the problem — estimating the branching factor, the likely depth of a shallowest solution, whether step costs are uniform or variable, whether the state space is finite, and how much memory you can afford — and then you match those characteristics to the strategy whose completeness, optimality, time, and space profile fits best.

Several rules of thumb fall out of this. When memory is the binding constraint, breadth-first and uniform-cost search are usually ruled out and iterative deepening becomes the default; when step costs vary, optimality requires uniform-cost search rather than breadth-first; bidirectional search only applies when you can generate predecessors, you have one or a few explicitly described goal states, and you can test frontier intersection cheaply; and a depth limit should be set from real knowledge of the problem (for example, the diameter of the state space) rather than guessed, since too small a limit makes the search incomplete.
