1

Fitness Functions and Evaluation

▶

The fitness function is the only part of a genetic algorithm that knows anything about the problem being solved. Selection, crossover and mutation are generic machinery; they shuffle and perturb strings of symbols without any understanding of what those symbols mean. All of the problem knowledge — the objectives, the constraints, the trade-offs, the definition of "better" — enters the algorithm through a single interface: a function that takes a chromosome and returns a number. Because of this, the quality of a GA's results is bounded far more tightly by the quality of its fitness function than by any parameter setting. A beautifully tuned algorithm with a badly shaped fitness function will reliably and efficiently converge on something useless. This topic examines how fitness is computed, how to shape it so that it actually guides search, how to handle constraints and multiple objectives, what to do when evaluation is noisy, and how to validate the function before trusting its output.

The Role of the Fitness Function

Evaluation is a two-step process: decoding followed by scoring. The chromosome is the genotype — the internal encoding the operators manipulate. It is rarely a direct description of a solution. A bitstring 1011001 might decode to the real number 3.47; a permutation [4,1,3,2,5] might decode to a route visiting cities in that order; an integer vector might decode to a machine assignment for each job in a schedule. Decoding builds the phenotype, the actual candidate solution in the problem domain. Scoring then measures that phenotype against the objectives: total route length, makespan, classification accuracy, portfolio return. Keeping these two steps conceptually separate pays off, because changing representation (say from binary to real-valued) should only require changing the decoder, not the scoring logic.

A worked example makes the separation concrete. Suppose we are solving a 0/1 knapsack problem with capacity 15 and the following items:

ItemWeightValue
A612
B59
C47
D814
E35

A chromosome is a 5-bit string, one bit per item. Decoding 10101 gives the item set {A, C, E}; scoring gives weight 13 (feasible) and value 24. Decoding 11011 gives {A, B, D, E} with weight 22 — over capacity — and here the fitness function must still return something sensible rather than crashing or returning an undefined value.

That last point generalises into a hard requirement: the fitness function must be total over the search space the operators can reach. Crossover and mutation are blind; they will produce chromosomes that encode duplicate cities, negative durations, empty solutions, all-zero bitstrings, parameter values outside the intended range, and tree expressions that divide by zero. Every one of these must yield a number. If the function throws an exception on an edge case, the run dies mid-experiment, often after hours. If it returns NaN or infinity, comparison operators behave unpredictably and selection silently breaks — roulette wheel selection with a single infinite fitness will pick the same individual forever. Defensive practice is to clamp outputs to a finite range, handle protected division (return 1 for x/0 in genetic programming), and give degenerate individuals a very poor but finite score. Writing a handful of deliberately malformed chromosomes as unit tests for the evaluator is cheap insurance.

Efficiency matters more here than anywhere else in the algorithm. Consider a modest run: population 200, 500 generations, 10 independent repetitions for statistical confidence. That is one million evaluations. If each evaluation takes 10 milliseconds, the run takes under three hours; if it takes one second, it takes eleven and a half days. Meanwhile, the combined cost of all the selection, crossover and mutation operations is usually under 5% of total runtime. Optimising the evaluator is therefore almost always the correct target for performance work.

Several techniques reduce evaluation cost:

  • Caching (memoisation). Store evaluated chromosomes in a hash map keyed by the genotype. In later generations, when the population has converged and many individuals are duplicates, cache hit rates of 40–70% are common, effectively halving runtime for free. The cache also gives a useful free diagnostic: the ratio of unique genotypes to population size is a direct measure of diversity.
  • Incremental (delta) evaluation. If a mutation changes only a small part of the solution, recompute only the affected contribution. In a TSP tour, a 2-opt move that reverses a segment changes exactly two edges; the new tour length is old_length - d(a,b) - d(c,d) + d(a,c) + d(b,d), an O(1) update instead of an O(n) re-sum. For a 1000-city instance that is a thousandfold saving per mutated individual. Incremental evaluation requires the operators and the evaluator to cooperate, which breaks the clean separation above, so it is worth doing only when profiling shows it matters.
  • Surrogate models (fitness approximation). When true evaluation involves a finite-element simulation, a CFD run, or training a neural network, each evaluation may take minutes or hours. A surrogate — a regression model such as a Gaussian process, radial basis function network, or gradient-boosted tree — is trained on the evaluations performed so far and used to screen candidates cheaply. Only the most promising individuals, or a fixed fraction per generation, are sent for true evaluation, and those results are fed back to retrain the surrogate. The risk is that the GA learns to exploit errors in the surrogate, converging on a region the model wrongly rates highly; periodic true evaluation of the apparent best individuals guards against this.
  • Parallel evaluation. Fitness evaluations within a generation are independent, making them embarrassingly parallel. A population of 200 on 8 cores gives close to an 8× speedup with minimal engineering effort.
  • Early termination. If a candidate's partial score already guarantees it will rank below any plausible survivor, stop evaluating it. In a simulation-based evaluation, abort runs that have already accumulated disqualifying failures.

Finally, fitness values are fundamentally ordinal and relative, not absolute statements of correctness. Selection operators care about which individual is better than which, and (for proportional selection) by how much relative to the population. A fitness of 0.83 means nothing on its own; it means something only in comparison to the 0.79 and 0.91 of its competitors. This has practical consequences. There is no need to normalise fitness to [0,1] for its own sake. It is legitimate for fitness to be an arbitrary positive number, as long as comparisons are meaningful and consistent throughout the run. Conversely, a fitness function whose values depend on something that changes across generations — a random test subset, a time-dependent constant, an adaptive penalty coefficient — makes comparisons between generations invalid, and elitism in particular must be handled carefully in that situation (see the discussion of noisy fitness below).

Designing a Discriminating Fitness Landscape

The fitness function does not merely rank solutions; it defines a landscape over the search space, and the shape of that landscape determines whether a GA can navigate it. The single most common design failure is all-or-nothing fitness: 1 if the solution is correct, 0 otherwise. Imagine evolving a 30-bit string to match a hidden target, scored as "1 if all bits match, else 0". The landscape is a flat plain with a single invisible spike. Selection has nothing to prefer, so the GA degenerates into random sampling of a space of 2³⁰ ≈ 10⁹ points. Replace the score with "number of matching bits" and the same problem becomes trivial — a gradient now exists everywhere, each generation accumulates correct bits, and the target is typically found in a few hundred generations with a modest population.

The design principle is therefore to reward partial progress. Concrete illustrations:

  • Timetabling. Instead of "valid timetable = 1, invalid = 0", count violations: number of double-booked rooms, number of lecturer clashes, number of oversubscribed rooms. Fitness becomes a graded measure that distinguishes a timetable with 3 clashes from one with 40, and crossover can combine the clash-free portions of two parents.
  • Symbolic regression. Instead of "expression exactly reproduces the data", use negative mean squared error over the training points. Near-misses are rewarded in proportion to how near they are.
  • Robot control. Instead of "reached the goal", reward distance travelled toward the goal, time survived, or fraction of the course completed. This "behavioural shaping" is what lets evolution bootstrap complex behaviour from random initial controllers.
  • Game playing. Instead of win/loss, incorporate material advantage, board position score, or number of moves survived, so that a strategy that loses on move 60 ranks above one that loses on move 8.

Shaping fitness is not risk-free, which brings us to deception. A landscape is deceptive when the gradient — the direction in which fitness improves locally — leads systematically away from the global optimum. The classic textbook case is the minimal deceptive problem and, more vividly, a "trap function" on bitstrings: fitness equals the number of ones, except that the all-zeros string scores higher than everything, including the all-ones string. Every local improvement step adds a one, marching the population straight to the all-ones deceptive attractor and away from the true optimum. Real problems exhibit softer versions of this. In a vehicle routing problem, penalising route length alone may push every vehicle toward short local loops that make a globally efficient assignment unreachable. In a neural controller, rewarding forward distance may produce a robot that falls forward rather than one that learns to walk. Deception cannot be eliminated in general — no fitness function is universally well-behaved — but it can be mitigated by using representations where building blocks that work well together are encoded close to one another, by maintaining diversity so the population explores several basins at once, by multi-objective formulations that do not collapse conflicting signals into one scalar, and by novelty or diversity rewards that explicitly value exploring unvisited regions.

Plateaus and neutral regions are the complementary pathology. A plateau is a large connected region of equal fitness. Selection is blind within it: all individuals look equally good, so selective pressure drops to zero and the population drifts randomly until some individual happens to step off the edge onto higher ground. Plateaus arise naturally from integer-valued fitness — "number of constraint violations" takes few distinct values once the population is good, so late in the run most individuals score 2 or 1 and are indistinguishable. Remedies include adding a secondary, finer-grained term as a tie-breaker (for example, total violation magnitude in addition to violation count, or a small bonus for shorter programs in genetic programming), weighting different violation types by severity so that counts rarely collide, or introducing a continuous component such as slack from a constraint boundary. Note that a small amount of neutrality is not always harmful: neutral drift can let a population cross a valley in genotype space without a fitness cost, and some evolutionary theories argue this aids escape from local optima. The problem is large neutrality that consumes the whole run.

Before launching an expensive run, hand-score a small set of solutions. Construct by hand: an obviously excellent solution, an obviously terrible one, a mediocre one, a boundary case (exactly at the constraint limit), and a pathological one (empty, all-identical, maximally violating). Compute fitness for each by hand or by calling the evaluator directly, and ask whether the ordering matches your intuition and whether the gaps are sensible. A typical discovery at this stage is that a penalty term swamps the objective, so that a feasible solution with poor objective value outranks every near-feasible excellent one — or the reverse. Another is that two visibly different solutions receive identical scores, revealing a plateau. Fixing these on paper costs minutes; discovering them after a 10-hour batch of runs costs a day.

Fitness Scaling and Selective Pressure

Selective pressure is the degree to which better individuals out-reproduce worse ones. Fitness-proportional (roulette wheel) selection makes an individual's expected number of offspring equal to f_i / f̄, its fitness divided by the population mean. This couples pressure directly to the raw numeric spread of fitness values, and that spread changes dramatically over the course of a run — producing two opposite failure modes.

Early premature convergence. In generation 1 the population is random, and occasionally one individual is far better than the rest. Consider a population of 100 where 99 individuals score around 10 and one scores 400. The mean is about 13.9, so the super-individual expects 400/13.9 ≈ 29 offspring in a single generation, and its descendants dominate within three or four generations. Diversity collapses, crossover between near-identical parents produces no new material, and the run stalls at a local optimum that was merely the best lucky draw in the initial sample.

Late stagnation. By generation 300 the population has converged and fitness values are, say, 998.2, 998.5, 998.9, 999.1. The ratio of best to average is 1.0004, so every individual gets essentially one offspring. Selection has become effectively random and the search drifts rather than refines. This is the "loss of discrimination" problem, and it is exactly when fine-grained exploitation is most needed.

Scaling transforms raw fitness into selection fitness to control this. The main schemes:

  • Linear scaling. Apply f' = a·f + b with a and b chosen each generation so that the scaled average equals the raw average (f̄' = f̄, preserving expected reproduction for average individuals) and the scaled best equals C·f̄, where C is a target best-to-average ratio, typically 1.2 to 2.0. This directly bounds the super-individual's advantage. Worked example with raw values {10, 10, 10, 400}, f̄ = 107.5, and C = 2: we need f'_max = 215 and f̄' = 107.5. Solving a·400 + b = 215 and a·107.5 + b = 107.5 gives a ≈ 0.3675, b ≈ 68.0. The super-individual now expects 2 offspring instead of 29. The practical wrinkle is that linear scaling can produce negative scaled values for very poor individuals when the spread is wide; the standard fix is to detect this and instead map the minimum to zero, accepting a lower effective C for that generation.
  • Sigma truncation. Compute f' = max(0, f − (f̄ − c·σ)) where σ is the population standard deviation and c is typically 2. Individuals more than c standard deviations below the mean get zero selection fitness and are eliminated; the rest are shifted. This handles outliers in both directions more gracefully than raw linear scaling and avoids negative values by construction. It is particularly useful when the objective can take negative values, which breaks naive roulette wheel selection.
  • Power-law scaling. Use f' = f^k. With k > 1 the pressure is amplified, which is the remedy for the late-run compressed-range problem: raising 998.2 and 999.1 to a high power exaggerates the small difference. With k < 1 pressure is reduced. Some implementations vary k over the run (low early for exploration, high late for exploitation), which is a crude but effective form of annealed selective pressure. The weakness is that a good value of k is problem-dependent and sensitive to the absolute magnitude of fitness values.
  • Rank-based fitness. Sort the population and assign selection fitness from rank alone, discarding raw magnitudes. With linear ranking, the best individual receives an expected s offspring and the worst 2 − s, where s ∈ (1, 2]; the common choice s = 1.5 to 2.0. Because the assignment depends only on ordering, selective pressure is constant throughout the run, immune both to the generation-1 super-individual and to the generation-300 compression. Exponential ranking (fitness proportional to q(1−q)^rank) gives a sharper profile. The cost is loss of magnitude information: an individual that is ten times better than the runner-up gets treated the same as one that is marginally better, which can slow exploitation of a genuine breakthrough. Sorting also costs O(n log n) per generation, negligible in practice.

This is a large part of why tournament selection has displaced roulette wheel selection as the default in practice — scaling is an extra mechanism that exists mainly to repair a weakness of proportional selection.

A separate but essential mechanical point: minimisation must be converted to maximisation. Most selection operators assume larger is better, and roulette wheel selection additionally requires non-negative values. If the raw objective is a cost to be minimised (makespan, tour length, error), the standard conversions are:

  • f = C_max − cost, where C_max is a constant at least as large as any cost encountered — for instance the worst cost in the current population, or a fixed generous upper bound. Using the population maximum makes the mapping generation-dependent, which is fine for selection but means fitness values are not comparable across generations; always log the raw cost as well.
  • f = 1 / (1 + cost), which is always positive and bounded, but compresses differences among good solutions non-uniformly (costs of 1 and 2 map to 0.5 and 0.333, a big gap; costs of 100 and 101 map to values differing by 0.0001, almost no gap). This is convenient but introduces a hidden, cost-magnitude-dependent change in selective pressure.
  • Simple negation, f = −cost, which is perfectly acceptable for rank-based or tournament selection and avoids all distortion. This is the cleanest option when proportional selection is not being used.

Constraint Handling: Penalties and Repair

Most real optimisation problems are constrained: knapsacks have capacities, schedules have precedence relations and resource limits, designs have stress and cost limits, routes have time windows. The genetic operators know nothing about these constraints, so crossing two feasible parents routinely yields infeasible children. There are four broad families of response.

1. Penalty functions. Evaluate the solution normally, then subtract a cost reflecting constraint violation. The general form for a minimisation problem is:

fitness(x) = objective(x) + Σ_j  w_j · violation_j(x)^β

where violation_j measures the amount by which constraint j is breached (not merely whether it is breached), w_j is a weight, and β is commonly 1 or 2. Measuring degree rather than occurrence is crucial: it restores the gradient discussed earlier, so that a solution exceeding capacity by 1 unit is clearly preferred to one exceeding it by 40, and the population can slide toward feasibility rather than jumping blindly.

Returning to the knapsack example with capacity 15, suppose the penalty is w · max(0, weight − 15) with the objective being value to maximise, so fitness = value − penalty:

ChromosomeItemsWeightValueExcessFitness (w = 1)Fitness (w = 10)
10101A, C, E132402424
11001A, B, E142602626
11100A, B, C152802828
11101A, B, C, E18333303
11111all26471136-63

This table shows the whole tension in a single picture. With w = 1 the penalty is too mild: the all-items chromosome scores highest, so the population will converge on grossly infeasible solutions and never produce a usable answer. With w = 10 feasible solutions win, but the near-feasible 11101 — which is only one bit-flip away from the optimum 11100 and carries the useful genetic material of the three best items — is crushed to a fitness of 3, below every feasible solution including poor ones. If the weight were raised to 20, near-feasible individuals would be driven out of the population entirely, and the search would be confined to the strict interior of the feasible region. In many constrained problems the optimum lies on the constraint boundary, so a population that never approaches the boundary from outside loses a valuable approach route. This is the central dilemma of penalty design: too harsh and you discard useful genetic material near the boundary, effectively reducing the method to a death penalty; too mild and infeasible solutions dominate because violating a constraint is a cheap way to buy objective value.

Three strategies manage that dilemma:

  • Static penalties fix w_j for the whole run. Simple and reproducible, but the right value depends on the instance, and a weight tuned for one problem size is usually wrong for another. A useful heuristic is to scale weights so that the maximum plausible penalty is of the same order as the range of the objective — compute the objective spread in a random sample, compute the violation spread, and set w as the ratio. A second heuristic is the "minimum penalty rule": the penalty should be just large enough that repairing a violation is always worth more than the objective gain that the violation buys.
  • Dynamic penalties increase w as a function of generation number, for example w(t) = (c·t)^α. Early in the run the penalty is weak, so the population can roam freely across the feasible boundary and exchange material with infeasible regions; late in the run the penalty is severe, forcing convergence into the feasible region. This mirrors the exploration-then-exploitation arc of the algorithm as a whole, and is often markedly more effective than any single static weight.
  • Adaptive penalties adjust w based on feedback from the search itself. A common rule monitors the proportion of feasible individuals over the last k generations: if all of the best individuals have been feasible, decrease w (the search is being over-constrained and should be allowed to explore the boundary); if none have been feasible, increase w; otherwise leave it unchanged. This keeps the population straddling the boundary, which is empirically where good solutions to tightly constrained problems are found. The price is that fitness values are no longer comparable across generations, so elitism must compare re-evaluated scores and reporting must use the raw objective.

2. Repair operators. Rather than punishing an infeasible chromosome, transform it into a feasible one. For the knapsack, a repair routine removes items in increasing order of value-to-weight ratio until the capacity constraint holds: chromosome 11111 (weight 26) loses D (ratio 1.75), then C (1.75), then B (1.80), yielding 10001 = {A, E}, weight 9, value 17 — feasible, and derived greedily from the original. For a timetable, a repair pass moves clashing events to the nearest free slot. For a permutation produced by a crossover that duplicated cities, a repair pass replaces duplicates with the missing ones.

An important design choice is Lamarckian versus Baldwinian repair. In the Lamarckian approach the repaired chromosome replaces the original in the population, so the repair is inherited. In the Baldwinian approach the repaired version is used only to compute fitness, while the original (infeasible) chromosome stays in the population and is passed to the operators. Lamarckian repair converges faster but can reduce diversity sharply, because many distinct infeasible genotypes collapse onto the same repaired phenotype. Baldwinian repair preserves the genotypic variety, at the cost of slower progress. A common compromise is to write back the repaired chromosome with some probability (say 0.1–0.3). A further caution: deterministic greedy repair introduces a strong bias — in the knapsack example, low-ratio items are systematically evicted, so solutions that require an unusual combination may be unreachable. Randomised repair (remove random items until feasible) avoids the bias but loses the quality boost.

3. Decoders and specialised encodings. The most elegant answer is to make infeasibility impossible to represent. A decoder interprets any chromosome as instructions for constructing a feasible solution, so every point in the genotype space maps to a valid phenotype. For the knapsack, a chromosome can be a permutation of items; the decoder walks the permutation adding each item if it fits and skipping it otherwise. Every permutation yields a feasible packing, the search space is closed under all permutation operators, and no penalty or repair is needed. Similarly, a permutation representation for the TSP makes "visit every city exactly once" structurally guaranteed, and a random-key representation (real values sorted to produce an ordering) permits standard real-valued operators while preserving feasibility. For job-shop scheduling, an operation-based encoding where each job index appears exactly as many times as it has operations guarantees that any decode respects precedence. The trade-offs are that the decoder adds computational cost to every evaluation, that the genotype-to-phenotype mapping is many-to-one (several chromosomes decode to the same solution, which enlarges the effective search space and creates neutrality), and that the mapping can distort the landscape so that a small genotype change produces a large phenotype change, weakening the locality that crossover relies on. Specialised encodings handle only the constraints they were designed for; a capacity constraint handled by a decoder still leaves time-window constraints to a penalty, so hybrid schemes are common.

4. Death penalty. Assign zero (or worst-possible) fitness to any infeasible individual, or discard it and regenerate. This is the simplest method and is defensible when feasible solutions are easy to find and the feasible region occupies a substantial fraction of the space. It fails badly when feasibility is rare: in a tightly constrained scheduling problem, 99% of random chromosomes may be infeasible, so 99% of evaluations are spent producing identical zero scores. The population carries no gradient information toward feasibility, offspring of two feasible parents are usually killed, and the search effectively becomes random restart. The death penalty also throws away the near-boundary individuals that are most informative. As a diagnostic, log the proportion of infeasible individuals per generation; if it stays above roughly 50% with a death penalty, switch to a graded penalty, repair, or a decoder.

Multi-Objective Fitness Evaluation

Real problems rarely have a single objective. A delivery schedule should minimise cost and minimise lateness and balance driver workload. A structural design should minimise mass and maximise stiffness. These objectives conflict: improving one degrades another, and there is no single "best" solution, only a set of best compromises.

Weighted-sum aggregation is the simplest response: collapse the objectives into one scalar, f = w₁·f₁ + w₂·f₂ + … + wₘ·fₘ, and run an ordinary single-objective GA. It is easy, fast, and compatible with every standard operator. Its difficulties are substantial, though. First, the weights encode a value judgement that must come from the problem owner; choosing w₁ = w₂ = 1 is not "neutral", it is a specific and usually arbitrary trade-off claim. Second, and more subtly, a weighted sum can only find solutions on the convex portion of the trade-off surface; points in a concave region are never optimal for any weight vector, so entire families of sensible compromises become invisible. Third, running the GA once gives one solution; exploring the trade-off requires re-running with many weight vectors.

Normalisation is mandatory whenever objectives have different units or magnitudes. Suppose cost is measured in pounds (range 50,000–90,000) and lateness in hours (range 0–40). With equal weights, a £1,000 cost change outweighs the entire lateness range; the second objective is decorative. The standard fix is min–max normalisation to [0,1] using estimated or observed bounds:

f_norm = (f - f_min) / (f_max - f_min)

applied to each objective before weighting, with minimised objectives first converted (1 - f_norm) so larger is always better. Bounds may be taken from domain knowledge, from a preliminary random sample, or from the current population (the latter makes fitness generation-dependent again). A worked comparison: candidate A costs £60,000 with 30 hours lateness; candidate B costs £75,000 with 5 hours lateness. Un-normalised with equal weights and minimisation, A scores 60,030 and B scores 75,005, so A wins by a landslide driven entirely by units. Normalised, A scores 0.25 + 0.75 = 1.00 and B scores 0.625 + 0.125 = 0.75, so B wins — a result that actually reflects a balanced trade-off.

Pareto-based approaches avoid collapsing the objectives at all. Solution a dominates solution b if a is at least as good as b on every objective and strictly better on at least one. Solutions that nobody dominates form the non-dominated set, and the true such set is the Pareto front. Consider five schedules, both objectives minimised:

P, Q and R represent genuinely different compromises and none is objectively better than the others; S and T are simply worse than something else and can be discarded. A Pareto-based GA uses dominance to assign fitness — for example by non-dominated sorting, where the non-dominated individuals form front 1, removing them and recomputing gives front 2, and so on, with front index acting as the primary rank.

NSGA-II is the canonical algorithm of this kind. Each generation it combines parents and offspring, sorts them into fronts, and fills the next population front by front. When a front does not fit entirely, it selects within that front using crowding distance: for each objective, solutions are sorted and each one is assigned the normalised gap between its two neighbours, summed across objectives; boundary solutions get infinite distance. Individuals in sparse regions have large crowding distance and are preferred, which spreads the population evenly along the front instead of letting it bunch in one attractive region. The selection comparison operator is therefore lexicographic: lower front rank wins; ties broken by larger crowding distance. Related mechanisms include fitness sharing (reducing an individual's fitness in proportion to how many neighbours lie within a niche radius σ_share) and, in SPEA2, nearest-neighbour density estimates. Newer algorithms such as MOEA/D decompose the problem into many scalarised subproblems solved cooperatively, and NSGA-III uses reference points to maintain spread when there are four or more objectives, where crowding distance becomes unreliable.

Lexicographic ordering suits problems where the objectives have a strict, agreed priority. Optimise objective 1 alone; among solutions tied (or within a tolerance ε) on objective 1, optimise objective 2; and so on. In an exam timetable, hard constraint violations might be objective 1, student travel burden objective 2, and room utilisation objective 3 — no amount of improved room utilisation should ever justify one extra clash. Implementation in a GA is easy with tournament selection: compare two individuals on objective 1, and only if they are equal (or within tolerance) move to objective 2. The risk is that strict lexicographic comparison creates plateaus and effectively ignores lower-priority objectives once the top one becomes finely discriminating; the ε-tolerance variant mitigates this.

A crucial practical point about Pareto methods: the output is a set, not a single answer. A run of NSGA-II on the schedule problem might return forty non-dominated schedules spanning £58k/40h to £82k/2h. The algorithm deliberately does not choose between them, because that choice depends on preferences it was never given. The decision-maker then inspects the front — often as a plotted trade-off curve — and selects, perhaps noticing a "knee" where a small additional cost buys a disproportionate lateness reduction. This is a strength, not an omission: it defers the value judgement until after the trade-offs are known, rather than requiring the weights to be guessed in advance.

Noisy and Uncertain Fitness

Many evaluations are stochastic. A schedule evaluated against simulated demand, a trading strategy tested on a random sample of market days, a robot controller assessed in a simulator with random initial conditions, or a classifier scored on a random data subsample — all return a different number each time they are called on the same chromosome. The measured fitness is then f̂(x) = f(x) + ε. Noise is dangerous in a GA for a specific reason: selection systematically favours individuals whose noise term happened to be positive. A mediocre individual with a lucky draw displaces a genuinely better individual with an unlucky one, and because elitism preserves high measured scores, lucky mediocrities can occupy the elite slots indefinitely while their true quality is never re-tested.

Mitigations, roughly in order of cost:

  • Averaging multiple samples. Evaluate each individual n times and use the mean. The standard error falls as σ/√n, so cutting noise in half requires four times the evaluations and cutting it to a tenth requires a hundred times. This quadratic cost means naive averaging is affordable only for small n; with a fixed evaluation budget there is a direct trade-off between evaluating more individuals and evaluating each one more accurately. Empirically, a modest n (3–5) combined with a larger population usually beats a large n with a small population.
  • Adaptive / sequential sampling. Spend evaluations where they change decisions. Give every individual one or two samples, then allocate extra samples only to individuals whose confidence intervals overlap with those of their competitors, or only to the top candidates competing for elite status. If an individual is clearly poor after two samples, no further evaluation can change its fate, so stop. Techniques such as racing and optimal computing budget allocation formalise this, and simple versions (resample only the current top 10%) capture most of the benefit for a few lines of code.
  • Larger populations. A GA averages implicitly. Noise affects individual selection events, but with a large population the many similar individuals that share a successful building block collectively carry a more reliable signal than any one of them; errors in individual comparisons partially cancel. Increasing population size is often a more efficient use of a fixed budget than increasing resampling, and it also preserves the diversity that noise tends to erode.
  • Re-evaluating elites. If the elite individual's stored score was an overestimate, keeping that stale score lets it dominate forever. Re-evaluating elites each generation (and either replacing the stored value or updating a running average over all samples ever taken of that genotype) causes inflated scores to regress toward the truth within a few generations. Maintaining a running mean plus sample count per genotype is a cheap and very effective implementation. A side effect to accept: the reported "best fitness" curve will no longer be monotonically increasing, which is correct behaviour under noise rather than a bug.
  • Deliberate perturbation for robust design. Sometimes noise is not an obstacle but the point. If the manufactured version of a design will differ slightly from the specification, or the schedule will face unexpected machine breakdowns, then a brittle optimum that collapses under small perturbation is worthless. Evaluating each individual under several randomly perturbed conditions and scoring by mean performance — or by a risk-averse statistic such as the worst case, the 10th percentile, or mean − λ·standard deviation — explicitly selects for solutions whose quality is insensitive to variation. This typically trades a few percent of nominal performance for a large gain in reliability, and the choice of statistic encodes how risk-averse the decision-maker is.

Validating and Tuning the Fitness Function

A GA will optimise exactly what you measure, which is frequently not what you meant. Validation is therefore a necessary stage, not an optional refinement.

Inspect the best individuals. After a short exploratory run, decode the top few chromosomes and examine the actual solutions, not just their scores. This is how specification bugs are caught, and the literature on "reward hacking" is full of examples: a scheduler that achieves zero lateness by assigning no jobs; a route optimiser that drives through a lake because the distance matrix was Euclidean; a controller that exploits a simulator's physics to gain energy from a collision; a classifier that scores perfectly by predicting the majority class because the metric was raw accuracy on imbalanced data. In every case the fitness function was computed correctly and the GA did its job faultlessly — the specification was wrong. Only inspection reveals this.

Plot best, average and worst fitness per generation. These three curves diagnose most pathologies:

Pattern observedLikely causeRemedy
Average rises to meet best within a few generations, then all curves flattenPremature convergence from excessive selective pressureScaling, rank or lower-k tournament selection, higher mutation, larger population
Best improves but average stays far below and erraticPressure too low, or mutation too destructiveIncrease pressure; reduce mutation rate; check crossover is producing viable offspring
All curves flat from generation 1All-or-nothing fitness or a vast plateauAdd graded partial-credit terms and tie-breakers
Best fitness decreases at some generationsNo elitism, or noisy evaluation with re-evaluated elitesAdd elitism; if noise, this is expected — track running means
Steady improvement then sudden plateau at a suspiciously round valueFitness clipped or dominated by a saturated penalty termInspect component values separately for the best individual

Logging the components of fitness separately — raw objective, each penalty term, each sub-objective — is far more informative than logging the aggregate alone, and costs nothing.

Compare against baselines. Two baselines are indispensable. The first is random search given the same number of evaluations: generate N random chromosomes, evaluate, keep the best. If the GA cannot beat this, the algorithm is contributing nothing and the landscape, the representation or the operators are broken. The second is a simple domain heuristic — greedy value-to-weight packing for the knapsack, nearest-neighbour plus 2-opt for the TSP, earliest-due-date dispatching for a schedule. A GA that fails to beat a five-line greedy rule is not worth its complexity. Both baselines should be reported with the GA results, and all should be compared over multiple independent runs with means, standard deviations and ideally a statistical test, since a single run tells you little about an inherently stochastic method.

Separate internal fitness from the reported objective. The number used to drive selection may include penalties, scaling, normalisation and multi-objective weights; the number reported to a stakeholder must be the actual, meaningful quantity — the true makespan in hours, the true cost in pounds, together with a statement of whether the solution is feasible. Mixing these is a common and embarrassing error: reporting "fitness 0.87" says nothing, and reporting a penalised score as if it were a cost understates the solution's quality or hides an infeasibility. A clean implementation returns a small record from the evaluator, for example:

Evaluation {
  objective:   28.0     # true value, reported to the user
  violations:  [0, 2]   # per-constraint violation magnitudes
  feasible:    false
  fitness:     8.0      # internal, used only for selection
}

Keeping these fields distinct also makes caching, logging and post-run analysis straightforward, because the raw objective remains available no matter how the internal fitness is later rescaled.

Change one thing at a time. Fitness functions accumulate parameters quickly: a penalty weight per constraint, a scaling constant, a set of objective weights, a sampling count. These interact, so simultaneous changes make attribution impossible — if you double the penalty weight and switch to rank selection at the same time and results improve, you have learned nothing about either. Disciplined tuning means fixing a random-seed set, varying one parameter across a small sweep of values, running several repetitions per value, and recording the mean and spread of final objective values before moving to the next parameter. Keep a short experiment log with the parameter set, the seeds, and the outcome. When several parameters genuinely must be explored together, use a structured design (a small grid, Latin hypercube sampling, or an automated tuner such as irace or SMAC) rather than ad hoc fiddling, and always validate the chosen configuration on problem instances that were not used for tuning, otherwise the parameters are simply overfitted to one instance.

Taken together, these practices turn the fitness function from an afterthought into the engineering centrepiece of the algorithm. Decode cleanly, score every reachable individual, grade partial progress, control selective pressure by scaling or rank, handle constraints in a way that keeps the boundary accessible, be explicit about multiple objectives, respect noise, and validate against both intuition and baselines. A GA built on a fitness function designed this way will usually work with default parameters; one built on a poorly designed fitness function will not work with any.

A genetic algorithm has no understanding of the problem you are solving — all it knows is the number your fitness function returns. That single number decides which individuals survive, which get to reproduce, and therefore where the search goes next. Designing it well is the difference between a GA that converges on a genuinely good solution and one that wanders, stalls, or cheerfully optimises the wrong thing.

This topic works through what a fitness function must do: give a graded signal (not just pass/fail) so the algorithm can tell a near-miss from a disaster, shape a landscape that rewards partial progress, and control selective pressure through scaling so the population neither converges prematurely nor drifts aimlessly. It also covers the practical complications you meet in real problems — infeasible solutions handled by penalty terms or repair operators, several competing objectives that must be weighted or traded off, fitness values corrupted by noise or sampling, and the need to validate and tune your evaluation before trusting its results.
