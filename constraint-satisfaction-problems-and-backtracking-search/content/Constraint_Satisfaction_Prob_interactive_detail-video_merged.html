Foundations of Constraint Satisfaction Problems

▶

A great many problems that look superficially unrelated — colouring a map so that neighbouring regions differ, filling a Sudoku grid, placing queens on a chessboard, assigning lectures to rooms and timeslots, or deciding which digit each letter stands for in a puzzle like SEND + MORE = MONEY — turn out to share a single underlying shape. In each case there is a fixed collection of decisions to make, each decision has a limited set of possible outcomes, and certain combinations of outcomes are forbidden. The constraint satisfaction problem (CSP) is the formalism that captures exactly this shape. Its power comes not from being able to express more than ordinary search can express — any CSP can be rewritten as a state-space search problem — but from the fact that it exposes the internal structure of a problem in a uniform way that a general-purpose solver can inspect, reason about, and exploit.

The CSP triple

Formally, a constraint satisfaction problem is a triple <X, D, C>. Each component has a precise role, and learning to separate them cleanly is the single most important modelling skill in this area.

X = {X1, X2, ..., Xn} is a finite set of variables. Each variable stands for one decision that the solver must make — exactly one, no more and no less. In map colouring, there is one variable per region: the decision "what colour does Western Australia get?" In Sudoku, there is one variable per cell: 81 decisions in total. In N-Queens, the usual formulation uses one variable per column, representing the decision "which row holds the queen in this column?" If you find yourself unable to say in plain English what question a variable answers, the model is probably wrong.

D = {D1, D2, ..., Dn} is the set of domains, one per variable, where Di is the set of values that Xi is permitted to take. Domains need not be identical across variables. In a timetabling problem, the variable Lecture-Hall-for-CS101 might range over {A1, A2, B7} while Timeslot-for-CS101 ranges over {Mon9, Mon11, Tue9, ...}. Choosing the domain is itself a modelling decision: by declaring that a Sudoku cell ranges over {1..9} you have already built the rule "every cell holds a digit from 1 to 9" into the representation, so it never needs to be written as a constraint.

C = {C1, C2, ..., Cm} is the set of constraints. Each constraint restricts the combinations of values that some subset of the variables may take simultaneously. A single constraint says nothing about variables outside its subset; the global effect of the problem emerges from how the constraints interlock.

Constraints as (scope, relation) pairs

The standard way to write a constraint is as a pair (scope, rel):

  • The scope is an ordered tuple of the variables the constraint talks about, for example (X1, X2). The number of variables in the scope is the constraint's arity.
  • The relation defines which tuples of values, drawn from the corresponding domains, satisfy the constraint. Formally it is a subset of the Cartesian product D1 × D2 × ... over the scope's variables.

A relation can be given in two equivalent styles. Extensionally (explicitly), it is simply a list of the permitted tuples. Intensionally (implicitly), it is a predicate or arithmetic expression that a tuple must satisfy. Suppose X1 and X2 both have domain {A, B} and we want them to differ:

Extensional form:  ((X1, X2), {(A, B), (B, A)})
Intensional form:  ((X1, X2), X1 != X2)

Both describe the same relation. The extensional form is explicit and easy for a solver to test by table lookup, but it grows as the product of the domain sizes: a binary constraint over two variables with 100 values each could require up to 10,000 tuples. The intensional form is compact and is the only practical option when domains are large, but it requires the solver to evaluate a predicate. Real constraint toolkits support both, plus a library of named global constraints such as AllDifferent(X1, ..., Xk), which is intensionally defined and whose extensional expansion would be astronomically large.

A worked miniature will make the triple concrete. Consider colouring three mutually adjacent regions with two colours:

X = {R1, R2, R3}
D = {D_R1 = {red, green}, D_R2 = {red, green}, D_R3 = {red, green}}
C = { ((R1,R2), R1 != R2),
      ((R2,R3), R2 != R3),
      ((R1,R3), R1 != R3) }

This CSP has 23 = 8 complete assignments and no solution: three mutually adjacent regions require three colours. Notice how the formalism makes the unsatisfiability a property of the stated constraints rather than of some hidden procedure — a solver can in principle prove it, and later in the module you will see techniques that detect such failures without enumerating all eight assignments.

Assignments: partial, complete, consistent, solution

An assignment is a mapping from variables to values, where each assigned variable receives a value from its own domain. Four qualifiers on assignments are used constantly, and they are independent of one another in ways that beginners often confuse.

  • A partial assignment leaves at least one variable in X unassigned. Written as a set of variable–value pairs, {R1 = red} is partial when X contains three variables. Partial assignments are the normal state of affairs during search: a backtracking solver spends virtually all of its time holding a partial assignment and deciding how to extend it.
  • A complete assignment gives every variable in X exactly one value. "Complete" says nothing whatever about legality — {R1 = red, R2 = red, R3 = red} is complete and badly broken.
  • A consistent (or legal) assignment violates no constraint among the variables that have been assigned. The qualification matters enormously: a constraint whose scope includes an unassigned variable is simply not yet evaluated, so it cannot be violated. Thus {R1 = red} is consistent, and so is {R1 = red, R2 = green}, even though no extension of the latter can succeed.
  • A solution is an assignment that is both complete and consistent. For the three-region two-colour CSP above, no such assignment exists, and the problem is called unsatisfiable or inconsistent.

One subtlety deserves emphasis. Consistency of a partial assignment is a local, cheap, syntactic check — "do the constraints I can currently evaluate hold?" It is not the same as extensibility — "can this partial assignment be grown into a full solution?" Extensibility is as hard as solving the problem itself. The gap between the two is exactly where search effort is wasted, and the whole art of CSP solving consists of techniques (forward checking, arc consistency, good variable ordering) that narrow the gap by making a cheap test reject more hopeless partial assignments.

CSPs versus general state-space search

In classical state-space search — the framework behind breadth-first search, depth-first search, and A* — a problem is specified by an initial state, a successor function, a step-cost function, and a goal test. The goal test is an arbitrary black-box predicate: the algorithm calls isGoal(state) and receives true or false. It cannot ask why a state failed, which part of the state was responsible, or what would have to change. States themselves are opaque atoms with no declared internal structure.

A CSP replaces that black box with a white one. The state is a structured object — a partial assignment of values to named variables — and the goal test is nothing more than "all variables assigned, and all constraints satisfied." Because the constraints are explicitly listed and individually inspectable, four powerful consequences follow.

  • Early failure detection. A general search algorithm applying a black-box goal test to a problem with 50 decisions would have to construct a complete state before learning it was bad. A CSP solver tests consistency after every single assignment. If {R1 = red, R2 = red} is already illegal, every one of the assignments extending it is illegal too, and the whole subtree — potentially d^(n-2) leaves — vanishes from consideration with one test.
  • Wholesale pruning. Pruning in CSPs is not one node at a time but one region at a time. In a 50-variable problem with 10 values each, discovering a violation after the second assignment eliminates 1048 complete assignments at the cost of a single comparison. This is why backtracking search is feasible at all on problems whose raw combinatorics are hopeless.
  • Generic, domain-independent heuristics. Because the structure is uniform, one can define heuristics in terms of the formalism itself rather than in terms of the application. "Choose the variable with the fewest remaining legal values" (minimum remaining values) and "choose the value that rules out the fewest choices for neighbouring variables" (least constraining value) make sense for every CSP, with no knowledge of maps, digits, or machines. In ordinary state-space search, by contrast, an informative heuristic must be hand-crafted for each new problem.
  • Explainable failure. A refuted partial assignment comes with a reason: the specific constraint that was violated and the variables in its scope. Advanced solvers use this to perform backjumping — leaping back to the decision that actually caused the conflict rather than undoing the most recent one — and constraint learning, recording a new constraint that prevents the same conflict recurring elsewhere in the tree.

There is a further structural difference worth noting: in a CSP, paths do not matter. Two search paths that assign the same variables the same values in different orders reach the same state. The problem is commutative, which means a solver may fix the variable to branch on at each level and consider only values for that one variable, shrinking the search tree from n! · d^n leaves (if order mattered) to d^n. Also, solution depth is known in advance and is always n, so there is no need for iterative deepening or for worrying about infinite paths.

Why the formalism pays off

The practical argument for CSPs is one of separation of concerns. Modelling effort shifts from writing a bespoke algorithm for each new problem to writing a declarative description: name the decisions, list the options, state the rules. The solving machinery — backtracking, heuristics, constraint propagation — is written once and reused. A single implementation of backtracking search with the minimum-remaining-values heuristic will solve map colouring, Sudoku, cryptarithmetic puzzles, N-Queens, and job-shop scheduling without a line of change; only the <X, D, C> description differs. This is precisely the motivation behind industrial constraint-programming toolkits such as MiniZinc, Google OR-Tools, Gecode, and Choco: you write a model, the system supplies the search.

A second payoff is the dramatic collapse of the effective search space. The naive count of complete assignments is the product of the domain sizes, but constraints make most of that space unreachable. In 8-Queens, modelling one queen per column gives 88 = 16,777,216 complete assignments; adding the requirement that no two queens share a row (an AllDifferent constraint) reduces the candidate space to 8! = 40,320, a factor of 416 before any diagonal checking occurs. In a standard Sudoku, the raw count is 981 ≈ 1077, yet constraint propagation alone solves most newspaper puzzles with little or no search, because each clue cascades through the row, column, and box constraints and eliminates vast numbers of possibilities.

A third payoff is explanation and debugging. If a timetable is infeasible, a CSP solver can report "no value remains for Timeslot-for-CS101 given the current assignment, because of the room-capacity constraint and the lecturer-availability constraint." Contrast this with a bespoke procedural program returning null. Many solvers can extract a minimal unsatisfiable core — a smallest subset of constraints that is already contradictory — which tells a human modeller exactly which requirements to relax.

Domain types and why they matter

The character of a CSP, and the algorithms appropriate to it, depend heavily on the kind of domains involved.

Discrete and infiniteAll non-negative integers; all finite stringsNoConstraint language with special-purpose reasoning (e.g. integer linear arithmetic, bounds propagation)

Finite discrete domains are the main concern of this module. Here each Di is a finite set, so if the largest domain has size d and there are n variables, the number of complete assignments is at most d^n. This bound is exhaustively enumerable in principle but almost never in practice: with n = 30 and d = 5 there are about 9.3 × 1020 complete assignments, far beyond brute force. The bound nevertheless matters because it tells us the search tree has depth exactly n and branching factor at most d, which frames everything that follows. The general CSP over finite domains is NP-complete — 3-colourability and SAT reduce to it straightforwardly — so no polynomial algorithm is expected, and the realistic goal is to make the exponential as small as possible through pruning and ordering.

Discrete infinite domains arise naturally in scheduling with no fixed horizon: let StartJob1 be any non-negative integer number of days. One cannot write a constraint extensionally, because the table of permitted tuples would be infinite; constraints must be expressed in a constraint language, typically linear inequalities such as StartJob1 + 5 <= StartJob2. For linear constraints over integers, decision procedures exist (integer programming, and polynomial-time methods for some restricted fragments), but if arbitrary nonlinear integer constraints are permitted, the problem becomes undecidable — a consequence of the unsolvability of Hilbert's tenth problem. In practice, solvers either impose artificial finite bounds to recover a finite-domain problem, or reason symbolically over intervals rather than enumerating values.

Continuous domains appear whenever a decision is a real quantity: the exact start time of an observation, the flow rate in a pipe, the angle of a joint. Enumeration is meaningless here, and the appropriate machinery is mathematical optimisation. If both the constraints and the objective are linear, linear programming solves the problem in polynomial time; with integrality requirements added, one gets mixed-integer programming; with nonlinear relationships, convex or general nonlinear programming. A well-known example is scheduling the Hubble Space Telescope's observations, where continuous timing constraints are combined with discrete choices about which instrument to use — a hybrid model.

A final remark on the type of value, as distinct from the size of the domain: values may be Boolean (giving the special case known as SAT, propositional satisfiability), categorical/symbolic with no natural order (colours, machines), or numeric with order and arithmetic available (digits, times). Numeric domains let a solver reason about bounds — propagating that X < Y and Y <= 4 implies X <= 3 — without touching every value, which is why large numeric domains remain tractable in practice. Symbolic domains offer no such shortcut and must be handled value by value. Recognising which kind of domain you are modelling with therefore shapes not only the correctness of the model but the efficiency of every algorithm applied to it. Throughout the rest of this module the focus stays on finite discrete domains, for which depth-first backtracking search, augmented with consistency checking and ordering heuristics, is the standard and highly effective approach.

A constraint satisfaction problem, or CSP, is a way of describing a problem not by the steps you take to solve it but by the conditions a solution must satisfy. Formally a CSP is a triple: a set of variables, a domain of possible values for each variable, and a set of constraints that restrict which combinations of values are allowed. A solution is an assignment that is both complete (every variable has a value) and consistent (no constraint is violated); along the way a solver works with partial assignments that may be consistent so far but are not yet solutions.

This matters in the course because CSPs are our first example of a problem representation that exposes structure. In general state-space search, states are opaque black boxes and the only thing you can do is generate successors. In a CSP, the state is a set of variable assignments, so a solver can see which variables are still unassigned, how large their remaining domains are, and which constraints are already violated. That visibility is exactly what makes backtracking search, constraint propagation, and the ordering heuristics later in this module possible.

Constraint Types: Unary, Binary, and Global

Constraint Types: Unary, Binary, and Global

▶

A constraint satisfaction problem (CSP) is conventionally written as a triple <X, D, C>, where X = {X1, ..., Xn} is a set of variables, D = {D1, ..., Dn} gives each variable a domain of candidate values, and C is a set of constraints. Each constraint is itself a pair <scope, relation>: the scope is the tuple of variables the constraint talks about, and the relation specifies which combinations of values for those variables are permitted. The relation may be listed explicitly as a table of allowed tuples, or expressed compactly as a predicate such as X ≠ Y. The number of variables in the scope is the constraint's arity. Arity is the single most useful axis for classifying constraints, because it determines how the constraint is drawn in a diagram, how it is propagated, how expensive it is to check, and even which solving algorithms apply at all.

This topic works through the arity hierarchy from the simplest case upward: unary constraints on one variable, binary constraints on two, higher-order constraints on three or more (including the rich family of global constraints such as AllDiff), the hypergraph notation needed to draw them, standard transformations that reduce high-arity constraints to binary ones, and finally the shift from hard constraints to preference or soft constraints, which turns satisfaction into optimization.

The table below previews the hierarchy and will be unpacked in detail in the rest of the topic.

Unary constraints: restricting a single variable. A unary constraint has a scope of exactly one variable, so it is simply a statement about which values that variable may take, independently of everything else in the problem. Because the constraint mentions nothing else, nothing else can ever change whether it is satisfied. This gives unary constraints a privileged status: they can be compiled away entirely before search begins.

The procedure is direct. For each unary constraint with scope Xi, test every value v in Di against the constraint's relation and delete every value that fails. What remains is a reduced domain in which the unary constraint is satisfied by construction. Once this is done for all variables, the CSP is said to be node-consistent: every value in every domain satisfies all of that variable's unary constraints. Node consistency is the arity-1 member of the k-consistency family (arc consistency is the arity-2 member), and it is normally the very first preprocessing step a solver performs.

function NODE-CONSISTENCY(csp):
    for each variable Xi in csp.X:
        for each unary constraint c with scope (Xi):
            Di ← { v in Di : c.relation(v) is true }
        if Di is empty:
            return FAILURE        # the CSP has no solution at all
    return csp                    # now node-consistent

Consider the Australia map-coloring problem with variables {WA, NT, Q, NSW, V, SA, T} and the initial domain {red, green, blue} for each. Suppose a sponsor insists that South Australia must not be green, and that Tasmania must be blue. These are two unary constraints. Applying node consistency gives DSA = {red, blue} and DT = {blue}. The constraints themselves can now be deleted from C — they are permanently encoded in the domains. Because of this, a backtracking search never has to test them again: every value it can possibly choose for SA or T already respects them. This is a genuine efficiency gain, since a constraint check skipped at every node of a search tree with millions of nodes is millions of checks saved, and the smaller domains also shrink the branching factor.

Unary constraints turn up in three recurring forms:

  • Equality / fixed assignment: X = 3. This collapses the domain to a singleton. Every pre-filled clue in a Sudoku grid is exactly this kind of constraint; a puzzle with 28 givens is a CSP with 81 variables, 28 of which have singleton domains after node consistency.
  • Disequality / exclusion: X ≠ red, or X ∉ {4, 7}. This deletes one or more named values. In timetabling, "Dr. Osei is unavailable on Friday" removes all Friday slots from that lecturer's variable.
  • Range or interval restriction: X > 10, 0 ≤ X ≤ 23. For integer or continuous domains this is usually stored as a bound rather than an explicit value list. A job's earliest release time and latest due date are both range constraints on its start-time variable.

One caution: node consistency is cheap but weak. It can detect that a problem is unsolvable only in the extreme case where some domain becomes empty. A node-consistent CSP may still be hopelessly over-constrained once binary and higher-order constraints are taken into account. Node consistency is a hygiene step, not a solving method.

Binary constraints and the constraint graph. A binary constraint has a scope of two variables and therefore expresses a relationship between a pair. A CSP in which every constraint is unary or binary is called a binary CSP, and it is the form most of the classical theory assumes. After unary constraints have been absorbed into domains, a binary CSP can be drawn as a constraint graph: one node per variable, one undirected edge for each binary constraint, with the edge labelled by the relation if there is more than one kind.

For Australia, the constraint set is {WA ≠ NT, WA ≠ SA, NT ≠ SA, NT ≠ Q, SA ≠ Q, SA ≠ NSW, SA ≠ V, Q ≠ NSW, NSW ≠ V} — nine edges. Tasmania participates in no binary constraint, so it is an isolated node; the graph has two connected components, and the solver can colour Tasmania independently of the mainland. Reading structure off the graph like this is the whole point of drawing it.

Graph structure has real algorithmic consequences, and this is why the representation matters rather than being mere decoration:

  • Tree-structured graphs are easy. If the constraint graph is a tree (no cycles), the CSP can be solved in O(n d2) time, where n is the number of variables and d the maximum domain size. The algorithm picks a root, orders the variables so parents precede children, makes each arc from parent to child consistent in one backward sweep, then assigns values in one forward sweep with no backtracking at all. Contrast this with the worst-case O(dn) of general search.
  • Near-trees can be reduced to trees. In the Australia graph, deleting SA leaves a tree. So one can try each of the three values of SA, prune it from its neighbours' domains, and solve the residual tree in linear time — the cutset conditioning technique. The cost is O(dc · (n−c) d2) for a cycle cutset of size c.
  • Dense graphs demand full search. When every variable constrains most others, no structural shortcut exists and the solver must rely on backtracking plus propagation and good variable-ordering heuristics.
  • Connectivity partitions the work. Separate components are independent subproblems, and solving them separately converts a product of search spaces into a sum.

Binary constraints come in many relational flavours. Beyond disequality (WA ≠ NT), common forms include precedence in scheduling (EndA ≤ StartB, read as "Task A must finish before Task B begins"), difference constraints (StartB − StartA ≥ 30 for a changeover gap), compatibility tables (an explicit list of allowed pairs, as in configuring a motherboard and a CPU socket), and equality links (X = Y when two names refer to the same physical quantity).

The dominance of binary form in the literature is largely an artefact of algorithm design. The standard consistency-enforcement algorithms are stated over arcs — that is, over ordered pairs of variables joined by a binary constraint. AC-3 is the canonical example: it maintains a queue of arcs, and for each arc (Xi, Xj) it deletes any value in Di that has no supporting value in Dj; if a deletion occurs, all arcs pointing back into Xi are re-queued.

function AC-3(csp) returns false if an inconsistency is found
    queue ← all arcs (Xi, Xj) in csp
    while queue is not empty:
        (Xi, Xj) ← POP(queue)
        if REVISE(csp, Xi, Xj):
            if size of Di = 0: return false
            for each Xk in NEIGHBOURS(Xi) \ {Xj}:
                add (Xk, Xi) to queue
    return true

function REVISE(csp, Xi, Xj) returns true iff Di was changed
    revised ← false
    for each x in Di:
        if no value y in Dj satisfies the constraint between Xi and Xj:
            delete x from Di
            revised ← true
    return revised

AC-3 runs in O(e d3) for e binary constraints and domain size d. On the Australia problem with SA fixed to blue, AC-3 immediately removes blue from WA, NT, Q, NSW, V, which in turn forces further pruning around the NT–Q and Q–NSW edges. The important point for this topic is that AC-3's correctness and complexity analysis both presuppose binary scopes — which is precisely why so much effort has gone into turning non-binary constraints into binary ones, and why the alternative route of writing dedicated propagators for global constraints is such an attractive counter-strategy.

Higher-order and global constraints. A constraint with three or more variables in its scope is higher-order (or n-ary). A ternary example from cryptarithmetic is X + Y = 10 · C + Z, relating two digits, a result digit, and a carry. A global constraint is a higher-order constraint whose scope size is not fixed in advance and which captures a recurring, semantically meaningful pattern — typically accompanied by a purpose-built filtering algorithm. Global constraints are the practical workhorses of modern constraint programming; catalogues list hundreds of them.

The best-known is AllDiff(X1, ..., Xn), which holds exactly when all n variables take pairwise distinct values. Sudoku is the archetypal illustration: with 81 cell variables of domain {1..9}, the rules are expressed as 27 AllDiff constraints — nine for the rows, nine for the columns, nine for the 3×3 boxes — plus one unary constraint per given clue. N-Queens uses AllDiff on the row variables and AllDiff on the derived diagonal expressions Qi + i and Qi − i. Cryptarithmetic puzzles such as SEND + MORE = MONEY use a single AllDiff over the eight distinct letters.

AllDiff is logically equivalent to the set of n(n−1)/2 pairwise disequalities Xi ≠ Xj, so one might ask why bother with the global version. The answer is pruning power. Consider three variables with domains D1 = {a, b}, D2 = {a, b}, D3 = {a, b}. Every pairwise disequality is arc-consistent: for any value of X1 there is a different value available for X2, and so on. The decomposed encoding therefore detects nothing and search proceeds happily into a dead end. But a global AllDiff propagator sees instantly that three variables are competing for two values and reports failure.

That observation generalises into the simple counting test for AllDiff inconsistency: if a set of m variables in the scope has fewer than m distinct values in the union of their domains, the constraint is unsatisfiable. A practical and inexpensive version of the test runs as follows: repeatedly find a variable with a singleton domain, remove that value from all other variables in the scope, and iterate; if at any point a domain empties, or the union of all remaining domains has fewer values than the number of remaining variables, fail. The complete, strongest form of filtering for AllDiff is achieved by Régin's algorithm, which models the constraint as a bipartite graph of variables versus values, computes a maximum matching, and uses the theory of alternating cycles to delete exactly those value-variable pairs that belong to no solution of the constraint — all in polynomial time.

A1 {1}        A2 {2}        A3 {3..9}
A4 {4,5}      A5 {4,5}      A6 {3..9}
A7 {6,7,8,9}  A8 {6,7,8,9}  A9 {6,7,8,9}

  A3 and A6 are now reduced to {3,6,7,8,9} minus whatever else follows.
A set of pairwise != constraints would have inferred none of the pair reasoning.

A second important family is the resource or AtMost constraint, which bounds the total consumption of a shared resource. Written AtMost(k, X1, ..., Xn), it requires X1 + ... + Xn ≤ k where each Xi is the amount of the resource consumed by activity i. Suppose four maintenance tasks each need between 2 and 7 workers drawn from a pool of 10: AtMost(10, P1, P2, P3, P4) with Di = {2,...,7}. Its propagator reasons about bounds rather than enumerating tuples: the minimum total is 2 + 2 + 2 + 2 = 8, so each individual variable can consume at most 10 − 6 = 4, and the domains collapse to {2, 3, 4} in one step. If the pool were only 7, the minimum total of 8 would exceed it and failure is detected without any search. Bounds propagation of this kind is the standard technique for numeric global constraints and scales to very large domains where enumerating values would be impossible.

Other widely used globals include Cumulative (resource usage over time never exceeds capacity — the backbone of job-shop scheduling), NoOverlap/Disjunctive (tasks on one machine must not overlap in time), GCC or global cardinality (each value is used between lv and uv times, a generalisation of AllDiff), Element (array indexing with a variable index), and Table (an explicit list of allowed tuples).

The design lesson is consistent: prefer a global constraint to an equivalent conjunction of binary constraints whenever one exists. The decomposition is logically faithful but informationally lossy — the solver can no longer see that the small constraints form a coherent combinatorial structure, and so it cannot apply the matching, flow, or counting arguments that make strong pruning possible. A global constraint also keeps the model compact and readable: one AllDiff over nine cells replaces thirty-six disequalities.

Hypergraph representation of n-ary constraints. An ordinary graph cannot draw a constraint over three or more variables, because an edge joins exactly two nodes. The general representation is a constraint hypergraph. A hypergraph contains two kinds of node: ordinary variable nodes, one per variable exactly as in a constraint graph, and hypernodes (sometimes drawn as squares or boxes to distinguish them from circular variable nodes), one per constraint. Each constraint's hypernode is joined by links — collectively a hyperedge — to every variable in that constraint's scope, and to no others. The picture is therefore bipartite: links always run between a constraint box and a variable circle, never between two variables or two constraints.

Take a single Sudoku row. In hypergraph form it is one square hypernode labelled AllDiff with nine lines radiating out to the cell variables A1 through A9. The whole puzzle becomes 81 circles and 27 squares, with each circle touching exactly three squares (its row, its column, its box) and each square touching exactly nine circles. Reading degrees off the diagram tells you immediately that every cell is involved in three global constraints — a fact that is very hard to see if the same puzzle is drawn as a tangle of 810 pairwise disequality edges.

Row constraint as a hyperedge (schematic)

   A1  A2  A3  A4  A5  A6  A7  A8  A9      <- 9 variable nodes
    \   \   \   \   |   /   /   /   /
     \---\---\---\--+--/---/---/---/
              [ AllDiff ]                   <- 1 hypernode, arity 9

Same information decomposed into binary form:
   36 separate edges A_i -- A_j, and no record that they belong together.

Three properties make the hypergraph the right default notation for general CSPs:

  • Scope is explicit. Every constraint is a single visible object, and the set of variables it governs can be read directly off its links. The notion of a constraint's arity becomes literally the degree of its hypernode.
  • Decomposition hides structure. If an AllDiff over nine cells is replaced by thirty-six disequalities, the resulting graph still encodes the same solutions, but the knowledge "these thirty-six constraints are jointly an all-different requirement" has been destroyed. No propagator can recover it, and the pruning arguments of the previous section become unavailable. The hypergraph preserves exactly what the decomposition throws away.
  • It generalises the binary case cleanly. A binary constraint graph is simply the hypergraph in which every hypernode has degree two. When all hyperedges are of arity two, the hypernodes can be suppressed and drawn as plain edges, recovering the familiar picture. So nothing is lost by always thinking in hypergraph terms; the constraint graph is just the convenient special case.

Hypergraph structure also drives theory in the same way graph structure does. The hypertree width of a constraint hypergraph generalises the tree-width of a graph, and CSPs whose hypergraphs have bounded hypertree width are solvable in polynomial time — the n-ary analogue of "tree-structured problems are easy". Likewise, the primal graph of a hypergraph (join every pair of variables that share any constraint) and the dual graph (introduced next) are the two standard ways of projecting a hypergraph back down into an ordinary graph for analysis.

Converting higher-order constraints to binary form. Because so much classical machinery — AC-3, arc consistency theory, tree-structure results, many textbook solvers — is defined only for binary CSPs, there are standard transformations that turn any finite-domain CSP with constraints of arbitrary arity into an equivalent binary CSP. It is a genuine theorem that this is always possible; the question is whether it is a good idea.

The dual graph transformation is the general-purpose method. It works by swapping the roles of variables and constraints:

  • For each constraint ck in the original problem, create one new dual variable Ck.
  • The domain of Ck is the set of tuples that satisfy ck — i.e. the constraint's relation is turned into a list of values.
  • For every pair of original constraints whose scopes share one or more original variables, add a binary constraint between the corresponding dual variables requiring that their tuples agree on all shared variables. These are called join or equality-of-projection constraints.

A worked example. Suppose X, Y, Z all have domain {1, 2, 3}, with two ternary constraints: c1: X + Y = Z and c2: X < Y < Z — wait, these share X, Y and Z, so take instead c1: X + Y = Z over (X, Y, Z) and c2: Z ≠ W over (Z, W) with W ∈ {1,2,3}. The dual variable C1 has domain {(1,1,2), (1,2,3), (2,1,3)} — the satisfying tuples. The dual variable C2 has domain {(1,2),(1,3),(2,1),(2,3),(3,1),(3,2)}. The two scopes share only Z, so the binary constraint between C1 and C2 says: the third component of C1's tuple must equal the first component of C2's tuple. The resulting problem has two variables, domains of size 3 and 6, and one binary constraint — and it is now fully in the scope of AC-3.

The second standard technique introduces auxiliary (hidden) variables to split one wide constraint into a chain of narrow ones. Cryptarithmetic is the classic illustration. The puzzle SEND + MORE = MONEY can be stated as one enormous constraint over eight letters:

1000·S + 100·E + 10·N + D
+ 1000·M + 100·O + 10·R + E
= 10000·M + 1000·O + 100·N + 10·E + Y        (arity 8)

Introducing carry variables C1, C2, C3, C4, each with domain {0, 1}, replaces it with one small constraint per column:

D + E        = Y  + 10·C1      (arity 4)
N + R  + C1  = E  + 10·C2      (arity 5)
E + O  + C2  = N  + 10·C3      (arity 5)
S + M  + C3  = O  + 10·C4      (arity 5)
C4           = M                (arity 2)
plus AllDiff(S,E,N,D,M,O,R,Y) and S ≠ 0, M ≠ 0

These are still ternary-and-up rather than strictly binary, but the arity has dropped sharply, each constraint is cheap to propagate, and the column structure lets a solver deduce M = 1 immediately (since C4 ≤ 1 and M ≠ 0). The same trick — add a hidden variable to carry partial information between sub-constraints — reduces any n-ary sum to a chain of ternary ones, and generalises to the hidden variable encoding, in which each constraint gets one auxiliary variable whose domain is its allowed tuples and which is linked by a binary constraint to each original variable in its scope.

The trade-offs are unavoidable and are why these encodings are not universally used:

  • Domain blow-up. A dual variable for an arity-9 constraint over domain size 9 could in principle have 99 ≈ 387 million tuples. For AllDiff over nine cells the figure is 9! = 362,880. Representing that domain explicitly is absurd.
  • More variables and more constraints. The transformed problem is larger, so each propagation pass costs more, and the search tree has more levels.
  • Weaker inference. Arc consistency on the encoded problem is often strictly weaker than the specialised filtering available on the original global constraint — the three-variables-two-values example of the previous section makes the point.
  • Loss of readability. A model full of dual variables no longer resembles the problem it came from, which makes debugging and maintenance harder.

Consequently, modern constraint solvers normally take the opposite route: keep high-arity and global constraints intact in the model and invest in specialised propagators that filter domains directly. Binarisation remains valuable as a theoretical device (it proves that binary CSPs are as expressive as general ones, so complexity results transfer) and as a practical tactic for small, awkward constraints with no library propagator, but it is not the default engineering choice.

Preference (soft) constraints and constrained optimization. Everything so far has assumed hard constraints: an assignment either satisfies a constraint or it does not, and any violation makes the whole assignment invalid. Many real problems are not like that. A lecturer prefers morning slots; a nurse would rather not work three consecutive nights; a delivery should ideally arrive before noon. These are preference constraints or soft constraints: desirable but violable.

The standard encoding attaches a numeric cost (equivalently a penalty, or a negated utility) to assignments that violate the preference. In the simplest case the cost is attached to individual variable assignments — a soft unary constraint. In university timetabling, for example, the variable SlotProf Lee might carry costs of 0 for a 9am slot, 1 for 11am, and 5 for a 4pm slot. Soft binary and soft global constraints work the same way, assigning a cost to each tuple rather than merely labelling it allowed or forbidden.

Hard constraint:   relation(t) ∈ {true, false}
Soft constraint:   cost(t)     ∈ {0, 1, 2, ...} or [0, ∞]
                   cost = 0      -> fully satisfied
                   cost = ∞      -> equivalent to a hard violation

Objective:  minimise  f(assignment) = Σ over all soft constraints of cost(projection of assignment)
Subject to: every hard constraint satisfied

Adding an objective function turns the CSP into a constraint optimization problem (COP). The task is no longer "find any complete, consistent assignment" but "find a complete assignment that satisfies all hard constraints and minimises (or maximises) the objective". This changes the success criterion in a fundamental way: with hard constraints only, every solution is equally good and the solver can stop at the first one it finds; with an objective, solution quality is graded, and the solver cannot stop at the first feasible assignment because a cheaper one may exist. Proving optimality generally requires exploring or formally excluding the whole remaining search space.

Because plain backtracking has no notion of "better", COPs are solved with different machinery:

  • Branch and bound. Search as usual, but maintain the cost of the best complete solution found so far (the incumbent). At each node compute a lower bound on the cost of any completion of the current partial assignment — typically the cost already accrued plus the minimum unavoidable cost of the unassigned variables. If that bound is not better than the incumbent, prune the subtree without exploring it. The tighter the bound, the more is pruned. This is the direct optimization analogue of consistency-based pruning.
  • Local search / metaheuristics. Start from a complete (possibly infeasible) assignment and repeatedly make small changes — min-conflicts, simulated annealing, tabu search, large-neighbourhood search — that reduce total cost. These methods scale to very large instances and are the practical choice for nurse rostering and vehicle routing, but they offer no optimality guarantee.
  • Linear and mixed-integer programming. When the hard constraints and the objective can be written as linear (in)equalities over integer or continuous variables, LP relaxations and MILP solvers apply. Linear programs over continuous variables are solvable in polynomial time, and MILP solvers combine LP relaxation bounds with branch and bound.
  • Weighted/valued CSP frameworks. Generalisations such as the weighted CSP, fuzzy CSP, and semiring-based CSP give a uniform algebra for combining costs, together with soft arc-consistency algorithms that shift costs around the problem to strengthen the lower bound used by branch and bound.

A concrete example ties the pieces together. A small examination timetable has hard constraints — no student sits two exams at once (a set of binary disequalities), no room exceeds capacity (AtMost resource constraints), each exam is scheduled exactly once (unary and AllDiff structure) — and soft constraints such as "avoid two exams for the same student on the same day" (cost 3 per occurrence), "avoid evening slots" (cost 1 each), and "large exams should be early in the period" (cost proportional to lateness). The solver must produce a feasible timetable; among feasible timetables it chooses the one minimising the weighted sum. Note the practical benefit: an over-constrained preference set never makes the problem infeasible, it merely raises the optimal cost, so the system always returns a usable answer and the weights expose the trade-offs being made.

Modeling Real Problems as CSPs

1

Modeling Real Problems as CSPs

▶

A constraint satisfaction problem (CSP) is a deceptively simple formalism: a triple (X, D, C) consisting of a set of variables X = {X₁, …, Xₙ}, a domain Dᵢ of candidate values for each variable, and a set of constraints C, each of which restricts the combinations of values that some subset of the variables may take simultaneously. The power of the formalism comes from the fact that an enormous range of practical problems — timetabling a university, allocating radio frequencies, assigning registers in a compiler, laying out a circuit, scheduling a factory floor — can be squeezed into this one shape, after which a single general-purpose solver can attack all of them. The difficulty, and the real intellectual work, lies in the squeezing. Two people handed the same problem statement will routinely produce models that differ by many orders of magnitude in how long a solver takes to crack them, even though both models are logically correct. This topic is about how to do that translation well.

Throughout, keep a distinction clear in your mind. Correctness of a model means that the solutions of the CSP are exactly the solutions of the real problem — no spurious answers, no lost answers. Efficiency of a model means that a solver can find those solutions quickly. Correctness is non-negotiable and is usually the easier property to argue. Efficiency is where modeling expertise lives, and it is largely about giving the solver as much structure as possible to reason with before and during search.

The Modeling Process: From Problem Statement to CSP

A disciplined four-step recipe will get you a correct model for almost any combinatorial decision problem. Treat it as a checklist rather than a straitjacket; experienced modelers loop back through the steps several times as they discover better encodings.

Step 1: Identify the decisions and make each one a variable. Read the problem statement and ask, "When the problem is solved, what exactly will I have decided?" Each independent decision becomes a variable. If the answer to the problem is "which colour each country gets," then there is one variable per country. If the answer is "when each operation starts," then there is one variable per operation. A good diagnostic question: if I handed you a value for every variable, could you write down the answer to the original problem without any further thought? If yes, your variable set is complete. If you would still have to compute something, you have either missed a decision or you have an implicit dependency that may be worth making explicit.

Note that the choice of what counts as "a decision" is itself a modeling decision. In N-Queens, you could decide "is there a queen on square (r, c)?" for each of the 64 squares, or "which row does the queen in column c occupy?" for each of the 8 columns. Both answer the question; one of them is drastically better, as we will see.

Step 2: Enumerate the finite set of legal values for each variable as its domain. Domains in classical CSP are finite and discrete. For a colouring problem the domain is a palette; for a scheduling problem it is a set of integer time points; for cryptarithmetic it is the digits 0–9. Two practical rules: first, make the domain as small as you can while still containing every value the variable could legitimately take, because the raw size of the search space is the product of the domain sizes, ∏ᵢ |Dᵢ|. Second, if a variable's "value" is naturally a tuple — a room, a time and an instructor, say — decide consciously whether to model it as one variable over a compound domain of tuples or as three separate variables. Compound domains make certain constraints easy to express but can blow up in size (|rooms| × |slots| × |instructors|); separate variables keep domains small but require constraints to tie them together.

Step 3: Translate each requirement into a constraint. Walk through the problem statement sentence by sentence and classify each restriction by arity:

  • Unary constraints restrict a single variable: "Western Australia cannot be red," "the letter S cannot be 0," "machine 3 is unavailable before time 10." These are best handled by simply deleting the forbidden values from the domain at model time — a unary constraint should rarely survive into the solver.
  • Binary constraints relate two variables: WA ≠ NT, Start_B ≥ Start_A + 5, |Q₁ − Q₃| ≠ 2. Binary CSPs are the classical case and every finite CSP can in principle be converted to a binary one, though the conversion often obscures structure.
  • Higher-order (n-ary) constraints relate three or more variables: the column equation D + E = Y + 10·C₁ in cryptarithmetic involves four variables at once.
  • Global constraints are n-ary constraints with a known semantic pattern and a specialised, efficient propagation algorithm attached — alldifferent, cumulative, element, nvalue, gcc (global cardinality). Reaching for a global constraint instead of hand-rolling an equivalent conjunction of binaries is one of the single highest-leverage modeling moves available.

Step 4: Verify that any complete assignment satisfying all constraints really is a valid solution. This is the step beginners skip, and it is where most modeling bugs hide. The verification has two directions. Soundness: pick an arbitrary assignment that satisfies all your constraints and argue that it describes a genuine solution of the original problem. Completeness: pick an arbitrary real solution and argue that it corresponds to an assignment your constraints accept. A model that fails soundness produces garbage answers; a model that fails completeness silently discards valid solutions and may report "unsatisfiable" for a solvable problem — a far nastier failure mode because it looks like a definitive answer.

Watch for implicit constraints. Natural-language problem statements are written for humans, who fill in a vast amount of unstated background. A solver fills in nothing. Classic omissions include: a queen cannot occupy two squares at once; a machine processes one job at a time; a room cannot host two lectures simultaneously; time runs forward, so a task cannot start before its predecessor finishes; digits in cryptarithmetic are distinct and numbers do not have leading zeros; a person cannot be in two places at once. If your solver returns a bizarre "solution," the first suspicion should always be a missing implicit constraint. Conversely — and this is the elegant move — some implicit constraints can be eliminated entirely by choosing variables so that violating them is impossible. That is the subject of the N-Queens discussion below.

Map Coloring: The Canonical Binary CSP

Map colouring is the textbook CSP because its structure is as clean as a CSP can be: all constraints are binary, all domains are identical, and the constraint graph is literally a map. The task: colour each region of a map so that no two regions sharing a border receive the same colour, using a fixed palette.

Applying the recipe to the standard Australia instance:

  • Variables: one per region — WA, NT, SA, Q, NSW, V, T (Western Australia, Northern Territory, South Australia, Queensland, New South Wales, Victoria, Tasmania).
  • Domains: every variable has domain {red, green, blue}.
  • Constraints: one binary disequality per shared border: WA ≠ NT, WA ≠ SA, NT ≠ SA, NT ≠ Q, SA ≠ Q, SA ≠ NSW, SA ≠ V, Q ≠ NSW, NSW ≠ V. Tasmania is an island and appears in no constraint at all.

The raw search space is 3⁷ = 2187 assignments, of which a handful are solutions. One solution is WA=red, NT=green, SA=blue, Q=red, NSW=green, V=red, T=red.

The constraint graph has one node per variable and one edge per binary constraint. For map colouring, this graph is exactly the adjacency graph (dual graph) of the map, so the picture and the formalism coincide. The graph is not merely decorative: it drives algorithmic reasoning. Tasmania is an isolated node, so the problem decomposes into two independent subproblems that can be solved separately — a general principle, since any CSP whose constraint graph splits into connected components can be solved component by component, turning a product of costs into a sum. Removing SA leaves a tree, and tree-structured CSPs are solvable in O(n·d²) time with no backtracking at all; this observation underlies the cutset conditioning technique, where you try all colours for a small cutset of variables and solve the resulting tree directly. The degree of a node (SA has degree 5) also feeds the degree heuristic for variable ordering.

This formulation generalises far beyond cartography, because the pattern "entities that conflict must receive different resources" is ubiquitous:

Sudoku: Global Constraints Over a Grid

Sudoku is the cleanest demonstration of why global constraints matter. The puzzle: fill a 9×9 grid with digits 1–9 so that every row, every column, and every 3×3 box contains each digit exactly once, respecting the given clues.

  • Variables: 81 cells, X₍r,c₎ for r, c ∈ {1..9}.
  • Domains: {1,…,9} for every empty cell. For a clue cell, the domain is the singleton containing the clue — equivalently, a unary constraint applied at model time.
  • Constraints: 27 alldifferent constraints — 9 over the rows, 9 over the columns, 9 over the boxes.
Variables: X[r][c] for r,c in 1..9, domain {1..9}
for r in 1..9:  alldifferent( X[r][1], X[r][2], ..., X[r][9] )   # rows
for c in 1..9:  alldifferent( X[1][c], X[2][c], ..., X[9][c] )   # columns
for each 3x3 box B: alldifferent( cells of B )                   # boxes
for each clue (r,c,v): X[r][c] = v                               # unary: domain := {v}

Each alldifferent over 9 variables is logically equivalent to C(9,2) = 36 pairwise disequalities, so the whole puzzle could be written as 27 × 36 = 972 binary constraints (with duplicates where a row and box share pairs). Logically equivalent — but computationally far weaker. Consider a row where three cells have been reduced to domains {4,7}, {4,7}, {4,7}. Every one of the 36 pairwise constraints is still individually satisfiable: pick 4 for one and 7 for another and no single ≠ is violated. A solver propagating only binary disequalities sees nothing wrong and happily continues searching. The global alldifferent, however, reasons about all nine variables at once: three variables confined to a two-value set is a pigeonhole violation, so it immediately reports failure. More typically, alldifferent detects a "naked pair" — two cells both reduced to {4,7} — and removes 4 and 7 from the other seven cells of that unit, a deduction no pairwise constraint can make.

This is not a hand-wavy improvement. Régin's propagation algorithm for alldifferent builds a bipartite value graph (variables on one side, values on the other, edges for membership) and computes a maximum matching; by a theorem of Berge, a value-variable edge can appear in some maximum matching only if it lies on an even alternating cycle or an alternating path starting at a free vertex. Edges failing that test are removed. This achieves generalized arc consistency (also called domain consistency): every remaining value in every domain participates in at least one satisfying tuple of the whole constraint. The pairwise decomposition, by contrast, achieves only arc consistency on each pair separately, which is strictly weaker.

The practical consequence is striking. Given clues become singleton domains; propagating them through the 27 alldifferent constraints removes those digits from every peer cell; that may reduce another cell to a singleton, which propagates in turn; and so on. For "easy" and many "medium" newspaper puzzles this cascade fixes all 81 cells with zero search — the solver never has to guess. Harder puzzles require a small amount of backtracking, but propagation keeps the search tree to dozens of nodes rather than astronomical numbers. The same code with pairwise disequalities instead of global alldifferent will usually still solve the puzzle, but it will search, often substantially.

Two further modeling notes. First, redundant reasoning can be made explicit: the "hidden single" rule (a digit that can go in only one cell of a unit must go there) is captured by alldifferent only under strong propagation, and some modelers add an explicit gcc (global cardinality) constraint stating that each digit occurs exactly once per unit, which encodes the counting view directly. Second, Sudoku shows that domains need not be homogeneous: clue cells have singleton domains from the start, which is simply the Step-2 principle "make the domain as small as legitimately possible" taken to its limit.

N-Queens: Choosing Variables to Shrink the Search Space

Place N queens on an N × N chessboard so that no two attack each other — no shared row, column, or diagonal. N-Queens is the canonical lesson in variable choice, because the obvious encoding and the good encoding differ enormously.

The naive Boolean encoding. Introduce one Boolean variable B₍r,c₎ ∈ {0,1} per square, meaning "a queen stands here." For N = 8 that is 64 variables and a raw space of 2⁶⁴ ≈ 1.8 × 10¹⁹ assignments. Worse, the encoding permits nonsense: the all-zeros assignment satisfies every "no two queens attack" constraint but places no queens at all. To exclude it you must add counting constraints — "exactly N variables are 1," or per-row and per-column cardinality constraints — which are extra n-ary constraints that must themselves be propagated. The structural requirement "there are exactly N queens, one per row and one per column" has to be laboriously stated and enforced.

The good encoding. Observe that any solution has exactly one queen per column. So let the decision be "which row does the queen in column i occupy?" This gives:

  • Variables: Q₁, …, Q_N, one per column.
  • Domains: {1, …, N}, the row indices.
  • Constraints: row disequality Qᵢ ≠ Qⱼ for all i < j; diagonal non-attack |Qᵢ − Qⱼ| ≠ |i − j| for all i < j.

For N = 8 the raw space is 8⁸ = 16 777 216 — twelve orders of magnitude smaller than the Boolean encoding. And notice what has disappeared: there is no constraint saying "exactly one queen per column," and no constraint saying "exactly 8 queens," because the structure of the variables makes those statements true by construction. A variable has exactly one value, therefore a column has exactly one queen, therefore the board has exactly N queens. An entire class of implicit constraints has been absorbed into the variable definition at zero runtime cost.

We can go further. The N(N−1)/2 pairwise row disequalities are precisely the semantics of alldifferent(Q₁, …, Q_N), and the diagonal conditions have their own global form. Writing |Qᵢ − Qⱼ| ≠ |i − j| as the pair of conditions Qᵢ + i ≠ Qⱼ + j and Qᵢ − i ≠ Qⱼ − j reveals that the two diagonal families are themselves all-different conditions on derived quantities. So the entire problem compresses to three global constraints:

Variables: Q[1..N], domain {1..N}
alldifferent( Q[1],      Q[2],      ..., Q[N]      )   # no shared row
alldifferent( Q[1]+1,    Q[2]+2,    ..., Q[N]+N    )   # no shared "/" diagonal
alldifferent( Q[1]-1,    Q[2]-2,    ..., Q[N]-N    )   # no shared "\" diagonal

Three constraints replace 3·N(N−1)/2 binary ones (84 of them at N = 8), and each propagates with the full strength of Régin's matching algorithm.

Let us make the diagonal algebra concrete. Suppose Q₂ = 5 and we ask whether Q₅ = 8 is allowed. Column distance is |5 − 2| = 3; row distance is |8 − 5| = 3; equal, so they share a diagonal and the assignment is rejected. Via the derived form: Q₂ − 2 = 3 and Q₅ − 5 = 3, equal, so the "\" alldifferent is violated. Both routes agree, but the second lets a single global constraint police all such clashes simultaneously.

The generalisable lesson: fold structural requirements into the variable definition rather than stating them as constraints. Whenever a problem says "exactly one X per Y," consider making Y the variable and X the value. Examples: "exactly one colour per region" → region is the variable; "exactly one time slot per exam" → exam is the variable; "each job visits each machine exactly once" → the (job, machine) pair indexes a variable. Constraints that a solver never has to check are infinitely cheaper than constraints it checks efficiently.

Cryptarithmetic: Auxiliary Variables and Higher-Arity Constraints

Cryptarithmetic puzzles ask you to replace letters with digits so that an arithmetic statement becomes true, with distinct letters mapping to distinct digits and no number beginning with 0. The famous instance:

    S E N D
  + M O R E
  ---------
  M O N E Y

The monolithic model. The direct translation is:

  • Variables: S, E, N, D, M, O, R, Y — the eight distinct letters.
  • Domains: {0,…,9}.
  • Constraints: alldifferent(S,E,N,D,M,O,R,Y); unary constraints S ≠ 0 and M ≠ 0 (leading letters); and the arithmetic identity 1000·S + 100·E + 10·N + D + 1000·M + 100·O + 10·R + E = 10000·M + 1000·O + 100·N + 10·E + Y.

This model is correct, and a solver will eventually return S=9, E=5, N=6, D=7, M=1, O=0, R=8, Y=2 (9567 + 1085 = 10652). But the arithmetic constraint is a single 8-ary constraint linking every variable. Propagating it is weak: until almost every letter is fixed, the huge coefficients leave enormous slack and the constraint rules out very little. The solver is effectively guessing most of the way down.

The decomposed model with carry variables. Reintroduce the structure of column-wise addition that the monolithic equation destroyed. Add auxiliary variables C₁, C₂, C₃, C₄ ∈ {0,1}, where Cₖ is the carry out of column k counting from the right. Then:

col 1 (units):      D + E         = Y + 10*C1
col 2 (tens):       N + R + C1    = E + 10*C2
col 3 (hundreds):   E + O + C2    = N + 10*C3
col 4 (thousands):  S + M + C3    = O + 10*C4
col 5 (ten-thous.):   C4            = M
alldifferent(S,E,N,D,M,O,R,Y)
S ≠ 0,  M ≠ 0

Each column constraint now involves at most four variables with coefficients of at most 10, so each one prunes hard. The payoff is immediate and can be worked by hand. From column 5, M = C₄, and since M ≠ 0 we get M = 1 and C₄ = 1 with no search whatsoever. Column 4 then reads S + 1 + C₃ = O + 10; since S ≤ 9 and C₃ ≤ 1, the left side is at most 11, so O ≤ 1; and O ≠ 1 because M = 1 already took that digit (via alldifferent), so O = 0. That forces S + C₃ = 10, so S ∈ {9, 10} and therefore S = 9 with C₃ = 1. Three letters have been determined by pure propagation. Column 3 now reads E + 0 + C₂ = N + 10, and since E ≤ 9 and C₂ ≤ 1 we need C₂ = 1 and N = E + 1 − 10 + 10 = E + 1... more carefully, E + C₂ = N + 10 forces C₂ = 1 and E = N + 9, which is impossible unless we track the carry correctly — the correct deduction is that column 3 produces the carry C₃ = 1 only when E + O + C₂ ≥ 10, and with O = 0 this requires E + C₂ ≥ 10, hence E = 9 and C₂ = 1 — but E = 9 clashes with S = 9. The resolution is that C₃ must in fact come from the tens column arrangement, and the solver discovers by a single backtrack that N = E + 1 with C₂ = 1, leading to E = 5, N = 6. The point of walking through this is not the particular arithmetic but the shape of the reasoning: the decomposed model lets a solver make long chains of forced deductions, whereas the monolithic model offers nowhere to start.

Empirically, on SEND+MORE a plain backtracking solver on the monolithic model explores thousands of nodes; on the carry-decomposed model with alldifferent propagation it typically explores a handful, sometimes none. The comparison below summarises the trade-off.

Notice the apparent paradox: the better model has more variables. Step 2 told us to shrink the search space, and adding four Boolean carries multiplies the raw space by 16. But raw space is a crude measure; what matters is how much of it propagation can eliminate without exploring it. Auxiliary variables that expose intermediate structure — carries here, "end time" variables in scheduling, "is this machine used?" indicators in configuration — are a standard and powerful technique precisely because they give constraints something small and local to talk about. The carries are not decisions in the Step-1 sense (they are determined once the letters are fixed), so a good solver can be told to branch only on the letters and let the carries be inferred.

Finally, the unary leading-zero constraints deserve a note. S ≠ 0 and M ≠ 0 are applied by deleting 0 from those two domains before search begins, costing nothing at runtime. A modeler who forgets them does not get a wrong answer here only by luck; in general, omitting leading-zero constraints admits spurious solutions such as interpreting "SEND" as a three-digit number, violating the soundness half of Step 4.

Scheduling: Job-Shop and Timetabling Formulations

Scheduling is where CSP modeling meets industrial reality, and it introduces two new features: domains that are ranges of integers rather than small symbolic sets, and a sharp distinction between requirements that must hold and preferences that we merely want.

Job-shop scheduling. A set of jobs must be processed; each job consists of an ordered sequence of operations; each operation requires a specific machine for a fixed duration; a machine processes at most one operation at a time; operations cannot be interrupted. The goal is a feasible schedule, usually one finishing within a horizon H (and, in the optimisation version, minimising the makespan).

  • Variables: one start time Sₒ per operation o. (End times Eₒ = Sₒ + dₒ are derived, not independent decisions, though many models introduce them as auxiliary variables for convenience.)
  • Domains: {0, 1, …, H − dₒ} — every integer time point at which the operation could start and still finish within the horizon. Subtracting the duration is a small but worthwhile domain reduction, and release dates or machine downtime shrink the domain further.
  • Precedence constraints: if operation A must precede B within a job, then S_B ≥ S_A + d_A. These are binary and propagate well: raising the lower bound of S_A immediately raises that of S_B, and lowering the upper bound of S_B pushes back on S_A.
  • Non-overlap (disjunctive) constraints: for two operations A and B requiring the same machine, S_A + d_A ≤ S_B ∨ S_B + d_B ≤ S_A. This is a disjunction, which is why job-shop is hard: each pair of same-machine operations represents a binary choice of ordering, and the number of orderings grows factorially per machine.

Consider a tiny instance: two jobs, two machines. Job 1 is O₁₁ on M1 for 3 units then O₁₂ on M2 for 2 units. Job 2 is O₂₁ on M2 for 4 units then O₂₂ on M1 for 1 unit. With horizon H = 10:

Variables: S11, S12, S21, S22
Domains:   S11 in 0..7,  S12 in 0..8,  S21 in 0..6,  S22 in 0..9
Precedence: S12 >= S11 + 3        (job 1 order)
            S22 >= S21 + 4        (job 2 order)
Machine M1: S11 + 3 <= S22  OR  S22 + 1 <= S11
Machine M2: S12 + 2 <= S21  OR  S21 + 4 <= S12

A valid solution is S₁₁ = 0, S₁₂ = 4, S₂₁ = 0, S₂₂ = 4: machine M1 runs O₁₁ during [0,3) and O₂₂ during [4,5); machine M2 runs O₂₁ during [0,4) and O₁₂ during [4,6); both job orders hold; makespan is 6. Observe that the disjunctions were resolved by choosing an ordering on each machine — exactly the branching decision a job-shop solver makes.

Two refinements matter in practice. First, rather than branching on start times directly (domains of hundreds of integers), good models branch on the ordering of each disjunctive pair, introducing a Boolean B_{AB} meaning "A precedes B" and reifying the disjunction; the search tree then has branching factor 2 instead of |domain|. Second, the per-machine non-overlap conditions are far better expressed with a single global disjunctive (unary resource) constraint over all operations on that machine, or a cumulative constraint when a resource has capacity greater than one (three identical welding robots, say). These globals apply edge-finding and energetic-reasoning algorithms that deduce bounds no pairwise disjunction can — for example, if four operations totalling 20 units of work must all fit between time 5 and time 22, there is a contradiction, and edge-finding sees it instantly.

Timetabling. University timetabling looks superficially like map colouring but is richer because each decision has several components. A typical formulation:

  • Variables: one per course section to be scheduled.
  • Domains: tuples (time slot, room, instructor) — or, in a decomposed model, three separate variables T_s, R_s, I_s per section. The tuple form makes it easy to pre-filter: only generate tuples where the room is big enough for the section's enrolment, the instructor is qualified and available in that slot, and the room has any required equipment. Pre-filtering during model construction is often the single most effective reduction, routinely shrinking a domain of thousands of tuples to dozens.
  • Hard constraints (must hold, or the timetable is unusable):
    • No two sections in the same room at the same time: (T_s, R_s) ≠ (T_t, R_t), or an alldifferent over the (slot, room) pairs.
    • No instructor teaches two sections at once: for sections sharing an instructor, T_s ≠ T_t.
    • No student cohort has two required sections at once: T_s ≠ T_t for conflicting pairs — this is precisely the map-colouring pattern again.
    • Room capacity ≥ section enrolment; instructor availability; equipment requirements — all unary, handled by domain filtering.
    • Curriculum precedence or spacing: a lab must follow its lecture in the same week.
  • Soft constraints (preferences, scored not enforced): an instructor prefers mornings; avoid 8 a.m. slots; minimise student travel between distant buildings; spread a course's meetings across the week; balance instructor workload.

The separation of hard from soft is a modeling decision with real consequences. If every preference is encoded as a hard constraint, the problem becomes unsatisfiable and the solver reports failure with no useful guidance — a classic over-constrained model. The standard remedy is to keep hard constraints as true constraints and convert soft ones into an objective: introduce a penalty variable per violated preference, often via reification (a Boolean V_k that is 1 exactly when preference k is violated), and minimise the weighted sum Σ wₖ·Vₖ. This turns the CSP into a constrained optimisation problem (COP) while preserving the guarantee that any returned timetable is at least workable. Weights encode institutional priorities: an instructor's hard "cannot teach Fridays, medical reason" may carry weight 1000 while "prefers not to teach at 4 p.m." carries weight 2.

Why Modeling Choices Drive Solver Performance

Everything above is an instance of a handful of general principles. Collecting them makes them reusable.

Smaller domains and fewer variables shrink the space before search starts. The raw size of the search space is ∏ᵢ |Dᵢ|, so every value you can legitimately delete at model time is value you never pay to explore. This is why unary constraints should be absorbed into domains, why N-Queens uses columns rather than squares (8⁸ versus 2⁶⁴), and why timetabling pre-filters its tuple domains. It is also why you should question any variable that is fully determined by others: if E = S + d always, E is derived, and while it may be worth keeping as an auxiliary for expressiveness, the solver should never branch on it.

Global constraints prune more than the equivalent binaries. A set of binary constraints reasons about pairs; a global constraint reasons about all its variables simultaneously and can therefore detect combinatorial facts — pigeonhole violations, matching infeasibility, resource-capacity overloads — that no pair can see. The three-cells-with-domain-{4,7} example in Sudoku is the canonical illustration: 36 pairwise disequalities are all individually satisfied while the situation is globally impossible. Whenever you find yourself writing X₁ ≠ X₂, X₁ ≠ X₃, X₂ ≠ X₃, …, stop and write alldifferent instead. Similarly, a conjunction of pairwise non-overlaps on one machine should be a disjunctive, and "each digit appears exactly once" should be a gcc.

Break symmetry. Many models contain interchangeable objects, and a solver with no knowledge of that interchangeability will explore essentially identical subtrees over and over — and, worse, will have to refute each equivalent failure separately when the problem is unsatisfiable. Map colouring has full colour symmetry: any solution relabelled red↔blue is another solution, so the three colours generate 3! = 6 equivalent copies of every solution. Fixing WA = red removes a factor of 3 and costs nothing. N-Queens has the eight symmetries of the square (four rotations × reflection), so constraining the first queen to the upper half of the board, Q₁ ≤ ⌈N/2⌉, roughly halves the work; stronger lexicographic constraints comparing the board to its own reflections remove more. In scheduling with identical machines, imposing an ordering such as "the lowest-indexed job on machine group G goes to the lowest-indexed machine" prevents the solver from permuting indistinguishable machines. The general tool is a symmetry-breaking constraint: an added constraint that keeps at least one representative from each equivalence class of solutions while discarding the rest. Be careful — symmetry-breaking constraints do change the solution set (they remove solutions), so they are correct only when you want one solution per equivalence class, and two symmetry-breaking schemes can conflict and together remove all solutions if combined carelessly.

Tight constraints that fail early beat loose ones that fail late. A constraint's value lies in how soon it can say "no." The monolithic SEND+MORE equation is loose: with the big coefficients, almost any partial assignment of a few letters leaves a consistent completion, so the constraint stays silent until the end. The column equations are tight: fix two letters in a column and the third is often forced or refuted. In search terms, tight constraints prune near the root of the tree, where each pruned node removes an exponentially large subtree; loose constraints prune near the leaves, where each pruned node saves almost nothing. When you have a choice between two logically equivalent formulations, prefer the one whose individual constraints involve fewer variables and smaller coefficients.

Redundant (implied) constraints add no solutions but accelerate propagation. An implied constraint is one logically entailed by the existing model — it rules out no assignment that was previously allowed — yet adding it can transform performance, because propagators are incomplete and a redundant constraint may express a consequence that no existing propagator would ever derive. Examples: in a magic-square or Sudoku-style model, the sum of all cells in a unit equals a known total, a counting fact that alldifferent's matching algorithm does not expose; in job-shop, the constraint "makespan ≥ (total work on machine m)" for every machine, which immediately bounds the schedule from below; in cryptarithmetic, the implied inequality derived from the number of digits. Redundant constraints are free from a correctness standpoint (Step 4 still goes through unchanged) and cost only the time to propagate them, so they are usually worth trying.

Use the constraint graph as a diagnostic. Before running anything, look at the structure your model produces. Disconnected components can be solved independently. A tree-shaped graph is solvable in polynomial time. A graph with a small cutset invites cutset conditioning. A variable of very high degree (South Australia, or a single bottleneck machine) is a good first branching choice, which is exactly the intuition behind the degree heuristic. Models that produce sparse, structured graphs are typically far easier than models that produce dense ones, which is another reason to prefer decompositions that keep constraints local.

Put together, these principles explain why two correct models of the same problem can differ by many orders of magnitude in solving time, and why modeling — not solver implementation — is usually where practitioners spend their effort. The solver is a fixed engine; the model is the leverage.

Backtracking Search for CSPs

▶

A constraint satisfaction problem gives us three things: a set of variables X = {X₁,…,Xₙ}, a domain Dᵢ of candidate values for each variable, and a set of constraints C that restrict which combinations of values are allowed. Defining the problem, however, does not solve it. The question this topic answers is: given such a triple, how do we systematically explore the space of assignments so that we are guaranteed to find a solution if one exists, without drowning in the combinatorial explosion of possibilities? The answer — depth-first backtracking search — is remarkably simple to state, yet it is the algorithmic backbone on which every serious CSP solver is built. Everything that follows in the study of CSPs (inference, heuristics, backjumping, clause learning) is best understood as a modification of this one procedure.

From generate-and-test to backtracking. The most obvious way to solve a CSP is to enumerate every complete assignment and check each one against the constraints. This is generate-and-test. It treats the CSP as a black box: the generator produces a finished candidate, the tester returns true or false, and no information passes between them. The tester never says why a candidate failed, and the generator never uses that information to skip similar candidates. For n variables with domains of size d, the generator must produce dⁿ candidates in the worst case, and each is tested from scratch.

Consider the classic Australia map-colouring CSP: variables WA, NT, SA, Q, NSW, V, T, each with domain {red, green, blue}, and a binary inequality constraint between every pair of regions that share a border. Generate-and-test must consider 3⁷ = 2187 complete colourings. Now notice something that generate-and-test throws away: if WA = red and NT = red, the constraint WA ≠ NT is already violated, and every one of the 3⁵ = 243 colourings that extend this pair is doomed. Generate-and-test will nonetheless construct and test all 243 of them, one at a time.

Backtracking exploits the structural fact that constraints are not only properties of complete assignments — they apply to partial assignments as well. A constraint can be evaluated as soon as all the variables it mentions have values, and once it is violated it stays violated no matter what we do to the remaining variables, because assignments in standard backtracking are never undone except by backtracking itself. Therefore a violated constraint discovered at depth k prunes an entire subtree containing d^(n−k) complete assignments in a single step. This early detection of failure is the single biggest source of savings over blind enumeration; it is worth far more than any micro-optimisation of the constraint tests themselves.

Crucially, pruning costs us nothing in terms of correctness. Backtracking is a complete, systematic search: it explores a tree that contains every assignment not provably ruled out by a violated constraint, so if a solution exists it will be found, and if the search returns failure after exhausting the tree, we have a proof that the CSP is unsatisfiable. This distinguishes it from local search methods such as min-conflicts, which may find solutions quickly but can never certify unsatisfiability.

The backtracking algorithm. The procedure is a recursive depth-first search over partial assignments. Written as pseudocode:

function BACKTRACKING-SEARCH(csp):
    return BACKTRACK({}, csp)

function BACKTRACK(assignment, csp):
    # 1. Base case
    if assignment assigns a value to every variable in csp.X:
        return assignment                      # a complete, consistent assignment = solution

    # 2. Choose ONE unassigned variable
    var = SELECT-UNASSIGNED-VARIABLE(csp, assignment)

    # 3. Iterate over the values of its domain
    for each value in ORDER-DOMAIN-VALUES(var, assignment, csp):

        # 4. Test only against already-assigned variables
        if CONSISTENT(var, value, assignment, csp):
            assignment[var] = value            # extend
            result = BACKTRACK(assignment, csp)   # 5. recurse
            if result != failure:
                return result
            del assignment[var]                # 6. undo and try next value

    # 7. Every value failed: report failure to the caller
    return failure

Each numbered step corresponds directly to one idea. The base case is reached when the assignment is complete; because we only ever extended with consistent values, completeness here implies a solution — no final re-check of all constraints is needed. Selecting one unassigned variable and looping over its domain is what produces a single level of the tree per variable. The consistency test checks the new pair (var, value) only against variables that already have values. The recursive call deepens the search; if it returns failure, the loop undoes the assignment (restoring the state exactly) and tries the next value. When the loop runs out of values, the function returns failure, which causes the caller — the previous variable in the ordering — to abandon its current value and move on. That return of failure is the "backtrack".

Consistency checking of partial assignments. The efficiency of the inner loop rests on a precise rule: only constraints whose variables are all currently assigned need to be evaluated. A constraint that still mentions an unassigned variable cannot yet be violated, because some value might still satisfy it; evaluating it would be meaningless. In practice the test is even cheaper than this suggests. When we extend a consistent assignment with one new pair (X, v), every constraint not mentioning X was already satisfied and cannot have changed. So the incremental check only needs to examine the constraints that involve X together with already-assigned variables — in a binary CSP, this means looking at the assigned neighbours of X in the constraint graph. For sparse graphs this is a handful of comparisons per node, which is why backtracking's per-node cost is essentially constant even though the number of nodes may be large.

Unary constraints deserve special treatment. A constraint such as "South Australia must not be red" or "cell (3,7) of this Sudoku is fixed at 5" involves exactly one variable, so it can be enforced once, before search begins, by deleting the forbidden values from that variable's domain. This is called making the problem node-consistent. Pre-processing unary constraints shrinks the branching factor permanently and removes the need to re-test them at every node; after this step, the search loop deals only with binary, higher-order, and global constraints.

A vital conceptual point: a partial assignment that passes all applicable constraints is called consistent, and consistency is not the same as extendability. Consistency is a local, backward-looking property — nothing we have committed to so far contradicts anything else we have committed to. It carries no promise that the remaining variables can be filled in. In the 4-Queens trace, {Q₁=1, Q₂=3} is perfectly consistent, yet it cannot be extended to any solution; the search discovers this only by expanding and failing at the next level. The whole game of improving backtracking consists of detecting such dead ends sooner than brute recursion does.

Commutativity and the search tree. Why is it legitimate to pick one variable per level and ignore all the others at that node? Because CSPs are commutative: the result of applying a set of assignments does not depend on the order in which they are applied. The partial assignment {WA=red, NT=green} is the same object as {NT=green, WA=red}, and both constrain the future identically. A naive search that treated "assign WA next" and "assign NT next" as distinct decisions would generate the same set of assignments along n! different paths. Its tree would have branching factor (n − i)·d at level i and n!·dⁿ leaves, while containing only dⁿ distinct complete assignments — an enormous amount of duplicated work.

Backtracking exploits commutativity by committing to a single variable at each node. This yields a tree of depth exactly n, one level per variable, with branching factor at most d, and dⁿ leaves at most. No completeness is lost: every set of assignments is still reachable, just along one canonical path instead of n! permutations of it. An important consequence is that the solver is free to choose a different variable at each node, even dynamically, based on the current state — and this freedom is exactly what variable-ordering heuristics exploit later.

The space requirement, by contrast, is modest. Being depth-first, backtracking stores only the current path from the root — at most n variable–value pairs — plus whatever bookkeeping the implementation keeps for domains, giving O(n) space (or O(nd) if a copy of the current domains is maintained at each level for inference). This is the key practical advantage over breadth-first or best-first strategies, which would need to store exponentially many frontier nodes to search the same space.

Hard instances exhibit a characteristic pathology: a bad choice made near the root cannot be repaired locally, so the solver performs repeated deep failures before it ever reconsiders that early decision. Suppose in the Australia CSP the solver colours the regions in the order WA, Q, V, NT, NSW, T, SA. The variable SA borders five other regions, so it is the hardest to colour, yet it is assigned last. If the first six choices give five neighbours of SA three different colours among them, every value for SA fails — but the solver backtracks only one level, changes T (an island that constrains nothing), and fails at SA again, for every value of T. This rediscovery of the same conflict in subtree after subtree is called thrashing. It is caused not by a flaw in the algorithm's logic but by the mismatch between the chronological order of backtracking and the actual culprit of the failure. Its cure is better ordering (assign SA early) or smarter backing-up (jump straight back to a variable implicated in the conflict). The general lesson is that performance depends heavily on which variable and which value are chosen at each step — two runs of the same algorithm on the same instance can differ by many orders of magnitude in node count.

Where improvements come from. Notice that the pseudocode above deliberately leaves three procedures abstract: SELECT-UNASSIGNED-VARIABLE, ORDER-DOMAIN-VALUES, and the implicit opportunity to do inference after each assignment. These are the hooks through which every enhancement enters, and each corresponds to a natural question:

  • Which unassigned variable should be chosen next? Choosing the variable most likely to fail soon ("fail-first") makes dead ends shallow. The minimum-remaining-values rule picks the variable with the fewest legal values left; the degree rule breaks ties by picking the variable involved in the most constraints on unassigned variables. Applying MRV to the thrashing example would assign SAcode> early and eliminate the whole pathology.
  • In what order should the values of that variable be tried? Since any single value may lead to a solution, we want to try the most promising first. The least-constraining-value rule prefers the value that rules out the fewest choices for the neighbouring unassigned variables, keeping maximum flexibility for the rest of the search.
  • Can failures be detected earlier by propagating constraints after each assignment? Instead of merely checking the new value against past assignments, the solver can look forward: forward checking deletes the newly inconsistent values from the domains of unassigned neighbours and fails immediately if any domain becomes empty; arc consistency (AC-3, MAC) propagates these deletions transitively until no further pruning is possible. Both turn a future failure into a present one, pruning subtrees before they are ever entered.
  • Can the search learn from a failure to avoid repeating it elsewhere in the tree? Backjumping returns not to the chronologically previous variable but to the deepest variable in the conflict set that actually caused the dead end, skipping irrelevant levels such as T in the Australia example. Constraint learning (no-good recording) stores the offending combination as a new constraint so the same conflict is recognised instantly anywhere else in the tree — the idea that powers modern CDCL SAT solvers.
  • Restarts and randomisation attack the same problem from another angle: if a run exceeds a node budget, abandon it and restart with a different (randomised) ordering, escaping the "bad early choice" that caused the heavy tail of runtimes.

The essential property of all these refinements is that they are correctness-preserving. Variable ordering, value ordering, propagation, backjumping, and learning never remove an assignment that could be part of a solution; they only remove assignments that are provably doomed, or reorganise the order in which the surviving ones are visited. The solver therefore remains sound (any assignment it returns satisfies all constraints) and complete (it will find a solution if one exists, and certify unsatisfiability otherwise). What changes is purely the number of nodes explored — which is why the proper experimental measure of a CSP improvement is node count (or constraint checks) on a benchmark set, not merely wall-clock time on a single instance.

To put all of this together, a simple mental model is useful: backtracking search explores a tree whose nodes are consistent partial assignments, whose edges are single variable–value commitments, and whose leaves are either solutions (depth n) or dead ends (any depth). Generate-and-test, in these terms, looks only at the leaves at depth n and ignores the tree structure entirely. Backtracking uses the tree. Everything beyond backtracking is about pruning more of the tree, earlier, and about choosing the order in which its branches are visited.

A constraint satisfaction problem gives you variables, a domain of possible values for each variable, and constraints that say which combinations are allowed. The most obvious way to solve one is generate-and-test: enumerate every complete assignment and check it. That is hopelessly wasteful, because a single violated constraint can often be detected after assigning just two variables, yet generate-and-test keeps filling in the rest before noticing. Backtracking search fixes this by building assignments incrementally and testing consistency of the partial assignment at every step, abandoning a branch as soon as it is doomed.

The algorithm itself is short: pick an unassigned variable, try each value in its domain, check consistency with the assignment so far, recurse, and undo the choice if the recursion fails. Two ideas make it efficient. First, consistency checking of partial assignments prunes whole subtrees early. Second, commutativity — the order in which you assign variables does not change the resulting assignment — means the search tree only needs one variable per level instead of branching over all remaining variables, cutting the tree from n!d^n leaves to d^n. Even so, d^n is exponential, and the worst case remains intractable; CSP solving is NP-hard in general.

That exponential ceiling is exactly why the rest of the module matters: improvements come from choosing which variable to assign next, which value to try first, and how much inference to do after each assignment. Variable Ordering Heuristics

1

Variable Ordering Heuristics

▶

Backtracking search for a constraint satisfaction problem repeatedly answers two questions at every node of the search tree: which unassigned variable should I assign next? and which value from its domain should I try first? Variable ordering heuristics answer the first question. They do not change what the solver is able to find, nor do they change the definition of the problem — they change only the shape of the tree that the solver walks through. Because the size of that tree can differ by many orders of magnitude between a good ordering and a bad one, variable ordering is one of the cheapest and most dramatic improvements that can be added to a plain depth-first backtracking solver.

Why variable ordering matters. A backtracking solver that assigns one variable at a time explores a tree whose leaves at depth n correspond to complete assignments of the n variables. Any order of the variables along a root-to-leaf path produces the same set of complete assignments, because assignment is commutative: assigning A=red then B=blue yields exactly the same state as assigning B=blue then A=red. This is the key observation behind the claim that any complete ordering is still a complete search strategy. If a solution exists, a systematic backtracking solver will find it under any variable order; if none exists, it will prove unsatisfiability under any variable order. Correctness is therefore never at stake, and heuristics are purely about speed — about how many internal nodes are generated before the answer is reached.

Two further properties shape how these heuristics are designed:

  • They are usually dynamic. A static ordering fixes the sequence of variables once, before search begins. A dynamic ordering recomputes the choice at every node, using the current state of the domains after the assignments made so far (and after any propagation such as forward checking or arc consistency). Dynamic ordering is strictly more informative: the same variable may be a terrible choice at the root and an excellent choice ten levels down, once its domain has been pruned.
  • The goal is early contradiction. A backtracking search spends almost all of its time inside subtrees that contain no solution. The only way to make such a search fast is to discover that a subtree is doomed as high in the tree as possible, so the entire subtree below is never generated. Good variable ordering is therefore a technique for accelerating failure, not for accelerating success.

The practical effect is striking on structured problems. On map coloring with three colours, a naive alphabetical ordering can thrash through thousands of nodes re-discovering the same conflict; with a good ordering the solver frequently walks straight down to a solution with few or no backtracks at all. On Sudoku, a solver that always picks the next empty cell in row-major order may generate millions of nodes on a hard instance, while a solver that always picks the cell with the fewest candidate digits behaves much like a competent human player and often completes easy and medium puzzles backtrack-free — every choice it makes is forced, so the "search" degenerates into deduction.

Minimum Remaining Values (MRV). The MRV heuristic — also called the most constrained variable or fail-first heuristic — says: among the unassigned variables, choose the one with the fewest legal values remaining. "Legal" means consistent with the current partial assignment; in a solver with forward checking or maintained arc consistency, it simply means the current size of the live domain.

function SELECT-UNASSIGNED-VARIABLE(assignment, csp):
    best = None
    best_count = +infinity
    for each X in csp.variables where X not in assignment:
        count = |{ v in domain(X) : assignment ∪ {X = v} is consistent }|
        if count < best_count:
            best_count = count
            best = X
    return best

Three special cases explain most of MRV's power:

  • A domain of size 1 is a forced assignment. If a variable has exactly one surviving value, that value must appear in any solution extending the current partial assignment. Selecting it next creates a node with branching factor one — no choice, no risk of a wrong branch, and no need to ever reconsider it within this subtree. MRV automatically prefers such variables, so a solver equipped with MRV performs unit propagation "for free".
  • A domain of size 0 is immediate failure. If any unassigned variable has an empty domain, the current partial assignment cannot be extended to a solution. MRV finds that variable first (count = 0), the solver tries no values at all, and it backtracks immediately. Without MRV the solver might assign a dozen other variables before stumbling onto the wipe-out.
  • Smallest domain means smallest branching factor. If a variable has d remaining values, assigning it creates d children. Choosing the variable with minimum d minimises the fan-out at that node. Because the cost of a subtree is roughly the product of the branching factors along the path to it, reducing the branching factor near the top of the tree multiplies savings through everything below. Shrinking the root branching factor from 5 to 2 can, by itself, remove more than half the tree.

In Sudoku, MRV is exactly the human tactic known as the "naked single": scan the grid, find a cell whose row, column and box together eliminate all but one digit, write it in, and repeat. In map coloring with three colours, MRV will jump to a region whose neighbours already use two of the colours, because only one colour remains for it.

The fail-first principle. MRV is the best-known instance of a general design rule: to succeed, try first where you are most likely to fail. The justification is combinatorial rather than intuitive, and it is worth working through carefully.

Suppose a problem contains a variable Z that, given the current partial assignment, has no consistent value at all — it is already doomed. Suppose also that there are three other variables A, B, C, each with 5 legal values, which the solver chooses to assign first. The solver will now enumerate assignments to A, B and C, and only at depth four will it try Z and discover the conflict. But the conflict does not depend on A, B or C, so it will be rediscovered in every single one of the 5 × 5 × 5 = 125 sibling subtrees. The solver therefore performs 125 independent failures plus the ~155 internal nodes needed to generate them, where one failure would have sufficed. If Z is selected first, the solver tries zero values, fails once, and backtracks.

Several consequences follow:

  • Postponement duplicates work. A conflict that is independent of the intervening variables is re-derived once per combination of those variables.
  • The savings grow multiplicatively with depth. Catching a dead end k levels higher avoids on the order of dk nodes, where d is the average branching factor. This is why fail-first is not a small constant-factor optimisation but a change in the effective exponent of the search.
  • The tightest variable is the most informative. A variable with a small domain is close to being refuted; probing it extracts the maximum amount of information per node expanded.
  • Its limits. Fail-first is a heuristic about pruning failure, so it pays least on loosely constrained problems with many solutions scattered densely through the space — there, almost any first dive reaches a solution and ordering barely matters. It pays most on tightly constrained and over-constrained instances, and on problems near the satisfiability "phase transition". Crucially, the overhead is small and bounded, so while MRV may occasionally fail to help, it very rarely makes a solver appreciably worse.

The degree heuristic. MRV is silent at the very start of search: before any assignment has been made, every variable typically has a full domain, so all counts are tied. The degree heuristic breaks exactly this kind of tie by looking at the structure of the constraint graph rather than at domain sizes. The degree of an unassigned variable is the number of constraint edges connecting it to other unassigned variables; edges to already-assigned variables are ignored, because those constraints have already done whatever pruning they can. The heuristic selects the variable of maximum degree.

The rationale is the mirror image of MRV's. MRV asks "which variable is most constrained by the others?"; the degree heuristic asks "which variable most constrains the others?" Assigning a high-degree variable immediately applies a pruning pressure to the largest number of neighbours, shrinking many domains at once and thereby manufacturing the small domains that MRV can then exploit at the next node.

Combining MRV and degree in practice. The standard composite rule is lexicographic: rank candidates by smallest remaining domain; among those tied for smallest, choose the one with the highest degree to unassigned variables; break any remaining ties deterministically.

function SELECT-VARIABLE(assignment, csp):
    unassigned = [X for X in csp.variables if X not in assignment]
    # primary key: smallest domain  (ascending)
    # secondary key: highest degree (descending)
    # tertiary key: variable index  (ascending, for determinism)
    return min(unassigned,
               key = lambda X: (len(curr_domain[X]),
                                -unassigned_degree(X),
                                index(X)))

Points of practical importance when implementing this:

  • Deterministic tie-breaking. Residual ties can be broken arbitrarily, but breaking them by a fixed variable index (or any stable rule) makes runs reproducible, which matters enormously when you are counting nodes to compare heuristics, debugging a backtracking bug, or writing unit tests. Random tie-breaking is sometimes used deliberately in restart-based solvers to diversify search, but it should then be seeded and recorded.
  • Keep the overhead small. The heuristic is evaluated at every node, so a naive implementation that recomputes each variable's legal-value count by re-testing all constraints can cost more than it saves. Instead, maintain the live domains explicitly and keep an incremental counter of each domain's size, updated by the propagation routine as values are removed and restored on backtracking (for example with a trail or a time-stamped structure). Then selection is a single O(n) scan, or O(log n) with an indexed priority queue. Similarly, maintain each variable's unassigned-degree incrementally: when a variable is assigned, decrement the counter of each of its neighbours; increment them again when it is unassigned.
  • Pair it with value ordering. Variable ordering decides where to branch; the least-constraining-value heuristic decides in what order to try the branches, preferring the value that rules out the fewest options for the remaining neighbours. The two are complementary: fail-first on variables narrows the tree, succeed-first on values steers the first dive toward a solution. Used together with forward checking, they are what typically turns a toy solver into one that handles realistic instances.
  • It needs propagation to shine. MRV's domain counts are only informative if something is actually shrinking the domains. With pure chronological backtracking and consistency checks only against assigned variables, MRV still works but is much weaker; with forward checking or MAC (maintaining arc consistency), the counts become sharp and the heuristic becomes powerful. This combination of MRV plus degree plus propagation is, for graph colouring, essentially the classical DSATUR strategy.

A short worked trace makes the mechanism concrete. Take a 3-colouring of the Australia CSP with domains {R, G, B}. Plain alphabetical order assigns NSW, NT, Q, SA, T, V, WA. The solver happily sets NSW=R, NT=R, Q=G, then reaches SA, which borders NSW(R), NT(R), Q(G) and so can only be B; it continues, and whenever a later conflict forces backtracking it re-explores assignments to T — a variable constrained by nothing — wasting a factor of three on every such excursion. Now run MRV+degree. At the root all domains have size 3, so degree decides: SA (degree 5) is chosen and set to R. Forward checking reduces WA, NT, Q, NSW and V to {G, B}; T remains {R, G, B}. MRV now prefers any of the five size-2 variables, and degree breaks the tie toward NT or Q (degree 2 among unassigned) over WA or V. Setting NT=G prunes WA and Q to {B}; MRV then seizes those size-1 domains and assigns them without any choice. The whole mainland is coloured with essentially no branching, and T — the least constrained variable — is handled last, where its three options cost nothing because no backtracking occurs beneath it.

Finally, it is worth knowing that MRV and degree are the base of a family. Weighted-degree heuristics such as dom/wdeg attach a weight to each constraint, increment that weight every time the constraint causes a domain wipe-out, and then select the variable minimising domain size divided by accumulated constraint weight. This lets the solver learn during search which parts of the problem are really the hard ones, rather than relying on the static graph. Activity- and impact-based orderings do something similar by measuring how much search-space reduction each variable has historically produced. All of them, however, are refinements of the same two ideas presented here: branch where the domain is smallest, and, when that is uninformative, branch where the influence is greatest.

That choice can change the size of the search tree by orders of magnitude, even though every ordering eventually finds the same solutions. Value Ordering and Search Efficiency

Value Ordering and Search Efficiency

▶

Backtracking search for constraint satisfaction problems makes two decisions at every node of the search tree. First it asks which variable should I assign next? — answered by variable-ordering heuristics such as minimum-remaining-values (MRV) and the degree heuristic. Then it asks in what order should I try that variable's remaining values? — answered by value-ordering heuristics, of which the least-constraining-value (LCV) heuristic is the canonical example. These two questions look symmetric, but they are governed by opposite logics. Variable ordering wants to fail fast; value ordering wants to fail last. Understanding why that asymmetry exists, and measuring how much it actually buys you on real instances, is the substance of this topic.

Why Value Ordering Matters

Consider a CSP solver part-way through a search. It has a partial assignment, it has just selected an unassigned variable X using its variable-ordering rule, and X has a current domain of, say, five surviving values. The solver must now generate child nodes — one per value — and recurse into them in some sequence. The set of children is fixed by the domain; only their order is under the solver's control.

This immediately tells us something important about the limits of value ordering. If the subproblem below this node has no solution at all, then every one of the five branches will eventually be explored and refuted, and the total work done is identical no matter which order we use. Value ordering cannot prune a subtree that must be exhausted; it can only change when we find a solution inside a subtree that contains one. Formally: for proving unsatisfiability, value ordering is work-neutral (up to small constant-factor effects on propagation); for finding the first solution, it can be the difference between zero backtracks and an exponential search.

That is exactly the common case in practice. Most applied CSPs — scheduling a timetable, colouring a map, placing queens, allocating registers — are satisfiable, and the user wants one consistent complete assignment, not an enumeration of all of them. In that regime, a good value order steers the search down a "corridor" of choices that remain mutually compatible, and the solver walks almost straight down to a leaf.

Conversely, poor value ordering wastes effort on branches that are doomed by constraints on neighbouring variables even though they are locally consistent. A value may be perfectly legal with respect to everything assigned so far and still annihilate the last remaining option of some unassigned neighbour. Plain backtracking without inference will not notice until it descends several levels deeper, assigns that neighbour's variable, discovers no value works, and unwinds. Every node visited in that doomed subtree is pure waste.

A small concrete illustration. Take map colouring with colours {Red, Green, Blue} on this fragment: region A is adjacent to B, C, and D; region B is additionally adjacent to C; and D has already been forced to {Green, Blue} by an earlier assignment. Suppose the variable-ordering heuristic picks A, whose domain is still {Red, Green, Blue}. Choosing Green for A strips Green from B, C, and D — leaving D with only {Blue}, a knife-edge situation. Choosing Red for A strips Red from B and C but costs D nothing, because Red was already gone from D's domain. Red is the less damaging choice, and a value-ordering heuristic that can see this will try it first.

The Least-Constraining-Value Heuristic

LCV formalises exactly the reasoning in that example. For the chosen variable X and each candidate value v in its current domain:

  • Tentatively assume X = v.
  • For every unassigned variable Y that shares a constraint with X, count how many values of Y's current domain become inconsistent with X = v.
  • Sum those counts over all such neighbours Y. This sum is the elimination count (or "conflict count") of v.
  • Sort the domain in increasing order of elimination count and try the smallest first.

The intuition is leave the maximum number of options open for the rest of the assignment. A value that removes two options from the remaining problem leaves a richer, more flexible residual CSP than one that removes eleven. Since we only need one solution, we want to walk into the roomiest part of the space, where a consistent completion is most likely to exist and most likely to be found quickly. This is the "fail-last" or "succeed-first" principle, and it is the mirror image of the fail-first principle used for variable selection.

Worked example on the map fragment above, with current domains B = {Red, Green, Blue}, C = {Red, Green, Blue}, D = {Green, Blue}:

Candidate value for AValues killed in BValues killed in CValues killed in DElimination countLCV rank
Red1 (Red)1 (Red)0 (Red absent)21st — try first
Green1 (Green)1 (Green)1 (Green)32nd (tie)
Blue1 (Blue)1 (Blue)1 (Blue)32nd (tie)

LCV therefore orders A's domain as Red, then Green/Blue (ties broken arbitrarily or by a static tiebreak such as domain index). Note what LCV did not do: it did not prune anything. All three values remain available; only the order changed.

Pseudocode for the heuristic, assuming a domains structure holding current (possibly pruned) domains:

function LCV_ORDER(X, assignment, domains, csp):
    scored = []
    for v in domains[X]:
        eliminated = 0
        for Y in NEIGHBOURS(X, csp):
            if Y is assigned: continue
            for w in domains[Y]:
                if not CONSISTENT(X, v, Y, w, csp):
                    eliminated = eliminated + 1
        scored.append( (eliminated, v) )
    sort scored by eliminated ascending
    return [v for (eliminated, v) in scored]

Two implementation facts follow directly from this code. First, LCV needs live domains. If domains[Y] is always the original static domain, the counts are the same at every node and LCV degenerates into a fixed static ordering that carries no information about the current state of the search. To be meaningful, LCV must be paired with a constraint-propagation step — forward checking at minimum, or arc consistency maintenance (MAC/AC-3) for sharper domains — so that the counts reflect what is genuinely still available. In fact the inner loops of LCV and of forward checking are the same loops, so a good implementation computes the elimination counts and the pruned domains in one pass and caches the result for the branch it eventually takes.

Second, LCV is not free. The cost at a node is O(d · k · d) = O(k·d²) consistency checks, where d is domain size and k the number of unassigned neighbours. For d = 3 (map colouring) that is trivial. For d = 500 (a scheduling variable with 500 possible start times) and a dense constraint graph, the heuristic computation can cost more than the search it saves.

And again, the hard limitation: on unsatisfiable instances LCV gives no benefit. If the subtree below the current node contains no solution, every value must be tried and refuted; reordering the refutations changes nothing but adds the heuristic's own overhead. Worse, on an unsatisfiable instance LCV systematically tries the least constrained value first, which is the value whose subtree tends to be the largest and slowest to refute — so the measured runtime can be marginally worse than with an arbitrary order.

Combining Variable and Value Ordering

In a well-built solver, three heuristics operate at each node in a fixed pipeline:

  • MRV (minimum remaining values) chooses the unassigned variable with the fewest legal values left. This is the fail-first principle: if some variable is going to fail, discover it as high in the tree as possible, because a failure near the root prunes an exponentially larger subtree than a failure near a leaf. In the extreme, if a variable's domain has been reduced to size zero, MRV picks it and the branch dies immediately; if it has size one, that assignment is forced and branching factor 1 costs nothing.
  • Degree heuristic breaks MRV ties by choosing the variable involved in the most constraints with unassigned variables. Among equally constrained variables, assigning the one with the highest connectivity propagates the most information and reduces the branching factor of the remaining subproblem the fastest. It is also used standalone at the very first node, where every domain is full and MRV has no information to offer.
  • LCV then orders the chosen variable's values so that the branch most likely to lead to a solution is visited first.

The division of labour is clean: fail-first variable choice shapes the tree; fail-last value choice chooses a path through it. Variable ordering affects both satisfiable and unsatisfiable instances because it genuinely changes the size and shape of the search tree — a different variable order yields a structurally different tree. Value ordering does not change the tree at all; it changes only the order in which a fixed tree is traversed, which matters only when traversal can stop early (i.e., on success).

A skeleton of the combined solver:

function BACKTRACK(assignment, domains, csp):
    if assignment is complete: return assignment
    X = SELECT_UNASSIGNED_VARIABLE(domains, csp)      # MRV, ties by degree
    for v in ORDER_DOMAIN_VALUES(X, assignment, domains, csp):   # LCV
        if CONSISTENT(X = v, assignment):
            assignment[X] = v
            new_domains = FORWARD_CHECK(X, v, domains, csp)      # inference
            if no domain in new_domains is empty:
                result = BACKTRACK(assignment, new_domains, csp)
                if result != failure: return result
            remove X from assignment                             # undo
    return failure

Both heuristic families depend on new_domains being accurate, which is why inference is not optional once you adopt these heuristics. Without forward checking, MRV sees only the static domains minus values conflicting with assigned variables (a weak approximation), and LCV sees nothing useful at all. The usual packaging in textbooks and solvers is therefore "MRV + degree + LCV + forward checking" or, stronger, "MRV + degree + LCV + MAC".

A subtle point worth internalising: MRV and LCV can appear to contradict each other — one minimises options, the other maximises them — but they act on different objects. MRV minimises the options of the variable we commit to (so that commitment is cheap and informative); LCV maximises the options of everything we have not yet committed to (so the remaining problem stays easy). There is no conflict.

Measuring Search Efficiency with Node Counts

Runtime in seconds is a poor primary metric for comparing CSP heuristics: it depends on language, hardware, data structures, and constant factors unrelated to search behaviour. The standard machine-independent metric is the node count — the number of partial assignments the search actually examines, i.e., the number of times the recursive BACKTRACK body is entered, or equivalently the number of variable assignments attempted. Related counters give a fuller picture:

MetricWhat it countsWhat it tells you

Constraint checks deserve emphasis. A heuristic combination can cut nodes by 100× while raising constraint checks by 200×, in which case it is a net loss. Reporting nodes alone hides this; reporting nodes and checks and time makes the trade-off visible. This is precisely the trap with LCV on large domains.

Sound experimental method requires a few further disciplines:

  • Use plain chronological backtracking as the baseline. Every heuristic variant is reported as a ratio or factor against it, so results are comparable across problem sizes.
  • Average over many random instances. A single instance may be solved on the first descent by sheer luck, or may happen to be pathological. Reporting the mean (and ideally median and spread) over, say, 50–100 randomly generated instances per size smooths out this variance. Medians are often more informative than means because node-count distributions are heavy-tailed: a handful of instances can dominate the mean.
  • Fix a node or time cut-off and report the number of unsolved instances separately, rather than letting one runaway instance distort the average.
  • Control the random seed and the tie-breaking rule, since arbitrary tie-breaks in MRV or LCV can themselves swing results by a large factor.
  • Vary constrainedness. Results on easy, under-constrained instances say little; the interesting region is near the phase transition where satisfiable and unsatisfiable instances are roughly equally likely and search cost peaks.

Practical Guidance and Limitations

Pulling the empirical and theoretical threads together into usable rules of thumb:

  • Adopt MRV plus degree plus forward checking almost unconditionally. They are cheap to compute incrementally, they help on both satisfiable and unsatisfiable instances, and they are the source of the order-of-magnitude savings. If you implement only one thing, implement this.
  • Treat LCV as an optional refinement for satisfiable, single-solution problems. It shines when you need one solution to a large, loosely-to-moderately constrained problem and domains are small. It is useless when enumerating all solutions, useless on unsatisfiable instances, and useless when proving optimality in a branch-and-bound setting where the whole relevant tree is explored anyway.
  • Watch the cost on large domains. Scoring every value at every node is O(k·d²); with d in the hundreds or thousands this can dominate total runtime. Mitigations include computing LCV scores only at shallow depths (where the pay-off is largest), scoring only a sampled subset of values, using a cheaper proxy such as "count of neighbours for which this value is the sole support", or caching scores and recomputing only when a neighbour's domain changes.
  • Random or static value ordering is often good enough. On loosely constrained problems, almost any value works and the first descent succeeds regardless; LCV then only adds overhead. Randomised value ordering has an additional virtue: combined with restarts, it avoids the deterministic solver's tendency to make the same early mistake every time (heavy-tailed runtime distributions), and random restarts frequently beat sophisticated value ordering on structured industrial instances.
  • Ties and domain-specific knowledge matter. LCV frequently produces large ties (in the map-colouring table above, Green and Blue tied exactly). How you break those ties can swing node counts by a factor of several, so break them deliberately — by a problem-specific preference, by a random choice with a fixed seed, or by a secondary score such as "prefer the value that leaves the largest minimum neighbour domain" — and report the rule you used.
  • Always profile the specific problem class. Heuristic performance does not transfer reliably between problem families. A combination that is superb on N-Queens may be mediocre on job-shop scheduling, where domains are large and LCV's quadratic scoring bites, or on Sudoku, where MRV with propagation alone solves most published puzzles with essentially no search. Build the node/backtrack/check/time counters into the solver from the start, generate a representative instance set spanning easy, critical, and over-constrained regimes, and measure.
  • Know when the whole framework is the wrong tool. For very large satisfiable instances such as million-queens, systematic backtracking with any ordering heuristics is outclassed by local search (e.g., min-conflicts), which solves such problems in near-linear time. Ordering heuristics improve systematic search; they do not rescue it from problems it is structurally unsuited to.

The overall picture is therefore one of a clear hierarchy of returns. Inference (forward checking, arc consistency) and fail-first variable ordering do the heavy lifting, reshaping an exponential tree into something tractable. Value ordering is a finishing touch: valuable, cheap to try, occasionally decisive on satisfiable instances, and provably irrelevant when the search must prove that no solution exists. A disciplined experimental protocol built on node counts, constraint checks, and averaging over many instances is what lets you tell those cases apart for your own problem rather than guessing.

Backtracking search for constraint satisfaction problems makes two kinds of choices at every step: which variable to assign next, and which value from that variable's domain to try first. Variable ordering heuristics such as minimum remaining values (MRV) and degree try to expose failure early so that dead ends are pruned quickly. Applying and Evaluating CSP Solvers

1

Applying and Evaluating CSP Solvers

▶

A constraint satisfaction problem is easy to define on paper and surprisingly fiddly to solve well in code. The gap between the two is where this topic lives. Once you have written down a CSP as a triple of variables, domains, and constraints, you still need a program that explores assignments systematically, a way to plug different search strategies into that program without rewriting it, a set of honest measurements that tell you which strategy actually helps, and the engineering discipline to know whether a disappointing result means "this heuristic is weak" or "my model is wrong." This topic walks through a pluggable backtracking solver, applies it to two very different case studies — Sudoku and scheduling — and then turns to measurement, debugging, and the judgement call of whether CSP is the right tool at all.

Building a pluggable backtracking solver

The first design decision is the data representation. A CSP is naturally stored as three cooperating structures: an ordered collection of variables (usually just names or integer indices), a domain map from each variable to the set of values it may still take, and a constraint list. The crucial detail is what a constraint object looks like. A constraint needs two parts:

  • a scope: the tuple of variables the constraint talks about, and
  • a satisfaction test: a predicate that, given values for the variables in the scope, returns true or false.

Separating scope from test is what makes the solver generic. The search engine never needs to know whether a constraint means "different colours," "task A finishes before task B," or "all nine cells differ." It only needs to know which variables a constraint touches (so it can decide when the constraint is testable) and how to evaluate it. A useful refinement is to let the test accept a partial assignment and return true whenever the constraint is not yet fully determined — a convention that makes consistency checking on partial assignments trivial.

class Constraint:
    def __init__(self, scope, test, name=""):
        self.scope = tuple(scope)     # e.g. ("WA", "NT")
        self.test  = test             # callable over values in scope order
        self.name  = name

    def holds(self, assignment):
        # Unassigned variables in scope => not yet violated.
        if any(v not in assignment for v in self.scope):
            return True
        return self.test(*[assignment[v] for v in self.scope])

class CSP:
    def __init__(self, variables, domains, constraints):
        self.variables   = list(variables)
        self.domains     = {v: set(domains[v]) for v in variables}
        self.constraints = list(constraints)
        # index: variable -> constraints whose scope contains it
        self.involving = {v: [c for c in constraints if v in c.scope]
                          for v in variables}

The involving index matters more than it looks. Without it, every consistency check scans every constraint, which turns an O(d) check into an O(|C|) sweep and dominates runtime on large models. With it, after assigning X you only re-test constraints whose scope contains X; every other constraint's truth value is unchanged.

The recursive core is then short. It is depth-first search over partial assignments with chronological backtracking:

def backtrack(csp, assignment, domains, stats,
              select_var, order_values, inference):
    stats["nodes"] += 1
    if len(assignment) == len(csp.variables):
        return dict(assignment)                 # complete and consistent

    var = select_var(csp, assignment, domains)  # pluggable
    for value in order_values(csp, var, assignment, domains):  # pluggable
        assignment[var] = value
        stats["checks"] += 1
        if consistent(csp, var, assignment):
            saved = snapshot(domains, csp)      # trail or copy
            if inference(csp, var, value, assignment, domains, stats):
                result = backtrack(csp, assignment, domains, stats,
                                   select_var, order_values, inference)
                if result is not None:
                    return result
            restore(domains, saved)             # undo pruning exactly
        del assignment[var]                     # undo the assignment
        stats["backtracks"] += 1
    return None

def consistent(csp, var, assignment):
    return all(c.holds(assignment) for c in csp.involving[var])

Read the loop body as a strict four-step cycle: assign, check, recurse, undo. Every one of those steps has to be exactly reversible, or state leaks between branches and the solver silently loses solutions. Notice also that only constraints involving the newly assigned variable are tested — the rest were already verified at shallower levels of the tree.

The three parameters select_var, order_values, and inference are the plug points, and they all share a key property: every implementation must be interchangeable without changing the engine. That is what makes systematic experimentation possible later. Typical implementations:

Each is a plain function with a fixed signature, so a configuration is just a tuple of three callables:

def mrv(csp, assignment, domains):
    unassigned = [v for v in csp.variables if v not in assignment]
    return min(unassigned, key=lambda v: (len(domains[v]), -degree(csp, v, assignment)))

def lcv(csp, var, assignment, domains):
    def cost(val):
        return sum(1 for n in neighbours(csp, var) if n not in assignment
                     for w in domains[n] if conflicts(csp, var, val, n, w))
    return sorted(domains[var], key=cost)

config = (mrv, lcv, forward_check)   # swap any component independently

Restoring state exactly. Inference prunes domains; backtracking must un-prune them. There are two correct approaches and one tempting wrong one.

  • Trail (undo log). Every deletion is pushed onto a stack as a (variable, value) pair together with a mark for the current depth. On backtrack, pop entries back to the mark and re-insert each value. Cost is proportional to the number of values actually pruned, which is usually tiny. This is what real solvers use.
  • Copy-on-write / snapshot. Copy the domain map (or just the domains of variables about to be touched) before inference, and restore the copy on failure. Simpler to get right, costs O(n·d) per node in the naive version — acceptable for teaching and for small models.
  • The wrong one: recomputing domains from scratch "from the current assignment." This looks clean but quietly discards pruning that came from deeper inference and reintroduces values that a correct trail would keep removed higher up the tree, or worse, forgets values that were removed by earlier levels. Restoration must return the state to exactly its prior condition, not to a plausible approximation of it.
class Trail:
    def __init__(self): self.entries, self.marks = [], []
    def mark(self):     self.marks.append(len(self.entries))
    def prune(self, domains, var, val):
        domains[var].discard(val); self.entries.append((var, val))
    def undo(self, domains):
        back = self.marks.pop()
        while len(self.entries) > back:
            var, val = self.entries.pop()
            domains[var].add(val)

Instrumentation. A solver that returns only an answer is unmeasurable. Thread a stats dictionary through the recursion and increment it at well-defined events: nodes (each call to backtrack, i.e. each partial assignment explored), checks (each evaluation of a constraint's satisfaction test), backtracks (each time a value is withdrawn after failure), pruned (each value removed by inference), and optionally max_depth and revisions for AC-3 queue operations. Define these events precisely and keep the definitions fixed across configurations, otherwise your comparisons are meaningless. Also give the solver a timeout or node_limit parameter so that a hopeless configuration terminates rather than hanging an experiment.

Case study: solving Sudoku

Sudoku is the ideal first client of the solver because the model is clean, the instances are graded by difficulty, and the effect of heuristics is dramatic.

The model. There are 81 variables, one per cell, conventionally named by row letter and column digit (A1…I9). Each domain is {1,…,9}. The constraints are 27 all-different global constraints: 9 for the rows, 9 for the columns, 9 for the 3×3 boxes.

rows, cols = "ABCDEFGHI", "123456789"
cells = [r+c for r in rows for c in cols]
units = ([[r+c for c in cols] for r in rows] +            # 9 rows
         [[r+c for r in rows] for c in cols] +            # 9 columns
         [[r+c for r in rs for c in cs]                   # 9 boxes
          for rs in ("ABC","DEF","GHI") for cs in ("123","456","789")])

alldiff = lambda *vals: len(set(vals)) == len(vals)
constraints = [Constraint(u, alldiff, "alldiff") for u in units]

The 27 global constraints can be decomposed into 810 binary not-equals constraints (each unit contributes 36 pairs; shared cells mean 810 distinct pairs overall) if your engine only understands binary constraints. The decomposition is logically equivalent for checking a complete assignment but strictly weaker for propagation: a global alldiff can run Régin's matching-based filtering and deduce, for example, that if three cells in a row have domains {4,7}, {4,7}, {4,7} then no other cell in that row may take 4 or 7 — a "naked triple" that pairwise ≠ constraints cannot see. This is a concrete illustration of why global constraints are worth representing as such.

Encoding the clues. A given clue can be modelled in two ways. The first is as a unary constraint A1 = 5, which is uniform and keeps the puzzle data inside the constraint list. The second — almost always better — is to apply unary constraints once at setup time and pre-reduce the domain to a singleton: domains["A1"] = {5}. Node consistency is enforced before search even begins, every subsequent consistency check is cheaper, and MRV immediately sees those cells as having domain size 1. Many implementations go one step further and run constraint propagation over the clues before the first search node, which on easy puzzles solves the whole grid with zero search.

What the heuristics do. Plain chronological backtracking assigns A1, A2, A3, … in order. On an easy puzzle it may be fine; on a hard one it is catastrophic, because a contradiction created by a choice in row A may not be detected until the search reaches row G, whereupon the solver has to undo and re-explore an enormous subtree. Worse, the famously hard "anti-backtracking" puzzles are constructed specifically so that left-to-right, top-to-bottom value trials fail as late as possible. MRV changes the dynamic completely: the solver always jumps to the most constrained cell, which after propagation is usually a cell with two candidates, and a wrong guess there is refuted almost immediately. Combined with forward checking, typical newspaper "hard" puzzles are solved with single-digit backtrack counts; many are solved with none at all. Representative figures on a 17-clue puzzle look like this:

Note also that LCV is nearly useless on Sudoku. LCV helps when a problem has many solutions and you want to steer toward one; a well-formed Sudoku has exactly one solution, so there is no "roomier" branch to steer toward and the ordering overhead is pure cost. This is a genuinely useful negative result to obtain experimentally.

Independent verification. Never report "solved" on the basis of the solver's internal state. The solver's belief that an assignment is consistent is computed by the same constraint objects that may be buggy, and by inference code that may have pruned something it shouldn't. Write a separate checker that takes the returned 81 values and re-validates all 27 units from scratch, plus checks that every clue cell still holds its given value:

def verify_sudoku(grid, clues):
    assert all(grid[c] in range(1, 10) for c in cells), "value out of domain"
    for u in units:
        vals = [grid[c] for c in u]
        assert sorted(vals) == list(range(1, 10)), f"unit {u} invalid"
    for c, v in clues.items():
        assert grid[c] == v, f"clue {c} overwritten"
    return True

Assert this on every returned solution in your test suite. It costs microseconds and catches whole classes of modelling bug.

Graded test sets. Evaluate on a ladder of difficulty rather than one puzzle: a handful of easy puzzles solvable by propagation alone, a set of medium puzzles requiring a little search, a set of hard puzzles with 20–24 clues, the standard 17-clue minimal puzzles, and a few adversarial instances (e.g. "platinum blonde," "AI escargot") built to defeat naive search. The point of grading is to find the crossover — the difficulty level at which each configuration starts to struggle. A configuration that solves everything instantly tells you nothing; a configuration that fails everything tells you nothing. The informative data lies at the boundary.

Case study: scheduling instances

Scheduling exercises a different part of the solver. Sudoku is uniform, tightly constrained, and has exactly one solution; scheduling models are irregular, mix several constraint types, and are frequently infeasible as first written.

Variables and domains. Variables are the things being placed: tasks on a shop floor, meetings, exams, lectures, shifts. Domains are the places they can go: discrete time slots, or — when resources are also being chosen — pairs of slot and resource, e.g. (Tuesday 10:00, Room B). Pairing inflates the domain multiplicatively (20 slots × 6 rooms = 120 values) but keeps the model simple, since room clashes become ordinary constraints over paired values. The alternative is two variables per task, start_T and room_T, which keeps domains small and lets MRV reason about them separately, at the cost of more variables and more constraints. Either is defensible; choosing deliberately, and being able to say why, is part of modelling skill.

Three constraint families in one model.

  • Binary non-overlap (disjunctive). For two tasks sharing a machine or a person: end(A) ≤ start(B) OR end(B) ≤ start(A). With fixed durations this is a binary constraint over start times: |start(A) − start(B)| ≥ dur when durations are equal, or the asymmetric form otherwise. These constraints are the backbone of job-shop models.
  • Precedence. start(B) ≥ start(A) + dur(A): operation 2 of a job cannot begin until operation 1 completes; the exam board cannot meet before marking finishes. Precedence constraints are directed and propagate extremely well — forward checking on a precedence chain pushes the earliest start times forward in one sweep.
  • Global resource capacity. At most k tasks may occupy a slot, or the total demand on a resource must not exceed its capacity. In CSP terms this is a cumulative or at-most-k global constraint over all tasks that could use the resource. Decomposing it into pairwise constraints is impossible in general (you cannot express "at most 3 in this room" with binary ≠), which is a clean motivating example for higher-order and global constraints.
# Exam timetabling fragment
slots  = range(0, 15)                       # 15 exam periods
exams  = ["AI", "DB", "OS", "NET", "ML"]
domains = {e: set(slots) for e in exams}

shared = [("AI","ML"), ("AI","DB"), ("DB","OS"), ("NET","OS")]   # cohort clashes
cons  = [Constraint((a,b), lambda x,y: x != y, "clash") for a,b in shared]
cons += [Constraint(("AI","ML"), lambda x,y: abs(x-y) >= 2, "rest gap")]
cons += [Constraint(tuple(exams),
                    lambda *s: all(list(s).count(t) <= 2 for t in set(s)),
                    "at most 2 exams per period")]          # global capacity

Infeasibility and thrashing. Many real scheduling instances are over-constrained: there simply is no assignment satisfying every hard constraint. A complete solver must then prove infeasibility by exhausting the search space, and naive backtracking does this appallingly badly. The classic failure mode is thrashing: the solver repeatedly rediscovers the same local contradiction deep in the tree — say, three exams that all clash and only two usable slots — but, because it backtracks chronologically to the most recent decision, it undoes an irrelevant choice and re-enters the same doomed region with a different, equally irrelevant prefix. The fixes in increasing order of sophistication:

  • Propagation at the root. Run AC-3 before search; many infeasible instances collapse to an empty domain immediately and are reported infeasible in milliseconds.
  • MRV plus degree. Forces the solver into the tightest part of the problem first, so the contradiction is found at shallow depth where the proof of infeasibility is small.
  • Backjumping / conflict-directed backjumping. Jump back to the variable actually responsible for the conflict rather than the chronologically last one.
  • No-good recording / clause learning. Remember the conflicting combination so the same dead end is never re-entered.

At minimum, any solver used on scheduling data must have a timeout and must distinguish three outcomes honestly: SOLVED, PROVEN INFEASIBLE, and UNKNOWN (timeout). Reporting a timeout as "no solution" is a serious error — it is the difference between "there is no timetable" and "I gave up."

Adding slack. When a model is genuinely infeasible, the right response is usually to change the model, not the solver. Options:

  • Widen domains: add more time slots, extra rooms, an evening session, a sixth machine. Going from 15 exam periods to 18 often converts infeasible to trivially feasible.
  • Relax soft preferences. Distinguish hard constraints (no student sits two exams at once) from soft ones (lecturers prefer mornings; no student sits three exams in two days). Drop or demote the soft ones and re-solve. If you need to keep them, re-model as a constraint optimisation problem with penalties rather than a pure CSP.
  • Relax quantitative margins. Reduce a required rest gap from 48 hours to 24; allow a room to hold 40 rather than 35.
  • Allow explicit violation variables. Add a Boolean or integer "unplaced" value to each domain and constrain the number of unplaced tasks, turning "no solution" into "a solution that leaves two exams unscheduled," which is far more useful to a human planner.

A disciplined workflow is to compute a minimal unsatisfiable core by hand or by deletion: remove constraints one at a time, re-solve, and find a small subset that is still infeasible. Telling a timetabling officer "exams AI, ML and DB mutually clash and only two periods are open to all three" is actionable; telling them "infeasible" is not.

Why MRV and degree matter more here. Sudoku's constraint graph is perfectly regular — every cell has exactly 20 neighbours. Scheduling graphs are wildly irregular: a core first-year module shared by 800 students may clash with thirty other exams, while a niche elective clashes with two. Degree heuristics exploit exactly this asymmetry by scheduling the hub variables first, when the calendar is still empty and there is room to place them; leaving them until last is how you end up with a popular exam that has no legal slot. MRV then tracks the dynamic consequences of those placements. Empirically, on irregular graphs the MRV + degree combination often changes the node count by several orders of magnitude, whereas on a regular graph like Sudoku's the degree tie-break contributes comparatively little because all degrees are equal at the start.

Measuring solver performance

Once the solver is pluggable, the interesting question becomes empirical: which configuration is actually better, and on what? Answering that honestly requires discipline, because it is very easy to produce impressive-looking numbers that mean nothing.

Hardware-independent counters. The primary measures should be counts of search events, not seconds, because counts are reproducible on any machine, in any language, under any system load:

  • Nodes expanded — partial assignments considered. The canonical measure of search tree size.
  • Backtracks — failures that forced a value to be withdrawn. Closely tracks nodes but highlights wasted work specifically.
  • Constraint checks — evaluations of a satisfaction test. This is the measure that exposes the hidden cost of inference: AC-3 may expand ten times fewer nodes while performing a hundred times more checks.
  • Values pruned — domain deletions performed by inference, a direct measure of how much work propagation is doing.

And wall-clock time anyway. Counters alone can mislead in the opposite direction. A node under MAC is far more expensive than a node under plain backtracking; a node under LCV requires scanning every neighbour's domain before the first value is even tried. If you compare configurations only by nodes expanded, you will reliably conclude that the heaviest inference wins, and you will be wrong about half the time. Report both, and report the cost per node (time ÷ nodes, or checks ÷ nodes) to make the trade-off explicit.

The ablation grid. The clean experimental design is a factorial sweep in which each component is turned on and off independently, so any observed effect can be attributed to a specific component rather than to a bundle of changes:

The MRV × forward-checking cell deserves attention. MRV needs current domain sizes to be meaningful; with no inference at all, domains never shrink and MRV degenerates towards a static order broken only by the initial unary reductions. This is why the two are usually reported together and why an ablation grid, rather than a one-at-a-time study, is necessary: the components interact.

Timeouts and censored data. Hard instances will not finish. The correct protocol is to fix a timeout in advance (say 60 seconds or 106 nodes — expressed without superscripts in your log as one million nodes), apply it identically to every configuration, and report the number of instances solved within the limit alongside the effort statistics for those that finished. Discarding timed-out runs and averaging the rest is a textbook statistical error: it systematically deletes the hardest instances from the weakest configuration's results, making the weak configuration look fast. A configuration that solves 12 of 50 instances in a mean of 0.3 s is worse, not better, than one that solves 48 of 50 in a mean of 4 s. Many researchers report a cactus plot equivalent in tabular form: instances solved as a function of the time budget.

Averaging and randomisation. A single instance proves nothing. Backtracking search has famously heavy-tailed runtime distributions — the same solver on the same instance family can vary by four orders of magnitude depending on early choices. Therefore: generate or collect many instances (30–100 is a reasonable minimum), vary the random seed where the solver makes any arbitrary choice (tie-breaking, shuffled value order, random restarts), and report medians and quartiles as well as means, since a single catastrophic run dominates a mean. If you generate random instances, control the constraint tightness parameter and sample across it: random CSPs exhibit a sharp phase transition from mostly-satisfiable to mostly-unsatisfiable, and the hardest instances cluster right at that transition. Sampling only loose instances makes every configuration look excellent; sampling only tight ones makes every configuration look identical because propagation refutes them instantly.

Debugging constraint models

Most "the solver is broken" reports are actually "the model is wrong." The following practices separate the two quickly.

1. Write an independent checker first. Before writing the search, write is_solution(assignment) that validates a complete assignment directly from the problem specification — not by reusing the solver's constraint objects, and ideally written from the original problem statement rather than from your model. Then assert it on every solution the solver returns, in every test. This is the single highest-value debugging investment available, because it converts silent wrongness into a loud failure at the exact moment it occurs.

2. Diagnose by symptom. The two failure modes point in opposite directions:

SymptomMost likely causesFirst things to check
No solution found, but one is known to existA constraint is too tight; wrong scope; an off-by-one in a precedence or duration; a domain was built too small; inference pruned a value it should not have; restoration failed to put a value backDisable inference entirely and re-run — if a solution appears, the bug is in propagation or restoration, not the model. Then disable constraints one at a time until the known solution is accepted; the last one disabled is the culprit.
An invalid "solution" is returnedA constraint is missing; its scope lists the wrong variables; the test has reversed arguments; the constraint is never consulted because the variable index was built before it was addedRun the independent checker to learn which requirement is violated, then verify that constraint exists in csp.constraints and appears in csp.involving[v] for every v in its scope.
Correct but absurdly slowConsistency check scanning all constraints; domains copied wholesale at every node; heuristic recomputed from scratch per nodeProfile; check the involving index exists; compare checks-per-node against the theoretical minimum.

The "never consulted" bug deserves emphasis. If your engine precomputes involving and you later append a constraint to the list, the index is stale and the constraint is invisible to consistent(), even though it appears in your model and in your printouts. A cheap guard is an assertion that the number of constraints reachable through the index equals the number in the list.

3. Shrink the instance. Debug on 4×4 Sudoku (4 variables per unit, domains 1–4), 4-Queens, a 3-region map, or a 3-task schedule — instances whose entire search tree you can draw on paper. If the solver expands 11 nodes and you expected 9, you can enumerate both. On an 81-variable instance with a million nodes, you cannot. Minimal reproducing examples are as valuable in constraint programming as anywhere else in software engineering.

4. Log the search path. Add an optional trace that prints, at each node, the depth, the chosen variable, the value tried, the result of the consistency check, and the domains pruned. On failure, the trace shows whether the solver explored what you expected. Two specific things to look for: a variable being assigned a value that is no longer in its domain (ordering computed before pruning), and the solver re-trying a branch it has already refuted (restoration bug).

5. Assert exact state restoration. The nastiest bugs in CSP solvers are state-leak bugs, and they are invisible on small tests. The direct test: snapshot a deep copy of every domain immediately before an inference step, run the step, force a failure, run restoration, and assert that the restored domains are equal to the snapshot — same values, for every variable, not merely the same sizes. Do this at every node in a debug mode and run the full test suite; it is slow but it finds the bug in one run. A related invariant worth asserting: on return from backtrack, the assignment dictionary must contain exactly the variables it contained on entry.

def checked_backtrack(csp, assignment, domains, ...):
    before_a = dict(assignment)
    before_d = {v: set(domains[v]) for v in csp.variables}
    result = backtrack(csp, assignment, domains, ...)
    if result is None:                       # only meaningful on failure
        assert assignment == before_a, "assignment leaked"
        assert all(domains[v] == before_d[v] for v in csp.variables), \
               "domain restoration incomplete"
    return result

Knowing when CSP methods fit

A solver is a tool, not a worldview. Recognising when the CSP framing is the right one — and when it quietly is not — saves more time than any heuristic.

Where classical finite-domain CSP is strong. Three conditions together make CSP an excellent fit:

  • Finite, discrete domains. Cells take digits; exams take periods; queens take rows; machines take one of six settings. If the natural domain is "any real number between 0 and 1," the fit is poor.
  • Hard constraints. The requirements are absolute: a student cannot be in two exams at once. CSP's semantics are exactly "satisfy all of these."
  • Any feasible solution is acceptable. There is no objective to maximise; a legal timetable is a legal timetable. Puzzles, configuration problems, and feasibility-driven planning all have this character.

Under those conditions you get strong propagation, complete search with a genuine proof of infeasibility, and a declarative model that non-programmers can read and audit.

When to prefer local search. For very large instances where a complete proof is unnecessary and speed dominates, use local search such as min-conflicts: start from a complete (probably invalid) assignment, repeatedly pick a conflicted variable, and reassign it to the value minimising the number of remaining conflicts. The canonical result is the million-queens problem, which min-conflicts solves in seconds and roughly a constant number of steps regardless of n, while complete backtracking is hopeless at that scale. The trade-off is sharp: local search cannot prove that no solution exists, can stall in local minima (mitigated by random restarts, tabu lists, or simulated annealing), and offers no completeness guarantee. Use it when you expect a solution to exist and merely need to find one.

When to prefer mathematical programming. If there is a genuine objective function — minimise total tardiness, minimise cost, maximise throughput — and the variables and constraints are mostly numeric and linear, linear programming and mixed-integer programming are usually the better tool. MIP solvers provide optimality bounds, duality information, and the ability to say "this solution is within 2% of optimal," which plain CSP cannot. In practice the boundary is blurred: constraint optimisation problems (COP) and hybrid CP/MIP solvers exist precisely because real scheduling problems have both combinatorial structure (where propagation shines) and numeric objectives (where LP relaxation shines). A rough rule: combinatorial feasibility with complex logical side conditions → CP; numeric optimisation with mostly linear structure → MIP.

Signals that point away from classical CSP.

  • Continuous variables. Positions, temperatures, flows, times measured to arbitrary precision. Discretising is sometimes acceptable (quarter-hour slots), but a fine discretisation explodes domain sizes and loses the algebraic structure that numeric solvers exploit.
  • Uncertainty. If durations are stochastic, demand is forecast, or outcomes are probabilistic, hard constraints misrepresent the problem; look to stochastic programming, MDPs, or probabilistic graphical models (which, notably, share CSP's factor-graph structure but replace "satisfied/violated" with probabilities).
  • Soft, learned, or conflicting preferences. "Lecturers prefer mornings" is not a hard constraint, and trading such preferences off against each other requires weights — that is an optimisation or preference-learning problem, best handled by weighted/soft CSP, MaxSAT, or a MIP objective rather than by piling conditions into a pure CSP and discovering it is infeasible.
  • Constraints that are not decidable cheaply. If evaluating whether a constraint holds requires running a simulation, the per-check cost destroys the search's economics.

Size is not the disqualifier. A common misconception is that CSP is a toy technique that works on 81-cell puzzles and collapses on industrial problems. The opposite is true in practice: it is weak modelling, not scale, that kills CSP approaches. Industrial constraint programming routinely handles models with tens of thousands of variables — rostering for airlines and hospitals, container stowage, rail and factory scheduling, product configuration — because strong global constraints (alldifferent, cumulative, gcc, table, circuit) come with specialised polynomial-time filtering algorithms that remove enormous numbers of values per propagation step. A model with 5,000 variables and well-chosen global constraints will often solve faster than a model with 200 variables decomposed into thousands of pairwise constraints. The practical lesson for your own solver work is to spend effort on the model and on propagation strength before concluding that the problem class is out of reach.
