Value Ordering and Search Efficiency

▶

Backtracking search for constraint satisfaction problems makes two decisions at every node of the search tree. First it asks which variable should I assign next? — answered by variable-ordering heuristics such as minimum-remaining-values (MRV) and the degree heuristic. Then it asks in what order should I try that variable's remaining values? — answered by value-ordering heuristics, of which the least-constraining-value (LCV) heuristic is the canonical example. These two questions look symmetric, but they are governed by opposite logics. Variable ordering wants to fail fast; value ordering wants to fail last. Understanding why that asymmetry exists, and measuring how much it actually buys you on real instances, is the substance of this topic.

Why Value Ordering Matters

Consider a CSP solver part-way through a search. It has a partial assignment, it has just selected an unassigned variable X using its variable-ordering rule, and X has a current domain of, say, five surviving values. The solver must now generate child nodes — one per value — and recurse into them in some sequence. The set of children is fixed by the domain; only their order is under the solver's control.

This immediately tells us something important about the limits of value ordering. If the subproblem below this node has no solution at all, then every one of the five branches will eventually be explored and refuted, and the total work done is identical no matter which order we use. Value ordering cannot prune a subtree that must be exhausted; it can only change when we find a solution inside a subtree that contains one. Formally: for proving unsatisfiability, value ordering is work-neutral (up to small constant-factor effects on propagation); for finding the first solution, it can be the difference between zero backtracks and an exponential search.

That is exactly the common case in practice. Most applied CSPs — scheduling a timetable, colouring a map, placing queens, allocating registers — are satisfiable, and the user wants one consistent complete assignment, not an enumeration of all of them. In that regime, a good value order steers the search down a "corridor" of choices that remain mutually compatible, and the solver walks almost straight down to a leaf.

Conversely, poor value ordering wastes effort on branches that are doomed by constraints on neighbouring variables even though they are locally consistent. A value may be perfectly legal with respect to everything assigned so far and still annihilate the last remaining option of some unassigned neighbour. Plain backtracking without inference will not notice until it descends several levels deeper, assigns that neighbour's variable, discovers no value works, and unwinds. Every node visited in that doomed subtree is pure waste.

A small concrete illustration. Take map colouring with colours {Red, Green, Blue} on this fragment: region A is adjacent to B, C, and D; region B is additionally adjacent to C; and D has already been forced to {Green, Blue} by an earlier assignment. Suppose the variable-ordering heuristic picks A, whose domain is still {Red, Green, Blue}. Choosing Green for A strips Green from B, C, and D — leaving D with only {Blue}, a knife-edge situation. Choosing Red for A strips Red from B and C but costs D nothing, because Red was already gone from D's domain. Red is the less damaging choice, and a value-ordering heuristic that can see this will try it first.

The Least-Constraining-Value Heuristic

LCV formalises exactly the reasoning in that example. For the chosen variable X and each candidate value v in its current domain:

  • Tentatively assume X = v.
  • For every unassigned variable Y that shares a constraint with X, count how many values of Y's current domain become inconsistent with X = v.
  • Sum those counts over all such neighbours Y. This sum is the elimination count (or "conflict count") of v.
  • Sort the domain in increasing order of elimination count and try the smallest first.

The intuition is leave the maximum number of options open for the rest of the assignment. A value that removes two options from the remaining problem leaves a richer, more flexible residual CSP than one that removes eleven. Since we only need one solution, we want to walk into the roomiest part of the space, where a consistent completion is most likely to exist and most likely to be found quickly. This is the "fail-last" or "succeed-first" principle, and it is the mirror image of the fail-first principle used for variable selection.

Worked example on the map fragment above, with current domains B = {Red, Green, Blue}, C = {Red, Green, Blue}, D = {Green, Blue}:

Candidate value for AValues killed in BValues killed in CValues killed in DElimination countLCV rank
Red1 (Red)1 (Red)0 (Red absent)21st — try first
Green1 (Green)1 (Green)1 (Green)32nd (tie)
Blue1 (Blue)1 (Blue)1 (Blue)32nd (tie)

LCV therefore orders A's domain as Red, then Green/Blue (ties broken arbitrarily or by a static tiebreak such as domain index). Note what LCV did not do: it did not prune anything. All three values remain available; only the order changed.

Pseudocode for the heuristic, assuming a domains structure holding current (possibly pruned) domains:

function LCV_ORDER(X, assignment, domains, csp):
    scored = []
    for v in domains[X]:
        eliminated = 0
        for Y in NEIGHBOURS(X, csp):
            if Y is assigned: continue
            for w in domains[Y]:
                if not CONSISTENT(X, v, Y, w, csp):
                    eliminated = eliminated + 1
        scored.append( (eliminated, v) )
    sort scored by eliminated ascending
    return [v for (eliminated, v) in scored]

Two implementation facts follow directly from this code. First, LCV needs live domains. If domains[Y] is always the original static domain, the counts are the same at every node and LCV degenerates into a fixed static ordering that carries no information about the current state of the search. To be meaningful, LCV must be paired with a constraint-propagation step — forward checking at minimum, or arc consistency maintenance (MAC/AC-3) for sharper domains — so that the counts reflect what is genuinely still available. In fact the inner loops of LCV and of forward checking are the same loops, so a good implementation computes the elimination counts and the pruned domains in one pass and caches the result for the branch it eventually takes.

Second, LCV is not free. The cost at a node is O(d · k · d) = O(k·d²) consistency checks, where d is domain size and k the number of unassigned neighbours. For d = 3 (map colouring) that is trivial. For d = 500 (a scheduling variable with 500 possible start times) and a dense constraint graph, the heuristic computation can cost more than the search it saves.

And again, the hard limitation: on unsatisfiable instances LCV gives no benefit. If the subtree below the current node contains no solution, every value must be tried and refuted; reordering the refutations changes nothing but adds the heuristic's own overhead. Worse, on an unsatisfiable instance LCV systematically tries the least constrained value first, which is the value whose subtree tends to be the largest and slowest to refute — so the measured runtime can be marginally worse than with an arbitrary order.

Combining Variable and Value Ordering

In a well-built solver, three heuristics operate at each node in a fixed pipeline:

  • MRV (minimum remaining values) chooses the unassigned variable with the fewest legal values left. This is the fail-first principle: if some variable is going to fail, discover it as high in the tree as possible, because a failure near the root prunes an exponentially larger subtree than a failure near a leaf. In the extreme, if a variable's domain has been reduced to size zero, MRV picks it and the branch dies immediately; if it has size one, that assignment is forced and branching factor 1 costs nothing.
  • Degree heuristic breaks MRV ties by choosing the variable involved in the most constraints with unassigned variables. Among equally constrained variables, assigning the one with the highest connectivity propagates the most information and reduces the branching factor of the remaining subproblem the fastest. It is also used standalone at the very first node, where every domain is full and MRV has no information to offer.
  • LCV then orders the chosen variable's values so that the branch most likely to lead to a solution is visited first.

The division of labour is clean: fail-first variable choice shapes the tree; fail-last value choice chooses a path through it. Variable ordering affects both satisfiable and unsatisfiable instances because it genuinely changes the size and shape of the search tree — a different variable order yields a structurally different tree. Value ordering does not change the tree at all; it changes only the order in which a fixed tree is traversed, which matters only when traversal can stop early (i.e., on success).

A skeleton of the combined solver:

function BACKTRACK(assignment, domains, csp):
    if assignment is complete: return assignment
    X = SELECT_UNASSIGNED_VARIABLE(domains, csp)      # MRV, ties by degree
    for v in ORDER_DOMAIN_VALUES(X, assignment, domains, csp):   # LCV
        if CONSISTENT(X = v, assignment):
            assignment[X] = v
            new_domains = FORWARD_CHECK(X, v, domains, csp)      # inference
            if no domain in new_domains is empty:
                result = BACKTRACK(assignment, new_domains, csp)
                if result != failure: return result
            remove X from assignment                             # undo
    return failure

Both heuristic families depend on new_domains being accurate, which is why inference is not optional once you adopt these heuristics. Without forward checking, MRV sees only the static domains minus values conflicting with assigned variables (a weak approximation), and LCV sees nothing useful at all. The usual packaging in textbooks and solvers is therefore "MRV + degree + LCV + forward checking" or, stronger, "MRV + degree + LCV + MAC".

A subtle point worth internalising: MRV and LCV can appear to contradict each other — one minimises options, the other maximises them — but they act on different objects. MRV minimises the options of the variable we commit to (so that commitment is cheap and informative); LCV maximises the options of everything we have not yet committed to (so the remaining problem stays easy). There is no conflict.

Measuring Search Efficiency with Node Counts

Runtime in seconds is a poor primary metric for comparing CSP heuristics: it depends on language, hardware, data structures, and constant factors unrelated to search behaviour. The standard machine-independent metric is the node count — the number of partial assignments the search actually examines, i.e., the number of times the recursive BACKTRACK body is entered, or equivalently the number of variable assignments attempted. Related counters give a fuller picture:

MetricWhat it countsWhat it tells you
Nodes expandedPartial assignments examinedRaw size of the explored portion of the tree; the headline efficiency number
BacktracksReturns to a parent after a failed branchHow often the heuristics mis-steered; sensitive to value ordering
Constraint checksCalls to the binary/n-ary consistency testCaptures the hidden overhead of computing MRV/LCV and of propagation
Runtime (ms)Wall-clockReality check: confirms whether node savings survive heuristic overhead

Constraint checks deserve emphasis. A heuristic combination can cut nodes by 100× while raising constraint checks by 200×, in which case it is a net loss. Reporting nodes alone hides this; reporting nodes and checks and time makes the trade-off visible. This is precisely the trap with LCV on large domains.

Sound experimental method requires a few further disciplines:

  • Use plain chronological backtracking as the baseline. Every heuristic variant is reported as a ratio or factor against it, so results are comparable across problem sizes.
  • Average over many random instances. A single instance may be solved on the first descent by sheer luck, or may happen to be pathological. Reporting the mean (and ideally median and spread) over, say, 50–100 randomly generated instances per size smooths out this variance. Medians are often more informative than means because node-count distributions are heavy-tailed: a handful of instances can dominate the mean.
  • Fix a node or time cut-off and report the number of unsolved instances separately, rather than letting one runaway instance distort the average.
  • Control the random seed and the tie-breaking rule, since arbitrary tie-breaks in MRV or LCV can themselves swing results by a large factor.
  • Vary constrainedness. Results on easy, under-constrained instances say little; the interesting region is near the phase transition where satisfiable and unsatisfiable instances are roughly equally likely and search cost peaks.

Benchmark Results: N-Queens and Map Colouring

N-Queens is the standard stress test. Variables are the N columns, domains are the N row positions, and the constraints forbid shared rows and shared diagonals. Plain chronological backtracking copes with small boards but explodes combinatorially once N passes a few dozen: the solver commits to an early queen placement that is locally fine but globally fatal, then thrashes through an enormous subtree before it can revise that early decision. Typical figures (order-of-magnitude, median over runs, first solution only) look like this:

NPlain backtracking (nodes)+ MRV & degree (nodes)+ MRV, degree, LCV & forward checking (nodes)
8~114~30~22
16~3,100~75~40
24~90,000~150~70
32~1.6 million~260~110
50exceeds cut-off~600~190

The qualitative shape of this table is the lesson, not the exact digits (which vary with implementation and tie-breaking). Three things stand out. First, MRV plus the degree heuristic cuts expanded nodes by orders of magnitude — several on larger boards — because fail-first detection combined with forward checking kills a bad placement within one or two levels instead of thousands. Second, the baseline's growth is clearly exponential in N while the heuristic columns grow nearly linearly over this range, so the gap widens with problem size; comparing heuristics only on N = 8 badly understates their value. Third, LCV plus forward checking delivers a further, genuine but much more modest reduction — commonly a factor of two to three in nodes and backtracks — precisely because LCV only reorders a tree that MRV has already shrunk. In N-Queens, LCV tends to favour central-ish rows early and push queens toward positions whose diagonals sweep the fewest cells out of neighbouring columns' domains, which keeps later columns from starving.

Map colouring tells a complementary story. Take randomly generated planar-ish graphs with 3 colours, varying the edge density. Representative node counts, averaged over 50 random instances per setting:

Instance classPlain backtracking+ degree only+ MRV & degree+ MRV, degree & LCV (with FC)

Several empirical regularities are visible here, and they generalise well beyond map colouring:

  • The degree heuristic helps most on graphs with highly connected regions. In the classic Australia map, New South Wales and South Australia are hubs; colouring a hub first immediately constrains most of the remainder, whereas starting at Tasmania (an isolated region) tells you nothing. On random graphs with a skewed degree distribution — a few very high-degree regions among many low-degree ones — the degree heuristic alone can cut nodes several-fold, and it is the only one of the three that provides guidance at the root node.
  • Gains are largest on critically constrained instances. On trivially easy instances (the 7-region Australia map) any method succeeds in a handful of nodes and the heuristics have no room to help — the overhead may even make them slower in wall-clock terms. The interesting territory is the critically constrained band where plain backtracking's cost explodes but a solution still exists.
  • On the unsatisfiable row, LCV's column is no better than the column without it (indeed marginally worse, reflecting its own overhead). This is the empirical confirmation of the theoretical point made earlier: the whole tree must be refuted, so value order is irrelevant. MRV and degree, by contrast, still help enormously on unsatisfiable instances because they genuinely restructure the tree and enable early domain wipe-out detection.

Practical Guidance and Limitations

Pulling the empirical and theoretical threads together into usable rules of thumb:

  • Adopt MRV plus degree plus forward checking almost unconditionally. They are cheap to compute incrementally, they help on both satisfiable and unsatisfiable instances, and they are the source of the order-of-magnitude savings. If you implement only one thing, implement this.
  • Treat LCV as an optional refinement for satisfiable, single-solution problems. It shines when you need one solution to a large, loosely-to-moderately constrained problem and domains are small. It is useless when enumerating all solutions, useless on unsatisfiable instances, and useless when proving optimality in a branch-and-bound setting where the whole relevant tree is explored anyway.
  • Watch the cost on large domains. Scoring every value at every node is O(k·d²); with d in the hundreds or thousands this can dominate total runtime. Mitigations include computing LCV scores only at shallow depths (where the pay-off is largest), scoring only a sampled subset of values, using a cheaper proxy such as "count of neighbours for which this value is the sole support", or caching scores and recomputing only when a neighbour's domain changes.
  • Random or static value ordering is often good enough. On loosely constrained problems, almost any value works and the first descent succeeds regardless; LCV then only adds overhead. Randomised value ordering has an additional virtue: combined with restarts, it avoids the deterministic solver's tendency to make the same early mistake every time (heavy-tailed runtime distributions), and random restarts frequently beat sophisticated value ordering on structured industrial instances.
  • Ties and domain-specific knowledge matter. LCV frequently produces large ties (in the map-colouring table above, Green and Blue tied exactly). How you break those ties can swing node counts by a factor of several, so break them deliberately — by a problem-specific preference, by a random choice with a fixed seed, or by a secondary score such as "prefer the value that leaves the largest minimum neighbour domain" — and report the rule you used.
  • Always profile the specific problem class. Heuristic performance does not transfer reliably between problem families. A combination that is superb on N-Queens may be mediocre on job-shop scheduling, where domains are large and LCV's quadratic scoring bites, or on Sudoku, where MRV with propagation alone solves most published puzzles with essentially no search. Build the node/backtrack/check/time counters into the solver from the start, generate a representative instance set spanning easy, critical, and over-constrained regimes, and measure.
  • Know when the whole framework is the wrong tool. For very large satisfiable instances such as million-queens, systematic backtracking with any ordering heuristics is outclassed by local search (e.g., min-conflicts), which solves such problems in near-linear time. Ordering heuristics improve systematic search; they do not rescue it from problems it is structurally unsuited to.

The overall picture is therefore one of a clear hierarchy of returns. Inference (forward checking, arc consistency) and fail-first variable ordering do the heavy lifting, reshaping an exponential tree into something tractable. Value ordering is a finishing touch: valuable, cheap to try, occasionally decisive on satisfiable instances, and provably irrelevant when the search must prove that no solution exists. A disciplined experimental protocol built on node counts, constraint checks, and averaging over many instances is what lets you tell those cases apart for your own problem rather than guessing.

Videos on This Topic

Backtracking search for constraint satisfaction problems makes two kinds of choices at every step: which variable to assign next, and which value from that variable's domain to try first. Variable ordering heuristics such as minimum remaining values (MRV) and degree try to expose failure early so that dead ends are pruned quickly. Value ordering works in the opposite direction: once a variable is chosen, we usually want the value most likely to lead to a solution, since any single solution is enough. The standard rule here is the least-constraining-value (LCV) heuristic, which prefers the value that rules out the fewest options in the domains of neighboring, still-unassigned variables.

This topic matters because these heuristics are cheap to add but can change solver performance by orders of magnitude. To compare them fairly we need a measurement discipline: counting nodes expanded (or consistency checks) on benchmark instances such as N-Queens and map coloring, rather than relying on intuition or wall-clock time alone. You should come away able to explain why MRV and LCV pull in opposite directions yet combine well, and able to read a table of node counts for different heuristic combinations.

While watching, keep three questions in mind. First, what exactly is being counted when a video says one method is "faster"? Second, how is the LCV score computed for a candidate value, and what does it cost to compute? Third, where do these heuristics fail to help — for example on problems where every value is equally constraining, or where the overhead of ranking values outweighs the savings. Also notice how value ordering interacts with inference techniques like forward checking, since both reason about the remaining domains of neighbors.
