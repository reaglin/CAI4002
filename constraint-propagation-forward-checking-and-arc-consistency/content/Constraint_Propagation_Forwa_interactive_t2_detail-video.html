Forward Checking

▶

Forward checking is the simplest and most widely used form of look-ahead in constraint satisfaction search. Plain chronological backtracking is a "look-behind" algorithm: it assigns a value to a variable, then checks the new assignment against the assignments already made, and only discovers that a branch is hopeless when it finally reaches the variable whose domain has been exhausted. Forward checking reverses the direction of reasoning. Immediately after a variable is assigned, it looks forward into the domains of the still-unassigned variables and deletes every value that the new assignment has made impossible. The payoff is that a contradiction shows up as an empty domain at the moment it is created, rather than many levels deeper in the search tree, and that the surviving domains give the variable- and value-ordering heuristics much better information to work with.

Formally, a constraint satisfaction problem (CSP) is a triple of variables X = {X₁ … Xₙ}, domains D(X₁) … D(Xₙ), and constraints C. In a binary CSP every constraint relates exactly two variables, and the problem can be drawn as a constraint graph whose nodes are variables and whose edges are constraints. Forward checking is defined most naturally on binary CSPs, and the discussion below assumes that setting unless stated otherwise.

What forward checking does

Forward checking is a local operation with a deliberately narrow scope. When the search assigns X = v, forward checking visits only the neighbours of X in the constraint graph — the unassigned variables Y such that a constraint C(X, Y) exists. For each such Y it scans D(Y) and deletes every value w for which the pair (v, w) violates C(X, Y). Variables that do not share a constraint with X are untouched, and variables that are already assigned are irrelevant because the assignment X = v was itself checked against them before being accepted. The work done is therefore proportional to the degree of X, not to the size of the whole problem — a crucial property when the constraint graph is sparse, as it is in scheduling, timetabling and map-colouring instances.

Because the deletions are provisional — they are consequences of a tentative assignment that may later be undone — they must be recorded. Every implementation keeps a trail: a per-assignment record of exactly which values were removed from which domains. The usual data structure is a stack of (variable, value) pairs with a mark pushed at each decision level, or an array pruned[X][v] listing the deletions attributable to assigning X = v. When the search abandons X = v, the trail is unwound and every recorded value is put back. Without this bookkeeping the search would be unsound: domains would shrink monotonically and legitimate solutions in other branches would be lost.

The invariant that forward checking maintains is worth stating precisely, because it is the whole justification for the technique:

  • Forward-checking invariant: at every node of the search tree, for every unassigned variable Y and every value w remaining in D(Y), the extended assignment that adds Y = w to the current partial assignment violates no constraint.

In the vocabulary of consistency, this is exactly arc consistency between each unassigned variable and each assigned variable. It is a strictly weaker property than full arc consistency, which also demands consistency between pairs of unassigned variables. Two immediate consequences follow from the invariant. First, when the search picks the next variable and value, it never needs to re-check that value against any earlier assignment — the check has already been done, which is why forward checking can replace rather than merely supplement the consistency test of plain backtracking. Second, an empty domain is a certificate of failure: if D(Y) is empty then no value of Y is compatible with the current partial assignment, so that partial assignment cannot be part of any solution.

Forward checking performs inference exactly one level deep. If removing values from D(Y) implies, through a constraint C(Y, Z), that some value of a third unassigned variable Z has lost all of its supports, forward checking does not notice. It never re-examines Y's other neighbours after pruning Y. This is the defining limitation, and it is the deliberate price paid for cheapness; propagating those consequences transitively is what arc consistency algorithms such as AC-3 do.

Finally, forward checking requires no structural change to the backtracking search. The recursive skeleton — choose a variable, iterate over its values, recurse, undo — is unchanged. Forward checking inserts one pruning step after the assignment and one restoration step after the recursive call returns. This modularity is the reason it is the usual default in textbook and production CSP solvers alike: it can be switched on or off with a flag, which also makes it an ideal baseline for benchmarking stronger inference.

The forward checking algorithm step by step

The five steps below describe one node of the search. They are written as a recursive procedure, but the same logic applies to an iterative solver with an explicit stack.

  • Step 1 — Select and assign. Choose an unassigned variable X (typically by the MRV heuristic, below) and iterate over the values v currently remaining in D(X). Note that D(X) here is the current, already-pruned domain, not the original one. Tentatively set X = v.
  • Step 2 — Prune the neighbours. For every unassigned variable Y with a constraint C(X, Y), examine each w ∈ D(Y) and delete w if (v, w) violates C(X, Y). Record every deletion on the trail under the decision X = v.
  • Step 3 — Test for domain wipe-out. If any D(Y) becomes empty, the assignment X = v is refuted. Undo the deletions made in Step 2 at once, and continue the loop of Step 1 with the next value of X. Do not recurse. If no value of X survives, return failure so that the parent node backtracks.
  • Step 4 — Recurse. If all neighbour domains are still non-empty, call the search recursively to assign the next variable. If the recursive call returns a solution, propagate it upward.
  • Step 5 — Restore on backtrack. When the recursive call fails and the search leaves X = v, unwind the trail for that decision: every value pruned in Step 2 is returned to the domain it came from, and X is marked unassigned again. The domains are then bit-for-bit identical to their state before Step 1, so the next value of X is tried in a clean context.
function BACKTRACK-FC(assignment, domains):
    if assignment is complete: return assignment
    X <- SELECT-UNASSIGNED-VARIABLE(domains)        # e.g. MRV, ties broken by degree
    for each v in ORDER-DOMAIN-VALUES(X, domains):   # e.g. least-constraining value
        assignment[X] <- v
        trail <- empty list
        wipeout <- false
        for each unassigned Y in NEIGHBOURS(X):
            for each w in domains[Y]:
                if not CONSISTENT(X, v, Y, w):
                    remove w from domains[Y]
                    append (Y, w) to trail
            if domains[Y] is empty:
                wipeout <- true
                break                                # fail fast: stop pruning
        if not wipeout:
            result <- BACKTRACK-FC(assignment, domains)
            if result != failure: return result
        for each (Y, w) in trail:                    # Step 5: restore
            add w back to domains[Y]
        remove X from assignment
    return failure

Two implementation details matter in practice. First, the break on wipe-out is an optimisation only: once one domain is empty the assignment is already refuted, so pruning the remaining neighbours is wasted work — but the trail must still be unwound correctly, which the code above does because it restores whatever was recorded. Second, domains are usually represented as bitsets or as "domain arrays with a current size" so that deletion and restoration are O(1) per value and the current domain size is available in constant time for the MRV heuristic.

Worked example: map colouring

The classic illustration is colouring the states and territories of Australia with three colours so that no two adjacent regions share a colour. The variables are WA, NT, SA, Q, NSW, V and T; each domain is initially {red, green, blue}. The adjacency constraints are: WA–NT, WA–SA, NT–SA, NT–Q, SA–Q, SA–NSW, SA–V, Q–NSW, NSW–V. Tasmania (T) borders nothing, so it is an isolated node in the constraint graph.

Suppose the search uses the fixed order WA, Q, V, … and always tries colours in the order red, green, blue. The following table traces the domains after each assignment; assigned variables are shown with their chosen value in braces for clarity.

Reading the trace line by line:

  • WA = red. WA's unassigned neighbours are NT and SA. Red is deleted from both, leaving D(NT) = D(SA) = {green, blue}. Q, NSW, V and T are not adjacent to WA, so they are untouched — a direct illustration of the "neighbours only" scope. The trail for this decision records (NT, red) and (SA, red).
  • Q = green. Q's unassigned neighbours are NT, SA and NSW. Green is deleted from each, giving D(NT) = {blue}, D(SA) = {blue} and D(NSW) = {red, blue}. No domain is empty, so the search continues. Notice that NT and SA are now both singletons holding the same colour, and NT–SA is a constraint — the partial assignment is already doomed, but forward checking cannot see this, for reasons taken up under "Limitations" below.
  • V = blue. V's unassigned neighbours are SA and NSW. Blue is deleted from D(SA) = {blue}, which wipes it out, and from D(NSW) = {red, blue}, leaving {red}. The empty domain for SA is detected the instant it occurs, so the solver immediately rejects V = blue, restores blue to SA and NSW, and tries the next value for V. It never descends into the subtree below V = blue.

Contrast this with plain chronological backtracking under the same variable order. Having set WA = red, Q = green and V = blue, plain backtracking has checked each new value only against the earlier assignments, all of which succeeded (WA and Q are not adjacent; V is adjacent to neither WA nor Q, so V = blue is accepted outright). It would then go on to assign NT, then NSW, and only when it finally reached SA would it discover that no colour is available — having in the meantime enumerated combinations of NT and NSW values, each of which requires its own consistency checks and its own node in the search tree. Forward checking collapses all of that wasted exploration into a single test.

When the search backtracks out of V = blue, the trail for that decision contains (SA, blue) and (NSW, blue). Restoring them gives D(SA) = {blue} and D(NSW) = {red, blue} — exactly the state shown in the "Q = green" row of the table. The restoration is exact and local: deletions attributable to WA = red and Q = green are untouched, because they belong to decisions that are still in force. This is why the trail must be organised by decision level rather than as a single undifferentiated set.

Early failure detection and interaction with heuristics

The logical content of an empty domain deserves emphasis. If D(Y) = ∅ after forward checking, then by the forward-checking invariant every original value of Y conflicts with at least one current assignment. Since Y must receive some value in any complete solution, the current partial assignment extends to no solution at all. The empty domain is therefore a proof of failure, not a heuristic guess, and the solver is entitled to prune the entire subtree below it. This soundness is what makes the technique safe: forward checking never prunes a branch that contains a solution.

Beyond failure detection, the pruned domains are a rich source of information for the ordering heuristics that do most of the practical work in CSP solving.

  • Minimum Remaining Values (MRV), also called "fail-first". Choose next the unassigned variable with the smallest current domain. This heuristic is almost useless under plain backtracking, where domains never shrink and every variable looks identical; it becomes powerful precisely because forward checking maintains live domain sizes. The rationale is that a variable with one remaining value is forced, so assigning it propagates information immediately, while a variable with zero remaining values signals failure at once. In the trace above, after Q = green MRV would select NT or SA (domain size 1) rather than V (domain size 3). Choosing SA, the only value is blue; forward checking then deletes blue from NT, wiping it out, and the doomed branch is refuted one assignment earlier still.
  • Degree heuristic. MRV often produces ties, especially at the root where all domains are the same size. The degree heuristic breaks ties by preferring the variable involved in the largest number of constraints with unassigned variables, because assigning it prunes the most domains and so maximises the amount of inference performed. In Australia, SA has degree 5 and would be chosen first at the root, which is an excellent decision: colouring SA immediately removes one colour from five other domains.
  • Least-constraining value (LCV). Having chosen a variable, order its values so that the one which rules out the fewest values in neighbouring domains is tried first. The counts needed are exactly the deletion counts that forward checking computes anyway — a trial forward-check per candidate value yields the number of prunings. Where MRV is "fail-first" on variables, LCV is "succeed-first" on values: it keeps the remaining search space as large as possible so that a solution is more likely to be found without backtracking.

The combination is more than the sum of its parts. On the n-queens problem, plain backtracking becomes impractical somewhere around n = 25–30; forward checking with MRV and degree tie-breaking routinely solves instances with hundreds of queens, because each queen placement immediately strips the attacked squares from the remaining columns' domains and MRV then pounces on whichever column has become most constrained. On random binary CSPs near the phase transition, the reduction in nodes expanded is typically one to three orders of magnitude relative to plain backtracking with the same static ordering.

Cost versus pruning power

Forward checking buys node reductions with per-node work, and it is worth quantifying both sides of the trade. Let n be the number of variables, d the maximum domain size and deg(X) the number of unassigned neighbours of the variable being assigned.

  • Time per assignment. Checking one neighbour costs O(d) constraint checks — one per remaining value of that neighbour. The whole forward-checking step therefore costs O(deg(X) · d) constraint checks, which in the worst case of a complete constraint graph is O(n · d). On sparse graphs the degree is a small constant and the cost is O(d).
  • Space. The trail stores one entry per pruned value. Across a root-to-leaf path of depth n, at most n · d values can ever be deleted in total (each value of each variable can be deleted at most once while it stays deleted), so the trail is O(n · d) in the worst case — modest, and easily implemented as a preallocated array. Restoration costs O(1) per recorded deletion.
  • Nodes. Plain backtracking creates and tests nodes that forward checking prevents from ever being generated: any assignment that would later be found inconsistent with an existing assignment is removed from the domain in advance. Each pruned node would otherwise have cost at least one consistency check plus the stack frame, and may have had an entire subtree below it.

A useful theoretical guarantee: with the same variable and value ordering, forward checking never visits a node that chronological backtracking does not also visit. Every node it prunes is one that backtracking would eventually have refuted. So the node count can only improve, and the only possible loss is the constant-factor overhead per node. That is why forward checking is generally adopted as the default rather than as an option to be justified case by case.

The overhead is nevertheless real, and its significance depends on constraint tightness. On a loosely constrained problem — few constraints, or constraints that forbid only a small fraction of value pairs — most forward-checking scans delete nothing, so the solver pays O(deg · d) per node for no return and may be measurably slower than plain backtracking in wall-clock terms even though it expands the same number of nodes. On tightly constrained problems, and especially near the satisfiable/unsatisfiable phase transition where most branches are doomed, the deletions come thick and fast, wipe-outs are frequent, and the saving in nodes dwarfs the per-node cost.

Limitations of forward checking

The single structural weakness is that forward checking does not propagate. When it shrinks D(Y), it stops. It does not ask whether the values that remain in D(Y) still support the values in the domains of Y's other neighbours, so a deletion never cascades. All of the following limitations are corollaries of that one fact.

  • Inconsistencies between two future variables are invisible. Return to the trace after WA = red, Q = green: D(NT) = {blue} and D(SA) = {blue}, and NT–SA is a constraint. The partial assignment is unsatisfiable, but no domain is empty, so forward checking sees nothing wrong and the search happily descends. Arc consistency would catch it instantly: revising the arc NT → SA finds that NT's only value, blue, has no support in D(SA) = {blue}, so blue is deleted from NT and NT is wiped out. This single example is the standard demonstration that forward checking is strictly weaker than arc consistency.
  • Doomed branches are still explored. Because such hidden conflicts go undetected, the solver continues to assign variables below a node that can never succeed, discovering the failure only when the conflict finally involves an assigned variable. Each wasted level multiplies the number of nodes by roughly the branching factor.
  • The guarantee is one-sided. An empty domain proves failure, but a non-empty domain proves nothing. Forward checking can certify that a branch is dead; it can never certify that a branch is alive. Stronger inference narrows the gap but never closes it entirely — only a complete search can confirm satisfiability.
  • Stronger look-ahead exists at higher cost. Running a full arc-consistency pass after every assignment — restricting the initial arc queue to the arcs (Y, X) that point at the newly assigned variable X, then propagating — gives the algorithm usually called Maintaining Arc Consistency (MAC), or sometimes "really full look-ahead". MAC subsumes forward checking: its first round of revisions performs exactly the prunings forward checking would perform, and then it keeps going. It expands fewer nodes, but each node costs more, and on easy or loosely constrained instances that extra work is not repaid.
  • Forward checking sits at the bottom of a hierarchy. The family of look-ahead schemes runs roughly: backtracking (no look-ahead) → forward checking (one level, neighbours of the assigned variable) → partial look-ahead / directional arc consistency (propagation restricted to future variables in one direction) → MAC with AC-3 or AC-4 (full arc consistency at every node) → path consistency and higher-order k-consistency (prohibitively expensive in general). Each step up the hierarchy prunes more per node and costs more per node, and the best choice is empirical, which is precisely why configurable solvers expose the inference level as a parameter and why benchmark comparisons report both nodes expanded and runtime.

A final practical note: forward checking generalises beyond binary constraints, but less elegantly. For an n-ary constraint, the usual rule is to prune only when all but one of its variables are assigned, at which point the single unassigned variable's domain can be filtered exactly — this is sometimes called the "forward checking on the last unassigned variable" rule. Earlier, weaker filtering of n-ary constraints is the province of specialised propagators (for example, bounds or domain propagators for alldifferent), which again belong to the stronger-inference end of the spectrum rather than to forward checking proper.

Forward checking is the simplest and most widely used form of constraint propagation inside backtracking search. Each time you assign a value to a variable, forward checking looks at every unassigned variable that shares a constraint with it and deletes from those domains any value that is now inconsistent with the new assignment. If any domain becomes empty, the current partial assignment cannot be extended to a solution, so the search backtracks immediately instead of wasting effort exploring doomed subtrees.

This matters in the course because it is the bridge between plain chronological backtracking and stronger propagation methods such as AC-3 and MAC. Forward checking also supplies exactly the information that dynamic variable ordering heuristics need: once domains shrink during search, minimum remaining values (MRV) can pick the most constrained variable, and degree and least-constraining-value heuristics can break ties. The trade-off to keep in mind throughout is cost versus pruning power — propagation work at every node must pay for itself in nodes that never get expanded.

As you watch the videos, track three things: (1) which domains change after each assignment and why, (2) the exact moment an empty domain reveals failure, and (3) how far ahead the method can and cannot see. Forward checking only checks constraints between the just-assigned variable and its unassigned neighbours; it will not notice an inconsistency that lies purely between two unassigned variables. That limitation is the motivation for arc consistency in the next part of the module.
