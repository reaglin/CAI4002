Foundations of Constraint Propagation and Inference

▶

Constraint satisfaction is one of the few places in artificial intelligence where the structure of a problem is exposed to the solver rather than hidden inside an opaque state. In a classical search problem — the sliding-tile puzzle, route finding, a game tree — a state is an atomic blob. The solver can test whether it is a goal and can generate its successors, but it cannot look inside and ask why a particular state is bad. A constraint satisfaction problem (CSP) breaks that opacity. States are factored into variables and the values assigned to them, and the goal test is decomposed into a set of explicit constraints. That single change in representation unlocks a whole family of techniques collectively called inference or constraint propagation: reasoning that removes impossible values from consideration before the search ever tries them. The remainder of this topic builds the vocabulary and the intuitions that every propagation algorithm depends on.

What is a constraint satisfaction problem? Formally, a CSP is a triple (X, D, C):

  • X = {X₁, X₂, …, Xₙ} is a finite set of variables.
  • D = {D₁, D₂, …, Dₙ} associates with each variable Xᵢ a domain Dᵢ — the finite set of candidate values that variable may take. Domains need not be the same size or even the same type; one variable may range over colours, another over integers 1–9, another over the booleans.
  • C = {C₁, C₂, …, C_m} is a set of constraints. Each constraint C_j is a pair ⟨scope, relation⟩, where the scope is the tuple of variables the constraint talks about and the relation specifies which combinations of values for those variables are permitted. The relation may be given extensionally, as an explicit list of allowed tuples, or intensionally, as a predicate such as X ≠ Y or X + Y ≤ 10.

An assignment maps variables to values drawn from their domains. A partial assignment leaves some variables unassigned; a complete assignment gives every variable a value. An assignment is consistent if it violates no constraint whose variables are all assigned. A solution is a complete assignment that is consistent — in other words, every constraint is satisfied simultaneously. Note the word simultaneously: constraints are conjunctive. There is no notion of satisfying most of them, and no partial credit. (Variants such as MAX-CSP and weighted CSP relax this, but the classical problem is all-or-nothing.)

The canonical teaching example is map colouring. Consider colouring the mainland states and territories of Australia so that no two adjacent regions share a colour, using only red, green and blue:

X = {WA, NT, SA, Q, NSW, V, T}
D_i = {red, green, blue}   for every i
C = { WA≠NT, WA≠SA, NT≠SA, NT≠Q, SA≠Q, SA≠NSW, SA≠V, Q≠NSW, NSW≠V }

Tasmania (T) is an island, so it participates in no constraints at all and may take any colour. One solution is {WA=red, NT=green, SA=blue, Q=red, NSW=green, V=red, T=red}. The search space contains 3⁷ = 2187 complete assignments, of which only a handful are solutions; the point of propagation is to avoid enumerating most of the 2187.

Unary constraints are trivial: simply delete the forbidden values from the domain before search begins, and the constraint never needs to be looked at again. Binary constraints are the sweet spot for theory and for most textbook algorithms, because a binary CSP can be drawn as a constraint graph — one node per variable, one edge per constraint — and many results about tractability depend on graph properties such as tree-width.

Higher-order and global constraints are where real modelling power lives. AllDifferent(X₁, …, Xₖ) asserts that all k variables take pairwise distinct values. It can be decomposed into k(k−1)/2 binary disequalities, and the decomposition has exactly the same set of solutions. But the decomposition is weaker for inference. Suppose three variables all have domain {1, 2}. Every pairwise disequality is individually satisfiable — pick 1 for one variable and 2 for another — so binary propagation detects nothing. A dedicated AllDifferent propagator reasons about the whole group at once: three variables cannot fit into a two-value pool (a Hall set argument), so it reports failure immediately. This is a recurring theme: decomposition preserves solutions but loses pruning strength.

There is also a general-purpose reduction from arbitrary finite constraints to binary ones, the dual graph transformation: create one new variable per original constraint, whose domain is the set of tuples that constraint permits, and add a binary constraint between any two new variables that share original variables, requiring them to agree on the shared components. Combined with the hidden variable encoding, this means that any CSP can in principle be run through binary machinery. In practice the encoded domains can be huge, so production solvers prefer specialised propagators.

Why factored states matter. The practical consequence of writing a problem as (X, D, C) is that failure becomes explanatory. When a classical search algorithm reaches a dead end it knows only "this state has no useful successors". When a CSP solver reaches a dead end it knows "the domain of NSW became empty because SA=blue, Q=red and V=green between them ruled out every colour". That explanation can be used in at least four ways: to prune siblings (propagation), to decide which variable to branch on next (heuristics), to jump back more than one level (backjumping), and to record a new constraint that prevents the same conflict recurring elsewhere (clause learning / nogood recording). All of these are impossible without a factored representation.

Inference versus search. These are the two complementary engines of any CSP solver, and it helps to state their difference sharply.

  • Search makes commitments. It picks an unassigned variable, picks a value from its domain, and recurses. If the commitment leads to a violated constraint, it undoes the choice and tries the next value; if all values fail, it undoes the previous commitment too. Search is complete — given enough time it will find a solution or prove none exists — but it explores a tree whose size is O(dn) for n variables with domains of size d.
  • Inference makes deductions. It examines the constraints and removes values that cannot participate in any solution given what is currently known, without ever selecting a value for a variable. Inference does not grow the search tree at all; it shrinks the branching factor of nodes that have yet to be created.

Propagation is the repeated, cascading application of local inference until nothing more can be deduced. Each deduction may enable further deductions — removing a value from D(SA) may destroy the last support some value in D(NSW) had — so propagation loops until it reaches a fixed point: a state of the domains from which the inference rules derive no further deletions. Because domains are finite and propagation only ever removes values, the process is guaranteed to terminate; it is a monotonically decreasing sequence in a finite lattice.

Consider what happens with no inference at all. Pure chronological backtracking assigns variables in some fixed order and checks, after each assignment, only the constraints whose variables are now all assigned. Its characteristic pathology is thrashing: rediscovering the same conflict over and over in different parts of the tree. Suppose the variable order is Q, NSW, V, T, SA, NT, WA and we set Q=red, NSW=green, V=blue. SA is adjacent to all three, so its domain is already empty — but a plain backtracker does not look at SA until it is reached. It will first enumerate all three values of T, and for each of those try all three values of SA, failing each time, before backtracking. Multiply this by every combination of irrelevant variables between the cause and the symptom, and the waste becomes exponential.

Conversely, pure inference almost never finishes the job. Enforcing arc consistency on the Australia map-colouring CSP with three colours deletes nothing: every colour of every region has a supporting different colour in each neighbour. The domains remain full and no solution has been identified. There exist CSPs — those whose constraint graph is a tree, or those in certain tractable classes such as 2-SAT or problems with max-closed constraints — where a single consistency-enforcement pass is enough to decide satisfiability, but these are special cases. The practical conclusion is simply stated: effective solvers interleave search and inference, using search to make the commitments inference cannot make, and inference to shrink the consequences of each commitment.

Local consistency and domain reduction. "Consistency" in the CSP literature is always local: it is a property of a small neighbourhood of the constraint graph that is necessary, but not sufficient, for global solvability. Local consistency properties form a hierarchy; the two most fundamental are node consistency and arc consistency.

Node consistency concerns a single variable. A variable Xᵢ is node-consistent if every value in Dᵢ satisfies all of Xᵢ's unary constraints. A CSP is node-consistent if all its variables are. Enforcing it is a single linear sweep: for each unary constraint, delete the values that violate it. If a Tasmanian regulation says Tasmania may not be green, we simply set D(T) = {red, blue} and discard the constraint. Node consistency is so cheap and so routine that most solvers perform it during model construction and never mention it again.

Arc consistency concerns a directed pair of variables. The arc (Xᵢ, Xⱼ) is arc-consistent if, for every value a ∈ Dᵢ, there exists at least one value b ∈ Dⱼ such that the pair (a, b) satisfies the constraint between them. The value b is called a support for a. A value with no support can be deleted without losing any solution, because any solution containing Xᵢ = a would have to assign something to Xⱼ, and nothing works.

Two points about arc consistency catch people out. First, it is directional: making (X, Y) consistent says nothing about (Y, X), so a CSP with m binary constraints has 2m arcs to consider. Second, it is local: a fully arc-consistent CSP may still have no solution. The classic counterexample is three variables X, Y, Z with domains {red, green} and mutual disequality constraints. Every arc is consistent — red in X is supported by green in Y, and so on — yet three mutually-adjacent regions cannot be 2-coloured. Detecting this requires a stronger property, path consistency (3-consistency), which reasons about triples. The general notion is k-consistency: any consistent assignment to k−1 variables can be extended to any k-th variable. Stronger consistency prunes more but costs exponentially more to enforce, which is precisely the trade-off that makes arc consistency the industry default.

Let us make the arc-consistency computation concrete with an arithmetic example. Let D(X) = D(Y) = {1, 2, 3, 4, 5} with the constraint Y = X².

  • Revise arc (X, Y): X=1 needs Y=1 ✓. X=2 needs Y=4 ✓. X=3 needs Y=9 ✗ — delete 3. X=4 needs Y=16 ✗ — delete 4. X=5 needs Y=25 ✗ — delete 5. Now D(X) = {1, 2}.
  • Revise arc (Y, X): Y=1 needs X=1 ✓. Y=2 needs X=√2 ✗. Y=3 ✗. Y=4 needs X=2 ✓. Y=5 ✗. Now D(Y) = {1, 4}.
  • Re-revise (X, Y) to be safe: X=1 still supported by Y=1, X=2 still supported by Y=4. Nothing changes. Fixed point reached.

From 25 candidate pairs we are down to 2, with no search and no backtracking. Note that this CSP is now arc-consistent but not solved — there are two solutions, (1,1) and (2,4), and only search can choose between them.

Monotonicity. Within a single propagation episode, domain reduction is strictly monotonic: values are only ever removed, never added. This is what guarantees termination, and it is also what makes the fixed point unique — enforcing arc consistency by any order of operations yields exactly the same final domains, so AC-3, AC-4, AC-6 and AC-2001 differ in efficiency but never in result. Values come back only when the solver backtracks and undoes the assignment that triggered the deletions. This is why propagation and backtracking must be tightly coordinated, as discussed below.

Cascading deletions. Because support is defined relative to the current domains, deleting a value from one domain can destroy the support of values elsewhere. Suppose X ≠ Y, Y ≠ Z, D(X) = {red}, D(Y) = {red, green}, D(Z) = {green}. Enforcing arc (Y, X) deletes red from D(Y), leaving D(Y) = {green}. That deletion is not the end: we must now revisit arc (Y, Z), where green in Y has lost its only support, so D(Y) becomes empty. The cascade is the essential dynamic of propagation, and it is why every arc-consistency algorithm maintains a worklist or queue of arcs to re-examine: when Dⱼ changes, every arc (Xₖ, Xⱼ) pointing into it must be re-queued.

The empty-domain condition. If propagation empties any domain, we have a proof — not a heuristic hunch, a proof — that the current partial assignment cannot be extended to any solution. The variable in question must receive some value, every candidate value has been shown to be unsupportable, therefore no solution lies below this node. This is the single most valuable product of propagation, because it converts an expensive subtree exploration into an immediate failure. A closely related signal is the opposite: when a domain is reduced to a singleton, the variable's value is effectively forced, and many solvers immediately assign it and propagate again. In Sudoku this is exactly the "naked single" rule, and a solver that propagates AllDifferent over rows, columns and boxes can crack easy puzzles with no search whatsoever.

Interleaving propagation with backtracking search. The standard architecture is a depth-first recursive backtracking search with a propagation step injected after every assignment. In pseudocode:

function BACKTRACK(assignment, csp):
    if assignment is complete: return assignment
    var = SELECT-UNASSIGNED-VARIABLE(csp)          # MRV, degree, ...
    for value in ORDER-DOMAIN-VALUES(var, csp):    # LCV, ...
        if value is consistent with assignment:
            add {var = value} to assignment
            trail = PROPAGATE(csp, var, value)     # returns record of deletions
            if no domain is empty:
                result = BACKTRACK(assignment, csp)
                if result != failure: return result
            UNDO(trail)                            # restore every deleted value
            remove {var = value} from assignment
    return failure

Three design points deserve emphasis.

First, propagate before recursing. The whole value of inference lies in doing it before the subtree is expanded. Assigning WA = red and immediately pushing red out of D(NT) and D(SA) means that every node beneath this one branches on two colours instead of three for those variables. The saving compounds multiplicatively with depth.

Second, fail fast and fail loudly. The moment any domain is empty, abandon the branch. Do not continue to assign other variables "just in case"; the proof of failure is already complete. Early detection is the dominant source of speed-up in practice, far more so than the raw number of values pruned, because it avoids expanding doomed subtrees whose size is exponential in the remaining depth.

Third, deletions must be undone exactly. Because propagation mutates shared domain data structures, the solver must be able to restore them precisely on backtracking. The standard mechanism is a trail: a stack onto which every (variable, value) deletion is pushed, together with a mark recording the stack height at each decision point. On backtracking, the solver pops the trail down to the mark, reinserting each value. This is O(number of deletions) rather than O(size of the problem), which matters when the CSP is large and each decision touches only a few domains. The naïve alternative — copying all domains at every node — is simpler to implement but wastes memory and time proportional to the whole model at every node. Hybrid schemes such as timestamped domains or sparse sets with backtrackable size counters are common in production solvers. Getting this wrong produces a spectacularly confusing class of bug: a value that was deleted on one branch stays deleted on a sibling branch, and the solver silently reports "no solution" for satisfiable problems.

Fourth, how much to propagate is a dial, not a constant. At one extreme, backtracking with simple consistency checking does no inference at all. A step up, forward checking propagates only one level deep: when X is assigned, remove inconsistent values from the domains of unassigned variables directly connected to X, and stop. Stronger still, maintaining arc consistency (MAC) runs full arc-consistency propagation to a fixed point after each assignment, so deletions cascade arbitrarily far through the constraint graph. Stronger yet are path consistency, singleton arc consistency and generalised k-consistency, which are rarely worth their cost. The trade-off is uniform: more inference per node means fewer nodes but more work at each one.

There is no universally correct setting. On loosely constrained problems, cheap inference wins because there is little to prune and the overhead dominates. On tightly constrained problems near the phase transition, strong inference wins because each deduction eliminates vast subtrees. This is precisely why configurable solvers expose the inference level as a parameter and why empirical benchmarking across problem families is the only reliable way to choose.

Heuristics that exploit reduced domains. Propagation has a second, less obvious payoff beyond pruning: it produces information that ordering heuristics can exploit. The size of a current domain is a measurement of how constrained a variable is right now, and that measurement only exists if domains shrink.

Minimum Remaining Values (MRV), also called the most-constrained-variable or fail-first heuristic, selects next the unassigned variable with the smallest current domain. The name "fail-first" captures the logic: if some branch of the tree is doomed, we want to discover that as high up as possible, because a failure detected at depth 3 prunes everything below it while the same failure detected at depth 12 has already cost nine levels of fruitless expansion. Choosing the variable with fewest options maximises the chance of hitting an empty or near-empty domain immediately. A secondary benefit is that branching on a small domain creates few children, so the effective branching factor of the tree falls.

Return to Australia and suppose we have assigned WA = red and Q = green, with forward checking in force. The domains are now:

VariableCurrent domainSize
NT{blue}1
SA{blue}1
NSW{red, blue}2
V{red, green, blue}3
T{red, green, blue}3

MRV will branch on NT or SA, each of which has exactly one legal value left. That is the right call: those assignments are forced, they generate no branching, and propagating them immediately shrinks NSW and V. A solver that instead picked T — which is unconstrained and therefore maximally "free" — would multiply the tree by three for no information gain whatsoever. Note too that MRV here is effectively performing unit propagation: branching on a singleton domain is not really a choice at all.

MRV frequently produces ties, especially at the root where every domain is still full. The degree heuristic (also called most-constraining-variable) breaks ties by choosing the variable with the largest number of constraints connecting it to still-unassigned variables. The rationale is structural: assigning a high-degree variable injects constraint into the largest part of the remaining graph, so it produces the most propagation and the fastest reduction in the problem's connectivity. In the Australian map at the very start of search, all seven domains have size 3, so MRV is silent; the degree heuristic picks SA, which borders five other regions, over T, which borders none. Assigning SA first immediately strips one colour from five neighbours' domains, and in fact after that choice the rest of the map can be coloured with backtrack-free propagation. The degree heuristic is also useful as a standalone tie-break at the root for solvers that cache a static ordering.

Where MRV and degree choose which variable, the Least Constraining Value (LCV) heuristic chooses which value first. For the selected variable, LCV tries values in increasing order of how many values they eliminate from the domains of neighbouring unassigned variables — in other words, the value that rules out the fewest options elsewhere is tried first. The intuition is the mirror image of fail-first: variable ordering should fail fast, because every variable must eventually be assigned and we want to detect dead ends early, but value ordering should succeed fast, because we only need one value to work. Leaving neighbours maximum flexibility maximises the probability that the first value tried leads to a solution.

A worked LCV example: suppose WA = red and NT = green are assigned and we must now choose a value for Q, whose current domain is {red, blue}. Q neighbours NT (assigned), SA and NSW.

  • Choosing Q = red removes red from D(SA). But D(SA) is currently {blue} — red is already gone — so the net additional pruning on SA is zero, and it removes red from D(NSW), leaving two values there.
  • Choosing Q = blue removes blue from D(SA), which empties it immediately — a guaranteed dead end.

LCV therefore orders red before blue, and in this instance it steers the solver straight past a failure. The counting is cheap but not free: evaluating LCV requires a trial scan over every neighbouring domain for every candidate value, which is O(d · degree · d) work at each node. This is why LCV is often disabled when the goal is to prove unsatisfiability — if there is no solution, every value must be tried anyway, so ordering them carefully is pure overhead. LCV pays off when solutions are plentiful and we want the first one quickly.

The crucial observation tying this section back to the rest of the topic is that all three heuristics are starved of information without propagation. In a solver that performs no inference, domains never shrink: every unassigned variable has the same domain it started with, MRV cannot distinguish between them, and LCV's "values eliminated from neighbours" count is based on constraint checks against values that have never been pruned. MRV degenerates into an arbitrary tie-break, and what is left is the static degree heuristic computed once from the constraint graph. Propagation and heuristics are therefore not two independent optimisations that happen to be used together — they are symbiotic. Propagation generates the dynamic signal; the heuristics convert that signal into better decisions; better decisions trigger more propagation. Modern solvers push this further with heuristics such as dom/wdeg, which divides the current domain size by the accumulated weight of constraints that have caused failures, learning from the search's own history which parts of the model are hardest.

The combined effect can be dramatic. On the n-queens problem, plain chronological backtracking becomes impractical well before n = 50, whereas MRV plus forward checking routinely solves instances in the thousands. On Sudoku, constraint propagation with AllDifferent plus MRV solves the overwhelming majority of published puzzles with a handful of backtracks or none at all. The theoretical worst case remains exponential — CSP is NP-complete, and no heuristic changes that — but on structured, real-world instances good ordering plus strong propagation frequently yields near-linear behaviour, because each decision propagates to force a cascade of other decisions and the search simply walks down a nearly deterministic path. That is the payoff that justifies everything in this topic: representation that exposes structure, inference that exploits it, search that commits only where inference cannot decide, and heuristics that read the state of the domains to decide where to commit next.

A constraint satisfaction problem (CSP) is a particular way of describing a problem: instead of a single opaque goal test, you state a set of variables, the values each variable may take (its domain), and constraints that say which combinations of values are allowed. Map colouring, Sudoku, timetabling, and the N-queens puzzle are all natural CSPs. Because the structure of the problem is exposed, a solver can do more than blindly try assignments — it can reason about what the constraints imply before committing to a choice.

That reasoning is called inference, or constraint propagation. When you assign a value to one variable, the constraints often rule out values in neighbouring variables' domains; removing those values is domain reduction, and doing it systematically is what we mean by enforcing local consistency. The practical payoff is that propagation detects dead ends early, so backtracking search explores far fewer nodes. This topic sets up the vocabulary and intuition you will need before we study forward checking and AC-3 in detail, including how propagation is interleaved with search and how shrunken domains feed variable- and value-ordering heuristics such as minimum remaining values.

As you watch, pay attention to three things: how a problem is formally specified as variables, domains and constraints; where inference happens relative to the search tree; and what information a reduced domain gives you about which variable to try next. Keep a small example (a map or a 4x4 queens board) on paper and track the domains yourself as the speaker works through the problem.

Forward Checking

▶

Forward checking is the simplest and most widely used form of look-ahead in constraint satisfaction search. Plain chronological backtracking is a "look-behind" algorithm: it assigns a value to a variable, then checks the new assignment against the assignments already made, and only discovers that a branch is hopeless when it finally reaches the variable whose domain has been exhausted. Forward checking reverses the direction of reasoning. Immediately after a variable is assigned, it looks forward into the domains of the still-unassigned variables and deletes every value that the new assignment has made impossible. The payoff is that a contradiction shows up as an empty domain at the moment it is created, rather than many levels deeper in the search tree, and that the surviving domains give the variable- and value-ordering heuristics much better information to work with.

Formally, a constraint satisfaction problem (CSP) is a triple of variables X = {X₁ … Xₙ}, domains D(X₁) … D(Xₙ), and constraints C. In a binary CSP every constraint relates exactly two variables, and the problem can be drawn as a constraint graph whose nodes are variables and whose edges are constraints. Forward checking is defined most naturally on binary CSPs, and the discussion below assumes that setting unless stated otherwise.

What forward checking does

Forward checking is a local operation with a deliberately narrow scope. When the search assigns X = v, forward checking visits only the neighbours of X in the constraint graph — the unassigned variables Y such that a constraint C(X, Y) exists. For each such Y it scans D(Y) and deletes every value w for which the pair (v, w) violates C(X, Y). Variables that do not share a constraint with X are untouched, and variables that are already assigned are irrelevant because the assignment X = v was itself checked against them before being accepted. The work done is therefore proportional to the degree of X, not to the size of the whole problem — a crucial property when the constraint graph is sparse, as it is in scheduling, timetabling and map-colouring instances.

Because the deletions are provisional — they are consequences of a tentative assignment that may later be undone — they must be recorded. Every implementation keeps a trail: a per-assignment record of exactly which values were removed from which domains. The usual data structure is a stack of (variable, value) pairs with a mark pushed at each decision level, or an array pruned[X][v] listing the deletions attributable to assigning X = v. When the search abandons X = v, the trail is unwound and every recorded value is put back. Without this bookkeeping the search would be unsound: domains would shrink monotonically and legitimate solutions in other branches would be lost.

The invariant that forward checking maintains is worth stating precisely, because it is the whole justification for the technique:

  • Forward-checking invariant: at every node of the search tree, for every unassigned variable Y and every value w remaining in D(Y), the extended assignment that adds Y = w to the current partial assignment violates no constraint.

In the vocabulary of consistency, this is exactly arc consistency between each unassigned variable and each assigned variable. It is a strictly weaker property than full arc consistency, which also demands consistency between pairs of unassigned variables. Two immediate consequences follow from the invariant. First, when the search picks the next variable and value, it never needs to re-check that value against any earlier assignment — the check has already been done, which is why forward checking can replace rather than merely supplement the consistency test of plain backtracking. Second, an empty domain is a certificate of failure: if D(Y) is empty then no value of Y is compatible with the current partial assignment, so that partial assignment cannot be part of any solution.

Forward checking performs inference exactly one level deep. If removing values from D(Y) implies, through a constraint C(Y, Z), that some value of a third unassigned variable Z has lost all of its supports, forward checking does not notice. It never re-examines Y's other neighbours after pruning Y. This is the defining limitation, and it is the deliberate price paid for cheapness; propagating those consequences transitively is what arc consistency algorithms such as AC-3 do.

Finally, forward checking requires no structural change to the backtracking search. The recursive skeleton — choose a variable, iterate over its values, recurse, undo — is unchanged. Forward checking inserts one pruning step after the assignment and one restoration step after the recursive call returns. This modularity is the reason it is the usual default in textbook and production CSP solvers alike: it can be switched on or off with a flag, which also makes it an ideal baseline for benchmarking stronger inference.

The forward checking algorithm step by step

The five steps below describe one node of the search. They are written as a recursive procedure, but the same logic applies to an iterative solver with an explicit stack.

  • Step 1 — Select and assign. Choose an unassigned variable X (typically by the MRV heuristic, below) and iterate over the values v currently remaining in D(X). Note that D(X) here is the current, already-pruned domain, not the original one. Tentatively set X = v.
  • Step 2 — Prune the neighbours. For every unassigned variable Y with a constraint C(X, Y), examine each w ∈ D(Y) and delete w if (v, w) violates C(X, Y). Record every deletion on the trail under the decision X = v.
  • Step 3 — Test for domain wipe-out. If any D(Y) becomes empty, the assignment X = v is refuted. Undo the deletions made in Step 2 at once, and continue the loop of Step 1 with the next value of X. Do not recurse. If no value of X survives, return failure so that the parent node backtracks.
  • Step 4 — Recurse. If all neighbour domains are still non-empty, call the search recursively to assign the next variable. If the recursive call returns a solution, propagate it upward.
  • Step 5 — Restore on backtrack. When the recursive call fails and the search leaves X = v, unwind the trail for that decision: every value pruned in Step 2 is returned to the domain it came from, and X is marked unassigned again. The domains are then bit-for-bit identical to their state before Step 1, so the next value of X is tried in a clean context.
function BACKTRACK-FC(assignment, domains):
    if assignment is complete: return assignment
    X <- SELECT-UNASSIGNED-VARIABLE(domains)        # e.g. MRV, ties broken by degree
    for each v in ORDER-DOMAIN-VALUES(X, domains):   # e.g. least-constraining value
        assignment[X] <- v
        trail <- empty list
        wipeout <- false
        for each unassigned Y in NEIGHBOURS(X):
            for each w in domains[Y]:
                if not CONSISTENT(X, v, Y, w):
                    remove w from domains[Y]
                    append (Y, w) to trail
            if domains[Y] is empty:
                wipeout <- true
                break                                # fail fast: stop pruning
        if not wipeout:
            result <- BACKTRACK-FC(assignment, domains)
            if result != failure: return result
        for each (Y, w) in trail:                    # Step 5: restore
            add w back to domains[Y]
        remove X from assignment
    return failure

Two implementation details matter in practice. First, the break on wipe-out is an optimisation only: once one domain is empty the assignment is already refuted, so pruning the remaining neighbours is wasted work — but the trail must still be unwound correctly, which the code above does because it restores whatever was recorded. Second, domains are usually represented as bitsets or as "domain arrays with a current size" so that deletion and restoration are O(1) per value and the current domain size is available in constant time for the MRV heuristic.

Worked example: map colouring

The classic illustration is colouring the states and territories of Australia with three colours so that no two adjacent regions share a colour. The variables are WA, NT, SA, Q, NSW, V and T; each domain is initially {red, green, blue}. The adjacency constraints are: WA–NT, WA–SA, NT–SA, NT–Q, SA–Q, SA–NSW, SA–V, Q–NSW, NSW–V. Tasmania (T) borders nothing, so it is an isolated node in the constraint graph.

  • Q = green. Q's unassigned neighbours are NT, SA and NSW. Green is deleted from each, giving D(NT) = {blue}, D(SA) = {blue} and D(NSW) = {red, blue}. No domain is empty, so the search continues. Notice that NT and SA are now both singletons holding the same colour, and NT–SA is a constraint — the partial assignment is already doomed, but forward checking cannot see this, for reasons taken up under "Limitations" below.
  • V = blue. V's unassigned neighbours are SA and NSW. Blue is deleted from D(SA) = {blue}, which wipes it out, and from D(NSW) = {red, blue}, leaving {red}. The empty domain for SA is detected the instant it occurs, so the solver immediately rejects V = blue, restores blue to SA and NSW, and tries the next value for V. It never descends into the subtree below V = blue.

Contrast this with plain chronological backtracking under the same variable order. Having set WA = red, Q = green and V = blue, plain backtracking has checked each new value only against the earlier assignments, all of which succeeded (WA and Q are not adjacent; V is adjacent to neither WA nor Q, so V = blue is accepted outright). It would then go on to assign NT, then NSW, and only when it finally reached SA would it discover that no colour is available — having in the meantime enumerated combinations of NT and NSW values, each of which requires its own consistency checks and its own node in the search tree. Forward checking collapses all of that wasted exploration into a single test.

When the search backtracks out of V = blue, the trail for that decision contains (SA, blue) and (NSW, blue). Restoring them gives D(SA) = {blue} and D(NSW) = {red, blue} — exactly the state shown in the "Q = green" row of the table. The restoration is exact and local: deletions attributable to WA = red and Q = green are untouched, because they belong to decisions that are still in force. This is why the trail must be organised by decision level rather than as a single undifferentiated set.

Early failure detection and interaction with heuristics

The logical content of an empty domain deserves emphasis. If D(Y) = ∅ after forward checking, then by the forward-checking invariant every original value of Y conflicts with at least one current assignment. Since Y must receive some value in any complete solution, the current partial assignment extends to no solution at all. The empty domain is therefore a proof of failure, not a heuristic guess, and the solver is entitled to prune the entire subtree below it. This soundness is what makes the technique safe: forward checking never prunes a branch that contains a solution.

Beyond failure detection, the pruned domains are a rich source of information for the ordering heuristics that do most of the practical work in CSP solving.

  • Minimum Remaining Values (MRV), also called "fail-first". Choose next the unassigned variable with the smallest current domain. This heuristic is almost useless under plain backtracking, where domains never shrink and every variable looks identical; it becomes powerful precisely because forward checking maintains live domain sizes. The rationale is that a variable with one remaining value is forced, so assigning it propagates information immediately, while a variable with zero remaining values signals failure at once. In the trace above, after Q = green MRV would select NT or SA (domain size 1) rather than V (domain size 3). Choosing SA, the only value is blue; forward checking then deletes blue from NT, wiping it out, and the doomed branch is refuted one assignment earlier still.
  • Degree heuristic. MRV often produces ties, especially at the root where all domains are the same size. The degree heuristic breaks ties by preferring the variable involved in the largest number of constraints with unassigned variables, because assigning it prunes the most domains and so maximises the amount of inference performed. In Australia, SA has degree 5 and would be chosen first at the root, which is an excellent decision: colouring SA immediately removes one colour from five other domains.
  • Least-constraining value (LCV). Having chosen a variable, order its values so that the one which rules out the fewest values in neighbouring domains is tried first. The counts needed are exactly the deletion counts that forward checking computes anyway — a trial forward-check per candidate value yields the number of prunings. Where MRV is "fail-first" on variables, LCV is "succeed-first" on values: it keeps the remaining search space as large as possible so that a solution is more likely to be found without backtracking.

The combination is more than the sum of its parts. On the n-queens problem, plain backtracking becomes impractical somewhere around n = 25–30; forward checking with MRV and degree tie-breaking routinely solves instances with hundreds of queens, because each queen placement immediately strips the attacked squares from the remaining columns' domains and MRV then pounces on whichever column has become most constrained. On random binary CSPs near the phase transition, the reduction in nodes expanded is typically one to three orders of magnitude relative to plain backtracking with the same static ordering.

Cost versus pruning power

Forward checking buys node reductions with per-node work, and it is worth quantifying both sides of the trade. Let n be the number of variables, d the maximum domain size and deg(X) the number of unassigned neighbours of the variable being assigned.

  • Time per assignment. Checking one neighbour costs O(d) constraint checks — one per remaining value of that neighbour. The whole forward-checking step therefore costs O(deg(X) · d) constraint checks, which in the worst case of a complete constraint graph is O(n · d). On sparse graphs the degree is a small constant and the cost is O(d).
  • Space. The trail stores one entry per pruned value. Across a root-to-leaf path of depth n, at most n · d values can ever be deleted in total (each value of each variable can be deleted at most once while it stays deleted), so the trail is O(n · d) in the worst case — modest, and easily implemented as a preallocated array. Restoration costs O(1) per recorded deletion.
  • Nodes. Plain backtracking creates and tests nodes that forward checking prevents from ever being generated: any assignment that would later be found inconsistent with an existing assignment is removed from the domain in advance. Each pruned node would otherwise have cost at least one consistency check plus the stack frame, and may have had an entire subtree below it.

A useful theoretical guarantee: with the same variable and value ordering, forward checking never visits a node that chronological backtracking does not also visit. Every node it prunes is one that backtracking would eventually have refuted. So the node count can only improve, and the only possible loss is the constant-factor overhead per node. That is why forward checking is generally adopted as the default rather than as an option to be justified case by case.

The overhead is nevertheless real, and its significance depends on constraint tightness. On a loosely constrained problem — few constraints, or constraints that forbid only a small fraction of value pairs — most forward-checking scans delete nothing, so the solver pays O(deg · d) per node for no return and may be measurably slower than plain backtracking in wall-clock terms even though it expands the same number of nodes. On tightly constrained problems, and especially near the satisfiable/unsatisfiable phase transition where most branches are doomed, the deletions come thick and fast, wipe-outs are frequent, and the saving in nodes dwarfs the per-node cost.

Limitations of forward checking

The single structural weakness is that forward checking does not propagate. When it shrinks D(Y), it stops. It does not ask whether the values that remain in D(Y) still support the values in the domains of Y's other neighbours, so a deletion never cascades. All of the following limitations are corollaries of that one fact.

  • Inconsistencies between two future variables are invisible. Return to the trace after WA = red, Q = green: D(NT) = {blue} and D(SA) = {blue}, and NT–SA is a constraint. The partial assignment is unsatisfiable, but no domain is empty, so forward checking sees nothing wrong and the search happily descends. Arc consistency would catch it instantly: revising the arc NT → SA finds that NT's only value, blue, has no support in D(SA) = {blue}, so blue is deleted from NT and NT is wiped out. This single example is the standard demonstration that forward checking is strictly weaker than arc consistency.
  • Doomed branches are still explored. Because such hidden conflicts go undetected, the solver continues to assign variables below a node that can never succeed, discovering the failure only when the conflict finally involves an assigned variable. Each wasted level multiplies the number of nodes by roughly the branching factor.
  • The guarantee is one-sided. An empty domain proves failure, but a non-empty domain proves nothing. Forward checking can certify that a branch is dead; it can never certify that a branch is alive. Stronger inference narrows the gap but never closes it entirely — only a complete search can confirm satisfiability.
  • Stronger look-ahead exists at higher cost. Running a full arc-consistency pass after every assignment — restricting the initial arc queue to the arcs (Y, X) that point at the newly assigned variable X, then propagating — gives the algorithm usually called Maintaining Arc Consistency (MAC), or sometimes "really full look-ahead". MAC subsumes forward checking: its first round of revisions performs exactly the prunings forward checking would perform, and then it keeps going. It expands fewer nodes, but each node costs more, and on easy or loosely constrained instances that extra work is not repaid.
  • Forward checking sits at the bottom of a hierarchy. The family of look-ahead schemes runs roughly: backtracking (no look-ahead) → forward checking (one level, neighbours of the assigned variable) → partial look-ahead / directional arc consistency (propagation restricted to future variables in one direction) → MAC with AC-3 or AC-4 (full arc consistency at every node) → path consistency and higher-order k-consistency (prohibitively expensive in general). Each step up the hierarchy prunes more per node and costs more per node, and the best choice is empirical, which is precisely why configurable solvers expose the inference level as a parameter and why benchmark comparisons report both nodes expanded and runtime.

A final practical note: forward checking generalises beyond binary constraints, but less elegantly. For an n-ary constraint, the usual rule is to prune only when all but one of its variables are assigned, at which point the single unassigned variable's domain can be filtered exactly — this is sometimes called the "forward checking on the last unassigned variable" rule. Earlier, weaker filtering of n-ary constraints is the province of specialised propagators (for example, bounds or domain propagators for alldifferent), which again belong to the stronger-inference end of the spectrum rather than to forward checking proper.

Arc Consistency and the AC-3 Algorithm

Arc Consistency and the AC-3 Algorithm

▶

Backtracking search alone explores a combinatorial space blindly: it assigns a value, discovers a conflict many levels deeper, and then undoes a great deal of work. Constraint propagation changes the economics of that search by reasoning about the constraints before committing to assignments. Rather than asking "which value shall I try next?", propagation asks "which values could never participate in any solution, given what I already know?" and deletes them. Arc consistency is the workhorse of this idea for binary constraint satisfaction problems (CSPs), and AC-3 is the algorithm that made it practical. Everything that follows — the REVISE subroutine, the queue of arcs, the termination analysis, the complexity bounds, and the comparison with forward checking and higher levels of consistency — is an elaboration of one simple principle: a value that has no support is a value that can be thrown away.

Defining arc consistency

A CSP is a triple of variables, domains and constraints. For a binary CSP, each constraint relates exactly two variables, say X and Y, and can be viewed as a set of permitted pairs C(X,Y) ⊆ D(X) × D(Y). Each binary constraint gives rise to two directed arcs: (X, Y) and (Y, X). The direction matters, because arc consistency is a statement about one variable's domain being supported by the other's.

Formally: the arc (X, Y) is arc consistent if and only if, for every value x ∈ D(X), there exists at least one value y ∈ D(Y) such that the pair (x, y) satisfies the constraint between X and Y. Such a y is called a support for x on that arc. A value with no support anywhere in D(Y) is unsupported.

Note the asymmetry carefully. Arc (X, Y) being consistent says nothing about arc (Y, X). Consider D(X) = {1, 2, 3}, D(Y) = {1, 2, 3, 4, 5} and the constraint X < Y. Arc (X, Y) is already consistent: 1 is supported by 2, 2 by 3, 3 by 4. But arc (Y, X) is not: y = 1 needs some x ∈ D(X) with x < 1, and none exists, so 1 must be deleted from D(Y). A CSP as a whole is arc consistent only when every arc, in both directions, is arc consistent.

Why is deleting an unsupported value safe? Suppose x ∈ D(X) has no support in D(Y). Any complete solution must assign some value to Y drawn from D(Y), and that value must be compatible with X's value. If X = x, no legal choice for Y exists, so no solution contains X = x. Deleting x therefore removes zero solutions: the pruned CSP is equivalent to the original in the sense that it has exactly the same solution set. This is the crucial property that lets us interleave propagation with search without compromising completeness.

Arc consistency is best understood as inference, not search. It never guesses a value, never branches, and never creates a choice point. It deduces consequences of the constraints and records those consequences by shrinking domains. Because it is sound (it deletes only values that cannot appear in a solution) but incomplete (an arc-consistent network may still have no solution), it is used as an accelerator inside search rather than as a replacement for it.

A small worked illustration of pure inference: let D(X) = D(Y) = {0,1,2,...,9} with the constraint Y = X².

  • REVISE on arc (X, Y): the value x survives only if x² ∈ D(Y). Thus 0, 1, 2, 3 survive (squares 0, 1, 4, 9), while 4..9 are deleted (16, 25, ... exceed 9). New D(X) = {0,1,2,3}.
  • REVISE on arc (Y, X): the value y survives only if some x ∈ D(X) has x² = y. So D(Y) = {0,1,4,9}.

Both arcs are now consistent and the network has been reduced from 100 candidate pairs to 4, with no assignment made and no solution lost.

Many real constraints are not binary: Alldiff(A,B,C,D), A + B + C = 10, or a table constraint over five variables. Generalized arc consistency (GAC), also called hyper-arc consistency or domain consistency, extends the definition to any arity: a constraint C(X₁,...,X_k) is GAC with respect to variable X_i if, for every value v ∈ D(X_i), there exists a tuple in C containing v whose other components are all drawn from the current domains of the other variables. Such a tuple is the support. Enforcing GAC on an arbitrary k-ary constraint by brute-force search over tuples costs O(d^k), which is why practical solvers attach a specialised propagator to each global constraint — an algorithm that achieves GAC for that constraint far faster than enumeration. Binary arc consistency is simply the case k = 2.

The REVISE step

REVISE is the atomic operation of arc consistency: it makes a single arc consistent by deleting unsupported values from the tail variable's domain. It never touches the head variable's domain.

function REVISE(csp, X, Y) returns true if D(X) was changed
    revised ← false
    for each x in D(X) do
        if no value y in D(Y) satisfies the constraint C(X, Y) with x then
            delete x from D(X)
            revised ← true
    return revised

Three details deserve emphasis:

  • Only D(X) is modified. To make the relationship symmetric you must also call REVISE(csp, Y, X), which is exactly why the queue is initialised with arcs in both directions.
  • The boolean return value is the propagation trigger. Returning true means at least one value disappeared from D(X). Any other variable Z constrained with X may have had values whose only support was one of the just-deleted values, so arcs (Z, X) must be re-examined. Returning false means the arc was already consistent; nothing changed, so nothing downstream can have become inconsistent because of this call, and no new work is scheduled. This simple flag is what turns a collection of local checks into a cascading global propagation.
  • Implementation hygiene. Deleting from a collection while iterating over it is a classic bug; implementations typically iterate over a snapshot of D(X) or collect deletions in a buffer and apply them afterwards. Solvers that support backtracking must also record deletions on a trail so they can be undone when search retreats.

The cost of the naive version is O(d²) where d = max|D|: the outer loop runs up to d times, and for each x the inner search for a support may scan all d values of D(Y) before giving up. The inner loop can of course exit early the moment a support is found, which is why REVISE is usually much cheaper than d² in practice — but the worst case is realised whenever many values are genuinely unsupported.

The AC-3 algorithm and its queue of arcs

AC-3 (Mackworth, 1977) drives REVISE to a fixed point using a worklist of arcs that still need checking.

function AC-3(csp) returns false if an inconsistency is found, true otherwise
    queue ← all arcs (Xi, Xj) of csp, both directions for every binary constraint
    while queue is not empty do
        (X, Y) ← REMOVE-FIRST(queue)
        if REVISE(csp, X, Y) then
            if size of D(X) = 0 then return false        // wipe-out: failure
            for each Z in NEIGHBOURS(X) \ {Y} do
                add arc (Z, X) to queue
    return true

The logic of each line:

  • Initialisation. Every arc, in both directions, must be examined at least once, because at the start we know nothing about which arcs are already consistent. For a CSP with c binary constraints the queue starts with 2c directed arcs. (When AC-3 is used for maintaining arc consistency inside search, the initial queue is smaller — typically only the arcs pointing into the variable just assigned — because the rest of the network was already arc consistent before the assignment.)
  • Pop and revise. The queue is really a set-like worklist: order affects speed but not the final result. A FIFO queue gives breadth-first-like propagation; a LIFO stack often reaches a wipe-out faster; many solvers use a priority scheme that revises arcs with small domains first. Whichever discipline is used, the fixed point reached is unique — arc consistency defines the largest sub-domains closed under the support condition, independently of processing order.
  • Re-enqueuing neighbours. If D(X) shrank, then for any neighbour Z of X there may be a value z ∈ D(Z) whose only support in D(X) was one of the deleted values. That is precisely the arc (Z, X), pointing into the shrunken variable, so (Z, X) goes back on the queue. The arc (Y, X) is excluded because Y's domain was untouched by this REVISE and every value of Y that had support in the old D(X) still has it: the values just deleted from D(X) were by definition unsupported by D(Y), so they were supporting nothing in D(Y). Arcs of the form (X, Z) are also not re-added, since shrinking the tail domain cannot make the tail arc inconsistent.
  • Loop to emptiness. When the queue drains, no arc can be revised further, which is the definition of a globally arc-consistent network.

A full worked example on map colouring. Take the Australian states WA, NT, SA, Q, NSW, V, T with colours {R, G, B} and "adjacent regions differ" constraints: WA–NT, WA–SA, NT–SA, NT–Q, SA–Q, SA–NSW, SA–V, Q–NSW, NSW–V (T is isolated). Suppose search has assigned WA = R and Q = G, so D(WA) = {R} and D(Q) = {G}, with every other domain still {R,G,B}. Running AC-3 produces:

Termination conditions and outcomes

An AC-3 run ends in exactly one of two ways, and the "success" case subdivides into three situations of practical interest.

  • Failure (domain wipe-out). Some D(X) becomes empty. Since every variable must receive a value, the current partial assignment has no extension to a solution. AC-3 returns false and the search backtracks at once — crucially, before wasting effort on the subtree below. Detecting failure early is the main source of AC-3's speed-up.
  • Success (queue empties, all domains non-empty). The network is now arc consistent, and the pruned CSP is equivalent to the original. Three sub-cases:
    • All domains are singletons. Then the unique remaining combination is forced and, because the network is arc consistent, every pair of neighbouring assignments is mutually supporting — so a solution has been read off directly by inference, with no search at all. (This is the dream case; it occurs, for example, in easy Sudoku puzzles solvable by simple elimination rules.)
    • Some domain is empty — impossible here by assumption, so the remaining case is that at least one domain has two or more values. The reduced domains are handed back to the search algorithm, which chooses a variable and value as usual but now over strictly smaller domains. Smaller domains also sharpen value-ordering and variable-ordering heuristics: minimum-remaining-values (MRV) and degree heuristics become far more informative after propagation.
    • No pruning at all occurred. The network was already arc consistent; AC-3 has cost time without reducing anything. This is the overhead that must be weighed against the pruning benefit.

It is essential to remember that an arc-consistent network is not necessarily solvable. The canonical counterexample is 2-colouring a triangle: variables A, B, C, domains {R, B}, with A≠B, B≠C, A≠C. Every value has support on every arc (for A=R, B=B works; for A=B, B=R works, and so on), so the network is perfectly arc consistent — yet no solution exists, because a triangle needs three colours. Arc consistency reasons only about pairs; it cannot see the three-way interaction. That limitation motivates stronger consistency levels, discussed below.

Why termination is guaranteed. Consider the quantity Φ = (total number of values remaining in all domains, size of queue) ordered lexicographically. Each iteration pops one arc. Either REVISE deletes at least one value — which strictly decreases the first component, and the first component is a non-negative integer bounded by nd — or REVISE deletes nothing, in which case no arcs are added and the queue strictly shrinks. Since Φ cannot decrease forever in a well-founded order, the loop must terminate. In other words, arcs can only be re-enqueued as a consequence of a deletion, and there are finitely many values to delete.

Complexity analysis of AC-3

Let n be the number of variables, d the maximum domain size, and c the number of binary constraints (so 2c directed arcs).

  • How often can an arc enter the queue? An arc (Z, X) is inserted initially (once) and thereafter only when D(X) loses a value. D(X) can lose at most d values in total over the entire run, because deletions are never undone within a run. Hence each directed arc is processed O(d) times.
  • Cost per processing. Each REVISE is O(d²).
  • Total time. O(2c · d · d²) = O(c d³). Since a binary CSP on n variables has at most n(n−1)/2 = O(n²) constraints, the bound can equivalently be written O(n² d³).
  • Space. The queue holds directed arcs and never needs duplicates (a well-implemented worklist checks membership before inserting), so it is O(c), i.e. O(n²). Added to that is the storage for the domains themselves, O(nd), plus — in a backtracking solver — a trail of deletions so that propagation can be undone on backtrack.

Comparing the three figures for a sense of scale:

QuantityBoundReason

Total time (AC-3)O(c d³) = O(n² d³)2c arcs × O(d) insertions × O(d²) per revision
SpaceO(c) + O(nd)Queue of arcs plus the domains (plus a trail inside search)

The O(cd³) figure is a genuine worst case and is rarely approached. Three reasons explain the gap between theory and practice. First, most arcs are revised only once or twice: a revision re-enqueues neighbours only when it actually deletes something, and in a typical network the great majority of REVISE calls delete nothing. Second, the inner support search exits at the first support found, so for loose constraints (where almost every pair is permitted) the first candidate y usually works and REVISE behaves like O(d). Third, domains shrink as propagation proceeds, so later revisions operate on smaller d than the bound assumes. The practical consequence is that AC-3 is simple, cache-friendly and fast enough that it remains the default generic propagator in many teaching solvers, even though AC-4, AC-6 and AC-2001 have asymptotically better O(cd²) bounds (which is worst-case optimal). AC-4 achieves this by precomputing support counters for every value pair, but the up-front cost of building those structures often makes it slower than AC-3 on real instances; AC-2001 reaches the optimal bound with much lighter bookkeeping by remembering, for each value x and arc, the last support found, and resuming the scan from there.

AC-3 versus forward checking

Forward checking (FC) and arc consistency sit on the same spectrum; they differ only in how far the inference is pushed.

When search assigns Y = v, forward checking revises exactly the arcs (X, Y) for each unassigned neighbour X of Y, deleting from D(X) every value incompatible with v. It then stops. Nothing is re-enqueued; if D(X) shrinks, the consequences of that shrinkage for X's own neighbours are never explored. In the AC-3 pseudocode, forward checking is what you get if you delete the inner for each Z in NEIGHBOURS(X) loop and initialise the queue with only the arcs into the newly assigned variable. In other words, forward checking is one round of revision with no propagation; AC-3 is revision driven to a fixed point.

Maintaining arc consistency (MAC) is the standard name for running AC-3 (or a stronger AC algorithm) after every assignment during backtracking search, starting the queue with the arcs (X, Y) for unassigned neighbours X of the just-assigned Y, and letting the cascade run.

The Australian map-colouring trace above shows the difference sharply. After WA = R and Q = G, forward checking would set D(NT) = {B} (removing R because of WA and G because of Q), D(SA) = {B} (same reasoning), and D(NSW) = {R,B}. No domain is empty, so forward checking reports no problem and search continues, only to discover the NT/SA clash one or two levels deeper. AC-3, by contrast, re-examines arc (NT, SA) because D(SA) changed, finds that NT's only value B has no support in SA's only value B, wipes out D(NT), and backtracks immediately. This is the characteristic pattern: forward checking cannot detect inconsistency between two unassigned variables; arc consistency can.

The trade-off is therefore between nodes expanded and work per node, and neither metric alone decides the winner — only their product, total runtime, does. On tightly constrained problems (many constraints, small domains, few solutions) propagation pays for itself many times over, because most branches are dead and AC-3 kills them near the root; MAC is the standard choice for hard instances such as large Sudoku variants, graph colouring near the chromatic threshold, or scheduling with tight resources. On loosely constrained problems (large domains, few constraints, many solutions) almost every branch leads to a solution anyway, AC-3 deletes little, and its overhead at every node is pure waste; forward checking — or even plain backtracking with good heuristics — can be the faster overall choice. Hybrid strategies exist: run full arc consistency once as a preprocessing step before search begins (cheap, done only once, and often a big win), then use forward checking during the search itself.

Stronger consistency: path and k-consistency

The triangle-colouring example showed the ceiling of arc consistency: it reasons about one constraint at a time and cannot see interactions among three or more variables. Higher levels of consistency raise that ceiling.

Path consistency (equivalently 3-consistency) considers pairs of variables and a third witness. A pair {X, Y} is path consistent with respect to Z if, for every assignment {X = a, Y = b} consistent with the constraint on X,Y, there exists some c ∈ D(Z) such that {X = a, Z = c} and {Y = b, Z = c} are both consistent. A CSP is path consistent when this holds for every pair and every third variable. Unlike arc consistency, enforcing path consistency may delete pairs, not just values — it tightens the binary constraints themselves, possibly adding explicit constraints between variables that previously had none.

Path consistency cracks the triangle example immediately. With D(A)=D(B)=D(C)={R,B} and all-different constraints, take the consistent pair {A=R, B=B} and the witness C: C=R clashes with A, and C=B clashes with B. No witness exists, so the pair (R, B) is deleted from the constraint on {A, B}. By symmetry the pair (B, R) also goes, leaving the constraint on {A,B} empty — an immediate, inference-only proof that the problem is unsolvable, which arc consistency could never produce.

k-consistency generalises the pattern. A CSP is k-consistent if, for any consistent assignment to any k−1 variables, and any k-th variable, there is a value for that k-th variable extending the assignment consistently. The hierarchy lines up as follows:

A CSP is strongly k-consistent if it is j-consistent for every j ≤ k. Strong n-consistency on an n-variable problem means a solution can be constructed greedily without ever backtracking — but establishing it is NP-hard in general (it essentially amounts to solving the problem), and in the worst case requires space exponential in n. This is the central practical lesson of the hierarchy: consistency levels above arc consistency buy pruning at a price that rises exponentially in k, and beyond k = 2 — occasionally k = 3 on small, very tight subproblems — the price usually exceeds the benefit. Arc consistency sits at the sweet spot of the cost/pruning curve, which is why MAC, not "maintaining path consistency", is the industry default. There is one notable structural exception: if the constraint graph is a tree, enforcing arc consistency (directionally, along a topological ordering of the tree) is sufficient to guarantee a backtrack-free solution in O(nd²) time.

Modern solvers get stronger-than-arc pruning by a different route: specialised propagators for global constraints. The classic example is Alldiff(X₁,...,X_k). Decomposed into k(k−1)/2 pairwise ≠ constraints and handled by generic arc consistency, it prunes very little — with D(X₁)=D(X₂)=D(X₃)={R,B} and pairwise ≠, arc consistency detects nothing, exactly as in the triangle example. Treated as a single global constraint, however, GAC can be enforced using Régin's algorithm, which models the value–variable relation as a bipartite graph and uses maximum matching plus a strongly-connected-components analysis (Hopcroft–Karp and Tarjan) to delete, in roughly O(k^1.5 d) time, every value that belongs to no maximum matching. That immediately detects the three-variables/two-values wipe-out. A cheaper but still very effective rule is the pigeonhole or Hall-interval check: if any set of m variables in an Alldiff collectively has fewer than m values available, fail; if their union is exactly m values, those values can be removed from all other variables in the constraint. Similar dedicated propagators exist for Sum, Cumulative, Element, Regular and many others. The general principle is that semantic knowledge of a constraint buys more pruning per unit of time than any syntactic increase in the generic consistency level — a far better trade than climbing the k-consistency ladder.

An arc (X, Y) is consistent when every value left in X's domain has at least one compatible partner value in Y's domain; values with no partner can be deleted immediately because they cannot appear in any solution. The REVISE subroutine performs exactly this deletion for a single arc, and AC-3 repeats REVISE over a queue of arcs, re-adding neighbouring arcs whenever a domain shrinks, until the queue empties or some domain becomes empty.

Integrating Propagation with Search and Heuristics

▶

Backtracking search on its own is a blunt instrument: it assigns a value, checks whether any constraint is already violated, and only discovers deeper trouble after many more assignments. Constraint propagation sharpens that instrument by deducing, before any further guessing takes place, which values can no longer appear in a solution. The real power of a constraint solver, however, comes from the integration of the two — inference running inside every node of the search tree, with ordering heuristics that read the propagated domains to decide what to try next, and intelligent backtracking that uses the reasons for failure to avoid repeating it. This topic develops that integration in detail: how Maintaining Arc Consistency (MAC) works inside backtracking, how variable and value ordering heuristics exploit the information propagation produces, how conflict-directed backjumping and no-good learning cut away unproductive regions of the tree, how to reason about the cost/benefit balance of all this machinery, and finally how to assemble the pieces into a single configurable solver that can be measured.

Throughout, the running example is the familiar binary CSP of map colouring. Take the Australian states and territories: WA, NT, SA, Q, NSW, V and T, with the constraint that any two regions sharing a border must receive different colours from the domain {red, green, blue}. SA is adjacent to WA, NT, Q, NSW and V; T is adjacent to nothing. This tiny problem is enough to expose every mechanism below, and where a sharper illustration is needed, larger families such as n-queens, Sudoku and random binary CSPs are used.

Maintaining Arc Consistency (MAC) during search. MAC is simply this rule: after every assignment, re-establish arc consistency over the whole remaining problem before descending to the next variable. Concretely, when the solver assigns WA = red, it first reduces D(WA) to the singleton {red}. That singleton is not a cosmetic change — it is the trigger for propagation. Every arc pointing into WA from an unassigned neighbour is pushed onto the propagation queue, and the standard AC-3 REVISE loop runs from there. Revising (NT, WA) removes red from D(NT); revising (SA, WA) removes red from D(SA). Because those domains changed, arcs into NT and SA from their other neighbours — (Q, NT), (Q, SA), (NSW, SA), (V, SA), (NT, SA), (SA, NT) — are enqueued in turn. This cascade is the essential difference from forward checking.

Forward checking only ever revises arcs of the form (unassigned variable → just-assigned variable). It performs one layer of filtering and stops. MAC continues through unassigned-to-unassigned arcs, so a contradiction that lies two or three constraints away from the current assignment is detected now rather than after two or three more wrong guesses. A classic illustration: suppose the solver has reached a state where D(NT) = {green, blue}, D(SA) = {green, blue} and D(Q) = {green, blue}. Forward checking sees nothing wrong — every domain is non-empty. MAC also sees nothing wrong here, because arc consistency is a local, pairwise property and these three mutually adjacent variables are pairwise consistent (this is exactly the standard counter-example showing arc consistency is weaker than global consistency). But now assign NSW = green. Forward checking strikes green from D(SA) and D(V), leaving D(SA) = {blue}, and halts. MAC goes further: the singleton {blue} in SA triggers revision of (NT, SA) and (Q, SA), removing blue from both and leaving D(NT) = {green} and D(Q) = {green}; then arc (Q, NT) is revised, green is removed from D(Q), and D(Q) becomes empty. The branch is refuted immediately, where forward checking would have wandered on and only failed after assigning NT and then Q.

That is the second defining property of MAC inside search: an empty domain is an immediate, unconditional failure. There is no need to continue, because every value for some variable has been shown inconsistent with the current partial assignment. The solver undoes its prunings, tries the next value, and if the values run out it returns failure to its caller. Note also what MAC does not guarantee: a state in which every domain is non-empty and arc consistent may still have no solution (the three-variable, two-colour example above). Arc consistency is a necessary, not sufficient, condition, so search is still required.

function MAC-BACKTRACK(assignment, csp):
    if assignment is complete: return assignment
    X <- SELECT-UNASSIGNED-VARIABLE(csp)          # e.g. MRV + degree tie-break
    for each v in ORDER-DOMAIN-VALUES(X, csp):    # e.g. LCV
        if v is consistent with assignment:
            mark <- trail.mark()                  # remember current trail position
            assign X = v  and  prune D(X) to {v}
            queue <- { (Y, X) : Y is an unassigned neighbour of X }
            if AC-3(csp, queue) != FAILURE:       # wipe-out detected?
                result <- MAC-BACKTRACK(assignment + {X=v}, csp)
                if result != FAILURE: return result
            trail.undo_to(mark)                   # restore all domains exactly
            unassign X
    return FAILURE

The trail deserves emphasis because it is where naive implementations go wrong. Propagation may remove dozens of values scattered across many domains, and the solver must be able to restore the state exactly as it was before the assignment. Copying every domain at every node is correct but wasteful in both time and memory. The standard technique is a trail: a stack of records such as (variable, value, level), one per removal. Before an assignment the solver notes the current top-of-stack as a mark; on backtracking it pops entries back to that mark, re-inserting each value into its domain. Undo is then O(number of removals since the mark) and requires no copying. Two refinements are common: timestamping, so a value is only trailed the first time it is removed at a given level, and sparse-set or bitset domain representations, in which restoring a domain is a single size-pointer reset. Getting this wrong produces the most insidious class of solver bug — a search that silently loses values and reports "no solution" on satisfiable instances, or retains stale prunings and reports solutions that violate constraints.

MAC is the default inference level in essentially all modern constraint solvers (Gecode, Choco, OR-Tools CP-SAT's presolve-and-propagate loop, MiniZinc backends) and has close analogues in SAT solving, where unit propagation plays the same role: assign a literal, propagate the consequences through the clause database, detect a conflict as early as possible. The reason is empirical and consistent across domains — the extra filtering almost always costs less than the subtrees it eliminates, provided propagation is implemented incrementally.

Variable ordering: minimum remaining values and degree. The order in which variables are assigned changes the size of the search tree by orders of magnitude, even though it does not change the set of solutions. The dominant heuristic is minimum remaining values (MRV), also called "most constrained variable" or dom: choose the unassigned variable whose current domain is smallest. The justification is the fail-first principle. If a variable has only one legal value left, assigning it is forced and risk-free; if it has two, the branching factor is two rather than three, and if it has zero, the solver discovers failure now instead of after expanding a subtree rooted at some other variable. Fail-first is counter-intuitive at first glance — we are deliberately steering toward the hardest variable — but the arithmetic is clear: a dead end found at depth 2 prunes everything below depth 2, whereas the same dead end found at depth 6 has already cost four levels of fruitless branching.

In the Australia example, suppose SA = blue has just been assigned and propagated, giving D(WA) = D(NT) = D(Q) = D(NSW) = D(V) = {red, green} and D(T) = {red, green, blue}. MRV will never select T, because its domain is largest; T is a disconnected variable whose assignment is irrelevant to everyone else, and postponing it is exactly right. Now assign WA = red; propagation gives D(NT) = {green}. MRV immediately selects NT, assigns the forced value green, propagates to give D(Q) = {red}, selects Q, and so on. On this instance MRV plus MAC solves the map with no backtracking whatsoever — the search degenerates into a chain of forced propagations.

The crucial caveat is that MRV is only as good as the domain information available to it. Under pure chronological backtracking with no inference, every unassigned domain still holds all its original values, so "fewest remaining values" is meaningless and MRV degenerates into an arbitrary tie-break. MRV therefore pairs naturally — and only usefully — with forward checking or MAC, which keep domain sizes current. The stronger the propagation, the better the information MRV consumes; this is one of the quiet reasons MAC+MRV outperforms FC+MRV by more than the pruning difference alone would suggest.

Ties under MRV are frequent, especially at the root where all domains have equal size. The degree heuristic breaks them: among the tied variables, select the one that participates in the most constraints with unassigned variables. The reasoning is complementary to MRV — assigning a high-degree variable propagates to many neighbours at once, shrinking several domains simultaneously and reducing the branching factor of the rest of the tree. In Australia, every domain starts at size 3, so MRV is silent; the degree heuristic breaks the tie in favour of SA, which has five unassigned neighbours while WA, NT, Q, NSW and V have two or three and T has none. Choosing SA first is demonstrably the best opening move, because colouring the hub of the graph constrains the entire periphery. Degree is also used as a standalone static ordering (sort variables once by degree) when propagation is weak or when a cheap deterministic ordering is wanted, and a popular refinement is the ratio heuristic dom/deg — minimise domain size divided by degree — which blends the two criteria into a single score rather than using one merely as a tie-break.

Value ordering: least constraining value. Variable ordering and value ordering answer different questions and therefore follow opposite principles. Variable ordering asks "which subtree should I expand?" and the answer is fail-first, because every child of the chosen variable must eventually be examined if the subtree contains no solution. Value ordering asks "which child should I try first?" and here the answer is succeed-first, because on a satisfiable instance the solver only has to find one solution; trying a promising value first may mean the remaining values are never examined at all.

The least constraining value (LCV) heuristic implements succeed-first: among the values still in D(X), prefer the one that rules out the fewest values in the domains of X's unassigned neighbours — in other words, the value that leaves the rest of the problem with the most freedom. It is computed by tentatively assigning each candidate value, running propagation (at minimum, forward checking; at most, full MAC), summing the surviving domain sizes over neighbouring variables, undoing the trial, and then sorting values by that count in descending order of remaining freedom. A value whose trial causes a domain wipe-out is removed from consideration altogether, which makes LCV a mild form of singleton consistency as a side effect.

A concrete illustration: suppose WA, NT and Q are already coloured, and the solver must choose a value for SA with D(SA) = {green, blue}, where the unassigned neighbours are NSW with D(NSW) = {red, green, blue} and V with D(V) = {green, blue}. Trial SA = green removes green from both, leaving sizes 2 + 1 = 3. Trial SA = blue removes blue from both, leaving 2 + 1 = 3. Here LCV is indifferent, which is typical of small uniform problems. Change V's domain to {green} and the picture sharpens: SA = green wipes out V entirely (score 0, value rejected), while SA = blue leaves 2 + 1 = 3. LCV correctly directs the search to blue and avoids an immediate backtrack.

function ORDER-DOMAIN-VALUES-LCV(X, csp):
    scored <- []
    for each v in D(X):
        mark <- trail.mark()
        tentatively set D(X) = {v}; run propagation
        if no domain is empty:
            score <- sum of |D(Y)| over unassigned neighbours Y of X
            scored.append((score, v))
        trail.undo_to(mark)
    return values from scored sorted by score descending

The cost is the obvious drawback: LCV performs |D(X)| extra propagation runs at every node, so the per-node cost may rise by a factor equal to the domain size. On easy or loosely constrained instances, where backtracking is rare anyway, this is pure overhead and LCV can make the solver measurably slower in wall-clock terms while barely changing the node count. On hard instances near the phase transition, where a single wrong value choice near the root can cost an exponentially large subtree, the investment pays for itself many times over. The standard, well-tested configuration is therefore MRV (with degree tie-breaking) for variables and LCV for values, applied on top of MAC — and when counting solutions or proving unsatisfiability, where the entire tree must be explored regardless, value ordering is switched off because it can save nothing.

Backjumping and conflict-directed strategies. Chronological backtracking always returns to the immediately preceding variable, even when that variable had nothing to do with the failure. Consider an ordering WA, NSW, T, NT, Q, SA in the Australia problem with a two-colour domain {red, blue}. Suppose WA and NSW are assigned, T is assigned (irrelevantly), and the search then fails deep inside the NT/Q/SA region. Chronological backtracking will dutifully retry every value of T, re-failing identically each time, because T's assignment is causally unrelated to the conflict. The wasted effort multiplies with the size of T's domain and the number of such irrelevant variables between the conflict and its true cause — a pathology known as thrashing.

Backjumping fixes this by maintaining a conflict set for each variable: the set of earlier assigned variables whose values eliminated at least one value from this variable's domain. When a variable X exhausts its domain, the solver does not return to the previous variable in the ordering; it jumps directly to the deepest (most recently assigned) variable in conf(X), because every intermediate assignment is provably irrelevant to this particular failure and no re-trial of those variables can repair it. In the example above, if the conflict set for the failing variable is {WA, NSW}, the search jumps straight back to NSW, bypassing T entirely.

Conflict-directed backjumping (CBJ) takes the further step of propagating conflict sets upward. When the solver backjumps from X to Y, it absorbs X's conflict set into Y's: conf(Y) <- conf(Y) ∪ conf(X) \ {Y}. Consequently, if Y subsequently exhausts its own domain, the jump target is computed from the accumulated reasons for failure of the whole subtree below Y, not merely Y's own local conflicts. This lets entire regions of the tree be bypassed in a single leap and is what makes CBJ substantially stronger than plain backjumping.

No-good learning generalises the idea from "where to jump" to "what to remember". A no-good is a partial assignment, such as {WA = red, NSW = red}, that has been proved to extend to no solution. Recording it means that if the search ever reconstructs that combination along a different path — perhaps with a different ordering of intermediate variables — it is rejected immediately without re-derivation. This is precisely the mechanism that, in SAT solving, appears as conflict-driven clause learning (CDCL): the conflict analysis walks the implication graph back to a cut, derives a learned clause, and backjumps to the assertion level implied by that clause. The practical issues are the same in both worlds — the number of no-goods can grow explosively, so solvers bound the size of recorded no-goods, periodically delete low-activity ones, and index them for fast lookup.

An important practical observation is that the benefits of MAC and backjumping overlap. Simple backjumping jumps back to the deepest variable that pruned a value from the dead variable's domain — but forward checking already computes exactly that information, and MAC already refutes many of those branches before they are ever entered. Russell and Norvig make this point explicitly: every branch pruned by simple backjumping is also pruned by forward checking, so adding plain backjumping to a forward-checking or MAC solver buys very little. Conflict-directed backjumping and no-good learning, by contrast, do add genuine power even on top of strong propagation, because they reason about the accumulated causes of failure in whole subtrees rather than single-level domain wipe-outs. The engineering judgement, therefore, is: adopt MAC first; add CBJ or learning only if profiling shows thrashing on structured instances.

Trade-offs between inference cost and search savings. Every technique above shifts work from the search tree into the node. The total runtime is roughly nodes explored × cost per node, and the design question is always whether the reduction in the first factor outweighs the increase in the second. The answer depends systematically on the structure of the instance.

  • Loosely constrained problems with large domains. Here solutions are plentiful and dead ends rare. Forward checking is cheap — one pass over the neighbours of the assigned variable — and is often enough, because the extra arcs MAC revises almost never fail. MAC's cascade in this regime does a great deal of work and removes very few values.
  • Tightly constrained problems near the phase transition. Here dead ends are everywhere and detecting them one or two levels earlier compounds exponentially. MAC routinely dominates, sometimes by orders of magnitude in node count, and the extra per-node work is trivial by comparison. Sudoku is the canonical teaching example: arc consistency alone (with the appropriate all-different propagator) solves most newspaper puzzles with little or no search.
  • Higher levels of consistency. Path consistency (3-consistency) and k-consistency for k > 2 prune strictly more than arc consistency, but at a cost that rises sharply: enforcing path consistency on a binary CSP is O(n3d3) and, worse, it may add new binary constraints between previously unconstrained pairs, destroying the sparse structure that made propagation fast in the first place. In practice it is almost never worth the overhead inside search; the main exception is specialised domains such as temporal reasoning, where path consistency over interval algebras is both cheap and decisive. Singleton arc consistency (SAC) and restricted forms of it sit in between and are occasionally used as a preprocessing step rather than at every node.
  • Specialised global propagators. Rather than climbing the generic consistency ladder, modern solvers get extra pruning from global constraints with dedicated algorithms — for example alldifferent propagated to generalised arc consistency via Régin's matching algorithm. This delivers far more pruning than pairwise arc consistency on the decomposed ≠ constraints, at a cost that is polynomial and tightly engineered. The lesson is that stronger inference pays when it exploits structure, not when it is applied blindly and uniformly.

Two implementation properties govern whether any of this is affordable. The first is incremental propagation: after an assignment, only the arcs affected by a changed domain should be re-examined, never the whole constraint graph. The AC-3 queue already captures this idea, and finer-grained algorithms (AC-4, AC-6, AC-2001) maintain support counters or last-support pointers so that a revision costs time proportional to the values actually removed. Event-driven propagator scheduling in industrial solvers goes further still, waking a constraint only on the specific events it subscribes to (a bound change, a value removal, a variable becoming fixed). The second is cheap state restoration: the trail discussed earlier, with timestamping and sparse-set domains, so that undoing a node's work costs no more than doing it. A solver with strong propagation and O(n·d) copy-based undo at every node can easily be slower than a plain forward-checking solver with O(1)-per-removal trailing.

Because these interactions are instance-dependent and frequently counter-intuitive, empirical benchmarking is the only reliable selection method. The discipline that makes such benchmarking trustworthy is worth stating explicitly: use a representative suite rather than a single instance; include both satisfiable and unsatisfiable cases, since value ordering helps only on the former; generate random instances across a range of constraint tightness so the phase transition is covered; run multiple seeds and report medians or means with spread, because runtimes on hard instances are heavy-tailed; impose a timeout and report the number of timeouts separately rather than silently excluding them; and always report at least one machine-independent metric (nodes expanded, constraint checks, propagation calls) alongside wall-clock time, so that a configuration that explores fewer nodes but runs slower can be recognised as such rather than confused with a genuine algorithmic loss.

Assembling a complete CSP solver. All of the above fits into a surprisingly compact architecture. The core recursive loop is: check for completeness; select an unassigned variable with the configured variable-ordering heuristic; order its values with the configured value-ordering heuristic; for each value, mark the trail, assign, propagate at the configured strength, recurse if propagation did not fail, and on failure undo to the mark and continue; if all values are exhausted, return failure (or backjump, if conflict analysis is enabled).

class Solver:
    def __init__(self, csp, var_order="mrv_deg", val_order="lcv",
                 inference="mac", backjump=False):
        self.csp = csp
        self.select_var  = VAR_HEURISTICS[var_order]
        self.order_vals  = VAL_HEURISTICS[val_order]
        self.propagate   = INFERENCE[inference]      # none | fc | mac
        self.backjump    = backjump
        self.trail       = Trail()
        self.stats       = Counters(nodes=0, checks=0, props=0,
                                    backtracks=0, max_depth=0)

    def search(self, assignment, depth=0):
        self.stats.nodes += 1
        self.stats.max_depth = max(self.stats.max_depth, depth)
        if len(assignment) == len(self.csp.variables):
            return assignment
        X = self.select_var(self.csp, assignment)
        for v in self.order_vals(self.csp, X, assignment):
            mark = self.trail.mark()
            assignment[X] = v
            self.csp.assign(X, v, self.trail)         # D(X) <- {v}, trailed
            if self.propagate(self.csp, X, self.trail, self.stats):
                result = self.search(assignment, depth + 1)
                if result is not None:
                    return result
            self.trail.undo_to(mark)                  # exact restoration
            del assignment[X]
            self.stats.backtracks += 1
        return None

Three design commitments make this skeleton useful for study rather than merely functional. The first is pluggability. Variable ordering, value ordering and inference strength are injected as strategy objects or function references, selected by configuration flags. This is what makes controlled experiments possible: hold the instance, the seed and the machine fixed, vary exactly one component, and attribute the difference to it. Hard-coding MAC and MRV into the recursion makes the solver faster to write and impossible to evaluate.

The second is exact state restoration. The invariant to maintain and, ideally, to assert in debug builds is: after undo_to(mark), every domain is bit-for-bit identical to its state immediately before the corresponding assignment. Every removal performed by assignment or propagation since the mark must be recorded on the trail, and nothing else may be undone. The common failure modes are forgetting to trail removals made during the cascading phase of MAC, trailing a value twice and re-inserting a duplicate into a list-based domain, and undoing past the mark because marks were stored in the wrong order. A cheap and highly effective regression test is to run the solver twice — once with inference enabled and once without — and verify that both return the same solution count on small instances.

The third is instrumentation. The counters that matter are: nodes visited (calls to search, i.e. search-tree size), constraint checks (individual consistency tests, the classic machine-independent effort measure), propagation calls and arc revisions (the per-node inference cost), backtracks or backjumps, maximum depth reached, values pruned, and wall-clock time. These are complementary rather than redundant, and the interesting results live in the gaps between them. A MAC configuration might visit 95% fewer nodes than forward checking while performing five times as many constraint checks per node; whether that is a win is decided by runtime, but why it is a win or a loss is only visible in the other counters. Similarly, LCV will typically reduce nodes modestly while increasing propagation calls sharply — a pattern immediately recognisable in the instrumentation and easy to misdiagnose from runtime alone.

Finally, a complete toolkit includes a complementary local-search fallback. Systematic backtracking with MAC is complete — it will find a solution or prove none exists — but its memory of the tree and its commitment to a fixed variable ordering make it ill-suited to very large, loosely constrained instances. Min-conflicts takes the opposite approach: start from a complete but possibly inconsistent assignment (often produced by a greedy constructive pass), repeatedly pick a variable currently involved in a conflict, and reassign it to the value that minimises the number of violated constraints, with random sideways moves or restarts to escape plateaux. On n-queens, min-conflicts solves instances with a million queens in seconds, essentially independently of n, whereas even a well-tuned MAC solver struggles far earlier. The trade-off is sharp and should be stated honestly: min-conflicts is incomplete, cannot prove unsatisfiability, and degrades badly on tightly constrained instances where conflicts cannot be repaired locally — exactly the regime in which MAC excels. A pragmatic solver therefore exposes both engines behind the same interface, uses the systematic engine by default, and switches to local search (or runs the two in parallel portfolios, as competition-winning solvers do) when the instance is large, loosely constrained and known or believed to be satisfiable.

Exploiting Problem Structure

Exploiting Problem Structure

▶

Generic backtracking search treats every constraint satisfaction problem as a flat list of variables to be assigned one after another, and in the worst case it pays the full exponential price of O(d^n) for n variables each with d values. Yet real CSPs are rarely structureless. The constraint graph — the graph whose nodes are the variables and whose edges join variables that share a constraint — often contains disconnected pieces, long thin chains, a few "hub" variables that create all the cycles, or clusters of tightly coupled variables loosely joined to each other. Each of these topological features can be converted into an algorithmic saving, and the savings are frequently dramatic: from exponential in n to exponential only in some small structural parameter, or even to linear time. This topic surveys the main structural techniques — component decomposition, tree-structured solving, cutset conditioning, and tree decomposition — unifies them through the notion of tree width, and then considers a complementary kind of structure that lives in the values rather than the graph: symmetry.

The common thread is a shift of perspective. Instead of asking "which variable should I assign next?", structural methods ask "what shape is this problem, and does that shape admit a cheaper algorithm than blind search?" Because the analysis is performed on the constraint graph rather than on the search tree, it can usually be carried out before search begins, as a preprocessing step whose cost is polynomial and often negligible.

Independent subproblems and connected components

The simplest and cheapest structural win is the observation that a constraint graph need not be connected. If no constraint ever links a variable in set A to a variable in set B, then the choices made in A cannot possibly invalidate the choices made in B. The two sets are independent subproblems and may be solved separately.

The canonical illustration is the map-colouring CSP for Australia. The mainland states and territories — Western Australia (WA), Northern Territory (NT), South Australia (SA), Queensland (Q), New South Wales (NSW), Victoria (V) — form one connected block of "must differ" constraints, while Tasmania (T) is an island and shares no border with anything. The constraint graph therefore has two connected components: one of six variables and one of a single variable. A naive search over all seven variables with three colours explores up to 3^7 = 2187 complete assignments; solving the components separately costs at most 3^6 + 3^1 = 729 + 3 = 732. The saving is modest here only because the split is so lopsided; when a problem breaks into several components of comparable size the effect is multiplicative in reverse — a product of exponentials becomes a sum of exponentials.

Finding the components requires nothing more sophisticated than a graph traversal. A depth-first search (or breadth-first search, or a union–find structure) started from an unvisited variable will reach exactly the variables in that variable's component; repeating until no unvisited variable remains enumerates all components in O(n + e) time, where e is the number of constraint edges.

function CONNECTED-COMPONENTS(graph G with vertices V, edges E):
    visited <- empty set
    components <- empty list
    for each vertex v in V:
        if v not in visited:
            comp <- empty list
            stack <- [v]
            while stack not empty:
                u <- stack.pop()
                if u not in visited:
                    visited.add(u)
                    comp.append(u)
                    for each neighbour w of u in G:
                        if w not in visited: stack.push(w)
            components.append(comp)
    return components

The complexity argument generalises cleanly. Suppose a CSP with n variables decomposes into components each containing at most c variables. There are at most n/c such components, and solving one costs at most O(d^c), so the total worst-case cost is O((n/c) · d^c) — linear in n and exponential only in the size of the largest component. With n = 80, d = 2 and c = 20, the undecomposed figure 2^80 (roughly 1024) collapses to 4 · 2^20, about four million: a problem that would outlive the universe becomes a fraction of a second's work.

Once each component has been solved, the overall solution is simply the union of the component assignments. Because no constraint crosses components, concatenating locally consistent assignments cannot create a violation. Conversely, if any component is unsatisfiable, the whole CSP is unsatisfiable, and the search can halt immediately without touching the other components — a useful early-failure property.

Two practical remarks. First, decomposition should be applied before any expensive inference or search, because its cost is trivial and its payoff can be enormous. Second, components can appear during search as well as before it: once a variable is assigned and its constraints are propagated, removing that variable from the graph may split the remainder in two. Solvers that re-run component detection at each node (sometimes called dynamic decomposition or "and/or search") exploit this, at the cost of some per-node overhead.

Tree-structured CSPs solved in linear time

The second structural class is the tree: a connected constraint graph with no cycles, so that any two variables are joined by exactly one path. Tree-structured CSPs are remarkable because they are solvable in time linear in the number of variables — specifically O(n · d²) — with no backtracking whatsoever. This is one of the cleanest tractable islands in an otherwise NP-complete landscape.

The algorithm has three stages.

  • Root and order. Pick any variable as the root and perform a traversal outwards, numbering the variables X1, X2, …, Xn so that every variable appears after its unique parent in the tree. This is a topological ordering of the tree viewed as a directed graph with edges pointing away from the root. Any DFS or BFS pre-order from the root produces such an ordering.
  • Backward pass (directional arc consistency). For j from n down to 2, make the arc (Parent(Xj) → Xj) arc consistent: delete from the domain of Parent(Xj) every value that has no compatible partner remaining in the domain of Xj. Because the ordering guarantees that children are processed before parents, each arc is revised exactly once and the result is directional arc consistency with respect to the chosen order.
  • Forward pass (assignment). For j from 1 to n, choose for Xj any remaining value consistent with the already-assigned value of its parent (the root is free to take any surviving value).
function TREE-CSP-SOLVER(csp):
    n <- number of variables
    root <- any variable
    X <- TOPOLOGICAL-SORT(csp.graph, root)      # parents before children
    for j = n down to 2:                        # backward pass
        REVISE(csp, Parent(X[j]), X[j])
        if domain of Parent(X[j]) is empty: return failure
    assignment <- {}
    for j = 1 to n:                             # forward pass
        assignment[X[j]] <- any value in D(X[j]) consistent with assignment[Parent(X[j])]
        if no such value exists: return failure  # cannot occur after a clean backward pass
    return assignment

The key correctness claim is that the forward pass never fails. After the backward pass, every value surviving in a parent's domain has, by construction, at least one compatible value in each child's domain. So when the algorithm reaches a child, a legal value is guaranteed to exist. Each of the n − 1 arcs is revised once, and a single revision compares at most d × d value pairs, giving the O(n · d²) bound. There is no choice point that can ever need to be undone, hence no backtracking.

If a domain becomes empty during the backward pass, the tree CSP is unsatisfiable, and this is detected without search. The emptiness is a proof, not a heuristic failure: a parent value is deleted only when it is incompatible with every remaining value of a child, and by induction those remaining child values are exactly the ones extendable to the whole subtree.

A worked example makes the mechanics concrete. Consider six variables arranged as a tree with root A, children B and C, with B having children D and E, and C having child F. Let every domain be {r, g, b} and every edge carry a "not equal" constraint, except that D is restricted to {r} and F to {r, g}.

Step (j from n down to 2)Arc revisedEffect on parent domain
6C → FC loses nothing: each of r, g, b differs from some value in {r, g}
5B → EB unchanged: E = {r, g, b}
4B → DD = {r}, so B must differ from r: B becomes {g, b}

The forward pass then picks, say, A = r; B must differ from r, so B = g; C must differ from r, so C = g; D = r (differs from B = g); E takes r or b; F takes r (differs from C = g). Every choice succeeded on the first attempt.

Trees are not an exotic curiosity. Many scheduling chains, Markov-chain-like temporal models, and hierarchical configuration problems are trees or near-trees, and the tree algorithm is the engine inside the two more general methods that follow.

Cutset conditioning

Most interesting constraint graphs contain cycles, but often only because of a handful of highly connected variables. Cutset conditioning exploits this: find a small set of variables whose deletion leaves a tree, fix their values by enumeration, and solve what remains in linear time.

Formally, a cycle cutset is a subset S of the variables such that the subgraph induced on the remaining variables V \ S is acyclic. The algorithm is:

  • Find a cycle cutset S of size c.
  • For each assignment to S that is consistent with the constraints internal to S:
    • Remove from the domain of every remaining variable all values inconsistent with the cutset assignment (this is just propagating the constraints that cross between S and the rest).
    • Run the linear-time tree solver on the residual tree CSP.
    • If it succeeds, return the cutset assignment combined with the tree solution.
  • If no cutset assignment yields a tree solution, report failure.

Returning to Australia, the mainland graph contains cycles (WA–NT–SA, NT–SA–Q, SA–Q–NSW, SA–NSW–V), but every one of them passes through South Australia. Deleting SA leaves the chain WA – NT – Q – NSW – V, which is a tree (indeed a path). So S = {SA} is a cycle cutset of size 1. Conditioning on SA = red strips red from the domains of WA, NT, Q, NSW and V, leaving each with {green, blue}; the path is then two-coloured in linear time by alternating the colours. Three cutset values × linear tree solve is a tiny amount of work compared with searching all six variables.

function CUTSET-CONDITIONING(csp):
    S <- FIND-CYCLE-CUTSET(csp.graph)
    for each assignment a to S consistent with constraints inside S:
        csp' <- copy of csp restricted to V \ S
        for each variable Y in V \ S:
            D'(Y) <- { v in D(Y) : v consistent with a on every constraint joining Y to S }
            if D'(Y) empty: continue with next a
        result <- TREE-CSP-SOLVER(csp')
        if result != failure: return a union result
    return failure

The cost analysis: there are at most d^c assignments to the cutset, and each triggers a tree solve over the n − c remaining variables costing O((n − c) · d²). The total is O(d^c · (n − c) · d²). The exponential has been confined to the cutset: the method is a clear winner when c is small and degrades to ordinary exhaustive search when c approaches n. One caveat matters in practice: finding a minimum cycle cutset is itself NP-hard (it is the feedback vertex set problem). Solvers therefore use approximations and heuristics — repeatedly remove the highest-degree vertex, or use a known 2-approximation algorithm — and accept a cutset that is small rather than smallest. Because the cost is exponential in c, spending a little extra preprocessing time to shave one or two variables off the cutset is usually worthwhile.

Tree decomposition

Cutset conditioning turns a graph into a tree by deleting variables. Tree decomposition takes the opposite route: it groups variables into overlapping clusters and arranges the clusters themselves into a tree, converting the original CSP into a new, tree-structured CSP whose "variables" are the clusters and whose "values" are the clusters' local solutions. Because the new problem is a tree, it can be solved with the linear-time algorithm already described.

A tree decomposition must satisfy three conditions:

  • Vertex coverage. Every variable of the original CSP appears in at least one cluster.
  • Edge (constraint) coverage. For every constraint, there is at least one cluster containing all the variables of that constraint, so the constraint can be enforced entirely inside a single cluster.
  • Connectedness (running intersection). If a variable appears in two clusters, it must also appear in every cluster on the unique path between them in the cluster tree. Equivalently, the set of clusters containing any given variable forms a connected subtree.

The connectedness condition is the one that does the real work: it guarantees that a variable cannot be assigned one value in one part of the tree and a different value in a distant part without the disagreement being visible somewhere along the connecting path. It is what makes local consistency between neighbouring clusters sufficient for global consistency.

For the Australian mainland, a valid decomposition uses five clusters arranged as a path:

ClusterVariablesShares with next cluster
C1WA, NT, SANT, SA
C2NT, Q, SAQ, SA
C3Q, NSW, SANSW, SA
C4NSW, V, SAV (and SA)
C5T— (separate component)

Check the conditions: every state appears somewhere; each border constraint (WA–NT, WA–SA, NT–SA, NT–Q, SA–Q, SA–NSW, SA–V, Q–NSW, NSW–V) sits wholly inside some cluster; and SA, which appears in C1 through C4, appears in every cluster along that path, as does each other repeated variable.

Solving proceeds in two phases. First, solve each cluster independently as a small CSP, enumerating all of its locally consistent assignments — these become the "values" of the meta-variable representing that cluster. C1, for example, with three colours and all-different constraints, has 3 × 2 × 1 = 6 solutions. Second, enforce consistency between adjacent clusters on their shared variables: a solution of C1 and a solution of C2 are compatible only if they agree on NT and SA. Because the cluster graph is a tree, running the directional arc consistency pass over the cluster tree and then assigning forwards yields a global solution with no backtracking, exactly as before. Projecting the chosen cluster solutions back onto the original variables gives the answer, and the connectedness condition ensures the projections agree wherever clusters overlap.

The complexity is O(n · d^(w+1)), where w is the tree width of the decomposition: the size of the largest cluster minus one. The d^(w+1) factor is the cost of enumerating the local solutions of a cluster containing w + 1 variables, and the n factor covers the linear sweep over the cluster tree (strictly, the consistency step between adjacent clusters costs O(d^(w+1)) per edge as well, which does not change the shape of the bound). In the Australian example the largest cluster has three variables, so w = 2 and the cost is proportional to n · d³.

As with cutsets, the optimisation problem is hard: computing a decomposition of minimum width is NP-hard, though good heuristics exist (min-fill and min-degree elimination orderings are the standard workhorses, and exact algorithms are practical for graphs of a few hundred vertices). Note also that a trivial decomposition always exists — one cluster containing every variable — with width n − 1 and cost d^n, i.e. no better than brute force. The art is in finding a decomposition whose width is genuinely small.

Tree width and the limits of structural methods

Tree width is the single parameter that ties all of these methods together. The tree width of a graph is the minimum width over all of its tree decompositions. It measures, intuitively, how far the graph is from being a tree.

  • A graph is a tree (acyclic and connected) precisely when its tree width is 1: each cluster holds one edge, i.e. two variables, so w + 1 = 2 and w = 1. (A graph with no edges at all has tree width 0.)
  • A single cycle of any length has tree width 2. The Australian mainland map also has tree width 2.
  • An m × m grid has tree width m — so the constraint graph of a Sudoku-like or image-labelling problem grows steadily harder with size.
  • A complete graph on k vertices has tree width k − 1, the worst possible.

The headline theoretical result is that a CSP whose constraint graph has tree width bounded by a constant w can be solved in polynomial time — specifically O(n · d^(w+1)), which is polynomial in n and d for fixed w. This is the formal sense in which "nice structure" buys tractability, and it subsumes the earlier cases: component decomposition bounds the problem by the width of its largest component, the tree algorithm is the w = 1 case, and cutset conditioning on a cutset of size c never does worse than a decomposition of width c + 1. It is worth stressing that n appears only linearly: a problem with ten thousand variables and tree width 4 is routine, while a problem with forty variables and tree width 35 may be hopeless.

The limits are equally important. The bound is exponential in the width, so the method collapses as soon as the graph becomes densely connected. Randomly generated 3-SAT instances at the satisfiability threshold are the standard cautionary example: with clauses drawn uniformly at random over all variables, the constraint graph is an expander-like object whose tree width grows as a constant fraction of n. For a 500-variable random instance with width in the hundreds, d^(w+1) is astronomically larger than d^n-style brute force is for small problems — the decomposition machinery simply has nowhere to grip. The same is true of many cryptographic, verification and hard combinatorial-design instances.

The practical protocol that follows from this is a cascade:

Two further qualifications are worth noting. First, structural bounds are worst-case bounds that ignore the tightness of the constraints; a high-width problem with very restrictive constraints may still be trivial for a propagating backtracker, because inference prunes the search long before the structural bound becomes relevant. Second, structure can be hidden: a problem may look dense in its original encoding yet decompose nicely after preprocessing, variable elimination, or re-encoding, so it is worth measuring the width of the model you actually intend to solve rather than of the problem as first stated.

Value-level structure and symmetry breaking

All of the techniques above read structure off the constraint graph. A quite different and complementary source of structure lies in the values: many CSPs contain large families of solutions that are, for all practical purposes, the same solution relabelled. Exploring every member of such a family is pure waste, and in unsatisfiable subproblems it is worse — the solver re-proves the same contradiction once for every relabelling.

In map colouring with three interchangeable colours, every solution has five siblings obtained by permuting the colour names; the symmetry group is the symmetric group S3 of size 3! = 6. In the n-queens problem the board's eight geometric symmetries (rotations and reflections) act on solutions. In a bin-packing or scheduling model with identical machines, permuting the machine identities maps solutions to solutions. These are symmetries: bijections of the assignment space that preserve satisfaction.

The standard remedy is to add symmetry-breaking constraints that impose an arbitrary but fixed ordering, keeping one canonical representative from each equivalence class and ruling out the rest. Typical examples:

  • Map colouring: require that the first region (say WA) takes the lowest-indexed colour, WA = colour1. This immediately removes a factor of 3 for three colours. A fuller "precede" constraint — colour k may only be used if colour k − 1 has already been used by an earlier-indexed region — removes the whole factor of 3! = 6.
  • Identical machines: require that the jobs assigned to machine 1 include the lowest-numbered job overall, or impose lexicographic ordering between the machines' job vectors.
  • Matrix models: when rows and/or columns of a decision matrix are interchangeable, impose lexicographic ordering on the rows and on the columns (row1 ≤_lex row2 ≤_lex …).
# Map colouring, colours indexed 0,1,2 ; regions indexed in a fixed order
# Value-precedence symmetry breaking:
#   region R may take colour k > 0 only if some earlier region took colour k-1
for k = 1 .. (d-1):
    for i = 0 .. (n-1):
        constraint:  (X[i] = k)  implies  (exists j < i with X[j] = k-1)

# Simplest partial version: fix the first region
constraint: X[0] = 0

The payoff is a reduction of the search space by (at most) a factor equal to the size of the symmetry group. With S3 on colours that is a factor of 6; with 10 interchangeable machines the group has 10! ≈ 3.6 × 10⁶ elements, and breaking it fully can turn an intractable model into an easy one. The gain is largest precisely where it is most needed: in exhaustive search for all solutions, and in proofs of unsatisfiability.

A closely related idea is value interchangeability. Two values of a variable are interchangeable if swapping them in any solution yields a solution; more locally, they are neighbourhood interchangeable if they are compatible with exactly the same values of every neighbouring variable. Such values can be bundled and treated as a single representative during search: the solver tries the bundle once instead of once per member, and expands it only at the end if all solutions are wanted. In a colouring problem where five colours are completely interchangeable, a variable's five-value domain collapses to a single "fresh colour" choice plus the colours already committed to elsewhere — this is the familiar idea behind dynamic symmetry breaking in graph colouring, where at each node one need only consider the colours already used plus one new one.

Symmetry breaking must be used carefully, because it adds constraints that were not in the original problem. The non-negotiable requirement is soundness: the added constraints must never eliminate all members of an equivalence class, or the solver may report "unsatisfiable" for a satisfiable problem, or miss optimal solutions in an optimisation setting. Two common pitfalls illustrate the danger:

  • Over-constraining. Fixing WA = red is sound when the three colours are genuinely interchangeable, but unsound if the model already contains a constraint such as "WA must not be red" or a preference that distinguishes colours. Any constraint that breaks the symmetry destroys the licence to assume it.
  • Incompatible combinations. Adding two separately sound symmetry-breaking schemes can be jointly unsound if they select different canonical representatives from the same class, so that no assignment satisfies both. The standard safe constructions — a single lexicographic-leader scheme, or the well-studied double-lex constraints for row/column symmetry — are designed to avoid this.

There is also a cost–benefit trade-off. Complete symmetry breaking (admitting exactly one representative per class) may require exponentially many constraints, each of which must be checked and propagated at every node. Practitioners therefore usually adopt partial symmetry breaking: a small set of cheap constraints — fix the first variable, order the first row, impose value precedence — that removes most of the redundancy for a negligible per-node cost. Dynamic alternatives such as symmetry breaking during search (SBDS) and symmetry breaking by dominance detection (SBDD) instead add nogoods on the fly as the search explores, avoiding a large static model at the price of bookkeeping.

Taken together, graph-level and value-level structure give a solver two independent levers. Decomposition, tree solving, cutset conditioning and tree decomposition shrink the shape of the search; symmetry breaking and interchangeability shrink its content. Both are preprocessing-style investments that cost little and, on well-structured problems, can convert an exponential nightmare into a routine computation — while on dense, symmetry-free instances neither helps, and the solver must fall back on inference-rich backtracking or local search.

Most CSP algorithms treat a problem as one undifferentiated pile of variables and constraints. But the constraint graph — which variables actually share constraints — often has structure we can exploit. If the graph splits into disconnected pieces, each piece can be solved separately and the costs multiply out far more cheaply than solving everything at once. If the graph is a tree, the problem can be solved in time linear in the number of variables by ordering the variables from a root and enforcing arc consistency in one backward sweep followed by one forward assignment pass.

Real problems are rarely perfect trees, so this topic introduces techniques that bring general graphs closer to tree-like form. Cutset conditioning instantiates a small set of variables whose removal leaves a tree, then solves the remaining tree for each assignment of the cutset. Local Search for CSPs

Local Search for CSPs

▶

Systematic constraint solvers such as backtracking search with forward checking or maintaining arc consistency build a solution incrementally: they start from the empty assignment, extend it one variable at a time, and retract decisions whenever a dead end is reached. Local search for constraint satisfaction problems takes the opposite stance. It begins with a complete assignment — every variable already has a value, almost certainly a bad one — and then repairs that assignment by changing one variable at a time until no constraint is violated. This family of methods is often called iterative repair or heuristic repair, and the best-known member is the min-conflicts heuristic. The shift in perspective is profound: there is no partial assignment, no search tree, no backtracking stack, and no guarantee of completeness. What is gained in exchange is an astonishing ability to scale, a natural anytime behaviour, and a near-perfect fit with dynamic, real-world problems where a slightly broken schedule needs mending rather than a brand new schedule needs inventing.

The complete-state formulation. In a partial-state (constructive) formulation, a state is an assignment to some subset of the variables, and the goal test is "all variables assigned and all constraints satisfied". In the complete-state formulation, a state is a total function from variables to values: {X1 = v1, X2 = v2, ..., Xn = vn}, with vi drawn from Di. Unary and domain constraints are therefore satisfied by construction; what may be violated are the binary (or higher-arity) constraints. A state is a candidate solution at all times, and it becomes an actual solution exactly when its conflict count reaches zero.

The neighbourhood structure defines the search space. The standard move is to pick one variable and change its value, which gives each state a neighbourhood of size Σi (|Di| - 1). For 8-queens formulated with one queen per column, that is 8 columns × 7 alternative rows = 56 neighbours. The full space of complete assignments is ∏i |Di| — 88 = 16,777,216 states for 8-queens — but local search never enumerates it; it only ever looks at the neighbours of the state it currently holds.

The objective function to be minimised is almost always the number of violated constraints, sometimes called the cost, energy, or conflict count of the state:

cost(s) = | { c in Constraints : c is violated under s } |

Goal: find s with cost(s) = 0

This turns satisfaction into optimisation. Weighted variants replace the plain count with Σ wc over violated constraints, which matters both for soft constraints (see the discussion of minimal perturbation below) and for the constraint-weighting escape technique.

Memory is constant. A backtracking solver must retain the current path from the root plus, in forward-checking or MAC variants, a trail of domain reductions to undo. Local search stores only the current assignment (n values), an auxiliary conflict data structure, and possibly a best-so-far copy. Whether the algorithm runs for 10 steps or 10 million, memory use does not grow. This is precisely why problems with millions of variables are tractable for local search and completely out of reach for systematic solvers whose trails and nogood stores would exhaust memory.

Initial states. The simplest initialisation assigns each variable a uniformly random value from its domain. A much better option for many problems is a greedy conflict-minimising construction: process the variables in some order and give each one the value that conflicts least with the variables already placed, breaking ties randomly. For n-queens this means walking column by column and placing each queen in the row that is attacked by the fewest already-placed queens. The greedy start typically leaves only a handful of conflicts even for n = 1,000,000, and min-conflicts then clears them in a small number of repairs. Note the tie-breaking must be randomised: deterministic tie-breaking produces highly structured, symmetric starting states that are often local minima.

GREEDY-INIT(csp):
  for each variable X in some (random) order:
      best ← argmin over v in D(X) of
                 conflicts(X = v, given variables assigned so far)
      assign X ← random choice among the argmin set
  return the complete assignment

The min-conflicts heuristic. Min-conflicts is a hill-climbing strategy specialised to CSPs. One iteration does three things: choose a variable that is currently in conflict, evaluate every value in that variable's domain by counting how many constraints the variable would violate if it took that value, and move to the value with the lowest count. The algorithm in pseudocode:

MIN-CONFLICTS(csp, max_steps):
  current ← an initial complete assignment (random or greedy)
  for i = 1 to max_steps:
      if current is a solution (cost = 0): return current
      X ← a randomly chosen variable from CONFLICTED-VARS(current)
      v ← argmin over v' in D(X) of CONFLICTS(X, v', current)
            (ties broken uniformly at random)
      current[X] ← v
  return failure            # no solution found within the step budget

Three design points deserve emphasis. First, the variable is chosen uniformly at random among conflicted variables, not greedily. Choosing the most-conflicted variable deterministically tends to cycle between a small set of variables and get trapped. Second, the value is chosen greedily, and ties are broken randomly — on plateaus, where many values give the same conflict count, random tie-breaking is what performs the sideways random walk that eventually leads off the plateau. Third, the current value of X is included among the candidates; if it is already the minimum, the move may be a no-op, and some implementations exclude the current value to force a genuine change.

Worked example: 4-queens. Variables Q1..Q4 are the columns, values are rows 1–4, and two queens conflict if they share a row or a diagonal. Start from the assignment Q1=1, Q2=1, Q3=1, Q4=1 (all on row 1). Every pair shares a row, so cost = 6 (all six pairs conflict).

The trace illustrates the typical shape of a min-conflicts run: a rapid, steep descent from a very poor state, followed by a slower phase of plateau moves near cost 1 or 2, then a final repair to zero. Note also the solution (2,4,1,3) is one of the two valid 4-queens configurations.

Incremental conflict counting. A naive implementation recomputes cost from scratch, which is O(number of constraints) per evaluation and would make each step expensive. Real implementations maintain auxiliary counters so each step costs time proportional only to the variables that could be affected. For n-queens the classical trick is to keep three integer arrays:

rowCount[r]      = number of queens on row r
diagCount1[c-r]  = number of queens on the "\" diagonal indexed by (col - row)
diagCount2[c+r]  = number of queens on the "/" diagonal indexed by (col + row)

conflicts(queen in column c moved to row r) =
      rowCount[r] + diagCount1[c-r] + diagCount2[c+r]
      (minus self-counts if the queen is currently on those lines)

Moving a queen means decrementing three counters at the old position and incrementing three at the new one: O(1) per move, and O(n) to evaluate all rows for one column. The same idea generalises: for an arbitrary binary CSP, keep for each variable–value pair a count of how many neighbours currently conflict with it, and update only the entries belonging to the neighbours of the variable that just changed. A separate "list of currently conflicted variables" structure (a set or bucket array) lets variable selection be O(1) as well.

Scaling behaviour. The headline empirical result, from Minton, Johnston, Philips and Laird's work in the early 1990s, is that min-conflicts solves the million-queens problem in roughly 50 moves on average after a greedy initialisation, and the number of repair steps is roughly independent of n for large n. This is not magic; it is a property of the problem class. The n-queens problem is massively under-constrained: the ratio of constraints to the available freedom is low, solutions are dense in the state space, and almost every region of the landscape contains a solution nearby. Under such conditions a gradient-following repair method walks downhill to a solution almost immediately. The same holds for random graph colouring well away from the satisfiability threshold and for many large scheduling problems with slack resources. The lesson is that the hardness of a problem for local search is governed by solution density and landscape structure, not by raw size.

Local minima and plateaus. Pure min-conflicts is hill climbing, and hill climbing gets stuck. Two failure modes matter:

  • A local minimum is a state with cost > 0 where every single-variable change strictly increases the cost. No greedy move escapes it.
  • A plateau is a connected region of equal-cost states. Random tie-breaking lets the search wander across it, but on a large plateau the wander can be very long, and a shoulder (a plateau with an exit downhill somewhere) may take exponential time to cross by random walking alone.

Because conflict counts are integers and the neighbourhood is small, CSP landscapes are riddled with plateaus. Every practical local-search solver therefore adds a diversification mechanism on top of greedy repair. Five standard ones follow.

Random restarts. The crudest and sometimes most effective method: if the search has not found a solution within max_steps moves, throw the state away and start over from a fresh (randomised) complete assignment. Restarts are the right tool when the run-time distribution is heavy-tailed — when a large fraction of runs finish quickly but a minority get stuck for an extremely long time. Cutting off the stuck runs and restarting converts a heavy-tailed distribution into a much better-behaved one. Choosing the cutoff matters: too short and no run ever has time to succeed; too long and the benefit disappears. Luby's universal restart schedule (cutoffs 1, 1, 2, 1, 1, 2, 4, 1, 1, 2, 1, 1, 2, 4, 8, ...) is a principled choice when the optimal cutoff is unknown.

Random walk (noise). With a small probability p, ignore the heuristic and move the chosen variable to a value picked uniformly at random from its domain; with probability 1 - p, take the greedy min-conflicts move. This is the CSP analogue of the WalkSAT strategy for Boolean satisfiability, and empirically it is one of the highest-value additions per line of code.

MIN-CONFLICTS-RANDOM-WALK(csp, max_steps, p):
  current ← initial complete assignment
  for i = 1 to max_steps:
      if cost(current) = 0: return current
      X ← random conflicted variable
      if random() < p:
          v ← uniformly random value from D(X)        # noise move
      else:
          v ← argmin_{v'} CONFLICTS(X, v', current)   # greedy move
      current[X] ← v
  return failure

Typical values of p lie between 0.02 and 0.2. The parameter trades off intensification against diversification: p = 0 is pure hill climbing and stalls in local minima; p = 1 is a blind random walk that never exploits the gradient. Adaptive noise schemes raise p when the cost has not improved for a while and lower it after each improvement, removing the need to tune it by hand.

Simulated annealing. Instead of a fixed noise probability, accept a randomly proposed move with a probability that depends on how much it worsens the cost and on a temperature parameter T that is lowered over time:

SIMULATED-ANNEALING(csp, schedule):
  current ← initial complete assignment
  for t = 1 to ∞:
      T ← schedule(t)
      if T = 0 or cost(current) = 0: return current
      next ← a randomly chosen neighbour of current
      ΔE ← cost(next) - cost(current)
      if ΔE <= 0:
          current ← next                    # always accept improvements
      else:
          current ← next with probability exp(-ΔE / T)

At high T nearly every move is accepted and the search is effectively random, exploring widely. As T → 0 only improving moves survive and the search behaves like hill climbing, settling into a basin. With a sufficiently slow (logarithmic) cooling schedule the method converges to a global optimum with probability 1, though that schedule is far too slow to be practical; geometric schedules such as T ← 0.95 T every k steps are the usual compromise. Annealing is the method of choice when the objective is a weighted sum with a rugged landscape, for instance timetabling with many soft preferences.

Tabu search. Tabu search attacks cycling directly by maintaining a short-term memory. After a variable–value pair (X, v) is changed, that pair (or the move that would undo the change) is declared tabu for the next tt iterations and may not be selected, even if it looks best. This forces the search away from the region it just left, allowing it to climb out of a local minimum and explore elsewhere. The implementation is a table tabuUntil[X][v] of iteration numbers, so the test is O(1):

if tabuUntil[X][v] > iteration: the move is forbidden
   unless ASPIRATION holds, e.g. the move would produce
   a state strictly better than the best found so far.

The aspiration criterion is important: a tabu move that would immediately improve on the best-ever cost should be allowed, since the reason for forbidding it (avoiding revisitation) is clearly outweighed. The tenure tt is the key parameter — small tenures intensify, large tenures diversify — and reactive tabu search adjusts it dynamically by detecting repeated states. Tabu search is the engine behind many of the strongest solvers for graph colouring and timetabling.

Constraint weighting (breakout / clause weighting). Rather than changing the search behaviour, constraint weighting changes the landscape. Each constraint c carries a weight wc (initially 1) and the objective becomes Σ{c violated} wc. Whenever the search reaches a local minimum, the weights of all currently violated constraints are incremented:

BREAKOUT:
  while not solved:
      take min-conflicts moves on the weighted cost
      if no move strictly improves the weighted cost:   # local minimum
          for each violated constraint c: w[c] ← w[c] + 1

Incrementing the weights lifts the floor of the basin the search is sitting in until it is no longer a minimum, and the search flows out. The weights also accumulate information about which constraints are structurally hard to satisfy, steering future effort towards them. Variants such as SAPS (Scaling and Probabilistic Smoothing) periodically smooth the weights back towards their mean to prevent runaway values from distorting the landscape permanently. The chief advantage over restarts is that the knowledge gained (the weights) persists instead of being discarded.

When local search beats systematic search. The two paradigms have complementary profiles, and the choice should be driven by the properties of the instance rather than by habit.

  • Scale. Because memory is constant and each move is O(1) or O(d) with incremental counters, local search routinely handles problems with hundreds of thousands or millions of variables. A backtracking solver on the same instance would spend all its time on the first few levels of a tree whose depth equals the number of variables.
  • Incompleteness. Local search is sound but not complete: if it reports a solution, that solution is genuinely conflict-free (easy to verify), but failure to find one proves nothing. It can never return "unsatisfiable", only "not found within my budget". If the task is to prove that a timetable with the given constraints is impossible, or to count solutions, or to find a provably optimal one, a systematic method (or a hybrid with a complete component) is mandatory.
  • The phase transition. For many random CSP families, hardness peaks at a critical constrainedness ratio where the probability of satisfiability passes through one half. Below it, solutions are dense and local search is extremely fast; above it, instances are usually unsatisfiable and local search spins forever. Exactly at the transition, satisfiable instances have very few, isolated solutions and the landscape is rugged with deep local minima — the worst case for iterative repair, and the regime where good systematic solvers with strong propagation and learning are usually superior.
  • Anytime behaviour. Local search always holds a complete assignment, so it can be interrupted at any moment and asked for its best-so-far state — perhaps a schedule with three violations instead of zero, which a human dispatcher can patch. Backtracking search interrupted halfway holds only a partial assignment, which is operationally useless.
  • Hybrids. The paradigms combine well. Local search can be used as a probe to identify promising regions, with a systematic solver then exploring a restricted neighbourhood exhaustively — this is the idea behind large neighbourhood search, where a fragment of the current solution is destroyed and a complete solver (often a CP or MIP engine) optimally re-completes it. Conversely, nogoods or value-ordering information harvested by a systematic solver can bias local search, and local search can supply a good upper bound that lets a branch-and-bound solver prune aggressively.

Online repair and real-world scheduling. Most industrial scheduling is not a one-shot computation but a continuous process. A crew member calls in sick, a machine breaks down, a cloud front moves over an observatory, a customer brings a deadline forward. The constraint network changes slightly, and the question is what to do with the schedule that was already published. A systematic solver has nothing to reuse: its search tree, its nogoods, and its propagation state were all derived from the old constraints, so it must discard them and solve again. Local search, by contrast, has an ideal starting point already in hand — the old schedule. Seed the current state with it, recompute the conflict counts under the new constraints (usually only a handful of constraints are violated), and run min-conflicts. Repair typically takes a few moves rather than a full re-solve.

ONLINE-REPAIR(old_solution, changed_csp):
  current ← old_solution                    # reuse, don't rebuild
  recompute conflict counters under changed_csp
  while cost(current) > 0 and time remains:
      X ← random conflicted variable
      v ← argmin CONFLICTS(X, v', current)   # with noise / tabu as needed
      current[X] ← v
  return current

Reusing the old solution also delivers something the user cares about independently of feasibility: stability. People have planned their lives around the published roster; a mathematically valid but entirely different schedule is operationally unacceptable. Because min-conflicts only touches variables that are actually in conflict (and their knock-on effects), the repaired schedule stays close to the original by construction. This is the minimal perturbation problem, and it can be modelled explicitly: add, for every variable X, a soft constraint X = old(X) with weight λ, and minimise

cost(s) = (number of violated hard constraints) × M
          + λ × |{ X : s(X) ≠ old(X) }|

with M large enough that no amount of stability
can compensate for a hard-constraint violation.

The parameter λ tunes how much churn is tolerated to regain feasibility. Because the stability term is itself just a count over variables, it slots straight into the same incremental conflict-counting machinery.

Classic deployments of this pattern include:

  • Telescope observation scheduling. The original min-conflicts work came out of NASA's scheduling of the Hubble Space Telescope, where the SPIKE system had to allocate thousands of observations subject to orbital visibility windows, instrument changeovers and target priorities, and had to re-plan whenever an instrument failed or a target of opportunity (a supernova, a comet) appeared. Iterative repair cut scheduling time dramatically compared with the previous approach.
  • Airline crew rostering and disruption management. Rosters covering tens of thousands of duties must respect legality rules on duty time, rest, qualifications and base returns. When weather closes an airport, an operations-control system repairs the roster in minutes, re-assigning the minimum number of crews rather than regenerating the month.
  • Factory job-shop scheduling. Machine breakdowns, rush orders and material shortages all perturb the plan; repair-based rescheduling keeps the shop floor instructions largely intact, which matters because setups and material movements have already begun.
  • University timetabling and nurse rostering follow the same shape: an annual systematic solve, then continual local repair as room availabilities and staff absences change.

Combining local search with constraint propagation. The two techniques of this module are not rivals; propagation strengthens local search in several concrete ways.

  • Preprocessing with AC-3. Before any repair begins, run arc consistency over the whole network. Every value removed is a value that cannot participate in any solution, so deleting it is free of risk. If a variable is assigned a value that AC-3 deletes, that value is simply reset to a surviving one before the search starts. Higher levels (path consistency, singleton arc consistency) or global-constraint filtering can be used when the extra preprocessing cost is justified.
  • Cheaper moves. The per-step cost of min-conflicts is dominated by evaluating every value in the chosen variable's domain. Shrinking d from, say, 40 to 12 by preprocessing cuts that cost by roughly a factor of three on every single iteration for the entire run — a large cumulative saving when runs last millions of moves. Pruned domains also shrink the search space and remove whole families of local minima that were supported only by impossible values.
  • Detecting unsatisfiability. This is arguably the most valuable contribution. Local search cannot distinguish "hard" from "impossible"; it will churn forever on an unsatisfiable instance. If AC-3 wipes out a domain during preprocessing, the instance is proven unsatisfiable immediately and the fruitless run is avoided entirely. A cheap propagation pass is therefore excellent insurance before committing a long local-search budget.
  • Propagation inside the loop. Some hybrids run limited filtering after each repair move: having set X = v, propagate the consequences a short distance to mark values of neighbouring variables that are now locally inconsistent, and exclude those values from the next move's candidate set. The filtering must be non-destructive with respect to the complete-state invariant — values are suppressed for the purposes of move selection rather than permanently deleted, since the current assignment must always remain total. The trade-off is familiar from forward checking versus MAC: stronger filtering prunes more candidate moves but raises the cost of each step, and for local search, where steps are supposed to be very cheap, the balance usually favours light propagation.
  • Structural analysis and decomposition. Analysing the constraint graph before searching often reveals exploitable structure. If the graph has several connected components, each is an independent CSP and local search can run on each separately (in parallel if desired), with the overall conflict count being the sum. Cut vertices and small cutsets permit cycle-cutset decomposition; tree-structured components can be solved exactly in O(n d²) by directional arc consistency rather than searched at all. Removing the easy parts leaves local search to concentrate its effort on the genuinely hard core of the problem.

A sensible default pipeline for a large, loosely constrained practical problem therefore looks like this: normalise and preprocess the model, run AC-3 (bailing out with "unsatisfiable" if a domain empties), decompose into independent components, build a greedy conflict-minimising initial assignment for each, run min-conflicts with random walk and a restart schedule under a time budget, and return the best-so-far assignment with its conflict count so that the user always has something actionable. When the instance turns out to sit near the phase transition and local search stalls, fall back on a systematic MAC-based solver, or wrap the two together in a large-neighbourhood scheme where the complete solver re-optimises fragments chosen by the local search.

So far in this module you have worked with systematic search: backtracking that extends a partial assignment one variable at a time, with forward checking or AC-3 pruning the domains along the way. Local search takes the opposite stance. It begins with a complete assignment in which every variable already has a value — typically one that violates many constraints — and then repairs it, changing one variable at a time until no constraint is broken. This is called a complete-state formulation, and the standard repair rule is the min-conflicts heuristic: pick a variable involved in a conflict and give it the value that leaves the fewest conflicts remaining.

The method is simple, but its behaviour is interesting. Greedy repair can stall in local minima and on plateaus where every move looks equally good, so practical solvers add sideways moves, random restarts, random walk steps, or constraint weighting to escape. Min-conflicts solves n-queens for very large n in roughly constant time regardless of n, which is why local search dominates on large, loosely constrained problems and in online repair settings such as rescheduling an observatory or an airline timetable after a disruption. The trade-off is that it is incomplete: it cannot prove that a problem is unsatisfiable, and it offers no guarantee of termination.

Implementation Project and Evaluation

▶

This topic turns the theory of constraint propagation into a working piece of software and, just as importantly, into a defensible experiment. The deliverable is a single configurable CSP solver that can be run as plain backtracking, as backtracking with forward checking, as backtracking maintaining arc consistency (MAC), or as a min-conflicts local search — plus a benchmark harness that measures what each configuration actually costs and gains. The engineering discipline matters as much as the algorithms: if the four configurations share one code path, differ only by arguments, and restore state identically, then any difference you measure is attributable to inference strength rather than to an accidental bug or an unfair implementation. Everything below assumes binary CSPs (every constraint relates exactly two variables), because that keeps arc consistency simple, but the architectural advice generalises to n-ary constraints with little change.

Project scope and solver architecture. A CSP is the triple (X, D, C): a finite set of variables, a finite domain per variable, and a set of constraints. In code this becomes three fields and one index. The index is the part beginners forget and then pay for in every inner loop.

class CSP:
    def __init__(self, variables, domains, constraints):
        self.variables   = list(variables)        # ["WA", "NT", "SA", ...]
        self.domains     = {v: set(domains[v]) for v in variables}
        self.constraints = {}                     # (X, Y) -> predicate(a, b)
        self.neighbours  = {v: set() for v in variables}
        for (x, y), pred in constraints.items():
            self.constraints[(x, y)] = pred
            self.constraints[(y, x)] = lambda a, b, p=pred: p(b, a)
            self.neighbours[x].add(y)
            self.neighbours[y].add(x)

    def consistent(self, x, a, y, b):
        pred = self.constraints.get((x, y))
        return True if pred is None else pred(a, b)

Two design choices here pay dividends later. First, the constraint dictionary is stored in both directions, so consistent(X, a, Y, b) never has to test which ordering was supplied; the symmetric wrapper costs a closure per constraint and removes a whole class of ordering bugs. Second, neighbours[v] gives every variable sharing a constraint with v in O(1) lookup, so forward checking can iterate over exactly the affected variables rather than scanning all constraints. For a map-colouring instance with 13 variables this is irrelevant; for a 500-variable random graph scanned at every one of a million nodes it is the difference between seconds and minutes.

The public interface should be a single function. Resist the temptation to write backtracking_search(), forward_checking_search() and mac_search() as three separate functions: they will drift apart, and then your comparison measures the drift rather than the algorithms.

Inside, inference selects a function object with a fixed signature such as infer(csp, X, v, assignment, trail) -> bool; "none" maps to a function that does nothing and returns True. The recursive body is then identical for every configuration, which is exactly what makes the experiment fair.

State restoration is the other architectural decision that determines whether the project is pleasant or painful. Backtracking search mutates domains on the way down and must restore them exactly on the way up. Two workable schemes:

  • Trail of removed values. Every pruning operation appends a (variable, value) pair to a list. Undo pops back to a recorded mark and re-inserts each value. Cost is proportional to the number of values actually removed — typically tiny — and memory overhead is one list for the whole search.
  • Copy-on-write / snapshot per level. Copy the affected domains before modifying them, and on undo simply discard the copies. Simpler to get right, but on a 500-variable problem with domain size 20 the copying can dominate runtime and inflate peak memory, which is precisely the effect you will later be asked to measure.
def prune(csp, var, val, trail):
    csp.domains[var].discard(val)
    trail.append((var, val))

def undo_to(csp, trail, mark):
    while len(trail) > mark:
        var, val = trail.pop()
        csp.domains[var].add(val)

Note the mark idiom: the caller records mark = len(trail) before trying a value and calls undo_to(csp, trail, mark) afterwards. This works uniformly for forward checking (a few removals) and MAC (potentially hundreds), so both inference modes share one undo mechanism.

Keep constraint checking separate from inference. Checking answers "is the partial assignment {X=a, Y=b} consistent?" and is a pure predicate with no side effects. Inference answers "given X=a, which values elsewhere are now impossible?" and mutates domains. Conflating them produces functions that are hard to unit-test and impossible to reuse: min-conflicts needs the checker but not the inference, and AC-3 as a preprocessor needs the inference but no assignment at all.

Finally, write plain backtracking first and keep it forever. It is twenty lines, it is almost certainly correct, and it is the oracle against which every other configuration is validated. A variant of it that enumerates all solutions rather than stopping at the first is even more valuable for testing, as explained in the validation subsection.

def backtrack(csp, assignment, stats):
    if len(assignment) == len(csp.variables):
        return assignment
    X = select_unassigned_variable(csp, assignment)
    for v in order_domain_values(csp, X, assignment):
        stats.nodes += 1
        if consistent_with_assignment(csp, X, v, assignment):
            assignment[X] = v

                result = backtrack(csp, assignment, stats)
                if result is not None:

Implementing forward checking. Forward checking is the cheapest useful inference: after committing X = v, look one step out along the constraint graph and delete from each unassigned neighbour's domain every value that cannot coexist with v. It enforces consistency of the arcs pointing into the newly assigned variable and nothing further.

def forward_check(csp, X, v, assignment, trail, stats):
    for Y in csp.neighbours[X]:
        if Y in assignment:
            continue
        doomed = []
        for b in csp.domains[Y]:
            stats.checks += 1
            if not csp.consistent(X, v, Y, b):
                doomed.append(b)
        for b in doomed:
            prune(csp, Y, b, trail)
        if not csp.domains[Y]:
            return False          # wipe-out: caller must undo
    return True

Three implementation details deserve emphasis. First, collect the doomed values into a list before removing them — mutating a set while iterating over it raises an error in most languages. Second, every removal goes on the shared trail, recording the exact (variable, value) pairs rather than copying whole domains; on undo you re-insert perhaps three values instead of rebuilding fifty sets. Third, when a neighbour domain empties, return False immediately: there is no point pruning the remaining neighbours when the branch is already dead. The caller is responsible for the undo, which is why the recursive skeleton above calls undo_to unconditionally after the if infer(...) block rather than inside it.

Forward checking and the minimum-remaining-values heuristic are natural partners. MRV selects the unassigned variable with the smallest current domain, and forward checking is precisely the machinery that keeps those domain sizes up to date. Under plain backtracking, MRV degenerates to a static count and gains little; under forward checking it is dynamic and typically delivers an order-of-magnitude reduction in nodes. Break MRV ties with the degree heuristic (most constraints on unassigned variables) for a further small gain.

def mrv(csp, assignment):
    unassigned = [v for v in csp.variables if v not in assignment]
    return min(unassigned, key=lambda v: (len(csp.domains[v]),
                                          -len(csp.neighbours[v])))

    after = {v: frozenset(d) for v, d in csp.domains.items()}
    assert before == after

If this fails, your trail is leaking: some pruning is not being undone, which means later branches are searching with illegally shrunken domains and will silently miss solutions. Running the test on a failing search is deliberate — a successful search returns early and leaves state deliberately unrestored, so it proves nothing.

Implementing AC-3 and maintaining arc consistency. An arc (X, Y) is consistent when every value in D(X) has at least one supporting value in D(Y) that satisfies the constraint. AC-3 enforces this over all arcs by repeatedly revising arcs from a worklist until it reaches a fixed point. The workhorse is REVISE:

def revise(csp, X, Y, trail, stats):
    stats.revisions += 1
    removed = False
    doomed = []
    for a in csp.domains[X]:
        supported = False
        for b in csp.domains[Y]:
            stats.checks += 1
            if csp.consistent(X, a, Y, b):
                supported = True
                break                       # one support is enough
        if not supported:
            doomed.append(a)
    for a in doomed:
        prune(csp, X, a, trail)
        removed = True
    return removed

The early break matters: you need the existence of one support, not a count, so the inner loop should abandon as soon as it finds one. Worst-case cost of a revision is d² constraint checks for domain size d; AC-3 overall is O(e·d³) for e arcs, because each of the e arcs can be re-enqueued at most d times (once per value deleted from the far domain).

def ac3(csp, arcs, trail, stats):
    queue = deque(arcs)
    in_queue = set(arcs)                     # duplicate suppression
    while queue:
        X, Y = queue.popleft()
        in_queue.discard((X, Y))
        if revise(csp, X, Y, trail, stats):
            if not csp.domains[X]:
                return False                 # wipe-out: inconsistent
            for Z in csp.neighbours[X]:
                if Z != Y and (Z, X) not in in_queue:
                    queue.append((Z, X))
                    in_queue.add((Z, X))
    return True

Four points to internalise. (1) Re-enqueue direction. When revise(X, Y) removes values from D(X), the variables that might lose support are the other neighbours of X, so you push arcs (Z, X) — pointing into X — for every neighbour Z except Y. Excluding Y is safe because D(Y) did not change, so (Y, X) cannot have become inconsistent. Getting this direction backwards is the classic AC-3 bug and produces a solver that terminates quickly and prunes almost nothing. (2) Seeding. As a preprocessor, seed the queue with all 2e directed arcs. As MAC inside search, after assigning X = v you first reduce D(X) to {v} and then seed the queue with only the arcs (Y, X) for unassigned neighbours Y; everything else was already arc-consistent before the assignment, so re-checking it is pure waste. (3) Early abort. Detect an empty domain the moment it happens and return False up to the search layer, which undoes the trail and tries the next value. (4) Duplicate suppression. The in_queue set prevents the same arc appearing many times; on dense graphs this visibly reduces the revision count, and since revisions are your overhead metric, it visibly improves measured runtime.

Revisiting the map-colouring trace shows MAC's extra power. After WA=R and Q=G, forward checking left D(NT)={B} and D(SA)={B}. MAC revises the arc (NT, SA): the only value B in D(NT) has no support in D(SA)={B}, so B is deleted, D(NT) empties, and the branch is refuted immediately after Q=G — one level earlier than forward checking managed. That is the whole trade in miniature: MAC does strictly more pruning per node at strictly higher per-node cost.

Implementing a min-conflicts local search solver. Local search abandons the partial-assignment paradigm entirely: it starts from a complete but probably invalid assignment and repairs it. The canonical repair heuristic is min-conflicts — pick a variable currently involved in a violated constraint and move it to the value that minimises the number of violations.

The initial assignment should be greedy rather than uniformly random. Process variables in some order and give each one the value conflicting least with the variables already placed, breaking ties randomly. On the classic n-queens benchmark this alone reduces the starting conflict count dramatically and is a large part of why min-conflicts solves million-queens instances in seconds.

def greedy_init(csp, rng):
    assignment = {}
    for X in csp.variables:
        best, best_count = [], None
        for v in csp.domains[X]:
            c = sum(1 for Y in csp.neighbours[X] if Y in assignment
                      and not csp.consistent(X, v, Y, assignment[Y]))
            if best_count is None or c < best_count:
                best, best_count = [v], c
            elif c == best_count:
                best.append(v)
        assignment[X] = rng.choice(best)
    return assignment

The main loop then repeats: if no constraint is violated, return the assignment; otherwise choose a conflicted variable uniformly at random and reassign it to a minimising value, with random tie-breaking. Random tie-breaking is not cosmetic — deterministic tie-breaking causes the search to cycle between the same two states forever.

def min_conflicts(csp, max_steps=100000, p_walk=0.02, rng=random.Random(0)):
    current = greedy_init(csp, rng)
    conflicted = compute_conflicted_set(csp, current)
    for step in range(max_steps):
        if not conflicted:
            return current, step
        X = rng.choice(list(conflicted))
        if rng.random() < p_walk:
            v = rng.choice(list(csp.domains[X]))          # random walk
        else:
            v = argmin_conflicts(csp, X, current, rng)    # greedy move
        apply_move(csp, current, conflicted, X, v)        # incremental update
    return None, max_steps                                 # give up

Incremental conflict maintenance is what makes this fast. Recomputing the global conflict count after every move costs O(e); instead, keep a per-variable conflict count and a set of currently conflicted variables, and when X changes value, update only X and its neighbours. Each move then costs time proportional to deg(X) · d, independent of problem size. On a sparse graph this is effectively constant, which is why millions of steps per second are achievable.

Escaping local minima is mandatory, because min-conflicts is a hill-climber on the conflict-count landscape and such landscapes are riddled with plateaus. Two standard remedies, both cheap: a random-walk probability p (typically 0.02–0.2) of taking an arbitrary rather than a minimising value, which is the WalkSAT idea applied to CSPs; and random restarts after a fixed number of non-improving steps. Report which you used and with what parameter, since the parameter materially affects results.

Finally, min-conflicts is incomplete: it can neither prove unsatisfiability nor guarantee it will find an existing solution. Always cap it with max_steps and return an explicit failure. Never let it loop forever, and never report its failure as "no solution exists" — on an unsatisfiable instance it will exhaust its budget and tell you nothing, whereas backtracking will prove unsatisfiability definitively.

Experimental design and benchmark instances. A benchmark suite exists to answer a question, and the question here is: how does inference strength trade pruning against overhead across different problem families? That dictates the instances you need.

  • Structured instances. Include tree-structured constraint graphs and "near-tree" graphs (a tree plus a handful of extra edges). Trees are special: a CSP whose constraint graph is a tree can be solved in O(n·d²) with no backtracking at all by making it directed-arc-consistent along a topological ordering of the tree. Benchmarking on trees therefore demonstrates the payoff of exploiting structure — MAC should solve them essentially backtrack-free, while plain backtracking may still thrash. Near-tree graphs let you show the degradation curve as cutset size grows.
  • Random binary CSPs. The standard generator is the four-parameter model <n, d, p1, p2>: n variables, domain size d, graph density p1 (fraction of the n(n−1)/2 possible constraints that exist), and tightness p2 (fraction of the d² value pairs each constraint forbids). Fix n, d and p1, then sweep p2 from near 0 to near 1 in small increments, generating many instances per point.
  • The phase transition. At low tightness nearly every instance is satisfiable and easy; at high tightness nearly every instance is trivially unsatisfiable and also easy. Between them lies a narrow band where the satisfiable fraction falls from ~1 to ~0 and median solving cost peaks by orders of magnitude. Sweeping tightness is how you locate that band and ensure your comparison includes genuinely hard instances rather than only trivial ones. Plotting satisfiable-fraction and median cost on the same p2 axis makes the alignment of the cost peak with the 50 % crossover point visible.

Control one factor at a time. If you change inference and variable ordering simultaneously you cannot attribute the resulting difference to either. So when comparing none / FC / MAC, pin the variable ordering (say, MRV with degree tie-break) and the value ordering (say, LCV or natural) and vary only inference. Run a separate experiment, with inference pinned, to measure the effect of ordering heuristics. Use identical instances across configurations — the same generated CSP objects, not merely the same parameters — so that instance-to-instance variance cancels out and you can legitimately report paired comparisons.

Handle stochasticity honestly. Min-conflicts, random restarts, random tie-breaking and random instance generation all introduce variance. Run every stochastic configuration k times (k = 25 or more is typical) with distinct, recorded seeds, and report the median plus a spread measure (interquartile range, or 10th/90th percentiles). Means are a poor choice here because local-search runtime distributions are heavy-tailed: a handful of catastrophic runs drag the mean far from anything you would ever observe. Recording the seed makes a surprising run reproducible for debugging.

Impose a uniform timeout and record it. Give every run the same budget — say 60 seconds of wall clock, or an equivalent node cap — and when a run exceeds it, log it as a timeout with the budget value rather than deleting the row. Silently dropping failures is a serious methodological error: it systematically removes the hardest instances from precisely the configuration that struggles most, making the weak configuration look artificially good. The standard honest presentations are (a) a table of "solved within budget / total" alongside the median time over solved instances, or (b) a cactus plot of instances solved against cumulative time, which handles censored data gracefully.

Performance metrics and instrumentation. One number cannot characterise a solver. Runtime alone conflates algorithmic quality with implementation quality and hardware; node counts alone ignore the cost of obtaining them. Use complementary metrics so each explains the other.

  • Nodes expanded — the number of assignments attempted, i.e. the size of the explored search tree. This is the cleanest measure of pruning power and is implementation- and machine-independent. Increment it at exactly one place in the code (the top of the value loop) so the definition is identical across configurations.
  • Backtracks — the number of times a value is retracted. Together with nodes it describes the shape of the tree: a high backtrack-to-node ratio indicates thrashing near the leaves.
  • Constraint checks — every evaluation of a constraint predicate. This is the classic machine-independent proxy for work, and it captures the overhead that inference adds. The informative statistic is checks per node: FC might use 30 checks per node, MAC 400, so MAC must reduce nodes by more than 13× to break even on this measure.
  • AC-3 revisions — how many times REVISE is called, plus optionally how many of those actually deleted something. A high call count with a low deletion rate is the signature of a missing duplicate-suppression set or an over-eager queue seeding.
  • Wall-clock time — the ground truth users care about, but report it with hardware, language and version. Measure with a monotonic clock and exclude instance generation and I/O from the timed region.
  • Peak memory — relevant because copy-on-write domain restoration allocates on every node; if you implemented both trail and copying schemes, this is the metric that shows why the trail wins on large instances. Recursion depth is a cheap companion statistic.
  • Local-search metrics — nodes and backtracks are meaningless for min-conflicts. Record instead steps to solution, success rate within the step budget, number of restarts, and time per step. Success rate is the headline number: a method that solves 60 % of instances quickly is not comparable to a complete method without saying so.

Then log raw per-run rows to CSV — one row per (instance, configuration, seed) — rather than printing aggregated summaries. Debugging, validation, and interpreting results. Inference bugs are insidious because they do not crash; they quietly delete valid values and the solver returns "no solution" on a satisfiable instance, or returns a solution but explores suspiciously few nodes. The following checks catch essentially all of them.

  • Solution-count equivalence. On small instances (say 6–10 variables, domain size 3), run every configuration in count-all-solutions mode and assert the counts are identical to plain backtracking's. Inference may change how many nodes you visit but must never change the solution set. A smaller count means something is pruning values that participate in real solutions; a larger count means your consistency check is too weak or restoration is leaking values back in at the wrong moment. Randomly generate a few hundred such instances and run the comparison as a property-based test.
  • Restoration assertions. Around every assignment, snapshot the domains (in a debug build only — it is far too slow for benchmarking) and assert after the undo that the restored domains equal the snapshot exactly. This localises a trail bug to the specific inference call that caused it, which is far better than discovering at the top level that something, somewhere, leaked.
  • Idempotence of AC-3. Run AC-3 to a fixed point, then run it again on the result: the second run must remove nothing and must return True. If it removes a value, your re-enqueue logic is incomplete (you reached a state you wrongly believed was a fixed point). This is a one-line test that catches the single most common AC-3 bug.
  • Sanity on known instances. Australia map colouring has exactly 18 solutions with three colours; 8-queens has 92; a tree-structured CSP made arc-consistent should be solved with zero backtracks. Hard-code these as regression tests.
  • Determinism control. Seed every random source explicitly. A bug that appears once in fifty runs is only fixable if you can reproduce it.

Finally, present the results as plots and a recommendation. The standard figures are: nodes expanded (log scale) against tightness p2, one line per configuration; wall-clock time (log scale) against p2, same lines; a cactus plot of instances solved against time budget; and a scatter of nodes against time to expose the per-node-cost difference between configurations. A benchmark report that stops at the graphs has only done half the work; the deliverable is the decision the graphs justify.
