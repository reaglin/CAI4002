Implementation Project and Evaluation

▶

This topic turns the theory of constraint propagation into a working piece of software and, just as importantly, into a defensible experiment. The deliverable is a single configurable CSP solver that can be run as plain backtracking, as backtracking with forward checking, as backtracking maintaining arc consistency (MAC), or as a min-conflicts local search — plus a benchmark harness that measures what each configuration actually costs and gains. The engineering discipline matters as much as the algorithms: if the four configurations share one code path, differ only by arguments, and restore state identically, then any difference you measure is attributable to inference strength rather than to an accidental bug or an unfair implementation. Everything below assumes binary CSPs (every constraint relates exactly two variables), because that keeps arc consistency simple, but the architectural advice generalises to n-ary constraints with little change.

Project scope and solver architecture. A CSP is the triple (X, D, C): a finite set of variables, a finite domain per variable, and a set of constraints. In code this becomes three fields and one index. The index is the part beginners forget and then pay for in every inner loop.

class CSP:
    def __init__(self, variables, domains, constraints):
        self.variables   = list(variables)        # ["WA", "NT", "SA", ...]
        self.domains     = {v: set(domains[v]) for v in variables}
        self.constraints = {}                     # (X, Y) -> predicate(a, b)
        self.neighbours  = {v: set() for v in variables}
        for (x, y), pred in constraints.items():
            self.constraints[(x, y)] = pred
            self.constraints[(y, x)] = lambda a, b, p=pred: p(b, a)
            self.neighbours[x].add(y)
            self.neighbours[y].add(x)

    def consistent(self, x, a, y, b):
        pred = self.constraints.get((x, y))
        return True if pred is None else pred(a, b)

Two design choices here pay dividends later. First, the constraint dictionary is stored in both directions, so consistent(X, a, Y, b) never has to test which ordering was supplied; the symmetric wrapper costs a closure per constraint and removes a whole class of ordering bugs. Second, neighbours[v] gives every variable sharing a constraint with v in O(1) lookup, so forward checking can iterate over exactly the affected variables rather than scanning all constraints. For a map-colouring instance with 13 variables this is irrelevant; for a 500-variable random graph scanned at every one of a million nodes it is the difference between seconds and minutes.

The public interface should be a single function. Resist the temptation to write backtracking_search(), forward_checking_search() and mac_search() as three separate functions: they will drift apart, and then your comparison measures the drift rather than the algorithms.

Inside, inference selects a function object with a fixed signature such as infer(csp, X, v, assignment, trail) -> bool; "none" maps to a function that does nothing and returns True. The recursive body is then identical for every configuration, which is exactly what makes the experiment fair.

State restoration is the other architectural decision that determines whether the project is pleasant or painful. Backtracking search mutates domains on the way down and must restore them exactly on the way up. Two workable schemes:

  • Trail of removed values. Every pruning operation appends a (variable, value) pair to a list. Undo pops back to a recorded mark and re-inserts each value. Cost is proportional to the number of values actually removed — typically tiny — and memory overhead is one list for the whole search.
  • Copy-on-write / snapshot per level. Copy the affected domains before modifying them, and on undo simply discard the copies. Simpler to get right, but on a 500-variable problem with domain size 20 the copying can dominate runtime and inflate peak memory, which is precisely the effect you will later be asked to measure.
def prune(csp, var, val, trail):
    csp.domains[var].discard(val)
    trail.append((var, val))

def undo_to(csp, trail, mark):
    while len(trail) > mark:
        var, val = trail.pop()
        csp.domains[var].add(val)

Note the mark idiom: the caller records mark = len(trail) before trying a value and calls undo_to(csp, trail, mark) afterwards. This works uniformly for forward checking (a few removals) and MAC (potentially hundreds), so both inference modes share one undo mechanism.

Keep constraint checking separate from inference. Checking answers "is the partial assignment {X=a, Y=b} consistent?" and is a pure predicate with no side effects. Inference answers "given X=a, which values elsewhere are now impossible?" and mutates domains. Conflating them produces functions that are hard to unit-test and impossible to reuse: min-conflicts needs the checker but not the inference, and AC-3 as a preprocessor needs the inference but no assignment at all.

Finally, write plain backtracking first and keep it forever. It is twenty lines, it is almost certainly correct, and it is the oracle against which every other configuration is validated. A variant of it that enumerates all solutions rather than stopping at the first is even more valuable for testing, as explained in the validation subsection.

def backtrack(csp, assignment, stats):
    if len(assignment) == len(csp.variables):
        return assignment
    X = select_unassigned_variable(csp, assignment)
    for v in order_domain_values(csp, X, assignment):
        stats.nodes += 1
        if consistent_with_assignment(csp, X, v, assignment):
            assignment[X] = v
            mark = len(trail)
            if infer(csp, X, v, assignment, trail):
                result = backtrack(csp, assignment, stats)
                if result is not None:
                    return result
            undo_to(csp, trail, mark)
            del assignment[X]
            stats.backtracks += 1
    return None

Implementing forward checking. Forward checking is the cheapest useful inference: after committing X = v, look one step out along the constraint graph and delete from each unassigned neighbour's domain every value that cannot coexist with v. It enforces consistency of the arcs pointing into the newly assigned variable and nothing further.

def forward_check(csp, X, v, assignment, trail, stats):
    for Y in csp.neighbours[X]:
        if Y in assignment:
            continue
        doomed = []
        for b in csp.domains[Y]:
            stats.checks += 1
            if not csp.consistent(X, v, Y, b):
                doomed.append(b)
        for b in doomed:
            prune(csp, Y, b, trail)
        if not csp.domains[Y]:
            return False          # wipe-out: caller must undo
    return True

Three implementation details deserve emphasis. First, collect the doomed values into a list before removing them — mutating a set while iterating over it raises an error in most languages. Second, every removal goes on the shared trail, recording the exact (variable, value) pairs rather than copying whole domains; on undo you re-insert perhaps three values instead of rebuilding fifty sets. Third, when a neighbour domain empties, return False immediately: there is no point pruning the remaining neighbours when the branch is already dead. The caller is responsible for the undo, which is why the recursive skeleton above calls undo_to unconditionally after the if infer(...) block rather than inside it.

A worked trace on Australian map colouring with domains {R, G, B} and the usual adjacency (WA–NT, WA–SA, NT–SA, NT–Q, SA–Q, SA–NSW, SA–V, Q–NSW, NSW–V) makes the mechanism concrete:

Assigning V=B wipes out SA, so forward checking reports failure and the search backtracks without ever assigning NT or NSW. Plain backtracking, by contrast, would have happily assigned NT and NSW and only discovered the problem when it reached SA. Notice also what forward checking misses: after Q=G the domains of NT and SA are both the singleton-ish set {B}, yet NT and SA are adjacent and cannot both be blue. That inconsistency is visible to arc consistency but invisible to forward checking, which never examines arcs between two unassigned variables.

Forward checking and the minimum-remaining-values heuristic are natural partners. MRV selects the unassigned variable with the smallest current domain, and forward checking is precisely the machinery that keeps those domain sizes up to date. Under plain backtracking, MRV degenerates to a static count and gains little; under forward checking it is dynamic and typically delivers an order-of-magnitude reduction in nodes. Break MRV ties with the degree heuristic (most constraints on unassigned variables) for a further small gain.

def mrv(csp, assignment):
    unassigned = [v for v in csp.variables if v not in assignment]
    return min(unassigned, key=lambda v: (len(csp.domains[v]),
                                          -len(csp.neighbours[v])))

The single most valuable test for this component is a prune/restore round-trip assertion. Take a small unsatisfiable instance, snapshot every domain, run the full (exhaustive, failing) search, and assert that the domains are identical afterwards:

def test_restore_is_exact():
    csp = make_unsatisfiable_instance()
    before = {v: frozenset(d) for v, d in csp.domains.items()}
    assert solve(csp, inference="fc") is None
    after = {v: frozenset(d) for v, d in csp.domains.items()}
    assert before == after

If this fails, your trail is leaking: some pruning is not being undone, which means later branches are searching with illegally shrunken domains and will silently miss solutions. Running the test on a failing search is deliberate — a successful search returns early and leaves state deliberately unrestored, so it proves nothing.

Implementing AC-3 and maintaining arc consistency. An arc (X, Y) is consistent when every value in D(X) has at least one supporting value in D(Y) that satisfies the constraint. AC-3 enforces this over all arcs by repeatedly revising arcs from a worklist until it reaches a fixed point. The workhorse is REVISE:

def revise(csp, X, Y, trail, stats):
    stats.revisions += 1
    removed = False
    doomed = []
    for a in csp.domains[X]:
        supported = False
        for b in csp.domains[Y]:
            stats.checks += 1
            if csp.consistent(X, a, Y, b):
                supported = True
                break                       # one support is enough
        if not supported:
            doomed.append(a)
    for a in doomed:
        prune(csp, X, a, trail)
        removed = True
    return removed

The early break matters: you need the existence of one support, not a count, so the inner loop should abandon as soon as it finds one. Worst-case cost of a revision is d² constraint checks for domain size d; AC-3 overall is O(e·d³) for e arcs, because each of the e arcs can be re-enqueued at most d times (once per value deleted from the far domain).

def ac3(csp, arcs, trail, stats):
    queue = deque(arcs)
    in_queue = set(arcs)                     # duplicate suppression
    while queue:
        X, Y = queue.popleft()
        in_queue.discard((X, Y))
        if revise(csp, X, Y, trail, stats):
            if not csp.domains[X]:
                return False                 # wipe-out: inconsistent
            for Z in csp.neighbours[X]:
                if Z != Y and (Z, X) not in in_queue:
                    queue.append((Z, X))
                    in_queue.add((Z, X))
    return True

Four points to internalise. (1) Re-enqueue direction. When revise(X, Y) removes values from D(X), the variables that might lose support are the other neighbours of X, so you push arcs (Z, X) — pointing into X — for every neighbour Z except Y. Excluding Y is safe because D(Y) did not change, so (Y, X) cannot have become inconsistent. Getting this direction backwards is the classic AC-3 bug and produces a solver that terminates quickly and prunes almost nothing. (2) Seeding. As a preprocessor, seed the queue with all 2e directed arcs. As MAC inside search, after assigning X = v you first reduce D(X) to {v} and then seed the queue with only the arcs (Y, X) for unassigned neighbours Y; everything else was already arc-consistent before the assignment, so re-checking it is pure waste. (3) Early abort. Detect an empty domain the moment it happens and return False up to the search layer, which undoes the trail and tries the next value. (4) Duplicate suppression. The in_queue set prevents the same arc appearing many times; on dense graphs this visibly reduces the revision count, and since revisions are your overhead metric, it visibly improves measured runtime.

Revisiting the map-colouring trace shows MAC's extra power. After WA=R and Q=G, forward checking left D(NT)={B} and D(SA)={B}. MAC revises the arc (NT, SA): the only value B in D(NT) has no support in D(SA)={B}, so B is deleted, D(NT) empties, and the branch is refuted immediately after Q=G — one level earlier than forward checking managed. That is the whole trade in miniature: MAC does strictly more pruning per node at strictly higher per-node cost.

Implementing a min-conflicts local search solver. Local search abandons the partial-assignment paradigm entirely: it starts from a complete but probably invalid assignment and repairs it. The canonical repair heuristic is min-conflicts — pick a variable currently involved in a violated constraint and move it to the value that minimises the number of violations.

The initial assignment should be greedy rather than uniformly random. Process variables in some order and give each one the value conflicting least with the variables already placed, breaking ties randomly. On the classic n-queens benchmark this alone reduces the starting conflict count dramatically and is a large part of why min-conflicts solves million-queens instances in seconds.

def greedy_init(csp, rng):
    assignment = {}
    for X in csp.variables:
        best, best_count = [], None
        for v in csp.domains[X]:
            c = sum(1 for Y in csp.neighbours[X] if Y in assignment
                      and not csp.consistent(X, v, Y, assignment[Y]))
            if best_count is None or c < best_count:
                best, best_count = [v], c
            elif c == best_count:
                best.append(v)
        assignment[X] = rng.choice(best)
    return assignment

The main loop then repeats: if no constraint is violated, return the assignment; otherwise choose a conflicted variable uniformly at random and reassign it to a minimising value, with random tie-breaking. Random tie-breaking is not cosmetic — deterministic tie-breaking causes the search to cycle between the same two states forever.

def min_conflicts(csp, max_steps=100000, p_walk=0.02, rng=random.Random(0)):
    current = greedy_init(csp, rng)
    conflicted = compute_conflicted_set(csp, current)
    for step in range(max_steps):
        if not conflicted:
            return current, step
        X = rng.choice(list(conflicted))
        if rng.random() < p_walk:
            v = rng.choice(list(csp.domains[X]))          # random walk
        else:
            v = argmin_conflicts(csp, X, current, rng)    # greedy move
        apply_move(csp, current, conflicted, X, v)        # incremental update
    return None, max_steps                                 # give up

Incremental conflict maintenance is what makes this fast. Recomputing the global conflict count after every move costs O(e); instead, keep a per-variable conflict count and a set of currently conflicted variables, and when X changes value, update only X and its neighbours. Each move then costs time proportional to deg(X) · d, independent of problem size. On a sparse graph this is effectively constant, which is why millions of steps per second are achievable.

Escaping local minima is mandatory, because min-conflicts is a hill-climber on the conflict-count landscape and such landscapes are riddled with plateaus. Two standard remedies, both cheap: a random-walk probability p (typically 0.02–0.2) of taking an arbitrary rather than a minimising value, which is the WalkSAT idea applied to CSPs; and random restarts after a fixed number of non-improving steps. Report which you used and with what parameter, since the parameter materially affects results.

Finally, min-conflicts is incomplete: it can neither prove unsatisfiability nor guarantee it will find an existing solution. Always cap it with max_steps and return an explicit failure. Never let it loop forever, and never report its failure as "no solution exists" — on an unsatisfiable instance it will exhaust its budget and tell you nothing, whereas backtracking will prove unsatisfiability definitively.

Experimental design and benchmark instances. A benchmark suite exists to answer a question, and the question here is: how does inference strength trade pruning against overhead across different problem families? That dictates the instances you need.

  • Structured instances. Include tree-structured constraint graphs and "near-tree" graphs (a tree plus a handful of extra edges). Trees are special: a CSP whose constraint graph is a tree can be solved in O(n·d²) with no backtracking at all by making it directed-arc-consistent along a topological ordering of the tree. Benchmarking on trees therefore demonstrates the payoff of exploiting structure — MAC should solve them essentially backtrack-free, while plain backtracking may still thrash. Near-tree graphs let you show the degradation curve as cutset size grows.
  • Random binary CSPs. The standard generator is the four-parameter model <n, d, p1, p2>: n variables, domain size d, graph density p1 (fraction of the n(n−1)/2 possible constraints that exist), and tightness p2 (fraction of the d² value pairs each constraint forbids). Fix n, d and p1, then sweep p2 from near 0 to near 1 in small increments, generating many instances per point.
  • The phase transition. At low tightness nearly every instance is satisfiable and easy; at high tightness nearly every instance is trivially unsatisfiable and also easy. Between them lies a narrow band where the satisfiable fraction falls from ~1 to ~0 and median solving cost peaks by orders of magnitude. Sweeping tightness is how you locate that band and ensure your comparison includes genuinely hard instances rather than only trivial ones. Plotting satisfiable-fraction and median cost on the same p2 axis makes the alignment of the cost peak with the 50 % crossover point visible.

Control one factor at a time. If you change inference and variable ordering simultaneously you cannot attribute the resulting difference to either. So when comparing none / FC / MAC, pin the variable ordering (say, MRV with degree tie-break) and the value ordering (say, LCV or natural) and vary only inference. Run a separate experiment, with inference pinned, to measure the effect of ordering heuristics. Use identical instances across configurations — the same generated CSP objects, not merely the same parameters — so that instance-to-instance variance cancels out and you can legitimately report paired comparisons.

Handle stochasticity honestly. Min-conflicts, random restarts, random tie-breaking and random instance generation all introduce variance. Run every stochastic configuration k times (k = 25 or more is typical) with distinct, recorded seeds, and report the median plus a spread measure (interquartile range, or 10th/90th percentiles). Means are a poor choice here because local-search runtime distributions are heavy-tailed: a handful of catastrophic runs drag the mean far from anything you would ever observe. Recording the seed makes a surprising run reproducible for debugging.

Impose a uniform timeout and record it. Give every run the same budget — say 60 seconds of wall clock, or an equivalent node cap — and when a run exceeds it, log it as a timeout with the budget value rather than deleting the row. Silently dropping failures is a serious methodological error: it systematically removes the hardest instances from precisely the configuration that struggles most, making the weak configuration look artificially good. The standard honest presentations are (a) a table of "solved within budget / total" alongside the median time over solved instances, or (b) a cactus plot of instances solved against cumulative time, which handles censored data gracefully.

Performance metrics and instrumentation. One number cannot characterise a solver. Runtime alone conflates algorithmic quality with implementation quality and hardware; node counts alone ignore the cost of obtaining them. Use complementary metrics so each explains the other.

  • Nodes expanded — the number of assignments attempted, i.e. the size of the explored search tree. This is the cleanest measure of pruning power and is implementation- and machine-independent. Increment it at exactly one place in the code (the top of the value loop) so the definition is identical across configurations.
  • Backtracks — the number of times a value is retracted. Together with nodes it describes the shape of the tree: a high backtrack-to-node ratio indicates thrashing near the leaves.
  • Constraint checks — every evaluation of a constraint predicate. This is the classic machine-independent proxy for work, and it captures the overhead that inference adds. The informative statistic is checks per node: FC might use 30 checks per node, MAC 400, so MAC must reduce nodes by more than 13× to break even on this measure.
  • AC-3 revisions — how many times REVISE is called, plus optionally how many of those actually deleted something. A high call count with a low deletion rate is the signature of a missing duplicate-suppression set or an over-eager queue seeding.
  • Wall-clock time — the ground truth users care about, but report it with hardware, language and version. Measure with a monotonic clock and exclude instance generation and I/O from the timed region.
  • Peak memory — relevant because copy-on-write domain restoration allocates on every node; if you implemented both trail and copying schemes, this is the metric that shows why the trail wins on large instances. Recursion depth is a cheap companion statistic.
  • Local-search metrics — nodes and backtracks are meaningless for min-conflicts. Record instead steps to solution, success rate within the step budget, number of restarts, and time per step. Success rate is the headline number: a method that solves 60 % of instances quickly is not comparable to a complete method without saying so.
class Stats:
    __slots__ = ("nodes", "backtracks", "checks", "revisions",
                 "steps", "restarts", "seconds", "timed_out", "solved")
    def __init__(self):
        self.nodes = self.backtracks = self.checks = 0
        self.revisions = self.steps = self.restarts = 0
        self.seconds = 0.0
        self.timed_out = False
        self.solved = False

Instrument by passing one mutable Stats object down the recursion rather than using globals, so parallel or repeated runs cannot contaminate each other. Then log raw per-run rows to CSV — one row per (instance, configuration, seed) — rather than printing aggregated summaries. Aggregation is cheap and can be redone a dozen ways; re-running a 6-hour benchmark because you forgot to record the seed or wanted the 90th percentile instead of the mean is not.

Debugging, validation, and interpreting results. Inference bugs are insidious because they do not crash; they quietly delete valid values and the solver returns "no solution" on a satisfiable instance, or returns a solution but explores suspiciously few nodes. The following checks catch essentially all of them.

  • Solution-count equivalence. On small instances (say 6–10 variables, domain size 3), run every configuration in count-all-solutions mode and assert the counts are identical to plain backtracking's. Inference may change how many nodes you visit but must never change the solution set. A smaller count means something is pruning values that participate in real solutions; a larger count means your consistency check is too weak or restoration is leaking values back in at the wrong moment. Randomly generate a few hundred such instances and run the comparison as a property-based test.
  • Restoration assertions. Around every assignment, snapshot the domains (in a debug build only — it is far too slow for benchmarking) and assert after the undo that the restored domains equal the snapshot exactly. This localises a trail bug to the specific inference call that caused it, which is far better than discovering at the top level that something, somewhere, leaked.
  • Idempotence of AC-3. Run AC-3 to a fixed point, then run it again on the result: the second run must remove nothing and must return True. If it removes a value, your re-enqueue logic is incomplete (you reached a state you wrongly believed was a fixed point). This is a one-line test that catches the single most common AC-3 bug.
  • Sanity on known instances. Australia map colouring has exactly 18 solutions with three colours; 8-queens has 92; a tree-structured CSP made arc-consistent should be solved with zero backtracks. Hard-code these as regression tests.
  • Determinism control. Seed every random source explicitly. A bug that appears once in fifty runs is only fixable if you can reproduce it.

Once the implementation is trustworthy, interpretation becomes the intellectual content of the project. Some well-established expectations to compare your data against:

ObservationUsual explanation
FC beats plain backtracking nearly everywhere, on both nodes and timeIts overhead is small and bounded (one pass over the neighbours of the assigned variable), while detecting wipe-outs one level early removes whole subtrees.
MAC expands far fewer nodes than FC on tightly constrained instancesTight constraints make future–future inconsistencies common, and only arc consistency sees them; the saved subtrees dwarf the propagation cost.
MAC loses to FC on wall-clock time on loose instancesFew values can be pruned, so most revisions delete nothing; the propagation is pure overhead paid at every node.

Explain anomalies by mechanism, not by hand-waving about noise. If MAC and FC produce identical node counts on your tree instances, say so and attribute it to the fact that forward checking is already sufficient to make a tree backtrack-free under a good ordering. If a single random seed produced a 100× outlier for min-conflicts, attribute it to the heavy tail of local-search runtime distributions and point at your percentile data.

Finally, present the results as plots and a recommendation. The standard figures are: nodes expanded (log scale) against tightness p2, one line per configuration; wall-clock time (log scale) against p2, same lines; a cactus plot of instances solved against time budget; and a scatter of nodes against time to expose the per-node-cost difference between configurations. Then state a conclusion in words — for example: "for loose random binary CSPs use FC + MRV, because MAC's propagation does not pay for itself; for phase-transition and tightly constrained structured instances use MAC + MRV, which expands roughly 20× fewer nodes at about 6× the per-node cost; for large, loose, known-satisfiable instances where no proof of unsatisfiability is required, use min-conflicts, which solved 98 % of our instances within 10,000 steps." A benchmark report that stops at the graphs has only done half the work; the deliverable is the decision the graphs justify.
