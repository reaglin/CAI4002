HMM Inference Tasks and Algorithms

▶

A Hidden Markov Model (HMM) is the simplest useful model of a world that changes over time and that we can only observe indirectly. The world is summarised at each moment by a single discrete random variable — the state — whose value we never see. What we do see is a stream of noisy evidence variables, one per time step, each generated by the hidden state at that moment. Almost every practical question we can ask about such a system (Where am I now? Where will I be in ten minutes? Where was I three minutes ago, now that I know what happened since? What is the single most plausible history that explains everything I saw?) turns out to be answerable by a small family of closely related dynamic-programming recursions: the forward recursion, the backward recursion, and the Viterbi recursion. This topic develops those recursions from first principles, works them numerically on a canonical example, and explains how to choose among them.

The HMM framework and inference setup

Let Xt denote the state variable at time step t and Et the evidence variable observed at that step. A discrete HMM over a state space of size S is completely specified by three ingredients:

  • A prior P(X0) — a distribution over the S possible initial states, before any observation has arrived. It encodes everything we believe at time zero.
  • A transition model P(Xt | Xt-1) — an S × S matrix T whose entry Tij = P(Xt = j | Xt-1 = i) gives the probability of moving from state i to state j. Each row sums to 1.
  • A sensor (emission/observation) model P(Et | Xt) — the probability of each possible observation given each possible state.

Both the transition and sensor models are assumed stationary: the same matrix and the same emission probabilities are reused at every time step. This is what makes it possible to describe an infinitely long process with a finite number of parameters, and it is why we can write a single recursion and apply it over and over.

Two independence assumptions give the model its tractability.

  • The (first-order) Markov assumption: P(Xt | X0:t-1, E1:t-1) = P(Xt | Xt-1). The next state depends on the whole past only through the immediately preceding state. The state variable is required to be a sufficient statistic for the future: if it is not, the fix is to enlarge the state (e.g. include velocity as well as position, or use a second-order model whose state is the pair (Xt-1, Xt)).
  • The sensor Markov assumption: P(Et | X0:t, E1:t-1) = P(Et | Xt). The reading at time t is produced by the state at time t and nothing else; past readings add no further information once the current state is known.

Together these give the full joint distribution over any finite horizon as a product of local factors:

P(X0:t, E1:t) = P(X0) · ∏ from i=1 to t of [ P(Xi | Xi-1) · P(Ei | Xi) ]

Graphically this is a Bayesian network shaped like a chain: X0 → X1 → X2 → ..., with a dangling child Ei hanging off each Xi. The prior plus the two models are sufficient to answer every query, because every query is just a marginal or conditional of this joint, and the joint is fully determined by them.

Notation: e1:t abbreviates the observed sequence e1, e2, …, et. The four standard inference tasks are then

  • Filtering: compute P(Xt | e1:t) — the belief about the present.
  • Prediction: compute P(Xt+k | e1:t) for k > 0 — belief about the future.
  • Smoothing: compute P(Xk | e1:t) for 0 ≤ k < t — a revised belief about the past.
  • Most likely explanation (MLE / decoding): compute argmaxx1:t P(x1:t | e1:t) — the single best whole trajectory.

The running example: the umbrella world

A guard works in an underground facility and cannot see the weather. Each day the guard observes only whether the director arrives carrying an umbrella. The hidden state is Rt ("it rains on day t"), the evidence is Ut ("the director carries an umbrella on day t"). The model is:

Read the sensor model carefully: the umbrella is evidence about the rain, not a cause of it. The arrow runs Rt → Ut, and inference runs against the arrow, which is exactly what Bayes' rule is for.

Filtering: maintaining the current belief state

The key insight is that filtering can be done recursively: there exists a function f such that

P(X(t+1) | e(1:t+1)) = f( e(t+1), P(Xt | e(1:t)) )

i.e. the new belief depends on the old belief and the newest observation only. The old evidence need never be stored or revisited. The derivation uses nothing but the three operations of probabilistic inference — conditioning, marginalisation, and Bayes' rule — plus the two Markov assumptions:

P(X(t+1) | e(1:t+1))
  = P(X(t+1) | e(1:t), e(t+1))
  = α · P(e(t+1) | X(t+1), e(1:t)) · P(X(t+1) | e(1:t))      [Bayes' rule, conditioned on e(1:t)]
  = α · P(e(t+1) | X(t+1)) · P(X(t+1) | e(1:t))               [sensor Markov assumption]
  = α · P(e(t+1) | X(t+1)) · Σ over xt of
            P(X(t+1) | xt) · P(xt | e(1:t))                   [marginalise over Xt; Markov assumption]

Here α is a normalising constant. The formula has two clearly separated phases:

  • Predict (time update): push the current belief one step forward through the transition model, P(Xt+1 | e1:t) = Σxt P(Xt+1 | xt) P(xt | e1:t). This phase always increases (or at best preserves) uncertainty, because it mixes the belief through a stochastic matrix.
  • Update (measurement update): multiply the predicted distribution pointwise by the likelihood of the new observation, P(et+1 | Xt+1). This phase generally decreases uncertainty, because it down-weights states that would have been unlikely to produce what we saw.
  • Normalise: the pointwise product is not a distribution; divide by its sum so the entries total 1. The sum that you divide by is itself meaningful — it equals P(et+1 | e1:t), the one-step predictive likelihood of the observation, and the product of these constants over the whole sequence is the data likelihood P(e1:t).

Writing the belief as a column vector f1:t and letting Ot be the diagonal matrix whose i-th diagonal entry is P(et | Xt = i), the whole step compresses to the matrix form

f(1:t+1) = α · O(t+1) · Tᵀ · f(1:t)      with f(1:0) = P(X0)

Let us run it on the umbrella world, observing an umbrella on day 1 (u1) and again on day 2 (u2).

Day 1. Predict: P(R1) = 0.7×0.5 + 0.3×0.5 = 0.5 for rain, and likewise 0.5 for no rain — the symmetric prior is a fixed point of this transition matrix, so prediction changes nothing. Update with u1: multiply by the likelihoods ⟨0.9, 0.2⟩ to get ⟨0.9×0.5, 0.2×0.5⟩ = ⟨0.45, 0.10⟩. Normalise by 0.55: P(R1 | u1) = ⟨0.818, 0.182⟩. One umbrella sighting has lifted belief in rain from 0.5 to roughly 0.82.

Day 2. Predict: 0.7×0.818 + 0.3×0.182 = 0.627; the predicted vector is ⟨0.627, 0.373⟩ — note that it has drifted back toward 0.5, the inevitable cost of a time step. Update with u2: ⟨0.9×0.627, 0.2×0.373⟩ = ⟨0.565, 0.075⟩, normalise by 0.639 to obtain P(R2 | u1, u2) = ⟨0.883, 0.117⟩.

Notice the characteristic saw-tooth: each prediction pulls belief toward the middle, each observation pushes it back out. With repeated consistent evidence the belief climbs toward an equilibrium just above 0.88 rather than to 1.0, because the transition model keeps injecting the possibility that the weather simply changed.

FORWARD-STEP(f, e):              # f is a length-S vector, e the new observation
    for each state j:
        pred[j] = Σ over i of  T[i][j] * f[i]        # predict
        new[j]  = P(e | X = j) * pred[j]             # update
    return NORMALISE(new)

Cost. Each step is one matrix–vector product plus a pointwise multiplication: O(S²) arithmetic operations, or O(S) if the transition structure is sparse. Crucially, the cost and the memory are constant per step and independent of t: we keep one vector of S numbers and overwrite it. This is what makes filtering suitable for an agent that must run forever — a robot localising itself, a speech recogniser consuming audio frames, a credit-card system scoring transactions as they arrive. A practical caveat: after many steps the unnormalised numbers underflow, so implementations either renormalise every step (as above, which is standard) or work with log-probabilities.

Prediction: projecting belief into the future

Prediction is filtering with the update phase deleted. Having filtered up to time t, we simply apply the transition model repeatedly:

P(X(t+k+1) | e(1:t)) = Σ over x(t+k) of P(X(t+k+1) | x(t+k)) · P(x(t+k) | e(1:t))

In matrix form, P(Xt+k | e1:t) = (Tᵀ)k f1:t. No normalisation is needed, because a stochastic matrix maps distributions to distributions exactly.

Because no evidence is injected, each extra step forward can only add uncertainty. Continuing the umbrella example from ⟨0.883, 0.117⟩ at day 2 and predicting forward with no further umbrella sightings:

The sequence converges to ⟨0.5, 0.5⟩. That limit is the stationary distribution of the Markov chain: the unique vector π satisfying π = Tᵀπ (here, by symmetry, the uniform distribution). For any ergodic chain — one that is irreducible and aperiodic, which holds whenever every transition probability is strictly positive — the powers (Tᵀ)k converge to a matrix all of whose columns equal π, so the prediction forgets its starting point entirely. Once that has happened, prediction is uninformative: the answer is the same whether we saw ten umbrellas or none, and the evidence has no lasting influence on the far future.

How fast this happens is governed by the mixing time of the chain, which is controlled by the magnitude of the second-largest eigenvalue modulus |λ₂| of T; the deviation from stationarity shrinks roughly like |λ₂|k. For the umbrella transition matrix the eigenvalues are 1 and 0.4, so each day's prediction moves 60 % of the remaining distance to 0.5 — which is exactly the pattern of the table (0.383 → 0.153 → 0.061 → 0.025 excess above 0.5). A "sticky" world with transition probabilities of 0.99 would have λ₂ = 0.98 and a mixing time of hundreds of steps, so useful forecasts would extend much further. The practical rule: the predictive horizon of an HMM is a property of the transition model, not of how much evidence you have gathered. Gathering more data sharpens f1:t but does not extend the horizon.

Smoothing and the forward–backward algorithm

Smoothing asks for P(Xk | e1:t) with k < t: what should we now believe about a past time slice, in the light of everything that happened afterwards? Hindsight genuinely helps — if it rained for the next five days, that raises our belief that it was already raining on day 1, because the transition model makes rain persistent.

Split the evidence at k and apply Bayes' rule plus conditional independence (given Xk, the past evidence and the future evidence are independent — this is exactly d-separation in the chain):

P(Xk | e(1:t)) = α · P(Xk | e(1:k)) · P(e(k+1:t) | Xk)
               = α · f(1:k) × b(k+1:t)

where × denotes pointwise (component-by-component) multiplication. The first factor f1:k is exactly the filtered belief already computed by the forward recursion — nothing new is needed. The second factor bk+1:t is a likelihood, not a distribution (its entries need not sum to 1), and it obeys its own recursion running backwards:

P(e(k+1:t) | Xk) = Σ over x(k+1) of
       P(e(k+1) | x(k+1)) · P(e(k+2:t) | x(k+1)) · P(x(k+1) | Xk)

or in matrix form bk+1:t = T · Ok+1 · bk+2:t, with the base case bt+1:t = ⟨1, 1, …, 1⟩ (there is no evidence after the end, so the likelihood of "nothing" is 1 for every state).

Worked smoothing in the umbrella world. We saw umbrellas on days 1 and 2 and want P(R1 | u1, u2). The forward message is f1:1 = ⟨0.818, 0.182⟩ from before. The backward message for day 2 onward is

b(2:2)[rain]    = Σ_{r2} P(u2 | r2) P(∅ | r2) P(r2 | R1 = rain)
                = 0.9·1·0.7 + 0.2·1·0.3 = 0.63 + 0.06 = 0.69
b(2:2)[no rain] = 0.9·1·0.3 + 0.2·1·0.7 = 0.27 + 0.14 = 0.41

Multiply pointwise and normalise: α⟨0.818 × 0.69, 0.182 × 0.41⟩ = α⟨0.5646, 0.0746⟩ = ⟨0.883, 0.117⟩. Belief that day 1 was rainy rises from the filtered 0.818 to the smoothed 0.883, because the day-2 umbrella is retrospective evidence for day-1 rain. (The numerical coincidence with P(R2|u1,u2) is an artefact of this symmetric model, not a general rule.)

The naïve way to smooth a whole sequence would be to redo this separately for each k, costing O(t²). The forward–backward algorithm avoids that: run the forward recursion once from 1 to t, caching every message f1:1, …, f1:t; then run the backward recursion once from t down to 1, and at each k combine the stored forward message with the current backward message. Total cost O(t·S²) time — linear in sequence length — with O(t·S) space for the cache.

FORWARD-BACKWARD(e(1:t), prior):
    f[0] ← prior
    for i = 1 to t:  f[i] ← NORMALISE( O[i] · Tᵀ · f[i-1] )    # store every f
    b ← ⟨1,...,1⟩
    for i = t down to 1:
        sv[i] ← NORMALISE( f[i] × b )                           # smoothed estimate
        b ← T · O[i] · b                                        # roll b back one step
    return sv[1..t]

The O(t·S) space requirement is the real limitation: it rules out running the algorithm forever on a streaming signal. Two remedies are common. First, fixed-lag smoothing computes P(Xt-d | e1:t) for a fixed lag d — the system reports a slightly delayed but better-informed estimate, keeping only the last d messages in a sliding window, which gives constant time and space per step (for HMMs, by incrementally multiplying the new observation matrix in at the front of the window and dividing the old one out at the back). A speech recogniser that lags half a second behind the speaker, or a GPS track-cleaner that reports your position as of two seconds ago, is doing exactly this. Second, for the whole-sequence case one can use a divide-and-conquer or checkpointing scheme that trades a logarithmic factor of time for a square-root or logarithmic reduction in space.

Smoothing is also the E step of the Baum–Welch (EM) algorithm that learns HMM parameters from unlabelled sequences: the smoothed single-slice posteriors and the smoothed pairwise posteriors P(Xk, Xk+1 | e1:t) ∝ f1:k[i] · T[i][j] · P(ek+1|j) · bk+2:t[j] become the expected counts from which the new transition and sensor tables are re-estimated.

Most likely explanation and the Viterbi algorithm

Suppose the umbrella appears on days 1, 2, 4 and 5 but not on day 3, and we want the single most probable weather sequence argmaxr1:5 P(r1:5 | u1:5). Enumerating all St sequences (here 2⁵ = 32, but 2¹⁰⁰ for a longer run) is hopeless. The saving observation is a dynamic-programming one: the most likely path to a given state at time t+1 must consist of the most likely path to some state at time t, extended by one step. So we only need to keep, for each state, the best path ending there.

Define m1:t[i] = maxx1:t-1 P(x1:t-1, Xt = i, e1:t). The recursion is the forward recursion with the summation replaced by a maximisation — max-product instead of sum-product:

m(1:t+1)[j] = P(e(t+1) | X(t+1)=j) · max over i of ( T[i][j] · m(1:t)[i] )
ptr(t+1)[j] = argmax over i of ( T[i][j] · m(1:t)[i] )

The second line is the back-pointer: for each state at the new time step we record which predecessor achieved the maximum. When the final step is reached, we take the largest entry of m1:t, and then trace the back-pointers backwards from it to recover the entire optimal path. This back-tracking phase is what distinguishes Viterbi from a mere score computation.

Running it on u1:5 = ⟨true, true, false, true, true⟩ with the umbrella model (values are joint probabilities of best-path-and-evidence, not normalised posteriors):

Tracing back: day 5 rain ← day 4 rain ← day 3 no rain ← day 2 rain ← day 1 rain. The most likely explanation is therefore ⟨rain, rain, no rain, rain, rain⟩. Note how the single missing umbrella on day 3 is enough to flip that slice even though rain is "sticky": the sensor model says a rainy day produces no umbrella only 10 % of the time.

Why Viterbi is not the same as per-slice argmax. A tempting shortcut is to smooth every time step and then take the most probable state at each step independently. This gives the sequence of marginally most likely states, which is a different object from the jointly most likely sequence, and it can be catastrophically wrong: the resulting sequence may have probability zero under the model. Imagine a three-state system in which the transition A → B is forbidden (T[A][B] = 0); if slice 7 is 51 % A and slice 8 is 51 % B, per-slice argmax outputs "…A, B…", an impossible trajectory that no amount of post-processing can rescue. Viterbi, because it maximises the joint probability of the whole path, can never return a path of probability zero if any positive-probability path exists. The flip side: Viterbi's single best path may itself have tiny absolute probability and may not maximise the number of individually correct slices. Choose per-slice smoothing when you are scored per time step; choose Viterbi when you need a globally coherent, legal sequence (a word transcription, a gene annotation, a decoded bit stream).

Cost and implementation notes. Viterbi performs the same number of arithmetic operations as the forward pass: O(t·S²) time, i.e. linear in sequence length and quadratic in the number of states. Unlike filtering, it needs O(t·S) space to store the back-pointer lattice, since the path cannot be recovered without it. Because the m values are products of many small numbers, real implementations work in logarithms, where max-product becomes a max-plus recursion, log mt+1[j] = log P(et+1|j) + maxi(log T[i][j] + log mt[i]), which is numerically stable and uses only additions and comparisons. Viterbi may also be read as a shortest-path computation in a layered graph (the "trellis") whose edge weights are negative log probabilities.

Comparing the tasks and choosing an algorithm

All four tasks are questions about the same joint distribution, differing only in which time slice (or slices) they ask about and in whether they sum or maximise:

Several structural points tie the family together:

  • Filtering and prediction are the online pair. They need only the current message, so an agent can run them in a perception–action loop forever. Prediction is just filtering with the eyes closed, and its value decays on the timescale of the chain's mixing time.
  • Smoothing is the offline (or lagged) task. It needs information from the future, so either the sequence must be complete or the answer must be delayed by d steps. In exchange it is strictly more accurate than filtering for any slice before the present, because it conditions on strictly more evidence.
  • Viterbi shares filtering's recursive skeleton — same lattice, same O(t·S²) work, same message-passing shape — and differs only in using max where filtering uses Σ, plus the book-keeping of back-pointers. Sum-product answers "how much total probability flows into this state?"; max-product answers "what is the single heaviest path into this state?".
  • Everything here is a specialisation of general Bayesian-network inference. The forward recursion is precisely variable elimination run left-to-right on the chain-structured network, eliminating X0, then X1, and so on; the forward and backward messages are the intermediate factors. The reason exact inference is cheap here — linear rather than exponential — is that the chain has treewidth 1, so every intermediate factor involves a single variable and never grows. The conditional independences that justify the recursions (future ⊥ past given present; evidence ⊥ everything else given its own state) are exactly what d-separation reports on the chain graph. Smoothing's factorisation f × b is the two-way message passing of the junction-tree/belief-propagation algorithm applied to a chain, and the same algorithms generalise: to continuous Gaussian states they become the Kalman filter and the Rauch–Tung–Striebel smoother; to richer state factorisations they become dynamic Bayesian networks, where exact inference may again become intractable and particle filtering or other approximations take over.

A checklist for choosing. Ask three questions. (1) Which slice do I need? Present → filtering; future → prediction; past → smoothing; the whole path → Viterbi. (2) Can I wait? If decisions must be made now, you are limited to the forward pass; if you can tolerate a delay d, fixed-lag smoothing buys accuracy cheaply; if the data are archival, use full forward–backward. (3) Do I need a coherent sequence or per-slice estimates? If a downstream consumer requires a legal trajectory, use Viterbi even though per-slice posteriors would score better on per-slice accuracy; if you need calibrated uncertainty at each step, use smoothing, because Viterbi returns a path with no probabilities attached to individual slices.

Alignment with Learning Outcomes

  • MO1: Strongly supported. Every recursion in this topic is derived by marginalisation, conditioning and Bayes' rule applied to the HMM joint distribution, and the filtering, smoothing and Viterbi examples are worked numerically, including the renormalisation step that turns a product of factors into a posterior.
  • MO2: Partially supported. The HMM is presented as a chain-structured Bayesian network with an explicit DAG (X0 → X1 → … with evidence children) and explicit conditional probability tables for the prior, transition and sensor models, so it illustrates network construction for a temporal domain without covering general network design.
  • MO3: Partially supported. The derivations of the filtering and smoothing recursions rest on the Markov and sensor Markov assumptions, and the split P(Xk|e1:t) ∝ f1:k × bk+1:t is justified by the d-separation fact that past and future evidence are independent given the state at time k.
  • MO4: Partially supported. The topic compares exact algorithms on accuracy and cost (forward vs. forward–backward vs. Viterbi, O(S²) per step vs. O(t·S²), constant vs. O(t·S) memory) and notes where exact chain inference is a special, cheap case of variable elimination, but it does not treat rejection sampling, likelihood weighting or Gibbs sampling, which are mentioned only in passing as the fallback for intractable dynamic models.

A Hidden Markov Model (HMM) describes a system that changes over time through a sequence of hidden states that we cannot observe directly. Instead, at each time step we receive an observation (evidence) that depends probabilistically on the current hidden state. The model is specified by three pieces: an initial state distribution, a transition model giving the probability of moving from one state to the next, and an emission (sensor) model giving the probability of each observation given a state. Because the state at time t depends only on the state at time t-1, and the observation depends only on the current state, we can reason about long sequences efficiently with dynamic programming instead of enumerating every possible state path.

This topic organizes HMM reasoning into four standard inference tasks. Filtering asks for the belief about the current state given all evidence so far, and is computed recursively by the forward algorithm. Prediction projects that belief forward past the last observation using only the transition model. Smoothing asks about a past state given all the evidence, including evidence that arrived later, and is handled by combining forward messages with backward messages (the forward-backward algorithm). Most likely explanation asks for the single best state sequence as a whole, which is the job of the Viterbi algorithm. These tasks matter in this course because they turn the general Bayesian-network machinery of the module into a practical, tractable procedure for sequential data such as speech, part-of-speech tagging, robot localization, and gene sequence analysis.

As you watch, keep three questions in mind. First, which evidence is being conditioned on in each task, and how does that change the recursion? Second, what is stored in each cell of the dynamic programming table, and how is it computed from the previous column? Third, where does Viterbi differ from the forward algorithm: Viterbi replaces the sum over predecessor states with a maximum and keeps backpointers so the best path can be recovered. Tracking those differences will make the four tasks feel like variations on one pattern rather than four separate formulas.
