Foundations of Local Search

▶

Classical search algorithms such as breadth-first search, uniform-cost search and A* treat a problem as the construction of a path. They begin at an initial state, expand nodes into successors, and build up a search tree until a goal state is reached; the answer they return is the sequence of actions that was followed. Local search turns this picture inside out. Instead of building partial solutions outward from a start state, it begins with a complete — though probably poor — candidate solution and iteratively nudges it toward a better one. The answer it returns is a state, not a route. This apparently small shift in perspective has enormous consequences for memory consumption, for the kinds of problems that become tractable, and for the theoretical guarantees that the algorithm can offer.

Local search sits at the intersection of artificial intelligence and mathematical optimisation. Hill climbing, simulated annealing, tabu search, genetic algorithms and gradient descent are all members of the family. What unites them is a common architecture: a representation in which every state is a legitimate (if imperfect) answer, a move operator that defines which states count as neighbours of which, and an objective function that scores states so that the search knows which direction is "better". Everything else — the sophistication of the move acceptance rule, the use of randomness, the handling of memory — is variation on that theme.

What local search is. The defining structural feature is that each node in local search is a complete, valid configuration of the problem. In the 8-queens problem, for example, a classical formulation might place queens one column at a time, so that intermediate nodes hold three or four queens and the rest of the board is empty. A local search formulation never does this. Every state has all eight queens on the board — one per column, say — and the only question is whether those queens attack one another. A state with twelve pairs of mutually attacking queens is a bad state, but it is still a state; it is not a fragment. Similarly, in a job-shop scheduling problem, a local search state is a complete schedule assigning every operation to a machine and a time slot, even if that schedule is wildly late and violates precedence preferences.

Because every state is complete, the algorithm does not need to grow anything. It simply keeps a current state and repeatedly replaces it with a neighbour. The loop is strikingly simple:

current <- some initial complete state
loop:
    neighbours <- MOVES(current)          // all states reachable by one local edit
    next <- SELECT(neighbours, current)   // the rule that distinguishes algorithms
    if next is not better than current:
        return current                    // or apply an escape strategy
    current <- next

Only two things live in memory at any moment: current, and whichever neighbour is being examined. There is no queue of unexpanded nodes and no record of where the search has been.

Neighbours are generated by small, local modifications to the current state. The choice of what counts as "small" is a design decision, and it is arguably the single most important one a practitioner makes. For 8-queens with the one-queen-per-column representation, the natural move is "pick a column, move its queen to a different row in that column", which yields 8 × 7 = 56 neighbours. For the travelling salesperson problem, the classic 2-opt move removes two edges from the tour and reconnects the resulting fragments the other way around, reversing a segment; a tour of n cities has roughly n²/2 such neighbours. For a Boolean satisfiability instance, the move is to flip a single variable from true to false or vice versa, giving exactly n neighbours. A move operator that is too timid produces a landscape full of traps; one that is too aggressive produces an enormous neighbourhood that is expensive to scan and that destroys whatever structure the current state has already achieved.

Progress is measured by an objective or cost function rather than by distance from a start node. In A*, the quantity g(n) — the cost accumulated along the path so far — is central, and the algorithm prefers nodes that are cheap to reach. In local search, how the current state was reached is completely irrelevant; two identical board configurations are the same state whether one of them took three moves to reach and the other three thousand. All that matters is the scalar value f(current). For 8-queens the usual objective is the number of attacking pairs, which is to be minimised to zero. For a timetable it might be a weighted sum of penalties: 100 points for each room double-booking, 10 for each lecturer clash, 1 for each student forced into a lunchtime gap. Maximisation and minimisation are interchangeable — simply negate the function — and the literature slips freely between "hill climbing" and "gradient descent" for this reason.

When the path does not matter. Local search is the right tool precisely when the question being asked is "what configuration should I adopt?" rather than "how do I get from here to there?". Consider the following contrast.

The distinction is sharp. If you hand someone a solved Rubik's cube and say "there you are", you have not solved their problem — they wanted to know the twists. A local search that teleports from one cube configuration to another by arbitrary edits produces states that are unreachable by legal moves and a "solution" that is no solution at all. (Local search can still be applied to such domains indirectly, for instance by searching over the space of candidate plans, where each state is a complete sequence of actions and a move perturbs that sequence. But then the state is the plan, and the principle is unchanged.)

Because the path is irrelevant, no search tree or parent pointers need to be stored. In A*, every node carries a pointer back to its parent so the solution path can be reconstructed when a goal is found. Local search needs none of this bookkeeping — not the pointers, not the node objects, not the tree structure. This is why a local search implementation is often a few dozen lines of code with a single mutable array as its entire data structure.

Goal tests are often replaced by an objective function to maximise or a cost to minimise. Sometimes there is still a crisp goal test — in 8-queens, zero attacking pairs is unambiguously a solution and the algorithm can stop. But in a great many applications there is no such thing as "the goal". No timetable is perfect; no circuit layout has zero wire length. The algorithm has no termination condition derived from the problem, only from the resources available: stop after k iterations, stop after m seconds, stop when no improvement has been seen for 1,000 moves, or stop when a human says the answer is good enough. This blurs the traditional AI line between "search" and "optimisation", and in modern practice that line has largely dissolved.

The state-space landscape. The standard mental picture for local search is a landscape: a surface stretched over the space of all states, in which horizontal position encodes which state you are in and vertical position encodes how good it is. Elevation corresponds to the objective value for maximisation or cost for minimisation. If we are maximising, we speak of climbing hills and seeking peaks; if minimising, of descending into valleys and seeking basins. The two pictures are mirror images and the terminology is used interchangeably in the literature, which is a frequent source of confusion for newcomers: a "local minimum" in a cost landscape is exactly a "local maximum" in the negated-objective landscape.

The horizontal axis of the picture is a convenient fiction. A real state space is not one-dimensional or even two-dimensional; the 8-queens space with one queen per column has 8⁸ = 16,777,216 states and its neighbourhood structure is a graph, not a plane. The landscape drawing is a projection that preserves the one thing that matters — the adjacency induced by the move operator — and discards everything else. Change the move operator and you change the landscape, even though the set of states and their objective values are unchanged. This is a subtle but important point: the landscape is a property of the state space plus the neighbourhood relation, not of the state space alone.

Within that landscape:

  • Global maximum — the best state overall in the entire landscape. There may be several states tied for the best value; any of them is a global optimum. This is what an exact optimisation method would return, and what local search aspires to but cannot promise.
  • Local maximum — a state that is better than all of its neighbours, but not globally best. Standing on a local maximum, every available move looks like a step downhill, so a strictly improving algorithm has nowhere to go and halts prematurely.
  • Plateau — a flat region in which many adjacent states have identical objective values. Because no neighbour is better, a strict hill climber stops; because no neighbour is worse, a sideways-moving climber can wander for a long time without making progress. A plateau that has an uphill exit somewhere along its edge is a shoulder, and crossing it is productive; a plateau with no uphill exit is a flat local maximum, and crossing it is futile. Crucially, from the inside, the two look identical.
  • Ridge — a sequence of local maxima forming a narrow crest that ascends in a direction not aligned with any single move. Imagine a staircase viewed edge-on: the overall slope rises, but every individual step from the current position goes down before it goes up. Each move operator can only take you perpendicular or parallel to the crest, never diagonally along it, so the search oscillates and stalls. Ridges are notoriously difficult because, unlike plateaus, they are not flat — the algorithm genuinely sees every neighbour as worse.

The last structural fact is the most important of all: the algorithm can only perceive the landscape immediately around its current state. A local search is a blindfolded climber who can feel the ground within arm's reach and nothing beyond. It cannot see that a far higher peak lies two valleys to the east; it cannot tell whether the flat ground it is standing on is a shoulder or a flat summit; it does not even know whether the current state is the global optimum, because confirming that would require examining the whole space. All local search strategies are, in essence, different answers to the question: given only local information, how should I decide where to step next?

Memory and efficiency advantages. The practical appeal of local search comes down to resource consumption. No frontier or explored set needs to be maintained, unlike BFS or A*. Breadth-first search on a problem with branching factor b and solution depth d stores O(bd) nodes in its frontier; A* typically stores a comparable number, and in practice it is memory, not time, that kills A* on hard instances. Local search stores one state. If an algorithm variant needs a tabu list or a population, it stores a constant or user-chosen number of states — never a number that grows with the depth or breadth of exploration.

Memory requirements remain small and usually independent of problem size. More precisely, memory is proportional to the size of a single state — an array of n integers for n-queens, a permutation of n cities for TSP — and independent of how long the search runs or how large the space is. Doubling the search time costs nothing extra in memory. This is what makes local search the method of choice for long-running background optimisation.

Local search can run on state spaces too large to enumerate, including continuous and infinite ones. The space of 1,000-city tours contains roughly 999!/2 ≈ 102564 elements, vastly more than the number of atoms in the observable universe; no systematic method will ever enumerate it, but a 2-opt local search will happily improve a tour in that space on a laptop. More strikingly, local search extends directly to continuous domains. If the state is a vector of real numbers — the positions of airport terminals, the weights of a neural network, the geometry of an aerofoil — the neighbourhood is an infinitesimal step and the move operator becomes x ← x + α∇f(x), i.e. gradient ascent. Every notion in this topic (landscape, local optimum, plateau, ridge) transfers unchanged; ill-conditioned optimisation problems in machine learning are literally the ridge phenomenon in high dimensions, which is why techniques like momentum exist.

It can often find reasonable solutions quickly, even when optimal search is intractable. Consider the concrete and much-cited case of n-queens. Exhaustive or backtracking search becomes awkward for large n, but min-conflicts local search — repeatedly pick a conflicted queen and move it to the row in its column with fewest conflicts — solves the million-queens problem in well under a minute, taking on average around fifty moves regardless of n. The runtime is essentially independent of problem size, a property that no systematic method comes close to. Similarly, Lin–Kernighan-style local search routinely produces TSP tours within 2% of optimal on instances with tens of thousands of cities, while exact solution of such instances is a research-paper-sized effort.

Completeness and optimality trade-offs. All of this comes at a price, and it is important to state the price honestly. Local search is generally incomplete: it may become stuck before reaching a goal, and even if a solution exists it may never find one. A basic hill climber on 8-queens with random restarts disabled gets stuck roughly 86% of the time, solving the problem only about 14% of the time from a random start. Incompleteness here means something specific — the algorithm terminates, but it terminates on a non-solution and cannot tell you whether a solution exists. Contrast this with BFS, which on a finite space will find a solution if one exists and will report failure otherwise. Local search can never report "no solution exists"; it can only report "I did not find one", which is why local search is useless for proving unsatisfiability.

It is not optimal, since it may settle on a local rather than global optimum. Even when a solution is found, there is no guarantee it is the best one. A 2-opt TSP search converges to a tour that cannot be improved by any single 2-opt move; such a tour is typically 5% worse than optimal, and nothing in the algorithm indicates how far from optimal it is. Being unable to certify quality is in some ways worse than being suboptimal, because it leaves the engineer without a stopping criterion.

Systematic search offers completeness guarantees but can require exponential memory. This is the fundamental trade. A* with an admissible heuristic will return an optimal path and will tell you it is optimal — but it may exhaust 16 GB of RAM in minutes on a problem that local search handles in kilobytes. Depth-first search and IDA* reduce memory but pay in repeated work, and still face exponential time. The engineering decision is therefore rarely "which algorithm is better" and almost always "which failure mode can I tolerate": the systematic method's failure mode is running out of memory and returning nothing; the local method's failure mode is returning something imperfect without warning.

In practice, anytime behaviour is valuable: a usable solution is available whenever the search is stopped. This is perhaps the most underappreciated advantage. Because the current state is always a complete, legal configuration, a local search can be interrupted at any instant and still hand back an answer. If a delivery company must dispatch routes at 05:00, it starts the optimiser at midnight, interrupts it at 04:59, and uses whatever the best-so-far tour is — guaranteed valid, probably good, certainly better than nothing. A* interrupted before termination yields nothing usable at all. This profile — monotonically improving, interruptible, bounded memory — maps neatly onto real deployment constraints, and it is why local search dominates industrial scheduling, routing, placement and configuration software even though it offers no guarantees whatsoever.

A useful summary framing: systematic search asks "is there a path to a goal?" and spends memory to answer it rigorously; local search asks "can I make this good solution better?" and spends time to answer it approximately. The remainder of the module is concerned with the many ways of answering that second question well — how to choose among neighbours, how to escape the traps the landscape sets, and how to balance the cost of searching against the quality of what is found.

Most of the search methods you have seen so far build a path: they start at an initial state, expand nodes, and return the sequence of actions that leads to a goal. Local search works differently. It begins with a complete candidate solution — every variable already has a value — and then repeatedly tweaks that candidate with small moves, keeping track of only the current state (and perhaps a few neighbors) rather than a frontier and an explored set. For problems like n-queens, scheduling, or constraint satisfaction with thousands of variables, the question is simply "what is the best configuration?" and the route taken to reach it carries no information worth storing.

The mental model that makes this work is the state-space landscape: imagine every complete state laid out on a surface whose height is the value of an objective function. Local search is then the act of standing somewhere on that surface and moving to a neighboring point that is higher (or lower, if you are minimizing cost). This picture explains both the appeal and the risk. Memory use is essentially constant and the method scales to spaces far too large — even infinite — to enumerate, but because the algorithm sees only its immediate neighborhood, it can be neither complete nor optimal: it may stall on a local maximum, a plateau, or a ridge and never discover that a better region exists elsewhere.

As you watch the videos below, keep four questions in mind. What exactly counts as a "state" and what counts as a "neighbor"? What objective is being improved at each step? What is the algorithm storing in memory at any moment? And what guarantees — if any — does it give you when it stops? Pay particular attention to the trade-off framing: local search exchanges the completeness and optimality guarantees of systematic search for speed, tiny memory footprint, and the ability to attack problems of realistic size.

State Spaces, Objective Functions, and Landscapes

1

State Spaces, Objective Functions, and Landscapes

▶

Classical search algorithms such as breadth-first search, uniform-cost search, and A* treat problem solving as the construction of a path. They begin from an initial state, expand partial solutions, and keep a frontier of unexplored options in memory. That approach is powerful when the sequence of actions is itself the answer — route finding, puzzle solving, planning. But an enormous class of practical problems is not about the path at all. When a factory wants a production schedule, an airline wants crew rosters, a chip designer wants a component layout, or a telecom operator wants frequency assignments, nobody cares how the solution was found. Only the final configuration matters. For these problems a different family of methods — local search — reframes the problem entirely: instead of building solutions piece by piece, it starts with a complete (probably bad) solution and repeatedly nudges it into a better one.

To make local search precise, we need four ingredients: a state representation in which every state is a complete candidate solution, a move operator that defines which states count as "nearby", an objective (or cost) function that scores every state, and a mental model — the state-space landscape — that lets us reason about why such a search succeeds or stalls. This topic develops each of these and then shows how to assemble them into a working formulation for a new problem.

Complete-State Formulation

In a complete-state formulation, every state is a full assignment of values to all of the problem's variables or decisions. Nothing is left undecided. Contrast this with the incremental (partial-state) formulation used by backtracking search:

AspectIncremental / partial-state formulationComplete-state formulation
Initial stateEmpty assignment (e.g., empty board)Full assignment (e.g., all 8 queens placed somewhere)
ActionExtend the assignment by one variableModify an existing assignment
Intermediate statesIncomplete, not yet candidate solutionsAlways complete candidate solutions
What is returnedTypically the path or the final leafThe state itself
MemoryFrontier + explored set: grows with searchCurrent state (+ best-so-far): constant
Can be interrupted?No useful answer until completeYes — any-time: current state is always an answer

Take the 8-queens problem. The incremental formulation places queens column by column, so a typical intermediate state has five queens on the board and three columns empty — that is not a candidate solution, it is a fragment. The complete-state formulation instead starts with all eight queens already on the board, one per column, at arbitrary rows. That configuration is almost certainly illegal in the sense that queens attack one another, but it is a complete configuration. Search then consists of moving queens around until no pair attacks.

Three consequences follow, and they are the reason local search exists:

  • The path is irrelevant. If two different sequences of queen-moves end at the same board, those outcomes are indistinguishable. There is no notion of "path cost" to accumulate, no need for a parent pointer, no solution path to reconstruct. The algorithm simply returns the state it is holding.
  • Memory is (typically) constant. A local search algorithm stores the current state and, optionally, the best state seen so far. It does not store a frontier, and it usually does not store an explored set. For 8-queens that is on the order of eight integers, regardless of how many millions of moves are made. This is O(1) space in the size of the search, which is the sharpest possible contrast with A*, whose memory requirement typically grows exponentially.
  • Vast or infinite spaces become tractable. The complete-state space for n-queens with one queen per column has n^n states — for n = 8 that is roughly 17 million, and for n = 1,000,000 it is an unthinkable number. Systematic search cannot enumerate it; local search does not need to, because it never enumerates, it only samples a neighborhood. Local search also extends naturally to continuous spaces, where the number of states is literally infinite (e.g., choosing real-valued coordinates for three airports in a country to minimize total travel distance from every city).

Because the current state is always a legal candidate, local search is an any-time algorithm: you can stop it after one second or one hour and read off the best configuration found so far. This property is enormously valuable in industry, where a good schedule produced in ten minutes beats a provably optimal schedule produced in ten days.

One design caution: "complete" and "legal" are not automatically the same thing, and you have a choice about which constraints to build into the representation and which to penalize in the objective. In 8-queens we usually build the one-queen-per-column constraint into the representation (the state is an array rows[0..7] where rows[c] is the row of the queen in column c), which instantly shrinks the space from C(64,8) ≈ 4.4 × 10^9 to 8^8 ≈ 1.7 × 10^7 and guarantees no two queens share a column. The remaining constraints (rows and diagonals) are handled by the cost function.

Neighbors and Move Operators

A complete-state space is useless without a notion of adjacency. The move operator (also called the neighborhood operator, or the set of local moves) defines, for any state s, the set N(s) of states reachable by a single modification. That set is the neighborhood of s. All of local search consists of inspecting N(s) and choosing where to go next, so the operator is arguably the single most consequential design decision in the whole formulation.

Common operator families:

  • Flip — change one Boolean variable from true to false or vice versa. For a SAT instance with n variables, |N(s)| = n. This is the operator used by WalkSAT and GSAT.
  • Re-assign / shift — change one variable to a different value from its domain. For n-queens with one queen per column, moving a queen to any other row in its column gives |N(s)| = n(n−1): 56 neighbors for 8-queens.
  • Swap / exchange — exchange the positions of two elements. This is the natural operator when the state is a permutation (job sequencing, the travelling salesperson problem, assigning n workers to n tasks) because a swap of two entries in a permutation yields another permutation, keeping the state legal by construction. Here |N(s)| = C(n,2) = n(n−1)/2.
  • 2-opt / segment reversal — in TSP, remove two edges and reconnect the tour the other way, which reverses a contiguous segment. This classic operator preserves tour validity and repairs crossings.
  • Insert / relocate — remove one element and reinsert it elsewhere (e.g., move a job from machine A's queue into machine B's queue at a given position).
  • Continuous step — add a small vector δ to a real-valued state, or take a step along the gradient. Neighborhoods here are infinite, so the "step size" plays the role of neighborhood size.

Three properties determine whether an operator is a good one.

1. Size, and the cost–coverage trade-off. A small neighborhood is cheap to scan but offers few escape routes, so the search gets stuck more often. A large neighborhood explores better but costs more per step. Consider TSP on 100 cities:

OperatorNeighborhood size (n = 100)Cost per full scanTypical effect on quality
Swap two adjacent cities99Very cheapWeak; many poor local optima
Swap any two cities4,950CheapModerate
2-opt (segment reversal)≈ 4,950Cheap (incremental Δ in O(1))Good; typically within ~5% of optimum
3-opt≈ O(n³) ≈ 10⁶ExpensiveBetter; ~3% of optimum
Lin–Kernighan (variable depth)Effectively hugeVery expensive per stepExcellent; ~2% or better

There is no universally right answer; the question is always whether the extra quality per step repays the extra time per step within your compute budget. A useful heuristic: if the search stalls quickly at poor solutions, enlarge the neighborhood; if it crawls, shrink it or sample it rather than scanning it exhaustively.

2. Locality, enabling incremental evaluation. A well-designed operator changes only a small part of the state, so the change in objective value — the delta — can be computed without re-evaluating the whole solution. This single trick often buys an order-of-magnitude speedup, and it is why operators that scramble the state wholesale are bad operators even though they "explore more".

// 8-queens: full evaluation is O(n^2) -- compare every pair
h(s):
    conflicts = 0
    for i in 0..n-1:
        for j in i+1..n-1:
            if rows[i] == rows[j] or |rows[i]-rows[j]| == |i-j|:
                conflicts += 1
    return conflicts

// Incremental evaluation of "move queen in column c from r_old to r_new"
// is O(n): only pairs involving column c can change.
delta(s, c, r_new):
    d = 0
    for j != c:
        if attacks(rows[c], c, rows[j], j): d -= 1      // conflict removed
        if attacks(r_new,   c, rows[j], j): d += 1      // conflict added
    return d

In TSP with 2-opt the saving is even more dramatic: reversing a segment changes only two edges, so Δ = d(a,c) + d(b,d) − d(a,b) − d(c,d) is computed in constant time rather than re-summing all n edge lengths.

3. Connectivity. The operator must make the state space connected — from any start state, some sequence of moves must reach an optimal state. If it does not, entire regions of the space are permanently unreachable and the search may be doomed before it begins. Example: in a permutation problem, the operator "swap positions i and i+2 only" preserves the parity of the permutation, so half of all permutations — possibly including every optimal one — can never be reached. Adjacent-transposition swaps, by contrast, generate the whole symmetric group and are fully connected. Beyond bare connectivity, we also care about the diameter of the space under the operator: if reaching an optimum requires 106 moves because each move is so timid, connectivity is a hollow guarantee.

Objective and Heuristic Cost Functions

The objective function f(s) (for maximization) or heuristic cost function h(s) (for minimization) assigns a number to every state. It is the only signal the search receives — the algorithm has no other way to tell good from bad — so its design determines success or failure far more than the choice of algorithm.

Maximization and minimization are the same problem. Minimizing h is identical to maximizing −h (or 1/(1+h), or C − h for any constant C). Textbook presentations of hill climbing speak of climbing toward peaks; most practical formulations are stated as cost minimization, so the "peak" is the bottom of a valley. Do not let the vocabulary confuse you: convert whichever way you prefer and stay consistent. In this topic we use "uphill" to mean "in the improving direction", whatever the sign convention.

It must be total. The function has to be defined for every complete state, not only for goal states. A goal test that merely answers "yes/no" is useless to local search because it gives no sense of how close a non-goal is. For 8-queens, the standard choice is h(s) = the number of pairs of queens attacking one another, directly or indirectly. This is defined everywhere, equals 0 exactly at a solution, and tells us that a board with 3 conflicts is better than one with 17. Globally, h ranges from 0 to 28 (C(8,2)), and a random board averages around 15 or 16.

It should provide gradient. A good evaluation function changes in small, informative increments as the state changes, so that moves in a promising direction are rewarded immediately. Compare two candidate functions for scheduling:

Candidate functionGranularityUsefulness to local search
"1 if all deadlines met, else 0"BinaryUseless — the landscape is a flat plain with one invisible pinhole
"number of jobs that miss their deadline"Coarse integerSome gradient, but large plateaus: shifting a job from 10 hours late to 1 hour late changes nothing
"total lateness in minutes, summed over jobs"Fine-grainedStrong gradient — every improvement, however small, is visible
"weighted sum: 100 × (deadline misses) + total lateness + 0.1 × (machine switches)"Fine + prioritizedBest — encodes priorities and still discriminates within each priority band

The same principle appears in SAT solving: "number of unsatisfied clauses" gives a usable gradient; "is the formula satisfied?" does not. Coarse or flat functions create plateaus, and plateaus are where local search goes to die (see below). When hard constraints must be respected, a common pattern is the weighted penalty function f(s) = quality(s) + Σ w_i · violation_i(s) with large weights w_i; this allows the search to pass through slightly infeasible states while still being driven strongly back toward feasibility.

It must be cheap. A local search run may evaluate tens of millions of states. If each evaluation costs 10 ms, you get 100 evaluations per second and the algorithm is worthless; if it costs 1 µs, you get a million per second. Hence the emphasis above on incremental evaluation, caching of partial sums, and precomputed lookup tables (e.g., an n × n distance matrix for TSP rather than recomputing Euclidean distances). A rough rule of thumb: the inner loop of a local search should touch only the data the move actually changed.

Beware of the function you did not mean to write. Because local search optimizes exactly what you specify, an objective that ignores something you care about will produce solutions that abuse the omission. If a roster objective penalizes only uncovered shifts, you will get a roster that covers every shift by assigning one exhausted person to fourteen consecutive nights. The objective is the specification.

The State-Space Landscape Metaphor

Combine the three ingredients and a geography emerges. Imagine the set of all states spread out on a horizontal plane, with neighboring states placed next to one another, and the objective value plotted as elevation. The result is a state-space landscape: a surface of hills and hollows. Local search is then a walker on this surface who can see only the elevation of the ground immediately around their feet. Hill climbing is the policy "always step to higher ground; stop when no neighboring ground is higher."

Two definitions follow naturally:

  • A local search algorithm is complete if it is guaranteed to find a goal state whenever one exists.
  • It is optimal if it is guaranteed to find a global maximum (or minimum). Plain hill climbing is neither; random-restart hill climbing is complete "with probability approaching 1" in the limit, because given infinitely many restarts it will eventually start in the basin of a solution.

The metaphor has to be handled with care, because the picture we can draw is a lie of dimensionality. A two-dimensional cross-section with a few bumps is drawn on one axis of state and one of value; a real landscape has one dimension per decision variable. The 8-queens landscape is 8-dimensional (each queen's row), a 10,000-variable SAT instance lives on a 10,000-dimensional Boolean hypercube, and a scheduling problem may have millions of dimensions. High-dimensional spaces behave counter-intuitively: a point that is a maximum along each individual axis need not be a maximum overall; the number of neighbors grows with dimension, so there are many more escape directions than a 2-D picture suggests; and "distance" in such spaces is dominated by the large number of coordinates. Use the picture as an aid to intuition about peaks and plateaus, never as a basis for quantitative claims.

The most useful single descriptor of a landscape is its ruggedness: how many local optima there are, how deep they are relative to the global optimum, and how far apart they lie. A smooth landscape with one broad peak is trivial for hill climbing. A rugged landscape with many isolated peaks of similar height is hard — every run stalls somewhere different. Many real problems have a "big valley" or funnel structure: locally rugged, but with the good local optima clustered near the global optimum, which is precisely why restart- and perturbation-based methods work well in practice. The pathological case is the "golf course" or "needle in a haystack" landscape: a flat plain with a single deep hole, where no gradient exists anywhere and local search degenerates to random sampling. Notice that ruggedness is not a property of the problem alone — it is a property of the problem together with your operator and objective. Changing the move operator literally re-sculpts the terrain, which is why operator design is where practitioners spend their effort.

Landscape Features: Peaks, Valleys, Ridges, Shoulders, and Plateaus

Specific terrain features correspond to specific failure modes, and being able to name them is the first step to fixing them.

  • Global maximum — the highest point in the entire landscape; the optimal solution. There may be several states tied at this value.
  • Local maximum — a state whose value is strictly greater than that of every neighbor, but lower than the global maximum. Simple hill climbing reaching such a state halts, because every available move looks worse. It has no way of knowing that a far better peak lies beyond a dip. This is the canonical failure of hill climbing. In 8-queens with the "move a queen within its column" operator, steepest-ascent hill climbing gets stuck on a local maximum about 86% of the time, solving only about 14% of random instances — but the stuck runs take only ~3 moves on average, while successes take ~4, so restarting is cheap. Roughly 1/0.14 ≈ 7 restarts suffice on average, for about 22 total moves.
  • Plateau — a flat region where all neighbors have equal value. The gradient is zero, so the objective offers no advice at all. The search either halts (if it refuses non-improving moves) or wanders aimlessly (if it allows sideways moves without limit). Plateaus arise most often from coarse-grained objective functions — the fewer distinct values the function can take, the more states must tie.
  • Shoulder — a plateau that is not a local maximum: it has an edge from which uphill progress resumes. A shoulder is a trap only if the algorithm gives up as soon as it sees no strictly improving move. The remedy is to permit sideways moves (moves to an equal-valued neighbor), which allow the walker to cross the flat ground and find the far edge. The cost of this permission is the risk of looping forever on a genuinely flat plateau, so implementations cap the number of consecutive sideways moves. In 8-queens, allowing up to 100 consecutive sideways moves raises the success rate of steepest-ascent hill climbing from about 14% to about 94%, at the price of a higher average move count (~21 per success, ~64 per failure). This single change illustrates how much algorithmic behaviour hinges on recognising a terrain feature.
  • Ridge — a long, narrow sequence of elevated points with steep drop-offs on both sides, oriented diagonally with respect to the available moves. Ridges are the subtlest trap. Imagine a ridge running north-east while your operator permits only single steps north, south, east, or west. From a point on the crest, a step north takes you off the ridge and down; so does a step east. Every single move is downhill, so hill climbing stops — even though a combined north-then-east move would take you higher. A search that is allowed to accept equal or slightly worse moves can still traverse a ridge, but it does so as an awkward zigzag, taking many moves to gain a little height. The real diagnosis is operator mismatch: the moves are axis-aligned and the improving direction is not. Fixes include adding compound moves (change two variables at once), rotating the representation, or using a method that can follow the true gradient direction.
  • Valleys and basins — the minimization-view mirror images of peaks and plateaus. Under a cost function h that we are minimizing, the global optimum is the deepest point of the deepest valley; a local minimum is the bottom of a shallower hollow; a plateau is a flat floor; and a ridge becomes a narrow canyon or trough that the search must follow downhill. The basin of attraction of a local optimum is the set of start states from which hill climbing ends at that optimum. Basins are the quantity that really governs random-restart behaviour: if the global optimum's basin occupies 2% of the space, you expect to need about 50 random restarts to land in it.

The table below links each feature to its symptom and its standard remedy.

Plateau (flat local max)All neighbors equalHalt, or endless aimless wanderingCap sideways moves; add tie-breaking terms to the objective; tabu list to avoid revisiting

States 3–5 form a flat stretch of value 6; because the right-hand edge at state 6 rises to 8, that stretch is a shoulder — a search permitted to move sideways will cross it and reach the global maximum. States 8–11 are also flat, but nothing adjacent rises, so that region is a true plateau and a flat local maximum; sideways moves there merely wander. Reading the same numbers as costs to be minimized inverts the picture: state 7 becomes the worst point and state 0 sits at the bottom of a valley.

Framing a Problem for Local Search

Putting it together, converting a new optimization problem into a local search instance is a five-part design task. Work through the parts in order, and expect to iterate — the parts interact.

  • 1. State representation. Choose a data structure in which every value is a complete, and preferably legal, candidate. Build the easy constraints into the representation so they can never be violated, and leave the hard ones to the objective. Examples: an array of n row indices for n-queens (enforces one queen per column); a permutation of city indices for TSP (enforces "visit each city exactly once"); a bit vector for SAT or knapsack; a vector of (job → machine, start time) pairs for scheduling. Ask yourself: "If I generate a random value of this type, is it a usable answer?" If the answer is no, the representation will force you to spend search effort just reaching feasibility.
  • 2. Move operator. Pick an operator that yields a neighborhood small enough to scan (or sample) quickly, local enough that Δ can be computed incrementally, and rich enough to connect the space. Check connectivity explicitly: can a chain of moves transform any state into any other? For permutations, swaps and 2-opt both qualify; for bit vectors, single-bit flips connect the whole hypercube in at most n moves. Record the neighborhood size as a formula in n so you can predict the cost of one step.
  • 3. Evaluation function. Make it total, fine-grained, and cheap. Prefer summed magnitudes ("total minutes late", "total tour length", "number of attacking pairs") over Boolean or coarse counts. Where several objectives compete, combine them with weights that reflect genuine priorities, giving hard-constraint violations weights large enough that no amount of quality gain can pay for a violation. Sanity-check the function by hand on two or three states you already know to be good and bad.
  • 4. Starting policy. Options are (a) random initialization — cheap, unbiased, and the right default when you intend to restart many times; (b) greedy construction — e.g., nearest-neighbor tour for TSP, or earliest-deadline-first for scheduling, which starts the walker partway up a hill and usually converges faster, though it can bias every run into the same basin; (c) warm start from yesterday's solution, which is ideal for repeated planning problems and often what operations staff actually want (small changes from the previous plan); (d) multiple restarts, keeping the best final state. A practical compromise is greedy construction perturbed randomly, so each restart lands in a different basin while still beginning from a decent value.
  • 5. Termination condition. Stop when any of the following holds: a state of known-optimal value is found (e.g., h = 0 for n-queens, or zero unsatisfied clauses for SAT); a budget of iterations, evaluations, or wall-clock seconds is exhausted; no improvement has been seen for k consecutive steps (stagnation); or the solution is "good enough" against a bound (e.g., within 2% of a known lower bound such as the TSP 1-tree bound). Always retain the best-so-far state separately from the current state, since searches that accept worsening moves may end at a state worse than one they passed through.

Hill Climbing and Its Variants

▶

Hill climbing is the simplest member of a family of algorithms called local search. Where classical search algorithms such as breadth-first search or A* build a tree of partial solutions and reason about paths from an initial state to a goal, local search throws the path away entirely. It keeps a single complete candidate solution in memory, repeatedly tweaks it, and keeps the tweak if it looks better. This apparently crude idea turns out to be one of the most practically important techniques in artificial intelligence and operations research: it is what underlies much of automated scheduling, VLSI layout, telecommunications network design, protein structure prediction, and the configuration of machine-learning models. The discussion below develops the formulation that makes local search possible, the basic hill-climbing loop, and the four standard variants — steepest-ascent, first-choice, stochastic, and random-restart — together with the trade-offs that determine which one to use.

Local search and the complete-state formulation

In an incremental (or constructive) formulation, a state is a partial solution: in the 8-queens problem, a board with between zero and eight queens placed, and an action adds one more queen. The solution is the path of placements. In a complete-state formulation, by contrast, every state is already a full candidate answer — all eight queens are on the board from the very beginning, possibly attacking each other — and the task is not to build a solution but to repair one. Three ingredients define such a formulation:

  • The state representation. A complete configuration that can be written down and evaluated on its own, with no reference to how it was reached. For 8-queens, an array of eight integers [c1 … c8] where ci is the row of the queen in column i; for the travelling salesperson problem (TSP), a permutation of the cities; for a nurse roster, a full assignment of every nurse to every shift in the planning horizon.
  • An objective function f(s) (to be maximised) or a cost function h(s) (to be minimised) that returns a single number measuring the quality of the state. For 8-queens the usual choice is h(s) = the number of pairs of queens attacking each other, directly or indirectly; a solution has h = 0. For TSP, h(s) = total tour length. For a roster, a weighted sum of constraint violations and staff-preference penalties.
  • A neighbourhood (move) operator. The set of states reachable from s by one small modification. For the 8-queens array, "move a single queen to another square in its own column" yields 8 × 7 = 56 neighbours. For TSP, the classic 2-opt move removes two edges and reconnects the tour the other way round, giving roughly n(n−3)/2 neighbours — 4 850 for 100 cities. For a roster, "swap the shifts of two nurses on one day" or "reassign one nurse's single shift".

Because the current state is a complete solution, the algorithm may be stopped at any moment and will still return something usable — a valuable property called anytime behaviour. The memory footprint is tiny: the current state, its value, and at most one candidate neighbour. There is no frontier, no explored set, and no search tree, so memory use is O(size of one state) rather than exponential in depth. This is precisely why local search can attack state spaces that systematic search cannot touch. The 8-queens space has 88 ≈ 16.7 million states; 100-queens has 100100; a 100-city TSP has 99!/2 ≈ 4.7 × 10155 tours. Local search is also meaningful in continuous spaces that are literally infinite — for example, choosing real-valued coordinates for the sites of three airports so as to minimise the sum of squared distances from every city to its nearest airport.

The standard mental picture is the state-space landscape. Imagine the states spread out on a horizontal plane (location = state, with neighbouring states placed near one another) and the objective value plotted as elevation. Maximising f means walking uphill to find the highest peak; minimising h means rolling downhill into the deepest valley. The two views are interchangeable — maximising f = −h is the same as minimising h — and the literature slides freely between "hill climbing", "gradient ascent" and "descent". A perfect landscape would be a single smooth hill; real landscapes are rugged, with many features that trap a purely uphill walker:

Landscape featureDefinitionEffect on a hill climber
Global maximumThe highest point in the whole space; the true optimum.The desired outcome, but never recognisable as such from local information alone.
Local maximumA state better than all its neighbours but worse than the global maximum.The climber halts and returns a suboptimal answer.
Plateau / flat local maximumA connected region of equal-valued states with no uphill neighbour.No improving move exists; the climber halts or, if sideways moves are allowed, may wander indefinitely.
ShoulderA flat region from which progress uphill is still possible after crossing it.Escapable only if sideways (equal-value) moves are permitted, usually with a cap on consecutive sideways moves.
RidgeA sequence of local maxima forming a narrow ascending crest that is not aligned with any single move direction.Every individual move goes down, even though the ridge rises; the climber stalls part-way up.

It is worth stressing that the landscape is defined jointly by the objective function and the move operator. Change the neighbourhood — say from 2-opt to 3-opt in TSP — and the very same states acquire a different set of local optima. Designing a smooth landscape with few spurious peaks is therefore as much a part of problem formulation as choosing the cost function.

The basic hill-climbing loop

Hill climbing, sometimes called greedy local search, is a loop that repeatedly moves to a better neighbour and stops when none exists.

function HILL-CLIMBING(problem) returns a state that is a local maximum
    current <- an initial complete state (random, or built by a heuristic)
    loop do
        neighbour <- a highest-valued successor of current
        if VALUE(neighbour) <= VALUE(current) then return current
        current <- neighbour

Four properties of this loop deserve emphasis.

  • Initialisation matters. The start state may be uniformly random (cheap, unbiased, good for restarts) or produced by a constructive heuristic. For TSP, starting from a nearest-neighbour tour rather than a random permutation typically cuts the number of improving 2-opt moves needed by a large factor and yields a better final tour; the danger is that a clever heuristic start may deposit every run in the same basin of attraction, destroying the diversity that restarts rely on.
  • Evaluation should be incremental. Recomputing h from scratch for every neighbour is usually wasteful. In 8-queens, moving one queen changes only the conflicts involving that queen, so the delta can be computed in O(n) instead of O(n²). In 2-opt TSP, the change in tour length is d(a,c) + d(b,d) − d(a,b) − d(c,d) — four distance lookups, independent of n. Efficient delta evaluation is what makes local search viable on large instances.
  • No memory of the past. Because visited states are not recorded, hill climbing cannot detect that it is revisiting a state; the strict "must improve" test is what guarantees termination, since the objective value increases monotonically and the space is finite.
  • Speed without guarantees. Hill climbing is incomplete: it returns a local maximum, which may be arbitrarily far below the global one. It is also not optimal in any sense. What it offers is extreme speed and tiny memory use, which is often exactly the right trade.

A concrete trace helps. Consider a small one-dimensional landscape in which the states are integers 0–11 and the neighbours of state i are i−1 and i+1:

State01234567891011
f(state)357644468975

Starting at state 0: neighbours of 0 is {1} with value 5 > 3, so move to 1; from 1 the best neighbour is 2 (value 7 > 5), so move to 2; from 2 the neighbours are 1 (5) and 3 (6), both worse than 7 — the algorithm halts and returns state 2 with value 7. The global maximum, state 9 with value 9, is never seen. States 4–6 form a shoulder: a hill climber that lands there finds no improving move, but one sideways step to state 7 would open the route to the real summit. This is why many implementations allow sideways moves (accepting a neighbour of equal value) with a hard limit on the number of consecutive sideways steps, to avoid looping forever on a true plateau.

The canonical empirical benchmark is 8-queens with the 56-successor neighbourhood. Starting from random states, basic steepest-ascent hill climbing solves roughly 14% of instances, taking on average about 4 steps when it succeeds and 3 steps when it gets stuck — so even the failures are extremely cheap compared with the 17 million states in the space. Permitting up to 100 consecutive sideways moves raises the success rate to about 94%, at the cost of about 21 steps per success and 64 per failure. That single modification, which simply lets the search cross shoulders, is the cheapest performance improvement available.

Steepest-ascent hill climbing

Steepest ascent is the version written above: generate all successors, evaluate every one, and move to the best. It is "steepest" in the sense of taking the direction of greatest local improvement, by analogy with gradient ascent in continuous optimisation.

function STEEPEST-ASCENT-STEP(current) returns next state
    best <- current
    for each s in NEIGHBOURS(current) do
        if VALUE(s) > VALUE(best) then best <- s
    return best        // equals current if no neighbour improves
  • Strength: maximal progress per step. Each iteration buys the largest available gain, so the number of iterations to reach a local optimum is typically small — in 8-queens, three or four moves.
  • Weakness: cost per step scales with the branching factor. Every step costs b evaluations, where b is the neighbourhood size. For 8-queens that is 56 — trivial. For 1000-queens it is 999 000 evaluations per move. For a scheduling problem where a state has millions of neighbours, or where evaluating a state requires running a simulation, steepest ascent is simply unaffordable.
  • Weakness: determinism. Given a fixed tie-breaking rule, steepest ascent from a given start always follows exactly the same trajectory to exactly the same local optimum. Re-running it changes nothing. In the small trace above, every run from state 0 ends at state 2. This makes it the variant most reliably trapped, and it means the only way to get diversity is to change the start state.
  • Note on greed. "Steepest" is not "best". The locally largest improvement may lead into a narrow, low peak while a modest improvement would have led to a broad, high one. Greedy choice is a heuristic about the future, not a guarantee.

First-choice hill climbing

First-choice hill climbing generates successors one at a time, in random order, and immediately accepts the first one that is better than the current state.

function FIRST-CHOICE-STEP(current) returns next state
    repeat
        s <- RANDOM-NEIGHBOUR(current)        // sampled without replacement, or just at random
        if VALUE(s) > VALUE(current) then return s
    until a stopping budget is exhausted (e.g. k consecutive failures,
          or all neighbours tried)
    return current                            // declare local optimum
  • Cheap steps. If a fraction p of neighbours are improving, the expected number of evaluations per step is about 1/p, independent of the total neighbourhood size. Early in a run, when the state is poor, improving moves are plentiful and a step may cost two or three evaluations instead of a million. This is the decisive advantage when a state has thousands or millions of successors — for example, local search on a 10 000-city TSP, or on a timetable with 50 000 assignment variables.
  • Smaller gains per step. The accepted move is merely improving, not optimal, so more steps are generally needed. In practice the product (cost per step × number of steps) is usually far lower than steepest ascent's, which is why first-choice is the default in large-scale implementations.
  • Stochastic trajectories. Because the order of successor generation is random, two runs from the same start can diverge immediately and terminate in different local optima. This built-in diversity is valuable: repeating first-choice from one good start can yield several distinct solutions, something steepest ascent can never do.
  • Detecting a local optimum. Strictly, one must try all neighbours before concluding none improves. In practice a budget is used (e.g. "stop after k = 3b consecutive non-improving samples"), which makes the termination test probabilistic rather than exact — an acceptable approximation when b is huge.

Applying first-choice to the 1-D example from state 0 with random neighbour selection: at state 1, the candidate 0 (value 3) is rejected and candidate 2 (value 7) is accepted; at state 2 both candidates fail and the run ends at the same local optimum. In this tiny neighbourhood (b = 2) first-choice saves almost nothing; its value appears only when b is large.

Stochastic hill climbing

Stochastic hill climbing restricts itself to uphill moves — like the other variants, it never knowingly goes downhill — but it does not automatically take the best one. Instead it chooses randomly among the improving neighbours, often with a probability weighted by the size of the improvement.

function STOCHASTIC-STEP(current) returns next state
    U <- { s in NEIGHBOURS(current) : VALUE(s) > VALUE(current) }
    if U is empty then return current
    for each s in U: w(s) <- VALUE(s) - VALUE(current)      // improvement size
    return s drawn from U with probability w(s) / sum of all w

Suppose the current state has value 20 and three improving neighbours A, B, C with values 21, 24 and 30, i.e. improvements of 1, 4 and 10. Steepest ascent takes C with certainty. Proportional stochastic selection takes A with probability 1/15 ≈ 0.07, B with 4/15 ≈ 0.27 and C with 10/15 ≈ 0.67. Large improvements are still strongly preferred, but the search retains the option of a different route. Other weighting schemes are common: uniform choice among improving neighbours (maximum diversity), or a softmax/Boltzmann weighting exp(Δ/T) that can be sharpened or flattened by a temperature parameter T.

  • Slower per-iteration convergence. Because it sometimes takes a small improvement when a large one was available, stochastic hill climbing typically needs more iterations than steepest ascent to reach a local optimum.
  • Better final quality on rugged landscapes. Randomised route selection means the search is not forced down a single deterministic funnel. On landscapes with many shallow peaks surrounding a few deep basins, this wider exploration frequently ends in a better optimum, and repeated runs give a distribution of answers from which the best can be taken.
  • A conceptual bridge. Stochastic hill climbing is the natural stepping stone to simulated annealing. Both randomise the choice of move; the crucial difference is that simulated annealing also accepts downhill moves with probability exp(−ΔE/T), with T lowered on a cooling schedule, which is what lets it escape local optima altogether rather than merely choosing between uphill routes.
  • Cost note. In its full form it still evaluates all neighbours to build the candidate set, so it shares steepest ascent's per-step cost; a cheap hybrid samples a small random subset of neighbours and selects stochastically among the improving ones found there.

Random-restart hill climbing

Random-restart hill climbing is a meta-strategy, not a new move rule. It runs an inner hill climber to completion from a randomly generated start, records the result, and repeats — keeping the best state found across all runs. It embodies the maxim "if at first you don't succeed, try, try again".

function RANDOM-RESTART-HILL-CLIMBING(problem, max_restarts) returns best state
    best <- none
    for i = 1 to max_restarts do
        s <- INNER-HILL-CLIMB(RANDOM-STATE())      // any variant above
        if best = none or VALUE(s) > VALUE(best) then best <- s
        if GOAL-TEST(best) then return best        // optional early exit
    return best

The analysis is simple and attractive. If each independent trial succeeds with probability p, the probability that at least one of n trials succeeds is 1 − (1 − p)^n, which tends to 1 as n grows; hence random-restart hill climbing is complete with probability approaching 1, for the trivial reason that it will eventually generate a goal state as a starting state. The expected number of trials until the first success is 1/p, so the expected total work is (1/p) × (cost of one trial) — roughly one successful run plus (1/p) − 1 failed runs.

The same technique scales startlingly well: random-restart hill climbing with the min-conflicts heuristic solves the 3 000 000-queens problem in well under a minute, because for large n the landscape has very few local optima relative to its size.

  • Independence is the point. Restarts share no information, which is both the weakness (nothing is learned from a failed run) and the strength: the trials are statistically independent, so the failure probabilitydecays geometrically rather than linearly.
  • Trivially parallelisable. Because no run depends on another, n restarts can be farmed out to n cores, machines or GPU threads with no synchronisation, no shared memory and no communication beyond reporting the final value. Few search algorithms parallelise so cleanly: wall-clock time falls almost linearly with the number of processors.
  • Cost grows linearly with restarts. Total work is (number of restarts) × (cost of one climb), so the strategy only pays when p is not vanishingly small. If p = 10−6, the expected million trials may be far more expensive than a single run of simulated annealing or a genetic algorithm. In practice a budget is imposed — a fixed max_restarts, a wall-clock deadline, or a stagnation rule such as "stop after 50 consecutive restarts that fail to improve the incumbent".
  • Diversity of starts matters. Uniformly random starts give independent samples of the basins of attraction. Starts produced by a strong deterministic heuristic may all land in the same basin, which destroys the statistical argument; randomised construction (e.g. a nearest-neighbour tour from a random city, or a greedy choice perturbed by noise, as in GRASP) is the usual compromise between quality and diversity.
  • When the goal is unknown. For optimisation problems with no recognisable "goal test" (TSP, scheduling), there is no early exit; one simply runs the budget out and returns the best incumbent. The incumbent value typically improves rapidly over the first few restarts and then plateaus, a diminishing-returns curve that itself suggests when to stop.

Several conclusions follow from this comparison.

  • Per-step power versus per-step price. Steepest ascent maximises progress per move but pays b evaluations to get it; first-choice pays about 1/p evaluations for a weaker move. The right choice depends entirely on b and on the cost of evaluating a state. With b = 56 (8-queens) the full scan is free and steepest ascent is sensible; with b in the millions, or when each evaluation requires a discrete-event simulation, first-choice wins by orders of magnitude.
  • Determinism is a liability. Steepest ascent's single trajectory means that repeating the run from the same start is pointless. First-choice and stochastic hill climbing both break that determinism internally, so repetition yields diversity even without restarts.
  • Randomness buys quality, not speed. Stochastic hill climbing almost always needs more iterations than steepest ascent, yet often terminates higher, because it is not funnelled into whichever peak the greedy rule happens to point at. On smooth, unimodal landscapes this extra wandering is pure overhead; on rugged ones it is where the benefit lies.
  • Random restart composes with everything. It is an outer wrapper, so one may run restarts around steepest ascent, around first-choice, or around stochastic hill climbing — and the inner choice should be made on cost grounds while the outer restart count is set by the time budget. Given a fixed budget it is usually better to run many cheap, imperfect climbs than one exhaustive, expensive one.
  • None of them is complete on its own. Steepest-ascent, first-choice and stochastic hill climbing all share the defining restriction that no downhill move is ever accepted. Consequently each terminates at the first local optimum (or plateau) it meets and has no mechanism whatsoever for leaving it. Only two remedies exist: start somewhere else (random restart, which abandons the trapped state) or allow the search to go downhill under controlled conditions (simulated annealing's exp(−ΔE/T) acceptance, tabu search's memory-guided non-improving moves, or local beam and genetic algorithms' populations). Sideways moves help with shoulders but not with genuine local maxima, and they introduce the risk of infinite looping on plateaus unless capped.
  • Practical recipe. A sound default for a large real problem is: a complete-state representation with cheap delta evaluation, a first-choice inner climber with a capped number of sideways moves, wrapped in random restarts across all available cores, with the best incumbent reported at the deadline. If this plateaus well short of acceptable quality, the next step is to accept downhill moves (simulated annealing) or to enrich the neighbourhood operator rather than to scan the existing one more thoroughly.

Most of the search methods you have seen so far build a path from a start state to a goal, keeping track of everything explored along the way. Local search works differently: it starts from a complete candidate solution — a full assignment such as all eight queens already placed on the board — and repeatedly tweaks it using a move operator, judging each candidate by an objective function. Because only the current state (and sometimes a few neighbors) is kept in memory, local search scales to very large problems where systematic search is hopeless.

Hill climbing is the simplest local search strategy: look at the neighbors of the current state, move to one that is better, and stop when no neighbor improves. That greedy loop is fast but short-sighted — it gets stuck on local maxima, wanders on plateaus, and struggles along ridges. The variants in this topic are all attempts to patch those weaknesses: steepest-ascent evaluates all neighbors and takes the best, first-choice generates neighbors at random and takes the first improvement, stochastic hill climbing picks among uphill moves with probability weighted by steepness, and random-restart simply runs hill climbing many times from different random starting points.

Second, how does the algorithm decide which neighbor to move to, and how is that decision different across the variants? Third, what happens when no neighbor is better — does the algorithm stop, restart, or accept a sideways move? Being able to answer these for any given landscape is the core skill this topic builds toward.

Local Maxima, Plateaus, and Ridges

▶

Local search abandons the idea of building a solution step by step along a path. Instead it keeps a single complete state — an entire candidate solution, however bad — and repeatedly nudges it into a neighbouring state in the hope of improving some measure of quality. This design buys enormous savings in memory (one state, not a frontier of partial paths) and makes it possible to attack problems whose state spaces are astronomically large. The price is that the search becomes blind: it can only compare the current state with states reachable by one move, and therefore has no global map of the terrain it is crossing. The characteristic failure modes of hill climbing — local maxima, plateaus, shoulders, and ridges — are all direct consequences of this blindness, and the standard remedies all amount to buying back, in one way or another, a little of the information that was given up.

The local search landscape. It is useful to picture the search space as a physical surface. Every point on that surface is one complete state: a full assignment of a queen to every column of a chessboard, a complete timetable for every class in a school, a complete tour visiting every city. The height of the point is the number produced by the objective function (for maximisation) or the heuristic cost function (for minimisation). The horizontal axes are a schematic stand-in for the move structure: two points are "adjacent" on the landscape if one move of the neighbourhood operator converts one into the other. A landscape is therefore defined jointly by three things — the state representation, the move operator, and the evaluation function — and changing any of them changes the shape of the surface. The same problem can have a cratered, treacherous landscape under one operator and a smooth, almost convex landscape under another.

Within this picture, a global maximum is the highest peak anywhere on the surface; reaching it means the algorithm has found an optimal solution. For a satisfaction problem such as 8-queens with the usual heuristic h = number of pairs of queens attacking each other, the global optimum is the flat ceiling at h = 0; for an optimisation problem such as the travelling salesperson problem, the global optimum is the single shortest tour (or the set of tours tied for shortest). The distinction matters because satisfaction problems often have many global optima scattered across the landscape, which makes them easier to hit by chance, while a genuine optimisation problem may have exactly one.

Hill climbing perceives none of this. At each iteration it evaluates only the states one move away, picks a better one, and moves. The classical metaphor is a climber in dense fog with amnesia: the fog means only the immediate neighbourhood is visible, and the amnesia means no record is kept of where the climber has already been. Both halves matter. Fog alone would still allow a systematic sweep; amnesia alone would still allow long-range vision. Together they mean the algorithm's entire fate is decided by local gradient information — the direction in which the terrain happens to rise at the current point. If the terrain stops rising, the climber stops, whether standing on Everest or on an anthill.

function HILL-CLIMBING(problem) returns a state
    current <- problem.INITIAL-STATE          // a complete, usually random, state
    loop do
        neighbour <- highest-valued successor of current
        if VALUE(neighbour) <= VALUE(current) then
            return current                     // no uphill move: stop here
        current <- neighbour

Note what is absent from this pseudocode: there is no visited set, no queue, no backtracking and no record of the best state ever seen. The single line if VALUE(neighbour) <= VALUE(current) then return current is the source of every difficulty discussed below.

Local maxima. A local maximum is a state that is higher than every one of its neighbours but lower than the global maximum. When hill climbing arrives at such a state, the loop condition fires and the algorithm halts, returning a suboptimal answer. Crucially, it returns that answer with complete confidence and no indication whatsoever that something better exists: from inside the algorithm, a local maximum and the global maximum are indistinguishable, because both look like "a state no neighbour improves on". Unless the problem supplies an external test (for example, "a solution is only acceptable if h = 0"), the caller cannot tell whether the result is optimal.

Local maxima are, empirically, the single most common cause of hill-climbing failure. The standard illustration is 8-queens with the "move one queen within its column" operator. Each state has 8 × 7 = 56 successors. Starting from random states, steepest-ascent hill climbing solves only about 14% of instances; the remaining 86% of runs get stuck, the overwhelming majority of them on local maxima rather than on flat regions. A typical stuck state has h = 1 — a single attacking pair — yet every one of the 56 single-queen moves either leaves h at 1 or raises it. The fix requires moving two queens at once, which is outside the neighbourhood, so the algorithm is genuinely trapped. On the positive side, the runs are cheap: successful runs average about 4 steps and failures about 3, so each attempt costs almost nothing.

The depth of the valleys surrounding a peak determines how hard it is to escape. If the neighbours of a local maximum are only slightly worse, a method that occasionally tolerates a small loss (simulated annealing at a moderate temperature, or a sideways/worsening move) will slip out quickly. If the peak is an isolated needle surrounded by a deep moat — a situation sometimes called a "golf-hole" landscape — then any perturbation large enough to leave the peak lands far down the slope, and the search effectively restarts. This is why escaping a true local maximum always requires accepting a temporarily worse state, something pure greedy search is by definition forbidden to do. Every escape mechanism in the rest of this topic is a disciplined way of relaxing that prohibition: randomised acceptance (annealing), forced acceptance through prohibition of the best move (tabu), or discarding the state entirely (restart).

Plateaus and shoulders. A plateau is a flat region of the landscape: a connected set of states all having the same objective value. Two very different situations hide under this one name, and telling them apart is the whole point:

  • A flat local maximum is a plateau with no uphill exit anywhere along its boundary. Every state outside the plateau that is reachable in one move is strictly worse. Progress by local moves is impossible; the only way out is a restart or a large perturbation.
  • A shoulder is a plateau that does have an uphill exit somewhere along its edge. The terrain is flat for a while and then resumes climbing. Here persistence genuinely pays off: if the search is willing to wander across the flat region long enough, it will eventually reach the lip and continue upward.

Strict hill climbing, as written above, halts on both kinds of plateau, because VALUE(neighbour) <= VALUE(current) is true when the values are equal. It thus throws away all shoulders along with all flat maxima — a severe loss, since shoulders are extremely common in combinatorial problems where the objective is integer-valued and coarse-grained (counts of conflicts, counts of violated constraints, numbers of satisfied clauses). In such problems huge numbers of distinct states share the same score, so plateaus are the norm rather than the exception.

The obvious remedy, allowing moves to equal-valued neighbours, introduces its own hazard. Because the algorithm has no memory, a random walk across a plateau can revisit states indefinitely. On a plateau of n states, an unbiased random walk needs on the order of n² moves to cross a one-dimensional strip, and the search may consume an enormous amount of time with the objective function never changing by so much as a single unit. Worse, on a flat local maximum this wandering can never succeed, so the time is wholly wasted. The practical answer is to allow sideways movement but to bound it, which leads to the next subtopic.

Ridges and zig-zagging. A ridge is a long, narrow, rising structure whose crest is sharp relative to the moves available. The defining feature is a mismatch between the orientation of the ridge and the directions the operator can move in. Suppose a continuous problem allows only axis-parallel steps (change x, or change y, but not both) while the ridge runs diagonally. Standing exactly on the crest, a step in x alone takes you off the crest and downhill; a step in y alone does the same. Every individual move is a loss, so steepest-ascent sees no improving step and stops — even though the terrain plainly rises if you walk along the diagonal.

If the steps are small enough that an off-crest move still lands slightly higher than where you started, the behaviour is different but barely better: the search zig-zags, alternating x and y steps and crawling up the ridge in a staircase of tiny net gains. Each gain costs a full round of neighbour evaluations, so the number of objective-function calls explodes while progress is minimal. Consider the function f(x, y) = -(x - y)² - 0.01(x + y - 10)², whose ridge runs along the line x = y. From the point (3, 3) a unit step in either coordinate alone immediately incurs the large -(x - y)² penalty, while the diagonal move to (4, 4) improves the objective. An axis-parallel operator simply cannot see the improvement.

Ridges are especially common in continuous optimisation when the variables are strongly correlated — that is, when the Hessian of the objective is ill-conditioned and its contours are long thin ellipses tilted with respect to the coordinate axes. Rosenbrock's banana function is the textbook example. Three families of remedy exist:

  • Compound or larger neighbourhoods. If the operator can change two variables simultaneously, or swap two assignments rather than reassign one, it may cut across the ridge in a single move. In 8-queens, a "swap the rows of two queens" operator reaches states that the single-queen operator cannot, flattening some of the landscape's worst features. The trade-off is cost: a k-variable compound neighbourhood grows combinatorially, so each step becomes much more expensive to evaluate.
  • Re-orienting the moves. Pattern search, Rosenbrock's method and conjugate-direction methods adapt the step directions to align with the ridge; gradient-based methods with momentum or second-order curvature information do the same thing analytically.
  • Re-representing the problem. A change of variables that decorrelates the dimensions converts the tilted ellipse into a circle and dissolves the ridge altogether. This is the deepest fix but requires insight into the problem structure.

Sideways moves and bounded persistence. Allowing sideways moves means permitting a transition to a neighbour of equal value. The modified acceptance test becomes if VALUE(neighbour) < VALUE(current) then return current — strictly less, rather than less-or-equal. This single character change lets the search traverse shoulders and resume climbing on the far side.

Without a limit, however, the algorithm can loop forever on a flat local maximum, drifting among equal-valued states that never lead anywhere. The standard implementation therefore caps the number of consecutive non-improving moves; the counter resets to zero whenever a strictly better state is found and the run is declared a failure when the cap is reached. The cap is a tuning parameter trading computation against coverage.

Variant on random 8-queens instancesSuccess rateAverage steps (success)Average steps (failure)

Sideways moves buy a substantially higher success rate with additional computation time, which is usually an excellent trade when evaluating a state is cheap.

What sideways moves do not do is escape a true local maximum. If every neighbour is strictly lower, there is no equal-valued state to move to, the counter never even starts, and the algorithm halts exactly as before. Sideways moves are a cure for flatness, not for peakedness — a distinction worth remembering when diagnosing why a particular search is underperforming. If a profiler shows runs terminating after very few steps with no sideways moves used, the landscape is peaked and restarts or annealing are needed; if runs terminate at the sideways-move cap, the landscape is flat and a larger cap or a plateau-aware operator may help.

Random restarts and stochastic variants. The simplest and often the most effective response to a trap is to leave the landscape entirely and start again somewhere else.

  • Random-restart hill climbing runs hill climbing from a randomly generated initial state, keeps the best result found, and repeats until a goal is found or a budget is exhausted. It is trivially complete in the limit: since initial states are drawn at random from the whole space, the generator will eventually produce a goal state (or a state in the goal's basin of attraction) with probability approaching one. If a single run succeeds with probability p, the expected number of runs needed is 1/p and the expected total cost is one successful run plus (1-p)/p failed ones. For 8-queens without sideways moves, p ≈ 0.14, so about 7 runs are needed — roughly 4 + 6 × 3 ≈ 22 steps in total, which is trivial. With sideways moves, p ≈ 0.94 and about 1.06 runs suffice.
  • Stochastic hill climbing does not automatically take the steepest ascent. It chooses at random among the uphill neighbours, with probability weighted by the steepness of the improvement. Because it sometimes takes a gentler slope, it converges more slowly than steepest ascent, but it explores a wider variety of trajectories and in many landscapes converges to better optima — the steepest local gradient is frequently the one that leads into the nearest mediocre peak.
  • First-choice hill climbing implements stochastic hill climbing for states with enormous branching factors. Instead of enumerating all successors, it generates them one at a time in random order and moves to the first one that improves on the current state. When a state has thousands or millions of neighbours, evaluating them all for one step is prohibitive, and first-choice gets a usable move after only a handful of evaluations.

Restarts are also embarrassingly parallel: independent runs share no state, so k processors deliver very nearly a k-fold speed-up with trivial coordination (each worker reports its best state; the controller keeps the maximum). They compose freely with every other variant — one can run random-restart first-choice hill climbing with bounded sideways moves, or restart simulated annealing with different seeds — which is why restarts are usually the first enhancement added to any local search implementation. The main caveat is that restarts discard all accumulated information; on problems where good solutions share common structure, a biased or perturbation-based restart (as in iterated local search, which restarts from a kicked version of the incumbent rather than from scratch) typically outperforms uniform random restarting.

Tabu search and memory-based escape. Tabu search attacks the amnesia directly. The algorithm always moves to the best neighbour even when that neighbour is worse than the current state, and prevents the resulting cycling by maintaining a tabu list: a short, fixed-length memory of recently performed moves, or of attributes of recently visited states (for example, "queen 5 was moved out of row 3", or "edge (c, d) was removed from the tour"). Moves that would reverse a tabu attribute are forbidden for as long as it stays on the list.

function TABU-SEARCH(problem, tenure, max-iterations) returns a state
    current <- problem.INITIAL-STATE
    best    <- current
    tabu    <- empty list
    for i = 1 to max-iterations do
        candidates <- { s in NEIGHBOURS(current) :
                        move(current, s) not tabu
                        or VALUE(s) > VALUE(best) }      // aspiration criterion
        current <- argmax VALUE over candidates           // may be worse than current
        push move(current) onto tabu; if length(tabu) > tenure then pop oldest
        if VALUE(current) > VALUE(best) then best <- current
    return best

The mechanism is elegant. On reaching a local maximum, every neighbour is worse; the algorithm nevertheless steps down to the least-bad one. Pure greedy search would immediately step back up to the peak, oscillating forever — but the upward move is now tabu, so the search is compelled to keep walking, descending one side of the peak until it finds a route up a different slope. Prohibiting backtracking is what converts a tolerance for worsening moves into actual escape.

The tabu tenure — how many iterations an attribute stays forbidden — is the key tuning parameter, and the trade-off is sharp:

Tenure settingEffect on searchTypical symptom
Too shortRecently reversed moves become legal again before the search has left the basinCycling: the same small set of states is revisited indefinitely
Well chosenEnough prohibition to leave a basin, enough freedom to exploit a promising regionSteady improvement of the incumbent best, with visible descents and recoveries
Too longLarge parts of the neighbourhood are forbidden at every stepOver-constrained search: the candidate set empties, moves become arbitrary, quality stalls

A tenure on the order of the square root of the neighbourhood size is a common starting heuristic, and reactive tabu search adjusts the tenure automatically, lengthening it when repetition is detected and shortening it when the search appears over-constrained. The aspiration criterion shown in the pseudocode is a standard safeguard: a tabu move is permitted anyway if it would yield a state better than any seen so far, since the prohibition exists to prevent cycling, not to prevent progress. Richer schemes add long-term memory: frequency counts that penalise moves used often (diversification, pushing the search into unexplored regions) and elite-solution pools that restart from previously good states (intensification).

Finally, memory-based and randomised escape mechanisms are complements rather than rivals. Simulated annealing escapes by probabilistically accepting downhill moves according to a temperature that falls over time; tabu search escapes by deterministically forbidding recently used moves. Annealing needs no memory but requires a well-tuned cooling schedule and may accept pointless downhill moves; tabu search needs no temperature but requires memory structures and tenure tuning. Hybrids are routine — for example, annealing with a short tabu list to suppress immediate reversals, or tabu search with randomised candidate-list sampling in the style of first-choice hill climbing. Choosing among them is an engineering decision driven by the shape of the landscape, the cost of evaluating a state, and the computational budget available.

Local search algorithms such as hill climbing move through a space of complete states, repeatedly stepping to a neighboring state that looks better according to an objective function. It helps to picture this as walking across a landscape where height represents objective value: the algorithm always steps uphill, and it stops when no neighbor is higher. That simple rule is fast and memory-efficient, but it is also short-sighted, and the shape of the landscape determines whether it succeeds or fails.

This topic catalogs the characteristic ways greedy local search gets stuck. A local maximum is a peak that is higher than everything adjacent but lower than the global optimum, so the search halts prematurely. A plateau is a flat region where all neighbors score the same, giving no gradient to follow; a shoulder is a plateau with an uphill exit somewhere, which makes limited sideways moves worthwhile. A ridge is a sequence of local maxima arranged so that no single move operator climbs it directly, causing the search to zig-zag slowly or stall. The standard remedies follow from these diagnoses: allow a bounded number of sideways moves, inject randomness through stochastic or first-choice selection, use random restarts to sample many basins of attraction, or keep a tabu list of recently visited states so the search is forced into new territory.

Simulated Annealing and Cooling Schedules

▶

Simulated annealing is the best known member of the family of stochastic local search algorithms. Like hill climbing, it keeps a single complete-state candidate in memory and repeatedly replaces it with a neighbour produced by a move operator. Unlike hill climbing, it is willing — under carefully controlled circumstances — to move to a worse state. That single change in policy transforms a fast but short-sighted optimiser into a method that can climb out of shallow local optima and still converge on a high-quality answer. The algorithm takes its name and its mathematics from metallurgy: annealing is the process of heating a metal or glass until its atoms become highly mobile and then cooling it slowly so that the atoms settle into a low-energy, highly ordered crystalline structure. Cool it too fast (quenching) and the material freezes into a defect-ridden, high-energy configuration. Simulated annealing treats an objective function as an energy landscape and applies exactly the same idea to search.

Motivation: escaping local optima. To see why the method exists, consider the two extremes it sits between. Pure hill climbing accepts a successor only if it strictly improves the objective. This makes each step cheap and the overall trajectory strongly directed, but it also means the search stops the moment it reaches any state whose neighbours are all worse — a local maximum, or the flat edge of a plateau. Hill climbing is therefore incomplete: it may terminate arbitrarily far from the global optimum and has no mechanism for recognising or repairing that failure. On random 8-queens instances, steepest-ascent hill climbing solves only around 14% of instances from a random start, getting stuck the rest of the time after a handful of steps.

At the opposite extreme, a pure random walk ignores the objective entirely and moves to a uniformly chosen neighbour every iteration. Because the walk can eventually reach any state reachable under the move operator, it is complete in the limit — given infinite time it will visit a global optimum with probability 1. But it is hopelessly inefficient: it discards every piece of information the objective function offers and wanders the landscape essentially blind, so the expected time to stumble on a good state grows explosively with problem size.

Simulated annealing blends the two behaviours and, crucially, shifts the blend over time. Early in the run the algorithm behaves much like a random walk: almost every proposed move is accepted, so the search diffuses widely across the landscape and is not captured by the first shallow basin it encounters. As the run progresses the random component is progressively suppressed and the search becomes increasingly greedy, refining its position within whichever broad region it has settled into. The intuition is to spend the early budget finding the right valley and the later budget finding the bottom of that valley.

  • Energy-landscape view. If we are minimising, we call the objective the energy E and we want the deepest valley; if we are maximising (as in n-queens scored by non-attacking pairs, or a profit function), we want the highest peak. The two formulations are equivalent — set E = -objective — and the literature uses both. What matters is that the acceptance rule is always expressed in terms of "how much worse the candidate is".
  • Why shallow basins are escapable. A shallow local optimum is one surrounded by a low barrier: leaving it requires only a small sacrifice in objective value. The acceptance rule makes small sacrifices cheap, so the search leaks out of shallow basins quickly while tending to remain inside deep ones, where escape would require a large sacrifice.
  • Ping-pong ball analogy. Imagine a ball bouncing on a bumpy surface. Shake the surface hard and the ball is thrown out of every small dimple; shake gently and it settles into the deepest nearby basin. Annealing is the policy of shaking hard first and then reducing the shaking to zero.

The algorithm. The control loop is remarkably short. On each iteration, the current temperature is read from a cooling schedule, one random neighbour is generated, the change in objective is evaluated, and a probabilistic accept/reject decision is made.

function SIMULATED-ANNEALING(problem, schedule) returns a state
    current  <- problem.INITIAL-STATE          // random or heuristically seeded
    best     <- current                        // always track the best seen
    for t = 1 to infinity do
        T <- schedule(t)                       // temperature for this iteration
        if T <= T_min or budget exhausted then
            return best
        next  <- a randomly selected successor of current     // ONE neighbour only
        dE    <- VALUE(next) - VALUE(current)                 // maximisation convention
        if dE > 0 then
            current <- next                    // improving move: always accept
        else
            with probability exp(dE / T): current <- next     // worsening move
        if VALUE(current) > VALUE(best) then
            best <- current
    return best

Several design decisions in this loop deserve emphasis:

  • One successor per iteration. Steepest-ascent hill climbing enumerates and evaluates all neighbours before moving; in 8-queens that is 56 successors per step, and in a 1000-city tour with 2-opt moves it is roughly 500,000. Simulated annealing samples a single neighbour uniformly at random, so each iteration costs O(1) move generation plus one objective evaluation. This is why annealing can afford hundreds of thousands or millions of iterations.
  • Incremental evaluation. In practice dE is almost never computed by scoring both states from scratch. For a 2-opt move on a tour, dE is the sum of two removed edge lengths minus two added edge lengths — four distance lookups regardless of tour length. For n-queens, moving one queen within its column changes only the conflicts involving that queen. Fast delta evaluation is usually the single most important implementation optimisation.
  • Improving moves are free. Since exp(dE/T) > 1 whenever dE > 0, the single expression "accept with probability min(1, exp(dE/T))" covers both branches, which is how the rule is usually stated formally.
  • Termination. The loop ends when the schedule drives T to (or below) a stopping temperature, when a wall-clock or iteration budget is exhausted, when the objective reaches a known optimum, or when no move has been accepted for many consecutive iterations (the system has "frozen").
  • Return the best, not the last. Because the walk can accept worsening moves at any time, the final state is not guaranteed to be the best state visited. Maintaining best costs one comparison per iteration and makes the algorithm a genuine anytime method: it can be interrupted at any point and will return the best solution found so far.

The Metropolis acceptance criterion. The probabilistic rule P(accept) = exp(ΔE / T) for ΔE < 0 comes from the Metropolis–Hastings algorithm in statistical physics, where it samples states in proportion to the Boltzmann distribution exp(-E / kT). Its behaviour is controlled by the ratio |ΔE| / T, and two separate monotonic effects follow:

  • Worse moves are exponentially less likely. Holding T fixed, doubling the damage |ΔE| squares the (sub-1) acceptance probability. The search therefore makes small concessions readily but almost never destroys a good solution in one catastrophic step. This is the property that keeps annealing "mostly greedy" even while it is stochastic.
  • Cooling suppresses all worsening moves. Holding |ΔE| fixed, as T → 0 the exponent ΔE/T → -∞ and the probability tends to 0; as T → ∞ the exponent tends to 0 and the probability tends to 1.

Iteration 3 shows the protective effect of the exponential — a six-point collapse is rejected with high probability. Iteration 2 also illustrates why best must be tracked separately: after accepting the worsening move the current state is no longer the best one seen.

The cooling schedule. The schedule is the function schedule(t) that maps iteration number to temperature, and it is where most of the tuning effort goes. Three parameters define it: the initial temperature T₀, the decay rule, and the stopping temperature T_min (together with the number of iterations spent at each temperature level, if the schedule is stepped rather than continuous).

Geometric cooling dominates practice because it is a single multiplication per step and its total length is easy to compute. With T₀ = 100, T_min = 0.01 and α = 0.95, the number of cooling steps is ln(T_min/T₀) / ln(α) = ln(0.0001)/ln(0.95) ≈ −9.21/−0.0513 ≈ 180. Change α to 0.99 and the same temperature range takes about 916 steps; α = 0.999 takes about 9,200. If each temperature level runs L = 1000 proposals, those become 180,000, 916,000 and 9.2 million objective evaluations respectively — so α is really a direct control over the computational budget.

The two failure modes are symmetric and both are easy to diagnose from the acceptance-rate trace:

  • Cooling too fast ("quenching"). The temperature collapses before the search has had time to traverse the landscape, so the method freezes into whatever basin it happened to occupy. The symptom is an acceptance rate that falls from high to near zero within a small fraction of the run, followed by a long tail during which the objective never changes. The result is typically no better — and sometimes worse, because of wasted early randomness — than plain hill climbing.
  • Cooling too slowly. The temperature stays high for most of the budget, so the search spends its iterations on an undirected random walk and only begins to exploit when the budget is nearly gone. The symptom is an acceptance rate that remains above roughly 50% for most of the run and a best-so-far curve that barely improves. The solution quality is poor not because the search is trapped but because it never committed.

Calibrating the initial temperature. A principled and widely used heuristic is to choose T₀ so that the initial acceptance ratio χ₀ is about 0.8–0.9 — hot enough that the landscape is essentially flat to the search, but not so hot that iterations are wasted. The procedure is: run a short warm-up of random moves, record the mean worsening magnitude ΔĒ⁻, and solve χ₀ = exp(−ΔĒ⁻ / T₀) for T₀:

T0 = -dE_mean / ln(chi0)

e.g. dE_mean = 12.4 (average damage of a worsening move), chi0 = 0.85
     T0 = -12.4 / ln(0.85) = 12.4 / 0.1625 = 76.3

The symmetric rule for the stopping temperature is to pick T_min so that even the smallest meaningful worsening move is accepted with negligible probability — e.g. if the smallest nonzero |ΔE| is 1 and we want that accepted less than once in a thousand attempts, T_min < 1 / ln(1000) ≈ 0.145. Below that point the algorithm is doing stochastic hill climbing and further cooling buys nothing. An adaptive variant monitors the acceptance ratio each level and tightens or relaxes α to keep the ratio following a target decay curve, which largely removes the need to hand-tune T₀.

Reheating and restarts. If the acceptance rate has been near zero for many iterations and the best-so-far value has not improved, the search has frozen. Two remedies are common: reheating (reset T to some fraction of T₀ and cool again, optionally restarting from best rather than current), and restarting (begin a fresh run from a new random state). Reheating preserves the work already done and is well suited to landscapes with large basins; restarting samples a genuinely independent region and is better when the landscape has many comparably sized basins.

Convergence guarantees. There is a genuine theoretical result behind simulated annealing, and it is important to state it precisely because it is routinely overclaimed. Modelling the search as an inhomogeneous Markov chain, Geman and Geman (1984) proved that if the temperature at iteration k satisfies Tk ≥ c / log(k + 1) for a constant c at least as large as the depth of the deepest local optimum, then the probability that the current state is a global optimum tends to 1 as k → ∞. The intuition is that at any fixed temperature the chain's stationary distribution is Boltzmann, π(s) ∝ exp(E(s)/T), which concentrates ever more sharply on the global optima as T shrinks; cooling slowly enough lets the chain re-equilibrate after every temperature reduction so that it tracks that distribution all the way down.

The catch is the logarithm. Inverting T_k = c / log(k+1), reaching a temperature of T requires k ≈ exp(c/T) iterations. With c = 100, cooling to T = 10 needs e¹⁰ ≈ 22,000 iterations, to T = 5 needs e²⁰ ≈ 4.9 × 10⁸, and to T = 1 needs e¹⁰⁰ ≈ 2.7 × 10⁴³ — vastly more than exhaustively enumerating most finite state spaces. The guarantee is therefore of theoretical interest only; a logarithmic schedule is not a practical algorithm, it is an existence proof.

  • Every real implementation uses a geometric or adaptive schedule, which cools exponentially faster than the proof requires and consequently forfeits the guarantee. Simulated annealing as deployed is a heuristic: it is neither complete nor optimal, and on any given run it may return a local optimum.
  • It is judged instead on empirical grounds — the quality of solutions obtained per unit of CPU time, measured acrossbenchmark instance families against known optima or against the best results from competing methods.
  • Because it keeps the best state seen, it behaves as a high-quality anytime algorithm: the best-so-far value rises steeply early and then flattens, so a run can be truncated whenever the marginal improvement per second drops below what the application is willing to pay for.
  • The standard practical safeguard is to run multiple independent anneals — different random seeds, different initial states, sometimes different schedules — and return the best result across all of them. Because the runs are completely independent they parallelise perfectly across cores or machines. For a fixed total budget there is a real trade-off: many short anneals sample more basins but quench each one, while a few long anneals explore fewer basins more thoroughly. A common compromise for a budget of N evaluations is 5–10 runs of N/5 to N/10 each.
  • Reporting a single best-of-many number hides variance, so empirical studies normally report the mean, standard deviation and best over (say) 30 runs, together with the time per run.

Practical use and comparison. The engineering appeal of simulated annealing is how little it demands of the problem. There is no requirement for the objective to be differentiable, continuous, convex, or even cheap to compute exactly; there is no requirement for the state space to have any algebraic structure. Three ingredients suffice:

  • A state representation that encodes a complete candidate solution — a permutation of cities, an assignment of one queen per column, a mapping of lectures to room/time slots, a vector of component coordinates on a chip.
  • A move operator that generates a random neighbour. Good operators make small, local perturbations (swap two cities, reverse a tour segment, move one queen one square, reassign one exam) so that most proposals produce small |ΔE| values and the acceptance rule has fine-grained control.
  • An objective function (energy) that scores a complete state, ideally with an incremental form so that ΔE can be computed in constant or near-constant time.

Memory use is O(1) in the size of the search space: the algorithm stores the current state, the candidate successor, and optionally the best state seen — three solutions, regardless of how astronomically large the state space is. This is the decisive advantage over systematic methods such as A* or branch-and-bound, whose frontiers and open lists grow with the explored portion of the space. A 10,000-city TSP has 9999!/2 tours; annealing holds three of them.

Where annealing earns its keep is on rugged landscapes — objective surfaces riddled with local optima, plateaus and ridges, where hill climbing's trajectory terminates almost immediately. Classic successful applications include VLSI cell placement and routing, where it was the industry standard for years; travelling-salesman and vehicle-routing problems using 2-opt or Or-opt neighbourhoods; university examination and nurse-rostering timetabling with weighted soft-constraint objectives; graph partitioning and image reconstruction. On a smooth, single-basin landscape, by contrast, annealing is simply a slower hill climber: all the early randomness is wasted, and a deterministic gradient-style method will beat it comfortably.

Its weaknesses are equally clear. Performance is sensitive to tuning: the same code with α = 0.99 versus α = 0.8, or with a swap neighbourhood versus a segment-reversal neighbourhood, can differ by a large margin in solution quality. Poor neighbourhood design is the more common failure — if a single move changes the objective by a huge amount, every worsening move is rejected once T is modest and the search freezes prematurely; if moves barely change the objective, the search drifts without direction. Annealing also gives no bound on how far the returned solution is from optimal, and it provides no proof of infeasibility if none exists.

Finally, the point that most often separates a working implementation from a broken one: always track and return the best state encountered. Because the acceptance rule permits a downhill move at any temperature above the stopping point, the state held when the loop exits may be worse — occasionally much worse — than a state visited thousands of iterations earlier. Storing best costs one comparison and one copy per improvement, and it converts the algorithm into a monotone anytime procedure whose reported quality can never decrease with additional time.

Hill climbing always moves uphill, so it stops the moment every neighbor looks worse — even when that peak is only a local optimum. Simulated annealing fixes this by borrowing an idea from metallurgy: start "hot," where the search is willing to accept moves that make the objective worse, and gradually "cool" until the search behaves like ordinary hill climbing. The willingness to accept a worsening move of size delta is governed by the Metropolis acceptance criterion, typically exp(-delta/T), where T is the current temperature.

The cooling schedule — the starting temperature, how quickly T decreases (for example geometric cooling T := alpha*T), and how many moves are attempted at each temperature — is the main design decision. Cool too fast and the search freezes in a poor local optimum; cool too slowly and you pay a large computational cost. There is a classical theoretical result that with a sufficiently slow (logarithmic) schedule the algorithm converges to a global optimum with probability approaching one, but that schedule is far too slow for practical use, so in practice we tune schedules empirically and compare against hill climbing with random restarts.

Applying Local Search to Large-Scale Problems

▶

Local search is the workhorse of practical optimisation. Once a problem becomes large enough that the state space cannot be enumerated and the path to a solution is irrelevant, the systematic search algorithms that build and store partial solutions become impractical. Local search abandons the idea of exploring a tree of partial plans and instead keeps a single complete candidate configuration, repeatedly nudging it with small modifications that tend to improve an objective function. The result is an algorithm family that uses almost no memory, scales to problems with millions of variables, and can be stopped at any moment to return the best configuration found so far. This topic examines where that trade-off pays off, how classic benchmark and industrial problems are encoded for local search, how to choose between hill climbing and simulated annealing, how to tune a cooling schedule, and how to report results honestly by weighing solution quality against computational cost.

When local search is the right tool

The first question to ask about any problem is: is the answer a configuration, or is it a sequence of actions? If the deliverable is a route plan, a sequence of robot motions, or a proof that must be replayed step by step, then the path matters and a path-finding algorithm such as A* or a planner is appropriate. If the deliverable is an arrangement — which queen sits in which row, which nurse works which shift, where each transistor cell is placed on a die — then the path by which you arrive at that arrangement is of no interest whatsoever. This is the complete-state formulation: every state in the search space is already a full candidate answer, possibly a bad one, and search means repair rather than construction.

The consequences for memory are dramatic. A breadth-first or A* search stores a frontier that grows exponentially with depth; a local search stores the current state, the incumbent best state, and a handful of scalars. For an 8-queens problem the difference is trivial, but for a one-million-queens instance — which local search solves in under a minute — the difference is between feasible and impossible. Memory use is O(1) in the size of the search space and O(n) in the size of a single state description.

A second precondition is cheap incremental evaluation. Local search lives or dies on how fast it can score a neighbour. If evaluating a candidate from scratch costs O(n²) but evaluating the change caused by a single move costs O(n) or O(1), then the algorithm can afford to examine orders of magnitude more candidates per second. This is called delta evaluation or incremental evaluation, and designing a move operator that admits it is often the single most important engineering decision in the whole project. Consider the travelling-salesperson problem with a 2-opt move that removes edges (a,b) and (c,d) and reconnects them as (a,c) and (b,d). Recomputing the whole tour length is O(n); computing the delta is:

delta = d(a,c) + d(b,d) - d(a,b) - d(c,d)

which is four distance lookups, independent of n. The same trick applies in n-queens: moving one queen changes only the conflicts involving that queen, so the change in h can be computed by inspecting one column's interactions rather than all n(n−1)/2 pairs. Problems where every move forces a complete re-simulation (for instance, an objective that requires running a discrete-event simulation of a factory for each candidate) are still tractable for local search, but the iteration budget shrinks by orders of magnitude and surrogate models or coarse screening become necessary.

Finally, there is the question of guarantees. Local search is incomplete and non-optimal: it may fail to find an existing solution, and when it returns an answer it usually cannot certify that nothing better exists. If the task demands a proven optimum (an exact bin-packing certificate for a regulatory filing), a proof of infeasibility (no schedule exists under these constraints), or an auditable bound on the gap, then branch-and-bound, integer programming, constraint programming with propagation, or SAT solving remain the correct tools. In practice the two families are often combined: a local search produces a good incumbent in seconds, and that incumbent is fed to an exact solver as an upper bound to prune its search tree.

N-queens as a benchmark problem

The n-queens problem is the standard teaching benchmark for local search because every design decision is visible in miniature. The complete-state formulation places exactly one queen in each column, so a state is an array q[0..n-1] where q[i] is the row of the queen in column i. This encoding already builds in two of the three constraint families — no two queens share a column by construction, and the representation is compact — leaving only row and diagonal conflicts to be optimised away.

The successor function moves a single queen to a different row within its own column. For an 8-queens board that gives 8 columns × 7 alternative rows = 56 neighbours; in general the neighbourhood has n(n−1) members. This is small enough to enumerate exhaustively for steepest ascent at modest n, and it is a well-behaved neighbourhood because any configuration can be transformed into any other by a finite sequence of such moves (the neighbourhood is connected).

The objective function h counts the number of pairs of queens that attack each other, directly or indirectly (ignoring blocking pieces, since there are none). A goal state has h = 0, so this is a minimisation problem; by convention we speak of hill climbing, which simply means we ascend on −h. Consider the state q = [0, 1, 2, 3, 4, 5, 6, 7] — all eight queens on the main diagonal. Every pair of queens attacks along that diagonal, so h = 28, the worst possible value. A single move of the queen in column 0 from row 0 to row 4 removes seven diagonal conflicts and introduces one row conflict (with the queen at q[4] = 4) plus possible new diagonal conflicts, giving an immediate, measurable improvement. This fine-grained response of h to single moves is exactly what makes the landscape climbable.

function STEEPEST-ASCENT(problem) returns a state
    current <- random complete state
    loop do
        neighbour <- the successor of current with the lowest h
        if h(neighbour) >= h(current) then return current   // no strict improvement
        current <- neighbour

The empirical behaviour of this algorithm on randomly generated 8-queens states is the classic result: it gets stuck roughly 86% of the time, solving only about 14% of instances. When it does succeed it is very fast, taking about 4 moves on average; when it fails it takes about 3 moves before freezing. The failure modes are the familiar landscape pathologies — a local minimum where every single-queen move increases h, and plateaux where many moves leave h unchanged. The state with h = 1 where no single move reaches h = 0 is a textbook local minimum: the configuration is tantalisingly close yet unreachable under the move operator.

Two cheap modifications transform these numbers. First, allowing sideways moves — accepting a neighbour with equal h — lets the search drift across plateaux, which in n-queens are frequently shoulders (flat regions with an exit that continues uphill) rather than true flat local optima. With a cap of 100 consecutive sideways moves to prevent infinite looping, the success rate on 8-queens rises from about 14% to about 94%, at the cost of a longer average run: roughly 21 steps per success and 64 per failure. Second, random restarts exploit the fact that failure is cheap and independent across runs. If a single run succeeds with probability p, the expected number of runs needed is 1/p, so with p ≈ 0.14 about 7 restarts suffice — roughly 22 total moves, which is a few microseconds of computation. Random-restart hill climbing is therefore complete with probability approaching 1, simply because it eventually generates a goal state as its initial state if nothing else works.

Scaling matters here. The success rate of plain hill climbing does not collapse as n grows — for large n the solution density is enormous and repair-based methods such as min-conflicts (choose a conflicted queen at random, move it to the row with fewest conflicts) solve million-queens instances in seconds, independent of problem size. The 8-queens failure statistics are a property of small, tightly constrained boards rather than a prediction about large instances, which is itself a useful lesson: benchmark results must be read with the instance size and constrainedness in mind.

Scheduling, layout, and routing applications

The n-queens formulation generalises directly to industrial problems, where the pattern is always the same triple: a state encoding that captures a complete candidate, a move operator that perturbs it locally, and an objective that mixes hard-constraint penalties with cost terms.

In job-shop scheduling, a state is an assignment of start times (or an ordering of operations on each machine) for every operation of every job. The usual objective is makespan — the completion time of the last job — though weighted tardiness, energy cost, or a weighted sum is common in practice. Effective move operators include swapping two adjacent operations on the same machine's sequence, shifting a start time earlier or later, and reassigning an operation to a parallel machine. The celebrated refinement is to restrict swaps to operations on the critical path, because only those can possibly change the makespan; this prunes a huge neighbourhood down to a handful of promising moves and is a general design principle — bias the neighbourhood toward moves that can actually change the objective. In airline scheduling, states assign crews and aircraft to flight legs; moves swap a crew pairing between two rotations or reassign a tail number, and the objective blends crew cost, deadhead flights, hotel nights, and penalties for violating duty-time regulations. Because the constraint set is legally mandated, a common architecture is to keep hard constraints inviolate by construction (the move operator only generates legal states) and to optimise cost within that feasible region.

In VLSI design, the two classic local-search stages are cell layout (placement) and channel routing. In placement, a state is the position and orientation of each standard cell or macro block on the die; moves translate a cell, swap two cells, or rotate/mirror a block; the objective is a weighted sum of estimated total wire length (usually the half-perimeter bounding box of each net), overlap penalties, and area or timing-slack terms. In channel routing, a state assigns wires to tracks and layers, and moves reassign a net to a different track or introduce a via; the objective minimises channel height, crossings, and via count. Simulated annealing achieved its industrial fame precisely here: the TimberWolf placement system of the 1980s demonstrated that an annealer could outperform hand-crafted constructive heuristics on real chips, and the technique remains embedded in modern physical-design flows.

In vehicle routing and the travelling-salesperson problem, a state is a set of routes (a permutation of customers per vehicle). The canonical moves are:

  • 2-opt: remove two edges and reverse the intervening segment, replacing a→b … c→d with a→c … b→d. This is the move that eliminates crossing edges in a Euclidean tour.
  • Or-opt: relocate a chain of one, two, or three consecutive customers to another position, possibly reversed, without reversing the rest of the tour.
  • 3-opt and Lin–Kernighan: remove three or a variable number of edges, giving a richer but more expensive neighbourhood; Lin–Kernighan-style variable-depth search remains the state of the art for large TSP instances.
  • Cross-exchange / relocate between routes: in multi-vehicle problems, move or swap customer segments between different vehicles to balance load and respect capacity and time windows.

Because a 2-opt neighbourhood has O(n²) members, large instances use neighbour lists (only consider reconnections to one of a city's 10 nearest neighbours) and don't-look bits (skip cities whose neighbourhood yielded no improvement and whose surroundings have not changed). These are not theoretical refinements but the difference between minutes and days on a 100,000-city instance.

Beyond these, local search is established in telecommunications network configuration — choosing link capacities, routing demands, and placing concentrators to minimise cost subject to survivability constraints — and in automatic programming and program synthesis, where states are candidate programs or expression trees and moves mutate subexpressions, with the objective measuring how many test cases pass. Related industrial uses include timetabling, frequency assignment in mobile networks, portfolio construction, protein structure prediction, and hyperparameter tuning.

Choosing between hill climbing and simulated annealing

All of these algorithms share the same skeleton — propose a neighbour, decide whether to accept it — and differ only in the proposal and acceptance rules. The choice among them is driven by two properties of the problem: the ruggedness of the landscape (how many local optima there are and how deep their basins run) and the cost per neighbour evaluation relative to the branching factor.

  • Plain or steepest-ascent hill climbing suits smooth landscapes with few local optima — convex-ish objectives, problems where a greedy repair almost always converges, or situations where you merely need to polish an already good solution produced by a constructive heuristic. Steepest ascent evaluates every neighbour and takes the best, which gives the most informed step per iteration but costs O(|N|) evaluations per move.
  • First-choice hill climbing generates successors at random and accepts the first improvement found. This is the right choice when the branching factor is large — thousands or millions of neighbours — because enumerating the full neighbourhood to find the single best move wastes effort that could have been spent making many adequate moves. In a VLSI placement with 100,000 cells, the swap neighbourhood is astronomically large and first-choice (or a randomly sampled subset) is the only practical option.
  • Stochastic hill climbing chooses among the uphill moves with probability weighted by steepness. It converges more slowly than steepest ascent but explores more, and often finds better final solutions on landscapes where the steepest move leads reliably into a shallow trap.
  • Random-restart hill climbing is the right answer whenever a single run is cheap and the per-run success probability p is not vanishingly small, since expected total cost is roughly (1/p) × cost per run. It is trivially parallelisable — run k restarts on k cores and take the best — and requires no parameter tuning beyond the restart count. It degrades badly when p is tiny (say 10−6), because then restarting is just repeated failure; in that regime an algorithm that escapes local optima without discarding its progress is needed.
  • Simulated annealing is that algorithm. It accepts a worsening move of magnitude ΔE with probability exp(−ΔE/T), where the temperature T falls over time. Early on it wanders almost randomly and is effectively doing a global exploration; late on it behaves like first-choice hill climbing. Use it when the landscape is rugged, when a single run is expensive so restarts are wasteful, and when final quality matters more than the time to the first feasible answer. The theoretical guarantee — that with a logarithmically slow schedule the probability of ending in a global optimum approaches 1 — is of no practical use (the required schedule is slower than exhaustive enumeration), but the practical performance on layout, scheduling, and routing is excellent.
function SIMULATED-ANNEALING(problem, schedule) returns a state
    current <- initial state
    best    <- current
    for t = 1 to infinity do
        T <- schedule(t)
        if T < T_min or budget exhausted then return best
        next  <- a randomly selected neighbour of current
        dE    <- value(next) - value(current)          // positive = better (maximisation)
        if dE > 0 then
            current <- next
        else if random(0,1) < exp(dE / T) then
            current <- next                             // accept a worsening move
        if value(current) > value(best) then best <- current

Note the explicit best variable: annealing's current state is allowed to deteriorate, so a production implementation must always retain the incumbent best separately. Forgetting this is one of the most common implementation bugs.

These choices are not mutually exclusive. A standard industrial recipe is hybridisation: construct a reasonable starting solution with a greedy heuristic (nearest neighbour for TSP, earliest-due-date for scheduling), improve it with fast first-choice hill climbing until no improvement is found, then apply simulated annealing or restarts from that incumbent. Tuning the cooling schedule and parameters

Simulated annealing has four tunable components — initial temperature, cooling rate, neighbourhood definition, and stopping criterion — and the first three interact. The guiding principle is that temperature should be calibrated in the units of the objective function: a temperature of 10 means nothing in the abstract, but a temperature equal to the average magnitude of a worsening move means a great deal.

Initial temperature. Set T₀ so that almost all proposed worsening moves are accepted at the start — an acceptance ratio of roughly 0.8 to 0.95 is the usual target. The standard calibration procedure is empirical: perform a few hundred random moves from a random state, record the average increase in cost Δ̄ among the worsening ones, and solve exp(−Δ̄/T₀) = χ₀ for the desired acceptance ratio χ₀, giving

T0 = -mean_positive_delta / ln(chi_0)
   e.g. mean_positive_delta = 12.0, chi_0 = 0.9  ->  T0 = -12.0 / ln(0.9) = 113.9

Too high a T₀ wastes budget on a pure random walk that carries no information; too low a T₀ freezes the search in whatever basin it started in, reducing annealing to hill climbing with noise.

Cooling rate. The three common schedules are geometric, linear, and logarithmic:

Geometric (exponential)T ← αT, with α ∈ [0.8, 0.999]Fast early cooling, long low-temperature tailThe practical default for almost all applications

With a geometric schedule the two knobs are α and the number of proposed moves per temperature level (the Markov chain length, often set proportional to the neighbourhood size, e.g. L = k·n). The goal is quasi-equilibrium: at each temperature the search should make enough moves for the distribution of visited states to settle before cooling further. Cooling too quickly produces quenching — the search is trapped in whatever basin it happened to occupy, which is exactly the local-optimum failure that annealing was meant to avoid. Cooling too slowly means the run does not reach low temperatures before the time budget expires, leaving a solution that is still being randomly perturbed. A simple and effective rule is to fix the total iteration budget first (from the time available), then derive α from α = (T_min/T₀)^(1/K), where K is the number of temperature levels the budget allows. For a budget of 107 moves with L = 1000 moves per level, K = 10,000 levels, and cooling from T₀ = 100 to T_min = 0.01 gives α = (0.0001)^(1/10000) ≈ 0.99908.

Neighbourhood design. The move operator defines the landscape, so it is a tuning parameter as much as any numeric constant. Moves must be small enough to be informative — a move that randomises half the state produces a delta uncorrelated with the current solution, which turns annealing into blind sampling — and large enough to traverse the space, meaning the neighbourhood graph must be connected so that any solution is reachable. Three practical guidelines:

  • Locality: the objective change caused by a move should be small and computable incrementally. If a typical delta dwarfs the current temperature range, the operator is too coarse.
  • Connectivity and symmetry: if move m can take state s to s′, some move should be able to return; asymmetric proposal distributions bias the stationary distribution in ways the Metropolis criterion does not correct.
  • Composite neighbourhoods: many strong implementations mix several operators with fixed probabilities — e.g. 70% single-customer relocate, 20% 2-opt, 10% inter-route swap — so that the search can both fine-tune and make structural changes. Choosing among several neighbourhoods systematically is the idea behind variable-neighbourhood search.

Stopping criteria. Terminate on whichever of these fires first: the temperature falls below T_min; a fixed iteration or wall-clock budget is exhausted; a whole temperature level completes with zero accepted moves (the system is frozen); the incumbent has not improved for N consecutive levels; or a known target/bound is reached (e.g. h = 0 for n-queens, where you should stop immediately on a feasible solution). The "no accepted moves" test is particularly useful because it is self-calibrating — it detects freezing regardless of what α was set to.

For hill climbing the parameter list is shorter but still real: the sideways-move cap (100 in the classic n-queens experiment), the restart count or restart budget, the neighbourhood sample size for first-choice, and the random-seed policy for reproducibility. A sensible discipline is to tune on a training set of instances and report results on a held-out set, exactly as in machine learning; otherwise the reported parameters are overfitted to the instances you happened to test.

Evaluating solution quality against computational cost

Local search is stochastic, so a single run tells you almost nothing. Any credible evaluation repeats each configuration over many independent runs (30 is a common minimum for stable statistics) and over a set of instances, then reports a distribution, not a point. The essential statistics are the mean objective value, the standard deviation, the best value found, and the median; the mean alone hides the case where an algorithm is usually mediocre but occasionally excellent, which matters a great deal if you intend to run it many times in parallel and keep the best.

Success rate and effort. For problems with a feasibility threshold (find a conflict-free queens placement; find a schedule under the deadline) report the fraction of runs that reached the threshold together with the average number of objective evaluations or moves per run. Evaluations are the fairer currency than seconds because they are hardware-independent, though wall-clock time should also be given since incremental evaluation costs differ between operators. The two numbers combine into the expected cost of a successful run:

expected_evaluations_to_success
    = evaluations_per_run / success_rate        (with restarts)

e.g. 5,000 evals/run at 25% success  ->  20,000 evals per solved instance

This single figure lets you compare, say, "fast but often failing" random-restart hill climbing against "slow but reliable" annealing on an equal footing.

Anytime curves. The most informative comparison plots best-so-far objective value against elapsed time (or evaluations), averaged over runs. Such a curve reveals behaviour a final-quality table conceals: hill climbing typically plunges quickly and then flatlines; annealing improves slowly at first (while the temperature is high and the current state is noisy) and overtakes hill climbing later. If your deployment must answer in 200 ms, the crossover point — not the asymptote — decides which algorithm to ship.

Reference points. Raw objective values are meaningless without a yardstick. Use, in order of preference: a known optimum (available for benchmark libraries such as TSPLIB or standard job-shop instances); a computed lower bound from a relaxation (the Held–Karp bound for TSP, a machine-load bound for job shops, an LP relaxation generally), which lets you report a guaranteed-correct "gap ≤ x%"; or, failing both, a competent baseline heuristic (nearest neighbour plus 2-opt, earliest-due-date dispatching) and the best-known published solution. Reporting "our annealer achieved cost 14,732" conveys nothing; "cost 14,732, which is 1.8% above the Held–Karp lower bound and 11% better than the greedy baseline" is an evaluation.

Diminishing returns. Improvement in local search is strongly front-loaded: the first few percent of the budget typically captures most of the attainable gain, after which each additional order of magnitude of computation buys a fraction of a percent. This has a direct managerial consequence — decide what a 1% improvement is worth in the application domain. For a delivery fleet, 1% of annual fuel spend may justify hours of nightly computation; for an interactive layout tool, a 1% shorter wire length is worthless if the user waits ten seconds for it. Practical rules that follow from the diminishing-returns curve include: stop when the incumbent has not improved for a defined share of the budget; prefer many short parallel runs over one very long run when the quality ceiling of a single run is low; and spend engineering effort on the move operator and incremental evaluation (which shift the whole curve) rather than on squeezing the last fraction of a percent out of α.

Finally, evaluate robustness, not just peak performance. An algorithm whose quality collapses when the instance distribution shifts, or which requires per-instance retuning of T₀ and α, is a liability in production. Parameter sensitivity analysis — sweeping α over {0.95, 0.99, 0.999} and T₀ over an order of magnitude, and reporting how much quality varies — is as important a result as the headline number, because it tells a deployment team how much slack they have when the problem changes next quarter.

Videos on This Topic

▶

So far in this module you have seen hill climbing and simulated annealing as abstract procedures operating on a state-space landscape. This topic turns to the practical question: when are these methods actually the right tool, and how do you apply them to problems that are too large for systematic search? Local search becomes attractive when the state space is enormous, when any complete configuration can be scored by an objective function, and when a good-enough solution found quickly is worth more than a guaranteed optimum found slowly.

The classic benchmark is n-queens, where a state is a full board placement and the objective counts attacking pairs. From there the same pattern extends to real applications: class and shift scheduling, VLSI and facility layout, and route optimization such as the traveling salesman problem. In each case the design work is the same three decisions — what counts as a state, what move operator defines the neighborhood, and what objective function measures quality — followed by the choice of algorithm, the cooling schedule if you use annealing, and the parameter tuning that follows.

As you watch the videos below, pay attention to how each problem is encoded. Ask yourself what the state representation is, what a single move changes, how the cost or fitness is computed, and how the presenter decides when to stop. Notice also where plain hill climbing gets stuck and what the implementer does about it, since that is exactly the tradeoff between solution quality and computational cost that you will be asked to justify.
