Why Problem Formulation Matters

▶

Almost every introductory treatment of artificial intelligence begins with search, and almost every disappointment with search begins with a bad problem formulation. The algorithms themselves — breadth-first search, uniform-cost search, A* — are short, well understood, and provably correct under stated conditions. What varies enormously from one application to another is the description of the problem that we hand to those algorithms. That description is not given to us by the world; it is constructed by a designer who decides what counts as a situation, what counts as a move, and what counts as success. The quality of those decisions determines whether a problem is solved in milliseconds, solved after a week of computation, or never solved at all. This topic examines the translation step from a messy real task to a precise computational object, the standard parts that object must have, and the judgement calls — above all, abstraction — that make the difference between a workable and an unworkable formulation.

From a real task to a search problem

A search problem is a task in which an agent must find a sequence of actions leading from a starting situation to a desired situation. The emphasis on sequence matters. Many computational tasks ask for a single answer — classify this image, predict tomorrow's temperature — and are not search problems in this sense. A search problem asks for a plan: do this, then this, then this, and you will have arrived. The output of a search algorithm is therefore a path, and the quality of the output is judged by both the destination (does it satisfy the goal?) and the route (how expensive was it?).

The striking property of this framing is that the agent needs no task-specific cleverness at all. A breadth-first search routine contains no knowledge of maps, puzzles, chemistry, or logistics. It knows only how to ask three questions repeatedly: Is this state a goal? What actions are available here? Where does each action lead? Given honest answers, it will systematically enumerate possibilities until it finds a solution. All of the domain intelligence has been pushed into the description. This is a genuine engineering advantage, because it means one well-tested implementation can serve many domains — but it is also the source of the risk, because the algorithm cannot compensate for a description that is wrong, redundant, or astronomically large.

Consider a traveller in Arad, Romania, who must reach Bucharest by tomorrow. The real task is awash in irrelevant detail: the colour of the car, the price of petrol at each station, the passengers' conversation, the weather, the exact position of the vehicle on the carriageway measured in centimetres. The formulation step discards all of this and declares that a state is simply the name of the city the traveller is currently in, an action is driving along a road to an adjacent city, and the goal is being in Bucharest. The resulting problem has twenty states and can be solved by hand. Nothing about the real journey has been made impossible by this simplification: every abstract plan such as Arad → Sibiu → Fagaras → Bucharest can actually be driven.

The same translation can be performed on tasks that look nothing like navigation. Assembling a protein-folding sequence, scheduling aircraft turnarounds, routing a packet, configuring a product line, solving a Rubik's cube, and planning a robot's grasp can all be cast in this mould. Once cast, they all accept the same algorithms. The formulation is the universal adapter between the world and the solver.

The standard components of a formulation

A problem formulation in the classical framework consists of five components. They are not arbitrary: each one answers a question that any systematic explorer must be able to ask.

The state is a description of the relevant configuration of the world at one moment. "Relevant" is doing an enormous amount of work in that sentence, and the section on abstraction below is devoted to unpacking it. The state space is the set of all states reachable from the initial state by any sequence of actions; it is usually defined implicitly, by giving the initial state and the transition model, rather than by listing states, because listing them is often impossible.

The initial state anchors the search. It need not be a single state in every variant of the framework — some problems have a set of possible starting points — but in the classical formulation it is one definite state. The goal test is a predicate applied to a state, returning true or false. Crucially, a goal test need not name a specific state. In the 8-queens problem the goal test is "no two queens attack each other", which is satisfied by 92 distinct boards; in a chess endgame it may be "the opponent is checkmated"; in a shopping task it may be "the basket contains milk, bread, and coffee" regardless of the order they were added.

The actions function, written Actions(s), returns the set of actions applicable in state s. The transition model, written Result(s, a), returns the state reached by performing action a in state s. Together they define the directed graph that search explores: nodes are states, edges are actions. Note that the pair must agree — if Actions offers a move that Result cannot evaluate, or offers a move that would produce an illegal state, the formulation is broken. In the 8-puzzle, Actions must exclude sliding the blank off the edge of the board; one may instead define all four moves always and have Result return the unchanged state for illegal ones, but then the state space contains self-loops that waste search effort.

Path cost is a function assigning a number to a sequence of actions, almost always as the sum of individual step costs c(s, a, s'). Its purpose is to make solutions comparable so that "optimal" means something. Without a cost function one can only speak of finding a solution; with one, we can ask for the cheapest. Two properties are usually required for the standard optimality guarantees of algorithms such as uniform-cost search and A*: step costs must be non-negative, and (for most practical purposes) bounded away from zero by some small ε. Negative step costs allow a search to improve a path forever by going round a loop, and zero-cost loops allow an infinite path of finite cost, both of which break termination and optimality arguments.

Formulation determines tractability

The combinatorial consequence of a formulation decision is rarely intuitive, because state spaces grow multiplicatively. Each independent feature you store in a state multiplies the number of distinct states by the number of values that feature can take. Adding one Boolean doubles the space; adding a variable with ten values multiplies it by ten.

Take the vacuum world. With two locations and a Boolean dirt flag per location, plus the robot's location, the state space has 2 × 22 = 8 states — small enough to draw on a napkin. Now extend to a realistic floor plan.

The two quantities that govern the cost of uninformed search are the branching factor b (how many successors a typical state has) and the solution depth d (how many actions a typical solution contains). Breadth-first search examines on the order of bd nodes. The exponent is the depth, so small changes in either number have large consequences.

A good formulation attacks both numbers. The classic illustration is 8-queens. The naive incremental formulation says: a state is any arrangement of zero to eight queens on the board; an action places a queen on any empty square. The branching factor at the first move is 64, and the number of distinct sequences to consider is roughly 64 × 63 × … × 57 ≈ 1.8 × 1014. A smarter formulation says: a state is an arrangement of k queens, one in each of the leftmost k columns, with no queen attacking another; an action places a queen in the leftmost empty column in any non-attacked square. Now the branching factor is at most 8, the depth is exactly 8, and only 2,057 states exist in the whole space. The problem has gone from hopeless-by-brute-force to solvable instantly, and no algorithm was changed. This is the single most important lesson of the topic: effort invested in representation typically pays a far higher return than effort invested in tuning the search procedure.

Deeper formulation changes can do even more. Choosing to search backwards from the goal, searching from both ends simultaneously, exploiting symmetry (in 8-queens, reflections and rotations collapse the 92 solutions to 12 fundamental ones), or replacing a path-finding formulation with a complete-state formulation suited to local search are all representational decisions made before a single line of search code runs.

Abstraction: choosing what to ignore

Abstraction is the process of removing detail from a representation. It is not a regrettable approximation forced on us by weak computers; it is the mechanism that makes reasoning possible at all. Any real situation contains an unbounded amount of detail, so every usable state is already an abstraction. The question is never whether to abstract but where to draw the line.

The practical test for inclusion is narrow and useful: a feature belongs in the state only if it affects which actions are legal, which state an action leads to, whether the goal test succeeds, or what an action costs. If a feature influences none of these four things, it cannot change the behaviour of the search and should be dropped. In the Romanian route-finding problem, the weather fails this test (it affects none of the four), so it is dropped; the current city passes it (it determines which roads are available), so it stays. If we added a constraint that mountain roads are closed in winter, then the season would suddenly affect action legality and would have to be promoted into the state.

Two properties distinguish a good abstraction from a merely small one:

  • Validity. Every abstract solution must be expandable into a solution of the original, more detailed problem. Formally, for each abstract path from the abstract initial state to an abstract goal, there must exist a corresponding detailed path in the real world. The city-level route plan is valid because the abstract step "drive from Sibiu to Fagaras" can always be realised as some sequence of real steering, accelerating, and braking actions.
  • Usefulness. Carrying out each abstract action must be easy relative to solving the whole problem — otherwise we have merely relocated the difficulty. An abstraction whose single action is "get from Arad to Bucharest" is valid and trivially small, and entirely useless, because expanding that one action is the original problem. Abstraction must decompose difficulty, not hide it.

The two failure modes sit on either side of the sweet spot. Over-abstraction discards information the problem actually needs, producing plans that are wrong or unexecutable: a delivery planner that ignores vehicle capacity will happily produce a route loading forty parcels into a van that holds twenty; a puzzle formulation that records only which tiles are present but not where they are cannot distinguish a solved board from a scrambled one, so the goal test becomes meaningless. Under-abstraction retains information that changes nothing, producing state explosion, exhausted memory, and failure of duplicate detection: two states identical in every respect that matters but differing in a stored timestamp will be treated as distinct, so the search re-explores the same situation endlessly.

A worked example sharpens the point. Suppose a hospital porter must collect a patient from Ward B and deliver them to Radiology. A thoughtful state might be (porter_location, patient_location, patient_on_trolley?) — three features, each needed: location determines which corridors are available, patient location and trolley status determine whether "deliver" is legal and whether the goal holds. Adding the porter's name, shift number, the lift's current floor, or the corridor's lighting level would multiply the space without changing any decision. But if lifts can be out of service, the lift's status does affect action legality and must be added. Abstraction decisions are therefore relative to the task, not absolute properties of the domain.

Assumptions behind the classical formulation

The five-component framework is not universally applicable. It rests on four assumptions about the environment, and when one of them fails, the formulation must be extended or replaced.

  • Observable. The agent knows which state it is in, so Result can be applied to a known state and the goal test can be evaluated with certainty. If the environment is partially observable, the agent must instead reason about belief states — sets of states it might be in. A vacuum robot with no sensors starting anywhere in a two-square world must plan over the eight-element power set of physical states, and its "goal test" becomes "every state in my belief set is clean". The search problem is still a search problem, but the state space has changed character and size dramatically.
  • Discrete. There is a finite (or at least countable) set of actions at each state, so successors can be enumerated. Continuous control problems — steering angle anywhere in a real interval — have infinitely many successors and require discretisation, sampling, or entirely different techniques such as optimisation or sampling-based motion planning.
  • Deterministic. Each action in each state produces exactly one known successor. This is what lets a solution be a simple sequence: the agent can compute the whole plan in advance and execute it blindly, confident about where each step lands. If actions may fail or have random outcomes, a sequence is no longer adequate; the solution becomes a contingency plan or policy that specifies what to do for each possible outcome, and the analysis moves toward AND–OR search or Markov decision processes.
  • Static. The world does not change while the agent deliberates, so a plan computed now is still valid when execution begins. In a dynamic environment — a moving obstacle, a competing agent, a fluctuating price — a plan can be invalidated before it is executed, and the agent must either replan continually or include the environment's evolution in the state (typically by adding time, with the attendant explosion in state count).

A fifth, often-implicit assumption is that the environment is single-agent: nobody else is acting to help or to frustrate the plan. Games violate this and require adversarial search. It is good practice, when writing down a formulation, to state explicitly which of these assumptions you are relying on, because readers and future maintainers can then see immediately when the formulation has outgrown its setting.

Evaluating a formulation before searching

A formulation can and should be criticised on paper, before any code runs. Four checks catch most of the common defects.

  • Are all states reachable and meaningful? A description may admit states the world cannot produce. The 8-puzzle is the standard example: of the 362,880 permutations of the nine symbols, only 181,440 are reachable from any given board, because sliding moves preserve the parity of the permutation. A formulation that assumes the whole space is connected will waste effort, or will promise a solution to an unsolvable instance. Similarly, a state with three queens in the same column is syntactically expressible but meaningless under the constraints, and should either be excluded by the Actions function or recognised as a dead end.
  • How big is the space, and how deep is a solution? Multiply out the feature cardinalities to estimate the state count; estimate b by counting typical legal actions; estimate d from known or sample solutions. Then compare bd with the memory and time you actually have. A back-of-the-envelope calculation that yields 1018 nodes tells you immediately that uninformed search is pointless and that you need a better representation, a heuristic, or both. The 8-puzzle has about 1.8 × 105 reachable states and is trivial; the 15-puzzle has about 1.3 × 1013 and needs good heuristics; the 24-puzzle has about 1025 and remains hard.
  • Is the goal test cheap and unambiguous? It is applied to every generated node, so an expensive test dominates the running time. More seriously, an ill-defined goal test is a silent killer: "the room is tidy", "the route is reasonable", and "the schedule is fair" are not predicates a program can evaluate. Each must be reduced to a checkable condition over the state — "every dirt bit is false", "total distance ≤ 300 km", "no worker has more than two night shifts". A goal test that cannot return a definite true or false means the search has no stopping condition at all.
  • Does the cost function measure what you care about? Minimising the number of road segments is not the same as minimising distance, which is not the same as minimising driving time, fuel, tolls, or emissions. Choosing step cost 1 per action — common and convenient — implicitly declares that all actions are equally undesirable, which is right for the 8-puzzle and wrong for route planning across roads of unequal length. The cost function must also be internally consistent: mixing kilometres on some edges with minutes on others makes "optimal" meaningless, and negative costs break optimality guarantees. If several objectives genuinely matter, they must be combined explicitly into a single scalar (for example, cost = time + λ × tolls) with the trade-off weight stated, or handled with a multi-objective method.

Running these checks produces a short, defensible document: the five components written out precisely, the assumptions named, the estimated size of the space, and a justification for each feature included in the state. That document is the real deliverable of problem formulation. The search algorithm applied afterwards is, by comparison, an off-the-shelf part.

The Five Components of a Search Problem

1

The Five Components of a Search Problem

▶

Search is the engine that drives a large part of classical artificial intelligence, but an algorithm can only search something that has been described precisely. Before any algorithm — breadth-first, uniform-cost, A* — can be let loose on a task, the task itself must be rewritten as a search problem: a mathematical object with exactly five parts. Those five parts are the state space (together with a designated initial state), the actions available in each state, the transition model that says what each action does, the goal test that recognises success, and the path cost function that measures how good a solution is. This topic works through each component in turn, shows how they interlock, and demonstrates with worked formulations that the five components together pin down a problem completely and unambiguously.

The payoff of this discipline is separation of concerns. Once a problem is expressed in the five-component form, the problem-solving agent no longer needs to know anything about tile puzzles, Romanian geography or dirty floors. It needs only to call ACTIONS(s), call RESULT(s, a), call GOAL-TEST(s) and add up step costs. The same search code therefore solves every problem that can be cast in this mould — which is the whole point of having a mould.

Why formal problem definition matters

An informal description such as "get the robot to the loading bay" or "tidy up the office" is useless to an algorithm because it leaves hundreds of questions open. Where can the robot start? Can it move diagonally? Does turning cost anything? Does "tidy" mean every surface clear, or merely the floor? A formal definition answers all such questions in advance. The practical test of a good formulation is a kind of inter-rater reliability: any two people given the same five-component specification should agree on exactly which action sequences are valid solutions, and which of those solutions is cheapest. If two competent readers disagree, the specification is incomplete, and the disagreement will show up later as a bug — an algorithm that returns an "illegal" plan, or one that reports failure on a solvable instance.

The formal vocabulary also gives us the definitions on which all later analysis rests:

  • A solution is a sequence of actions that leads from the initial state to a state satisfying the goal test, where every action in the sequence is applicable in the state in which it is taken.
  • An optimal solution is a solution whose total path cost is minimal among all solutions. A problem may have many optimal solutions (ties) or, if no goal state is reachable, none at all.
  • Failure is the correct answer when no solution exists; an algorithm that cannot distinguish "no solution" from "I gave up" is answering a different question.

Crucially, formulation is a modelling choice, not a fact of nature. The same real-world task can be formulated in many ways, and the choice has enormous practical consequences. Consider the 8-queens problem — place eight queens on a chessboard so that none attacks another. Two formulations:

  • Incremental, naive: states are any arrangement of 0–8 queens on the board; actions add a queen to any empty square. The state space contains roughly 1.8 × 1014 sequences to examine.
  • Incremental, constrained: states are arrangements of k non-attacking queens, one per column in the leftmost k columns; actions add a non-attacking queen to the leftmost empty column. The state space shrinks to about 2,057 states.

Both formulations are correct — both have exactly the same 92 solutions — yet one is searchable in milliseconds and the other is hopeless. Nothing changed about the world; only the model changed. This is why formulation is treated as a skill in its own right rather than as a clerical preliminary.

States and the state space

A state is a representation of a situation in the world, expressed at a chosen level of abstraction. The guiding principle is: a good abstraction removes every detail that is irrelevant to the task, while retaining everything needed to decide which actions are applicable, to compute their effects, and to test the goal.

Take the classic Romania route-finding problem. The real world contains the weather, the fuel level, the radio station, the colour of the car, fellow travellers and the scenery. For the purpose of getting from Arad to Bucharest, a state can be reduced to a single atomic fact: In(Arad). The abstraction is valid because every abstract solution (a sequence of city-to-city moves) can be expanded into a real-world solution (an actual drive along those roads), and it is useful because each abstract action is easier to carry out than the original problem. Abstraction that goes too far breaks solvability. If we abstracted the 8-puzzle state down to "number of tiles out of place", we could no longer tell which moves are legal or what they do — the model would be unusable even though it is smaller.

Contrast this with the 8-puzzle, where the state must record the exact position of all eight tiles and the blank. Discarding tile identities ("three tiles in the top row") destroys the ability to test the goal. The right abstraction is problem-specific; there is no universal rule beyond "keep what the other four components need".

Formally, the state space is the set of all states reachable from the initial state by any sequence of applicable actions. It is naturally viewed as a directed graph: nodes are states, and a directed edge labelled a runs from s to s' whenever a is applicable in s and RESULT(s, a) = s'. Edges carry weights given by the step cost. A solution is then simply a path in this graph from the initial node to any goal node, and an optimal solution is a minimum-weight such path. (Note that the state-space graph is an object in the world of the problem; the search tree that an algorithm builds while exploring it is a different object, since a single state may correspond to many tree nodes reached by different paths.)

State spaces grow explosively with problem size — the phenomenon known as combinatorial explosion:

This is an important lesson — the state space is defined by reachability, not by everything one could write down. Half of all "states" in the naive sense are simply not in the state space of a given 8-puzzle instance, and an algorithm that searches for a goal in the wrong half will correctly report failure.

State spaces may be finite (the 8-puzzle, Romania) or infinite (the set of all integers reachable by "add 1" and "double"; a robot on an unbounded grid; the set of all strings generated by a grammar). Finiteness matters for completeness guarantees, but it is not a precondition for formulating a problem. In almost every case the state space is defined implicitly — by giving the initial state plus the actions and transition model, and letting the reachable set follow — rather than by enumerating states explicitly. Nobody stores 1.3 × 1013 fifteen-puzzle configurations; the search generates them on demand.

The initial state

The initial state is the state from which the agent begins. Three properties of it deserve emphasis.

First, it must be written in exactly the same representation used for all other states. If states are tuples (agentLocation, dirtA, dirtB), then the initial state must be a tuple of that shape, e.g. (A, Dirty, Dirty). Mixing representations — describing the start in English and the successors as tuples — breaks the transition model and the goal test, both of which are functions over the state representation. This sounds obvious but it is one of the commonest errors in student formulations.

Second, changing the initial state generally changes both the solution and the reachable portion of the state space. In Romania, starting In(Arad) and starting In(Iasi) yield entirely different optimal routes. In the 8-puzzle, an initial state in the "odd permutation" half makes the standard goal unreachable, so the reachable sub-graph contains no goal state and the correct answer is failure. The problem is therefore the pair (world dynamics, starting point): the dynamics alone do not determine the state space.

Third, some problems do not supply a known initial state. If the agent's sensors are absent or imperfect, the best it can say is "I am in one of these states". The standard remedy is to search in the space of belief states — sets of physical states consistent with what is known. For the two-square vacuum world with no sensors at all, the initial belief state is the set of all eight physical states, {s1, s2, ..., s8}, and the transition model maps belief states to belief states. The remarkable consequence is that a conformant plan such as [Right, Suck, Left, Suck] cleans the world from any starting configuration, because each action shrinks the belief state until it contains only clean states. Belief-state search is still an ordinary five-component search problem — only the meaning of "state" has changed.

Together with the actions and transition model, the initial state implicitly defines the whole state space: state space = closure of {initial state} under RESULT.

Actions and applicability

The function ACTIONS(s) returns the set of actions that are applicable (legal) in state s. Applicability is state-dependent: an action that is perfectly legal in one state may be illegal in another. In the 8-puzzle, Up is applicable only when the blank is not already in the top row; in Romania, the action "drive to Sibiu" exists only in states where the agent is in a city adjacent to Sibiu. Writing a single global action list without applicability conditions is a modelling error, because it allows the search to generate states that cannot exist.

This is the core function of applicability: restricting the action set prevents the generation of invalid or impossible states. A sliding-tile formulation that permits Up from the top row would either crash or, worse, silently invent a tenth square. A 8-queens formulation that forbids placing a queen on an attacked square keeps the entire search inside the space of partial solutions. Constraints can be enforced either in ACTIONS (pruning at the source) or in the goal test (filtering at the end); pushing them into ACTIONS is almost always vastly more efficient.

The granularity of actions is another modelling decision with real consequences:

  • Too fine: modelling a drive from Arad to Sibiu as thousands of one-metre movements makes solutions thousands of steps long, bloats the branching factor and renders search intractable — even though the model is "more accurate".
  • Too coarse: modelling the action as "travel to any city in Romania" hides the road network, assumes capabilities the agent lacks, and may admit abstract solutions that cannot be executed. Likewise, defining the 8-puzzle action as "swap any two tiles" produces a formulation whose solutions are not legal puzzle moves.
  • Just right: each action is a self-contained step that the agent can reliably execute without further planning — one road segment, one tile slide, one queen placement.

In the Romania example the applicability sets are read directly off the map. From Arad there are exactly three roads, so:

ACTIONS(In(Arad))      = { Go(Sibiu), Go(Timisoara), Go(Zerind) }
ACTIONS(In(Bucharest)) = { Go(Fagaras), Go(Pitesti), Go(Giurgiu), Go(Urziceni) }
ACTIONS(In(Oradea))    = { Go(Zerind), Go(Sibiu) }

Note that Go(Bucharest) is not in ACTIONS(In(Arad)): there is no direct road, and allowing it would make the model describe a different (non-existent) Romania.

The transition model (successor function)

The transition model RESULT(s, a) specifies what each applicable action does: it returns the state that results from performing action a in state s. It is the component that turns a static vocabulary of states into a dynamic system.

Taken together, ACTIONS and RESULT constitute the successor function, which maps a state to the set of all states directly reachable from it:

SUCCESSORS(s) = { (a, RESULT(s, a)) : a in ACTIONS(s) }

This is precisely the operation that a search algorithm calls "expanding a node". In a deterministic, fully observable environment each action leads to exactly one successor state, so RESULT is a single-valued function. Applied repeatedly from the initial state, it generates the entire reachable state space — which is why we can define vast state spaces in a few lines of code without ever enumerating them.

For the two-square vacuum world, with state written as (location, dirtA, dirtB) and actions {Left, Right, Suck}, the model is small enough to tabulate:

Two modelling decisions are visible in the table. Moving Left in square A is treated as a legal no-op rather than as an inapplicable action — an equally valid alternative is to remove it from ACTIONS(A, ·, ·); and Suck on a clean square is a no-op. Both choices must be stated explicitly, because a reader who assumed otherwise would compute different solutions.

For the 8-puzzle the model is defined by formula rather than table: if the blank is at row r, column c, then RESULT(s, Up) is the state obtained by exchanging the blank with the tile at (r−1, c). Note the convention — actions are named for the movement of the blank, which keeps the branching factor at 2–4 and the description compact.

Non-deterministic problems generalise the model so that RESULTS(s, a) returns a set of possible outcome states. The "erratic vacuum cleaner", whose Suck action sometimes cleans the adjacent square too and sometimes deposits dirt on a clean square, has RESULTS((A, Clean, Dirty), Suck) = {(A, Clean, Dirty), (A, Dirty, Dirty)}. In such worlds a solution is no longer a simple sequence but a contingency plan containing conditionals, e.g. [Suck, if State = Dirty then Suck else []]. The five components survive intact; only the type of RESULT and the type of "solution" change.

The goal test

The goal test GOAL-TEST(s) is a Boolean function that determines whether a given state is a goal state. It comes in two flavours.

  • Explicit: the goal is an enumerated set of states, and the test is set membership. Romania: GOAL-TEST(s) ≡ (s = In(Bucharest)). The 8-puzzle: GOAL-TEST(s) ≡ (s = the designated goal configuration). The vacuum world with an explicit goal: s ∈ {(A, Clean, Clean), (B, Clean, Clean)}.
  • Implicit: the goal is a property that a state may satisfy, checked by evaluating a condition. The vacuum world is more naturally written GOAL-TEST(s) ≡ (every square is Clean) — which works for 2 squares or 200 without listing anything. The 8-queens goal test is "8 queens placed and no pair attacking". Chess uses "checkmate", a structural property that no one could usefully enumerate.

Implicit tests are essential whenever goal states are numerous, unknown in advance, or expensive to enumerate. They also keep the formulation honest: writing the goal as a condition forces you to say exactly what "done" means. A vague goal test such as "the room is tidy" or "the route is good" is one of the classic formulation errors, because two readers will disagree about which action sequences count as solutions.

The number of goal states varies: there may be many (92 solutions to 8-queens; any clean configuration in the vacuum world), exactly one (the standard 8-puzzle target), or none reachable at all (an 8-puzzle instance of the wrong parity; a route-finding instance where the destination lies on an isolated island). An algorithm must be prepared to search the entire reachable space and report failure.

Finally, when the test is applied is an algorithmic detail with real consequences. The generic search algorithm applies GOAL-TEST to a node when it is selected for expansion (popped from the frontier); this is what allows uniform-cost search and A* to guarantee optimality, since a cheaper path to the same goal may still be sitting in the frontier. Other algorithms — breadth-first search, for example — apply the test when a node is generated, which saves a whole level of expansion and is safe there because with uniform step costs the first goal generated is already shallowest. Testing at generation time in uniform-cost search, by contrast, can return a sub-optimal solution. The goal test is the same function in both cases; the placement of the call is a design decision that must be justified.

Path cost and step cost

The path cost function assigns a numeric cost to a sequence of actions, and it is what makes "optimal" meaningful. It is almost always built additively from step costs: c(s, a, s') is the cost of taking action a in state s and arriving at s'. For a path that visits states s0, s1, …, sn via actions a1, …, an:

g(path) = c(s0, a1, s1) + c(s1, a2, s2) + ... + c(s(n-1), an, sn)

Three technical conditions matter. Step costs are assumed non-negative: negative edges would mean that looping could reduce cost indefinitely, so there would be no optimal solution and the standard algorithms' arguments would collapse. Many algorithms go further and require step costs to be strictly positive — bounded below by some small ε > 0 — to guarantee termination: with zero-cost actions available, an agent could execute an infinite sequence of free moves without ever increasing g, and uniform-cost search could be trapped in that infinite zero-cost loop forever. Finally, the cost function must be consistent with itself: the same action in the same state must always cost the same, and costs must be expressed in a single unit. A formulation that charges kilometres for some roads and minutes for others is meaningless, because the sums being compared are not comparable.

An optimal solution is a solution whose path cost is lowest among all solutions. Note that "optimal" is relative to the cost function you chose, not to any absolute notion of goodness — which is why the final principle below matters so much.

A very common and important special case is the unit-cost model, where c(s, a, s') = 1 for every action. Then g(path) is simply the number of actions, and minimising path cost is identical to finding the shallowest goal node. This is exactly the condition under which breadth-first search is optimal, and under which uniform-cost search degenerates into breadth-first search. The 8-puzzle is conventionally given unit step costs, so an optimal solution is one with the fewest tile slides.

State Space Representation and Abstraction

State Space Representation and Abstraction

▶

Before any search algorithm can run, a task described in ordinary language — "get the robot from the loading bay to the inspection table", "tidy the two-room office", "solve this sliding tile puzzle" — must be turned into a mathematical object that an algorithm can manipulate. That object is the state space: a set of states, together with the actions that move between them. The quality of a search system depends far more on how this space is defined than on which algorithm is later applied to it. A well-chosen representation can turn an apparently hopeless problem into one that is solved in milliseconds; a careless one can make a trivial problem intractable, or worse, can produce "solutions" that cannot be carried out in the real world at all.

This topic examines the design decisions behind a state representation: what information a state must carry, how abstraction discards everything else, how the resulting space is structured as a graph, how large that graph is, and how its shape — measured by branching factor and depth — determines the cost of searching it. It closes by returning to the relationship between the abstract graph and the physical situation it models, because that relationship is where most formulation errors ultimately reveal themselves.

What a State Must Capture

A state is a snapshot of the world, but it is a selective snapshot. The guiding principle is the Markov property: the state must contain enough information that the consequences of every future action depend only on the current state, never on the history of how that state was reached. Formally, if s is a state and a an applicable action, the successor RESULT(s, a) must be determined by s and a alone. If two different histories lead to the same recorded state but would lead to different futures, the representation is incomplete — some history-dependent fact has been left out and must be promoted into the state.

A concrete illustration: suppose we model a delivery robot by its grid cell only, (x, y), but the robot physically carries at most one parcel and cannot pick up a second. Two histories bring the robot to cell (3, 4): in one it is empty-handed, in the other it is already loaded. The action Pickup is legal in the first case and illegal in the second, yet both map to the same recorded state. The representation violates the Markov property. The fix is not to patch the algorithm but to enrich the state to (x, y, carrying), where carrying ∈ {none, parcel}.

Errors run in both directions. Too little information makes legal actions or the goal test impossible to evaluate. If the vacuum world's state recorded only the agent's room and not the dirt, there would be no way to decide whether the goal "both rooms clean" had been reached; the goal test would be undefined. If a route-finding state recorded only the current city and the goal was "visit every city once", the goal test would again be unevaluable because the set of visited cities is nowhere recorded. The symptom is always the same: an action precondition or the goal predicate needs a fact the state does not contain.

Too much information is a subtler fault because the formulation still "works" — it just works badly. Each extra state variable multiplies the number of distinct states, and every one of those copies must potentially be stored by a graph search and distinguished from its siblings. Suppose a route-finding state is recorded as (city, current_time, fuel_litres, odometer, weather) when the task is simply to find the shortest road distance between two towns. The odometer reading alone makes every revisit of a city a new state, so the explored set never recognises a repeat, cycles are never pruned, and the search degenerates. Worse, states that should be recognised as identical and merged are kept apart, destroying the main efficiency advantage of graph search over tree search.

A practical two-part test for any candidate representation:

  • Sufficiency test: Taking only the data in the state, can I determine which actions are applicable, compute the resulting state of each, assign its step cost, and evaluate the goal test? If any of these requires looking at the path taken to get here, the state is too thin.
  • Necessity test: For each variable in the state, if I deleted it, would any action precondition, transition, cost, or goal test become unevaluable? If not, the variable is decoration and should go.

The reason the sufficiency test matters so much is that the remaining four components of a search problem are all written in the vocabulary of the state variables. The initial state is an assignment to those variables. Each action's precondition is a predicate over them. The transition model is a function from an assignment and an action to a new assignment. The goal test is a predicate over them (or a comparison against an explicit goal assignment). Fix the state variables and you have fixed the language in which everything else must be expressed; change them and every other component must be rewritten. This is why representation design precedes, rather than follows, the rest of the formulation.

Vacuum world, two rooms
  State variables:  agent ∈ {L, R},  dirtL ∈ {clean, dirty},  dirtR ∈ {clean, dirty}
  Initial state:    (L, dirty, dirty)

None of these is needed to decide which action to take next or to tell when the job is done, so none of them belongs in the state. Notice too that every component after the state list is phrased purely in terms of agent, dirtL and dirtR.

Abstraction: Removing Irrelevant Detail

The process of deciding what to leave out is abstraction. An abstract state is not a simplified world; it is a name for a set of real-world situations that the model treats as equivalent. When we write the route-finding state In(Arad), that single symbol stands for an uncountable collection of genuine physical situations: the car parked on the north side of the square, idling at the traffic lights, the driver's hands at ten-to-two or quarter-past-three, the radio on or off, the temperature at 14°C or 15°C. All of these collapse into one abstract state because none of them changes which roads can be taken next or how far they are.

In the same way, an abstract action stands for a large and complicated family of real-world activities. The action Go(Arad, Sibiu) abstracts hundreds of kilometres of steering corrections, gear changes, overtaking decisions, a stop for fuel and a detour around roadworks. The abstraction is a deliberate compression of an enormous amount of physical detail into a single symbol with a single cost label (140 km).

For this compression to be legitimate, two distinct properties are required, and it is worth keeping them apart.

  • Validity. Every abstract solution must be expandable into a solution of the detailed problem. For the route-finding abstraction, this means: for any two adjacent abstract states, there exists at least one sequence of real-world steering and acceleration actions that carries the car from some detailed situation denoted by the first abstract state to some detailed situation denoted by the second. If a road in the map has been closed, or if the "road" is a ferry that only runs in summer, the abstraction is invalid: the abstract plan cannot be refined into real behaviour and the search has produced a fiction.
  • Usefulness. Carrying out each abstract step must be easier than solving the original problem. An abstraction that validly reduces "get from Arad to Bucharest" to a single abstract action Go(Arad, Bucharest) is valid but useless, because expanding that one step is exactly as hard as the problem we started with. Abstraction buys nothing unless the refinement of each abstract action is comparatively routine — handled by a lower-level controller, a human driver, or a separate and much smaller search.

These two requirements pull in opposite directions, which is why the level of abstraction is a genuine design trade-off between fidelity and tractability. Consider a mobile robot:

The 8-puzzle offers a cleaner example of the same reasoning. The real world contains plastic tiles that can be slid, jiggled, lifted out of the frame, or dropped on the floor. The standard formulation abstracts away the physical act of sliding (replacing it by an instantaneous permutation), abstracts away the intermediate positions of a tile mid-slide, and abstracts away actions such as "shake the puzzle" or "prise out a tile". The last of these is an abstraction of the action set rather than the state, and it is the one that needs justification: we are asserting that a solution exists without cheating. It does, so the abstraction is valid; and each abstract move is trivially executable, so it is useful.

The State Space and Its Graph

Once states and actions are fixed, the state space has the structure of a directed, labelled graph. The nodes are states. There is a directed edge from s to s' labelled a whenever a is applicable in s and RESULT(s, a) = s'. Each edge carries a step cost c(s, a, s'). A path is a sequence of states linked by such edges; its cost is the sum of the edge costs along it. A solution is a path whose first node is the initial state and whose last node satisfies the goal test; an optimal solution is a solution of minimum total cost.

Edges are directed because actions are not always reversible. In route finding on a road network with one-way streets, Go(A, B) may exist while Go(B, A) does not. In the vacuum world, Suck turns a dirty room clean but no action turns it dirty again, so many edges are one-way and the graph has a layered structure that drains towards the goal. Reversibility is a property worth noting explicitly, because it affects whether techniques such as bidirectional search are applicable.

The single most important structural fact is that the state space graph is almost always implicit. It is not a data structure sitting in memory. It is defined intensionally, by rules: a description of what counts as a legal state, a function that lists the applicable actions for any given state, and a function that computes the successor. The graph is generated on demand, one node at a time, by calling those functions. The 8-puzzle's graph is defined by half a dozen lines of code, even though it contains 181,440 reachable nodes; the 15-puzzle's by the same code, though it contains about 1013.

# An implicit state space: the whole graph in three definitions
def actions(state):          # state is a 9-tuple, 0 = blank
    i = state.index(0)
    moves = []
    if i >= 3: moves.append('Up')
    if i <  6: moves.append('Down')
    if i % 3 > 0: moves.append('Left')
    if i % 3 < 2: moves.append('Right')
    return moves

def result(state, action):   # returns the successor state
    i = state.index(0)
    j = {'Up': i-3, 'Down': i+3, 'Left': i-1, 'Right': i+1}[action]
    s = list(state); s[i], s[j] = s[j], s[i]
    return tuple(s)

def goal_test(state):
    return state == (1,2,3,4,5,6,7,8,0)

Because the graph is implicit and vast, no search algorithm ever "looks at the state space". It materialises a small neighbourhood of it, starting from the initial state and expanding outwards, and stops as soon as a goal is found. A well-guided A* search on the 15-puzzle may touch a few hundred thousand nodes out of 1013 — a vanishingly small fraction. The entire purpose of search algorithms, and of heuristics in particular, is to make that explored fraction as small as possible.

Measuring State Space Size

A first estimate of state space size comes from the product rule: if the state consists of independent variables v₁ … vₙ with domain sizes |D₁| … |Dₙ|, then the number of syntactically possible states is |D₁| × |D₂| × … × |Dₙ|. For the two-room vacuum world: 2 positions × 2 dirt values × 2 dirt values = 8. For an n-room version: n × 2ⁿ — the exponential term already dominates at n = 10 (10,240 states) and is hopeless at n = 100.

This product is an upper bound, not the true size, for two reasons. First, some syntactic combinations may be illegal — they violate a structural constraint of the domain. Second, and more importantly, some legal combinations may be unreachable from the initial state. The 8-puzzle is the standard illustration: there are 9! = 362,880 distinct arrangements of eight tiles and a blank in nine cells, but the permutation parity invariant means the reachable set from any given start is exactly half of them, 9!/2 = 181,440. The other half forms a separate connected component that no sequence of legal slides can enter. A formulation that assumes all 362,880 states are reachable will waste effort searching for a goal that is provably unattainable — a correctness problem, not merely an efficiency one.

The 8-queens rows in that table make the central point about abstraction and size with unusual clarity. All three formulations describe the same puzzle and have the same solutions, but they differ by eleven orders of magnitude. Moving from "place eight queens anywhere" to "place one queen per column" is an abstraction step: it folds together all the placements that differ only by which of several queens occupies a square (queens are indistinguishable) and discards outright the placements with two queens in a column, which can never lead to a solution. Removing a single irrelevant variable has a comparable effect, because its domain size is a multiplicative factor. If a delivery-robot state is (cell, carrying, battery_percent) with 500 cells, 2 carrying values and 101 battery readings, the space has 101,000 states. If the battery is irrelevant to the task — because the robot is on a charging rail, or because any plan under consideration is far shorter than its endurance — deleting it leaves 1,000 states, a hundredfold reduction. Keeping a fine-grained clock, an odometer, or a continuous sensor reading in the state is the single most common way that students accidentally make a small problem enormous.

State space size matters directly because graph search must store the states it has visited. The explored set, in the worst case, grows to the size of the reachable state space, so the reachable size is a hard upper bound on the memory a complete graph search may consume. At roughly 100 bytes per stored 15-puzzle state, 1013 states would require around a petabyte — which is why the 15-puzzle is solved with memory-bounded methods such as IDA* rather than plain breadth-first graph search. Estimating state space size is therefore not an academic exercise; it is the calculation that tells you in advance whether an algorithm is viable at all.

Branching Factor and Depth

Size alone does not determine search cost; the shape of the space matters just as much. Three parameters summarise that shape:

  • b, the branching factor: the number of successors generated per state, usually quoted as an average or a maximum.
  • d, the depth of the shallowest goal: the length (in actions) of the shortest solution.
  • m, the maximum path length in the state space, possibly infinite if the space contains cycles and the algorithm does not detect repeated states.

The number of nodes at depth d of a search tree is roughly b^d, and the total generated by a breadth-first search down to that depth is O(b^d). Because b sits in the base of an exponential, even small reductions compound dramatically. Compare the node counts at depth 12:

Dropping b from 4 to 3 cuts the depth-12 tree by a factor of about 32; dropping it from 10 to 3 cuts it by roughly two million. There are several standard ways to lower b through representation choices:

  • Prune inapplicable actions at the source. In the 8-puzzle, defining moves in terms of the blank tile rather than the eight numbered tiles reduces b from a potential 8-ish to between 2 (blank in a corner) and 4 (blank in the centre), averaging about 3.
  • Merge symmetric or equivalent actions. If four rotations of a board position are equivalent, treat them as one state, which both shrinks the space and removes redundant branches.
  • Forbid immediately-undoing moves. Disallowing the inverse of the previous action cuts b by one — but note carefully that this makes the action set history-dependent and therefore technically requires the last action to be part of the state, or an equivalent check inside the search node. This is a case where an apparently harmless optimisation quietly changes the state representation.
  • Impose an ordering on commutative actions. In 8-queens, placing queens column by column rather than allowing any queen to be placed anywhere removes all the orderings of the same final placement; the n! permutations of one set of moves collapse into a single path.

Abstraction affects d as well as b, and usually in the helpful direction: a coarser abstraction gives each action more reach, so fewer of them are needed to span the problem. A route planner working on motorway junctions may solve a cross-country trip in 12 abstract steps; the same trip at the level of 10-metre road segments takes tens of thousands of steps. Since cost grows as b^d, shortening d is at least as valuable as shrinking b — though coarse abstractions often raise b slightly (a motorway junction has more outgoing choices than a 10-metre segment, which usually has one), so the net effect must be computed rather than assumed.

The parameter m matters for a different family of algorithms. Depth-first search has space complexity O(bm) and time complexity O(b^m), so a space with long or unbounded paths punishes it severely even when a shallow goal exists. In the vacuum world, m is infinite under tree search because Left and Right can be alternated forever, even though d is at most 3. That single observation tells you that depth-first tree search is the wrong choice here, and that either a depth limit, a cycle check, or graph search with an explored set is required. In spaces where actions are irreversible — such as the 8-queens incremental formulation, where queens are only ever added — m is bounded by construction (at most 8), and depth-first search becomes an excellent, memory-cheap choice.

For this reason, a formulation should always be reported together with its parameters. A statement such as "the 8-puzzle has 181,440 reachable states, b ≈ 3, average d ≈ 22, and m unbounded without repeated-state detection" conveys more about the practical difficulty of the problem than any prose description, and it is exactly the information that complexity results about completeness, optimality, time and space are stated in terms of.

State Space Graph Versus the Physical World

It is worth saying plainly what the graph is and is not. The state space graph is a model. Its nodes are not places, configurations or situations; they are equivalence classes of situations that the modeller has chosen to treat as interchangeable. The many-to-one mapping from physical reality to abstract states is not a defect or an approximation to be apologised for — it is the entire point. Searching would be impossible if every microscopically distinct situation were a separate node, because there would be infinitely many of them and no two would ever repeat.

Alongside the abstraction, the standard search framework carries a set of environment assumptions that are usually left implicit and should be made explicit when a formulation is presented:

  • Observable: the agent knows which state it is in, so it can evaluate action preconditions and the goal test directly. If the agent cannot observe the state, the correct object to search is a space of belief states (sets of possible physical states), which is exponentially larger.
  • Deterministic: each action from each state has exactly one outcome, so RESULT is a function. If outcomes are uncertain, a solution is no longer a sequence but a contingency plan or policy, and the search problem becomes an AND–OR search or a Markov decision process.
  • Discrete: there are finitely many actions in each state, so successors can be enumerated. Continuous control variables require discretisation (itself an abstraction choice) or entirely different methods.
  • Static: the world changes only as a result of the agent's actions, so a plan computed now will still be valid when it is executed. A world with other moving agents, deadlines, or weather violates this.
  • Fully known: the agent knows the actions and their effects in advance, which is what makes offline planning possible.

These assumptions are properties of the model, not of reality. Route finding is treated as static and deterministic even though traffic is neither; the justification is that over the planning horizon, the deviations are small enough to be absorbed by re-planning. The assumptions are therefore claims that must be defended, not free gifts.

The critical correctness condition is this: every detail the abstraction discards must genuinely be irrelevant to the choice of action and to the executability of the plan. If a discarded detail does affect either, the abstract solution may be unexecutable, and the search will have returned a confident answer that is simply wrong. Some representative failures:

  • A warehouse robot's state records only (cell, carrying), but some aisles are too narrow for the robot when it is holding a wide pallet. The plan routes a loaded robot down a narrow aisle. The discarded detail — the physical footprint of the load — did affect which actions were applicable. Fix: make the action precondition depend on carrying, or add a load_width variable.
  • A route planner's abstraction assumes every road edge is traversable, but one edge is a seasonal mountain pass. The abstract plan cannot be refined into real driving in winter. Fix: either remove the edge or add a season/date variable and condition the action on it.
  • A delivery plan ignores battery level because "the robot is usually charged". On a long route it halts mid-plan. The omitted variable mattered to executability. Fix: add a discretised battery variable and recharge actions.
  • An 8-puzzle formulation permits a tile to move diagonally because the modeller wrote the successor function in terms of index arithmetic without checking row wrap-around. Cell 2 "moves right" to cell 3, which is physically a different row. The abstraction has invented an edge that does not exist.

The last example illustrates the complementary error: as well as discarding something that mattered, an abstraction can add transitions the real world does not support. Both are failures of validity, and both are detected by the same discipline — walk each abstract action and ask whether it can actually be executed, from every state in which the model says it is applicable. A practical validation checklist for a completed formulation:

  • For each action, state its precondition in words and check that the real system can perform it whenever that precondition holds, from any physical situation the abstract state might denote.
  • Confirm that the successor state is reachable in reality and that its cost label matches a real resource (distance, time, money, energy) measured consistently across all actions.
  • Check the goal test against the real acceptance criterion — would a stakeholder agree that a state passing the test is a finished job?
  • Confirm the initial state is one the system can actually be in, and is described in the same variables as every other state.
  • Spot-check reachability: is the goal provably reachable from the initial state, or could it lie in a disconnected component (the 8-puzzle parity trap)?

When execution does reveal that information is missing — the robot stalls, the plan calls for an impossible manoeuvre, the goal test passes on a state nobody would accept — the remedy is almost always to revise the representation, not the algorithm. Switching from breadth-first to A*, adding a cleverer heuristic, or increasing the node limit will make a flawed formulation fail faster, but it cannot make it correct: the search is answering exactly the question it was asked, and the question was wrong. The repair is to promote the missing fact into a state variable, tighten an action precondition, correct a cost function, or sharpen the goal test — and then to re-check the size, b, d and m consequences, because every enrichment of the state multiplies the space and may change which algorithms remain viable. Representation design is therefore an iterative loop: formulate, estimate, search, attempt execution, and revise.

Before an AI agent can search for a solution, someone has to decide what a "state" actually is. A state must capture exactly the information needed to decide what happens next — no more, no less. Include too little and the agent cannot tell legal moves apart; include too much (the color of the puzzle tiles, the time of day, the exact pixel position of a robot) and the state space explodes with distinctions that never affect the outcome. This graph is a mathematical object, not the physical world — the same physical room can map to a handful of abstract states, and a single abstract action can stand for a long sequence of real-world motions. The size of that graph, its branching factor (how many actions are available on average) and its depth (how far the goal lies from the start) are what determine whether search is feasible at all.

Formulating Classic Example Problems

Formulating Classic Example Problems

▶

Once the five standard components of a search problem — state space, initial state, actions, transition model, goal test and path cost — have been defined in the abstract, the only way to gain real fluency is to apply them repeatedly to concrete tasks. This topic works through four classic examples that have become the standard vocabulary of the field: the 8-puzzle, the vacuum world, the 8-queens problem, and route-finding and touring problems. Each example is chosen because it stresses a different aspect of formulation. The 8-puzzle shows how a careful choice of action set collapses the branching factor; the vacuum world is small enough that the entire state graph can be drawn on a page; 8-queens shows that the same goal can be reached from radically different formulations with state spaces differing by eleven orders of magnitude; and route-finding shows how real-world messiness is tamed by abstraction, and how a single extra piece of bookkeeping in the state can blow the space up exponentially.

A useful distinction running through all four examples is that between a toy problem and a real-world problem. Toy problems have a crisp, concise description and are used to compare algorithms; real-world problems are those people actually care about, and their formulations are usually contested because no single description is agreed upon. The 8-puzzle, vacuum world and 8-queens are toy problems; route finding, touring and the travelling salesperson problem are real-world problems with industrial applications in logistics, circuit-board drilling and vehicle routing. The formulation skills are identical; only the stakes and the messiness differ.

The 8-Puzzle as a Search Problem

The 8-puzzle consists of a 3×3 frame holding eight numbered tiles and one blank square. A tile adjacent to the blank can be slid into it. The object is to reach a specified goal configuration. A typical instance looks like this:

The formulation is as follows.

ComponentDefinition for the 8-puzzle

Path cost1 per move, so the cost of a solution equals the number of moves made.

The single most instructive design decision here is the choice to describe actions as movements of the blank rather than movements of individual tiles. Both descriptions generate exactly the same set of reachable states and exactly the same solutions, so they are equally correct — but they are not equally economical. If actions were "slide tile 5 right", "slide tile 2 down", and so on, the action set would nominally contain eight tiles × four directions = 32 named actions, and the formulation would have to carry preconditions stating that a tile may move only if the blank is adjacent in that direction. With blank-moves the action set has exactly four members, the preconditions reduce to a simple boundary check, and the branching factor is at most four (averaging roughly three over the whole space). Since the cost of search grows roughly as bd, shaving the branching factor is worth far more than any micro-optimisation of the search loop.

The state space contains 9! = 362,880 arrangements of the nine symbols. However, only half of them — 181,440 — are reachable from any given state. The reason is a parity invariant. Define the number of inversions in a configuration as the number of pairs of tiles (ignoring the blank) that appear in the wrong relative order when the board is read row by row. Any blank move left or right leaves the reading order of the tiles unchanged, so inversions are unchanged. Any blank move up or down jumps a tile past exactly two others, so the inversion count changes by 0 or ±2 — always an even amount. The parity of the inversion count is therefore invariant under every legal move. Two configurations with different inversion parity lie in different connected components of the state graph, and no sequence of moves connects them. This has a very practical consequence for formulation: the goal test can be unsatisfiable for a given initial state, and an uninformed search would grind through 181,440 states before reporting failure. A well-engineered formulation performs the parity check as a preliminary solvability test rather than delegating it to the search algorithm.

The 8-puzzle generalises to the 15-puzzle (16!/2 ≈ 1.3 × 1013 reachable states) and the 24-puzzle (≈ 1025 states). These larger versions are the standard testbeds for heuristic search, because the state space explodes faster than the solution depth: optimal 8-puzzle solutions average about 22 moves, while optimal 15-puzzle solutions run to around 53. Finding optimal solutions to the general n-puzzle is NP-hard, which is a reminder that a tidy formulation does not imply a tractable problem.

The Vacuum World

The vacuum world is deliberately minuscule so that every state and every transition can be written down and inspected. In the classic two-square version, a cleaning agent occupies one of two squares, A (left) and B (right), and each square is either clean or dirty.

ComponentDefinition for the two-square vacuum world
StatesThe agent's location combined with the dirt status of each square: 2 locations × 2 dirt-states for A × 2 dirt-states for B = 8 states. Written as, e.g., (AgentIn=A, A=Dirty, B=Dirty).
Initial stateAny of the eight states; the canonical starting point is "agent in A, both squares dirty".
ActionsLeft, Right, Suck. (Richer versions add NoOp for switching off.)
Transition modelLeft/Right change the agent's location; Suck removes dirt from the agent's current square. Moving into a wall leaves the state unchanged.
Goal testNo square contains dirt. The agent's final location is irrelevant, so there are two goal states, not one.
Path cost1 unit per action, so the optimal solution is the shortest action sequence.

Three features of this formulation deserve emphasis. First, the goal test is a predicate over a property of the state, not an equality check against a single stored state. "All squares clean" picks out two of the eight states. Beginners often write the goal test as "state equals (AgentIn=A, A=Clean, B=Clean)", which silently makes the problem harder by forcing the agent to return to A and may force an unnecessary extra move into the optimal path. Whenever the task description contains the phrase "regardless of" or "it doesn't matter where", the goal test should be a property, not a state comparison.

Second, bumping into a wall is modelled as a no-op that leaves the state unchanged. This is a modelling convention with consequences. A self-loop in the state graph means the search tree can contain a child identical to its parent, which an algorithm without a repeated-state check will expand forever. The alternative convention — making Left simply inapplicable when the agent is in A — removes the self-loop and is usually cleaner. Either is defensible, but the choice must be made explicitly and the search algorithm must be compatible with it. The same applies to Suck in an already-clean square: it is either a no-op or an inapplicable action.

Third, the state space is small enough that the entire state graph can be drawn, which makes it an unrivalled teaching device. With eight nodes and at most three outgoing edges per node, one can trace breadth-first search, depth-first search and uniform-cost search by hand and watch the frontier and explored set evolve step by step. From the canonical start state (agent in A, both dirty), an optimal solution is [Suck, Right, Suck] with cost 3; the alternative [Right, Suck, Left, Suck] reaches a goal at cost 4 and is therefore complete but not optimal.

Scaling up exposes the combinatorics: with n squares in a line, the state space has n × 2n states — the agent's location times the dirt status of every square. Ten squares give 10,240 states; thirty squares give over 32 billion. The vacuum world is also the standard vehicle for introducing harder agent settings: if the agent cannot perceive its location or the dirt, the problem becomes a sensorless (conformant) problem whose states are belief states — sets of physical states — and whose state space has 28 = 256 members for the two-square case. A plan such as [Right, Suck, Left, Suck] then works from every possible starting state, which illustrates how changing what the agent knows changes what the state must represent.

The 8-Queens Problem and Alternative Formulations

The 8-queens problem asks for a placement of eight queens on a chessboard such that no queen attacks another; queens attack along rows, columns and both diagonals. There are 92 solutions, reducing to 12 under rotation and reflection. The problem is famous in this context not because it is hard, but because it admits several completely different formulations whose state spaces differ enormously — a perfect demonstration that representation, not algorithm, is often the decisive choice.

Naive incremental formulation. States are any arrangement of 0 to 8 queens on the board; the initial state is the empty board; actions add a queen to any empty square; the goal test checks for 8 queens with no attacks. This is correct but catastrophic. The number of sequences is 64 × 63 × 62 × … × 57 ≈ 1.8 × 1014. Worse, the formulation wastes effort on hopeless lines: it will happily place all eight queens on the first rank and only discover the failure at the goal test, because nothing in the action definition forbids an attacked square.

Restricted incremental formulation. Keep the incremental idea but build the constraints into the action generator. States are arrangements of k queens, one in each of the leftmost k columns, with no queen attacking another. Actions add a queen to any square in the leftmost empty column such that she is not attacked by any queen already placed. The initial state, transition model and goal test are unchanged in spirit. This formulation has roughly 2,057 states — a reduction by a factor of about 1011. Two separate ideas produce this gain: the column restriction removes the pointless permutations of the order in which columns are filled and guarantees no two queens share a column; the non-attack precondition prunes dead branches at generation time rather than at test time. The 8-queens problem is now trivially solvable by depth-first search with backtracking, and the same idea scales to 100 queens.

Complete-state formulation. Every state has all eight queens already on the board, one per column; a state is just a vector such as (3,1,6,2,5,7,4,0) giving each queen's row. Actions move a single queen to another square in her own column. The state space is 88 = 16,777,216 states — larger than the restricted incremental space, but every state is a complete candidate solution that can be scored by the number of attacking pairs. That makes the formulation ideal for local search methods such as hill climbing, simulated annealing and genetic algorithms, which wander the space of complete states looking for one with zero conflicts. Min-conflicts hill climbing with random restarts solves the n-queens problem for n in the millions in a few seconds.

Two points unify the three formulations. First, the goal test is identical in all of them: eight queens on the board, no two attacking each other. The goal is a property of the world, not an artefact of the representation, and it should be written the same way whichever formulation is chosen. Second, the path is irrelevant. Nobody cares in what order the queens were placed or how many times a queen was moved; only the final configuration matters. Problems of this kind are sometimes called configuration or design problems, as opposed to planning problems where the action sequence is the answer. Because the path carries no meaning, path cost can be dropped (or set uniformly to zero/one and ignored), and "optimality" in the classical sense of least-cost path does not apply — which in turn is precisely why local search, which discards paths entirely, is legitimate here but would be nonsense for the 8-puzzle, where the sequence of moves is the whole point of the exercise.

Route Finding and Touring Problems

Route finding is the archetypal real-world search problem: it runs in every satnav, every map website, every airline reservation system and every router on the internet. The basic formulation is reassuringly simple.

  • States. Locations — cities, road junctions, airports, network nodes. In richer versions the state is augmented with extra variables: the current time (because flight departures and traffic conditions are time-dependent), fare class or ticket type, remaining fuel or battery charge, driver hours worked under rest regulations, or the set of seats still available. Each augmentation multiplies the size of the state space.
  • Initial state. The traveller's starting location, together with values for any augmenting variables (the departure time, a full tank, and so on).
  • Actions. Take one of the links leaving the current location: traverse a road segment, board a particular flight, forward a packet on a given interface. In airline problems the action must name the specific flight, not merely the destination, because different flights to the same airport differ in time and price.
  • Transition model. Returns the location reached, plus the updated time, fuel, fare class and so on. For a flight, the new state has the arrival airport and the arrival time; for a road segment, the new junction and the time advanced by the segment's travel time.
  • Goal test. Usually "am I at the destination?", but in practice it can be richer: "am I at the destination before 18:00 with at least 45 minutes of connection slack?".
  • Path cost. Distance in kilometres, travel time in minutes, fuel or energy consumed, monetary fare, tolls, number of transfers, driver comfort, or — most commonly in deployed systems — a weighted combination of several of these. The weights encode the user's preferences, and choosing them is part of the formulation, not an afterthought.

A critical constraint on any of these cost functions is consistency and non-negativity. Step costs must be non-negative, or uniform-cost search and A* lose their guarantees (a negative-cost cycle makes "cheapest path" meaningless, since the cost can be driven to minus infinity by looping). The cost function must also be a function of the step taken, not of the search algorithm's internal state; mixing units — adding minutes to pounds without an explicit exchange rate — produces an incoherent objective and hence an incoherent notion of optimality.

Touring problems look superficially like route finding but are fundamentally different. The task "visit every city in Romania at least once, starting and ending in Bucharest" cannot be formulated with the current city as the state. If the state were just In(Vaslui), the agent would have no way to tell whether it still owed a visit to Craiova, and the goal test would be impossible to write. The state must include the set of cities already visited, for example In(Vaslui), Visited({Bucharest, Urziceni, Vaslui}). The goal test becomes "current city is Bucharest and the visited set contains every city". The transition model adds the newly reached city to the visited set.

The cost of this extra bookkeeping is severe. A map with n cities supports n states in the plain route-finding formulation, but n × 2n states once the visited set is part of the state — one for each combination of current city and subset of visited cities. For 20 cities that is 20 × 1,048,576 ≈ 2.1 × 107; for 50 cities it is about 5.6 × 1016. The exponential term comes directly from the power set of cities.

The travelling salesperson problem (TSP) tightens the touring problem by requiring that each city be visited exactly once and that the total cost of the closed tour be minimal. It is NP-hard, so no known algorithm finds optimal tours in time polynomial in n; the number of distinct tours is (n−1)!/2 for a symmetric complete graph, which is about 6 × 1016 for twenty cities. Exact dynamic programming over the (current city, visited set) state space — the Held–Karp algorithm — runs in O(n22n) time, which is exponential but vastly better than brute-force enumeration, and it is nothing more than systematic search over precisely the state space defined above. In practice, large instances are attacked with heuristic search (A* with a minimum-spanning-tree heuristic) or with local search over complete tours (2-opt, Lin–Kernighan), the latter being the touring analogue of the complete-state 8-queens formulation. TSP formulations underlie real tasks well beyond travel: drilling holes in printed circuit boards, scheduling a robotic arm's movements, routing delivery vans, and sequencing genome fragments.

It is worth noticing how small a change to the task description forces a large change to the state. "Go from Arad to Bucharest" needs one variable. "Go from Arad to Bucharest visiting Sibiu and Craiova on the way" needs a two-bit flag. "Visit all twenty cities" needs twenty bits. The state must contain exactly the information needed to (a) determine which actions are applicable, (b) compute the successor, and (c) evaluate the goal test — no less, or the problem is unsolvable; no more, or the space is needlessly large.

Comparing Formulations: Abstraction and State Space Size

Abstraction is the process of removing detail from a representation. Every formulation above is an abstraction of a messy reality. A real journey from Arad to Bucharest involves travelling companions, the radio station playing, the weather, the road surface, the scenery, the state of the driver's patience and several million other facts. The state In(Arad) discards all of it. Even the actions are abstractions: the single action "drive from Arad to Sibiu" stands in for hundreds of thousands of steering corrections, gear changes and glances in the mirror. Abstraction is not sloppiness; it is the only thing that makes the problem solvable at all, because an agent reasoning over the full detail of the real world would never finish enumerating even one state.

Several distinct abstraction techniques appeared in the examples, and it is worth separating them:

  • Dropping irrelevant state variables. Weather, road surface, fellow passengers and scenery are omitted from the route-finding state because they do not affect which roads exist, where they lead, or (under the chosen cost function) how much a journey costs. If the cost function changed to "expected journey time in winter", the weather would stop being irrelevant and would have to be reinstated — relevance is defined relative to the actions, transitions, goal test and costs, not absolutely.
  • Choosing a coarser action vocabulary. Describing 8-puzzle actions as moves of the blank rather than moves of tiles reduces the branching factor from a nominal set of up to 32 named tile-moves to at most four. Similarly, "drive from Arad to Sibiu" abstracts away the continuous control problem beneath it. The benefit is immediate: search cost scales as bd, so dividing b by a constant divides the work by that constant raised to the power of the solution depth.
  • Building constraints into the generator. The restricted 8-queens formulation prunes illegal and hopeless states before search ever sees them, by refusing to generate a queen in an attacked square or in a column other than the leftmost empty one. This is the difference between generate-and-test and constrained generation, and it accounts for the drop from 1.8 × 1014 sequences to about 2,057 states. The same idea reappears as constraint propagation in constraint-satisfaction solvers and as parity checking in the 8-puzzle.
  • Collapsing many concrete states into one abstract state. Two real journeys that differ only in the colour of the car map to the same abstract state. This many-to-one mapping is what shrinks the space; it is also what must be justified.

Working in the opposite direction, extra bookkeeping in the state makes the space grow combinatorially rather than additively. The table below collects the growth patterns seen in this topic.

Abstraction is cheap and powerful, but it is not free of obligations. A valid abstraction must preserve solvability: every abstract solution must correspond to a solution in the more detailed world. Formally, for each abstract action there must exist a sequence of concrete actions that realises it, and the realisation must be achievable "no matter what" — the abstract plan must not depend on detail that was thrown away. The abstraction In(Arad) → In(Sibiu) is valid because any driver in Arad can in fact get to Sibiu. It would become invalid if the road were closed, if the car had insufficient fuel to reach Sibiu, or if the journey could only be made in daylight and the abstraction had discarded the time of day. Two characteristic failure modes are therefore worth naming:

  • Over-abstraction throws away detail that the solution depends on, producing abstract plans that cannot be executed (a flight itinerary with a four-minute connection, because the abstraction ignored terminal transfer times) or making a solvable problem look unsolvable. The touring problem without a visited set is the cleanest example: the goal test simply cannot be written.
  • Over-rich states retain detail that is irrelevant to actions, transitions, goal test and cost. The problem remains correct but the state space is inflated, duplicate-detection stops working (two states that are identical for all practical purposes are treated as different because they differ in some irrelevant field), and search slows by orders of magnitude. Recording the weather, or the order in which queens were placed, or the full move history inside the 8-puzzle state, are all over-rich.

A useful working test for whether a variable belongs in the state is to ask three questions: does it change which actions are applicable; does it change the result of any action; does it appear in the goal test or in the cost function? If the answer to all three is no, the variable can be abstracted away. If the answer to any is yes, it must stay. Applying the test to the touring problem immediately shows that the visited set must stay (it appears in the goal test), while the order of visits can go (it appears nowhere).

The final lesson from comparing these examples is a strategic one. The restricted 8-queens formulation makes the problem solvable by the simplest possible algorithm — depth-first search with backtracking — while the naive formulation defeats sophisticated algorithms. The touring formulation without a visited set is unsolvable by any algorithm. Describing 8-puzzle actions as blank moves buys a speed-up that no amount of code tuning could match. In short, choosing the representation is a design decision that frequently matters more than the choice of search algorithm. The formulation determines the shape and size of the space; the algorithm only determines the order in which that space is explored. Practitioners therefore spend their effort first on what a state is, what the actions are and what the costs mean, and only afterwards on which search strategy to run over the result.

Search Trees, Nodes, and Expansion

▶

Once a task has been formulated as a search problem — a state space, an initial state, a set of actions, a transition model, a goal test, and a path-cost function — the remaining work is to explore that formulation systematically until a goal state is reached. The data structure that an algorithm builds while it explores is not the state space itself: it is a search tree. Confusing the two is one of the most common sources of error in reasoning about search algorithms, because the two objects have different sizes, different shapes, and different properties. The state space is a static mathematical object that exists whether or not anyone searches it; the search tree is a dynamic, algorithm-specific record of the paths that have actually been considered so far. This topic develops that distinction carefully, dissects the node as a bookkeeping record, explains the mechanics of expansion, introduces the frontier and explored set that together drive every systematic search algorithm, examines the damage done by repeated states and loops, and finishes with the simple pointer-chasing trick that lets an algorithm return an executable plan at the end.

The state space graph. A state space can always be drawn as a directed graph. Each vertex is a distinct state — a configuration of the world at the level of abstraction chosen during problem formulation — and each directed edge from state s to state s' exists exactly when there is an action a applicable in s with RESULT(s, a) = s'. Edges may carry weights, namely the step cost c(s, a, s'). The crucial property is uniqueness: each state appears exactly once. The graph for the Romania route-finding problem has twenty vertices, one per city, no matter how many routes pass through Pitesti. The graph for the two-cell vacuum world has eight vertices (two possible robot positions × two possible dirt conditions per cell = 2 × 2 × 2). The graph for the 8-puzzle has 9! = 362,880 vertices, of which 181,440 are reachable from any given start. These counts are properties of the problem, not of any algorithm.

The search tree. When an algorithm searches, it does not manipulate vertices; it manipulates paths. A node in the search tree stands for one specific path starting at the initial state. If three different routes from Arad reach Bucharest, the search tree contains three different nodes whose state is Bucharest. Nothing is wrong with this — the nodes are genuinely different objects, because they record different histories with different costs — but it means the search tree can be enormously larger than the state space. In the Romania map, with reversible roads, the state space has 20 vertices while the search tree, if cycles are not detected, is infinite: Arad → Sibiu → Arad → Sibiu → … is a legal (if silly) path of unbounded length, and every one of its prefixes is a distinct node.

The root and lazy generation. Every search tree begins with a single node whose STATE is the problem's initial state, whose PARENT is empty, whose ACTION is empty, whose PATH-COST is 0 and whose DEPTH is 0. The rest of the tree is produced on demand. This laziness is not an optimisation detail but a necessity: for the 8-puzzle the complete search tree to depth 20 contains on the order of 220–320 nodes, and for chess the tree is astronomically beyond any storage. The algorithm therefore holds only a thin slice of the tree in memory at any instant — the nodes it has generated but not yet discarded — and generates children of a node only at the moment it decides to expand that node. A useful mental image: the search tree is a potential structure, implicitly defined by the problem, and the algorithm is a torch illuminating one small region of it at a time.

First, DEPTH and PATH-COST coincide only when every step costs exactly 1; when step costs vary, a shallow node may be expensive and a deep node cheap, and conflating the two is a classic bug (it turns uniform-cost search into breadth-first search in disguise). Second, the node is not the state. Two nodes may share a state; comparing nodes for equality is almost never what you want, whereas comparing node.STATE values is exactly what the explored set does. In languages without automatic structural equality, this distinction must be enforced by writing a hash function over states, not over nodes.

function CHILD-NODE(problem, parent, action) returns a node
    s' <- problem.RESULT(parent.STATE, action)
    return a Node with
        STATE     = s'
        PARENT    = parent
        ACTION    = action
        PATH-COST = parent.PATH-COST + problem.STEP-COST(parent.STATE, action, s')
        DEPTH     = parent.DEPTH + 1

Expansion and successor generation. Expanding a node means: take node.STATE, ask the problem's ACTIONS function which actions are applicable there, and for each one build a child node with CHILD-NODE. The children are the node's successors. Precise vocabulary matters here:

  • A node is generated the moment it is created by CHILD-NODE and placed on the frontier. It occupies memory from this moment.
  • A node is expanded when it is removed from the frontier and its own children are produced. It consumes time from this moment.
  • Most algorithms generate far more nodes than they expand; at termination the frontier is full of generated-but-never-expanded nodes. Memory analyses count generated nodes; time analyses typically count expansions (or generations — one must say which).

Consider the 8-puzzle with the blank in the centre. ACTIONS returns {Up, Down, Left, Right} (conventionally described as moves of the blank). Expanding that node generates four children, each with PATH-COST = g(parent) + 1 and DEPTH = depth(parent) + 1. With the blank in a corner, only two actions apply; along an edge, three. The branching factor b is the number of successors produced per expansion — exactly, when it is constant, or on average otherwise. For the 8-puzzle the average is about 3 (roughly 2.13 for a version that forbids undoing the previous move). For chess it is about 35; for the Romania map it is roughly 2.1 (average road degree). Because the number of nodes at depth d is about bd, and the total tree to depth d is O(bd), the branching factor is the single most important number governing whether a search is feasible. Reducing b from 35 to 20 by pruning hopeless actions buys more than doubling the machine's speed.

// Expanding one node
function EXPAND(problem, node) returns a set of nodes
    successors <- empty set
    for each action in problem.ACTIONS(node.STATE) do
        add CHILD-NODE(problem, node, action) to successors
    return successors

The frontier. The frontier (sometimes called the open list) is the collection of all leaf nodes of the partially built search tree that are available for expansion. It is initialised with the single root node. Each iteration of the main loop removes one node from the frontier, tests it for goalhood, expands it, and inserts its children back into the frontier. The algorithm halts when a goal is found or when the frontier empties, the latter meaning that every reachable state has been examined and no solution exists.

The queue discipline — the rule for deciding which node leaves the frontier next — is where the search strategies differ, and essentially nothing else about the skeleton changes:

The explored set. The explored set (or closed list) records the states of all nodes that have already been expanded. It is almost always a hash table or hash set over states, so that membership can be tested in effectively constant time; this requires a canonical, hashable encoding of a state (for the 8-puzzle, the tile permutation as a 9-character string or a packed integer; for the vacuum world, a triple ⟨position, dirtA, dirtB⟩). Note that the explored set stores states, not nodes — it answers the question "have we already finished with this configuration of the world?"

The separation property. The frontier and explored set together carve the reachable state space into three regions: explored states, frontier states, and the unexplored remainder. The key invariant, which holds for every graph-search algorithm, is that the frontier separates the explored region from the unexplored region: every path from the initial state to a state that has not yet been reached must pass through some node currently on the frontier. Geometrically, the explored region is a connected blob containing the start, the frontier is its boundary, and nothing outside can be reached without crossing the boundary. This single property is what makes the algorithms complete — nothing can be missed — and it is also why the frontier must never be allowed to shrink to empty while unexplored reachable states remain. If an implementation discards frontier nodes carelessly (for instance, dropping a frontier node without replacing it) it punches a hole in the boundary and loses completeness.

Space complexity. Memory, not time, is usually what kills a search. The algorithm must simultaneously hold every node on the frontier and every state in the explored set. For breadth-first graph search on a problem with branching factor b and shallowest solution depth d, the frontier alone holds O(bd) nodes and the explored set O(bd−1) states. With b = 10 and one million nodes generated per second at 1 KB per node, depth 10 implies roughly 1010 nodes and 10 terabytes — impossible — long before the three-hour running time becomes the complaint. Depth-first search, by contrast, keeps only the current path plus its siblings, O(bm) nodes for maximum depth m, which is why it survives on deep problems but loses optimality and (without cycle checking) completeness. Whenever you are asked for the space complexity of a search algorithm, the honest answer is a statement about the maximum simultaneous size of the frontier plus the explored set.

Repeated states and redundant paths. A repeated state is a state reached again by a different node. Not every repeat is wasteful in principle, but most are. A redundant path is a path that reaches an already-seen state by a route that is longer than, or no cheaper than, one already known: expanding its endpoint can only rediscover the same subtree of descendants at equal or greater cost. In a rectangular grid world where you may move in four directions, the number of distinct paths of length d from the origin grows like 4d, while the number of distinct states within d steps grows only like 2d2; at d = 20 that is about 1012 paths over roughly 800 states. Ignoring repeats here converts a trivial problem into an impossible one.

Reversible actions and loops. If an action can be undone — moving a tile and moving it back, driving from Arad to Sibiu and back to Arad, moving the vacuum left and then right — the state space contains cycles, and the corresponding search tree contains infinitely deep branches. A depth-first tree search dropped into such a space may descend one of these branches forever and never terminate, even when the state space is finite and tiny. This is why the maxim "algorithms that forget their history are doomed to repeat it" is more than a joke: finiteness of the state space does not imply termination of tree search.

Tree search versus graph search. The two skeletons differ by exactly three lines.

function TREE-SEARCH(problem) returns a solution, or failure
    frontier <- a queue containing the root node (problem.INITIAL-STATE)
    loop do
        if frontier is empty then return failure
        node <- POP(frontier)
        if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
        add EXPAND(problem, node) to frontier          // repeats are never noticed

function GRAPH-SEARCH(problem) returns a solution, or failure
    frontier <- a queue containing the root node (problem.INITIAL-STATE)
    explored <- an empty hash set of states
    loop do
        if frontier is empty then return failure
        node <- POP(frontier)
        if problem.GOAL-TEST(node.STATE) then return SOLUTION(node)
        add node.STATE to explored
        for each child in EXPAND(problem, node) do
            if child.STATE not in explored and child.STATE not on frontier then
                insert child into frontier
            else if child.STATE is on frontier with a higher PATH-COST then
                replace that frontier node with child     // keep the cheaper path

The penultimate test is the classic repeated-state filter; the final clause is the one students most often omit. When step costs vary, discarding a newly generated node merely because its state is already on the frontier can destroy optimality: the new node may represent a genuinely cheaper route. The correct policy is replace, do not discard — if the new node's PATH-COST is lower, swap it in (a decrease-key operation on the priority queue) so that the frontier always holds the best known path to each of its states. With unit step costs and a FIFO frontier this subtlety vanishes, because the first time breadth-first search reaches a state it has already found a shortest path to it; which is precisely why the issue is so easy to overlook when moving from breadth-first to uniform-cost or A* search.

There is also a cost to graph search: the explored set must hold every expanded state, so space becomes proportional to the size of the explored region. This is the root of depth-first search's dilemma — it can either keep its small memory footprint and risk loops, or add cycle checking and lose its chief advantage. Practical compromises include checking only the current path for repeats (eliminating infinite loops at O(depth) cost without eliminating all redundancy) and forbidding the action that simply undoes the parent's action.

Notice how much the explored set is doing: the Left action at the root regenerates the initial state, and without the filter that single reversible pair would seed an unbounded Left–Right–Left–Right branch. Notice also the generated/expanded distinction: by step 5 nine children have been generated, five nodes expanded, and the goal node sits on the frontier awaiting the pop that will trigger the goal test.

Recovering the solution path. A search algorithm must return not a state but a plan: the sequence of actions that transforms the initial state into a goal state. The goal node by itself appears to contain only one action, the last one — but because every node stores a PARENT pointer, the whole history is implicitly present. Starting at the goal node and following PARENT links repeatedly, one walks back up the tree through the node's parent, grandparent, and so on, until reaching the root, whose PARENT is null. Each step of that walk hands back one ACTION field, so the walk produces the actions of the solution in reverse order. Reversing the collected list yields the executable sequence, ready to be handed to the agent for execution.

function SOLUTION(node) returns an action sequence
    actions <- empty list
    while node.PARENT is not null do
        prepend node.ACTION to actions        // or append, then reverse at the end
        node <- node.PARENT
    return actions

Applied to the vacuum-world trace above, the goal node ⟨B, clean, clean⟩ has ACTION = Suck and PARENT = the node ⟨B, clean, dirty⟩, whose ACTION = Right and whose parent is ⟨A, clean, dirty⟩, whose ACTION = Suck and whose parent is the root ⟨A, dirty, dirty⟩. The reversed chain is therefore [Suck, Right, Suck], a three-action plan of cost 3 — which matches the goal node's PATH-COST of 3. That correspondence is guaranteed, not coincidental: because each child's cost is its parent's cost plus one step cost, node.PATH-COST is by construction the sum of the step costs of exactly the actions that SOLUTION returns. The algorithm therefore never needs to re-walk the path to price it; g(n) at the goal is the solution cost, and in an optimal algorithm it is the optimal cost C*.

The memory argument for parent pointers is worth making explicit. An alternative design stores the complete action list inside every node. At depth d that costs O(d) per node and O(d · bd) for a breadth-first frontier — an extra factor of d in both space and in the time to create each child, since the list must be copied. With parent pointers each node stores a constant number of fields, so node creation is O(1) and total space is O(bd). The path is reconstructed once, at the very end, in O(d) time, and only for the single node that matters. The cost of the trick is that nodes cannot be freed while any descendant survives: ancestors of frontier nodes must be retained even though they have already been expanded, which is why the explored region is in practice kept as a graph of retained nodes rather than discarded outright. Some memory-bounded variants (such as iterative-deepening A* or recursive best-first search) sidestep this by re-deriving paths through recursion, trading repeated work for a smaller footprint.

Two final cautions. First, when a graph search replaces a frontier node with a cheaper one, the replacement's PARENT pointer must be updated too — otherwise the algorithm reports the right cost with the wrong plan, or an inconsistent one. Second, the goal test should be applied when a node is selected for expansion, not when it is generated, in any algorithm whose optimality depends on cost ordering (uniform-cost search, A*); testing at generation time can return a goal node whose path is not the cheapest, because a better path to the same goal may still be sitting on the frontier.

Once a problem has been formulated with a state space, initial state, actions, transition model, goal test, and path cost, we need machinery to actually explore it. That machinery is the search tree: a structure that a search algorithm builds as it considers sequences of actions. The crucial idea in this topic is that the search tree is not the same thing as the state space graph. The graph is a fixed description of the world — states connected by actions — while the tree is a record of the paths the algorithm has chosen to examine. A single state in the graph can appear many times in the tree, once for each distinct path that reaches it.

To make this precise, we define a search node as a small bundle of data: the state it represents, a pointer to its parent node, the action that produced it, the cost of the path from the root, and its depth. Expanding a node means applying the applicable actions to its state and generating child nodes for the resulting successors. The nodes generated but not yet expanded form the frontier (sometimes called the open list); the states already expanded are kept in the explored set (closed list). Without an explored set, repeated states produce redundant paths and, in graphs with cycles, infinite loops. Finally, because every node stores a parent pointer, the solution is recovered by walking backwards from the goal node to the root and reversing the sequence of actions.

Evaluating Search Algorithms

▶

Once a task has been formulated as a search problem — a state space, an initial state, a set of actions, a transition model, a goal test and a path cost function — the problem itself is fixed. What remains open is the strategy: the rule that decides, at each step, which of the currently available unexpanded nodes should be expanded next. Remarkably, all of the classical uninformed search algorithms share exactly the same skeleton and differ only in that one decision. Because the problem is the same but the behaviour is wildly different, we need a vocabulary and a set of measurements that let us compare strategies fairly, argue about them on paper, and predict whether a given approach will finish in seconds, in days, or never.

The common skeleton makes the point concrete. Every graph search algorithm can be written as:

function GRAPH-SEARCH(problem) returns a solution or failure
    frontier <- a container holding one node: the initial state
    explored <- an empty set
    loop do
        if frontier is empty then return failure
        node <- REMOVE-CHOICE(frontier)          // <-- the ONLY difference between strategies
        if problem.GOAL-TEST(node.state) then return SOLUTION(node)
        add node.state to explored
        for each action in problem.ACTIONS(node.state) do
            child <- CHILD-NODE(problem, node, action)
            if child.state not in explored and child not in frontier then
                add child to frontier

Replace REMOVE-CHOICE with "remove the oldest node" and you have breadth-first search; with "remove the newest node" and you have depth-first search; with "remove the node of lowest path cost" and you have uniform-cost search. The state space graph is unchanged, but the search tree that is actually built — and therefore the time and memory consumed — can differ by many orders of magnitude.

Why we need evaluation criteria. Suppose you are routing a delivery vehicle across a city with ten thousand junctions. One ordering of the frontier might find a route after examining three hundred junctions; another might wander down a long ring road, revisiting states, and exhaust memory before finding anything. Running both on the full instance to find out which is better is expensive and, on an infinite or very large space, may never terminate. Evaluation criteria let us reason before implementation, using only structural facts about the problem such as how many actions are available per state and how deep the shallowest solution is likely to be. The four standard criteria are:

  • Completeness — is the algorithm guaranteed to find a solution when one exists, and to report failure when none exists?
  • Optimality — if it finds a solution, is it guaranteed to be one of lowest path cost?
  • Time complexity — how long does it take, measured in nodes generated or expanded?
  • Space complexity — how much memory does it need at its peak?

No strategy wins on all four. Breadth-first search buys completeness and (under uniform costs) optimality by paying exponential memory. Depth-first search buys linear memory by surrendering both completeness and optimality. Uniform-cost search guarantees the cheapest solution but may expand enormous numbers of cheap, useless nodes. Selection is therefore always a trade-off, and the criteria are the currency in which the trade is priced.

Completeness in detail. A strategy is complete if, whenever a goal state is reachable from the initial state, the strategy will eventually reach it. The usual phrasing — "it will eventually generate every reachable state" — is a sufficient condition and a useful mental test: if there is any reachable state the strategy could permanently fail to look at, it is incomplete. Two mechanisms cause incompleteness:

  • Infinite paths. In an infinite state space, depth-first search can descend forever down a single branch. Consider the problem of generating a number equal to 100 starting at 0 with the actions "add 1" and "subtract 1". Depth-first search may follow 0, 1, 2, 3, … and succeed by luck, or follow 0, −1, −2, −3, … and never terminate, even though the goal is only a hundred steps away.
  • Cycles (loops). Even a finite state space produces an infinite tree if the graph contains cycles. In a road network you can drive A → B → A → B indefinitely; the search tree has infinite depth although the state space has only a handful of states.

The standard repair is to remember where you have been. A cycle check compares each new node's state against the states on its own ancestor path and discards repeats; it costs memory proportional to the depth of the path only. A full explored set (closed list) records every state ever expanded and discards any duplicate; in a finite state space this makes even depth-first search complete, because each state can be expanded at most once and the number of states is finite. The price is memory proportional to the number of distinct states visited — which, as we will see, can destroy depth-first search's main advantage.

Completeness is always stated relative to assumptions, and those assumptions must be checked for the problem at hand. Breadth-first search is complete only if the branching factor is finite: with infinitely many successors per node, the algorithm would never finish expanding even the root. Uniform-cost search is complete only if every step cost exceeds some small positive ε: if actions can cost zero, the algorithm can be trapped expanding an infinite sequence of zero-cost actions while a cheap goal waits one unit of cost away. Negative step costs break the guarantees of nearly every classical algorithm.

Finally, incompleteness is not automatically disqualifying. If solutions are dense — if a large proportion of leaves at modest depth are goals, as in many constraint-satisfaction-style problems such as placing 8 queens — a fast, memory-light, incomplete method with random restarts may dramatically outperform a complete one. The judgement is pragmatic, not dogmatic.

Optimality in detail. Optimality has no meaning independent of the path cost function chosen during problem formulation. A route that is optimal under "minimise kilometres" may be far from optimal under "minimise travel time" or "minimise toll charges". If the formulation defines cost as the number of actions, then the shallowest solution is by definition the cheapest, and breadth-first search is optimal. The moment step costs vary — a 2 km city street and a 90 km motorway stretch both count as one action — shallowest and cheapest come apart, and breadth-first search loses its optimality guarantee while uniform-cost search retains one based on cumulative cost.

Depth-first search returns the first solution it stumbles upon. In a tree where one branch reaches a goal at depth 40 and another reaches a different goal at depth 4, depth-first search may well return the depth-40 solution simply because of the order in which successors were generated. There is no mechanism for it to know that a better solution exists elsewhere.

Guaranteeing optimality almost always costs something. Uniform-cost search cannot stop when it generates a goal; it must wait until the goal is selected for expansion, because a cheaper route to the same goal may still be lurking in the frontier. That delay translates into extra node expansions and a larger frontier. In practice, many applications accept satisficing solutions: a delivery route within 5% of optimal, computed in 50 milliseconds, is usually worth more than the perfect route computed in 50 seconds. Heuristic methods with bounded suboptimality (for example, weighted A*) formalise exactly this trade.

Measuring time and space. We do not measure time in seconds, because seconds depend on hardware, language and implementation. We count node generations (or equivalently, up to a constant factor, node expansions), treating each as a constant-cost operation: apply the transition model, build a node record, test it, place it in the frontier. Space is measured as the peak number of nodes held in memory simultaneously — the frontier plus the explored set, if one is used. Peak, not total, is what matters, because exceeding available memory causes outright failure, whereas taking a long time merely causes impatience.

Three parameters characterise the search tree:

  • b, the branching factor: the maximum (or, for average-case analysis, the average) number of successors of any node.
  • d, the depth of the shallowest goal node: the length of the shortest solution in actions.
  • m, the maximum depth of the state space: the length of the longest path, which may be infinite.

For the 8-puzzle, the blank tile has 2, 3 or 4 moves depending on whether it is in a corner, an edge or the centre, giving an average branching factor of about 2.67 (around 3 before accounting for the move that immediately undoes the previous one), and the hardest instances have d = 31. For an 8-queens formulation that places one queen per column, b = 8 and d = 8 exactly. For route finding on a road network, b is the average number of outgoing roads per junction — typically 2 to 4 — and d is the number of road segments in the shortest route.

Note the asymmetry between d and m. In an infinite state space, or one with cycles and no cycle checking, m is unbounded, so a bound like O(bm) carries no information at all: it is a formal way of saying "this may never terminate". This is exactly why the analysis of depth-first search is so sensitive to whether the space is finite.

Exponential growth and the branching factor. A uniform tree with branching factor b has b nodes at depth 1, b² at depth 2, and bd at depth d; the total down to depth d is b + b² + … + bd = O(bd), dominated overwhelmingly by the deepest level. Breadth-first search must generate essentially all of these nodes and, because every node at the deepest completed level sits in the frontier at once, it must also store O(bd) of them. Depth-first search generates in the worst case all O(bm) nodes, but it only ever stores the nodes on the current path plus their unexpanded siblings: m levels with at most b nodes each, hence O(bm).

Two lessons follow. First, adding two levels of depth multiplies the cost by 100; the difference between a tractable and an impossible problem can be a single extra action in the solution. Second, and more importantly for algorithm design, reducing b beats buying faster hardware. Doubling processor speed halves the running time — equivalent to a fraction of one extra level of depth. But reducing the effective branching factor from 10 to 5 at depth 12 cuts the node count from 1012 to about 2.4 × 108, a factor of roughly four thousand. This is precisely what a good heuristic does: it does not make each node cheaper to process, it makes most nodes unnecessary to process at all. The quality of a heuristic is often reported as its effective branching factor b*, the branching factor a uniform tree would need to contain the same number of nodes that the heuristic search actually generated, and a value close to 1 indicates excellent guidance.

Memory as the binding constraint. Students usually expect time to be the limiting factor, but in practice a search that needs 100 gigabytes fails immediately, whereas a search that needs two minutes merely annoys. Breadth-first search's fatal flaw is that an entire frontier level — O(bd) nodes — must coexist in memory. At a million nodes per second and a kilobyte per node, memory runs out in minutes while there are still hours of processing time available in the budget.

Depth-first search inverts the profile: linear O(bm) memory, no completeness, no optimality. Iterative deepening depth-first search resolves the dilemma by running depth-limited depth-first searches with limits 0, 1, 2, 3, … until a solution is found. It inherits depth-first search's O(bd) memory and breadth-first search's completeness and (under uniform step costs) optimality, because the first solution found is at the shallowest depth at which any solution exists.

The obvious objection is wasted work: the nodes at depth 1 are generated d times, those at depth 2 are generated d−1 times, and so on. But exponential growth makes this cheap, because the deepest level dominates and is generated only once. With b = 10 and d = 5, iterative deepening generates 50 + 400 + 3,000 + 20,000 + 100,000 = 123,450 nodes against breadth-first search's 111,110 — an overhead of about 11%, in exchange for reducing peak memory from roughly 100,000 nodes to about 50. As b grows the overhead shrinks further, tending towards b/(b−1). The general principle is worth internalising: when costs grow exponentially with depth, repeating the shallow work to save memory is almost always a good trade.

An explored set presents the mirror-image trade. It eliminates repeated states — essential in spaces like the 8-puzzle, where the tree of 322 ≈ 3.1 × 1010 paths collapses onto only 181,440 reachable states — but it costs memory proportional to the number of distinct states visited. Adding a full explored set to depth-first or iterative-deepening search therefore sacrifices the very linear-memory property that motivated choosing them. The usual compromise is cycle checking against the current path only: cheap, memory-light, and sufficient to prevent infinite loops, though it will not prevent the same state being re-reached via a different branch.

A disciplined selection procedure runs roughly as follows.

  • Decide whether optimality is genuinely required. If the task is "find any legal configuration" — as in 8-queens — optimality is meaningless and a cheap, memory-light strategy is appropriate. If the task is "find the cheapest delivery route", you need uniform-cost search, A*, or an explicit suboptimality bound you are willing to defend.
  • Check whether step costs are uniform. If they are, breadth-first and iterative-deepening search are optimal and you can avoid the overhead of a priority queue. If they are not, be explicit that shallowest ≠ cheapest, and move to uniform-cost or heuristic search.
  • Estimate b and d before implementing. Count the typical number of applicable actions per state for b, and estimate the length of a plausible solution for d. Compute bd. If it is 106, implement whatever is simplest. If it is 1012, do not write the code yet.
  • Check for infinite depth and cycles. If the state space is infinite (unbounded counters, continuous coordinates discretised without limit) or heavily cyclic (any navigation graph), rule out plain depth-first search and either add cycle detection or choose iterative deepening or breadth-first search.
  • Check the memory budget, not just the time budget. Multiply the predicted peak node count by the bytes per node. If the result exceeds available RAM, prefer a linear-space strategy such as iterative deepening even at the cost of regenerating nodes.
  • If bd is infeasible, do not just pick a different uninformed strategy — change the problem. Uninformed strategies are all exponential; swapping one for another buys a constant factor or a memory profile, not a complexity class. The real gains come from improving the formulation (coarser abstraction, fewer irrelevant state variables, pruning symmetric or redundant actions, a better action set) or from adding heuristic guidance that reduces the effective branching factor.

A concrete illustration: the 15-puzzle has about 1013 reachable states and solutions averaging 53 moves,with b ≈ 2.13 after excluding the inverse move; blind breadth-first search would need on the order of 2.1353 ≈ 1017 node generations and far more memory than exists. Iterative deepening fixes the memory problem but not the time problem. Adding the Manhattan-distance heuristic to an IDA* search drops the effective branching factor to roughly 1.5, bringing the node count down to the order of 109 — solvable in minutes on an ordinary machine. Nothing about the hardware changed; the formulation gained information, and the exponent's base shrank. That single comparison encapsulates why the four criteria matter: they tell you, before a line of code is written, whether you need a better algorithm, a better formulation, or simply a bigger coffee.

A worked critique. Suppose a student proposes solving a warehouse-robot routing problem with depth-first search on a grid of 200 × 200 cells, with states recording the robot's position, the battery level to two decimal places, and a timestamp. The criteria expose three faults at once. Time: including the timestamp makes the state space effectively infinite and acyclic in a useless way, so m is unbounded and O(bm) is a non-answer. Completeness: on a cyclic grid without an explored set, depth-first search can loop forever; with the timestamp in the state it never recognises a loop, because no two states are ever equal. Optimality: if the cost function is distance travelled but actions have differing lengths (diagonal versus orthogonal moves), depth-first search's first solution carries no guarantee whatsoever. The fix is formulation-level — drop the timestamp, discretise or drop the battery level if it is not needed for the goal test, and then apply uniform-cost or A* search on a space of only 40,000 states, where b ≤ 8 and d ≤ 400 and the whole problem becomes trivial.

Once you can formulate a problem as a state space, the next question is how to choose a strategy for searching it. Different search algorithms explore the same state space in very different orders, and they differ in whether they are guaranteed to find a solution at all, whether the solution they find is the cheapest one, how long they take, and how much memory they consume. These four questions — completeness, optimality, time complexity, and space complexity — are the standard criteria used throughout AI to compare search strategies.

Complexity in search is normally expressed with three quantities: the branching factor b (how many successors a node has on average), the solution depth d (how deep the shallowest goal lies), and the maximum depth m of the search tree. Costs like O(b^d) grow explosively, so a modest increase in depth or branching factor can make an otherwise reasonable algorithm unusable. In practice memory is usually the binding constraint: an algorithm that stores an exponential frontier will exhaust RAM long before you run out of patience waiting for it.

Applying the Framework to New Problems

Applying the Framework to New Problems

▶

Most real scenarios arrive as prose: a paragraph from a stakeholder, a ticket in an issue tracker, a description of a warehouse floor. None of that is a search problem yet. A search problem is a precise mathematical object — a set of states, a designated starting point, a set of actions with a deterministic successor rule, a predicate that recognises success, and a numeric cost attached to each step. The work of formulation is the disciplined translation from the prose to that object. This translation is where most of the intellectual difficulty of applied search lives: once a problem is formulated well, the algorithms are off-the-shelf; formulated badly, no algorithm can rescue it. The sections below give a repeatable procedure for performing that translation, a way of choosing the level of detail to keep, a validation routine to run before writing any search code, and a catalogue of the three failure modes that account for the majority of broken formulations in practice.

A step-by-step formulation procedure

The procedure below is deliberately ordered. Each step constrains the next, and skipping ahead — in particular, inventing a state representation before you know who the agent is and what it controls — is the usual root cause of bloated or unusable models.

Step 1 — Identify the decision-making agent and the aspects of the world it can actually change. Write down, in one sentence, whose decisions the search is producing. Then split the world into three buckets: things the agent changes by acting, things that change on their own, and things that never change. Only the first bucket belongs in the state; the third bucket is background knowledge that can be hard-coded or stored in the problem object; the second bucket signals that you may have a non-deterministic or dynamic problem and may need to either fix it by assumption or move to a different framework.

Consider a hospital delivery robot. The stakeholder says: "The robot collects medication trays from the pharmacy on level 2 and delivers them to nurse stations. It should not keep patients waiting and the battery should not run flat." The agent is the robot's route planner. It changes its own location, which trays it is carrying, and its battery level. It does not change the building layout, the positions of the lifts' shafts, or the contents of a tray. Corridor congestion changes on its own — a candidate for abstraction away, or for an assumption such as "corridors are modelled as always traversable at a fixed average speed".

Step 2 — Choose a state representation that captures exactly the information needed to decide the next action. The operational test is the Markov question: if I handed you only this state description and nothing about how it was reached, could you determine the legal actions and their outcomes? If yes, the representation is sufficient. If it contains anything you would never consult to answer that question, it is excessive. For the delivery robot, a reasonable state is:

State = (location, carried_trays, battery_level)
  location      ∈ {pharmacy, lift_L2, lift_L3, ward_A, ward_B, ward_C, charger}
  carried_trays ⊆ {t1, t2, t3}        # a set, not a list
  battery_level ∈ {0, 1, ..., 100}    # integer percentage

Note the deliberate choices already made: carried_trays is a set because the order in which trays were picked up never affects anything; battery is an integer percentage rather than a float voltage because a one-percent resolution is enough to decide whether to detour to the charger.

Step 3 — Specify the initial state from the scenario's starting conditions. The initial state must be a single, fully-instantiated member of the state space — not a description of a class of situations. "The robot starts its shift" is not an initial state. (pharmacy, {}, 100) is. If the scenario genuinely admits several starting configurations, you either run one search per starting configuration, or you add a dummy initial state whose actions are "choose starting configuration i" at zero cost.

Step 4 — Define the action set and the transition model. Actions are named, discrete, and parameterised; the transition model RESULT(s, a) maps a state and an applicable action to exactly one successor state. Alongside RESULT you need ACTIONS(s), the applicability test, which is what keeps illegal successors out of the search tree.

ACTIONS(s):
  for each neighbour n of s.location in corridor_graph:
      if s.battery_level >= cost_watts(s.location, n):
          yield Move(n)
  for each tray t at s.location awaiting pickup:
      if |s.carried_trays| < 2: yield Pickup(t)
  for each tray t in s.carried_trays with destination == s.location:
      yield Deliver(t)
  if s.location == charger: yield Charge

RESULT(s, Move(n))    = (n, s.carried_trays, s.battery_level - cost_watts(s.location, n))
RESULT(s, Pickup(t))  = (s.location, s.carried_trays ∪ {t}, s.battery_level - 1)
RESULT(s, Deliver(t)) = (s.location, s.carried_trays \ {t}, s.battery_level - 1)
RESULT(s, Charge)     = (s.location, s.carried_trays, 100)

Two properties are worth checking at this point. First, RESULT is a total function on applicable pairs: every legal action yields a state, never an error and never "nothing happens". Second, successor states are built fresh rather than by mutating the parent — a state that is mutated after being placed on the frontier corrupts the search.

Step 5 — Write the goal test as a checkable predicate over states. Translate "all deliveries complete and the robot parked" into code that looks only at a state:

GOAL_TEST(s)  ≡  s.carried_trays == {} and all_trays_delivered(s) and s.location == charger

If all_trays_delivered cannot be answered from s alone, the representation is incomplete — which is a signal to add a delivered set to the state, or to re-define carried_trays as a vector of tray statuses. This is the healthy direction of influence: the goal test exposes a missing field, rather than the state hoarding fields "just in case".

Step 6 — Attach a path cost function reflecting the quantity actually to be minimised. The stakeholder said patients should not wait, so the objective is elapsed time, not distance and not energy. Energy belongs in the constraints (via the applicability test on battery level), not the objective. So STEP_COST(s, a, s') returns seconds: corridor traversal time for Move, a fixed handling time for Pickup/Deliver, and the full recharge duration for Charge. Path cost is the sum of step costs, and the search now genuinely optimises the thing the hospital cares about.

Choosing the right level of abstraction

Abstraction is the act of deciding what the real world contains that your state will not mention. Every usable formulation is an abstraction: a real robot has a continuous pose, wheel slip, a camera buffer and a battery chemistry curve, yet the state above mentions none of it. The question is never "should I abstract?" but "how far, and is this particular abstraction legitimate?"

Include a detail only if it can change which action is optimal. This is the sharpest available filter. Apply it as a counterfactual: imagine two runs of the system identical except for the detail in question. Does the best next action differ? If the robot's exact millimetre offset within a corridor never changes whether it should turn left or right at the next junction, the offset does not belong in the state. If, however, the robot carries trays for two different wards and the better route depends on which wards, then the set of carried trays does change the optimal action and must stay. Note that the test is about optimality of action, not about realism: a detail can be perfectly real and still irrelevant.

Collapse sequences of fine-grained real actions into single abstract actions. Real execution of "move from the pharmacy to ward A" involves hundreds of motor commands, obstacle avoidance manoeuvres and door-opening sub-behaviours. Modelling them explicitly would inflate the state space by many orders of magnitude without ever changing the route chosen. So they are packaged into one abstract action whose cost is the expected duration of the whole package. Similarly, a flight-booking formulation uses the abstract action "take flight BA117" rather than "walk to gate, board, taxi, take off…"; an 8-puzzle formulation uses "slide tile left" rather than the physics of a finger pushing plastic.

A valid abstraction must guarantee that abstract solutions remain executable. This is the correctness condition, and it is easy to state: for every abstract action in the plan, there must exist some real sequence of low-level actions that carries the agent from any real state consistent with the abstract source state to some real state consistent with the abstract successor state. If "move to ward A" is sometimes impossible — because a fire door is locked at night, say — then the abstraction is invalid as written, and must be repaired, either by adding a time-of-day field to the state, or by removing that corridor edge from the graph, or by restricting the problem to daytime shifts. An abstraction that produces plans the agent cannot carry out is worse than no plan at all, because the failure surfaces only at execution time.

Test the abstraction by asking whether two states you called identical would ever require different behaviour. This is the dual of the first test and catches over-abstraction. Suppose, trying to shrink the state space, you drop battery_level. Now the state (ward_C, {t3}) covers both a robot with 95% battery and a robot with 3% battery. Would those two situations ever require different behaviour? Obviously yes — one should deliver, the other should divert to the charger. The merge is therefore illegitimate and the field must return. Run this test on every field you are tempted to delete and every pair of situations you are tempted to collapse; it is the single most reliable guard against an abstraction that is too aggressive.

Validating a formulation

A formulation should be validated before it is handed to a search algorithm, because almost every formulation defect manifests as the same unhelpful symptom — "the search returns failure" or "the search never terminates" — and debugging it from that symptom alone is slow. Five concrete checks catch most problems.

Confirm the initial state satisfies the same representation rules as all other states. Write an is_valid_state(s) invariant checker and run it on the initial state first. Typical catches: the initial state is given as a list where successors are sets; it omits a field that RESULT always writes; a puzzle's initial board is supplied with a 0 for the blank while successors use None. These mismatches break equality and hashing, so the initial state never matches a later-generated identical state and the explored set silently stops working.

assert is_valid_state(initial)
for a in ACTIONS(initial):
    assert is_valid_state(RESULT(initial, a))

Check that every action produces a state the goal test can legally evaluate. Generate a few hundred random reachable states (random walks from the initial state are fine) and call GOAL_TEST on each. It should return True or False every time — never raise an exception, never return None, never depend on a field that some successors lack. A goal test that crashes on an unusual successor is a latent bug that will appear only after a long search.

Verify that at least one path from the initial state to a goal exists in small instances. Shrink the problem until you can solve it by hand — two trays and three rooms; a 2×2 sliding puzzle; four queens instead of eight — and confirm both that your hand solution is a legal action sequence under RESULT, and that breadth-first search finds some solution. This separates "my formulation is unsolvable" from "my algorithm is broken", which is otherwise very hard to distinguish.

Count the reachable states to confirm the state space size is what you expected. Run an exhaustive breadth-first enumeration on the small instance and compare the count against a hand calculation. If you predicted 7 locations × 2³ tray subsets = 56 reachable states (ignoring battery) and the enumeration reports 448, you have an extra factor of 8 somewhere — perhaps the tray set is being stored as an ordered list, so {t1,t2} and {t2,t1} count as different states. If the enumeration reports 12, some actions are not applicable where you thought they were. A mismatch in either direction is a genuine finding, and this check frequently exposes over-rich states before they cause performance problems.

Confirm the cost of a hand-computed optimal path matches your intuition about the real problem. Take the small instance, compute the optimal path by hand, and compare its cost with reality. If a route you know takes about six minutes comes out as cost 420, your units are inconsistent somewhere. If two obviously different-quality routes come out with identical cost, your cost function is not discriminating on the dimension you care about. This final check validates the objective, which none of the earlier checks touch.

Common error: over-rich states

An over-rich state carries information that the transition model never reads and the goal test never consults. It is the most common formulation error because it feels safe — "I will include the timestamp, just in case" — and because its damage is invisible until the search runs.

Redundant attributes multiply the state space without improving solution quality. State space size is the product of the ranges of the fields. Adding a steps_taken counter to a 104-state problem where paths can be up to 200 steps long multiplies the space by 200, to 2×106, and the solutions found are exactly the same ones. Adding a timestamp with second resolution over an eight-hour shift multiplies it by nearly 29,000. The table below shows how quickly this compounds for the delivery robot.

Over-rich states defeat repeated-state detection because equivalent situations no longer compare as equal. Graph search depends on the explored set recognising that a newly generated state has been seen before. If the state carries a step counter, then reaching ward A in 4 moves and reaching ward A in 6 moves produce different states, both are expanded, and the search degenerates from a graph search over a small space to a tree search over an exponentially larger one. A state containing the full path history is the pathological case: no two states are ever equal, the explored set never fires, and a problem that should solve in milliseconds runs forever. This is why "add the path to the state so I can print it later" is always wrong — the path belongs to the node, a bookkeeping wrapper in the search tree, not to the state, which is a description of the world.

Remove any attribute derivable from the rest of the state or never read by the transition model. Two mechanical tests. First, derivability: if blank_position can be computed from the tile array, do not store it as part of the identity of the state (cache it outside the equality/hash definition if you want the speed). Second, read-usage: instrument ACTIONS, RESULT, GOAL_TEST and STEP_COST, run a few thousand expansions, and list which fields were ever read. Any field read by none of them is dead weight and should be deleted.

Symmetry often signals that several state descriptions should be merged into one. In the 8-queens problem, a board is unchanged in difficulty under reflection and rotation, and column-by-column placement already removes the symmetry of queen ordering — placing queens as a set rather than a sequence shrinks the space from roughly 1.8×1014 ordered placements to about 2,057 reachable configurations under incremental column assignment. In the delivery robot, representing carried trays as a set rather than a list merges all orderings of the same load. In a puzzle with interchangeable identical pieces, treating the pieces as distinguishable multiplies the space by the factorial of the number of duplicates for no benefit. Whenever you notice that two state descriptions "mean the same thing operationally", canonicalise: define a normal form (sorted tuple, lexicographically smallest rotation, frozen set) and map every state into it before hashing.

Common error: ill-defined goal tests

Avoid goal conditions that depend on the path taken rather than the state reached. "Visit every ward and return to the charger" is not a predicate over the states defined earlier: given (charger, {}), you cannot tell whether every ward was visited. Two legitimate repairs exist. Either enrich the state with a visited set, accepting the resulting 2n blow-up because the information genuinely is needed (this is what turns route-finding into a travelling-salesman-style problem); or re-express the objective so it is state-checkable, for example by tracking undelivered trays rather than unvisited rooms. What you must not do is write a goal test that peeks at the node's parent chain while pretending the problem is a plain state-space search — that quietly invalidates the explored set, since two nodes with the same state but different histories are no longer interchangeable.

Make sure the goal test is cheap, since it runs on every generated node. If the goal test re-solves a constraint satisfaction problem or queries a database, it will dominate runtime. A test like "is the board sorted?" is O(n) and fine. A test like "is this configuration reachable from the target by some other planner?" is not. Where a natural goal condition is expensive, cache aggressively or maintain an incremental counter in the state — for example, store num_misplaced and update it by ±1 in RESULT, so the goal test becomes num_misplaced == 0, an O(1) comparison.

Handle multiple acceptable goal states with a predicate, not a single enumerated target. Many problems have a large or implicit goal set. In 8-queens there are 92 solutions, and nobody enumerates them in advance; the goal test is "eight queens placed and no two attacking". In route finding where any of several car parks is acceptable, the goal test is s.location ∈ acceptable_parks. Writing the test as s == specific_goal_state when the problem actually accepts a family of states makes the search work harder than necessary and can make a solvable problem look unsolvable.

# Brittle: only one target accepted
GOAL_TEST(s) ≡ (s == (charger, {}, 100))        # battery must be exactly 100?!

# Robust: a predicate over the properties that matter
GOAL_TEST(s) ≡ (s.location == charger and s.carried_trays == {} and s.undelivered == {})

The brittle version above also illustrates a subtler trap: over-specifying irrelevant fields. Demanding an exact battery level turns a reachable goal into an almost-unreachable one.

An unreachable orcontradictory goal condition causes a complete algorithm to exhaust the space and report failure. Breadth-first search on a finite state space will eventually enumerate everything reachable from the initial state and then return failure — correct behaviour, but expensive and uninformative. Contradictions are often accidental: requiring s.carried_trays == {} and simultaneously t3 ∈ s.carried_trays; requiring a sliding puzzle to reach a configuration in the opposite parity class from the initial board (exactly half of all 8-puzzle configurations are unreachable from any given start, because a legal move always preserves the parity of the permutation plus blank row distance); requiring the robot to end at a charger that no corridor edge reaches. Before concluding "no solution exists", always (a) run the goal test directly on a few hand-built states you believe should qualify, and confirm it returns True, and (b) check that the goal condition is satisfiable by some syntactically valid state at all, independently of reachability. If no valid state satisfies it, the bug is in the predicate; if valid states satisfy it but search cannot reach them, the bug is in the actions, the transition model, or the problem instance itself.

Common error: inconsistent cost functions

The cost function is the least-scrutinised component and the one most likely to make a technically correct search produce an answer the stakeholder rejects. Three classes of defect recur: mixed units, illegal cost values, and a mismatch between the modelled objective and the real one.

Use one consistent unit for all action costs across the whole problem. Costs are summed, so they must be commensurable. A formulation that charges kilometres for Move, 5 for Pickup and 30 for Charge is adding kilometres to unnamed integers; the resulting "optimal" path is optimal with respect to a quantity that does not exist. Pick a unit — seconds, metres, pounds, number of actions — declare it in a comment next to the cost function, and convert every action's cost into that unit explicitly.

ActionInconsistent costsConsistent costs (seconds)Conversion applied
Move along corridor42 (metres)42 m ÷ 1.4 m/s ≈ 30distance ÷ speed

Under the inconsistent column, charging appears free and the planner will happily top up the battery between every delivery; under the consistent column, a 900-second recharge is correctly treated as the major commitment it is.

Non-negative step costs are required for standard uniform-cost and heuristic search guarantees. Uniform-cost search pops the cheapest frontier node and relies on the fact that extending a path can never make it cheaper; A* relies on the same property plus admissibility. Introduce a negative step cost — "delivering a tray earns −10 because it pleases the ward" — and that reasoning collapses: a node popped as cheapest may later be reachable more cheaply, and the first goal node popped need not be optimal. If the problem genuinely has rewards as well as costs, model it as maximisation of utility with an appropriate algorithm, or re-scale so every step cost is non-negative (for example, cost = baseline_time − bonus, with the baseline chosen so the result is never below zero), being explicit about what the re-scaling does to the ordering of solutions.

Zero-cost cycles can let an algorithm loop indefinitely without increasing path cost. A step cost of exactly zero is legal for uniform-cost search's optimality argument but dangerous for termination: if a cycle of zero-cost actions exists — "rotate in place", "toggle a flag and toggle it back", "re-scan the shelf" — then infinitely many distinct paths share the same cost, and a tree search can expand them forever without the cost bound ever advancing. Two defences: run graph search with an explored set so repeated states are discarded, and insist on a small strictly positive cost ε for every action unless you have a specific reason not to. Formally, optimal search algorithms are usually stated as complete only when every step cost is at least some ε > 0 and the branching factor is finite.

If the stated objective is "fewest actions", every action should cost exactly one. This sounds trivial but is violated constantly, usually by importing a plausible-looking distance metric into a problem that did not ask for it. In the 8-puzzle the task is to solve the puzzle in the fewest moves, so every slide costs 1, and breadth-first search is then optimal. If instead you charge each slide by the Manhattan distance the moved tile travels — always 1, so no harm here — or by some invented "difficulty" value, the search minimises the wrong total and may return a 24-move sequence in preference to a 22-move one. Conversely, if the real objective is driving time, do not fall back on unit costs: with unit costs, a route-finder prefers a path with three 80-kilometre motorway legs over a path with four 2-kilometre urban legs, which is plainly wrong. Match the cost to the stated objective, and when the objective is "fewest actions" resist the urge to be clever.

Check that the cost you minimise is genuinely the quantity the stakeholder cares about. This is the final and most important validation. The hospital said "patients should not be kept waiting", which is a statement about delivery latency, not about total route duration — and those differ. A plan that delivers all three trays at minute 30 has a worse average wait than a plan that delivers them at minutes 8, 16 and 32, even though the second plan takes longer overall. If average wait is what matters, the cost model must accumulate per-tray waiting time, which in turn means the state needs enough information to compute it (elapsed time, and which trays remain). Notice the cascade: fixing the objective forced a change in the state representation. This is normal and healthy, and it is precisely why the cost function should be settled before the state is frozen, and why the validation step "does the hand-computed optimal cost match intuition?" is worth the effort. Common mismatches to look for include optimising distance when money matters (tolls and fuel are not proportional to distance), optimising expected time when worst-case reliability matters, and optimising a single trip when throughput across a shift is what the business measures.

Putting it together: a worked micro-example

Scenario: "A warehouse picker starts at the packing bench, must fetch items A and B from shelves, and return to the bench. Minimise walking time." Applying the procedure: the agent is the picker; it changes its location and what it holds. State = (location, held) with held ⊆ {A, B}; the initial state is (bench, {}); actions are Walk(x) for adjacent nodes and Grab(i) when the item is at the current shelf; the goal test is s.location == bench and s.held == {A, B}; step cost is walking seconds, with Grab costing a fixed 3 seconds. Validation: the state space has 4 locations × 4 subsets = 16 states — small enough to enumerate and check by hand; breadth-first finds a path; the hand-optimal route takes 46 seconds, matching a stopwatch estimate. Error checks: no step counter or visit history in the state (not over-rich); held is a set, collapsing the symmetric "grabbed A then B" and "grabbed B then A" descriptions; the goal test reads only state fields (well-defined, and cheap); all costs are in seconds and strictly positive (consistent). The formulation is ready for search.

So far you have seen problems that arrive pre-packaged: the 8-puzzle, the vacuum world, route finding on a tidy map. Real scenarios do not arrive that way. Someone hands you a messy description — scheduling deliveries, assembling a product, routing a robot through a cluttered room — and your job is to decide what counts as a state, what an action is, when you are done, and what a step costs. This topic gives you a repeatable procedure for doing that translation and for checking your answer before you spend hours implementing a search that was doomed by its formulation.

Two ideas carry most of the weight. The first is abstraction: a good state records exactly the detail that affects which actions are legal and whether the goal is reached, and nothing more. Pack in extra attributes and the state space explodes; strip out too much and the solution you find no longer maps back to a real plan. The second is validation: before you trust a formulation, you check that the goal test is a crisp predicate over states rather than a vague wish, that the cost function is consistent and non-negative in a single unit, and that the initial state is actually reachable toward some goal.
