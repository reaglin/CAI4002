Why Problem Formulation Matters

▶

Almost every introductory treatment of artificial intelligence begins with search, and almost every disappointment with search begins with a bad problem formulation. The algorithms themselves — breadth-first search, uniform-cost search, A* — are short, well understood, and provably correct under stated conditions. What varies enormously from one application to another is the description of the problem that we hand to those algorithms. That description is not given to us by the world; it is constructed by a designer who decides what counts as a situation, what counts as a move, and what counts as success. The quality of those decisions determines whether a problem is solved in milliseconds, solved after a week of computation, or never solved at all. This topic examines the translation step from a messy real task to a precise computational object, the standard parts that object must have, and the judgement calls — above all, abstraction — that make the difference between a workable and an unworkable formulation.

From a real task to a search problem

A search problem is a task in which an agent must find a sequence of actions leading from a starting situation to a desired situation. The emphasis on sequence matters. Many computational tasks ask for a single answer — classify this image, predict tomorrow's temperature — and are not search problems in this sense. A search problem asks for a plan: do this, then this, then this, and you will have arrived. The output of a search algorithm is therefore a path, and the quality of the output is judged by both the destination (does it satisfy the goal?) and the route (how expensive was it?).

The striking property of this framing is that the agent needs no task-specific cleverness at all. A breadth-first search routine contains no knowledge of maps, puzzles, chemistry, or logistics. It knows only how to ask three questions repeatedly: Is this state a goal? What actions are available here? Where does each action lead? Given honest answers, it will systematically enumerate possibilities until it finds a solution. All of the domain intelligence has been pushed into the description. This is a genuine engineering advantage, because it means one well-tested implementation can serve many domains — but it is also the source of the risk, because the algorithm cannot compensate for a description that is wrong, redundant, or astronomically large.

Consider a traveller in Arad, Romania, who must reach Bucharest by tomorrow. The real task is awash in irrelevant detail: the colour of the car, the price of petrol at each station, the passengers' conversation, the weather, the exact position of the vehicle on the carriageway measured in centimetres. The formulation step discards all of this and declares that a state is simply the name of the city the traveller is currently in, an action is driving along a road to an adjacent city, and the goal is being in Bucharest. The resulting problem has twenty states and can be solved by hand. Nothing about the real journey has been made impossible by this simplification: every abstract plan such as Arad → Sibiu → Fagaras → Bucharest can actually be driven.

The same translation can be performed on tasks that look nothing like navigation. Assembling a protein-folding sequence, scheduling aircraft turnarounds, routing a packet, configuring a product line, solving a Rubik's cube, and planning a robot's grasp can all be cast in this mould. Once cast, they all accept the same algorithms. The formulation is the universal adapter between the world and the solver.

The standard components of a formulation

A problem formulation in the classical framework consists of five components. They are not arbitrary: each one answers a question that any systematic explorer must be able to ask.

The state is a description of the relevant configuration of the world at one moment. "Relevant" is doing an enormous amount of work in that sentence, and the section on abstraction below is devoted to unpacking it. The state space is the set of all states reachable from the initial state by any sequence of actions; it is usually defined implicitly, by giving the initial state and the transition model, rather than by listing states, because listing them is often impossible.

The initial state anchors the search. It need not be a single state in every variant of the framework — some problems have a set of possible starting points — but in the classical formulation it is one definite state. The goal test is a predicate applied to a state, returning true or false. Crucially, a goal test need not name a specific state. In the 8-queens problem the goal test is "no two queens attack each other", which is satisfied by 92 distinct boards; in a chess endgame it may be "the opponent is checkmated"; in a shopping task it may be "the basket contains milk, bread, and coffee" regardless of the order they were added.

The actions function, written Actions(s), returns the set of actions applicable in state s. The transition model, written Result(s, a), returns the state reached by performing action a in state s. Together they define the directed graph that search explores: nodes are states, edges are actions. Note that the pair must agree — if Actions offers a move that Result cannot evaluate, or offers a move that would produce an illegal state, the formulation is broken. In the 8-puzzle, Actions must exclude sliding the blank off the edge of the board; one may instead define all four moves always and have Result return the unchanged state for illegal ones, but then the state space contains self-loops that waste search effort.

Path cost is a function assigning a number to a sequence of actions, almost always as the sum of individual step costs c(s, a, s'). Its purpose is to make solutions comparable so that "optimal" means something. Without a cost function one can only speak of finding a solution; with one, we can ask for the cheapest. Two properties are usually required for the standard optimality guarantees of algorithms such as uniform-cost search and A*: step costs must be non-negative, and (for most practical purposes) bounded away from zero by some small ε. Negative step costs allow a search to improve a path forever by going round a loop, and zero-cost loops allow an infinite path of finite cost, both of which break termination and optimality arguments.

Formulation determines tractability

The combinatorial consequence of a formulation decision is rarely intuitive, because state spaces grow multiplicatively. Each independent feature you store in a state multiplies the number of distinct states by the number of values that feature can take. Adding one Boolean doubles the space; adding a variable with ten values multiplies it by ten.

Take the vacuum world. With two locations and a Boolean dirt flag per location, plus the robot's location, the state space has 2 × 22 = 8 states — small enough to draw on a napkin. Now extend to a realistic floor plan.

If the task is simply "clean every square", the battery, bag, and clock are irrelevant and their inclusion inflates the search space by a factor of ten million for no benefit — and worse, it fragments the space, because two states that differ only in the clock will be treated as different and re-explored, destroying the benefit of duplicate detection.

The two quantities that govern the cost of uninformed search are the branching factor b (how many successors a typical state has) and the solution depth d (how many actions a typical solution contains). Breadth-first search examines on the order of bd nodes. The exponent is the depth, so small changes in either number have large consequences.

A good formulation attacks both numbers. The classic illustration is 8-queens. The naive incremental formulation says: a state is any arrangement of zero to eight queens on the board; an action places a queen on any empty square. The branching factor at the first move is 64, and the number of distinct sequences to consider is roughly 64 × 63 × … × 57 ≈ 1.8 × 1014. A smarter formulation says: a state is an arrangement of k queens, one in each of the leftmost k columns, with no queen attacking another; an action places a queen in the leftmost empty column in any non-attacked square. Now the branching factor is at most 8, the depth is exactly 8, and only 2,057 states exist in the whole space. The problem has gone from hopeless-by-brute-force to solvable instantly, and no algorithm was changed. This is the single most important lesson of the topic: effort invested in representation typically pays a far higher return than effort invested in tuning the search procedure.

Deeper formulation changes can do even more. Choosing to search backwards from the goal, searching from both ends simultaneously, exploiting symmetry (in 8-queens, reflections and rotations collapse the 92 solutions to 12 fundamental ones), or replacing a path-finding formulation with a complete-state formulation suited to local search are all representational decisions made before a single line of search code runs.

Abstraction: choosing what to ignore

Abstraction is the process of removing detail from a representation. It is not a regrettable approximation forced on us by weak computers; it is the mechanism that makes reasoning possible at all. Any real situation contains an unbounded amount of detail, so every usable state is already an abstraction. The question is never whether to abstract but where to draw the line.

The practical test for inclusion is narrow and useful: a feature belongs in the state only if it affects which actions are legal, which state an action leads to, whether the goal test succeeds, or what an action costs. If a feature influences none of these four things, it cannot change the behaviour of the search and should be dropped. In the Romanian route-finding problem, the weather fails this test (it affects none of the four), so it is dropped; the current city passes it (it determines which roads are available), so it stays. If we added a constraint that mountain roads are closed in winter, then the season would suddenly affect action legality and would have to be promoted into the state.

Two properties distinguish a good abstraction from a merely small one:

  • Validity. Every abstract solution must be expandable into a solution of the original, more detailed problem. Formally, for each abstract path from the abstract initial state to an abstract goal, there must exist a corresponding detailed path in the real world. The city-level route plan is valid because the abstract step "drive from Sibiu to Fagaras" can always be realised as some sequence of real steering, accelerating, and braking actions.
  • Usefulness. Carrying out each abstract action must be easy relative to solving the whole problem — otherwise we have merely relocated the difficulty. An abstraction whose single action is "get from Arad to Bucharest" is valid and trivially small, and entirely useless, because expanding that one action is the original problem. Abstraction must decompose difficulty, not hide it.

The two failure modes sit on either side of the sweet spot. Over-abstraction discards information the problem actually needs, producing plans that are wrong or unexecutable: a delivery planner that ignores vehicle capacity will happily produce a route loading forty parcels into a van that holds twenty; a puzzle formulation that records only which tiles are present but not where they are cannot distinguish a solved board from a scrambled one, so the goal test becomes meaningless. Under-abstraction retains information that changes nothing, producing state explosion, exhausted memory, and failure of duplicate detection: two states identical in every respect that matters but differing in a stored timestamp will be treated as distinct, so the search re-explores the same situation endlessly.

A worked example sharpens the point. Suppose a hospital porter must collect a patient from Ward B and deliver them to Radiology. A thoughtful state might be (porter_location, patient_location, patient_on_trolley?) — three features, each needed: location determines which corridors are available, patient location and trolley status determine whether "deliver" is legal and whether the goal holds. Adding the porter's name, shift number, the lift's current floor, or the corridor's lighting level would multiply the space without changing any decision. But if lifts can be out of service, the lift's status does affect action legality and must be added. Abstraction decisions are therefore relative to the task, not absolute properties of the domain.

Assumptions behind the classical formulation

The five-component framework is not universally applicable. It rests on four assumptions about the environment, and when one of them fails, the formulation must be extended or replaced.

  • Observable. The agent knows which state it is in, so Result can be applied to a known state and the goal test can be evaluated with certainty. If the environment is partially observable, the agent must instead reason about belief states — sets of states it might be in. A vacuum robot with no sensors starting anywhere in a two-square world must plan over the eight-element power set of physical states, and its "goal test" becomes "every state in my belief set is clean". The search problem is still a search problem, but the state space has changed character and size dramatically.
  • Discrete. There is a finite (or at least countable) set of actions at each state, so successors can be enumerated. Continuous control problems — steering angle anywhere in a real interval — have infinitely many successors and require discretisation, sampling, or entirely different techniques such as optimisation or sampling-based motion planning.
  • Deterministic. Each action in each state produces exactly one known successor. This is what lets a solution be a simple sequence: the agent can compute the whole plan in advance and execute it blindly, confident about where each step lands. If actions may fail or have random outcomes, a sequence is no longer adequate; the solution becomes a contingency plan or policy that specifies what to do for each possible outcome, and the analysis moves toward AND–OR search or Markov decision processes.
  • Static. The world does not change while the agent deliberates, so a plan computed now is still valid when execution begins. In a dynamic environment — a moving obstacle, a competing agent, a fluctuating price — a plan can be invalidated before it is executed, and the agent must either replan continually or include the environment's evolution in the state (typically by adding time, with the attendant explosion in state count).

A fifth, often-implicit assumption is that the environment is single-agent: nobody else is acting to help or to frustrate the plan. Games violate this and require adversarial search. It is good practice, when writing down a formulation, to state explicitly which of these assumptions you are relying on, because readers and future maintainers can then see immediately when the formulation has outgrown its setting.

Evaluating a formulation before searching

A formulation can and should be criticised on paper, before any code runs. Four checks catch most of the common defects.

  • Are all states reachable and meaningful? A description may admit states the world cannot produce. The 8-puzzle is the standard example: of the 362,880 permutations of the nine symbols, only 181,440 are reachable from any given board, because sliding moves preserve the parity of the permutation. A formulation that assumes the whole space is connected will waste effort, or will promise a solution to an unsolvable instance. Similarly, a state with three queens in the same column is syntactically expressible but meaningless under the constraints, and should either be excluded by the Actions function or recognised as a dead end.
  • How big is the space, and how deep is a solution? Multiply out the feature cardinalities to estimate the state count; estimate b by counting typical legal actions; estimate d from known or sample solutions. Then compare bd with the memory and time you actually have. A back-of-the-envelope calculation that yields 1018 nodes tells you immediately that uninformed search is pointless and that you need a better representation, a heuristic, or both. The 8-puzzle has about 1.8 × 105 reachable states and is trivial; the 15-puzzle has about 1.3 × 1013 and needs good heuristics; the 24-puzzle has about 1025 and remains hard.
  • Is the goal test cheap and unambiguous? It is applied to every generated node, so an expensive test dominates the running time. More seriously, an ill-defined goal test is a silent killer: "the room is tidy", "the route is reasonable", and "the schedule is fair" are not predicates a program can evaluate. Each must be reduced to a checkable condition over the state — "every dirt bit is false", "total distance ≤ 300 km", "no worker has more than two night shifts". A goal test that cannot return a definite true or false means the search has no stopping condition at all.
  • Does the cost function measure what you care about? Minimising the number of road segments is not the same as minimising distance, which is not the same as minimising driving time, fuel, tolls, or emissions. Choosing step cost 1 per action — common and convenient — implicitly declares that all actions are equally undesirable, which is right for the 8-puzzle and wrong for route planning across roads of unequal length. The cost function must also be internally consistent: mixing kilometres on some edges with minutes on others makes "optimal" meaningless, and negative costs break optimality guarantees. If several objectives genuinely matter, they must be combined explicitly into a single scalar (for example, cost = time + λ × tolls) with the trade-off weight stated, or handled with a multi-objective method.

Running these checks produces a short, defensible document: the five components written out precisely, the assumptions named, the estimated size of the space, and a justification for each feature included in the state. That document is the real deliverable of problem formulation. The search algorithm applied afterwards is, by comparison, an off-the-shelf part.
