Propositional Inference: Model Checking and Resolution

1

Propositional Inference: Model Checking and Resolution

▶

Logical inference is the process of deriving new sentences from old ones in a way that is guaranteed to preserve truth. A knowledge-based agent stores what it knows in a knowledge base (KB) of sentences and must be able to answer questions of the form "given everything I know, does it follow that α is true?" This topic develops the machinery that answers that question for propositional logic: the semantic notion of entailment, the brute-force method of model checking, the refinements that make satisfiability search practical, the normal form that makes proof mechanical, the resolution rule together with proof by refutation, and finally the restricted but highly efficient world of Horn clauses with forward and backward chaining.

Entailment and the inference problem. Entailment is a relationship between sentences that rests entirely on semantics, not on any particular algorithm. We write KB ⊨ α and read it as "KB entails α". The definition is: KB ⊨ α if and only if, in every model in which KB is true, α is also true. A model in propositional logic is simply a complete assignment of true or false to every proposition symbol under consideration. If M(KB) denotes the set of models satisfying the KB and M(α) the set satisfying the query, then entailment is set inclusion: KB ⊨ α exactly when M(KB) ⊆ M(α). The more a KB says, the fewer models it admits, and the more sentences it entails.

A worked illustration helps. Suppose the KB contains the two sentences P ∨ Q and ¬Q. With two symbols there are four models. The KB is true only in the single model {P = true, Q = false}. The sentence P is true in that model, so KB ⊨ P. The sentence Q is false there, so KB ⊭ Q; indeed KB ⊨ ¬Q trivially since ¬Q is already in the KB. Note carefully that KB ⊭ Q is not the same as KB ⊨ ¬Q in general — a KB may simply be silent about a symbol, entailing neither it nor its negation.

Against this semantic yardstick we measure algorithms. An inference procedure is written KB ⊢ᵢ α, meaning "procedure i derives α from KB".

  • Soundness (also called truth-preservation): whenever KB ⊢ᵢ α, it is also the case that KB ⊨ α. A sound procedure never invents conclusions that are not genuinely supported. An unsound procedure is worse than useless, because an agent acting on a fabricated conclusion may take catastrophic actions.
  • Completeness: whenever KB ⊨ α, the procedure can derive it, KB ⊢ᵢ α. A complete procedure never misses a consequence. Incompleteness is tolerable in practice (many fast reasoners are deliberately incomplete), but it means a "no" answer must be read as "I could not show it", not "it is false".

Both properties are relative to a semantics, and both are needed for an inference engine to be a faithful implementation of entailment. Truth-table enumeration and resolution are each sound and complete for propositional logic; forward and backward chaining are sound and complete for the Horn fragment only.

Decidability and complexity. Because a propositional KB mentions only finitely many symbols, there are only finitely many models, so entailment is decidable: an algorithm always terminates with a correct yes/no answer. That is a stronger guarantee than first-order logic offers, where entailment is only semi-decidable. Decidability, however, says nothing about cost. Deciding whether KB ⊨ α is co-NP-complete in general. The reason is the duality with satisfiability: KB ⊨ α holds exactly when KB ∧ ¬α is unsatisfiable, and SAT is the canonical NP-complete problem, so its complement — proving unsatisfiability — sits in co-NP. A "no" answer to entailment has a short certificate (exhibit one model satisfying KB ∧ ¬α), but a "yes" answer in general does not; one must in effect rule out all models. This asymmetry explains why practical systems invest so heavily in search heuristics and proof techniques rather than hoping for a polynomial algorithm.

The deduction theorem. The bridge between entailment and the familiar notion of a valid (tautological) sentence is the deduction theorem: for any sentences KB and α, KB ⊨ α if and only if the implication (KB ⇒ α) is valid, i.e. true in every model. (Here KB is understood as the conjunction of all its sentences.) The proof is immediate from the semantics of ⇒: the implication can only fail in a model where KB is true and α false, and such a model exists precisely when entailment fails. A second, equally useful equivalence is proof by refutation (reductio ad absurdum): KB ⊨ α if and only if (KB ∧ ¬α) is unsatisfiable. These three formulations — entailment, validity of an implication, unsatisfiability of a conjunction — are interchangeable, and each suggests a different algorithm: enumerate models, test a tautology, or run a satisfiability solver.

Model checking by truth-table enumeration. The most direct algorithm simply implements the definition of entailment. Collect every proposition symbol occurring in KB or α; call them P₁ … Pₙ. Enumerate all 2ⁿ assignments of truth values to these symbols. For each assignment, evaluate the KB. If the KB evaluates to false, the model is irrelevant and is skipped. If the KB evaluates to true, evaluate the query: if the query is also true, continue; if the query is false, stop and report that entailment fails. If the enumeration completes without finding such a model, report that KB ⊨ α.

function TT-ENTAILS?(KB, α) returns true or false
    symbols ← a list of the proposition symbols in KB and α
    return TT-CHECK-ALL(KB, α, symbols, {})

function TT-CHECK-ALL(KB, α, symbols, model) returns true or false
    if EMPTY?(symbols) then
        if PL-TRUE?(KB, model) then return PL-TRUE?(α, model)
        else return true          // KB false here: model places no constraint
    else
        P ← FIRST(symbols);  rest ← REST(symbols)
        return TT-CHECK-ALL(KB, α, rest, model ∪ {P = true})
               and
               TT-CHECK-ALL(KB, α, rest, model ∪ {P = false})

Exactly one model satisfies the KB, and in it R is true, so KB ⊨ R. Now change the query to α = ¬P. The same single KB-model has P = true, so ¬P is false there: entailment fails, and the model {P = true, Q = true, R = true} is a counterexample — a concrete world consistent with everything the agent knows in which the query is false. Counterexamples are valuable diagnostics: they tell the knowledge engineer exactly which scenario the KB has failed to rule out, often revealing a missing axiom.

Truth-table enumeration is sound and complete by construction, because it is a literal transcription of the semantic definition of entailment; there is no gap between what it derives and what is entailed. Its cost, however, is brutal. The time complexity is O(2ⁿ) for n symbols (strictly, O(2ⁿ · m) if evaluating the sentences costs m). The space complexity is only O(n), because the recursive formulation never materialises the whole table — it performs a depth-first traversal of a binary tree of partial models, holding just one root-to-leaf path at a time. Even so, a modest KB with 60 symbols yields roughly 1018 models, which is beyond any machine. Enumeration is therefore a definitional tool and a teaching device rather than a production algorithm; it is, however, an excellent way to verify small examples and to confirm the correctness of logical equivalences.

Satisfiability and DPLL-style search. Because entailment reduces to unsatisfiability of KB ∧ ¬α, any good satisfiability (SAT) solver is also a good entailment checker. The Davis–Putnam–Logemann–Loveland (DPLL) algorithm is a backtracking search over partial models that takes the same recursive enumeration skeleton as above and adds three devastatingly effective improvements. Its input is a sentence in CNF, viewed as a set of clauses.

  • Early termination. A partial model often settles the outcome without assigning every symbol. A clause is already satisfied the moment any one of its literals is true, so the clause (A ∨ B) is satisfied by A = true regardless of B. If every clause is satisfied, the search can stop immediately and report satisfiability. Conversely, if any clause has all of its literals assigned false, that branch is dead and must be abandoned at once rather than extended through the remaining symbols. Truth-table enumeration, by contrast, stubbornly completes every assignment.
  • Unit propagation (the unit clause heuristic). A unit clause is one with exactly one literal still unassigned and all other literals already false. That literal is forced: there is no choice but to make it true. Assigning it may in turn reduce other clauses to unit clauses, producing a cascade that fixes many symbols with no search at all. For example, with clauses (¬A ∨ B), (¬B ∨ C), (¬C ∨ D) and the unit clause (A): asserting A makes the first clause a unit on B, forcing B; that forces C; that forces D. Unit propagation applied to a KB of definite clauses is exactly forward chaining. In modern solvers it typically consumes the majority of running time and is the single most important optimisation.
  • The pure symbol heuristic. A symbol is pure if, across all clauses not yet satisfied, it appears with only one polarity — always positive or always negative. Such a symbol can safely be assigned the value that makes its literals true, since doing so can only satisfy clauses and never falsify one; no backtracking over this choice is ever required. In the clause set (A ∨ ¬B), (¬B ∨ ¬C), (C ∨ A), the symbol A occurs only positively and B only negatively, so we may set A = true and B = false outright. Purity is relative to the remaining clauses: once early termination marks clauses as satisfied, further symbols may become pure.
function DPLL-SATISFIABLE?(s) returns true or false
    clauses ← the set of clauses in the CNF representation of s
    symbols ← a list of the proposition symbols in s
    return DPLL(clauses, symbols, {})

function DPLL(clauses, symbols, model) returns true or false
    if every clause in clauses is true in model then return true
    if some clause in clauses is false in model then return false
    P, value ← FIND-PURE-SYMBOL(symbols, clauses, model)
    if P is non-null then return DPLL(clauses, symbols − P, model ∪ {P = value})
    P, value ← FIND-UNIT-CLAUSE(clauses, model)
    if P is non-null then return DPLL(clauses, symbols − P, model ∪ {P = value})
    P ← FIRST(symbols);  rest ← REST(symbols)
    return DPLL(clauses, rest, model ∪ {P = true})
        or DPLL(clauses, rest, model ∪ {P = false})

Industrial solvers layer further techniques on this core: intelligent backtracking that jumps back to the decision actually responsible for a conflict, clause learning that records the cause of each conflict as a new clause so the same dead end is never revisited, activity-based branching heuristics such as VSIDS, random restarts, and lazy "watched literal" data structures that make unit propagation nearly free. The cumulative effect is startling: DPLL-derived solvers routinely dispatch industrial instances with millions of variables and tens of millions of clauses, despite the worst-case exponential bound that complexity theory guarantees must remain. This is why hardware verification, software model checking, and planning are now commonly compiled into SAT.

Local search and WALKSAT. An entirely different strategy abandons systematic search. Local search starts from a complete random assignment and repeatedly flips the value of a single symbol, guided by the number of clauses satisfied. WALKSAT picks a clause that is currently unsatisfied and then flips one of its symbols, choosing with some probability p a random symbol in the clause (a "random walk" move that escapes local optima) and otherwise the symbol that maximises the number of satisfied clauses (a greedy "min-conflicts" move). The balance between the two keeps the search from stagnating on plateaux.

function WALKSAT(clauses, p, max_flips) returns a model or failure
    model ← a random assignment of true/false to the symbols in clauses
    for i = 1 to max_flips do
        if model satisfies clauses then return model
        clause ← a randomly selected clause from clauses that is false in model
        with probability p
            flip the value in model of a randomly selected symbol from clause
        else
            flip whichever symbol in clause maximises the number of satisfied clauses
    return failure

WALKSAT is often dramatically faster than DPLL on large satisfiable instances, especially ones with many solutions. Its crucial limitation is that it is incomplete: returning failure after max_flips flips means only "no model found within the budget", never "no model exists". Since entailment requires demonstrating that KB ∧ ¬α is unsatisfiable, local search cannot establish entailment. It is, however, perfectly suited to the opposite task: finding a counterexample that refutes a conjectured entailment, and to applications such as planning where any satisfying assignment is the answer sought.

Conjunctive normal form. Both DPLL and resolution require their input in a uniform syntactic shape. A literal is a proposition symbol or its negation; a clause is a disjunction of literals; a sentence is in conjunctive normal form (CNF) if it is a conjunction of clauses. Every propositional sentence has a logically equivalent CNF, obtained by a deterministic four-stage rewriting procedure.

  • Step 1 — eliminate biconditionals. Replace every α ⇔ β with (α ⇒ β) ∧ (β ⇒ α). This is the step most likely to be forgotten, and it doubles the size of the affected subformula.
  • Step 2 — eliminate implications. Replace every α ⇒ β with ¬α ∨ β. After this step the only connectives left are ¬, ∧, and ∨.
  • Step 3 — move negations inward (negation normal form). Apply De Morgan's laws, ¬(α ∧ β) ≡ (¬α ∨ ¬β) and ¬(α ∨ β) ≡ (¬α ∧ ¬β), together with double-negation elimination ¬¬α ≡ α, until every negation sign sits directly on a proposition symbol.
  • Step 4 — distribute ∨ over ∧. Apply α ∨ (β ∧ γ) ≡ (α ∨ β) ∧ (α ∨ γ) repeatedly until the sentence is a flat conjunction of disjunctions. Finally, flatten nested associative operators and optionally simplify by dropping duplicate literals and deleting tautological clauses that contain both P and ¬P.

A full worked conversion of the wumpus-world style sentence B₁,₁ ⇔ (P₁,₂ ∨ P₂,₁):

1. Eliminate ⇔ :
   (B₁,₁ ⇒ (P₁,₂ ∨ P₂,₁)) ∧ ((P₁,₂ ∨ P₂,₁) ⇒ B₁,₁)

2. Eliminate ⇒ :
   (¬B₁,₁ ∨ P₁,₂ ∨ P₂,₁) ∧ (¬(P₁,₂ ∨ P₂,₁) ∨ B₁,₁)

3. Move ¬ inward (De Morgan):
   (¬B₁,₁ ∨ P₁,₂ ∨ P₂,₁) ∧ ((¬P₁,₂ ∧ ¬P₂,₁) ∨ B₁,₁)

4. Distribute ∨ over ∧ :
   (¬B₁,₁ ∨ P₁,₂ ∨ P₂,₁) ∧ (¬P₁,₂ ∨ B₁,₁) ∧ (¬P₂,₁ ∨ B₁,₁)

The result is three clauses, and it is logically equivalent to the original — equivalent, not merely equisatisfiable, because every rewrite rule used is an equivalence. That equivalence guarantee has a price. Step 4 can cause exponential blow-up: the sentence (A₁ ∧ B₁) ∨ (A₂ ∧ B₂) ∨ … ∨ (Aₙ ∧ Bₙ) distributes into 2ⁿ clauses, one for each way of choosing a literal from each disjunct. In practice this is avoided by the Tseitin transformation, which introduces a fresh symbol to name each compound subformula and adds clauses defining it; the result is linear in size and equisatisfiable (though not equivalent, since it mentions new symbols). For entailment checking, equisatisfiability is all that is needed, so Tseitin encoding is the standard industrial practice.

The resolution rule. Resolution is a single inference rule that, with CNF and refutation, is complete for propositional logic. In its general form, the full resolution rule takes two clauses containing complementary literals and produces the disjunction of all the remaining literals:

    ℓ₁ ∨ … ∨ ℓᵢ ∨ … ∨ ℓₖ ,     m₁ ∨ … ∨ mⱼ ∨ … ∨ mₙ
   ---------------------------------------------------------   where ℓᵢ and mⱼ are complementary
    ℓ₁ ∨ … ℓᵢ₋₁ ∨ ℓᵢ₊₁ … ∨ ℓₖ ∨ m₁ ∨ … mⱼ₋₁ ∨ mⱼ₊₁ … ∨ mₙ

The canonical example: from (A ∨ B) and (¬B ∨ C) infer (A ∨ C). The rule is sound, and the reason is easy to see by case analysis on B. If B is false, then for the first clause to hold A must be true. If B is true, then for the second clause to hold C must be true. Either way A ∨ C holds. Note that resolution must be applied to exactly one complementary pair at a time. If two clauses share two complementary pairs — for instance (A ∨ B) and (¬A ∨ ¬B) — then resolving on A gives (B ∨ ¬B) and resolving on B gives (A ∨ ¬A); both resolvents are tautologies and carry no information, which is correct, since those two clauses are jointly satisfiable and entail nothing new. Resolving on both pairs at once would illegitimately produce the empty clause, so the rule is deliberately restricted.

Factoring. A resolvent is a set of literals, not a list, so duplicate literals must be collapsed. This step is called factoring. Resolving (A ∨ B) with (A ∨ ¬B) yields the raw resolvent (A ∨ A), which factoring reduces to the single-literal clause (A). Keeping clauses in this canonical form matters for two reasons: it keeps clauses from growing without bound through repeated duplication, and it allows the algorithm to recognise when a newly generated clause is identical to one already present, which is what makes termination detection possible.

Proof by refutation. Resolution alone cannot derive every entailed sentence — from (A) it will never produce the entailed sentence (A ∨ B), because resolution only ever shortens or merges clauses. What resolution is guaranteed to do is detect unsatisfiability, a property known as refutation completeness: if a set of clauses is unsatisfiable, resolution applied exhaustively will derive the empty clause. Combined with the refutation equivalence established earlier, this gives a complete decision procedure for entailment. The algorithm is:

  • Form the sentence KB ∧ ¬α, i.e. add the negation of the query to the knowledge base.
  • Convert the whole thing to CNF and collect the clauses into a set.
  • Repeatedly select pairs of clauses containing complementary literals, compute the resolvent, factor it, and add it to the set if it is new.
  • If the empty clause { } (written □) is ever derived, stop and report KB ⊨ α. The empty clause is a disjunction of no literals, which is false in every model; deriving it from KB ∧ ¬α by sound rules proves that KB ∧ ¬α has no model, i.e. that it is unsatisfiable, i.e. that KB ⊨ α.
  • If the process saturates — no pair of clauses yields a resolvent that is not already present — stop and report that KB ⊭ α, because KB ∧ ¬α is satisfiable. Termination is guaranteed: with n symbols there are only finitely many distinct clauses (at most 3ⁿ, since each symbol appears positively, negatively, or not at all), so the clause set cannot grow forever.
function PL-RESOLUTION(KB, α) returns true or false
    clauses ← the set of clauses in the CNF representation of (KB ∧ ¬α)
    new ← { }
    loop do
        for each pair of clauses Cᵢ, Cⱼ in clauses do
            resolvents ← PL-RESOLVE(Cᵢ, Cⱼ)          // factored
            if resolvents contains the empty clause then return true
            new ← new ∪ resolvents
        if new ⊆ clauses then return false            // saturation
        clauses ← clauses ∪ new

A worked refutation. Let the KB be the three sentences P ⇒ Q, Q ⇒ R, P, and let the query be R. CNF of the KB gives the clauses (¬P ∨ Q), (¬Q ∨ R), (P); negating the query adds (¬R).

StepClauseJustification
1(¬P ∨ Q)from KB
2(¬Q ∨ R)from KB
3(P)from KB
4(¬R)negated query
5(Q)resolve 1 and 3 on P
6(R)resolve 2 and 5 on Q
7□resolve 4 and 6 on R — contradiction

The empty clause appears, so KB ⊨ R. Now contrast a non-entailment. Take KB = (P ∨ Q) and query α = P. The clause set is (P ∨ Q) and (¬P). The only available resolution is on P, giving (Q). Resolving (Q) against the others produces nothing new — there is no clause containing ¬Q. The set {(P ∨ Q), (¬P), (Q)} is saturated and contains no empty clause, so KB ⊭ P; and indeed the model {P = false, Q = true} satisfies the KB while falsifying the query.

The practical difficulty with naive resolution is the combinatorial explosion of generated clauses; real theorem provers therefore impose strategies such as unit preference (prefer resolving with short clauses, since the goal is the shortest clause of all), the set-of-support strategy (require every resolution step to involve a descendant of the negated query, keeping the proof goal-directed), and subsumption (discard any clause that is a superset of an existing clause, since it is weaker and therefore redundant).

Horn clauses and definite clauses. The expense of full resolution motivates a restricted language in which inference is cheap. A definite clause is a disjunction of literals of which exactly one is positive; a Horn clause is a disjunction with at most one positive literal. Horn clauses therefore comprise definite clauses together with goal clauses (no positive literal) and facts (a single positive literal, a definite clause with an empty premise). The crucial observation is that a definite clause can be rewritten as an implication whose premise is a conjunction of positive literals and whose conclusion is a single positive literal:

(¬L₁ ∨ ¬L₂ ∨ … ∨ ¬Lₖ ∨ H)   ≡   (L₁ ∧ L₂ ∧ … ∧ Lₖ) ⇒ H

This form is enormously natural for knowledge engineering — it reads as a rule, "if all of these conditions hold, then conclude this" — and it is the basis of logic programming (Prolog), production-rule systems, and deductive databases. For example:

Facts:  Mythical? — no;  we know:  Mammal
Rules:  Mammal ⇒ WarmBlooded
        WarmBlooded ∧ HasFeathers ⇒ Bird
        Mammal ∧ GivesMilk ⇒ Nurtures

Three properties make the Horn fragment attractive. First, entailment of an atom from a Horn KB can be decided in time linear in the size of the KB, a dramatic improvement on the co-NP-completeness of the general case. Second, inference can be carried out with forward or backward chaining, which produce proofs that humans can follow as chains of rule applications. Third, unit propagation in DPLL is precisely forward chaining, so the same machinery serves both worlds. The cost of these benefits is expressiveness: a Horn KB cannot state genuine disjunctions such as P₁,₂ ∨ P₂,₁ or negative conclusions, so the wumpus world's knowledge cannot be fully captured in Horn form.

Forward chaining. Forward chaining is data-driven: it begins with the atoms known to be true and repeatedly fires any rule all of whose premises are already known, adding the conclusion to the set of known facts. It stops when the query atom is derived, or when a complete pass adds no new fact (a fixed point has been reached), in which case the query is not entailed.

function PL-FC-ENTAILS?(KB, q) returns true or false
    count ← a table where count[c] is the number of symbols in clause c's premise
    inferred ← a table where inferred[s] is initially false for all symbols
    agenda ← a queue of symbols known to be true in KB (the facts)
    while agenda is not empty do
        p ← POP(agenda)
        if p = q then return true
        if inferred[p] = false then
            inferred[p] ← true
            for each clause c in KB where p appears in c's premise do
                decrement count[c]
                if count[c] = 0 then add c's conclusion to agenda
    return false

The count table is what delivers linear time. Instead of rescanning every rule on every iteration to see whether its premises are now satisfied, the algorithm stores, for each rule, how many premises remain unsatisfied. When a symbol becomes known, only the rules mentioning that symbol in their premise are touched, and each is decremented by one. A rule fires exactly when its counter hits zero. Over the whole run, each premise occurrence in the KB is processed exactly once, so the total work is proportional to the number of symbol occurrences in the KB — linear in its size.

Forward chaining is sound, because every fact it adds is produced by one application of Modus Ponens, which is a sound rule. It is complete for definite-clause KBs, and the argument is instructive: when the algorithm reaches its fixed point, take the set of inferred atoms and build the model that assigns true to each of them and false to every other symbol. This model satisfies every clause of the KB — if some clause L₁ ∧ … ∧ Lₖ ⇒ H were false in it, all the Lᵢ would be inferred and H would not be, contradicting the fact that the algorithm had reached a fixed point. Hence this is a model of the KB, so any atom entailed by the KB must be true in it, so any entailed atom is one of the inferred atoms. This model is in fact the unique minimal model of the KB, the one that makes as few atoms true as possible.

Backward chaining. Backward chaining is goal-driven. It starts from the query q and works backwards. If q is already a known fact, it succeeds. Otherwise it finds every rule whose conclusion is q and, for each, recursively attempts to prove all of that rule's premises; if every premise of some rule can be proved, q is proved. The search is depth-first and must keep track of the goals currently on the stack so that it does not loop forever on cyclic rule sets (for instance P ⇒ Q together with Q ⇒ P). This is the inference strategy used by Prolog.

Running backward chaining on the same KB with query Q: the goal Q matches the conclusion of r1, so the subgoal is P; P is the conclusion of r2, giving subgoals L and M; L is the conclusion of r4 (subgoals A and P — but P is already on the stack, so this branch is abandoned to avoid a loop) and of r5 (subgoals A and B, both facts — success); M is the conclusion of r3, with subgoals B (a fact) and L (already proved). All subgoals succeed, so Q is proved. Like forward chaining, backward chaining is sound and complete for definite-clause knowledge bases.

Comparing the two. The algorithms compute the same answers but explore the KB in opposite directions and have different cost profiles.

The practical rule of thumb: if the agent continuously receives new percepts and should maintain everything derivable from them — a sensor-monitoring or alarm application — forward chaining is appropriate, since the incremental cost of each new fact is small and all consequences are kept up to date. If the agent has a large KB but a specific question, backward chaining is usually far cheaper, because the cost is proportional to the size of the proof tree rather than the size of the KB. A medical KB with a hundred thousand rules asked "does this patient have condition X?" should certainly not derive every consequence of the patient's record; it should chain backwards from X. Many real systems combine both, using forward chaining to propagate cheap, highly constraining facts and backward chaining to resolve the remaining questions on demand.

The topic defines entailment, develops model checking by truth-table enumeration and DPLL-style search, gives the four-step CNF conversion procedure, and presents the resolution rule with proof by refutation, including worked examples of both entailment and non-entailment.
  • MO4 — Not addressed. This topic is confined to propositional logic; predicates, functions, and quantifiers belong to the first-order material elsewhere in the module.
  • MO5 — Directly addressed. The final section defines Horn and definite clauses, gives algorithms and traces for forward and backward chaining, establishes their soundness and completeness, and compares them explicitly on direction of reasoning, work done, and suitability for monitoring versus specific-query tasks.
