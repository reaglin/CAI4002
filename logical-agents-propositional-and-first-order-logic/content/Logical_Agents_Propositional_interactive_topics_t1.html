Knowledge-Based Agents and Knowledge Bases

▶

Most of the agent designs studied before the introduction of logic are, in a sense, opaque. A reflex agent carries its competence inside a table or a nest of condition–action rules; a search agent carries it inside a successor function and a heuristic. In each case the designer knows what the agent will do, but the agent itself has no explicit, inspectable account of the world it inhabits. A knowledge-based agent takes the opposite stance: the world model is written down explicitly, in a formal language, as a collection of statements that the agent can examine, add to, and reason over. This single architectural decision — separating what is known from what is done with it — is the foundation of logical AI, and it underpins everything from expert systems and database query engines to modern verification tools and hybrid neuro-symbolic systems.

The central component of such an agent is the knowledge base (usually abbreviated KB). A knowledge base is a set of sentences, each expressed in a knowledge representation language such as propositional logic or first-order logic. The word "sentence" here is a technical term: it does not mean an English sentence, but a syntactically well-formed expression of the formal language. Crucially, each sentence is an assertion — a claim about how the world is, taken by the agent to be true. The sentence Wall(1,1) is not a label, a variable name, or a data record; it is a claim that there is a wall at location (1,1), and the agent's subsequent reasoning will proceed on the assumption that this claim holds.

Where do these assertions come from? Broadly, from two sources. Some are supplied in advance by the designer as background knowledge: the physics of the domain, the rules of the game, definitions of terms, constraints that always hold. In a Wumpus World agent, a background axiom might state that a square is breezy exactly when an adjacent square contains a pit:

B(1,1) <=> (P(1,2) OR P(2,1))
B(2,1) <=> (P(1,1) OR P(2,2) OR P(3,1))

Other sentences are acquired through perception at run time. When the agent stands in square (1,1) and senses no breeze and no stench, it records:

NOT B(1,1)
NOT S(1,1)

Neither kind of sentence, by itself, tells the agent what to do. What makes the architecture powerful is the third ingredient: an inference mechanism that derives new sentences that follow logically from those already stored. From the background axiom and the percept above, the agent can derive NOT P(1,2) and NOT P(2,1) — facts it never perceived and was never told directly, but which are nonetheless guaranteed true if the stored sentences are true. This is the decisive advantage: the same reasoning machinery serves many tasks and environments. A resolution theorem prover does not know or care whether the propositions concern pits and wumpuses, circuit faults, medical symptoms, or airline schedules. Change the knowledge base and the agent changes domain; the inference engine is untouched. Compare this with a reflex agent, whose every competence must be hand-coded afresh for each new environment.

The TELL and ASK interface. Because the knowledge base is a data structure with logical meaning, it must not be manipulated carelessly. Knowledge-based agents therefore interact with the KB through exactly two operations, which together form an abstract interface that hides the KB's internal representation:

  • TELL(KB, α) — add the sentence α to the knowledge base. This is how percepts enter the agent's world model, and also how conclusions the agent has derived, or commitments it has made (such as "I executed Forward at time 3"), are recorded for future use.
  • ASK(KB, α) — query the knowledge base. The answer must be one that follows from what the KB contains.

The subtlety — and the whole point — lies in the word "follows." ASK is not a lookup operation and must not be confused with retrieving a record from a database table. Consider a knowledge base containing only:

Breezy(1,1) => (Pit(1,2) OR Pit(2,1))
Breezy(1,1)
NOT Pit(1,2)

The sentence Pit(2,1) appears nowhere in this KB, yet ASK(KB, Pit(2,1)) must return true, because Pit(2,1) is entailed by the stored sentences: in every state of the world in which all three stored sentences are true, Pit(2,1) is also true. Entailment, written KB |= α, is the formal relation that governs what counts as a correct answer. The design requirement is therefore stated as a guarantee: every answer returned by ASK must be entailed by the knowledge base. This is the property of soundness, and it is what prevents a logical agent from inventing unsupported claims. It cannot hallucinate a safe square, because no inference rule it possesses can produce a conclusion that the premises do not support.

A consequence that often surprises newcomers is that both operations may trigger inference. ASK obviously may: computing an entailed answer can require an arbitrarily long chain of deductions. But TELL may also trigger work. Many implementations perform forward chaining on assertion, immediately computing and storing the consequences of a new fact so that later queries are fast. Others normalise the incoming sentence (for example, converting it to conjunctive normal form) or check it for consistency with what is already believed. The interface deliberately does not say which strategy is used — that is a matter for the implementation.

The agent control loop. With TELL and ASK in place, the behaviour of a generic knowledge-based agent can be written in a handful of lines. The agent maintains a persistent knowledge base and a persistent counter t for the current time step:

function KB-AGENT(percept) returns an action
    persistent: KB, a knowledge base
                t, a counter, initially 0, indicating time

    TELL(KB, MAKE-PERCEPT-SENTENCE(percept, t))
    action <- ASK(KB, MAKE-ACTION-QUERY(t))
    TELL(KB, MAKE-ACTION-SENTENCE(action, t))
    t <- t + 1
    return action

Each line repays close reading.

  • TELL the percept. MAKE-PERCEPT-SENTENCE converts the raw percept into a logical sentence that also records when it was received. A Wumpus percept such as [Stench, None, None, None, None] at time 4 becomes something like Stench(4) AND NOT Breeze(4) AND NOT Glitter(4). The time stamp matters enormously: without it the agent could not distinguish "there was a breeze here, earlier" from "there is a breeze now," and could not reason about change at all.
  • ASK for an action. MAKE-ACTION-QUERY builds a query meaning roughly "which action should be performed at time t?" — for instance ShouldDo(a, 4), whose answer binds a to a specific action. The KB must contain enough knowledge — about the environment, about goals, about what counts as a good move — for a unique or at least a preferred action to be entailed.
  • TELL that the action was taken. This step is easy to overlook but essential. The agent's own actions change the world, and the agent must model those changes. Recording Did(Forward, 4) allows the KB, together with axioms describing the effects of actions, to infer the agent's new location at time 5. Without this step the agent would lose track of itself.
  • Return the action and increment the clock. The action is dispatched to the actuators and the time counter advances, readying the agent for the next cycle.

Observe what this pseudocode does not contain: any hint of how answers are computed. The details of inference are hidden inside ASK. The KB might be interrogated by enumerating models, by resolution refutation, by forward or backward chaining over definite clauses, or by a compiled decision diagram. The control loop is identical in every case. This encapsulation is precisely what lets us analyse the agent's competence separately from its performance.

Knowledge level versus implementation level. That separation is formalised in a distinction introduced by Allen Newell: the difference between describing an agent at the knowledge level and at the implementation level.

At the knowledge level we specify only what the agent knows and what its goals are. We say nothing about data structures, algorithms, or hardware. A knowledge-level description of a taxi agent might be: "it knows that the Golden Gate Bridge links San Francisco to Marin County, and its goal is to reach Marin County." From this alone we can predict its behaviour, using what Newell called the principle of rationality: assume the agent will select actions that its knowledge entails will achieve its goals. We predict that it drives across the bridge — without knowing a single thing about how the agent is built. This is a genuinely predictive abstraction, analogous to predicting a chess program's move from its evaluation of the position rather than from its machine code.

At the implementation level we specify the concrete realisation: the syntax of the representation language, the data structures that hold sentences (lists, hash-indexed clause sets, binary decision diagrams), and the inference algorithms applied to them (model enumeration, DPLL, resolution, chaining). Here questions of time and space complexity, indexing strategy, and memory layout become central.

The key observation is that many different implementations realise the same knowledge-level description. Two agents may be indistinguishable in what they know and therefore in what they will do, while one stores its knowledge as CNF clauses and the other as a set of Horn rules with a forward-chaining engine; one may answer in microseconds and the other in minutes.

What is specifiedWhat the agent knows; what it wantsData structures and algorithms

This separation has a practical payoff: designers can reason about correctness independently of efficiency. One can first establish that a knowledge base correctly and completely captures the domain — that the right conclusions are entailed — and only afterwards worry about making ASK fast. If a faster inference engine is substituted later, the agent's competence is unchanged, because competence was fixed at the knowledge level. Conversely, if the agent behaves wrongly, the fault can be localised: either the knowledge base is incorrect or incomplete (a knowledge-level bug) or the inference procedure is unsound or too slow (an implementation-level bug). In a monolithic procedural program these two kinds of error are tangled together.

Declarative versus procedural approaches. How does knowledge get into the agent in the first place? Two philosophies compete.

In the declarative approach, the designer starts with an empty knowledge base and TELLs the agent sentences one at a time until the agent knows enough to operate in its environment. The designer states facts about the world; the agent works out what to do. To build a Wumpus agent declaratively, one asserts the rules relating breezes to pits, stenches to the wumpus, the geometry of the grid, the consequences of moving, and a characterisation of a desirable action — and then leaves the inference engine to connect them.

In the procedural approach, desired behaviours are compiled directly into program code. Rather than telling the agent that breezes indicate adjacent pits, the designer writes a routine: if breeze_detected then mark_all_neighbours_unsafe(). The knowledge is still present, but it is implicit, dissolved into control flow. It cannot be inspected as knowledge, only read as code.

The declarative approach's advantages follow from the explicitness of its knowledge. Because the knowledge is easy to inspect and debug, an incorrect behaviour can be traced to a specific false or missing sentence, which is then corrected in place. Because it is easy to extend, new information requires only a TELL. Suppose we discover that our Wumpus cave contains quicksand that produces a squelching sound. In a declarative agent we add sentences relating Squelch to Quicksand and asserting that quicksand squares are unsafe; the inference engine immediately begins avoiding them, because the reasoning machinery was never written in terms of pits in the first place. In a procedural agent, every routine that computes safety must be found and rewritten, with the attendant risk of missing one. And because the knowledge is reusable, the very same sentences that support navigation also support answering "where is the gold likely to be?" or "which square have I not yet ruled out?"

Taken to its conclusion, the declarative stance permits an agent that learns. A fully declarative agent can be dropped into a previously unknown environment with little more than a general learning capability and an inference engine, and can build up its own knowledge base by TELLing itself sentences derived from its observations. A general-purpose inference procedure applied to a learned theory yields competence that the designer never explicitly supplied — the agent becomes, in a limited but real sense, a general-purpose system rather than a special-purpose one.

Why declarative representation supports intelligence. It is worth drawing the threads together and asking why this architecture is associated with intelligent behaviour rather than merely with tidy software engineering. Several properties are characteristic of intelligence and fall out naturally from declarative representation.

  • Novel situations are handled by recombination. A procedural agent can respond only to situations its designer anticipated. A declarative agent possesses sentences that can be combined in exponentially many ways. A Wumpus agent told only the local rules linking breezes, stenches and neighbouring squares can nevertheless solve a configuration of pits and walls that neither it nor its designer has ever encountered, because the deduction required is assembled on the fly from general facts. The number of situations a rule base can address vastly exceeds the number of rules it contains.
  • Partial information can be represented and reasoned about. This is perhaps the deepest advantage, and it is the one that distinguishes logic from a simple state array. A conventional data structure must record that square (2,2) either has a pit or does not. A logical KB can say precisely what the agent knows and no more: Pit(2,1) OR Pit(1,2) asserts that at least one of two squares is dangerous without committing to which. Disjunctions, negations, implications and (in first-order logic) existential quantifiers all let the agent hold incomplete knowledge in a usable form, so that later percepts can be combined with it to sharpen the conclusion. Learning that NOT Pit(1,2) immediately yields Pit(2,1) — information that would simply have been discarded by a representation unable to express uncertainty of this kind.
  • Knowledge acquired for one purpose serves unanticipated goals. Because sentences state facts about the world rather than instructions for achieving a particular objective, they are goal-neutral. A map of a building stored declaratively supports route planning, evacuation analysis, and the question "which rooms have no windows?" alike. Procedural knowledge compiled for route planning supports only route planning.
  • Explanations can be produced by tracing inference. Because each conclusion is derived from identifiable premises by identifiable inference steps, the agent can answer "why?" — "I will not enter (1,2) because I perceived a breeze at (1,1), and the rule linking breezes to adjacent pits leaves (1,2) unproven safe." This transparency is a prerequisite for trust, for auditing, and for effective debugging, and it is exactly what opaque, subsymbolic systems struggle to provide.
  • Autonomy grows over time. An agent whose knowledge is explicit can TELL itself new sentences as it learns, progressively reducing its dependence on the designer's initial theory. Its competence is no longer bounded by what was anticipated at design time. An agent that begins with general background knowledge and accumulates environment-specific sentences through experience becomes increasingly independent — which is one reasonable operational definition of autonomy.

None of this makes declarative representation free. General inference is computationally expensive — propositional entailment is co-NP-complete, and first-order entailment is only semi-decidable — and much of the engineering of logical agents is devoted to recovering efficiency through restricted representations such as Horn clauses, or through indexing and compilation. But the architecture draws the line in a principled place: knowledge is stated once, declaratively, and the cost of using it is an implementation-level concern that can be attacked separately, without disturbing what the agent knows.
