Heuristic Evaluation Functions

1

Heuristic Evaluation Functions

▶

Search algorithms that know nothing about the problem beyond its state space — breadth-first, depth-first, uniform-cost — must explore blindly. They cannot tell the difference between a node that sits one step from the goal and a node that sits fifty steps away, except by eventually expanding both. An heuristic evaluation function is the mechanism by which we inject problem-specific knowledge into an otherwise generic search procedure, so that the algorithm can prefer nodes that look closer to a solution. The remainder of this topic develops what such a function is, where its numbers come from, what the classic examples look like in pathfinding and sliding-tile domains, and how to compare and combine several heuristics for a single problem.

What Is a Heuristic Function?

A heuristic function, written h(n), is a mapping from a search node n to a non-negative real number that estimates the cost of the cheapest path from the state at n to a goal state. Formally:

h : Nodes -> R, with h(n) >= 0 for all n
h(n) = 0 whenever n is a goal node (by convention and good practice)

The non-negativity requirement is not arbitrary: costs in a search problem are non-negative, so a "remaining cost" of less than zero is meaningless and would corrupt the node-ordering arithmetic used by algorithms such as A*. The convention h(goal) = 0 matters too — a heuristic that reported some positive value at the goal would discourage the algorithm from recognising the solution it has already found.

It is essential to keep h(n) distinct from the other cost quantity carried by a search node, g(n):

QuantityDirectionNature of the valueHow it is obtained
g(n)Backward-lookingExact, knownAccumulated by summing the step costs along the path actually followed from the start node to n
h(n)Forward-lookingEstimated, uncertainComputed from the state description by a domain-specific formula
h*(n)Forward-lookingExact, usually unknownThe true cost of the optimal path from n to the nearest goal; computing it is generally as hard as solving the problem
f(n)Whole pathEstimate of total solution cost through ng(n) + h(n)

Two subtleties follow from this table. First, g(n) is a property of a node — of a particular path to a state — whereas h(n) is a property of the state itself. Two different nodes holding the same state necessarily have the same h value but may have quite different g values. Second, h*(n) is a well-defined mathematical object even though we cannot compute it cheaply; it is the yardstick against which heuristic quality is measured. If a state has no path to any goal at all, h*(n) is infinite.

Because h(n) is an estimate, it is permitted to be wrong. A heuristic may underestimate (h(n) < h*(n)), be exact (h(n) = h*(n)), or overestimate (h(n) > h*(n)). These three cases have very different consequences. Underestimating heuristics are safe for optimal search, because a search algorithm that trusts them will never prematurely discard a path whose true cost turns out to be low. Overestimating heuristics can cause an algorithm to abandon the genuinely best route and return a suboptimal answer; in exchange they often reduce the number of expansions. The term admissible is reserved for heuristics that never overestimate — that is, those satisfying 0 <= h(n) <= h*(n) for every node.

The operational role of a heuristic is to rank the frontier. A best-first search keeps a priority queue of unexpanded nodes and repeatedly removes the one with the smallest evaluation value. Greedy best-first search orders by h(n) alone; A* orders by f(n) = g(n) + h(n). In both cases the heuristic is what makes the ordering informative. Consider a toy illustration: the frontier contains three nodes with g values 4, 6 and 9. Uniform-cost search expands the one with g = 4. But if their heuristic values are 20, 3 and 1 respectively, A* computes f values of 24, 9 and 10, and expands the second node instead — it has used forward-looking knowledge to recognise that the cheap-so-far path is heading in a hopeless direction.

The payoff from a heuristic is measured in how much of the state space the search can avoid touching. A useful way to quantify this is the effective branching factor b*: if a search expands N nodes to find a solution at depth d, then b* is the branching factor a uniform tree of depth d would need to contain N + 1 nodes:

N + 1 = 1 + b* + (b*)^2 + ... + (b*)^d

A well-designed heuristic drives b* close to 1, meaning the search advances almost in a straight line towards the goal. For the 8-puzzle, blind iterative-deepening search has an effective branching factor near 2.45; the misplaced-tile heuristic brings it to roughly 1.4 and Manhattan distance to roughly 1.25. Those small-looking differences compound exponentially with depth: at depth 24, iterative deepening may expand on the order of tens of millions of nodes, misplaced tiles tens of thousands, and Manhattan distance a couple of thousand. The quality of h is therefore not a marginal tuning concern — it is the dominant factor in whether a search is feasible at all.

Encoding Domain Knowledge as an Estimate

Where do the numbers in a heuristic come from? The single most reliable and principled technique is problem relaxation. The recipe is:

  • Write down the problem's actions together with their preconditions.
  • Delete one or more preconditions, producing a relaxed problem whose action set is a superset of the original's.
  • Solve the relaxed problem exactly — ideally by a closed-form formula rather than by search.
  • Use that exact relaxed cost as h(n) for the original problem.

This construction automatically produces an admissible heuristic, and the argument is worth internalising. Every legal solution to the original problem is still a legal solution to the relaxed problem, because removing preconditions can only add options, never remove them. Hence the relaxed problem's optimal solution is at least as cheap as the original's optimal solution, so the relaxed cost can never exceed h*(n). Relaxation-derived heuristics are also, as it happens, always consistent, because the relaxed cost itself obeys a triangle inequality over the relaxed state space.

Apply the recipe to the 8-puzzle. The legal action can be stated as: "a tile may move from square A to square B if A is horizontally or vertically adjacent to B and B is blank." There are two preconditions to play with.

  • Delete both preconditions — a tile may move from any square to any square in one step. The cheapest solution is then simply to teleport each misplaced tile directly home, one move per misplaced tile. The exact relaxed cost is the count of misplaced tiles, which is the heuristic h1.
  • Delete only "B is blank" — a tile may slide to any adjacent square, passing straight through occupied squares. Each tile now travels independently along a grid path to its goal square, and the shortest such path has length equal to the tile's horizontal plus vertical offset. Summing over all tiles gives Manhattan distance, the heuristic h2.
  • Delete only "A is adjacent to B" — a tile may jump to the blank square from anywhere. This yields a third, less commonly used heuristic sometimes called Gaschnig's heuristic, computable by simulating the simplified puzzle; it lies between h1 and h2 in strength on many states.

Apply the same recipe to road navigation. The real problem says: "you may move from town A to town B at cost equal to the road length, provided a road connects A and B." Delete the precondition that a road must exist and let the cost be the Euclidean separation — you may now fly in a straight line across fields, rivers and mountains. The exact solution to this relaxed problem is the straight-line distance from the current location to the destination, giving h_SLD.

Relaxation is not the only source of domain knowledge, however. Two further families are important in practice:

  • Pattern databases. Select a subset of the problem's elements — for example tiles 1, 2, 3 and 4 of the 15-puzzle, treating the other tiles as indistinguishable "don't care" markers. Exhaustively search this reduced space backwards from the goal and store, in a lookup table keyed by pattern configuration, the exact minimum number of moves needed to place those tiles correctly. At search time, h(n) is a single array lookup. Because every real solution must also solve the subproblem, the stored value never overestimates. Disjoint (additive) pattern databases go further: if each database counts only moves of its own tiles, and the tile sets are disjoint, the separate lookups may be added rather than merely maximised, producing dramatically stronger estimates. Additive databases are what made optimal solution of the 24-puzzle practical.
  • Subproblem decomposition and learned heuristics. Costs of independently solvable components can be summed when the components do not share resources. Alternatively, a function approximator can be trained on features of the state (for instance, "number of adjacent tile pairs that are out of order") using solved instances as training data. Learned heuristics are usually inadmissible, since statistical fitting offers no guarantee of never overestimating, but they can be fast and accurate in the average case.

Straight-Line Distance for Pathfinding

In a map or grid domain where every location carries coordinates, the canonical heuristic is straight-line (Euclidean) distance to the goal:

h_SLD(n) = sqrt( (x_n - x_goal)^2 + (y_n - y_goal)^2 )

Its appeal begins with cost: the computation is two subtractions, two multiplications, one addition and one square root — a few nanoseconds, independent of the size of the map. Nothing about the road network need be consulted, only a coordinate pair per node, which is a trivial amount of data to store.

Its admissibility is equally straightforward. In the Euclidean plane, the line segment between two points is the unique shortest curve joining them. Any actual route, being a sequence of road segments, is a path in the plane from n to the goal and therefore has length at least the length of that segment. Hence h_SLD(n) <= h*(n) always, provided edge costs really are road lengths. The qualification matters: if edge costs represent travel time in minutes rather than distance in kilometres, then raw kilometres may exceed the minute-count and destroy admissibility. The standard fix is to divide by the maximum achievable speed, h(n) = h_SLD(n) / v_max, which restores the guarantee because no vehicle can cover the straight-line gap faster than that.

Consider a concrete miniature example. Suppose the goal lies at coordinates (0, 0) and four frontier nodes have coordinates and known path costs as follows:

NodeCoordinates (x, y)g(n)h_SLD(n)f(n) = g + h
A(30, 40)2050.070.0
B(60, 0)7560.0135.0
C(0, 25)9525.0120.0
D(9, 12)14015.0155.0

A greedy best-first search, ordering by h alone, would seize on node D as the closest to the goal — ignoring the 140 units already spent getting there. An A* search, ordering by f, expands A, whose total estimated journey is cheapest. Notice also how the heuristic separates genuinely different situations that g alone conflates: C and D are geometrically near the goal but expensively reached, while B is both far and expensive and is correctly deprioritised.

The weakness of straight-line distance appears when geometry and topology diverge. If the destination lies directly across a bay, a mountain range, a motorway with no crossing, or a one-way system, the physical detour may be several times the straight-line gap. The heuristic then reports a small number while h* is large, so the heuristic error h* - h is large and the search degenerates towards uniform-cost behaviour — it expands a broad disc of nodes around the start before committing. A particularly vivid failure is the dead-end peninsula: nodes deep inside the peninsula have low h_SLD because they are geometrically close to a goal on the far shore, so the search is lured in and must exhaust the entire peninsula before backing out. The heuristic remains admissible throughout — it never lies upwards — it is simply uninformative. Remedies include using a different metric that matches the movement model (Manhattan or octile distance on grids where diagonal moves are forbidden or cost sqrt(2)), or precomputing landmark-based lower bounds (the ALT technique) that capture real connectivity rather than raw geometry.

Puzzle Heuristics: Misplaced Tiles and Manhattan Distance

The 8-puzzle — eight numbered tiles and one blank in a 3×3 frame — is the standard laboratory for heuristic design. Its state space contains 9!/2 = 181,440 reachable states, and the average optimal solution length is about 22 moves, so blind search is painful while informed search is easy. Two heuristics dominate the discussion.

h1, the misplaced-tile heuristic, counts the tiles that are not currently on their goal square. The blank is deliberately excluded: counting it would allow overestimation, since a single move that puts the last tile in place also, necessarily, relocates the blank, and counting both would charge two moves for one.

h2, the Manhattan distance (or city-block) heuristic, sums over all tiles the horizontal plus vertical grid separation between the tile's current square and its goal square:

h2(n) = sum over tiles t != blank of ( |row(t) - goalRow(t)| + |col(t) - goalCol(t)| )

The true optimal solution length for this state is 18 moves, so both heuristics underestimate, but h2 = 14 is far closer to the truth than h1 = 6. The practical consequence is that a search guided by h2 prunes much more aggressively: nodes whose f value already exceeds the eventual solution cost are recognised as hopeless much earlier.

Why is each heuristic admissible? For h1: every move repositions exactly one tile, and every misplaced tile must be repositioned at least once before the puzzle is solved, so any solution contains at least as many moves as there are misplaced tiles. For h2: every move changes one tile's position by exactly one grid step, which alters that tile's Manhattan distance by at most 1. A tile currently d steps from home therefore needs at least d moves of its own, and since moves of different tiles are distinct moves, the total is at least the sum of the individual distances. Both arguments can also be read off directly from the relaxation construction described earlier, which is their real justification.

Both heuristics are also underestimates in a structural way: they ignore the interference between tiles. Only one tile can occupy a square, and tiles must be shuffled around the single blank, so real solutions almost always need more moves than Manhattan distance predicts. This observation leads to the well-known linear conflict enhancement: if two tiles are in their goal row, and their goal columns are in the opposite order to their current columns, one must move out of the row and back again, adding at least 2 moves beyond Manhattan distance. Adding 2 per such conflicting pair preserves admissibility and typically improves the estimate by a useful margin.

Crucially, h2(n) >= h1(n) for every state. The reason is immediate: a misplaced tile contributes exactly 1 to h1 and contributes its Manhattan distance — which is at least 1 — to h2; a correctly placed tile contributes 0 to both. Summing term by term gives the inequality. Equality holds only in the special case where every misplaced tile is exactly one step from home.

Comparing and Combining Heuristics

The comparison above generalises into the central concept of heuristic quality. We say h2 dominates h1 when both are admissible and h2(n) >= h1(n) for every node n. Dominance is a pointwise, universally-quantified condition: a heuristic that is larger on most states but smaller on a few does not dominate, and comparing two such heuristics requires empirical measurement rather than proof.

The practical importance of dominance is captured by the following result: if h2 dominates h1 and both are admissible, then A* using h2 expands no more nodes than A* using h1 (ignoring tie-breaking among nodes whose f value exactly equals the optimal cost). The reasoning rests on a fact about A* with an admissible heuristic: every node with f(n) < C*, where C* is the optimal solution cost, is certain to be expanded, and no node with f(n) > C* is ever expanded. Since h2 >= h1 implies f2(n) >= f1(n), any node that h2 forces into the "must expand" category is already in that category under h1, but not conversely. The stronger heuristic therefore prunes a superset of what the weaker one prunes. In short: bigger admissible values are always better, because they push more nodes above the C* cut-off while never pushing the true optimal path above it.

The effective branching factor column explains why. h1 leaves b* drifting upward with depth, around 1.45–1.48, whereas h2 holds it near 1.25; since total work grows like (b*)^d, a persistent gap of 0.2 in the base becomes an enormous gap in the exponentiated total.

When several admissible heuristics are available and none dominates the others, they can be combined for free by taking the pointwise maximum:

h(n) = max( h_1(n), h_2(n), ..., h_k(n) )

This composite is itself admissible. The argument is one line: each h_i(n) <= h*(n), so the largest of them is also at most h*(n). If every component is consistent, the maximum is consistent too. And by construction the maximum dominates every component, so it expands no more nodes than any of them individually. Suppose, for instance, that a 15-puzzle solver has a Manhattan-plus-linear-conflict estimate and three separate pattern databases covering overlapping tile groups; evaluating all four and keeping the largest gives a heuristic strictly stronger than any single one. Note the contrast with the additive case: summing is only permitted when the components provably account for disjoint portions of the solution cost (as with disjoint pattern databases), whereas taking the maximum is always safe.

Maximisation is not free in time, however, and this brings us to the central engineering trade-off. The real objective is not "fewest nodes expanded" but "least total wall-clock time", which is roughly

total time  ~=  (nodes expanded) x (time to generate and evaluate one node)

A more accurate heuristic shrinks the first factor and inflates the second. Taking the maximum of four heuristics may halve the node count while quadrupling the per-node cost — a net loss. Manhattan distance costs a handful of additions per node and buys an order-of-magnitude reduction in expansions, which is why it is universally used; a heuristic that solved a near-complete relaxation by its own internal search might be nearly perfect yet so slow that plain Manhattan distance finishes first. Pattern databases sit at a favourable point on this curve precisely because their accuracy is purchased in an offline precomputation phase, leaving only an array lookup at run time; their cost shows up as memory rather than time. Useful practical tactics include computing cheap heuristics first and evaluating expensive ones only when the cheap value fails to prune, and updating Manhattan distance incrementally — when a tile moves one square, its contribution changes by exactly ±1, so a child's h can be derived from its parent's in constant time rather than recomputed from scratch.

Finally, it is illuminating to consider the two extremes of the heuristic spectrum.

  • h(n) = 0 for all n. This is trivially admissible and consistent — it never overestimates anything — but it carries no information. With f(n) = g(n) + 0 = g(n), A* degenerates exactly into uniform-cost search (Dijkstra's algorithm), expanding nodes in order of path cost and radiating uniformly outward from the start. It still finds optimal solutions; it simply pays the full exponential price.
  • h(n) = h*(n) for all n. The perfect oracle. At every step along an optimal path, f(n) = g(n) + h*(n) = C*, the optimal cost, while every node off an optimal path has f(n) > C*. With favourable tie-breaking, A* walks straight down an optimal path to the goal, expanding only the solution nodes themselves. The catch is that computing h* means solving the remaining subproblem optimally, which is as hard as the original problem — so the perfect heuristic is a theoretical reference point, not an implementation strategy.

Every real heuristic lives between these poles, and heuristic design is the craft of climbing from the h = 0 end towards the h = h* end while keeping evaluation cheap and admissibility intact. Relaxation tells you how to climb safely; dominance tells you whether you have actually climbed; maximisation lets you merge partial climbs; and the time-versus-accuracy trade-off tells you when to stop.

A heuristic function, written h(n), is an estimate of the cost of the cheapest path from a state n to a goal state. It is the place where human knowledge about a problem domain enters an otherwise blind search: instead of expanding nodes in an arbitrary order, a search algorithm can use h(n) to prefer states that look closer to a solution. Good heuristics are cheap to compute and informative enough to cut the number of nodes expanded dramatically.

This topic introduces the standard examples you will reuse for the rest of the module. For grid or map pathfinding, straight-line (Euclidean) distance estimates the remaining travel cost, and Manhattan distance does the same when movement is restricted to horizontal and vertical steps. For the 8-puzzle, the number of misplaced tiles and the sum of each tile's Manhattan distance to its goal position are the two classic heuristics, and both can be derived by relaxing the rules of the puzzle. Once you have more than one candidate heuristic, you need a way to compare them: a heuristic that dominates another (gives larger but still admissible estimates) generally expands fewer nodes.

As you watch the videos, keep three questions in mind. First, what simplified or relaxed version of the problem does each heuristic solve exactly? Second, can this estimate ever exceed the true remaining cost — that is, is it admissible? Third, how do two heuristics for the same problem compare, and what happens when you take the maximum of several admissible heuristics? These questions set up the admissibility, consistency, and A* material that follows.
