Foundations of Uninformed Search

▶

Almost every interesting task an intelligent agent performs can be re-described as a question about sequences of choices: what series of actions takes me from where I am now to where I want to be? Planning a delivery route, solving a Rubik's cube, deciding the moves that restore a scrambled 8-puzzle, routing a packet across a network, or scheduling a set of machine operations all share this shape. The field of AI calls this shared shape a search problem, and the algorithms that solve it search algorithms. The power of the idea lies in its abstraction: once a task is phrased in the standard vocabulary, any search algorithm can be applied to it without knowing anything about puzzles, maps or packets. This topic develops that vocabulary precisely, builds the generic algorithmic skeleton that all the classical strategies share, and establishes the four yardsticks by which those strategies are compared.

The strategies examined in this module are called uninformed (or blind) because they operate with no domain knowledge about which unexplored directions look promising. They are the baseline against which informed methods such as greedy best-first search and A* are later measured, and — crucially — they are built on exactly the same framework, so understanding them thoroughly is the cheapest possible investment in understanding everything that follows.

Formulating a Search Problem

A search problem is specified by five components. Getting these five right is the entire modelling step; everything afterwards is mechanical. The five parts are the initial state, the actions, the transition model, the goal test, and the path cost function.

The initial state is the state in which the agent begins. For the 8-puzzle — a 3×3 frame holding eight numbered tiles and one blank — the initial state is the particular scrambled configuration you are handed. A convenient encoding is a tuple listing the tile in each cell in row-major order, with 0 for the blank:

initial_state = (7, 2, 4,
                 5, 0, 6,
                 8, 3, 1)      # written as the 9-tuple (7,2,4,5,0,6,8,3,1)

For a route-finding problem in Romania, the initial state might simply be the string "Arad". For a vacuum-cleaner world with two rooms, a state could be the pair (robot_location, dirt_status), e.g. ("L", ("dirty", "clean")). Note that a state is an abstraction: it records only what matters for solving the problem. The 8-puzzle state does not record the colour of the tiles, the time of day, or how the puzzle was scrambled. Choosing the right abstraction is a modelling decision with real consequences — too coarse and the model loses solvability, too fine and the state space explodes needlessly.

The actions component gives, for each state s, the set of actions legally applicable in s, usually written ACTIONS(s). This is a function of the state, not a fixed global list, because legality depends on context. In the 8-puzzle the natural action set is the movement of the blank: {Up, Down, Left, Right}. But in the configuration above the blank is in the centre so all four apply, whereas if the blank were in the top-left corner only {Down, Right} would be applicable. In route finding, ACTIONS("Arad") = {Go(Zerind), Go(Sibiu), Go(Timisoara)} — the roads that actually leave Arad.

def actions(state):
    i = state.index(0)          # position of the blank, 0..8
    row, col = divmod(i, 3)
    result = []
    if row > 0: result.append("Up")
    if row < 2: result.append("Down")
    if col > 0: result.append("Left")
    if col < 2: result.append("Right")
    return result

The transition model, also called the successor function, answers: if I am in state s and perform action a, what state results? It is written RESULT(s, a) = s'. In the 8-puzzle, RESULT((7,2,4,5,0,6,8,3,1), "Up") swaps the blank with the tile above it, giving (7,0,4,5,2,6,8,3,1). The model is deterministic in classical search: one state and one action yield exactly one successor. Together, ACTIONS and RESULT implicitly define a directed graph over states — and this is the key point: the graph is never written down in advance. It is generated on demand, one successor at a time, which is what makes it possible to search spaces with 1020 states on a laptop.

def result(state, action):
    i = state.index(0)
    swap = {"Up": i - 3, "Down": i + 3, "Left": i - 1, "Right": i + 1}[action]
    s = list(state)
    s[i], s[swap] = s[swap], s[i]
    return tuple(s)

The goal test decides whether a given state satisfies the objective. It comes in two flavours. The first is explicit enumeration: there is a single goal state, or a small listed set, and the test is an equality or membership check — for the 8-puzzle, state == (1,2,3,4,5,6,7,8,0); for route finding, state == "Bucharest". The second is an abstract property check, used when the goals cannot practically be listed. In the 8-queens problem the goal test is "no two queens attack each other" — there are 92 solutions and nobody enumerates them in advance. In the vacuum world the test is "every square is clean", regardless of where the robot ends up. Property-based goal tests are extremely common and are what allow search to be applied to design and configuration problems.

The path cost function assigns a numeric cost to a path, and is almost always additive: the cost of a path is the sum of the costs of its individual steps, where the step cost c(s, a, s') is the cost of applying action a in state s to reach s'. We write g(n) for the cost of the path from the initial state to node n. In the 8-puzzle every move costs 1, so path cost equals path length. In Romanian route finding each step costs the road distance in kilometres, so g(n) is total distance travelled. Step costs may encode time, fuel, money, risk, or any additive quantity. A standard and important assumption in uninformed search is that step costs are non-negative, and for some guarantees that they are bounded below by some ε > 0; negative-cost cycles would make "cheapest path" meaningless, and zero-cost infinite loops can defeat termination arguments.

Here is a compact worked formulation of the vacuum world to show all five parts together.

Initial state("L", ("dirty", "dirty")) — robot in left room, both rooms dirty

With 2 robot positions × 2 dirt statuses × 2 dirt statuses, this world has exactly 8 states — small enough to draw in full, which makes it a favourite teaching example.

State Space, Paths, and Solutions

The state space is the set of all states reachable from the initial state by any finite sequence of applicable actions. It is not the set of all syntactically describable states. The 8-puzzle has 9! = 362,880 arrangements of eight tiles and a blank, but these split into two parity classes that cannot reach one another by legal moves, so the reachable state space from any given start is 9!/2 = 181,440 states. This distinction matters: half of all 8-puzzle "goals" are unreachable from any given start, and a search that is not told this will exhaustively and fruitlessly explore 181,440 states before reporting failure.

Viewed as a graph, the state space has states as vertices and actions as directed edges labelled with their step costs. A path is a sequence of states s0, s1, …, sk in which each consecutive pair is connected by an applicable action. A solution is a path whose first state is the initial state and whose last state passes the goal test. An optimal solution is a solution of minimum path cost among all solutions. Note the asymmetry: completeness is about finding a solution; optimality is about finding the cheapest one. An algorithm can easily have the first property and lack the second.

Consider a tiny weighted graph to make this concrete, with start S and goal G:

S --1--> A --1--> G        total cost 2, length 2
S --4--> G                 total cost 4, length 1
S --1--> B --1--> C --1--> G   total cost 3, length 3

There are three solutions. The shortest in number of steps is S → G (one action), but the cheapest is S → A → G (cost 2). An algorithm that minimises the number of steps returns a sub-optimal answer here, which is exactly why breadth-first and uniform-cost search are not interchangeable.

State spaces are frequently enormous and sometimes infinite. The 15-puzzle has about 1.3 × 1013 reachable states; Rubik's cube has about 4.3 × 1019; chess has an estimated 1040-plus legal positions. An infinite state space arises whenever states are drawn from an unbounded set — for instance, a problem whose states are integers with actions "add 1" and "double". No algorithm can enumerate such a space, and none tries to. Search algorithms build only the fragment of the graph they actually touch, generating successors lazily. This is the single most important implementation idea in the whole area: the state space is a mathematical object; the search tree is the concrete, partially-built data structure the algorithm holds in memory.

That distinction deserves emphasis. The search tree's nodes are not states — they are nodes, bookkeeping records that pair a state with the path used to reach it. The same state can appear in many different nodes (reached by different routes), and in a cyclic state space a finite graph can generate an infinite tree. A node typically carries four fields:

class Node:
    def __init__(self, state, parent=None, action=None, path_cost=0):
        self.state     = state       # the state this node represents
        self.parent    = parent      # the node that generated this one
        self.action    = action      # the action applied to the parent
        self.path_cost = path_cost   # g(n): cost from the initial state

def solution_path(node):             # parent-pointer reconstruction
    actions = []
    while node.parent is not None:
        actions.append(node.action)
        node = node.parent
    return list(reversed(actions))

The parent pointer is what makes the solution recoverable. The algorithm does not store whole paths in the frontier — it stores single nodes, and reconstructs the path backwards from the goal node when the search succeeds.

Two structural parameters summarise a state space for analysis purposes. The branching factor b is the number of successors a node has — usually the average or maximum over the space. For the 8-puzzle it averages roughly 2.67 (two successors from a corner blank, three from an edge, four from the centre); for Rubik's cube with quarter-turn moves it is 12; for chess roughly 35. The solution depth d is the number of actions in the shallowest solution. A third parameter, m, denotes the maximum depth of the search tree (possibly infinite). Nearly every complexity result in this module is a formula in b, d and m. The reason they matter so much is exponential growth: with b = 10, a depth-6 search touches on the order of 106 nodes, depth-10 touches 1010, and depth-14 touches 1014. Each extra level multiplies the work by b.

The Generic Search Framework: Tree Search

All the classical strategies are instances of a single loop. The loop maintains a frontier (also called the open list or fringe): the collection of nodes that have been generated but not yet expanded — the growing boundary between the explored region and the unexplored region. The algorithm is:

function TREE-SEARCH(problem) returns a solution, or failure
    frontier <- a container holding Node(problem.initial_state)
    loop do
        if frontier is empty then return failure
        node <- REMOVE(frontier)                 # strategy decides WHICH node
        if problem.GOAL-TEST(node.state) then return SOLUTION(node)
        for each action in problem.ACTIONS(node.state) do
            child <- CHILD-NODE(problem, node, action)
            INSERT(child, frontier)

Step by step: initialise the frontier with a single node wrapping the initial state, with no parent, no action and path cost 0. Then loop. If the frontier is ever empty, every reachable node has been expanded without success, so return failure. Otherwise remove one node — and this removal rule is the strategy. Apply the goal test to the removed node; if it passes, walk the parent pointers back to the root and return the action sequence. If it fails, expand the node: for every applicable action, build a child node whose state is RESULT(s, a), whose parent is the current node, and whose path cost is node.path_cost + c(s, a, child.state); insert each child into the frontier.

def child_node(problem, parent, action):
    s2 = problem.result(parent.state, action)
    return Node(state=s2,
                parent=parent,
                action=action,
                path_cost=parent.path_cost + problem.step_cost(parent.state, action, s2))

Now the central observation of the entire module: the only difference between breadth-first, depth-first, and uniform-cost search is the rule by which REMOVE chooses the next node. Change the frontier's data structure and you change the algorithm, with no other edits at all.

StrategyFrontier data structureNode removed next
Breadth-first searchFIFO queuethe shallowest unexpanded node (oldest inserted)
Depth-first searchLIFO stackthe deepest unexpanded node (newest inserted)
Uniform-cost searchpriority queue keyed on g(n)the unexpanded node of lowest path cost

This is a remarkably economical design. A single, well-tested implementation of the loop, parameterised by a frontier object exposing push, pop and is_empty, yields three distinct algorithms with entirely different behavioural guarantees. When informed search is introduced later, greedy best-first (priority queue on h) and A* (priority queue on g + h) slot into exactly the same loop.

One subtlety deserves attention: when the goal test is applied. In the framework above it is applied when a node is removed from the frontier ("late" goal test). An alternative applies it when a node is generated ("early" goal test), which can save a level of expansion. For breadth-first search with uniform step costs, early testing is safe and faster. For uniform-cost search it is not safe: a goal node may be generated via an expensive path long before a cheaper path to the same goal is found, so the goal test must be deferred until the node is selected for expansion. Keeping the test at removal time is the conservative default that works for all strategies.

The weakness of pure tree search is that it has no memory of where it has been. In a state space with cycles — which includes virtually every realistic one, since most actions are reversible — it will regenerate states endlessly. In the 8-puzzle, moving the blank Up and then Down returns to the original state; pure tree search will happily follow such loops forever and never terminate, even though the state space is finite. Worse, even in acyclic spaces, repeated states cause exponential blow-up: a rectangular grid with four movement actions has roughly 2d distinct paths of length d leading to only O(d2) distinct cells.

Graph Search and the Explored Set

The fix is to remember what has already been dealt with. Graph search augments tree search with an explored set (historically the closed list): the set of states of all nodes that have been expanded.

function GRAPH-SEARCH(problem) returns a solution, or failure
    frontier <- a container holding Node(problem.initial_state)
    explored <- an empty set
    loop do
        if frontier is empty then return failure
        node <- REMOVE(frontier)
        if problem.GOAL-TEST(node.state) then return SOLUTION(node)
        add node.state to explored
        for each action in problem.ACTIONS(node.state) do
            child <- CHILD-NODE(problem, node, action)
            if child.state not in explored and child.state not in frontier then
                INSERT(child, frontier)

The two added lines carry the whole idea. A newly generated child is discarded if its state is already in the explored set (we have already expanded it, so its successors are already accounted for) or already present in the frontier (a node for that state is already queued). For uniform-cost search the frontier check is refined: if the state is in the frontier with a higher g value, the old node is replaced by the cheaper new one rather than discarding the new one — a step usually called decrease-key or relaxation.

The consequences are significant:

  • Termination on finite state spaces. Each state can be expanded at most once, so the loop performs at most |S| expansions and must terminate, with success or with a correct report of failure. Cycles are no longer fatal.
  • Elimination of redundant work. The search tree is pruned down to something no larger than the state space itself. In the grid example above, graph search explores O(d2) cells instead of O(2d) paths — an exponential saving.
  • A memory cost. The explored set grows with the number of distinct states visited, and nothing is ever removed from it. For large spaces, the explored set, not the frontier, can become the binding constraint. This is the reason depth-first search's celebrated O(bm) space advantage evaporates in its graph-search form: once you store every visited state, you are back to space proportional to states visited.

The membership tests must be fast, because they run once per generated node, which is the inner loop of the whole algorithm. A hash set keyed on a canonical representation of the state gives expected O(1) membership checks. "Canonical" means two logically identical states always produce the identical key. For the 8-puzzle, a 9-tuple of integers hashes cleanly and compares by value. Pitfalls to avoid include hashing mutable objects (a Python list is unhashable; convert to a tuple), hashing by object identity instead of content (two distinct objects describing the same board must be treated as equal), and non-canonical orderings (if a state is a set of facts, sort it or use a frozenset so that {A,B} and {B,A} produce the same key).

explored = set()
frontier_states = set()       # mirrors the frontier for O(1) membership

explored.add(node.state)      # states must be hashable and canonical
if child.state not in explored and child.state not in frontier_states:
    frontier.push(child)
    frontier_states.add(child.state)

Keeping a parallel frontier_states set is the standard trick: a bare queue or stack supports O(1) push and pop but only O(n) membership testing, which would dominate the running time. The set mirrors the frontier's contents so that both checks are constant-time.

The choice between tree search and graph search is therefore a classic time–space trade-off, resolved differently in different settings. Use graph search when the state space has many repeatedstates and the explored set fits in memory — which covers most puzzles, maps and planning graphs. Use tree search (or a cheaper partial remedy) when memory is scarce: a common middle ground is to store no explored set at all but to reject any child whose state already appears on the path from the root to the current node, which costs O(d) per check, uses no extra memory beyond the path itself, and eliminates cycles though not all repeated states.

What Makes a Strategy 'Uninformed'

A search strategy is uninformed — equivalently blind — when its decision about which node to expand next uses no information about the problem beyond what the five-part specification provides. The defining characteristics follow from that single restriction.

  • No estimate of remaining distance. An uninformed strategy has no heuristic function h(n) estimating the cost from n to the nearest goal. Standing at Arad with Bucharest as the goal, it does not know that Sibiu is geographically nearer to Bucharest than Timisoara; both are simply successors.
  • Goal states are recognised, not anticipated. The only window onto "goalness" is the boolean goal test, which returns true or false. It cannot return "almost". A state one move from solving the 8-puzzle and a state eighty moves away are, to an uninformed algorithm, indistinguishable: both simply fail the test.
  • Ordering uses structural facts only. Decisions are made from quantities the framework already computes: a node's depth, its insertion time, or its accumulated path cost g(n). Breadth-first orders by depth, depth-first by recency, uniform-cost by g(n). Every one of those is derivable from the node record itself without consulting the problem domain.
  • General-purpose but often inefficient. Because they assume nothing, uninformed strategies apply unchanged to every problem that can be cast in the five-part form — the same BFS code solves the vacuum world, route finding and the 8-puzzle. The price is that they explore in essentially every direction at once. On the 8-puzzle, breadth-first search may generate hundreds of thousands of nodes where an informed search guided by a good heuristic generates a few thousand.
  • They are the foundation of informed search. Greedy best-first search and A* are not different algorithms; they are the same generic loop with a priority queue keyed on h(n) or g(n) + h(n). Indeed, uniform-cost search is A* with h(n) = 0 everywhere. Mastering the frontier, the explored set, node records and parent-pointer reconstruction here means that the later material adds only the heuristic and its properties.

A useful illustration of the gap: on a road map, uniform-cost search expands nodes in rings of equal path cost outward from the start in all directions. If the goal lies 200 km east, the algorithm still expands everything within 200 km to the west, north and south before reaching it. A* with straight-line distance as the heuristic stretches those rings into an ellipse elongated towards the goal, expanding a small fraction of the same nodes. The difference is entirely due to information, not to algorithmic cleverness.

It is worth being clear about what uninformed does not mean. It does not mean ignorant of cost: uniform-cost search uses step costs intensively. It does not mean random or unsystematic: these strategies are highly systematic. It means only that no knowledge about the goal's location in the state space is used to bias the ordering.

Four Criteria for Evaluating Search Algorithms

Every search strategy in this module is assessed on four criteria. They are the common currency that makes it possible to compare algorithms rigorously rather than by impression.

  • Completeness. Is the algorithm guaranteed to find a solution whenever at least one exists, and to report failure correctly when none does? Completeness is usually conditional, and the conditions matter. Breadth-first search is complete provided the branching factor b is finite. Depth-first tree search is incomplete: on an infinite-depth branch or a cycle it can descend forever past a solution sitting one step to the side; in graph-search form on a finite state space it becomes complete. Uniform-cost search is complete provided every step cost exceeds some ε > 0 — without that condition it can be trapped by an infinite sequence of zero-cost actions, accumulating no cost and never advancing.
  • Optimality. Does the algorithm always return a least-cost solution? This is strictly stronger than completeness. Depth-first search returns the first solution it stumbles upon, which may be arbitrarily worse than the best. Breadth-first search returns the shallowest goal, which is optimal only when path cost is a non-decreasing function of depth — in practice, when all step costs are equal. Uniform-cost search returns the cheapest goal under any non-negative step costs, which is precisely why it exists as a separate algorithm. Returning to the earlier three-path example, BFS returns S → G at cost 4 while UCS returns S → A → G at cost 2; both are "correct" solutions, but only one is optimal.
  • Time complexity. How long does the search take, measured as the number of nodes generated (some texts count nodes expanded; the two differ by roughly a factor of b). The standard expressions are in terms of b, d and m. Breadth-first search generates O(bd) nodes; depth-first search may generate O(bm). These are exponential, and the exponent is what dominates — doubling b is far less damaging than adding one to d when d is large.
  • Space complexity. How many nodes must be held in memory simultaneously — the frontier plus, in graph search, the explored set. This is frequently the binding constraint in practice, and it is the single most important reason depth-first and iterative-deepening variants remain in use. A machine generating 106 nodes per second will produce 109 nodes in under twenty minutes, which is tolerable; but storing 109 nodes at, say, 100 bytes each requires 100 GB, which usually is not. Breadth-first search typically exhausts memory long before it exhausts patience, while depth-first search's frontier holds only O(bm) nodes.

Two points about how these measures are expressed. First, complexity is counted in nodes rather than seconds or bytes. A count of nodes is a property of the algorithm and the problem, independent of language, compiler, processor speed and memory architecture; a time in seconds would have to be re-measured on every new machine and would tell you nothing transferable. Translating back is straightforward if needed: multiply the node count by the per-node cost of generating and testing a node, and multiply the stored-node count by the bytes per node record.

Second, the parameters must be stated carefully. b is the branching factor (maximum or average), d the depth of the shallowest goal, m the maximum depth of the search space, which may be infinite. For uniform-cost search the natural parameters are not b and d but the optimal solution cost C* and the minimum step cost ε, giving O(b1+⌊C*/ε⌋) — a bound that reduces to roughly bd when all step costs are 1, but can be substantially worse when small step costs allow many cheap paths to be explored before a solution is reached.

Almost every classical AI problem — route planning, puzzle solving, scheduling moves in a game — can be cast in the same shape: you have a current situation, a set of legal moves, a way to tell when you are done, and a cost for getting there. Formulating a search problem means writing that down precisely as five parts: the initial state, the available actions, the transition model that says what each action does, the goal test, and the path cost function. Once a problem is in that form, the same generic algorithm can solve it regardless of whether the states are cities, board configurations, or robot positions.

The generic framework keeps a frontier of nodes waiting to be expanded and (in graph search) an explored set of states already visited, which prevents infinite loops and repeated work. Different search strategies differ only in one decision: which node to pull off the frontier next. A strategy is called uninformed (or blind) when that decision uses nothing beyond the problem definition itself — no estimate of how far a state is from the goal. We judge these strategies on four criteria: completeness (will it find a solution if one exists), optimality (will it find the cheapest one), time complexity, and space complexity.

As you watch the videos below, keep two things in mind. First, watch the data structure driving the frontier — a queue versus a stack changes nothing else about the algorithm but changes its behavior, guarantees, and memory use completely. Second, try to map what you see back onto the five-part formulation: what is the state, what counts as an action, and where does the explored set appear in the code or trace?

Breadth-First Search

1

Breadth-First Search

▶

Breadth-first search (BFS) is the canonical uninformed strategy: it explores a state space in order of increasing depth, examining every node that is one step from the start before any node that is two steps away, and so on. It needs no knowledge of the goal's location, no heuristic estimate, and no information about which branch "looks promising" — only the ability to generate the successors of a state. The entire behaviour of BFS follows from a single design decision: the frontier is a first-in, first-out (FIFO) queue. Everything else — the level-by-level sweep, the guarantee of finding a shallowest goal, the crippling memory appetite — is a consequence of that one choice. This topic develops BFS from its data structures through to its complexity, with concrete traces on a small graph and on the 8-puzzle.

BFS and the FIFO frontier. The frontier (sometimes called the open list) is the collection of nodes that have been generated but not yet expanded. BFS keeps this collection in a queue: newly generated successors are appended to the back, while the node chosen for expansion is always removed from the front. Because a node's children are necessarily one level deeper than the node itself, and because the parent entered the queue before any node of its own depth that was generated later, the queue is always sorted by depth. Concretely, every node at depth d is enqueued before any node at depth d+1 can be created, so the queue at any instant contains at most two adjacent depth levels: the tail of level d followed by the head of level d+1. The search therefore sweeps the tree level by level, and the point in the queue where depth changes is the "level boundary".

A node in a search algorithm is not the same thing as a state. A state is a configuration of the world (a city, a puzzle board); a node is a bookkeeping record in the search tree. The standard node record carries four fields:

  • state — the world configuration this node represents;
  • parent — a pointer to the node from which this one was generated;
  • action — the action applied to the parent to produce this node;
  • path-cost (often written g) — the cost of the path from the root to this node; for BFS on unit-cost edges this is simply the depth.

The parent pointer is what makes a solution recoverable. BFS does not store paths in the queue (that would be wasteful, since prefixes are shared); it stores single nodes and reconstructs the path only once, at the end, by walking parent pointers from the goal node back to the root and reversing the resulting list. The action fields along that chain give the plan; the path-cost field of the goal node gives the solution cost.

class Node:
    def __init__(self, state, parent=None, action=None, path_cost=0):
        self.state     = state
        self.parent    = parent
        self.action    = action
        self.path_cost = path_cost

def solution(node):
    actions, states = [], []
    while node.parent is not None:
        actions.append(node.action)
        states.append(node.state)
        node = node.parent
    states.append(node.state)
    actions.reverse(); states.reverse()
    return actions, states

Alongside the frontier sits the explored set (closed list): a set of states that have already been expanded. Its job is to stop the search from re-expanding a state it has already dealt with, which on a graph with cycles would otherwise cause infinite looping or combinatorial blow-up. In addition, a practical implementation keeps a membership structure over the states currently on the frontier — a hash set mirroring the queue's contents — because testing "is this state already queued?" by scanning a queue is O(n) and would dominate the running time. With a hash set the test is O(1).

def breadth_first_search(problem):
    node = Node(problem.initial)
    if problem.goal_test(node.state):          # trivial case
        return solution(node)
    frontier     = deque([node])               # FIFO queue
    frontier_set = {node.state}                # O(1) membership mirror
    explored     = set()

    while frontier:
        node = frontier.popleft()              # expand from the FRONT
        frontier_set.discard(node.state)
        explored.add(node.state)
        for action in problem.actions(node.state):
            child_state = problem.result(node.state, action)
            if child_state in explored or child_state in frontier_set:
                continue                       # duplicate: discard
            child = Node(child_state, node, action,
                         node.path_cost + problem.step_cost(node.state, action))
            if problem.goal_test(child_state): # goal test at GENERATION
                return solution(child)
            frontier.append(child)             # append to the BACK
            frontier_set.add(child_state)
    return None                                # frontier empty: failure

Note the cost profile of the data structures. popleft and append on a doubly-linked deque are O(1); hash-set insertion and lookup are O(1) expected. The queue machinery therefore never dominates: BFS's running time is proportional to the number of nodes it generates, multiplied by the cost of generating successors and hashing states. If one carelessly uses a Python list with pop(0), each dequeue becomes O(n) and the whole algorithm degrades to quadratic in the number of nodes — a classic implementation bug that is invisible on toy graphs and fatal on real ones.

Goal-test timing: generation versus expansion. There are two moments at which an algorithm can ask "is this a goal?": when a node is generated (just after it is created as a child) or when it is selected for expansion (just after it is removed from the frontier). BFS conventionally tests at generation, as in the pseudocode above, and the difference matters.

  • Testing at generation lets BFS stop the instant the first goal appears in a successor list. In the trace above, G was recognised during the expansion of E and the search stopped with F still unexpanded.
  • Testing at expansion would push G onto the queue behind F, expand F (generating nothing new), and only then dequeue G and report success. On a small graph this is a trifle; in general it forces BFS to generate the entire level d+1 before the goal at depth d is announced — roughly b times more nodes generated and, worse, b times more memory consumed. The time bound rises from O(b^d) to O(b^(d+1)).

The early test is safe for BFS because all nodes at a given depth are equally shallow: if a goal is generated at depth d, no goal can exist at depth less than d, because BFS would have generated every node at every shallower depth already. The shallowest goal is the cheapest goal only when depth and cost agree — that is, when every step costs the same (or, more generally, when path cost is a non-decreasing function of depth).

If step costs vary, testing at generation can be badly wrong. Imagine S → G as a single edge of cost 100 and S → X → G as two edges of cost 1 each. BFS generates G at depth 1, tests it, and returns a path of cost 100, having never looked at the cost-2 alternative at depth 2. This is exactly why uniform-cost search abandons the generation-time test: it orders the frontier by g and only declares success when a goal node is selected for expansion, at which point no cheaper path to any goal can remain on the frontier. The timing of the goal test is thus not a micro-optimisation but a correctness condition tied to the cost model.

Duplicate detection and repeated states. Real state spaces are graphs, not trees: many different action sequences lead to the same state. Without duplicate detection, BFS on the tiny graph above would generate A as a child of B, then B again as a child of that A, and so on forever, exploring an infinite tree over a seven-state world. The fix is the pair of membership tests in the pseudocode:

  • Discard a child whose state is in the explored set. That state has already been expanded, so every path through it has already been considered.
  • Discard a child whose state is already on the frontier. The queued copy was generated no later than this one, hence at depth no greater, so the new copy cannot improve on it.

The second rule deserves emphasis because it is specific to BFS's ordering guarantee: the first time BFS reaches a state, it has reached it by a path with the fewest possible steps. (Proof sketch: suppose a state s is first generated at depth k but a k'-step path with k' < k exists. Every node at depth k'-1 is expanded before any node at depth k-1, so the predecessor of s on the shorter path would have generated s earlier — contradiction.) Consequently later duplicates can be thrown away without storing or comparing costs. In uniform-cost search this is not true, and a cheaper later path to a frontier state must trigger a decrease-key replacement rather than a discard.

Efficient duplicate detection requires a canonical representation of each state that can be hashed. The representation must be such that two states are equal as world configurations exactly when their representations are equal. For the 8-puzzle, a tuple or string of the nine cell contents in row-major order works perfectly:

board  = ((1, 2, 3),
          (8, 0, 4),            # 0 denotes the blank
          (7, 6, 5))
key    = "123804765"            # canonical string, hashable, O(1) to compare
explored.add(key)

Mutable containers (Python lists, 2-D arrays) are not hashable and must be converted; and if a state has symmetries or an arbitrary internal ordering — a set of items, say — the canonical form must sort or normalise it, or logically identical states will hash to different keys and duplicate detection will silently fail.

The payoff is a change in the asymptotics of the problem itself. Without duplicate detection the search tree has as many nodes as there are paths, which is exponential in depth even for a tiny graph. With it, no state is ever expanded twice, so the number of expansions is bounded by the number of distinct reachable states. For a finite state space such as the 8-puzzle, this converts an unbounded search into one that provably terminates after at most 181,440 expansions. The price is memory for the explored set — which, for BFS, is memory we were going to spend on the frontier anyway.

Because every slide costs exactly 1, the depth of the first goal generated is the minimum number of moves, so BFS returns a provably optimal solution — this is the unit-cost case in which "shallowest" and "cheapest" coincide.

What stops you is memory, not time. The number of distinct states at depth d grows roughly as 2.13^d for the 8-puzzle, so a 20-move solution involves hundreds of thousands of generated nodes and a frontier holding tens of thousands of boards simultaneously; a complete BFS of the whole space holds up to roughly 24,000 boards on the frontier at the deepest levels and 181,440 in the explored set. That is comfortable on a modern machine. Scale the puzzle to 4×4 (the 15-puzzle) and the reachable space is about 1.3 × 10^13 states with solutions up to 80 moves: BFS cannot store a frontier of that size under any realistic memory budget, which is the practical motivation for iterative-deepening and heuristic search.

Completeness, optimality, and complexity. Let b be the maximum branching factor, d the depth of the shallowest goal, and m the maximum depth of the state space.

  • Completeness — yes. If a solution exists at some finite depth d and b is finite, BFS will find it. The argument is simply that BFS generates all nodes at depth 0, then all at depth 1, and so on; each level is finite (at most b^k nodes, and with duplicate detection at most the number of distinct states), so level d is reached after finitely many steps. BFS is complete even in infinite state spaces, provided the branching factor is finite — a property that depth-first search conspicuously lacks, since DFS can plunge down an infinite branch and never return. If the state space is infinite and no solution exists, BFS does not terminate, but no algorithm can do better in that case.
  • Optimality — conditionally. BFS returns a shallowest goal node. That is a least-cost goal only if path cost is a non-decreasing function of depth — which holds automatically when every step costs the same. With unequal step costs BFS is not optimal, as the S → G (cost 100) versus S → X → G (cost 2) example showed. For such problems, uniform-cost search — BFS's generalisation with a priority queue ordered by g, a goal test at expansion, and decrease-key on improved frontier paths — must be used instead.
  • Time complexity — O(b^d). With the goal test applied at generation, BFS expands the 1 + b + b² + … + b^(d-1) nodes above depth d and generates at most b^d nodes at depth d before stopping, giving O(b^d) nodes generated. Deferring the test to expansion adds a full extra level and raises the bound to O(b^(d+1)). On a graph with duplicate detection the bound is further capped by |S|, the number of distinct reachable states, so the true complexity is O(min(b^d, |S|)) — or, in graph terms, O(|V| + |E|) for a full traversal.
  • Space complexity — O(b^d). Every generated node must be retained: the explored set holds O(b^(d-1)) states and the frontier alone holds O(b^d) nodes at the deepest level. Unlike depth-first search, whose frontier is only O(bm), BFS keeps an entire level in memory simultaneously.

Depth-First Search

1

Depth-First Search

▶

Depth-first search (DFS) is the natural counterpart to breadth-first search. Both are uninformed strategies: they have no knowledge of how close a state is to the goal and differ only in which node they choose to expand next from the frontier. BFS always expands the shallowest unexpanded node; DFS always expands the deepest unexpanded node. That single change in expansion policy produces a radically different algorithm — one that uses dramatically less memory, dives to the bottom of the search tree before considering alternatives, can run forever in an infinite or cyclic space, and gives no guarantee whatsoever about the quality of the solution it returns. Understanding exactly where DFS wins, where it fails, and how the depth-limited and iterative-deepening variants repair its weaknesses is the core of this topic.

DFS strategy and the LIFO frontier. Every graph- or tree-search algorithm in the general framework shares the same skeleton: initialise the frontier with the root node, repeatedly remove a node from the frontier, test it for the goal, and add its successors. The only free choice is the data structure used for the frontier. BFS uses a FIFO queue. DFS uses a LIFO stack: the most recently generated successor is the next node to be popped and expanded. Because a node's children are generated at the moment the node is expanded, they sit on top of everything else, so the search immediately descends into the first child, then into that child's first child, and so on.

function DEPTH-FIRST-SEARCH(problem) returns a solution node or failure
    node  <- NODE(STATE = problem.INITIAL_STATE, PARENT = null, ACTION = null)
    frontier <- a LIFO stack containing node
    explored <- an empty set
    loop do
        if frontier is empty then return failure
        node <- POP(frontier)                     // deepest node, most recently added
        if problem.GOAL_TEST(node.STATE) then return SOLUTION(node)
        add node.STATE to explored
        for each action in REVERSE(problem.ACTIONS(node.STATE)) do
            child <- CHILD-NODE(problem, node, action)
            if child.STATE not in explored and child not in frontier then
                PUSH(child, frontier)

Two implementation details in that skeleton deserve attention. First, the successors are pushed in reverse order. A stack reverses whatever you put into it, so if the successor list is [Timisoara, Sibiu, Zerind] and you push left to right, Zerind ends up on top and is explored first. Pushing in reverse restores the intuitive behaviour in which the first-listed child is the first one explored, which matters a great deal when you are asked to trace an algorithm by hand and your trace must match the expected expansion order.

Second, the goal test is applied on expansion (when the node is popped), not on generation. For DFS this choice is largely cosmetic, because DFS offers no optimality guarantee either way; testing on generation simply lets the algorithm stop one expansion earlier. (In BFS, by contrast, testing on generation is a genuine efficiency win that preserves optimality for unit costs.) The tree-search variant of DFS, which has no explored set, typically tests on generation to avoid pushing a goal node and then losing it beneath a pile of deeper nodes.

The behavioural consequence of the LIFO rule is that DFS follows one path to its maximum depth before any sibling is considered. If the root has children A, B and C, the entire subtree beneath A — possibly millions of nodes — is exhausted before B is even looked at. Compare this with BFS, which sweeps across each level in turn and therefore necessarily finds a shallowest goal first. DFS has no such property: the first solution it returns may lie at depth 400 when a goal sits at depth 3 down a sibling branch that was never visited.

Recursive formulation and backtracking. Because the frontier is a stack, DFS maps perfectly onto the call stack of a recursive procedure. Each recursive call handles exactly one node and loops over that node's successors, calling itself on each in turn:

function RECURSIVE-DFS(problem, node, explored) returns a solution node or failure
    if problem.GOAL_TEST(node.STATE) then return node
    add node.STATE to explored
    for each action in problem.ACTIONS(node.STATE) do
        child <- CHILD-NODE(problem, node, action)
        if child.STATE not in explored then
            result <- RECURSIVE-DFS(problem, child, explored)
            if result != failure then return result
    return failure                                // dead end: backtrack to caller

Here the explicit stack has disappeared; the chain of pending for loops on the call stack is the frontier. When a call returns failure, the runtime pops that stack frame and execution resumes in the parent's successor loop at the next action — this is exactly the backtracking step. Backtracking is triggered in three circumstances: (1) the node is a genuine dead end with no successors, (2) every successor leads to an already-visited state, or (3) a depth limit has been reached (see the depth-limited variant below).

A further refinement is the backtracking search variant used in constraint satisfaction and puzzle solvers. Instead of generating all of a node's successors at once, it generates them one at a time, storing only a pointer to the next untried action at each node on the current path. Even better, many problems allow the successor state to be produced by modifying the current state in place and undoing the modification on backtracking (apply a move to the 8-puzzle board, then slide the tile back). This reduces the memory needed per node from a full state description to a single action index, so the whole search occupies only O(m) memory rather than O(bm).

The price of the recursive formulation is that recursion depth is bounded by path length. A search that descends 100,000 nodes deep will attempt 100,000 nested calls; typical default stack sizes overflow somewhere in the tens of thousands of frames. For deep searches, the explicit-stack iterative version is safer, because a heap-allocated stack can grow to whatever the heap allows.

Tracing DFS on the route-finding map. Take the familiar Romania map and ask DFS to find a route from Arad to Bucharest. Suppose the adjacency lists are stored in the order the cities were read from the input file, so that ACTIONS(Arad) = [Timisoara, Sibiu, Zerind] and ACTIONS(Craiova) = [Dobreta, Pitesti, Rimnicu Vilcea]. Successors are pushed in reverse so that the first-listed city is expanded first. Using graph search (with an explored set) and goal testing on expansion, the trace is:

BFS on the same map returns Arad → Sibiu → Fagaras → Bucharest: three hops and 450 km, and uniform-cost search returns the 418 km route through Rimnicu Vilcea and Pitesti. DFS plunged down the south-western detour simply because Timisoara happened to be first in Arad's adjacency list, and it never reconsidered. Notice also that Zerind and Sibiu — pushed at step 1 — sat untouched at the bottom of the stack for the entire search. That is the signature of DFS: a small frontier consisting of the current path plus the untried siblings hanging off it.

The solution path is recovered by parent pointers, exactly as in BFS. Each node stores a reference to the node that generated it, so from the goal node you walk backwards — Bucharest → Pitesti → Craiova → Dobreta → Mehadia → Lugoj → Timisoara → Arad — and reverse the list. In the recursive formulation the path is already implicit in the chain of active stack frames, so it can instead be read off as the recursion unwinds.

Tracing DFS on the 8-puzzle. The contrast is even starker on the 8-puzzle, whose branching factor averages about 2.67 (2 moves when the blank is in a corner, 3 on an edge, 4 in the centre). A typical scrambled start state is solvable in at most 31 moves, and BFS will find a 20-move optimal solution after expanding on the order of 105–106 nodes. DFS applied to the same instance behaves quite differently. Each expansion slides one tile, and the LIFO rule means the search keeps applying the first legal move in its action ordering, producing something like "blank up, blank up (blocked, so left), left, down, down, right, ..." — a random-looking walk through configuration space. With tree search (no explored set) this walk never terminates: the blank can oscillate Up, Down, Up, Down, ... forever, revisiting two states indefinitely, so DFS descends hundreds of thousands of levels without ever approaching a solved board. With graph search, the explored set blocks the oscillation, and because the reachable state space for a given parity contains only 181,440 states, DFS must eventually terminate. But it may return a solution path tens of thousands of moves long for a puzzle solvable in twenty — a legal plan, and a useless one.

The practical lesson from both traces is that DFS should be traced by writing down the stack at every step. The stack simultaneously shows the current path (the chain from the root down to the node just popped) and the pending alternatives (the siblings waiting beneath it). Students who track only the expansion order usually lose track of where backtracking will resume.

Space and time complexity. The memory advantage of DFS is its entire reason for existing. In the tree-search formulation, once a node has been expanded it can be removed from memory as soon as all of its descendants have been fully explored. At any instant the algorithm therefore stores only the nodes on the current root-to-leaf path, plus the unexpanded siblings of each node on that path. With branching factor b and maximum depth m, that is at most bm + 1 nodes, i.e. O(bm) space, which is linear in the depth. BFS, by contrast, needs O(b^d) space — exponential. The numbers are brutal: for b = 10 at depth 16 with 1 kB per node, BFS requires roughly 10 exabytes while DFS requires about 156 kB. The backtracking variant described above, which generates one successor at a time and mutates the state in place, cuts even this to O(m).

Time complexity, however, is O(b^m) — governed by the maximum depth m of the state space, not the depth d of the shallowest goal. When m is much larger than d, DFS can be catastrophically worse than BFS, because it may exhaust gigantic subtrees that lie entirely below the level at which a goal was available. Conversely, when solutions are dense at depth — many goal states lie at or near the bottom of the tree, as in the n-queens problem or many constraint-satisfaction problems — DFS often finds one almost immediately and beats BFS by orders of magnitude.

A critical caveat: graph-search DFS forfeits the space advantage. The explored set must retain every state ever expanded, so memory grows to O(min(|S|, b^m)) where |S| is the size of the reachable state space — the same asymptotic burden as BFS. If you want DFS for its linear memory, you must use the tree-search or backtracking form and accept the risk of repeated states, or use a partial cycle check (for instance, checking only against the states on the current path, which costs O(m) and eliminates loops but not all redundant paths).

Completeness, optimality, and infinitebranches. DFS pays for its cheap memory with weak guarantees. Consider the tree-search form first. Because it has no explored set, it can follow a cycle indefinitely: in the Romania map, tree-search DFS can generate Arad → Sibiu → Arad → Sibiu → ... forever, expanding deeper and deeper nodes that merely repeat two states. It never returns failure and never reaches Bucharest, even though a three-hop solution exists. Tree-search DFS is therefore incomplete.

Cycles are not the only danger. In a state space that is acyclic but infinitely deep — for instance, a planning problem in which an unbounded number of "add one more block to the tower" actions is always legal — DFS can march down a single non-goal branch forever while a goal sits two levels below the root on a different branch. No finite amount of computation will bring it back. This is the deepest structural weakness of DFS: it commits totally to its first choice and has no mechanism for reconsidering.

Adding an explored set repairs completeness in one important case. Graph-search DFS is complete in finite state spaces, because a state can be expanded at most once, so the search must eventually exhaust the reachable states and either find a goal or report failure. In infinite state spaces the explored set does not help: the search can still generate infinitely many distinct states down one branch.

Optimality is lost in every variant. DFS returns the first goal node it happens to encounter, which is determined by the arbitrary ordering of the successor function rather than by any property of the solution. That first goal is rarely the shallowest, and step costs are ignored entirely — DFS never examines g(n), never compares two paths to the same state, and would happily return a 733 km route when a 418 km route exists. Running DFS on a cost-weighted graph gives you exactly the same behaviour as running it on an unweighted one. If you need optimality under non-uniform costs you need uniform-cost search; if you need shallowest-goal optimality under uniform costs you need BFS or iterative deepening.

Depth-limited search. The cure for infinite branches is to refuse to look below a fixed depth L. Depth-limited search (DLS) is plain DFS with the added rule that a node at depth L is treated as having no successors. The algorithm must now distinguish two different kinds of non-success, so it returns one of three outcomes:

  • solution — a goal node was found within the limit;
  • failure — the whole space reachable within the limit was exhausted and contains no goal, so no solution exists at depth ≤ L;
  • cutoff — at least one branch was truncated at the limit, so a solution might exist deeper than L.
function DEPTH-LIMITED-SEARCH(problem, L) returns solution, failure, or cutoff
    return RECURSIVE-DLS(NODE(problem.INITIAL_STATE), problem, L)

function RECURSIVE-DLS(node, problem, limit) returns solution, failure, or cutoff
    if problem.GOAL_TEST(node.STATE) then return SOLUTION(node)
    else if limit = 0 then return cutoff
    else
        cutoff_occurred? <- false
        for each action in problem.ACTIONS(node.STATE) do
            child  <- CHILD-NODE(problem, node, action)
            result <- RECURSIVE-DLS(child, problem, limit - 1)
            if result = cutoff then cutoff_occurred? <- true
            else if result != failure then return result
        if cutoff_occurred? then return cutoff else return failure

The three-valued return is what makes DLS composable. A plain failure would be ambiguous and would mislead any caller that wanted to retry with a larger limit; the cutoff token says precisely "I ran out of permission, not out of states." Note how the flag propagates: an interior node returns failure only if every one of its subtrees returned failure.

Choosing L is the hard part. If L < d the search is incomplete — it reports cutoff and finds nothing even though a solution exists. If L is far larger than d the search wastes enormous effort exploring depths that could never contain the shallowest goal, and in the extreme it degenerates back towards plain DFS. Sometimes problem knowledge supplies a sound limit. In Romania there are 20 cities, so any city is reachable from any other by at most 19 steps; in fact the map's diameter is 9, so L = 9 is both sound (no solution is missed) and tight. For the 8-puzzle the diameter is 31 (God's number for the 3×3 sliding tile puzzle), so L = 31 guarantees completeness. For Rubik's Cube the corresponding figure is 20 quarter-... (half-turn metric) moves. When no such bound is known, any fixed L is a gamble.

The complexity of DLS follows directly from substituting L for m in the DFS analysis: O(b^L) time and O(bL) space. It is complete only if L ≥ d, and it is not optimal (within the limit it still returns the first goal it meets, not the shallowest).

Iterative deepening search. Iterative deepening depth-first search (IDS, or IDDFS) sidesteps the problem of choosing L by trying every value in turn: run DLS with limit 0, then 1, then 2, and so on until a solution is found.

function ITERATIVE-DEEPENING-SEARCH(problem) returns a solution or failure
    for limit = 0 to INFINITY do
        result <- DEPTH-LIMITED-SEARCH(problem, limit)
        if result != cutoff then return result     // solution, or genuine failure

Each iteration starts from scratch with a fresh, empty frontier, so the memory in use at any moment is that of a single depth-limited search: O(bd), the same linear order as plain DFS. Yet because the limits increase one at a time, the first goal found is necessarily at the shallowest goal depth d — which makes IDS complete whenever the branching factor is finite (and a solution exists), and optimal when all step costs are equal, exactly like BFS.

The obvious objection is that IDS regenerates the top of the tree over and over. The objection sounds damning and turns out not to be. Nodes at the bottom level are generated once, those at level d-1 twice, those at d-2 three times, and the root d+1 times. The total number of generated nodes is

N(IDS) = (d+1)b^0 + (d)b^1 + (d-1)b^2 + ... + 3b^(d-2) + 2b^(d-1) + 1b^d

Because the tree's node count grows geometrically, almost all nodes live in the deepest level, and that level is regenerated only once. For b = 10, d = 5, BFS generates 111,111 nodes while IDS generates 123,456 — about 11% more. For larger b the overhead shrinks further: the ratio tends to b/(b-1), so at b = 10 it is roughly 11% and at b = 25 only about 4%. The repeated work is thus a small constant factor, and the asymptotic time complexity is O(b^d) — the same as BFS — while the space complexity is exponentially better. (Only when b is very small, as in b = 2, does the overhead become significant, roughly doubling the work.)

Traced on the Romania map with the same adjacency ordering as before, IDS behaves like this: limit 0 expands only Arad and reports cutoff; limit 1 expands Arad, Timisoara, Sibiu, Zerind and reports cutoff; limit 2 expands those plus Lugoj, Oradea, Fagaras, Rimnicu Vilcea, Arad again (in the tree-search form) and reports cutoff; limit 3 finally reaches Bucharest via Sibiu → Fagaras and returns the three-hop, 450 km route — the same solution BFS found, obtained with a frontier that never held more than a handful of nodes. The cost was re-expanding Arad, Timisoara, Sibiu and Zerind four times, which is negligible.

The decision rule that follows is straightforward. Use DFS when memory is the binding constraint, the state space is finite and shallow relative to b, and solutions are dense at depth — the classic cases being n-queens, graph colouring, Sudoku and other constraint-satisfaction problems where any complete assignment at the bottom level is a solution. Use depth-limited search when a trustworthy bound on solution depth is available from the problem structure. If step costs vary, none of these strategies offers a cost guarantee, and uniform-cost search (or its iterative-deepening analogue, which increases a cost bound rather than a depth bound) is required instead.

Depth-first search (DFS) explores a state space by always expanding the deepest unexpanded node first. In practice this means the frontier behaves as a stack (last-in, first-out): the most recently generated successors are the next ones tried. DFS can also be written recursively, where the call stack itself holds the path being explored and returning from a call is exactly the act of backtracking to the most recent branch point.

Uniform-Cost Search

▶

Uniform-cost search (UCS) is the uninformed strategy that answers the question breadth-first search cannot: what if some actions are more expensive than others? Breadth-first search explores the state space in layers of increasing depth, which is the right thing to do only when depth and cost happen to be the same quantity. Uniform-cost search replaces the notion of "shallowest unexpanded node" with "cheapest unexpanded node", and in doing so it becomes a general shortest-path algorithm over arbitrary non-negative edge weights while remaining completely blind to where the goal actually is. It is, in essence, Dijkstra's algorithm recast in the vocabulary of problem solving by search: a start state instead of a source vertex, a transition model instead of an adjacency list, and a goal test instead of a full distance table.

From BFS to Uniform-Cost Search

Consider a road map in which the operator "drive from Arad to Sibiu" costs 140 km and "drive from Arad to Zerind" costs 75 km. Breadth-first search treats these two actions as interchangeable: both produce a node at depth 1, both are enqueued in generation order, and BFS will happily return a two-step route of 500 km in preference to a three-step route of 200 km. BFS is optimal with respect to number of actions, and that coincides with optimality in cost only under the special condition that every action has the same positive cost. Remove that condition and BFS's guarantee evaporates immediately.

Uniform-cost search fixes this by ordering the frontier on the function

g(n) = the total cost of the path from the initial state to node n
     = sum of the step costs of every action along that path

For the root, g(start) = 0. For any child generated by applying an action to a parent, g(child) = g(parent) + cost(parent, action, child). The algorithm then always expands a frontier node with minimum g. Everything else — the transition model, the explored set, parent pointers, path reconstruction — is unchanged from BFS.

Three consequences follow directly from this definition and are worth stating explicitly:

  • UCS generalises BFS. If every step costs the same constant c > 0, then g(n) = c × depth(n), so ordering by cost is exactly ordering by depth. UCS then expands nodes in non-decreasing depth order and reduces to BFS (with the minor difference, discussed below, that it goal-tests later). This is a useful sanity check: any correct UCS implementation, run on an unweighted graph, must reproduce BFS's expansion order up to tie-breaking.
  • UCS requires non-negative step costs. The entire correctness argument rests on the claim that once a node is expanded, no cheaper route to it can ever appear later — because every route still under construction already costs at least as much, and extending a route can only add cost. A negative edge breaks this. Take S→A = 2, S→B = 5, B→A = −4. UCS pops A at cost 2 and marks it explored, but the true cheapest path S→B→A costs 1 and is discovered only after A has been closed. For graphs with negative weights one needs Bellman–Ford or Johnson's algorithm, not UCS.
  • UCS is still uninformed. It consults g(n), the cost already spent, and never any estimate h(n) of the cost remaining. It therefore has no idea whether a node is near the goal or in the opposite direction; it only knows which partial routes are cheap. Adding an estimate of the remainder produces A* and greedy best-first search, which belong to the informed family.

The Priority Queue Frontier

The data structure that implements "cheapest first" is a priority queue (usually a binary min-heap) keyed on g. Its contract is simple: pop() removes and returns an element whose key is minimal among all elements currently stored. A typical UCS implementation maintains three structures:

  • frontier — a priority queue of generated-but-not-yet-expanded nodes, ordered by g;
  • explored — a set of states already expanded (sometimes called the closed set);
  • parent / cost tables — maps recording, for each reached state, its best known predecessor and its best known g value, so that the solution path can be reconstructed backwards from the goal.

A crucial invariant is that each state appears at most once in the frontier, holding its cheapest known cost. If a state is reached again by a cheaper route, we do not insert a second copy; we lower the key of the existing entry. Allowing duplicates is not wrong in the sense of producing wrong answers (the cheap copy pops first, and the expensive copy can be discarded when it eventually pops), but it inflates memory and lets the heap grow with the number of edges rather than the number of states.

function UNIFORM-COST-SEARCH(problem) returns a solution or failure
    node  ← NODE(state = problem.INITIAL, g = 0, parent = none)
    frontier ← priority queue ordered by g, containing node
    explored ← empty set

    loop do
        if frontier is empty then return failure
        node ← POP(frontier)                      # cheapest unexpanded node
        if problem.IS-GOAL(node.state) then       # goal test AT EXPANSION
            return RECONSTRUCT-PATH(node)
        add node.state to explored
        for each action in problem.ACTIONS(node.state) do
            child ← CHILD-NODE(problem, node, action)
            # child.g = node.g + problem.STEP-COST(node.state, action)
            if child.state not in explored and child.state not in frontier then
                INSERT(frontier, child)
            else if child.state in frontier with g_old > child.g then
                DECREASE-KEY(frontier, child.state, child.g)
                set parent[child.state] ← node    # keep the path consistent

On cost: a binary heap performs insert, pop-min and decrease-key in O(log n) time for a heap of n entries. Since every generated node is inserted at most once and popped at most once, the queue discipline multiplies the work by only a logarithmic factor — the dominant cost of UCS is still the number of nodes generated, not the bookkeeping. With a Fibonacci heap, decrease-key becomes amortised O(1), giving the textbook Dijkstra bound O(E + V log V); in practice binary heaps are faster for the graph sizes typical of search problems.

Many standard libraries (for example Python's heapq) provide no decrease-key operation. The usual workaround is lazy deletion: push a second entry (new_g, state) and, when popping, discard any entry whose state is already in explored or whose stored cost exceeds the best known cost for that state. This preserves correctness and the optimality guarantee, at the price of a larger heap.

# Lazy-deletion variant of the pop step
cost, state, parent = heappop(frontier)
if state in explored: continue          # stale duplicate — skip it
if cost > best_g[state]: continue       # superseded entry — skip it

Goal Test at Expansion, Not Generation

Breadth-first search is normally written to test each child as it is generated, which saves a whole extra layer of expansion. Uniform-cost search must not do this. The reason is that in a weighted graph a goal node can be generated early by an expensive route while a cheaper route to the same goal is still buried in the frontier.

The minimal counterexample has three nodes. Let S→G cost 10, S→A cost 1, and A→G cost 2.

  • Expand S. Children generated: A at g = 1 and G at g = 10.
  • Testing at generation would return the route S→G at cost 10 and stop.
  • Testing at expansion, we instead pop A (cost 1), generate G again at cost 3, lower G's key from 10 to 3, and finally pop G at cost 3 — the optimal answer.

The positive statement of the rule is the heart of UCS's correctness: because the frontier is ordered by g, every node still in the frontier costs at least as much as the node just popped, and (with non-negative costs) every node reachable through the frontier costs at least that much too. Therefore the first goal node popped has minimal path cost among all solutions. BFS escapes this argument only because, with uniform costs, all paths reaching a given depth cost exactly the same, so no later-found route to the goal can possibly be cheaper.

Testing at expansion costs a little: UCS will typically pop and expand every node whose g is strictly less than C* (the optimal solution cost), and may also pop some nodes whose g exactly equals C* if tie-breaking happens to order them before the goal. That extra work is precisely the price of the optimality guarantee, and it is the same phenomenon that makes A* expand all nodes with f(n) < C* and some with f(n) = C*.

Re-opening Nodes with Cheaper Paths

When a child is generated whose state has already been reached, UCS must decide what to do with it. There are exactly three cases:

  • The state is in the frontier at a higher cost. The new route is better: perform decrease-key to lower the stored cost to g(child), and update the parent pointer to the new parent. Updating the key without updating the parent is a classic bug — the algorithm would then report the correct cost but reconstruct a different, more expensive path, so cost and path disagree.
  • The state is in the frontier at an equal or lower cost. The new route is no improvement. Discard the child node immediately; do not insert, do not touch the parent pointer. (Discarding on ties keeps the frontier small and causes no loss, since the retained path costs the same.)
  • The state is already in the explored set. With non-negative step costs it has already been expanded at its optimal cost, so no cheaper route to it can exist. Discard the child. This is why UCS never genuinely "re-opens" closed nodes — the term re-opening properly belongs to A* with an inconsistent heuristic, where a closed node's value can still improve. For UCS, re-opening is unnecessary, and an implementation that does it wastes time without changing the answer.

Omitting the first check entirely — simply ignoring any child whose state has been seen before, regardless of cost — does not break termination and still returns a path, but that path may be suboptimal, because the first route discovered to a state is not necessarily the cheapest one. In the trace below, exactly this check is what turns a 12-cost answer into the correct 9-cost answer.

Several features of the trace deserve comment:

  • Expansion order follows increasing g: 0, 1, 3, 5, 6, 9. This is a strict invariant of UCS with non-negative costs and is the easiest way to spot an error in a hand trace — if your popped costs ever decrease, something is wrong.
  • Cost contours. UCS sweeps outwards from the start in bands of equal cumulative cost, like ripples on a pond. After expanding the node at cost 5, every state reachable for 5 or less has been settled. This is the geometric intuition behind the phrase "uniform cost": the search boundary is a surface of uniform g.
  • Three decrease-key events occurred (B from 4 to 3, C from 6 to 5, D from 8 to 6, and G from 12 to 9 — four in fact). Had the implementation skipped already-reached states instead of comparing costs, it would have returned S → B → C → G or similar at cost 12: valid, but 33% worse than optimal.
  • UCS expands nodes "in the wrong direction". Node A, at cost 1, is expanded first even though it may lie away from G; a greedy or A* search with a straight-line heuristic would prefer nodes pointing towards the goal. UCS cannot do this because it has no notion of where G is. On a road map this means UCS explores a roughly circular region around the start of radius C*, whereas A* explores an ellipse stretched towards the goal.

Properties and Complexity

Let b be the branching factor, C* the cost of the optimal solution, and ε a positive lower bound on any step cost (so every action costs at least ε).

  • Completeness. UCS is complete provided every step cost is at least ε > 0 and a solution exists. The ε condition is not pedantry: if costs may approach zero, an infinite sequence of ever-cheaper actions can form an infinite path of finite total cost, and UCS can get trapped expanding it forever without ever reaching the contour containing the goal. With costs bounded below, only finitely many nodes have g < C*, so the goal must eventually be popped.
  • Optimality. UCS is optimal, by the argument given above: the first goal node expanded has the lowest achievable path cost. Note that this holds regardless of where goal states sit in the graph and regardless of how many of them there are.
  • Time and space complexity. UCS's performance is governed by cost, not depth. It may expand every node with g < C*, and the number of such nodes is bounded by O(b^(1 + ⌊C*/ε⌋)). Compare BFS's O(b^d): when all step costs equal ε, C*/ε = d and the two bounds coincide apart from the "+1" that reflects UCS's later goal test. When cheap actions abound, C*/ε can greatly exceed d, and UCS does strictly more work than BFS would — the price of handling weights.
  • Space is the binding constraint. As with BFS, space complexity equals time complexity because every generated node is retained in either the frontier or the explored set. Exponential growth in the frontier exhausts memory long before patience runs out: a frontier of a few tens of millions of nodes is already gigabytes. This, not running time, is what usually kills UCS on large problems, and it motivates memory-bounded variants and informed search.
  • Relationship to Dijkstra's algorithm. UCS is Dijkstra's single-source shortest-path algorithm with two cosmetic differences: it stops as soon as the goal is popped rather than settling every vertex, and it generates successors on demand from the transition model rather than reading a stored adjacency list. The second point matters for implicitly defined state spaces (puzzle configurations, robot poses) where the graph is far too large to build explicitly but each node's successors are cheap to compute.

Breadth-first search finds the shallowest solution, which is only the cheapest solution when every edge costs the same. Uniform-cost search (UCS) removes that assumption: instead of a FIFO queue, the frontier is a priority queue ordered by g(n), the cumulative cost of the path from the start node to n. The algorithm always expands the cheapest-so-far node, which is why it returns an optimal solution on graphs with non-negative edge weights, and why it is essentially Dijkstra's algorithm rephrased in search-problem language.

Two details separate a correct UCS implementation from a subtly broken one. First, the goal test happens when a node is expanded (popped from the frontier), not when it is generated (pushed), because a goal discovered along an expensive path may later be reached more cheaply. Second, when a node already on the frontier is reached again by a cheaper path, its priority must be lowered — or the cheaper entry inserted and the stale one ignored — so that optimality is preserved. Both points will come up repeatedly when you trace UCS by hand on a weighted route map.

Data Structures and Implementation

Data Structures and Implementation

▶

Every uninformed search algorithm — breadth-first, depth-first, depth-limited, iterative deepening, and uniform-cost — is built from the same three moving parts: a node representation, a frontier (the collection of generated-but-not-yet-expanded nodes), and an explored set (the record of states already expanded). What distinguishes one algorithm from another is almost entirely the data structure chosen for the frontier. This is one of the most useful simplifications in all of classical AI: once you have written a single generic graph-search loop, you obtain BFS by plugging in a FIFO queue, DFS by plugging in a LIFO stack, and uniform-cost search by plugging in a min-priority queue keyed on path cost. The correctness, the running time, and the memory profile of your solver all hinge on choosing those structures carefully and on a handful of implementation details that are easy to get subtly wrong.

The sections below work through those details: what a search node must store and why, how each frontier structure behaves, how hash-based explored sets make duplicate detection cheap, how uniform-cost search handles the awkward case of rediscovering a state along a cheaper path, how to rebuild the solution path from parent pointers, and finally two complete coding exercises — the 8-puzzle and weighted route finding — that exercise all of it.

The Search Node: More Than Just a State

A beginner's instinct is to put raw states on the frontier. That works just long enough to find a goal and then fails, because at that moment you know that the goal is reachable but not how you reached it. The fix is to wrap each state in a search node, a small bookkeeping record that remembers where the state came from.

A node carries four essential fields and one optional one:

  • state — the configuration of the world this node refers to (a board layout, a city name, a coordinate pair).
  • parent — a pointer to the node that generated this one; None for the root.
  • action — the action applied to the parent's state to produce this state (e.g. 'Up', 'Sibiu'). None for the root.
  • path_cost, conventionally written g(n) — the total cost of the path from the initial state to this node, computed as parent.path_cost + step_cost(parent.state, action).
  • depth (optional) — the number of actions from the root. It is simply parent.depth + 1, and it is worth storing explicitly whenever you implement depth-limited or iterative-deepening search, because those algorithms test it on every expansion. If you do not store it, you can always derive it by walking parent links, but that turns an O(1) test into an O(d) test inside the inner loop.
class Node:
    __slots__ = ('state', 'parent', 'action', 'path_cost', 'depth')

    def __init__(self, state, parent=None, action=None, step_cost=0):
        self.state = state
        self.parent = parent
        self.action = action
        self.path_cost = (parent.path_cost + step_cost) if parent else 0
        self.depth = (parent.depth + 1) if parent else 0

    def child(self, action, next_state, step_cost=1):
        return Node(next_state, self, action, step_cost)

    def __repr__(self):
        return f"<Node {self.state} g={self.path_cost} d={self.depth}>"

State versus node is the distinction that trips people up most often, and it matters for correctness, not just vocabulary. A state is a configuration of the world. A node is a point in the search tree — a particular path that arrives at that state. Many distinct nodes can share the same state. In the Romania road map, the state Bucharest can be reached via Arad→Sibiu→Fagaras→Bucharest (450 km) and via Arad→Sibiu→Rimnicu→Pitesti→Bucharest (418 km). Those are two different nodes with the same state and different path_cost values. The explored set stores states; the frontier stores nodes. Mixing these up produces solvers that either refuse to find obvious solutions or report costs that do not match their own action sequences.

Because of this distinction, equality and hashing on Node objects are dangerous. Two nodes with the same state are not interchangeable — one may be far cheaper than the other — so it is safest to leave Node with default identity-based equality and to always hash the state attribute rather than the node itself.

The parent pointer is the piece of engineering that makes all of this affordable. The naive alternative is to store the whole path in every frontier entry. If the frontier holds bd entries and each path is length d, that is O(d·bd) memory and a full list copy on every expansion. Parent pointers reduce each node to O(1) extra storage while still permitting exact path reconstruction, because sibling nodes share their ancestor chain instead of duplicating it. The memory saved is typically an order of magnitude on non-trivial problems.

Finally, treat nodes as immutable once created. It is tempting, when uniform-cost search discovers a cheaper route to an already-known state, to simply reach into the existing node and overwrite path_cost, parent, and action. The trouble is that other nodes may already point at that node as their parent, and that a heap's internal ordering depends on keys that you have just silently changed. The result is a heap that violates its invariant and reconstructed paths that are inconsistent with reported costs — bugs that appear only on particular graphs and are miserable to track down. Create a fresh node instead; the old one becomes garbage and the heap stays sound. The __slots__ declaration above is a cheap way to keep millions of such short-lived nodes compact.

Frontier Structures: Queue, Stack, and Priority Queue

The frontier is the algorithm's agenda. Its discipline — which node is removed next — is the search strategy.

  • BFS uses a FIFO queue. Nodes leave the frontier in exactly the order they were discovered, so all nodes at depth d are expanded before any node at depth d+1. This shallowest-first ordering is what makes BFS complete and, when every step has the same cost, optimal in number of steps.
  • DFS uses a LIFO stack. The most recently generated node is expanded next, so the search plunges down one branch to its maximum depth before backtracking. The frontier then holds only the siblings along the current path — O(bm) nodes instead of O(bd) — which is DFS's single great virtue.
  • UCS uses a min-priority queue keyed on g(n). The cheapest frontier node is popped each iteration, so the search expands states in non-decreasing order of true path cost. This generalises BFS: when all step costs are equal, cost order and depth order coincide.

The practical implementations in Python:

from collections import deque
import heapq

# FIFO queue for BFS
frontier = deque([root])
frontier.append(child)       # enqueue, O(1)
node = frontier.popleft()    # dequeue, O(1)

# LIFO stack for DFS
frontier = [root]
frontier.append(child)       # push, O(1)
node = frontier.pop()        # pop,  O(1)

# Min-priority queue for UCS
frontier = []
heapq.heappush(frontier, (node.path_cost, counter, node))   # O(log n)
cost, _, node = heapq.heappop(frontier)                     # O(log n)

A classic performance trap deserves its own warning. A Python list looks like it can serve as a queue: append() to enqueue, pop(0) to dequeue. But pop(0) removes from the front of a contiguous array and must shift every remaining element left, costing O(n) where n is the current frontier size. In BFS the frontier routinely holds tens or hundreds of thousands of nodes, so an algorithm that should be linear in nodes generated becomes quadratic. Nothing crashes and no error is raised — the solver simply appears to hang on inputs it should handle in seconds. collections.deque is a doubly-linked block structure with genuine O(1) operations at both ends; use it. (A list is perfectly fine as a DFS stack, because append/pop at the end are amortised O(1).)

Recursive DFS deserves a note. Instead of an explicit stack you let the language's call stack hold the frontier implicitly:

def dfs_limited(node, goal_test, successors, limit, explored):
    if goal_test(node.state):
        return node
    if node.depth == limit:
        return 'cutoff'
    explored.add(node.state)
    cutoff_occurred = False
    for action, next_state, cost in successors(node.state):
        if next_state in explored:
            continue
        result = dfs_limited(node.child(action, next_state, cost),
                             goal_test, successors, limit, explored)
        if result == 'cutoff':
            cutoff_occurred = True
        elif result is not None:
            return result
    return 'cutoff' if cutoff_occurred else None

The code is shorter and the backtracking is free, which is why depth-limited and iterative-deepening search are usually written recursively. The cost is loss of control and a hard ceiling: CPython's default recursion limit is around 1000 frames, so a search that needs to go 5000 moves deep raises RecursionError rather than returning a result. Raising the limit with sys.setrecursionlimit risks a genuine C-level stack overflow and a segfault. For deep or unbounded state spaces, prefer the explicit-stack version.

One more ordering subtlety: an explicit-stack DFS pops successors in the reverse order you pushed them. If you want the search to try successors in the order successors() yields them, push them reversed (for action, s, c in reversed(list(successors(state)))). This does not affect correctness, but it makes hand-traces in a tutorial match what the code actually does.

Explored Sets and Frontier Membership Tests

Graph search differs from tree search in exactly one respect: it remembers which states it has already expanded and refuses to expand them again. That memory is the explored set (also called the closed list).

It must be a hash set — Python's set, Java's HashSet, C++'s unordered_set — so that state in explored costs average O(1). Using a list instead makes each membership test O(n) in the number of explored states, and since you perform that test for every generated child, the whole search again degrades to quadratic. On the 8-puzzle, where a depth-14 BFS can expand tens of thousands of states, the difference between a set and a list is the difference between a fraction of a second and several minutes.

The standard child-filtering test checks both the explored set and the frontier:

for action, next_state, step_cost in successors(node.state):
    if next_state not in explored and next_state not in frontier_states:
        child = node.child(action, next_state, step_cost)
        frontier.append(child)
        frontier_states.add(next_state)

Note the second structure, frontier_states. The frontier itself (a deque or a heap) cannot be membership-tested in O(1), so you maintain a parallel hash set — or, for UCS, a dictionary mapping state → best known frontier cost — that mirrors the frontier's contents. Every push adds to the mirror; every pop removes from it. Keeping the mirror synchronised with the real frontier is a common source of bugs, so it is worth encapsulating both inside a small Frontier class rather than scattering the updates through the main loop.

class PriorityFrontier:
    def __init__(self):
        self.heap = []
        self.best = {}        # state -> best known g on the frontier
        self.counter = 0

    def push(self, node):
        if node.state in self.best and self.best[node.state] <= node.path_cost:
            return False      # we already have an equal-or-cheaper route
        self.best[node.state] = node.path_cost
        heapq.heappush(self.heap, (node.path_cost, self.counter, node))
        self.counter += 1
        return True

    def pop(self):
        while self.heap:
            cost, _, node = heapq.heappop(self.heap)
            if self.best.get(node.state) == cost:   # not a stale duplicate
                del self.best[node.state]
                return node
        return None

    def __len__(self):
        return len(self.best)

Hashability is a practical constraint on how you represent states. Python can only hash immutable objects. A board represented as a list [1,2,3,4,5,6,7,8,0] or a 2-D list of lists raises TypeError: unhashable type: 'list' the instant you try to put it in a set. The fixes are straightforward:

  • Use a tuple: (1,2,3,4,5,6,7,8,0) — immutable, hashable, and comparison/copying are fast.
  • Use a frozenset when the state is an unordered collection.
  • Use a canonical string: "123456780" — compact and hashable, though you pay to parse it back.
  • If you must work with mutable structures internally, convert to a canonical hashable key only at the moment of set insertion or lookup: tuple(map(tuple, grid)).

The word canonical matters. Two representations that mean the same state must hash to the same key. If you store a set of visited coordinates as a tuple, ((0,0),(1,1)) and ((1,1),(0,0)) describe the same state but are different keys, and the explored set will fail to catch the duplicate. Sort before converting, or use a frozenset.

Omitting the explored set converts graph search into tree search. On a tree-shaped state space that is harmless. On any graph containing cycles it is fatal: in the Romania map, BFS without an explored set will generate Arad→Sibiu→Arad→Sibiu→… forever, the frontier growing without bound until memory is exhausted. Even on acyclic but non-tree graphs (a grid, where many paths lead to the same cell) the absence of duplicate detection causes exponential blow-up in redundant work. The explored set is not an optimisation; for cyclic graphs it is the difference between termination and non-termination.

The one algorithm where a full explored set is not standard is iterative deepening, whose whole point is to use O(d) memory. There you typically check only the current path for cycles (walk the parent links, or keep a set of states on the path and remove them as you backtrack), accepting redundant work across branches in exchange for linear memory.

Decrease-Key and Duplicate Handling in UCS

Uniform-cost search faces a situation BFS never does: a state already sitting on the frontier can be rediscovered along a cheaper path. BFS can simply discard any rediscovery, because the first path to a state is always a shortest-in-steps path. UCS cannot, because the first path discovered to a state is not necessarily the cheapest.

Consider a tiny graph: S→A costs 10, S→B costs 1, B→A costs 2. UCS pushes A with g=10 and B with g=1. It pops B (cheapest), expands it, and discovers A again with g=3. The frontier entry for A claiming g=10 is now obsolete and must not be allowed to determine A's recorded parent or cost.

There are two standard remedies.

  • Decrease-key (the textbook version). On discovering a cheaper route to a state already on the frontier, replace that frontier entry: update its key to the new, lower g and repair the heap's ordering. This keeps the frontier free of duplicates and bounds its size by the number of distinct states. Its drawback is that a plain binary heap offers no efficient way to find an arbitrary element, so you need an index map from state to heap position, maintained through every sift-up and sift-down. Python's heapq provides no such facility, so true decrease-key requires writing your own heap or using a library.
  • Lazy deletion (the practical version). Never modify existing entries. Simply heappush a second entry for the state with the lower cost, so the heap temporarily holds both. Because the heap pops in cost order, the cheaper entry is guaranteed to come out first. When you pop an entry whose state is already in the explored set — or whose recorded cost no longer matches the best known cost — you discard it and pop again. The heap may grow larger than the number of distinct states, but every operation stays a clean O(log n) and the code is a dozen lines.

Lazy deletion is what the PriorityFrontier.pop method above implements, and it is the right default for coursework and most production code. The two approaches produce identical solutions; they differ only in memory and constant factors.

Two implementation details make or break a heapq-based UCS.

First, push tuples, not bare nodes, and include a tiebreak counter: (cost, counter, node). Python compares tuples lexicographically. When two entries have equal cost, it moves on to the second element. If the second element were the Node object, Python would try to evaluate node_a < node_b and raise TypeError: '<' not supported between instances of 'Node' and 'Node'. Inserting a monotonically increasing integer counter as the second element guarantees that comparison never reaches the node, because no two counters are ever equal. (Using the state itself as a tiebreaker works only if states are mutually comparable — tuples of ints are, but mixed types are not — so the counter is the robust choice.)

Second, that counter does more than prevent crashes: it makes the algorithm deterministic. With a counter, ties in cost are broken by insertion order (FIFO among equal-cost nodes), so the same input always produces the same expansion order and the same solution path across runs and machines. Without it — or with a random tiebreak — your solver may return a different, equally optimal path each time, which makes unit tests flaky and hand-traces impossible to verify. If you prefer LIFO tie-breaking (which tends to dive toward goals faster), push -counter instead.

Third and most important: in UCS the goal test is applied when a node is popped, not when it is generated. This is the single most common correctness bug in student implementations. Suppose the goal G is reachable from the start directly at cost 100, and also via a node X at cost 5 with X→G costing 10. If you test children as you generate them, you will see G at cost 100 while expanding the start node and return immediately, reporting a cost of 100 when a 15-cost path exists. Testing at pop time guarantees that when G finally comes off the heap, no cheaper frontier node remains, so g(G) is the true optimal cost. (BFS with unit costs is the exception: there you may safely goal-test on generation, which saves a whole final layer of expansion, because depth order and cost order agree. Make the difference explicit in your code comments so nobody "optimises" UCS into incorrectness.)

def uniform_cost_search(problem):
    root = Node(problem.initial)
    if problem.goal_test(root.state):          # handle trivial case
        return solution(root)
    frontier = PriorityFrontier()
    frontier.push(root)
    explored = set()
    generated = expanded = 0

    while True:
        node = frontier.pop()
        if node is None:
            return None                        # frontier exhausted: failure
        if problem.goal_test(node.state):      # GOAL TEST ON POP
            return solution(node, generated, expanded)
        explored.add(node.state)
        expanded += 1
        for action, next_state, step_cost in problem.successors(node.state):
            if next_state in explored:
                continue
            generated += 1
            frontier.push(node.child(action, next_state, step_cost))

Reconstructing and Returning the Solution Path

When the goal node is found, the answer is not the node itself but the sequence of actions that produced it. Parent pointers make this a short walk back up the tree.

def solution(node, generated=0, expanded=0):
    actions, states = [], []
    current = node
    while current.parent is not None:
        actions.append(current.action)
        states.append(current.state)
        current = current.parent
    states.append(current.state)               # the initial state
    actions.reverse()
    states.reverse()
    return {
        'actions': actions,
        'states': states,
        'cost': node.path_cost,                # read off, never recomputed
        'depth': node.depth,
        'nodes_generated': generated,
        'nodes_expanded': expanded,
    }

Four points about that function are worth dwelling on.

  • Stop at parent is None, not at the start state. The loop condition tests the parent pointer because the root is precisely the node without one. Testing current.state != problem.initial instead looks equivalent but breaks the moment the search legitimately revisits the initial state along some path, and it fails outright if several nodes share that state.
  • Reverse the list. Walking parent links yields actions in goal-to-start order. One list.reverse() (or building with appendleft on a deque) puts them in executable start-to-goal order. Forgetting this produces a sequence that is exactly backwards — a bug that passes a "length is correct" test and fails a "replay it" test, which is why the replay test matters.
  • Read the cost from node.path_cost. The goal node's g value already is the total path cost, accumulated incrementally and correctly as the path was built. Re-summing step costs over the reconstructed path duplicates logic, invites off-by-one errors at the endpoints, and silently diverges from the value the priority queue actually used to order expansions. If the two ever disagree, you have a bug — which is why re-summing is a useful assertion in tests but a bad idea in the returned result.
  • Return a clear failure sentinel. When the frontier empties without a goal, the problem has no solution and the function must say so unambiguously: None, the string 'failure', or a dedicated Failure object. Do not return an empty action list, because an empty list is also the correct answer when the initial state is the goal. Depth-limited search needs a third outcome as well — 'cutoff', meaning "no solution within this limit, but one may exist deeper" — which is exactly the signal iterative deepening uses to decide whether to try the next limit.

Returning instrumentation alongside the solution turns the solver into an experimental instrument. Two counters suffice:

  • nodes generated — incremented once per child created, i.e. the total search effort including nodes that sat on the frontier and were never expanded;
  • nodes expanded — incremented once per node removed from the frontier and whose successors were produced.

With these you can measure, rather than merely assert, that BFS generates roughly b times as many nodes as it expands, that iterative deepening expands only a modest constant factor more nodes than BFS while using a fraction of the memory, and that UCS expands more nodes than BFS on a unit-cost graph because it must exhaust an entire cost contour before stopping. Add a peak-frontier-size counter (max_frontier = max(max_frontier, len(frontier))) and you can plot memory growth as well. A tidy comparison table from one 8-puzzle instance might look like this:

Coding Exercise: 8-Puzzle Solver

The 8-puzzle is a 3×3 grid holding tiles 1–8 and one blank. A move slides a tile adjacent to the blank into it; equivalently, the blank moves up, down, left, or right. There are 9! = 362 880 arrangements, split into two unreachable halves, so 181 440 states are reachable from any given start. That is small enough to search exhaustively and large enough to make bad data structures hurt.

Representation. Store the board as a flat 9-tuple in row-major order, with 0 for the blank. The goal is (1,2,3,4,5,6,7,8,0). A tuple is immutable and therefore hashable, which is exactly what the explored set needs; it is also compact and compares quickly. The blank's index i gives its row i // 3 and column i % 3.

Successors with edge constraints. The whole correctness of the model rests on refusing moves that would push the blank off the grid. Because the board is flat, the naive "add ±1 or ±3 to the index" rule wraps around rows: from index 2 (row 0, column 2), adding 1 gives index 3, which is row 1 column 0 — a move that teleports the blank across the board. Guard with the row/column test, not with a bare bounds check on the index.

GOAL = (1, 2, 3, 4, 5, 6, 7, 8, 0)
MOVES = {'Up': -3, 'Down': 3, 'Left': -1, 'Right': 1}

def successors(state):
    """Yield (action, next_state, step_cost) triples."""
    i = state.index(0)
    row, col = divmod(i, 3)
    for action, delta in MOVES.items():
        if action == 'Up'    and row == 0: continue
        if action == 'Down'  and row == 2: continue
        if action == 'Left'  and col == 0: continue
        if action == 'Right' and col == 2: continue
        j = i + delta
        board = list(state)
        board[i], board[j] = board[j], board[i]
        yield action, tuple(board), 1

Written as a generator, successors produces children lazily, which matters for DFS: if the first child leads straight to a goal, the remaining boards are never even constructed. Note also that each call builds a fresh list and converts it back to a tuple, so no caller can mutate a state another node is relying on.

Running BFS and watching the explosion. With a branching factor of about 2.67 (the blank has 2 moves from a corner, 3 from an edge, 4 from the centre), BFS at depth d touches roughly 2.67d nodes before duplicate elimination, and the number of distinct states at depth d grows nearly as fast until the 181 440-state space starts to saturate. Why DFS needs a depth limit. Plain DFS on the 8-puzzle is a disaster. The state space is a graph, not a tree, and its diameter is 31 moves — yet a DFS that keeps an explored set of every state it has ever touched will happily wander through tens of thousands of states and return a "solution" 40 000 moves long, while a DFS that only checks the current path for cycles may never terminate in practice. Imposing a limit converts it into depth-limited search:

for limit in range(0, 31):                 # iterative deepening
    result = dfs_limited(Node(start), lambda s: s == GOAL,
                         successors, limit, set())
    if result != 'cutoff':
        break

Run depth-limited DFS at limit 10 on your depth-14 instance and it returns 'cutoff' — correctly reporting that no solution exists within 10 moves. Raise the limit to 14 and it finds one. Wrapping that loop is iterative deepening, which recovers BFS's optimality (under unit costs) at DFS's memory cost: a frontier of at most bl nodes, perhaps 40 entries, versus BFS's 20 000.

Verification by replay. The indispensable test is not that the solver returned something of plausible length, but that its action sequence actually works. Replay it from the start state and assert the result:

def replay(start, actions):
    state = start
    for action in actions:
        moves = {a: s for a, s, _ in successors(state)}
        assert action in moves, f"illegal action {action} in state {state}"
        state = moves[action]
    return state

sol = breadth_first_search(start)
assert replay(start, sol['actions']) == GOAL
assert len(sol['actions']) == sol['cost'] == sol['depth']   # unit costs

This single test catches the majority of implementation bugs at once: reversed action lists, actions stored on the wrong node, parent pointers overwritten during re-expansion, off-by-one depth accounting, and costs that disagree with the path. Make it the first test you write.

Stress-testing termination with cycles and zero-cost edges. The Romania graph is already full of cycles (Arad–Sibiu–Oradea–Zerind–Arad), so an explored-set-free version loops forever; verify that by disabling the set and watching the frontier grow without bound. Then add two deliberate hazards:

  • A zero-cost edge, say 'Sibiu': {'Fagaras': 0} in both directions. With cost 0 the pair Sibiu/Fagaras can be traversed back and forth without g ever increasing, so a cost-ordered frontier has no incentive to move on. The explored set is what breaks the loop: once Sibiu is expanded, the Fagaras→Sibiu child is filtered out and the search proceeds. This is also the concrete reason UCS's completeness guarantee requires every step cost to be ≥ ε > 0 in infinite state spaces — with zero-cost edges and infinitely many states, the search can expand forever without ever increasing the cost bound.

Finally, run the same two solvers on an unreachable target — add an isolated city 'Atlantis': {} and search for it — and confirm both return the failure sentinel rather than crashing or looping. A solver that handles success, failure, cutoff, cycles, and zero-cost edges correctly is one you can trust to generate the empirical comparisons the rest of the module depends on.

Search algorithms are often described on paper as abstract procedures, but turning BFS, DFS, and uniform-cost search into working code forces you to make concrete decisions about data structures. The central idea is that the frontier is not just a bag of states: it is a specific container whose behavior defines the strategy. A FIFO queue gives you breadth-first search, a LIFO stack gives you depth-first search, and a priority queue ordered by path cost gives you uniform-cost search. Swap the container and you swap the algorithm.

Just as important is the search node, which wraps a state together with a pointer to its parent, the action that produced it, and the accumulated path cost. Those extra fields are what let you reconstruct the solution path by walking parent pointers backward from the goal. Alongside the frontier you also need an explored set and a membership test for the frontier itself, usually backed by a hash set keyed on a canonical representation of the state, so that repeated states do not cause redundant expansion or infinite loops. Uniform-cost search adds one more wrinkle: when a cheaper path to an already-queued state is discovered, you must either decrease its key or push a duplicate entry and discard stale ones when they are popped.

Comparative Analysis and Strategy Selection

Comparative Analysis and Strategy Selection

▶

Once breadth-first search, depth-first search, uniform-cost search and their depth-limited variants have been implemented, the practical question is no longer "how does each one work?" but "which one should I run, and what will it cost me?" Answering that requires a common vocabulary for measuring algorithms, a set of symbols that let very different search behaviours be written down in the same notation, and a feel for how the asymptotic formulas translate into real node counts and real memory consumption. This topic assembles that comparative picture: the four standard evaluation criteria, the side-by-side complexity table they produce, the reason memory rather than time is usually the binding constraint, concrete measurements on benchmark problems, a decision procedure for selecting a strategy, and finally an honest account of what every uninformed method has in common — blindness.

The four evaluation criteria

Every search strategy in the uninformed family is judged on the same four questions. They are deliberately coarse — they ignore constant factors, implementation language and cache behaviour — but they capture the differences that matter when the state space grows large.

  • Completeness. Is the algorithm guaranteed to find a solution whenever at least one exists, and to report failure in finite time when none does? Completeness is a guarantee, not a tendency. An algorithm that finds the goal "almost always" is not complete. The usual ways to lose completeness are infinite branches (a state space with unbounded depth, such as a robot that can keep moving east forever), infinite branching factors, and cycles that trap the search in a loop.
  • Optimality. If a solution is returned, is it guaranteed to be a cheapest solution under the problem's path-cost function? Note the careful wording: in a unit-cost problem "cheapest" collapses into "shallowest", which is why BFS appears optimal in grid and puzzle domains but loses that property the moment edges acquire different weights. An algorithm can be complete without being optimal (DFS is the standard example) and can in principle be optimal without being complete (an algorithm that only sometimes terminates, but returns the best path when it does).
  • Time complexity. How many nodes are generated (or, in some textbook conventions, expanded) before the algorithm halts? In search analysis we count nodes rather than seconds because node generation is the dominant repeated operation and because node counts are machine-independent. The two conventions differ by a factor of roughly b, which is irrelevant asymptotically but worth stating explicitly when you report empirical numbers.
  • Space complexity. What is the maximum number of nodes held in memory simultaneously — frontier plus explored set plus whatever bookkeeping the implementation needs? This is a peak measurement, not a total: a node that is generated, expanded and discarded still contributes to time but may not contribute to the peak space.

To compare algorithms on equal footing, all four criteria are expressed in terms of a small set of parameters of the problem, not of the algorithm:

SymbolMeaningTypical interpretation
bBranching factor — maximum (or average) number of successors of any node8-puzzle ≈ 2.67 effective; chess ≈ 35; Rubik's cube ≈ 13.3 after pruning inverse moves

Two relations between these parameters are worth internalising. First, d ≤ m always, and in hard problems m can be enormously larger than d — that gap is precisely the risk DFS takes. Second, ⌊C*/ε⌋ ≥ d whenever all costs are at least ε, because the optimal path of cost C* can contain at most C*/ε edges. This is why UCS's exponent is never smaller than BFS's, and can be much larger when the cheapest action is tiny relative to the solution cost.

Several entries deserve unpacking.

  • Why BFS is optimal only for equal step costs. BFS returns the shallowest goal. Shallowest equals cheapest exactly when every edge contributes the same amount to the path cost. Give one edge a cost of 100 and a four-edge path may beat a two-edge path, at which point BFS's answer is merely "fewest actions", not "least cost".
  • Why UCS needs ε > 0. If arbitrarily small positive costs are allowed, an infinite branch whose edge costs are 1/2, 1/4, 1/8, … has finite total cost, and UCS can march down it forever without ever reaching a cost at which the goal would be popped. A positive lower bound ε forbids that pathology, because then any infinite path has infinite cost.
  • Why UCS's exponent is 1+⌊C*/ε⌋ rather than d. UCS must expand every node whose path cost is strictly less than C* before it can pop the goal. The number of such nodes is governed by how many cost steps of size ε fit inside C*, not by how many edges fit inside d. If ε is small — say, road segments as short as 10 m on a route whose optimal length is 50 km — that exponent dwarfs d.
  • Why DFS is never optimal. DFS returns the first goal it stumbles on, which depends entirely on the order in which successors happen to be generated. Nothing in the algorithm compares that goal against any alternative.
  • Why DFS space is O(bm), not O(bm). At any instant a tree-search DFS holds only the nodes on the current root-to-leaf path (at most m of them) together with the as-yet-unexpanded siblings at each of those levels (at most b−1 each). That is a linear quantity. A recursive implementation makes this especially visible: the stack frames are the path. Note the caveat in the table — the moment you add a full explored set to make DFS complete on a graph, the space advantage is sacrificed, because the explored set can grow to the size of the reachable state space. A common compromise is to check only for repeated states along the current path, which costs O(m) extra and prevents infinite loops on cycles without storing the whole graph.

UCS as a generalisation of BFS. If every edge has identical cost c, then path cost is simply c × depth, so ordering the frontier by g(n) is the same as ordering it by depth: UCS expands nodes in exactly the layered order BFS does, and ⌊C*/ε⌋ = d, so the complexity formula collapses to O(bd+1). The only residual differences are implementation details — UCS pays a logarithmic factor for heap operations, and it performs its goal test on popping rather than on generating, which is what gives it its optimality guarantee in the weighted case and costs it one extra layer of expansion in the unit-cost case. It is entirely correct to describe BFS as the special case of UCS for unit costs, and to describe UCS as "BFS with a priority queue".

The decisive BFS-versus-DFS difference. Both have exponential worst-case time, and in practice a time-bound search can simply be stopped. The gap that cannot be papered over is space: O(bd) versus O(bm). A search with b = 10 at depth 12 holds on the order of 1012 nodes in a BFS frontier; the same search in DFS holds roughly 10 × 12 = 120 nodes on its stack. That is the difference between an impossible program and a trivial one.

Memory as the binding constraint

It is tempting to read O(bd) for time and O(bd) for space as "equally bad". They are not, because computers consume time and memory at wildly different rates. That asymmetry is the single most important practical fact about uninformed search, and it is why memory-bounded variants exist at all.

DFS sits at the opposite extreme. Its stack holds the current path plus the untried siblings hanging off it, so at b = 10, m = 20 the peak is about 200 nodes — twenty kilobytes. DFS can be run for days without memory pressure. What it cannot do is guarantee a good answer: it may plunge down a 10 000-step branch that contains no goal, or find a wildly suboptimal one.

Depth-limited search is the first repair. Impose a cutoff ℓ and refuse to expand beyond it. Space becomes O(bℓ) and the algorithm always terminates, but you now need to know ℓ: set it below d and the search returns cutoff having found nothing; set it far above d and you reintroduce wasted effort. Sometimes the domain supplies the bound — on a map of 20 cities any simple route has at most 19 edges, so ℓ = 19 is sound.

Iterative-deepening DFS (IDDFS) removes the guesswork by running depth-limited search for ℓ = 0, 1, 2, … until a goal is found:

function IDDFS(problem):
    for limit = 0 to infinity:
        result = DEPTH-LIMITED-SEARCH(problem, limit)
        if result != cutoff:
            return result

The result is remarkable: IDDFS is complete (for finite b), optimal for unit step costs, runs in O(bd) time — the same order as BFS — and uses only O(bd) memory. The obvious objection is that it regenerates the shallow levels over and over. The objection is answered by arithmetic. In a tree with branching factor b, level k contains bk nodes, and because the levels grow geometrically the deepest level contains more nodes than all shallower levels combined (for b ≥ 2). Counting the generations:

IDDFS total generations = (d+1)·b^0 + d·b^1 + (d-1)·b^2 + ... + 1·b^d
BFS   total generations =       b^0 +   b^1 +         b^2 + ... +   b^d

b = 10, d = 5:  BFS = 111,111    IDDFS = 123,456    (ratio 1.11)

For b = 10 the repeated work costs about 11% extra; asymptotically the overhead factor tends to b/(b−1), which is small for any realistic branching factor and only becomes significant for near-unary trees. Paying 11% more time to cut memory from 10 GB to 20 KB is one of the best trades in algorithm design, which is why IDDFS is the default uninformed strategy for large unit-cost spaces. (The cost-sensitive analogue, iterative lengthening — repeating a cost-limited search with increasing cost bounds — exists but is rarely used, because cost thresholds do not increase in convenient integer steps and the overhead is far less predictable.)

BFS expands tens of thousands of nodes to find a solution only a dozen moves deep, because exhaustively sweeping every state within 12 moves is simply a large set. DFS, by contrast, dives: it will happily shuffle tiles for hundreds or thousands of moves, eventually tripping over a goal state, and the "solution" it returns is a meandering sequence that no human would accept. If you run DFS on the 8-puzzle without any repeated-state check at all, it typically never terminates, because sliding a tile left and then right returns you to a state you already visited and the search cycles.

Now switch domains to a weighted road map, where states are towns and edge costs are driving distances. Consider a small network:

A --2-- B --2-- C --2-- D --2-- E --2-- G      (five hops, total cost 10)
A ------------- 12 ------------------- G      (one hop,  total cost 12)

BFS, which counts segments, pops the goal via the single 12-unit edge after exploring depth 1 and reports "A → G, 1 road segment". UCS, which counts distance, expands outward in order of increasing g: A(0), B(2), C(4), D(6), E(8), G(10) — and only then would it ever consider the 12-unit direct edge, which it discards because G has already been popped at cost 10. The returned path is the five-hop route. This is the everyday experience of a satellite navigation system: the route with the fewest turns is frequently not the fastest, and a navigator that minimised segment count would send you down a long rural road rather than three short motorway links.

The outward sweep of UCS has a useful geometric reading: it expands nodes in order of increasing distance from the start, so at any moment the explored set is everything inside a cost contour of radius g, and the frontier is the contour itself. The contours spread like ripples on a pond, uniformly in all directions, until one of them touches the goal. That image makes two things obvious at once: UCS is guaranteed to find the cheapest route (the ripple reaches the goal at exactly radius C*), and it is wasteful (it also reaches every irrelevant town at distance less than C*, including those in precisely the wrong direction). Instrumenting the solver to print len(frontier) at each iteration confirms the theory directly: BFS and UCS frontier sizes climb roughly geometrically and then collapse when the goal is found, while DFS frontier size oscillates within a narrow band bounded by b·m. Recording peak frontier size is the cheapest possible experiment that distinguishes exponential from linear memory, and it is worth adding to any implementation.

Choosing a strategy for a given problem

Strategy selection is a short decision procedure driven by four properties of the problem: edge costs, expected solution depth, memory budget, and state-space structure.

  • All actions cost the same and the goal is expected to be shallow → BFS. Unit costs make BFS optimal, shallowness keeps bd affordable, and the FIFO implementation is the simplest correct thing you can write. Typical cases: word-ladder puzzles, shortest path in an unweighted grid, social-network degrees of separation, state spaces whose diameter is small.
  • Edge costs vary and you genuinely need the cheapest solution → UCS. Nothing simpler will do: BFS answers a different question, and DFS answers no question at all. Typical cases: routing with distances or tolls, scheduling with task durations, any problem where "cost" is a real resource. Before committing, check the ratio C*/ε; if the smallest edge cost is minuscule, the search may expand astronomically many near-zero-cost nodes, and rescaling or quantising costs can help.
  • Memory is tight, solutions are plentiful and deep, or the space is a finite tree → DFS. DFS shines when you need a solution rather than the best one and when goals are abundant at depth, so the first dive is likely to succeed. Constraint-satisfaction backtracking, topological ordering, maze generation, exhaustive enumeration of permutations, and connected-component labelling are all DFS applications. A finite tree is the ideal case because there are no cycles to guard against and m is bounded.
  • You need BFS guarantees but cannot afford BFS memory → iterative deepening. This is the default for large unit-cost spaces such as the 15-puzzle or Rubik's cube: complete, optimal, linear memory, and only a constant-factor time penalty. If you additionally have a reliable upper bound on depth, a single depth-limited search with that bound avoids even the repeated work.
  • Always add cycle detection in graph spaces. Any state space in which two different action sequences can reach the same state — which is to say almost every realistic one — needs duplicate handling. Without it DFS can loop forever between two mutually reachable states, and BFS, while still correct, re-expands the same states along many redundant paths and inflates its node count from O(bd) towards the far larger number of distinct paths. The standard mechanism is an explored set (a hash set of visited states) plus a membership test against the frontier; for DFS under a strict memory budget, checking only the states on the current path is a lighter-weight compromise that still eliminates infinite loops.

Two further selection heuristics are worth keeping in mind. First, if the state space is known in advance and small enough to enumerate, classical shortest-path algorithms (Dijkstra, which is UCS over an explicit graph, or Bellman–Ford for negative edges) may be preferable to on-the-fly search, because they can exploit the full adjacency structure. Second, if forward branching is large but backward branching is small — as in puzzles with a single known goal state — bidirectional search running BFS from both ends meets in the middle at cost roughly O(bd/2), a dramatic saving, at the price of needing an invertible transition model and a frontier-intersection test.

Limitations shared by all uninformed methods

Having compared the strategies, it is important to see what they have in common, because that shared weakness motivates everything that follows in the study of search.

They are blind. Every algorithm in this family chooses the next node to expand using a fixed structural rule — oldest first, newest first, cheapest-so-far first — and none of them has any notion of whether a node is close to the goal. UCS's rule, "expand the node with the smallest g(n)", looks backwards at the cost already incurred; it says nothing about the cost still to come. A UCS exploring a road map from Arad towards Bucharest will cheerfully expand towns to the west, away from the destination, simply because they are nearby. The only information these algorithms use is the problem definition itself: initial state, actions, transition model, goal test, and path cost. The goal test is a yes/no oracle, not a measure of proximity, so there is no signal to steer by.

They are exponential. The growth in bd is not a defect of any one implementation but a property of the search tree. Doubling the solution depth squares the work. No reordering of a blind frontier can change that: whichever order you choose, if you must guarantee optimality you must examine essentially every node cheaper than the optimum, and there are exponentially many of them. A faster machine buys you an additive increase in reachable depth — roughly logb(speedup) extra levels — not a multiplicative one. A thousand-fold hardware speedup at b = 10 buys three extra levels of depth. This is why "wait for better hardware" has never been a viable answer to combinatorial explosion, and why the 15-puzzle (about 1013 states) was already out of reach for pure BFS decades ago and remains so.

Where the real gains come from. Within the uninformed framework, the levers that genuinely help are not algorithmic swaps but changes to the problem and its representation:

  • Better problem formulation. Choosing a coarser or more abstract state representation can shrink the space by orders of magnitude. Representing the 8-queens problem as "place one queen per column" rather than "place any queen on any square" reduces the space from about 3 × 1014 sequences to 2 057 nodes. The algorithm did not change; the problem did.
  • Smaller branching factors. Pruning obviously useless actions — never undoing the previous move in a sliding puzzle, never rotating the same cube face twice in a row, enforcing a canonical ordering on commutative actions — reduces b, and because b is the base of the exponent, even a modest reduction compounds enormously over depth. Dropping b from 4 to 2.67 in the 8-puzzle shrinks the depth-20 tree by a factor of over a thousand.
  • Duplicate elimination. Replacing tree search with graph search converts the cost from "number of distinct paths" to "number of distinct states", which in a densely connected space is a difference between astronomically large and merely large. In a 2-D grid, the number of paths of length d grows exponentially while the number of reachable cells grows only quadratically.
  • Memory-bounded variants. Iterative deepening and bidirectional search squeeze real improvements out of the same blind framework by trading recomputation for space, or by splitting the exponent in half.

The next lever. After formulation, pruning and duplicate elimination have been applied, the remaining source of leverage is domain knowledge: information about the problem that is not contained in the bare five-part specification. Encoded as a heuristic function h(n) — an estimate of the cost from n to the nearest goal — this knowledge lets the frontier be ordered by where the search is going rather than only by where it has been. Straight-line distance for route finding, or the number of misplaced tiles for a sliding puzzle, are cheap to compute and dramatically reduce the number of nodes expanded; combining g(n) with h(n) yields A*, which retains UCS's optimality guarantee when the heuristic never overestimates. Everything established here — the four criteria, the parameters b, d, m, C*, ε, the frontier data structures, the explored set — carries over unchanged into that informed setting. Uninformed search is not a dead end; it is the chassis onto which heuristics are bolted.

The standard way to answer that is to evaluate each strategy on four criteria — completeness (does it find a solution if one exists?), optimality (is the solution it finds the cheapest?), time complexity (how many nodes does it expand?), and space complexity (how many nodes must it hold in memory at once?). Empirical node counts on benchmark problems make this concrete: a modest increase in depth multiplies BFS memory by a factor of b. Choosing a strategy therefore means matching problem structure to these trade-offs — uniform edge costs or varying ones, shallow or deep solutions, finite or unbounded depth, and how much memory you actually have.
