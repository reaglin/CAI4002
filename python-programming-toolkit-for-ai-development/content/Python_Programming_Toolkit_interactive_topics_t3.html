Core Python Constructs for Algorithm Implementation

▶

Artificial intelligence textbooks present algorithms as pseudocode: compact, mathematical descriptions such as function BREADTH-FIRST-SEARCH(problem) returns a solution, or failure. The gap between that pseudocode and working software is bridged by a surprisingly small set of Python constructs. If you choose those constructs deliberately, your implementation reads almost line-for-line like the book; if you choose them carelessly, you end up with a tangle of global variables and nested loops that is impossible to test or to compare against the published algorithm. This topic works through the core constructs — functions, classes, comprehensions, generators, recursion, exceptions, and type hints — with an emphasis on how each one maps onto the shapes that appear in AI pseudocode.

Functions as building blocks for algorithms. Pseudocode is written as a set of named procedures, and the cleanest translation is one Python function per procedure. A function that does exactly one thing is easier to name, easier to reason about, and — critically for assignment work — easier to test in isolation. Compare the two versions below. The first mixes search, path reconstruction, and reporting; the second separates them.

# Poor: one function doing three jobs, printing as a side effect
def search(problem):
    frontier = [problem.initial]
    explored = set()
    while frontier:
        state = frontier.pop(0)
        if problem.goal_test(state):
            print("Found goal:", state)   # reporting mixed into search
            return
        explored.add(state)
        for action in problem.actions(state):
            frontier.append(problem.result(state, action))

# Better: one responsibility each
def breadth_first_search(problem):
    """Return a goal Node, or None if no solution exists."""
    node = Node(problem.initial)
    if problem.goal_test(node.state):
        return node
    frontier = deque([node])
    explored = set()
    while frontier:
        node = frontier.popleft()
        explored.add(node.state)
        for child in expand(node, problem):
            if child.state not in explored and child not in frontier:
                if problem.goal_test(child.state):
                    return child
                frontier.append(child)
    return None

def solution_path(node):
    """Return the list of states from the root to this node."""
    path = []
    while node is not None:
        path.append(node.state)
        node = node.parent
    return list(reversed(path))

Notice the parameter and variable names: problem, node, frontier, explored. These are not arbitrary. They are the names used in the pseudocode, and using them means a reader (or marker) can place your code beside the textbook and verify correctness by inspection. Descriptive names also remove the need for most comments: frontier.popleft() already says "remove the shallowest node from the frontier".

Return values, not global mutation. A function that writes to a module-level variable is effectively communicating through a hidden channel. Two tests running in the same session can interfere with each other, and you cannot call the function twice with different problems. Prefer returning the result:

# Fragile: hidden state
best_path = None
def dfs(state):
    global best_path
    ...
    best_path = path          # caller must know to read this afterwards

# Robust: explicit result
def dfs(problem, state, path):
    ...
    return path               # caller receives the answer directly

The second form is referentially cleaner: given the same arguments it produces the same result and leaves nothing behind. That property is exactly what makes unit testing straightforward — assert dfs(p, p.initial, []) == expected needs no setup or teardown.

Default and keyword arguments for optional components. Many AI algorithms have optional parts: a depth limit, a cost function, a heuristic, a tie-breaking rule. Default arguments let you express the common case concisely while leaving the knob available.

def best_first_search(problem, f=None, limit=float("inf")):
    """Generic best-first search; f(node) gives the priority.
    With f = lambda n: n.path_cost this is uniform-cost search.
    """
    if f is None:
        f = lambda node: node.path_cost
    ...

# Calls read clearly because the optional parts are named:
best_first_search(problem)
best_first_search(problem, f=lambda n: n.path_cost + h(n))
best_first_search(problem, limit=12)

One important caution: never use a mutable object such as [] or {} as a default value. Defaults are evaluated once, when the function is defined, so the same list is shared across every call.

# Bug: the list persists between calls
def record(step, log=[]):
    log.append(step)
    return log

# Correct idiom
def record(step, log=None):
    if log is None:
        log = []
    log.append(step)
    return log

Functions as first-class objects. In Python a function is an ordinary value: it can be stored in a variable, placed in a list or dictionary, passed to another function, and returned from one. This is what makes a single generic search routine usable for uniform-cost search, greedy search and A* — you simply pass a different evaluation function.

def astar_search(problem, h):
    """A* = best-first search with f(n) = g(n) + h(n)."""
    return best_first_search(problem, f=lambda n: n.path_cost + h(n))

def manhattan(node):
    (r1, c1), (r2, c2) = node.state, GOAL
    return abs(r1 - r2) + abs(c1 - c2)

def straight_line(node):
    x1, y1 = COORDS[node.state]
    x2, y2 = COORDS[GOAL]
    return ((x1 - x2) ** 2 + (y1 - y2) ** 2) ** 0.5

# A dispatch table of heuristics, selected at run time
HEURISTICS = {"manhattan": manhattan, "sld": straight_line}
result = astar_search(problem, HEURISTICS[args.heuristic])

Classes for modelling problems, agents and nodes. Where a function captures a procedure, a class captures a thing with state. In search code the recurring things are the problem definition, the search node, and the agent. The standard pattern is an abstract base class that declares the interface every algorithm relies on, followed by one subclass per concrete problem.

class Problem:
    """Abstract formulation of a search problem."""

    def __init__(self, initial, goal=None):
        self.initial = initial
        self.goal = goal

    def actions(self, state):
        """Return an iterable of actions legal in `state`."""
        raise NotImplementedError

    def result(self, state, action):
        """Return the state reached by doing `action` in `state`."""
        raise NotImplementedError

    def goal_test(self, state):
        return state == self.goal

    def step_cost(self, state, action, next_state):
        return 1        # sensible default; override for weighted graphs


class RomaniaMap(Problem):
    def __init__(self, initial, goal, graph):
        super().__init__(initial, goal)
        self.graph = graph

    def actions(self, state):
        return list(self.graph[state])

    def result(self, state, action):
        return action          # the action *is* the neighbouring city

    def step_cost(self, state, action, next_state):
        return self.graph[state][next_state]

Because breadth_first_search only ever calls actions, result and goal_test, it works unchanged on an 8-puzzle, a maze, or a map of Romania. This is the practical payoff of programming to an interface: algorithms and problems vary independently.

Dunder methods: __repr__, __eq__ and __hash__. Search code stores states in sets and dictionaries, compares nodes, and prints them during debugging. Python's default behaviours are wrong for all three purposes unless you supply the special methods.

class Node:
    def __init__(self, state, parent=None, action=None, path_cost=0):
        self.state = state
        self.parent = parent
        self.action = action
        self.path_cost = path_cost
        self.depth = 0 if parent is None else parent.depth + 1

    def __repr__(self):
        return f"<Node {self.state} g={self.path_cost} d={self.depth}>"

    def __eq__(self, other):
        return isinstance(other, Node) and self.state == other.state

    def __hash__(self):
        return hash(self.state)

    def __lt__(self, other):
        # Needed so heapq can break ties between equal priorities
        return self.path_cost < other.path_cost

Three rules govern these methods. First, __repr__ should produce an unambiguous developer-facing string — without it you see <__main__.Node object at 0x7f1c...> and learn nothing. Second, if you define __eq__ you must define a consistent __hash__, because Python sets __hash__ to None on any class that overrides __eq__, making instances unhashable. Third, objects that compare equal must hash equal, and anything used as a dictionary key or set member must be immutable in the fields that feed the hash. That is why states are typically tuples or frozensets rather than lists:

# 8-puzzle state as an immutable tuple -> hashable, usable in `explored`
state = (1, 2, 3,
         4, 0, 6,
         7, 5, 8)
explored = set()
explored.add(state)           # fine

bad_state = [1, 2, 3, 4, 0, 6, 7, 5, 8]
explored.add(bad_state)       # TypeError: unhashable type: 'list'

Dataclasses to remove boilerplate. For plain record types — a transition, a training example, a configuration bundle — @dataclass generates __init__, __repr__ and __eq__ automatically. Adding frozen=True makes instances immutable and gives you __hash__ for free, which is perfect for states.

from dataclasses import dataclass, field

@dataclass(frozen=True)
class GridState:
    row: int
    col: int

@dataclass
class Transition:
    state: GridState
    action: str
    reward: float
    next_state: GridState
    done: bool = False

@dataclass(order=True)
class PrioritisedNode:
    priority: float
    node: Node = field(compare=False)   # compare on priority only

That last pattern is the standard way to push objects onto a heapq priority queue without requiring the payload itself to be orderable.

Comprehensions for concise data transformation. A comprehension expresses "build a collection by transforming and filtering another collection" in one line. The single most common use in search code is node expansion:

def expand(node, problem):
    """Return the list of child nodes reachable from `node`."""
    return [child_node(node, problem, action)
            for action in problem.actions(node.state)]

def child_node(node, problem, action):
    next_state = problem.result(node.state, action)
    cost = node.path_cost + problem.step_cost(node.state, action, next_state)
    return Node(next_state, parent=node, action=action, path_cost=cost)

A set comprehension deduplicates automatically, which is useful when several actions lead to the same successor state:

successors = {problem.result(state, a) for a in problem.actions(state)}

A dictionary comprehension builds lookup tables — exactly the shape needed for utility tables in value iteration, or word counts in text processing:

utility = {s: 0.0 for s in problem.states}                 # initialise V(s)
policy  = {s: best_action(s, utility) for s in problem.states}
counts  = {w: text.count(w) for w in set(text.split())}
inverse = {value: key for key, value in index.items()}      # invert a mapping

An if clause filters inline, letting you express "generate the frontier additions, skipping anything already seen" in a single readable expression:

new_nodes = [child for child in expand(node, problem)
             if child.state not in explored and child.state not in frontier_states]

Comprehensions earn their place through clarity, not cleverness. The guideline is at most two levels of nesting — one iteration plus one filter, or two iterations over a small cross-product. Beyond that, write the loop.

# Acceptable: two levels, still readable
cells = [(r, c) for r in range(rows) for c in range(cols) if grid[r][c] != WALL]

# Unreadable: refactor into an explicit loop
scores = [f(a, b, c) for a in A for b in B(a) for c in C(a, b) if valid(a, b, c)]

Generators and lazy evaluation. A generator function contains yield; calling it does not run the body but returns a generator object. Each time you ask for the next item, the body resumes exactly where it left off, with all local variables intact, runs to the next yield, and suspends again. The practical consequence is that values are produced one at a time, on demand, so memory stays flat no matter how many values there are.

def expand(node, problem):
    """Yield children lazily; callers that find a goal early stop the work."""
    for action in problem.actions(node.state):
        next_state = problem.result(node.state, action)
        yield Node(next_state, node, action,
                   node.path_cost + problem.step_cost(node.state, action, next_state))

def all_states(problem):
    """Enumerate the reachable state space without ever materialising it."""
    seen, stack = {problem.initial}, [problem.initial]
    while stack:
        state = stack.pop()
        yield state
        for action in problem.actions(state):
            nxt = problem.result(state, action)
            if nxt not in seen:
                seen.add(nxt)
                stack.append(nxt)

A generator expression is the same idea in expression form — parentheses instead of square brackets. Use it whenever the sequence is consumed exactly once, especially inside any, all, sum, min and max, which stop as soon as they can.

if any(problem.goal_test(child.state) for child in expand(node, problem)):
    ...
total_cost = sum(n.path_cost for n in path)
best = min(expand(node, problem), key=lambda c: c.path_cost + h(c))

Generators compose beautifully with itertools, which supplies lazy combinatorial building blocks:

from itertools import islice, chain, product, permutations, count

first_ten = list(islice(all_states(problem), 10))        # peek without exhausting memory
every_cell = product(range(8), range(8))                 # 64 (row, col) pairs, lazily
tours = permutations(cities)                             # n! orderings, one at a time
combined = chain(frontier_a, frontier_b)                 # iterate two sources as one
for episode in count(1):                                 # infinite counter for training loops
    ...

The one trap is exhaustion: a generator yields its values once and is then empty. If you need to iterate twice, materialise it.

children = expand(node, problem)        # generator
print(sum(1 for _ in children))         # 4
print(sum(1 for _ in children))         # 0  -- already exhausted!

children = list(expand(node, problem))  # now reusable

Recursion for tree and graph algorithms. Many AI algorithms are defined recursively because the problems themselves are recursive: the value of a game position is defined in terms of the values of its successor positions. Translating such a definition into Python is almost mechanical, provided you write the base case first.

def depth_limited_search(problem, node, limit):
    if problem.goal_test(node.state):          # base case 1: success
        return node
    if limit == 0:                             # base case 2: cutoff
        return "cutoff"
    cutoff_occurred = False
    for child in expand(node, problem):
        result = depth_limited_search(problem, child, limit - 1)
        if result == "cutoff":
            cutoff_occurred = True
        elif result is not None:
            return result
    return "cutoff" if cutoff_occurred else None

Adversarial search is the showcase example. Minimax is a pair of mutually recursive functions, and alpha–beta pruning adds two accumulator parameters that thread through the recursion:

def alphabeta_decision(game, state):
    best_score, best_action = -INF, None
    alpha, beta = -INF, INF
    for action in game.actions(state):
        score = min_value(game, game.result(state, action), alpha, beta)
        if score > best_score:
            best_score, best_action = score, action
        alpha = max(alpha, best_score)
    return best_action

def max_value(game, state, alpha, beta):
    if game.terminal_test(state):                 # explicit base case
        return game.utility(state)
    value = -INF
    for action in game.actions(state):
        value = max(value, min_value(game, game.result(state, action), alpha, beta))
        if value >= beta:                         # beta cutoff: prune
            return value
        alpha = max(alpha, value)
    return value

def min_value(game, state, alpha, beta):
    if game.terminal_test(state):
        return game.utility(state)
    value = INF
    for action in game.actions(state):
        value = min(value, max_value(game, game.result(state, action), alpha, beta))
        if value <= alpha:                        # alpha cutoff: prune
            return value
        beta = min(beta, value)
    return value

Note that alpha, beta and (in depth-limited variants) depth are passed as parameters. Each recursive call then gets its own copy, which is exactly the semantics the algorithm requires; using globals would let one branch's bounds leak into a sibling branch and silently produce wrong answers.

Memoisation. Recursive formulations frequently re-solve the same subproblem many times. functools.lru_cache converts exponential recomputation into linear work with one decorator, provided the arguments are hashable.

from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

@lru_cache(maxsize=None)
def minimax_value(state, player):
    """State must be an immutable tuple for caching to work."""
    if terminal(state):
        return utility(state)
    scores = (minimax_value(apply(state, a), -player) for a in actions(state))
    return max(scores) if player == 1 else min(scores)

print(fib.cache_info())   # CacheInfo(hits=..., misses=..., maxsize=None, currsize=...)

In game-playing code this cache is the transposition table: different move orders that reach the same position are evaluated only once. Be aware that the cache keys on all arguments, so a mutable or unhashable argument raises TypeError, and that an unbounded cache grows without limit — set maxsize for long-running processes.

When recursion is the wrong choice. CPython's default recursion limit is about 1000 frames, and each frame costs memory. A depth-first search over a deep graph will raise RecursionError. Rather than raising the limit (which risks a hard interpreter crash), convert the recursion to a loop with an explicit stack — the transformation is mechanical, because the stack simply holds what the call frames held.

# Recursive DFS: fails on deep graphs
def dfs_recursive(graph, state, visited):
    visited.add(state)
    for nxt in graph[state]:
        if nxt not in visited:
            dfs_recursive(graph, nxt, visited)

# Iterative DFS: depth limited only by heap memory
def dfs_iterative(graph, start):
    visited, stack = set(), [start]
    while stack:
        state = stack.pop()
        if state in visited:
            continue
        visited.add(state)
        stack.extend(nxt for nxt in graph[state] if nxt not in visited)
    return visited

Exception handling for robust algorithm code. Algorithms meet the outside world at their boundaries — reading a maze file, parsing a CSV of training data, converting a string to a float — and that is exactly where failures occur. Wrap the risky operation, not the whole program, and catch the specific exceptions you can actually handle.

def load_graph(path):
    try:
        with open(path, encoding="utf-8") as f:
            return parse_graph(f)
    except FileNotFoundError:
        raise InvalidStateError(f"Map file not found: {path}") from None
    except PermissionError as exc:
        raise InvalidStateError(f"Cannot read {path}: {exc}") from exc

def parse_weight(text):
    try:
        return float(text)
    except ValueError:
        return 1.0            # a missing weight defaults to unit cost

The reason to avoid a bare except: (or even a broad except Exception:) is that it swallows everything — including KeyboardInterrupt, typos that raise NameError, and genuine logic bugs. A search that silently returns None because you masked an AttributeError is far harder to debug than one that crashes loudly with a traceback.

# Dangerous: hides bugs and makes Ctrl-C impossible
try:
    result = astar_search(problem, h)
except:
    result = None

# Precise: each clause states a failure mode you have thought about
try:
    cost = costs[state]
except KeyError:
    cost = float("inf")            # unvisited state has infinite cost

try:
    probability = successes / trials
except ZeroDivisionError:
    probability = 0.0              # no trials yet

Custom exceptions express domain errors. Returning None to mean "no solution" is workable, but it conflates "there is no path" with "you gave me a malformed problem". Defining a small exception hierarchy makes the distinction explicit and lets callers choose which failures to handle.

class SearchError(Exception):
    """Base class for all search-related failures."""

class SearchFailure(SearchError):
    """Raised when the state space is exhausted without reaching a goal."""

class InvalidStateError(SearchError):
    """Raised when a state or problem definition is malformed."""

class ResourceLimitExceeded(SearchError):
    """Raised when a node or time budget is exhausted."""

Cleaning up with finally and context managers. Resources — open files, timers, database handles, pools of worker processes — must be released whether the block succeeds or raises. The with statement does this automatically and is always preferable to manual open/close pairs. You can write your own context manager for cross-cutting concerns such as timing an experiment.

import time
from contextlib import contextmanager

@contextmanager
def timer(label):
    start = time.perf_counter()
    try:
        yield
    finally:                                   # runs even if the body raises
        elapsed = time.perf_counter() - start
        print(f"{label}: {elapsed:.3f}s")

with timer("A* on 8-puzzle"), open("results.csv", "w") as out:
    try:
        node = astar_search(problem, manhattan)
        out.write(f"{problem.initial},{node.path_cost}\n")
    except SearchFailure:
        out.write(f"{problem.initial},unsolved\n")

Type hints and readable, reusable code. Annotations record, in the signature itself, what a function expects and produces. Python does not enforce them at run time — they are documentation that tooling can check — but editors use them for autocompletion and error highlighting, and mypy can verify them statically. For algorithm code they are especially valuable because a signature such as def h(node: Node) -> float tells a reader instantly how to supply a heuristic.

Typing constructs for complex signatures. Optional[X] means "an X or None" and is the right annotation for a search that may fail. Callable[[Node], float] describes a function argument precisely: one Node parameter, a float result. Iterator[Node] is the return type of a generator. List, Dict, Set and Tuple from typing are the legacy spellings; from Python 3.9 onwards the built-ins list[Node], dict[str, float] and tuple[int, ...] are preferred.

Docstrings that cite the pseudocode. Because the algorithms you implement are published, your docstring should say which algorithm it is and where the pseudocode came from. This is traceability: a marker, a teammate, or you in six weeks can check the implementation against the source without guessing.

def uniform_cost_search(problem: Problem) -> Optional[Node]:

Short, side-effect-free functions are testable functions. Every guideline in this topic converges on the same goal: a function small enough to understand at a glance, whose output depends only on its inputs, can be verified by a two-line test. That is what lets you build an algorithm incrementally and know each piece works before combining them.

def test_child_node_accumulates_cost():

    root = Node("Arad")
    child = child_node(root, problem, "Sibiu")
    assert child.state == "Sibiu"
    assert child.parent is root
    assert child.path_cost == 140
    assert child.depth == 1

def test_bfs_finds_shortest_hop_path():
    problem = RomaniaMap("Arad", "Bucharest", ROMANIA)
    assert solution_path(breadth_first_search(problem)) == [
        "Arad", "Sibiu", "Fagaras", "Bucharest"
    ]

def test_search_failure_is_raised_for_unreachable_goal():
    problem = RomaniaMap("Arad", "Atlantis", ROMANIA)
    try:
        breadth_first_search(problem)
        assert False, "expected SearchFailure"
    except SearchFailure:
        pass

Taken together, these constructs form a toolkit with a consistent philosophy: name things as the pseudocode names them, let functions compute rather than mutate, let classes hold the interface that algorithms depend on, let comprehensions and generators express transformation without clutter, let recursion mirror recursive definitions (and know when to unroll it), let exceptions express failure explicitly, and let type hints and docstrings record your intent for the next reader.
