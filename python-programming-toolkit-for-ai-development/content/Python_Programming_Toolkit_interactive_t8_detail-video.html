Version Control and Project Workflow

▶

Almost every piece of work you produce in an AI module is an experiment. You write a search algorithm, it solves the 8-puzzle in four seconds, you "improve" the heuristic, and suddenly it runs for ten minutes and returns a suboptimal path. Without a record of what changed, you are reduced to guessing. Version control is the discipline of recording the state of your project over time so that every change is reversible, attributable, and explainable. Git is the de facto standard tool for this, and GitHub is the hosting platform that turns a private local history into a shared, reviewable workspace. This topic treats Git not as an administrative chore bolted onto your coursework, but as a core part of the engineering workflow that makes AI experimentation tractable.

Why version control matters for AI coursework. A Git repository stores snapshots of your entire project tree, not just diffs of individual files. Each snapshot — a commit — is identified by a SHA-1 hash such as 3f9a1c2 and carries an author, timestamp, parent commit, and message. Because every commit is a complete, consistent picture of the project, you can return to any earlier working state with a single command. If your minimax agent passed all tests on Tuesday and fails on Thursday, you can check out Tuesday's commit, confirm the behaviour, and then bisect the intervening history to find the exact change that broke it.

  • History as a debugging instrument. Machine learning and search code fails in subtle, non-crashing ways: a model stops converging, a loss curve flattens, a heuristic stops being admissible. The commit log tells you what you altered between the last good run and the bad one. git bisect automates a binary search over commits to isolate the offending change in logarithmic time.
  • Branches as experiment sandboxes. You can try a Manhattan-distance heuristic on one branch and a pattern-database heuristic on another, benchmark both, and merge only the winner. Your main branch — the version you would submit if the deadline were today — never breaks.
  • Collaboration without file chaos. Shared repositories replace emailed ZIP files and report_final_v3_REALLY_FINAL.ipynb. Git merges concurrent edits to different parts of a file automatically and flags the rest for human resolution, so two teammates can work on the same module simultaneously.
  • Evidence of original, incremental work. A commit timeline showing forty small commits over three weeks is strong evidence of genuine authorship. A single commit named "upload" the night before the deadline is not. Markers may legitimately inspect the timeline, the diff sizes, and the commit messages as part of assessing academic integrity.
  • Reproducibility. Results reported in a write-up should be traceable to a specific commit. Quoting "accuracy 0.91 at commit a47bd3e" means anyone can check out that exact code and re-run it.

Core Git operations: repositories, staging, and commits. A repository is simply a directory containing a hidden .git folder that holds the object database and references. You create one in two ways:

$ mkdir ai-assignment-1 && cd ai-assignment-1
$ git init
Initialized empty Git repository in /home/student/ai-assignment-1/.git/

# or, to copy an existing project (e.g. a provided starter repo)
$ git clone https://github.com/course-org/assignment-1-starter.git
$ cd assignment-1-starter

Git has a three-stage model that beginners often find confusing but which is genuinely useful. Files live in the working tree (what you edit), the index or staging area (what you have marked for the next commit), and the repository (the permanent commit history). Staging lets you craft a commit that contains exactly one logical change even if you have touched several unrelated things.

git restore search.pyIndex/HEADWorking treeDiscard uncommitted edits

Commit messages are documentation, so write them deliberately. The conventional form is a short imperative summary of at most ~50 characters, optionally followed by a blank line and a fuller explanation. Imperative mood ("Add", "Fix", "Refactor") reads as an instruction describing what applying the commit does, which matches how Git's own generated messages are phrased.

Weak messageBetter messageWhy
stuffAdd successor generation for 8-puzzle statesNames the actual change
fixed bugFix off-by-one in BFS depth counterIdentifies which bug
updated filesReplace list frontier with heapq priority queueExplains the design decision
final versionPin scikit-learn 1.4.2 in requirements.txtSpecific and searchable

A longer example with a body:

Replace list frontier with heapq priority queue

The list-based frontier performed a linear scan for the minimum
f-value on every expansion, giving O(n) pops. heapq gives O(log n)
push and pop. Runtime on the 15-puzzle benchmark fell from 42s to 6s.

Inspecting history. Three commands do most of the work:

$ git log --oneline --graph --decorate -5
* 7c1d94e (HEAD -> main) Add A* heuristic for 8-puzzle solver
* a47bd3e Add breadth-first search baseline
* 1b0f22c Add puzzle state representation and tests
* 93ee517 Add .gitignore and requirements.txt
* 0d4a118 Initial commit

$ git diff                 # working tree vs index (unstaged changes)
$ git diff --staged        # index vs last commit (what you are about to commit)
$ git diff a47bd3e 7c1d94e -- src/heuristics.py   # changes between two commits
$ git show a47bd3e         # full patch and metadata for one commit

A git diff hunk header such as @@ -12,6 +12,9 @@ means "six lines starting at line 12 of the old file became nine lines starting at line 12 of the new file"; lines prefixed - were removed and + added.

Undoing things safely. There are two broad strategies, and the distinction matters enormously once work is shared.

  • git restore <file> throws away uncommitted modifications in the working tree, returning the file to its committed state. git restore --source=a47bd3e src/heuristics.py pulls an older version of one file back into your working tree.
  • git revert <commit> creates a new commit whose content is the inverse of the named commit. The original commit remains in the history. This is the safe way to undo something you have already pushed, because it adds to history rather than rewriting it.
  • git reset --hard moves the branch pointer and discards commits. It rewrites history and will cause problems for collaborators who already pulled those commits. Reserve it for local, unpushed work, and never use it on a shared branch.
  • git stash temporarily shelves uncommitted changes so you can switch branches; git stash pop reapplies them.
$ git revert a47bd3e
[main 5e9ab02] Revert "Add breadth-first search baseline"
 1 file changed, 0 insertions(+), 37 deletions(-)

Branching and merging workflows. A branch in Git is nothing more than a movable pointer to a commit, which is why creating one is instantaneous and essentially free. HEAD is a pointer to the branch you currently have checked out.

$ git branch feature/minimax          # create, stay where you are
$ git switch feature/minimax          # switch to it (modern syntax)
# or do both at once:
$ git checkout -b feature/minimax     # classic syntax
$ git switch -c feature/minimax       # modern equivalent

$ git branch
* feature/minimax
  main

Adopt a descriptive naming convention so a teammate reading the branch list understands the intent without asking. A common scheme uses a type prefix followed by a short slug:

Branch namePurpose
feature/minimaxNew functionality: adversarial search agent
feature/alpha-beta-pruningNew functionality layered on minimax
fix/dataloader-bugCorrection to an existing defect
experiment/pattern-db-heuristicExploratory work that may be discarded
docs/readme-results-tableDocumentation-only change

When the branch is finished and tested, you integrate it with git merge. Note the direction: you check out the branch that should receive the changes, then merge the other branch into it.

$ git switch main
$ git merge feature/minimax
Updating 7c1d94e..b2f8017
Fast-forward
 src/agents/minimax.py  | 72 ++++++++++++++++++++
 tests/test_minimax.py  | 31 +++++++++
 2 files changed, 103 insertions(+)

Git performs a fast-forward when main has not moved since the branch was created — it simply slides the main pointer forward. If both branches have new commits, Git creates a merge commit with two parents, combining the two lines of development.

Merge conflicts arise only when the same region of the same file was changed differently on both branches. Git cannot decide which version is correct, so it writes both into the file surrounded by conflict markers and stops:

$ git merge feature/weighted-astar
Auto-merging src/search/astar.py
CONFLICT (content): Merge conflict in src/search/astar.py
Automatic merge failed; fix conflicts and then commit the result.
def priority(node, goal):
<<<<<<< HEAD
    return node.cost + manhattan(node.state, goal)
=======
    return node.cost + 1.5 * manhattan(node.state, goal)
>>>>>>> feature/weighted-astar

The section between <<<<<<< HEAD and ======= is your current branch's version; the section between ======= and >>>>>>> is the incoming branch's version. Resolution is a human decision: keep one side, keep the other, or write a third version that reconciles both — for instance introducing a weight parameter so both behaviours are available. Delete all three marker lines, then finish the merge:

$ git status                      # lists "both modified" files
$ # edit src/search/astar.py, remove markers, run the tests
$ pytest -q
$ git add src/search/astar.py
$ git commit                      # Git pre-fills a merge commit message

Useful supporting commands: git merge --abort returns you to the pre-merge state if the conflict turns out to be larger than expected, and git diff --name-only --diff-filter=U lists exactly which files remain unresolved. To reduce conflicts in the first place, keep branches short-lived, pull from main often, and agree with teammates on who owns which module. Once merged, tidy up:

$ git branch -d feature/minimax        # safe: refuses if not merged
$ git branch -D experiment/pattern-db  # force-delete an abandoned experiment
$ git push origin --delete feature/minimax   # remove the remote copy too

Remote collaboration on GitHub. A remote is a named URL pointing at another copy of the repository. By convention the primary remote is called origin. If you cloned, origin already exists; if you ran git init locally, you add it yourself after creating an empty repository on GitHub.

$ git remote add origin https://github.com/your-username/ai-assignment-1.git
$ git remote -v
origin  https://github.com/your-username/ai-assignment-1.git (fetch)
origin  https://github.com/your-username/ai-assignment-1.git (push)

$ git push -u origin main      # -u sets the upstream so later 'git push' suffices
$ git push                     # subsequent pushes
$ git pull                     # fetch remote commits and merge into current branch

git pull is really git fetch (download remote commits) followed by git merge (integrate them). Some teams prefer git pull --rebase, which replays your local commits on top of the remote ones, producing a linear history without merge commits. Either is acceptable; be consistent within a team. The single most effective habit for avoiding painful conflicts is to pull before you start work and push when you finish a coherent chunk. Divergence is the enemy: a branch that has not seen main for two weeks will be far harder to merge than one synced daily.

If someone else pushed while you were working, your push is rejected:

$ git push
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '...'

$ git pull            # integrate their work (resolve conflicts if any)
$ pytest -q           # confirm the combined code still works
$ git push

Pull requests (PRs) are a GitHub feature, not a Git command. You push a feature branch, open a PR proposing to merge it into main, and teammates review the diff line by line, leave comments, request changes, and approve. For coursework this gives you a documented code-review trail and lets automated checks (a GitHub Actions workflow running pytest, for example) run before anything reaches main. A good PR description states what changed, why, how it was tested, and any results — e.g. "Adds alpha–beta pruning; node expansions on the tic-tac-toe benchmark drop from 549,946 to 18,297; all 14 tests pass."

GitHub Issues are the lightweight task tracker. Open one per bug or work item ("Dataloader drops the final batch when len(data) % batch_size != 0"), assign it to a team member, label it, and reference it from commits. Writing Fixes #12 in a commit message or PR body closes issue 12 automatically when the PR merges, creating a permanent link between problem and solution. For a three-person project, a simple board with columns for To do / In progress / Done plus one issue per deliverable is enough to prevent duplicated effort.

Submitting assignments. Push your final work to the designated repository (often created for you by GitHub Classroom) and submit whatever identifier the brief requires — typically the full 40-character commit hash, a short hash, a tag, or a PR link. Tagging is a clean way to mark a submission point:

$ git tag -a v1.0-submission -m "Assignment 1 final submission"
$ git push origin v1.0-submission
$ git rev-parse HEAD
b2f8017c5a1d9e3f4a7c2b6d8e0f1a2c3d4e5f60

Check that the pushed state is what you think it is: git status should report a clean tree with nothing to commit, and the GitHub web view should show the files you expect. Work that exists only on your laptop has not been submitted.

Keeping logic in src/ and only thin orchestration in notebooks has a practical benefit: notebook code cannot be unit-tested or diffed meaningfully, whereas a module can be both. Notebooks stored as JSON produce enormous, unreadable diffs when outputs are included, so clear outputs before committing (jupyter nbconvert --clear-output --inplace notebooks/*.ipynb) or use a tool such as nbstripout.

Reproducible environments. Commit a dependency manifest so that anyone can recreate your interpreter environment. For pip-based workflows this is requirements.txt with pinned versions; for conda it is environment.yml.

# requirements.txt
numpy==1.26.4
pandas==2.2.2
scikit-learn==1.4.2
matplotlib==3.8.4
pytest==8.1.1
# environment.yml
name: ai-course
channels: [conda-forge]
dependencies:
  - python=3.11
  - numpy=1.26.4
  - pandas=2.2.2
  - scikit-learn=1.4.2
  - pip
  - pip:
      - pytest==8.1.1

Exact pins (==) matter in AI work because library behaviour changes between versions — default solvers, random-number streams, and deprecation of parameters can all alter your numbers. Note that you commit the manifest, never the virtual environment directory itself, which is large, machine-specific, and regenerable.

A caveat worth knowing: .gitignore only prevents untracked files from being added. If you have already committed __pycache__/, ignoring it later has no effect until you untrack it with git rm -r --cached __pycache__/ followed by a commit. Similarly, a large file committed once stays in the history forever, bloating every future clone, even if you delete it in a later commit — which is why getting .gitignore right at the start is worth thirty seconds of attention.

What must never be committed. Two categories are non-negotiable:

  • Credentials. API keys, access tokens, database passwords, and SSH private keys must stay out of the repository. Public GitHub repositories are continuously scraped by bots that find and abuse leaked keys within minutes. Load secrets from environment variables instead — api_key = os.environ["OPENAI_API_KEY"] — and keep a committed .env.example listing the required variable names with blank values, while .env itself is ignored. If you do leak a key, rotating (revoking and reissuing) it is the only real fix; deleting the file does not remove it from history.
  • Large binaries. Multi-gigabyte datasets and model checkpoints make clones slow and may exceed GitHub's file-size limits (a hard rejection above 100 MB). Instead, commit a small script or README instruction that downloads the data, or use Git LFS where the course permits it. A checksum in the README lets others verify they obtained the same file.

Relative paths. Code containing pd.read_csv("C:/Users/Sam/Desktop/data/train.csv") will fail on every machine except yours, including the marker's. Always resolve paths relative to the project, which you can do robustly with pathlib:

from pathlib import Path
import pandas as pd

PROJECT_ROOT = Path(__file__).resolve().parents[2]   # .../ai-assignment-1
DATA_DIR = PROJECT_ROOT / "data" / "processed"

def load_training_data() -> pd.DataFrame:
    """Load the processed training split as a DataFrame."""
    return pd.read_csv(DATA_DIR / "train.csv")

This pattern works regardless of where the project is cloned and regardless of the current working directory from which the script is launched. It also keeps Windows/macOS/Linux separator differences out of your code.

Testing practices. Automated tests convert "I think the successor function is right" into a repeatable, machine-checked claim. They are especially valuable in AI code because the outputs — paths, probabilities, accuracy scores — are not obviously correct by inspection. Put tests in a tests/ directory, name files test_*.py, and name functions test_* so pytest discovers them automatically.

# tests/test_successors.py
import pytest
from src.search.puzzle import PuzzleState, successors

def test_corner_state_has_two_moves():
    """A blank in the top-left corner permits exactly two moves."""
    state = PuzzleState((0, 1, 2,
                         3, 4, 5,
                         6, 7, 8))
    assert len(successors(state)) == 2

def test_successors_are_distinct_from_parent():
    state = PuzzleState((1, 2, 3, 4, 0, 5, 6, 7, 8))
    assert all(s.tiles != state.tiles for s in successors(state))

@pytest.mark.parametrize("blank_index, expected", [(0, 2), (1, 3), (4, 4)])
def test_branching_factor(blank_index, expected):
    tiles = list(range(1, 9))
    tiles.insert(blank_index, 0)
    assert len(successors(PuzzleState(tuple(tiles[:9])))) == expected

For numerical code, compare with a tolerance rather than exact equality, because floating-point arithmetic is not associative:

import numpy as np
from src.metrics import accuracy, f1_score

def test_accuracy_matches_hand_calculation():
    y_true = np.array([1, 0, 1, 1, 0])
    y_pred = np.array([1, 0, 0, 1, 0])
    assert accuracy(y_true, y_pred) == pytest.approx(0.8)

def test_f1_is_zero_when_no_positives_predicted():
    y_true = np.array([1, 1, 0])
    y_pred = np.array([0, 0, 0])
    assert f1_score(y_true, y_pred) == pytest.approx(0.0)

The equivalent in the standard library's unittest uses classes and assertion methods:

import unittest
from src.search.bfs import breadth_first_search

class TestBFS(unittest.TestCase):
    def setUp(self):
        self.graph = {"A": ["B", "C"], "B": ["D"], "C": ["D"], "D": []}

    def test_finds_shortest_path(self):
        self.assertEqual(breadth_first_search(self.graph, "A", "D"),
                         ["A", "B", "D"])

    def test_returns_none_when_unreachable(self):
        self.assertIsNone(breadth_first_search(self.graph, "D", "A"))

if __name__ == "__main__":
    unittest.main()

Run the suite with pytest -q (or python -m unittest discover) before every commit, and certainly before every push. A useful discipline when fixing a bug is to write a failing test that reproduces it first, then fix the code until the test passes; the test then permanently protects against regression. Good targets for tests in AI coursework include successor/action generation, goal tests, heuristic admissibility on known instances, data-loading shapes and dtypes, evaluation metrics against hand-computed values, and edge cases such as empty inputs, single-element inputs, and already-solved start states.

Documentation practices. Every public function, class, and module should carry a docstring stating its purpose, its parameters, and what it returns, including the types and any exceptions raised. Docstrings are not comments: they are accessible at runtime via help(obj) and obj.__doc__, and tools such as Sphinx and pydoc generate reference documentation from them.

The README.md is the front door of the repository and the first thing a marker reads. It should let a stranger go from a bare clone to reproduced results without asking you a single question. A workable template covers:

  • Title and one-paragraph problem statement — what task is being solved and with what approach.
  • Installation — the exact commands: create a virtual environment, activate it, pip install -r requirements.txt.
  • Data — where the dataset comes from, how to download it, and where to place it, since it is not in the repository.
  • How to run — concrete invocations such as python -m src.experiments.run_search --algorithm astar --puzzle 8.
  • How to test — pytest -q.
  • Project structure — a short directory map.
  • Results — a table of the numbers you report in your write-up.
  • Known limitations and future work — honest statements about what does not work.
# 8-Puzzle Search Agents

heuristics) on randomly generated solvable 8-puzzle instances.

Recording results for reproducibility. State the random seeds you used, the hardware, the library versions (which the pinned requirements.txt already captures), and the commit hash at which each reported number was produced. Write experiment outputs to a versioned CSV in results/ rather than retyping numbers from a terminal into a report — this removes transcription errors and lets a marker diff your table against a re-run. Being explicit about limitations is not a weakness in an assignment; an unqualified claim that turns out to be fragile costs more credit than a documented caveat.

Putting it together: a realistic week of work.

$ git switch main && git pull                 # start from the team's latest
$ git switch -c feature/alpha-beta
$ # ... implement, run pytest, iterate ...
$ git add src/agents/minimax.py tests/test_minimax.py
$ git commit -m "Add alpha-beta pruning to minimax agent"
$ git add results/benchmarks.csv README.md
$ git commit -m "Record alpha-beta node-expansion benchmarks"
$ git switch main && git pull                 # pick up teammates' work
$ git switch feature/alpha-beta
$ git merge main                               # resolve conflicts here, not in main
$ pytest -q
$ git push -u origin feature/alpha-beta        # open a PR on GitHub, request review
$ # after approval and merge:
$ git switch main && git pull
$ git branch -d feature/alpha-beta

Each command in that sequence is trivial; the value lies in the habit. A repository maintained this way is simultaneously a backup, a lab notebook, a collaboration channel, a debugging tool, and the submission artefact itself.

Version control is the practice of recording the history of your project so that every change is tracked, reversible, and attributable. Git is the tool that does this on your own machine, and GitHub is the hosting service that lets you back up a repository online and share it with instructors and teammates. In this course you will use both to manage assignment code: initialising a repository, staging and committing changes, creating branches for experiments, merging work back together, and pushing to a remote for submission.

This matters for AI coursework in a very practical way. Machine learning and search code changes constantly as you tune parameters, refactor functions, and try alternative approaches, and without version control it is easy to lose a working version or to be unable to explain what changed between two sets of results. Commits give you a trail you can return to; branches let you try an idea without breaking code that already runs; a GitHub remote protects against losing a laptop the night before a deadline.

As you watch, pay attention to the mental model rather than memorising commands: the difference between the working directory, the staging area, and the commit history, and what each command moves between them. Notice how commit messages are written, how a branch is created and merged, and how a local repository is connected to a remote. Where a video uses a graphical interface, try to map each button back to the underlying Git command — you will meet both in this course.
