The AIMA Python Code Base

▶

The Artificial Intelligence: A Modern Approach (AIMA) textbook by Russell and Norvig presents its algorithms as boxed pseudocode figures — compact, language-neutral descriptions such as GRAPH-SEARCH(problem, frontier) or DPLL-SATISFIABLE?(s). Those figures are excellent for reasoning about an algorithm, but they are not runnable, and the gap between "I understand the pseudocode" and "I have working code" is exactly where most learners stumble. The AIMA Python repository closes that gap. It is a community-maintained, open-source collection of Python modules that implement essentially every algorithm in the book, together with Jupyter notebooks, test suites, sample data, and visualisation helpers. For this module it serves three purposes at once: a reference implementation you can read when your own code misbehaves, a library you can import and extend for assignments, and a worked example of idiomatic Python showing how classes, generators, comprehensions and the standard-library data structures are used in real AI code.

What the AIMA Python Repository Is

At its heart, the repository is a faithful translation layer. Each boxed figure in the book becomes a Python function or class with the same name (converted to Python naming conventions) and the same parameters. Consider the book's BEST-FIRST-SEARCH(problem, f): in search.py you will find best_first_graph_search(problem, f, display=False), whose body follows the pseudocode step by step — initialise a node from the initial state, push it onto a priority frontier ordered by f, maintain an explored set, pop the best node, test for the goal, expand, and relax improved frontier entries. Reading the two side by side is the fastest way to internalise what the pseudocode actually means operationally.

Every core module is paired with a Jupyter notebook of the same stem — search.py with search.ipynb, logic.py with logic.ipynb, and so on. The notebooks are not API documentation; they are guided tours. They set up a concrete problem (the Romania road map, an eight-queens board, a wumpus cave), call the algorithm, and then render the result, often with an animation showing which nodes were expanded in which order. Because a notebook interleaves narrative, code and output, it is the ideal place to experiment: change the heuristic, re-run the cell, and watch the explored set shrink or grow.

A deliberate design choice runs through the whole repository: clarity beats speed. The code is pedagogical, not production-hardened. You will see list comprehensions where a hand-rolled loop would be faster, `str` keys where an integer encoding would be leaner, and full copies of states where in-place mutation with undo would save memory. Error handling is minimal and the code generally assumes you pass sensible arguments. That is a feature, not a bug — the implementations are meant to be read in a single sitting and mapped onto the textbook. If you later need performance, you will know exactly which lines to optimise.

The tests/ directory contains pytest suites such as tests/test_search.py and tests/test_logic.py. These serve double duty. They verify the implementations, and because each test constructs a small problem and asserts an expected answer, they are also the most concise usage examples in the project. If you are unsure how to instantiate GraphProblem or what astar_search returns, grep the tests before reading the source:

# excerpt in the spirit of tests/test_search.py
romania_problem = GraphProblem('Arad', 'Bucharest', romania_map)

def test_astar_search():
    assert astar_search(romania_problem).solution() == ['Sibiu', 'Rimnicu', 'Pitesti', 'Bucharest']
    assert astar_search(eight_puzzle).solution() == ['LEFT', 'UP', 'LEFT', 'DOWN', 'RIGHT', 'RIGHT']

Finally, the practical payoff: cloning the repository and installing its requirements.txt gives you a complete, self-contained AI sandbox. NumPy, pandas, scikit-learn-era numerics, matplotlib, ipython/jupyter, networkx and sortedcontainers come along for the ride, so you can go from a bare virtual environment to running A* on a map of Romania in about two minutes.

Repository Layout and Navigation

The project is intentionally flat. Nearly all the algorithm code lives in top-level .py files in the repository root, each corresponding to one or more chapters of the book. There is no deep package hierarchy to learn and no src/aima/... nesting, which is why a plain from search import astar_search works when your script sits in the same directory.

utils.py deserves special attention because it is the common substrate. It supplies the queue abstractions used by search (PriorityQueue, built on heapq, plus the use of collections.deque for FIFO frontiers), geometric helpers (distance, euclidean_distance, manhattan_distance), small vector and matrix routines (vector_add, dot_product, matrix_multiplication), probability utilities (normalize, weighted_sample_with_replacement), and decision helpers (argmax_random_tie, probability). It also provides memoize, a caching decorator used heavily to avoid recomputing heuristics:

from utils import memoize

def best_first_graph_search(problem, f, display=False):
    f = memoize(f, 'f')          # cache f(node) on the node object itself
    node = Node(problem.initial)
    frontier = PriorityQueue('min', f)
    frontier.append(node)
    explored = set()
    while frontier:
        node = frontier.pop()
        if problem.goal_test(node.state):
            return node
        explored.add(node.state)
        for child in node.expand(problem):
            if child.state not in explored and child not in frontier:
                frontier.append(child)
            elif child in frontier and f(child) < frontier[child]:
                del frontier[child]
                frontier.append(child)
    return None

Navigation tip: the module docstring at the top of every file lists the pseudocode figures it implements, usually as a plain-text index of names and figure numbers. Opening search.py and reading the first thirty lines tells you immediately that the file covers tree and graph search, uniform-cost, depth-limited, iterative deepening, bidirectional, greedy best-first, A*, recursive best-first, hill climbing, simulated annealing, genetic algorithms and online search. Combine that with Python's introspection to explore without leaving the interpreter:

import search, inspect
print(search.__doc__[:400])            # the figure index
print([n for n, o in inspect.getmembers(search, inspect.isfunction)][:12])
print(inspect.getsource(search.depth_first_graph_search))

Key Modules: Agents, Search, Logic, and Learning

agents.py implements the agent/environment framework of the book's opening chapters. The base vocabulary is small and worth memorising. A Thing is anything that can occupy a location in a world. An Agent is a Thing that carries a program: a callable mapping a percept to an action. An Environment holds a list of things and agents and drives the simulation loop in its step() and run(steps) methods, calling percept(agent) to deliver sensory input and execute_action(agent, action) to apply the chosen action. Concrete worlds built on this base include TrivialVacuumEnvironment, the two-dimensional VacuumEnvironment, WumpusEnvironment, and the agent programs TableDrivenAgentProgram, ReflexVacuumAgent, ModelBasedVacuumAgent and RandomAgentProgram. The module also supplies compare_agents and test_agent for measuring average performance scores across randomised worlds.

from agents import TrivialVacuumEnvironment, ReflexVacuumAgent

env = TrivialVacuumEnvironment()
agent = ReflexVacuumAgent()
env.add_thing(agent)
env.run(steps=10)
print(env.status, agent.performance)

search.py is the module you will use most. It defines two abstractions that everything else hangs off. Problem is the formal statement of a search problem: an initial state, a goal, and the methods actions(state), result(state, action), goal_test(state), path_cost(c, state1, action, state2) and optionally value(state) for local search. Node is a node in the search tree, holding state, parent, action, path_cost and depth, and providing expand(problem), child_node(problem, action), solution() (the action sequence) and path() (the node sequence). On top of these sit the uninformed algorithms (breadth_first_graph_search, depth_first_graph_search, uniform_cost_search, iterative_deepening_search, bidirectional_search), the informed ones (greedy_best_first_graph_search, astar_search, recursive_best_first_search), and local search (hill_climbing, simulated_annealing, genetic_algorithm). Ready-made problems include GraphProblem with the romania_map, EightPuzzle and NQueensProblem.

logic.py covers both propositional and first-order logic. Its central data type is Expr, a symbolic expression object that overloads Python operators so that logical formulas can be written almost as in the book: & for conjunction, | for disjunction, ~ for negation, and the special infix |'==>'| idiom for implication. The helper expr('(A & B) ==> C') parses a string into the same structure. Knowledge bases are represented by KB, PropKB and FolKB, each supporting tell, ask and retract. Inference procedures include tt_entails (truth-table enumeration), pl_resolution, dpll_satisfiable, WalkSAT, forward and backward chaining for definite clauses, and unify plus subst for first-order substitution. A PlanRoute/WumpusKB layer shows logic driving an agent.

from logic import expr, PropKB, dpll_satisfiable

kb = PropKB()
kb.tell(expr('Rain ==> WetGrass'))
kb.tell(expr('Rain'))
print(kb.ask_if_true(expr('WetGrass')))      # True
print(dpll_satisfiable(expr('(A | B) & ~A & ~B')))  # False

learning.py is the machine-learning chapter in code. The DataSet class loads a comma-separated file from the data directory, tracks attribute names, the target index, the set of possible values per attribute, and offers split_values, sanitize (strip the target for prediction) and remove_examples. Learners follow a uniform convention: a learner function takes a DataSet and returns a predictor function that maps an example vector to a predicted class. The family includes PluralityLearner, NaiveBayesLearner, NearestNeighborLearner(dataset, k), DecisionTreeLearner, DecisionListLearner, PerceptronLearner and NeuralNetLearner, together with evaluation utilities err_ratio, train_test_split, cross_validation and learning_curve.

from learning import DataSet, DecisionTreeLearner, err_ratio

iris = DataSet(name='iris')
tree = DecisionTreeLearner(iris)
print(tree([5.1, 3.5, 1.4, 0.2]))      # 'setosa'
print(err_ratio(tree, iris))

Beyond these four, the supporting modules fill out the rest of the book. csp.py gives CSP, backtracking search with MRV/degree heuristics, forward checking, AC-3 and min-conflicts, plus ready-made instances such as map colouring, Sudoku and Zebra. mdp.py provides MDP, GridMDP, value_iteration and policy_iteration. games.py covers adversarial search with Game, minimax_decision, alpha_beta_search, monte_carlo_tree_search and example games like TicTacToe and ConnectFour. Others include probability.py (Bayesian networks, enumeration, elimination, sampling, particle filtering), planning.py, nlp.py and text.py.

Importing and Running AIMA Code

The setup sequence is short but every step matters. First clone the repository (use --recursive if the data lives in a submodule), then create an isolated virtual environment so the AIMA dependency versions cannot collide with anything else on your machine, then install the pinned requirements:

git clone --recursive https://github.com/aimacode/aima-python.git
cd aima-python
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install --upgrade pip
pip install -r requirements.txt

Because the modules sit at the repository root and are imported by bare name, Python must be able to find that directory on its import path. The simplest reliable approach is to place your own scripts in the repository root; Python automatically puts the directory containing the script at the front of sys.path, so from search import astar_search resolves immediately.

# my_assignment.py, saved inside aima-python/
from search import astar_search, GraphProblem
from search import romania_map

problem = GraphProblem('Arad', 'Bucharest', romania_map)
goal = astar_search(problem)
print(goal.solution(), goal.path_cost)

If you prefer to keep your coursework in its own folder or Git repository, extend the path explicitly instead. Either append it at runtime:

import sys, pathlib
sys.path.append(str(pathlib.Path.home() / 'code' / 'aima-python'))
from search import astar_search

or set the environment variable before launching Python, which keeps the path manipulation out of your source files:

export PYTHONPATH=$HOME/code/aima-python     # Windows: set PYTHONPATH=C:\code\aima-python
python my_assignment.py

A word on import style. The notebooks commonly begin with from agents import * because at the console you want every class and demo world within reach, and a notebook is throwaway exploratory code. In assignment code, prefer explicit imports: from search import Problem, Node, astar_search. Explicit imports document your dependencies, prevent a wildcard from silently shadowing one of your own names (Node, distance and Problem are common collisions), and let linters and IDEs resolve symbols correctly. Note also that some modules import heavy third-party libraries at the top, so a wildcard import can pull in more than you expect.

Before you build anything, prove the installation works by running the test suite. A clean run tells you the dependencies resolved and the data files are present:

pip install pytest
pytest tests/                       # whole suite
pytest tests/test_search.py -q      # one module, quiet output
pytest tests/test_search.py::test_astar_search -v   # one test

If a few tests fail in modules you are not using (notebooks, NLP corpora, optional dependencies), that is usually harmless; if test_search.py or test_utils.py fail, stop and fix the environment first. A frequent cause of failure is a missing data directory — the DataSet loader looks for files such as iris.csv under aima-data/, which is only populated if you cloned recursively or ran git submodule update --init.

Mapping Pseudocode to Reference Implementations

The translation from book to code follows a small set of consistent rules, and once you know them you can predict where to look for anything in the text.

  • Names. SMALL-CAPS-WITH-HYPHENS becomes snake_case. UNIFORM-COST-SEARCH → uniform_cost_search; AC-3 → AC3; DPLL-SATISFIABLE? → dpll_satisfiable (the predicate question mark is simply dropped). Parameters keep their order and meaning, so a figure's (problem, limit) is the function's (problem, limit).
  • Abstract data types become classes. The book's problem with its INITIAL-STATE, ACTIONS, RESULT, GOAL-TEST and PATH-COST components becomes the Problem class with attribute initial and methods actions, result, goal_test and path_cost. A node with its STATE, PARENT, ACTION and PATH-COST fields becomes the Node class with exactly those attributes plus depth. Similarly CSP, MDP, KB and Game each become a class whose methods are the pseudocode's accessor functions.
  • Control flow is near-literal. A pseudocode loop do … if … then return … becomes a Python while with the same guard and the same early return, and variable names survive the trip: frontier, explored, node, child, result, f-limit → flimit.
  • Concrete data structures are chosen where the book is silent. The pseudocode says "a FIFO queue", "a priority queue ordered by f", "a set"; the code says collections.deque, utils.PriorityQueue (a thin wrapper over heapq), and the built-in set. These choices are exactly the performance trade-offs you will reason about elsewhere in this module.

The following table makes the correspondence explicit for a handful of frequently used figures.

A concrete side-by-side makes the fidelity obvious. The book's depth-limited search reads roughly: recursive-DLS(node, problem, limit): if GOAL-TEST(node.STATE) then return SOLUTION(node); else if limit = 0 then return cutoff; else for each action in ACTIONS(node.STATE) do child ← CHILD-NODE(...); result ← recursive-DLS(child, problem, limit−1); if result = cutoff then cutoff_occurred? ← true; else if result ≠ failure then return result; return cutoff if cutoff_occurred? else failure. The Python is almost a transcription:

def depth_limited_search(problem, limit=50):
    def recursive_dls(node, problem, limit):
        if problem.goal_test(node.state):
            return node
        elif limit == 0:
            return 'cutoff'
        else:
            cutoff_occurred = False
            for child in node.expand(problem):
                result = recursive_dls(child, problem, limit - 1)
                if result == 'cutoff':
                    cutoff_occurred = True
                elif result is not None:
                    return result
            return 'cutoff' if cutoff_occurred else None
    return recursive_dls(Node(problem.initial), problem, limit)

Notice the three small engineering decisions the book leaves open: failure is represented by None, cutoff by the sentinel string 'cutoff', and SOLUTION(node) is deferred — the function returns the goal Node and you call .solution() yourself. Knowing those conventions lets you read any AIMA function at a glance.

This correspondence is also the most efficient debugging tool available to you. When your own from-scratch A* returns a suboptimal path, run the AIMA version on the identical problem instance, print both frontiers after each pop, and find the first step where they diverge. Common discoveries: you tested the goal when generating rather than when expanding (or vice versa), you forgot to update a frontier entry when a cheaper path to the same state appeared, your __eq__/__hash__ on states is inconsistent so the explored set never matches, or your heuristic is inadmissible. Instrumenting the reference implementation costs one line:

goal = astar_search(problem, h=my_heuristic, display=True)   # prints paths/states explored
print(len(goal.path()), goal.path_cost)

Extending AIMA Classes for Assignments

The real payoff of a well-factored reference library is that you rarely write an algorithm twice: you write a problem and reuse every algorithm. The contract is simple. Subclass Problem, call super().__init__(initial, goal), and override four methods: actions(state) returning an iterable of legal actions, result(state, action) returning the successor state, goal_test(state) returning a boolean, and path_cost(c, state1, action, state2) returning the cumulative cost (the default adds 1 per step). States must be hashable and immutable — use tuples, frozensets or strings, never lists or dicts — because they are stored in sets and used as dictionary keys.

from search import Problem, astar_search, breadth_first_graph_search

class JugProblem(Problem):
    """Two jugs of capacity 4 and 3; measure exactly 2 litres."""

    def __init__(self, initial=(0, 0), capacities=(4, 3), target=2):
        self.capacities = capacities
        self.target = target
        super().__init__(initial)

    def actions(self, state):
        a, b = state
        cap_a, cap_b = self.capacities
        acts = []
        if a < cap_a: acts.append('fill A')
        if b < cap_b: acts.append('fill B')
        if a > 0:     acts.extend(['empty A', 'pour A->B'])
        if b > 0:     acts.extend(['empty B', 'pour B->A'])
        return acts

    def result(self, state, action):
        a, b = state
        cap_a, cap_b = self.capacities
        if action == 'fill A':   return (cap_a, b)
        if action == 'fill B':   return (a, cap_b)
        if action == 'empty A':  return (0, b)
        if action == 'empty B':  return (a, 0)
        if action == 'pour A->B':
            amount = min(a, cap_b - b)
            return (a - amount, b + amount)
        if action == 'pour B->A':
            amount = min(b, cap_a - a)
            return (a + amount, b - amount)
        raise ValueError(action)

    def goal_test(self, state):
        return self.target in state

    def h(self, node):
        """Admissible: at least one more action unless we are already done."""
        return 0 if self.goal_test(node.state) else 1

print(breadth_first_graph_search(JugProblem()).solution())
print(astar_search(JugProblem()).solution())

Adding a heuristic is deliberately lightweight: define a method h(self, node) on your Problem subclass and astar_search(problem) will pick it up automatically, because its default is h = memoize(h or problem.h, 'h'). Note the signature — h receives the node, not the state, so you write node.state inside. For a sliding-tile puzzle, misplaced tiles and the sum of Manhattan distances are both admissible, and the second dominates the first:

from utils import manhattan_distance

class MyEightPuzzle(Problem):
    goal_positions = {v: divmod(i, 3) for i, v in enumerate((1,2,3,4,5,6,7,8,0))}

    def h(self, node):
        return sum(manhattan_distance(divmod(i, 3), self.goal_positions[tile])
                   for i, tile in enumerate(node.state) if tile != 0)

Because admissibility (never overestimating the true remaining cost) is what guarantees A* optimality, it is worth sanity-checking a new heuristic against uniform-cost search on small instances: if A* ever returns a more expensive solution than UCS, the heuristic is inadmissible.

Agents follow the same subclass-and-override pattern. An Agent is constructed with a program — any callable taking a percept and returning an action — so the simplest custom agent is a function wrapped in Agent(...); for agents with internal state, subclass Agent and attach a closure or a bound method:

from agents import Agent, Environment, Thing

class CleaningAgent(Agent):
    def __init__(self):
        self.visited = set()
        super().__init__(self.program)

    def program(self, percept):
        location, status = percept
        self.visited.add(location)
        if status == 'Dirty':
            return 'Suck'
        return 'Right' if location == (0, 0) else 'Left'

New worlds are built by subclassing Environment and overriding three hooks: percept(agent), which packages whatever the agent is allowed to sense; execute_action(agent, action), which mutates the world and updates agent.performance; and is_done(), which stops the simulation (the default stops when no agent is alive). Optionally override thing_classes() and default_location(thing).

class TwoCellWorld(Environment):
    def __init__(self):
        super().__init__()
        self.status = {(0, 0): 'Dirty', (1, 0): 'Dirty'}

    def percept(self, agent):
        return (agent.location, self.status[agent.location])

    def execute_action(self, agent, action):
        if action == 'Suck':
            if self.status[agent.location] == 'Dirty':
                agent.performance += 10
            self.status[agent.location] = 'Clean'
        elif action in ('Left', 'Right'):
            agent.location = (0, 0) if action == 'Left' else (1, 0)
            agent.performance -= 1

    def is_done(self):
        return all(v == 'Clean' for v in self.status.values())

env = TwoCellWorld()
env.add_thing(CleaningAgent(), location=(0, 0))
env.run(steps=20)

The same philosophy applies across the library: implement CSP's variables, domains, neighbours and a constraint function and you inherit backtracking, AC-3 and min-conflicts; implement Game's actions, result, utility and terminal_test and you inherit minimax, alpha–beta and MCTS; build a DataSet with the right attribute metadata and every learner in learning.py will train on it. The rule to internalise is that the algorithms are written against an interface, not against a specific problem — so as long as your subclass honours the expected method names, signatures, return types and the hashability of states, you can reuse the whole library unchanged. When something fails, the cause is almost always an interface violation: returning a list where a tuple (hashable state) was expected, forgetting to call super().__init__(), defining h(self, state) instead of h(self, node), or mutating a state in place inside result rather than returning a fresh copy.

Alignment with Learning Outcomes

  • MO1: Directly supported — the setup workflow for the repository (clone, python3 -m venv, activate, pip install -r requirements.txt, verify with pytest) is exactly the isolated, pinned environment the outcome describes, and it establishes the sandbox in which all later course libraries are installed.
  • MO2: Strongly supported — the topic shows how boxed pseudocode becomes Python functions and classes (Problem, Node, Agent, Environment), including recursive implementations such as recursive_dls, generator-based expand, comprehensions in heuristics, and the subclassing patterns learners imitate when implementing algorithms themselves.
  • MO3: Supported — the discussion of where the book is silent on data structures highlights AIMA's concrete choices (collections.deque for FIFO frontiers, a heapq-backed PriorityQueue for best-first search, set for the explored/visited collection, dict for models and utilities), giving learners concrete reference points for comparing their performance trade-offs.
  • MO4: Partially supported — learning.py's DataSet loader and learner-returns-predictor convention introduce the data-loading and train-then-predict workflow, and requirements.txt brings in NumPy and pandas; however, scikit-learn's specific fit/predict API is not taught here and is developed in the machine-learning topics of the module.
  • MO5: Lightly supported — the topic uses git clone (including --recursive and git submodule update --init) and discusses keeping coursework in its own repository separate from the AIMA checkout, but commits, branches, merges and pushing to GitHub are not covered here and belong to the version-control topic.
