IDEs and Interactive Tools for AI Work

▶

The tools you choose to write code in shape how quickly you can move from a half-understood idea to a working, inspectable implementation. In an artificial intelligence course this matters more than in a typical programming subject, because you will spend your time alternating between two very different kinds of work. One kind is algorithm construction: writing a breadth-first search, a minimax routine with alpha-beta pruning, a constraint propagation loop, or a class hierarchy for agents and environments. That work is structural, it spans multiple files, it benefits from refactoring, and it needs a real debugger because the bugs live in control flow and in subtle data-structure misuse. The other kind is data and model exploration: loading a CSV, checking what the columns actually contain, plotting a distribution, trying three values of a hyperparameter, and looking at a confusion matrix. That work is iterative and exploratory, and it is miserable if every small question requires re-running an expensive data load from scratch.

An integrated development environment (IDE) serves the first kind of work. A notebook serves the second. Neither is a replacement for the other, and the practitioners who struggle most are usually those who try to force all their work into whichever single tool they learned first — writing a 400-line search algorithm in a notebook cell, or restarting a script that takes ninety seconds to load data every time they want to check the shape of an array. Learning to move fluidly between the two, and knowing which questions belong in which environment, is a genuine professional skill rather than a matter of taste.

Everything described below is free for students and runs on Windows, macOS, and Linux. Visual Studio Code is open source and free for any use. PyCharm Community Edition is free, and the Professional Edition is available free to students and educators through JetBrains' educational licence. Jupyter is open-source software from Project Jupyter and installs through pip like any other Python package. There is no cost barrier to trying all three, and you should try all three before settling into a habit.

Visual Studio Code as the course default. VS Code is a lightweight, extensible editor that becomes a capable Python IDE once the Microsoft Python and Pylance extensions are installed. It is the course default because it starts quickly, handles both scripts and notebooks, has first-class Git integration, and does not demand that you create a formal "project" before you can edit a file.

The single most important configuration step — and the source of most early confusion — is interpreter selection. VS Code does not automatically know which Python you intend to use. Open the Command Palette (Ctrl+Shift+P on Windows and Linux, Cmd+Shift+P on macOS) and run Python: Select Interpreter. You will see a list that typically includes a system Python, perhaps a Homebrew or Microsoft Store Python, and any virtual environments VS Code has discovered. Choose the one inside your course virtual environment — its path will end in something like .venv/bin/python on macOS or Linux, or .venv\Scripts\python.exe on Windows. Once selected, the interpreter is shown in the status bar at the bottom of the window, and VS Code stores the choice per workspace in .vscode/settings.json:

{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/bin/python",
  "python.terminal.activateEnvironment": true
}

Symptoms of a wrong interpreter are distinctive and worth memorising: ModuleNotFoundError: No module named 'numpy' when you are certain you installed NumPy; squiggly underlines under imports that nevertheless run fine; or autocompletion offering nothing for pandas. In almost every case the editor is analysing your code with a different Python installation from the one you installed packages into.

The integrated terminal (Ctrl+`) opens a shell rooted at your workspace folder, and with python.terminal.activateEnvironment enabled it activates the selected virtual environment automatically — you will see the environment name in the prompt. This means you can install a package, run a script, and inspect the output without ever leaving the editor window:

$ python -m pip install scikit-learn
$ python -m pip freeze > requirements.txt
$ python search/bfs.py --start A --goal G

Use python -m pip rather than a bare pip. The -m form guarantees that the pip being invoked belongs to the interpreter you just ran, which eliminates an entire family of "I installed it but Python can't find it" problems.

The Source Control panel (the branch icon in the activity bar) gives a live view of your repository. Modified files appear under "Changes" with an M, new untracked files with a U, and deleted files with a D. Clicking a file opens a side-by-side diff showing exactly what changed since the last commit, which is a far better way to review your own work than scrolling through the file hoping to spot the edit. The + icon stages a file (equivalent to git add), the message box plus the commit button performs git commit, and the sync arrows push and pull from the remote. Gutter markers in the editor itself — small coloured bars beside the line numbers — show added, modified, and removed lines in real time as you type. None of this replaces understanding the underlying Git commands, but it makes the state of your repository continuously visible rather than something you must interrogate with git status.

The Jupyter extension lets VS Code open .ipynb files natively. You get the familiar cell-based interface — Shift+Enter to run a cell and advance, outputs rendered beneath each cell — but inside the editor, with the same keybindings, extensions, and Git panel you use for scripts. A useful intermediate mode is the interactive window: in an ordinary .py file, write a comment of the form # %% to mark a cell boundary, and VS Code will offer a "Run Cell" code lens above it. The code executes in a persistent kernel with its output shown in a side panel, so you get notebook-style iteration while your file remains a plain Python script that diffs cleanly in Git.

# %%
import pandas as pd
df = pd.read_csv("data/iris.csv")

# %%
df.describe()          # runs against the already-loaded df

# %%
df["species"].value_counts()

Linting and formatting extensions keep style consistent without argument. Black is an opinionated formatter: it rewrites your code to a canonical layout — line length, quote style, trailing commas, bracket placement — and offers almost no configuration, which is precisely the point. Ruff is an extremely fast linter (and now also a formatter) that implements the rules of Flake8, isort, pycodestyle, and many others; it catches unused imports, undefined names, shadowed built-ins, and mutable default arguments. Enable format-on-save so that correctness of style is never something you have to think about:

{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "charliermarsh.ruff",
  "editor.codeActionsOnSave": {
    "source.organizeImports": "explicit"
  }
}

Beyond aesthetics, consistent formatting has a concrete benefit for assessed work: when everyone's code is formatted the same way, Git diffs contain only meaningful changes rather than reflowed whitespace, and a marker reading your submission spends their attention on your algorithm rather than on your indentation.

PyCharm for larger, structured projects. PyCharm is a full IDE built specifically for Python, and its strengths appear as projects grow beyond a handful of files. Where VS Code is an editor that you extend into an IDE, PyCharm arrives as an IDE and indexes your entire project up front — which is why it is slower to start and heavier in memory, but also why it understands your code more deeply.

On opening a folder, PyCharm will detect an existing virtual environment in conventional locations such as .venv or venv and offer to use it; if none exists it can create one during the New Project dialog, choosing between venv, Conda, Pipenv, or Poetry. It also notices a requirements.txt in the project root and displays a banner offering to install any packages listed there but missing from the environment. Conversely, if you import a package that is installed but not listed in requirements.txt, PyCharm can flag it — a small guard against the classic situation where your code works on your machine and nowhere else.

PyCharm's refactoring tools operate on a semantic model of your code rather than on text. Rename (Shift+F6) on a class or method updates every reference across the project, including in docstrings and string literals if you ask it to, while correctly leaving alone an unrelated identifier of the same name in a different scope — something a find-and-replace cannot do. Extract Method takes a selected block, works out which local variables must become parameters and which must be returned, and creates the new function with a correct signature. Move relocates a class or function to another module and rewrites every import that referred to it. Consider a search module that has grown unwieldy:

class GraphSearch:
    def solve(self, problem):
        frontier = [(0, problem.initial)]
        explored = set()
        while frontier:
            cost, node = heapq.heappop(frontier)
            if problem.goal_test(node):
                return node
            explored.add(node)
            for action in problem.actions(node):
                child = problem.result(node, action)
                if child not in explored:
                    heapq.heappush(frontier, (cost + problem.step_cost(node, action), child))
        return None

Selecting the inner for loop and invoking Extract Method produces an _expand(self, problem, node, cost, frontier, explored) method with the right parameters, leaving solve readable. Doing the same by hand is where off-by-one parameter mistakes creep in.

The integrated test runner discovers tests automatically. Point PyCharm at pytest or unittest in the project settings and it will find every test_*.py file, display the test tree in a dedicated panel, and let you run a single test, a single class, or the whole suite with one click. Failures are shown with the assertion diff expanded, and a green gutter arrow appears beside each test function so you can re-run it from the source file. For algorithm work this is transformative: you write a small test asserting that uniform-cost search on a known graph returns a path of cost 11, then re-run it after every refactor to confirm you have not broken the behaviour.

def test_ucs_finds_cheapest_path():
    problem = RomaniaProblem(initial="Arad", goal="Bucharest")
    node = GraphSearch().solve(problem)
    assert node.path_cost == 418
    assert node.path() == ["Arad", "Sibiu", "Rimnicu Vilcea", "Pitesti", "Bucharest"]

PyCharm's visual debugger is particularly well suited to recursive code. When execution pauses inside a recursive call, the Frames panel shows the entire call stack — minimax at depth 1, depth 2, depth 3 — and clicking any frame shows the local variables as they were in that frame. For a recursive search you can literally watch the stack grow and unwind, and see which branch returned which value to its parent. The variable inspector renders nested structures as expandable trees, so a dictionary of lists of tuples can be explored without writing any printing code, and large collections are paginated rather than truncated. Conditional breakpoints — right-click a breakpoint and enter an expression such as depth == 4 and node.state == "E" — let you stop only at the moment of interest instead of pressing Continue two hundred times.

The cost of all this is weight. PyCharm takes noticeably longer to start, consumes more RAM, indexes the project before it is fully responsive, and insists on a project-level mental model. For a twelve-line script to check how itertools.product behaves, opening PyCharm is disproportionate; VS Code or even a terminal REPL is the right tool. A reasonable working rule is: PyCharm for the multi-file assignment with tests, VS Code for everything else.

Jupyter notebooks for interactive exploration. A Jupyter notebook is a document made of cells, executed by a background process called a kernel. The kernel is an ordinary Python interpreter that stays alive between cell executions, and this single fact explains the notebook's entire character. When you run a cell that assigns df = pd.read_csv("large_dataset.csv"), that DataFrame remains in memory. You can then run twenty subsequent cells that inspect, filter, group, and plot it without ever paying the loading cost again. The same applies to an expensive model fit: train once in one cell, then evaluate it, inspect its coefficients, and plot its predictions in separate cells over the following half hour.

# Cell 1 — slow, run once
import pandas as pd
from sklearn.ensemble import RandomForestClassifier
X_train, y_train = load_training_data()        # takes 40 seconds
model = RandomForestClassifier(n_estimators=500).fit(X_train, y_train)

# Cell 2 — fast, run many times
importances = pd.Series(model.feature_importances_, index=X_train.columns)
importances.sort_values(ascending=False).head(10)

Markdown cells let you write prose, headings, bullet lists, and LaTeX mathematics between code cells. This turns a notebook into a narrative document rather than a pile of code: you can state a hypothesis, show the code that tests it, display the result, and then interpret the result immediately beneath it. For report-style assessments this is exactly the structure a marker wants to read, and it is the reason notebooks are often the required submission format for analysis tasks. A heuristic admissibility argument, for example, can be written in a Markdown cell as $h(n) \le h^*(n)$ with surrounding explanation, directly above the code that empirically checks it on a sample of states.

Rich output rendering is the third pillar. A Matplotlib figure appears as an image beneath the cell that created it (enable this with %matplotlib inline, which is the default in modern Jupyter). A pandas DataFrame renders as an HTML table with styled headers rather than as monospaced text. A scikit-learn estimator displays as an interactive diagram of its pipeline steps. Because outputs are stored in the notebook file, a reader can see your results without re-running anything.

import matplotlib.pyplot as plt

fig, ax = plt.subplots(figsize=(6, 4))
ax.plot(depths, nodes_expanded, marker="o")
ax.set_xlabel("Search depth limit")
ax.set_ylabel("Nodes expanded")
ax.set_title("Iterative deepening cost growth")
plt.show()

The great danger of the live kernel is hidden state from out-of-order execution. Cells can be run in any order, any number of times, and the execution counter in the brackets beside each cell — [1], [7], [2] — records the order in which they actually ran, which may bear no relation to their order on the page. A variable may exist in the kernel because you defined it in a cell you have since edited or deleted. Consider this sequence: you write threshold = 0.5 in cell 3, run everything, then edit cell 3 to threshold = 0.8 but forget to re-run it before running cell 8. Cell 8 silently uses the old value. Worse, you might delete the cell that defined a helper function entirely; the function remains in the kernel's namespace, your notebook continues to work perfectly on your machine, and it fails immediately for anyone else.

The defence is simple and non-negotiable: before submitting or sharing any notebook, use Kernel → Restart Kernel and Run All Cells. This discards the entire namespace and executes every cell from the top in document order. If it completes without error and reproduces the outputs you expect, the notebook is genuinely reproducible. If it fails, you have just discovered a dependency on hidden state that your marker would otherwise have discovered for you. After a successful restart-and-run-all, the execution counters will read [1], [2], [3]… in order, which is itself a quick visual check that a reader can perform on your submitted file.

Choosing between notebooks and scripts. The decision is not about preference but about the nature of the artefact you are producing. Ask whether the code's primary purpose is to answer a question now or to be used again later.

  • Notebooks for data inspection. Checking column dtypes, finding missing values, looking at class balance, plotting feature distributions — all of this is a conversation with a dataset, and a conversation needs persistent memory and immediate visual feedback.
  • Notebooks for hyperparameter experiments. Trying five values of max_depth and comparing validation scores is naturally cell-by-cell work, and the resulting table or plot is the deliverable.
  • Notebooks for visual explanation of results. When the audience needs to see the reasoning as well as the answer, interleaved Markdown and output is the clearest medium available.
  • Scripts for reusable functions and classes. A Node class, an astar(problem, heuristic) function, a Problem abstract base class — these are library code. They belong in a .py module that both your notebook and your tests can import.
  • Scripts for command-line tools. Anything you want to launch with arguments (python run_search.py --algorithm astar --heuristic manhattan) needs an if __name__ == "__main__": block and argparse, which only make sense in a script.
  • Scripts for anything under unit test. pytest collects from .py files. Code that must be verified automatically must live where the test runner can import it.
  • Scripts for long-running or batch jobs. A training run of several hours should be launched from a terminal, ideally under nohup, screen, or tmux, so that it survives a closed laptop lid or a dropped SSH connection. A browser tab is not a reliable host for a long computation.

The version control argument deserves emphasis because it is the one students most often underestimate. A .py file is plain text, so git diff shows a human-readable change: three lines added, one line modified. A .ipynb file is JSON containing source, metadata, execution counts, and base64-encoded output images. Changing a single character in one cell and re-running the notebook can produce a diff of thousands of lines, most of it altered execution counters and re-encoded PNG data. Merge conflicts in notebook JSON are notoriously painful to resolve by hand because a mistake produces an invalid file that will not open at all. Mitigations exist — nbstripout as a Git filter to remove outputs before committing, or jupytext to pair each notebook with a synchronised .py representation — but the structural solution is to keep substantial logic in modules and let the notebook be a thin layer of calls and commentary:

# In the notebook
from search.algorithms import astar
from search.heuristics import manhattan
from problems.puzzle import EightPuzzle

problem = EightPuzzle(start=(1, 2, 3, 4, 5, 6, 7, 0, 8))
solution = astar(problem, manhattan)
print(f"Solved in {len(solution.path())} moves, {solution.nodes_expanded} nodes expanded")

This hybrid is the arrangement most working practitioners settle on. The algorithm is tested, refactorable, and diffable; the notebook is short, readable, and cheap to re-run.

Debugging and inspecting intermediate results. Printing works, but it scales badly: every question you want to ask requires editing the source, re-running, and then remembering to remove the print afterwards. A debugger lets you ask arbitrary questions at an arbitrary moment without changing the program at all, which is why it is worth the small investment required to learn the five keys that matter.

In both VS Code and PyCharm, a breakpoint is set by clicking in the gutter to the left of a line number; a red dot appears. Starting the program under the debugger (F5 in VS Code, the bug icon in PyCharm) runs normally until that line is about to execute, then pauses with the whole program state intact. From there the controls are:

  • Step Over (F10 / F8) — execute the current line, including any function it calls, and stop on the next line of the same function.
  • Step Into (F11 / F7) — if the current line calls a function you wrote, descend into it and stop at its first line.
  • Step Out (Shift+F11 / Shift+F8) — run the rest of the current function and stop immediately after it returns.
  • Continue (F5 / F9) — resume until the next breakpoint is hit.
  • Restart / Stop — begin again or abandon the session.

This is exactly the right instrument for watching a search frontier evolve. Place a breakpoint on the line that pops from the frontier in a best-first search, then press Continue repeatedly and watch the frontier and explored set change at each iteration:

import heapq

def best_first(problem, f):
    frontier = [(f(problem.initial), problem.initial)]
    explored = set()
    while frontier:
        priority, node = heapq.heappop(frontier)   # <-- breakpoint here
        if problem.goal_test(node):
            return node
        explored.add(node)
        for child in problem.expand(node):
            if child not in explored:
                heapq.heappush(frontier, (f(child), child))
    return None

Stopping on the heappop line each time round the loop answers questions that prints struggle with: Is the frontier ordered as I expect? Is the same state being pushed twice with different priorities? Does explored grow monotonically, or am I accidentally re-adding states? If the loop runs thousands of times before the interesting moment, attach a condition to the breakpoint — right-click it and enter something like node.state == "Bucharest" or len(explored) > 50 — so it only triggers when the condition holds. A hit count condition ("break on the 200th hit") serves the same purpose when you know roughly how deep the problem lies.

The variables pane shows every local and global name in the paused frame, with nested structures expandable: click the arrow beside frontier to see its elements, click into an element to see the tuple's contents, click into the node to see its parent chain. This is where the debugger decisively beats printing, because a print(frontier) of a hundred-element heap of custom objects produces an unreadable wall of <Node object at 0x7f3c...>, whereas the tree view lets you open only the parts you care about. Watch expressions go further: add an arbitrary expression such as len(frontier), sorted(p for p, _ in frontier)[:5], or problem.heuristic(node) and it will be re-evaluated and displayed every time execution pauses. Most debuggers also offer a debug console in which you can type and evaluate any Python expression in the paused frame — effectively a REPL positioned at the exact point of the bug.

Recursive code deserves special mention. When minimax calls itself, each invocation gets its own frame with its own copies of depth, alpha, beta, and best_value. The call stack panel lists these frames from the innermost outwards, and selecting a frame repopulates the variables pane with that frame's locals. Stepping out of a deep frame and watching the returned value propagate upwards makes the structure of recursion concrete in a way that no amount of reading does. It is also the fastest way to find the classic recursion bugs: a base case that never fires, a mutable default argument shared between calls, or a value that is computed but never returned.

Notebooks have weaker step-debugging support, but their cell structure substitutes for it. If a long function misbehaves, paste its body into a cell, define its arguments as ordinary variables above it, and run the statements in small groups so you can inspect every intermediate value directly:

# Instead of debugging preprocess(df) blindly, unroll it
df = pd.read_csv("data/raw.csv")
df = df.dropna(subset=["label"])
print(df.shape)                 # 4821 rows — expected ~5000, so 179 dropped

X = df.drop(columns=["label"])
print(X.dtypes)                 # 'age' is object, not int64 — found the bug

IPython also provides the %debug magic: run it in a fresh cell immediately after an exception and it opens a post-mortem pdb session at the point where the error was raised, letting you inspect the local variables that caused it. %pdb on makes this automatic for every subsequent exception. For shape errors in NumPy and pandas work, printing arr.shape, arr.dtype, and df.head() at each step remains the fastest diagnostic, because almost all such bugs are a mismatch between the shape you believe you have and the shape you actually have.

In any script, from any terminal and with no IDE at all, you can insert the built-in breakpoint() call. Since Python 3.7 this drops you into pdb at that line:

def astar(problem, h):
    frontier = [(h(problem.initial), problem.initial)]
    while frontier:
        priority, node = heapq.heappop(frontier)
        if priority > 1000:
            breakpoint()        # investigate the suspicious priority
        ...

Running the script normally produces a (Pdb) prompt where n steps to the next line, s steps into a call, c continues, l lists surrounding source, p expr prints an expression, pp expr pretty-prints it, w shows the call stack, u and d move up and down it, and q quits. Because breakpoint() consults the PYTHONBREAKPOINT environment variable, setting PYTHONBREAKPOINT=0 disables every such call without editing the code — useful when running a batch job that you forgot to clean up. It also means the same statement can be routed to a richer debugger such as ipdb by setting PYTHONBREAKPOINT=ipdb.set_trace.

Finally, for diagnostic output you intend to keep in submitted code, use the logging module rather than print. A logging call carries a severity level, so the same statements can be silenced in normal operation and switched on when you need them, without deleting or re-adding anything:

import logging

logger = logging.getLogger(__name__)

def astar(problem, h):
    frontier = [(h(problem.initial), problem.initial)]
    explored = set()
    while frontier:
        f_cost, node = heapq.heappop(frontier)
        logger.debug("Expanding %s with f=%.2f (frontier=%d, explored=%d)",
                     node.state, f_cost, len(frontier), len(explored))
        if problem.goal_test(node):
            logger.info("Goal reached after expanding %d nodes", len(explored))
            return node
        explored.add(node)
        ...

if __name__ == "__main__":
    logging.basicConfig(level=logging.DEBUG,
                        format="%(levelname)s %(name)s: %(message)s")

Changing the single level argument to logging.INFO suppresses every per-node message while keeping the summary, and logging.WARNING silences both. Note the %s style arguments: passing values to the logger rather than formatting the string yourself means the formatting cost is never paid when the message is filtered out, which matters inside a loop that runs a hundred thousand times. Levels run DEBUG < INFO < WARNING < ERROR < CRITICAL, and output can be redirected to a file with a single configuration change — all of which prints cannot do. A submission littered with commented-out print statements reads as unfinished; the same code with a clean logging configuration reads as professional.

Every AI project you write this term will be typed, run, and debugged inside some tool, and the tool you pick shapes how quickly you can test an idea or track down a bug. This topic introduces the three environments used in the course: Visual Studio Code as the default editor, PyCharm for larger and more structured projects, and Jupyter notebooks for interactive exploration. The goal is not to declare a winner but to help you recognize which workflow fits the task in front of you.

Notebooks are excellent when you want to load a dataset, plot something, and inspect intermediate results cell by cell. Scripts and modules are better when code must be reused, tested, version-controlled, and handed to someone else. Much of professional AI work moves back and forth between the two: explore in a notebook, then refactor the useful parts into clean Python files.

As you watch, pay attention to three things. First, the mechanics: how to create and run cells, select a Python interpreter or kernel, and view variables. Second, the debugging story: where breakpoints, the variable explorer, and step-through execution appear in each tool. Third, the trade-offs: note the specific problems that notebooks cause as a project grows, and think about how you would avoid them in your own assignments.
