Data Structures for Search and State Representation

▶

Search algorithms — breadth-first search, depth-first search, uniform-cost search, A*, bidirectional search, and the planning algorithms built on top of them — are deceptively simple on paper. A textbook pseudocode listing for A* is perhaps fifteen lines long. What separates an implementation that solves an 8-puzzle instance in 40 milliseconds from one that takes four minutes on the same instance is almost never the algorithm: it is the choice of container used for the frontier, the container used for the visited set, and the representation chosen for a state. Python gives you a small, well-engineered family of built-in collections whose asymptotic behaviour is documented and predictable. Learning which one to reach for, and why, is one of the highest-leverage skills in practical AI programming.

This topic works through that toolkit systematically. We begin with the four core built-in collections and the comprehension syntax that builds them, move to the stack and queue abstractions that determine whether a graph search behaves as DFS or BFS, then to heapq for informed search, then to the critical question of how to encode a state so that Python can hash and compare it, then to the extra containers in the collections module, and finally to a consolidated discussion of the performance trade-offs that actually show up in search code.

Core built-in collections: lists, tuples, sets, and dictionaries

A list is an ordered, mutable sequence backed by a dynamic array of pointers. Indexing is O(1), appending is amortised O(1), and the order of elements is exactly the order you put them in. In search code, lists are the natural representation for anything that is intrinsically sequential: the path from the root to a node, the sequence of actions in a plan, the list of successors returned by an expansion function, and — when you only ever push and pop at the right-hand end — a depth-first frontier.

path = ['Start']
path.append('A')
path.append('B')
print(path)          # ['Start', 'A', 'B']
print(path.pop())    # 'B'  -- O(1) from the end

A tuple is the immutable sibling of the list. Because it cannot change after construction, Python can compute a hash for it (provided every element is itself hashable), which means a tuple can be an element of a set or a key in a dictionary. This single property makes the tuple the default encoding for a state. A position on a grid is (row, col); a state in a vacuum world is ('A', 'clean', 'dirty'); a complete 8-puzzle board is a flat nine-element tuple. Tuples also compare lexicographically element by element, which we will exploit when building priority-queue entries.

state = (2, 3)
visited = set()
visited.add(state)
print((2, 3) in visited)   # True -- value equality, not identity

grid = [[1, 2], [3, 4]]
# grid cannot be hashed:
# visited.add(grid)  -> TypeError: unhashable type: 'list'
visited.add(tuple(tuple(row) for row in grid))   # fine

A set is an unordered collection of unique hashable items implemented as a hash table. Membership testing, insertion, and deletion are all O(1) on average. This is precisely the operation a graph search performs most often: "have I already expanded this state?" A visited (or closed) set must therefore be a set or a dictionary, never a list. Sets also support the algebraic operations — union, intersection, difference — which are useful when comparing the explored regions of two concurrent searches, or when checking in a planning problem whether a set of goal literals is a subset of the current state.

explored = set()
explored.add((0, 0))
explored |= {(0, 1), (1, 0)}          # union-update
frontier_states = {(1, 0), (2, 2)}
new_states = frontier_states - explored   # {(2, 2)}

A dictionary maps hashable keys to arbitrary values, again with average O(1) lookup, insertion, and deletion. Dictionaries carry three distinct responsibilities in search code:

  • Cost tables. g_score[state] stores the cheapest known cost from the start to a state, so that uniform-cost search and A* can decide whether a newly discovered path is an improvement.
  • Parent pointers. came_from[child] = parent lets you reconstruct the solution path by walking backwards from the goal, which avoids storing a full path list in every frontier node and therefore saves a great deal of memory.
  • Adjacency lists. graph[node] = [neighbour, ...] is the standard representation of a sparse graph; it uses O(V + E) memory instead of the O(V²) of an adjacency matrix.
graph = {
    'Arad':      ['Zerind', 'Sibiu', 'Timisoara'],
    'Zerind':    ['Arad', 'Oradea'],
    'Sibiu':     ['Arad', 'Oradea', 'Fagaras', 'Rimnicu'],
}

def reconstruct(came_from, goal):
    path = [goal]
    while path[-1] in came_from:
        path.append(came_from[path[-1]])
    path.reverse()
    return path

A dictionary can also serve as a visited set with extra information attached: explored[state] = best_cost gives you membership testing and the stored cost in one lookup, which is why A* implementations usually keep a g_score dict rather than a separate closed set.

Comprehensions provide a compact, fast way to build all four of these containers. A list comprehension generates successors; a dict comprehension builds a lookup table; a set comprehension deduplicates in one pass. Comprehensions run in a dedicated bytecode loop and are typically faster than an equivalent explicit loop with .append(), and — more importantly for readability — they state the construction rule declaratively.

def successors(pos, walls, width, height):
    r, c = pos
    moves = [(-1, 0), (1, 0), (0, -1), (0, 1)]
    return [(r + dr, c + dc) for dr, dc in moves
            if 0 <= r + dr < height
            and 0 <= c + dc < width
            and (r + dr, c + dc) not in walls]

# dict comprehension: straight-line heuristic for every city
h = {city: euclidean(coords[city], coords['Bucharest']) for city in coords}

# set comprehension: all states reachable in one step from any frontier node
fringe_next = {s for node in frontier for s in successors(node, walls, w, hgt)}

Stacks and queues for frontier management

The single structural difference between depth-first and breadth-first search is the discipline used to remove nodes from the frontier. The rest of the algorithm — expand a node, generate successors, skip those already seen — is identical. This is worth stating explicitly, because it means you can write one generic graph_search(problem, frontier) routine and obtain different algorithms purely by passing a different container.

A stack is last-in-first-out. The most recently discovered node is the next one expanded, so the search plunges as deep as it can before backtracking: that is depth-first search. A plain Python list is an excellent stack, because append() and pop() both operate at the end of the underlying array in amortised O(1) time.

def dfs(start, goal, succ):
    frontier = [start]            # list used as a LIFO stack
    explored = set()
    came_from = {}
    while frontier:
        node = frontier.pop()     # O(1): removes the last element
        if node == goal:
            return reconstruct(came_from, goal)
        if node in explored:
            continue
        explored.add(node)
        for child in succ(node):
            if child not in explored:
                came_from.setdefault(child, node)
                frontier.append(child)
    return None

A queue is first-in-first-out. The oldest node is expanded next, so the search sweeps outward layer by layer and finds the shallowest goal: that is breadth-first search, which is complete and, for unit step costs, optimal. The temptation is to reuse a list and write frontier.pop(0). Resist it. Removing the first element of a list requires shifting every remaining element one position to the left, which is O(n) per operation. A BFS that expands 100 000 nodes therefore performs on the order of 1010 pointer moves in the worst case purely on queue maintenance — the algorithm is correct but unusably slow, and the slowdown grows quadratically rather than showing up on small test cases.

The correct container is collections.deque, a doubly linked list of fixed-size blocks. Appends and pops at both ends are O(1), so it serves equally well as a queue (append / popleft) or as a stack (append / pop).

from collections import deque

def bfs(start, goal, succ):
    frontier = deque([start])     # FIFO queue
    explored = {start}            # mark on generation, not on expansion
    came_from = {}
    while frontier:
        node = frontier.popleft() # O(1)
        if node == goal:
            return reconstruct(came_from, goal)
        for child in succ(node):
            if child not in explored:
                explored.add(child)
                came_from[child] = node
                frontier.append(child)
    return None

Note the small but important detail in the BFS above: children are added to explored at the moment they are generated, not when they are expanded. For BFS this is safe (the first time a state is reached is via a shortest path) and it prevents the frontier from filling with duplicates.

Bidirectional search exploits the fact that a breadth-first tree of depth d with branching factor b contains roughly bd nodes, whereas two trees of depth d/2 contain only 2·bd/2 — an enormous saving. It is implemented with two deques and two parent dictionaries, one pair expanding forwards from the start and one pair expanding backwards from the goal, alternating one layer at a time and stopping when the two explored sets intersect.

def bidirectional_bfs(start, goal, succ, pred):
    if start == goal:
        return [start]
    f_frontier, b_frontier = deque([start]), deque([goal])
    f_parent, b_parent = {start: None}, {goal: None}
    while f_frontier and b_frontier:
        # expand the smaller frontier to keep the two trees balanced
        if len(f_frontier) <= len(b_frontier):
            node = f_frontier.popleft()
            for child in succ(node):
                if child in b_parent:
                    return join(f_parent, b_parent, node, child)
                if child not in f_parent:
                    f_parent[child] = node
                    f_frontier.append(child)
        else:
            node = b_frontier.popleft()
            for parent_state in pred(node):
                if parent_state in f_parent:
                    return join(f_parent, b_parent, parent_state, node)
                if parent_state not in b_parent:
                    b_parent[parent_state] = node
                    b_frontier.append(parent_state)
    return None

Priority queues with heapq for informed search

Uniform-cost search, greedy best-first search, and A* all require the frontier to deliver the node with the smallest priority value — path cost g, heuristic h, or their sum f = g + h. Scanning a list for the minimum is O(n) per pop; a binary min-heap does it in O(log n). Python's heapq module implements such a heap directly on top of an ordinary list, maintaining the invariant heap[k] <= heap[2*k+1] and heap[k] <= heap[2*k+2]. The smallest element is therefore always at heap[0], readable in O(1), while heappush and heappop each cost O(log n).

import heapq

frontier = []
heapq.heappush(frontier, (7.5, 'Sibiu'))
heapq.heappush(frontier, (3.0, 'Arad'))
heapq.heappush(frontier, (9.1, 'Fagaras'))
print(frontier[0])            # (3.0, 'Arad') -- peek, O(1)
print(heapq.heappop(frontier))# (3.0, 'Arad') -- O(log n)

Entries are normally tuples whose first element is the priority, because tuples compare lexicographically: Python compares the first elements, and only if they are equal does it move on to the second. That gives you the right ordering for free — but it also creates a trap. If two nodes have identical f-values, Python will try to compare the second elements, and if those are custom state objects without an ordering defined, you get TypeError: '<' not supported between instances of 'Node' and 'Node'. The idiomatic fix is to insert a monotonically increasing counter as a tie-breaker, so the comparison never reaches the payload:

import heapq
from itertools import count

counter = count()             # 0, 1, 2, ... never repeats

def push(frontier, priority, node):
    heapq.heappush(frontier, (priority, next(counter), node))

frontier = []
push(frontier, 12.0, node_a)
push(frontier, 12.0, node_b)  # same f-value: tie broken by counter, FIFO order
priority, _, node = heapq.heappop(frontier)

A side benefit is determinism: with the counter in place, ties are broken in insertion order, so repeated runs expand nodes in the same sequence and your unit tests are reproducible. Some implementations prefer a tie-break on higher g (push -g as the second element) so that, among equal f-values, deeper nodes nearer the goal are preferred.

heapq deliberately omits a decrease-key operation. If A* later discovers a cheaper route to a state already in the frontier, there is no supported way to locate and lower that entry's priority — the heap does not index its contents. Two workarounds exist; the standard one is lazy deletion: push a second, better entry for the same state, and on popping, discard any entry whose recorded cost is worse than the best currently known.

def astar(start, goal_test, succ, h):
    counter = count()
    g = {start: 0}
    came_from = {}
    frontier = [(h(start), next(counter), start)]
    closed = set()
    while frontier:
        f, _, node = heapq.heappop(frontier)
        if node in closed:          # stale duplicate -- skip it
            continue
        if goal_test(node):
            return reconstruct(came_from, node), g[node]
        closed.add(node)
        for child, step_cost in succ(node):
            tentative = g[node] + step_cost
            if tentative < g.get(child, float('inf')):
                g[child] = tentative
                came_from[child] = node
                heapq.heappush(frontier, (tentative + h(child), next(counter), child))
    return None, float('inf')

Lazy deletion lets the heap grow larger than the number of distinct frontier states, but each stale entry costs only O(log n) to push and O(1) to recognise and skip on pop, and the memory overhead is usually far smaller than the cost of maintaining an index-into-heap dictionary. The alternative — an explicit entry_finder dict that marks superseded entries as REMOVED — is documented in the heapq module itself and is worth knowing, but lazy deletion is simpler and adequate for coursework-scale problems.

Finally, avoid queue.PriorityQueue in single-threaded search code. It is a thin wrapper around heapq that adds a mutex and condition variables so that multiple threads can share the queue safely. Every put and get acquires and releases locks you do not need, typically costing a factor of two or more in throughput, and its blocking get() semantics can hang a search that has emptied its frontier. Use heapq on a plain list.

Encoding states so they can be hashed and compared

Everything above depends on one requirement: a state must be hashable to live in a set or serve as a dictionary key, and hashability in Python requires immutability (more precisely, it requires that the object's hash never changes and that equal objects hash equally). Only immutable built-ins qualify out of the box: numbers, strings, bytes, tuples of hashable elements, and frozenset. Lists, dictionaries, sets, and ordinary mutable class instances with a custom __eq__ do not.

The practical consequence is that mutable working representations must be converted before storage. A grid held as a list of lists becomes a tuple of tuples; or, more compactly, it is flattened into a single tuple or encoded as a string.

board = [[1, 2, 3],
         [4, 0, 5],
         [6, 7, 8]]

key_nested = tuple(tuple(row) for row in board)   # ((1,2,3),(4,0,5),(6,7,8))
key_flat   = tuple(x for row in board for x in row)  # (1,2,3,4,0,5,6,7,8)
key_string = ''.join(str(x) for row in board for x in row)  # '123405678'

All three are hashable. The flat tuple is usually the best compromise: it is compact, fast to hash, and trivially convertible back to a grid with slicing. The string form is the most memory-efficient of all for small alphabets and is attractive when you must store tens of millions of states, at the cost of slightly clumsier successor generation.

When the state is genuinely an unordered collection — the set of propositions true in a STRIPS planning state, the set of goals already satisfied, the set of nodes visited in a tour where order is irrelevant — use frozenset. It hashes in a way that ignores insertion order, so frozenset({'a','b'}) == frozenset({'b','a'}) and the two share a hash value, which is exactly the semantics you want.

state = frozenset({'at(robot, room1)', 'holding(key)'})
goal  = frozenset({'holding(key)'})
achieved = goal <= state      # subset test, True
new_state = (state - {'at(robot, room1)'}) | {'at(robot, room2)'}  # still a frozenset

Canonicalisation goes one step further. Two different encodings may describe the same situation; if you do not normalise them, the search will treat them as distinct and expand the same configuration repeatedly, inflating the search tree. The remedy is to map every equivalence class to one chosen representative — typically by sorting, or by taking the lexicographically smallest image under the problem's symmetry group.

def canonical_assignment(assignment: dict) -> tuple:
    # order of variable assignment is irrelevant to the state
    return tuple(sorted(assignment.items()))

def canonical_board(board: tuple) -> tuple:
    # an N-queens / grid puzzle invariant under reflection
    return min(board, reflect(board))

In the missionaries-and-cannibals problem the individuals are interchangeable, so a state is just counts; in a graph-colouring problem the colour names are interchangeable, so renaming colours to first-use order collapses a factorial number of duplicates. The saving can be dramatic — often an order of magnitude fewer expansions.

If you prefer a class to a bare tuple, you must make the class behave like an immutable value. Define __eq__ and __hash__ together and consistently: objects that compare equal must have equal hashes, or they will be stored twice in the same set and your visited check will silently fail. Note also that defining __eq__ on a class sets __hash__ to None unless you define it explicitly. The least error-prone routes are a frozen dataclass or a NamedTuple, both of which generate correct __eq__ and __hash__ for you.

from dataclasses import dataclass
from typing import NamedTuple

@dataclass(frozen=True, order=True)
class GridState:
    row: int
    col: int
    carrying: bool = False

class PuzzleState(NamedTuple):
    tiles: tuple
    blank: int

a = GridState(2, 3)
b = GridState(2, 3)
print(a == b, hash(a) == hash(b), {a, b})   # True True {GridState(row=2, col=3, carrying=False)}

Writing it by hand is perfectly acceptable provided the two methods agree, and it is worth doing once to understand what the decorators generate:

class State:
    __slots__ = ('tiles',)          # saves memory: no per-instance __dict__
    def __init__(self, tiles):
        object.__setattr__(self, 'tiles', tuple(tiles))
    def __eq__(self, other):
        return isinstance(other, State) and self.tiles == other.tiles
    def __hash__(self):
        return hash(self.tiles)     # derived from the same data as __eq__

The collections module toolkit

The standard library's collections module supplies specialised containers that remove boilerplate and, in several cases, change the asymptotic cost of an operation.

deque has already appeared as the BFS frontier. Its second use is the fixed-length history buffer: constructing it with maxlen makes it a sliding window that discards from the opposite end automatically. That is useful for cycle detection over the last k moves in local search, for tracking a rolling window of heuristic values in simulated annealing, or for keeping the most recent episodes in a reinforcement-learning replay buffer.

from collections import deque

history = deque(maxlen=3)
for move in ['up', 'left', 'down', 'right']:
    history.append(move)
print(history)      # deque(['left', 'down', 'right'], maxlen=3)

# cheap tabu check: have we just undone our last move?
if history and history[-1] == opposite(candidate):
    continue

defaultdict takes a zero-argument factory and calls it automatically whenever a missing key is read, which removes the repetitive "check whether the key exists, create an empty container if not" idiom that clutters graph-building code. defaultdict(list) builds adjacency lists; defaultdict(set) builds adjacency sets with automatic deduplication; defaultdict(int) gives a counter; defaultdict(lambda: float('inf')) gives a cost table whose default is "unreachable", which is exactly what uniform-cost search and A* want.

from collections import defaultdict

edges = [('Arad', 'Zerind', 75), ('Arad', 'Sibiu', 140), ('Zerind', 'Oradea', 71)]

graph = defaultdict(list)
for u, v, cost in edges:
    graph[u].append((v, cost))      # no 'if u not in graph' needed
    graph[v].append((u, cost))      # undirected

g_score = defaultdict(lambda: float('inf'))
g_score[start] = 0
if tentative < g_score[child]:       # no KeyError, no .get() with a default
    g_score[child] = tentative

One caution: because reading a missing key inserts it, a defaultdict silently grows when you merely test it. If you need a pure membership test on a defaultdict, use key in d rather than d[key].

Counter is a dictionary subclass specialised for tallying. It accepts any iterable and counts its elements, returns 0 rather than raising for missing keys, and supports most_common(n), addition, and subtraction. In AI code it appears in three recurring roles: computing frequency features for naive Bayes or bag-of-words models; collecting diagnostics such as how many nodes were expanded at each depth or how many times each action was selected; and implementing the misplaced-tile family of heuristics or any comparison of multisets.

from collections import Counter

expansions_by_depth = Counter()
expansions_by_depth[depth] += 1          # no initialisation required
print(expansions_by_depth.most_common(3))

words = Counter("the cat sat on the mat".split())
print(words['the'], words['dog'])        # 2 0  -- missing keys are 0, not an error

# multiset difference: which tiles are still misplaced?
remaining = Counter(current_hand) - Counter(required_hand)

namedtuple (and its typed sibling typing.NamedTuple) creates a lightweight immutable record class. Instances are real tuples: they are hashable, comparable, unpackable, and consume essentially the same memory as a plain tuple, yet their fields can be read by name. The canonical search node is exactly this shape.

from collections import namedtuple

Node = namedtuple('Node', ['state', 'parent', 'action', 'path_cost'])

root  = Node(state=(0, 0), parent=None, action=None, path_cost=0)
child = Node(state=(0, 1), parent=root, action='right', path_cost=1)

print(child.action, child.path_cost)     # right 1
print(child[0])                          # (0, 1) -- still indexable
deeper = child._replace(path_cost=2)     # returns a new node; originals unchanged

Because Node is a tuple, two nodes compare field by field — which is why you should still use an explicit counter in heap entries rather than relying on nodes to break ties, and why a parent chain of nodes should normally be keyed in dictionaries by node.state, not by the node itself.

OrderedDict preserves insertion order and, unlike a plain dict, treats order as significant in equality comparisons; it also offers move_to_end() and a popitem(last=False) that make a textbook LRU cache a few lines long — handy for memoising expensive heuristic evaluations. Since Python 3.7 ordinary dictionaries also guarantee insertion order, so most code no longer needs OrderedDict; what matters for us is the guarantee itself. Deterministic iteration order means that a search which iterates over graph[node] or over a dict of successors will expand nodes in the same sequence on every run, so expansion counts and returned paths are reproducible and can be asserted in unit tests. Sets, by contrast, iterate in an order determined by hash values, and string hashing is randomised per process unless PYTHONHASHSEED is fixed — so never iterate a set when deterministic output matters; sort it or iterate a dict instead.

from collections import OrderedDict

class HeuristicCache:
    def __init__(self, capacity=100_000):
        self.capacity = capacity
        self.data = OrderedDict()
    def get(self, state, compute):
        if state in self.data:
            self.data.move_to_end(state)        # mark as recently used
            return self.data[state]
        value = compute(state)
        self.data[state] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)       # evict least recently used
        return value

Performance trade-offs that matter in search

The decisions above are only worth making because the costs differ by orders of magnitude at the scales search algorithms reach. The table below summarises the operations that dominate a typical graph search.

Operation list deque set / dict heapq on a list
Membership test (x in c) O(n) O(n) O(1) average O(n)
Append / push at the right end O(1) amortised O(1) O(1) average (add) O(log n)
Pop from the right end O(1) O(1) — —
Insert / pop at the left end O(n) O(1) — —
Extract minimum O(n) scan O(n) scan O(n) scan O(log n)
Peek at minimum O(n) O(n) O(n) O(1)
Indexing by position O(1) O(n) in the middle — O(1)

Three practical rules follow. First, closed sets must be sets or dictionaries. A list-based visited check turns an O(N) search into an O(N²) one: with 200 000 expansions, the list version performs about 2·1010 comparisons against roughly 2·105 hash lookups for the set version. This is the single most common performance bug in student search code, and it is invisible on a 10-node test graph.

Second, use the right end of the right container. Lists are optimised for the tail; append and pop() are amortised O(1) because the underlying array over-allocates, but insert(0, x) and pop(0) must memmove every remaining pointer. A deque pays a slightly higher constant factor per operation and loses O(1) random access in the middle, but it never degrades at the ends. Use a list for a DFS stack and a path, a deque for a BFS queue or a sliding window.

Third, do not use a heap where a dictionary will do. Heap operations are O(log n) with a non-trivial constant: each push and pop performs up to log2 n tuple comparisons, and tuple comparison is itself several interpreter operations. That is a fine price for ordered extraction from the frontier, but it is far more expensive than the O(1) dictionary lookup used to read or update g_score. Keep the two jobs separate: the heap orders the frontier, the dictionary remembers the costs.

Memory is the other half of the story, and in search it is often the binding constraint — breadth-first search on a problem with branching factor 10 and depth 8 must hold 108 states. Compactness therefore matters enormously. A tuple of three small integers occupies roughly 70–80 bytes plus the (usually shared and cached) integers themselves; the equivalent list occupies more because it over-allocates its array and carries a mutable header; a plain class instance adds a per-instance __dict__ of several hundred bytes unless you declare __slots__. Across ten million states the difference between a flat tuple and an ordinary object is measured in gigabytes.

import sys
print(sys.getsizeof((1, 2, 3)))        # ~64-80 bytes
print(sys.getsizeof([1, 2, 3]))        # larger, and over-allocates on append
print(sys.getsizeof('123405678'))      # compact for small alphabets

Practical memory tactics: store parent pointers in a dictionary instead of carrying a full path list inside every frontier node; store state keys (tuples or strings) rather than rich objects in the closed set; use __slots__ on node classes; and consider array, bytes, or NumPy arrays when states are large fixed-size numeric vectors.

Finally, measure before optimising. Asymptotic analysis tells you which container cannot work; it does not tell you where the time actually goes. In a great many search programs the dominant cost is not the frontier at all but successor generation — the legality checks, the tuple rebuilding, and above all the heuristic function, which may be called once per generated node. Use timeit for micro-comparisons of container operations and cProfile for whole-program attribution.

import timeit
setup = "from collections import deque; d = deque(range(100000)); l = list(range(100000))"
print(timeit.timeit("d.popleft(); d.append(0)", setup=setup, number=100000))
print(timeit.timeit("l.pop(0);   l.append(0)", setup=setup, number=100000))

import cProfile, pstats
cProfile.run('astar(start, goal_test, successors, manhattan)', 'stats.out')
pstats.Stats('stats.out').sort_stats('cumulative').print_stats(10)

A typical profile of an 8-puzzle A* implementation shows something like 45% of the time in the heuristic, 25% in successor generation, 15% in hashing tuples for set and dict operations, and under 10% in heappush/heappop. That tells you to memoise or simplify the heuristic before you start hand-tuning the heap — which is precisely the lesson: choose containers with the right asymptotics as a matter of routine, then let the profiler decide where further effort goes.
