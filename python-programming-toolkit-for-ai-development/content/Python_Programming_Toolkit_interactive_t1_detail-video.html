Setting Up the Python Development Environment

▶

Every piece of code you write for this module — search algorithms, constraint solvers, classifiers, notebooks full of plots — depends on a chain of invisible assumptions: that a Python interpreter of the right version exists on your machine, that it can be reached from the command line, that the libraries your code imports are installed for that specific interpreter, and that a marker can reproduce the same conditions on a completely different computer. When any link in that chain breaks, the symptom is rarely a clear error message. It is more often a confusing one: ModuleNotFoundError: No module named 'sklearn' on a machine where you distinctly remember installing scikit-learn, or code that runs perfectly in your editor and fails in the terminal. Setting up the development environment carefully at the start is not administrative overhead; it is the single highest-leverage hour you will spend in the module, because it removes an entire category of problems that would otherwise masquerade as bugs in your algorithms.

The sections below move through the full lifecycle: installing an interpreter, proving it works, isolating each project in its own environment, installing packages into that environment, freezing the result so it can be rebuilt, and diagnosing the handful of failures that account for the overwhelming majority of setup problems.

Installing Python 3

There are three mainstream routes to a working Python 3 interpreter, and the right choice depends mostly on your operating system and whether you expect to lean heavily on compiled scientific packages.

  • The official installer from python.org. This is the reference distribution, maintained by the Python Software Foundation. You download a .exe for Windows or a .pkg for macOS, run it, and you have a clean, predictable interpreter plus pip and the standard library. It is the best default for Windows users and for anyone who wants the newest stable release.
  • A system package manager. On macOS, Homebrew gives you brew install python@3.11. On Debian or Ubuntu, sudo apt install python3 python3-venv python3-pip does the equivalent. Note the explicit python3-venv package on Debian-family systems: the virtual environment module is split out into a separate package there, and omitting it produces a baffling error later when you try to create an environment.
  • Anaconda or Miniconda. These distributions bundle Python with the conda tool and, in Anaconda's case, several hundred pre-built scientific packages. The decisive advantage is that conda ships pre-compiled binaries including the non-Python dependencies (BLAS/LAPACK linear algebra libraries, compilers, CUDA toolkits), which sidesteps the build failures that sometimes afflict NumPy, SciPy, or specialised libraries on machines without a C/C++ toolchain. Miniconda is the slim version: the same tool, without the preinstalled package set, letting you install only what you need.

On Windows, the installer presents a checkbox labelled "Add Python to PATH" on its first screen, and it is unticked by default. Tick it. PATH is the environment variable holding the list of directories the shell searches when you type a bare command name. If Python's directory is not on that list, then typing python in PowerShell or Command Prompt produces 'python' is not recognized as an internal or external command — the single most common first-day failure. If you have already installed without ticking it, you do not need to uninstall: re-run the installer, choose Modify, and enable the option, or add the paths manually through System Properties → Environment Variables (you need both the install directory and its Scripts subdirectory).

One rule deserves emphasis: do not build your coursework on the system Python. macOS ships a Python that exists to support Apple's own tooling; many Linux distributions use Python for core administrative utilities such as the package manager itself. If you install, upgrade, or remove packages in that interpreter, you can silently break operating system components — there are well-documented cases of users rendering apt unusable by upgrading a dependency it relied on. Treat the system interpreter as read-only infrastructure. Install your own, and do your work there.

Verifying the Installation

Never assume an install worked. Four quick checks confirm that the interpreter exists, that the package installer is attached to it, that the interpreter actually executes code, and that the right interpreter wins when several are present.

$ python3 --version
Python 3.11.9

$ python3 -m pip --version
pip 24.0 from /usr/local/lib/python3.11/site-packages/pip (python 3.11)

Read the pip --version output carefully — it is more informative than it looks. It tells you not only the pip version but which interpreter's site-packages directory it will install into, and it repeats the Python version in parentheses. If that trailing version does not match what python3 --version reported, you have two installations fighting, and anything you install with bare pip will land in the wrong place.

Next, prove that the interpreter runs code by launching the REPL (read–eval–print loop):

$ python3
Python 3.11.9 (main, Apr  2 2024, 08:25:04) [Clang 15.0.0] on darwin
Type "help", "copyright", "credits" or "license" for more information.
>>> print(2 + 2)
4
>>> import sys; sys.executable
'/usr/local/bin/python3.11'
>>> exit()

sys.executable is worth remembering: it prints the absolute path of the interpreter currently running, which is the definitive answer to "which Python am I actually using?" It is far more reliable than inference, because it is reported by the running process itself.

When several Pythons are installed — a system one, a Homebrew one, a conda one — you need to know which the shell resolves first:

# Windows (PowerShell / cmd)
where python

# macOS / Linux
which -a python3
# /Users/you/miniconda3/bin/python3
# /usr/local/bin/python3
# /usr/bin/python3

The -a flag lists all matches in PATH order; the first line wins. On Windows, Python also installs a launcher, py, which lets you select a version explicitly: py -3.11 --version. On many macOS and Linux systems the bare name python may not exist at all, or may point at a legacy Python 2; python3 is the safe spelling outside an activated virtual environment.

Creating Isolated Virtual Environments

A virtual environment is a self-contained directory holding its own interpreter link, its own site-packages folder, and its own scripts directory. Anything you install while it is active goes into that directory and is visible only to code run with that environment. This solves two problems at once. First, it keeps your base interpreter clean so you never risk the operating system. Second, it allows different projects to hold mutually incompatible dependency versions — the AI coursework pinned to one NumPy release, a different project pinned to another — without either breaking.

Create one inside your project folder:

$ cd ~/projects/ai-coursework
$ python3 -m venv ai-course-env

Note the -m venv form: you are asking a specific interpreter to build an environment based on itself, which removes all ambiguity about which Python version the environment will contain. Activation then alters your shell's PATH so that the environment's directory comes first:

# macOS / Linux (bash, zsh)
$ source ai-course-env/bin/activate

# Windows PowerShell
PS> ai-course-env\Scripts\Activate.ps1

# Windows Command Prompt
C:\> ai-course-env\Scripts\activate.bat

Success is visible: your prompt gains a prefix such as (ai-course-env). Confirm with the same diagnostics as before, and you should now see paths inside the environment:

(ai-course-env) $ which python
/Users/you/projects/ai-coursework/ai-course-env/bin/python
(ai-course-env) $ python -c "import sys; print(sys.prefix)"
/Users/you/projects/ai-coursework/ai-course-env

Inside an active environment, plain python and plain pip are now unambiguous and safe. When you are finished, type deactivate to restore your original PATH. Activation is per-terminal-session: opening a new terminal tab means activating again, and this is the root cause of a great many "but I installed it!" moments.

If PowerShell refuses to run the activation script with an execution-policy error, the fix is to permit locally created scripts for your user account:

PS> Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

The environment directory is a build artefact, not source code. It can contain hundreds of megabytes of binaries compiled for your operating system and CPU, which would be useless — and possibly broken — on anyone else's machine. It must never be committed. Add a .gitignore at the repository root:

# .gitignore
ai-course-env/
.venv/
__pycache__/
*.pyc
.ipynb_checkpoints/

The conda workflow is parallel but differs in one important respect: conda environments are stored centrally (under your conda installation) rather than inside the project, are referenced by name, and can install a different version of Python itself:

$ conda create -n ai-course python=3.11
$ conda activate ai-course
(ai-course) $ conda deactivate
$ conda env list        # show all environments; * marks the active one

That last capability is the clearest advantage of conda over venv: venv can only clone the interpreter that created it, whereas conda can fetch and install any supported Python release on demand.

Managing Packages with pip and conda

With the environment active, install the scientific stack this module relies on:

(ai-course-env) $ python -m pip install --upgrade pip
(ai-course-env) $ python -m pip install numpy scipy scikit-learn matplotlib jupyter pandas

pip resolves each requested package together with its transitive dependencies, so the list above pulls in considerably more than six distributions — scikit-learn requires NumPy, SciPy, joblib and threadpoolctl; Jupyter drags in a whole constellation of server, kernel and messaging packages. Inspect the result:

(ai-course-env) $ pip list
Package         Version
--------------- -------
joblib          1.4.2
matplotlib      3.8.4
numpy           1.26.4
pandas          2.2.2
scikit-learn    1.4.2
scipy           1.13.0
threadpoolctl   3.5.0
...

(ai-course-env) $ pip show scikit-learn
Name: scikit-learn
Version: 1.4.2
Location: /Users/you/projects/ai-coursework/ai-course-env/lib/python3.11/site-packages
Requires: joblib, numpy, scipy, threadpoolctl
Required-by:

pip show is the diagnostic to reach for when something behaves unexpectedly: the Location line proves whether the package landed inside your environment or somewhere else entirely, and Requires/Required-by reveal the dependency relationships that explain why removing one package may break another. A related command, pip check, scans the environment for unsatisfied or conflicting requirements and reports them.

Note the import names do not always match the install names. You install scikit-learn but write import sklearn; you install pillow but write import PIL; you install opencv-python but write import cv2. Running pip install sklearn is a classic error — it fetches a deprecated placeholder package, not the real library.

Inside an Anaconda or Miniconda installation, prefer conda's own installer, drawing from the community-maintained conda-forge channel, which is broader and more current than the default channel:

(ai-course) $ conda install -c conda-forge scikit-learn matplotlib jupyter pandas

The ordering rule matters. pip and conda maintain separate pictures of what is installed. conda records its packages in its own metadata; pip records its own in site-packages. Neither fully understands the other's bookkeeping. If you conda-install SciPy and then pip-install a package that silently upgrades NumPy underneath it, conda's dependency graph becomes stale and you can end up with a binary-incompatible pair that raises obscure errors at import time (the notorious "numpy.dtype size changed" style of message). The practical discipline is:

  • Decide per environment whether it is a conda environment or a pip environment, and stick to it.
  • In a conda environment, install everything conda can provide with conda first, in as few commands as possible so the solver sees all constraints at once.
  • Only then use pip, and only for packages conda genuinely lacks.
  • After that point, avoid going back to conda for installs in that environment — if you need to change things substantially, it is cleaner and faster to delete the environment (conda env remove -n ai-course) and rebuild it from a specification file.

Reproducibility with Requirements Files

"It works on my machine" is not a defence when a marker cannot run your submission. A requirements file is the written contract describing exactly what your code needs. Capture the active environment:

(ai-course-env) $ pip freeze > requirements.txt
(ai-course-env) $ cat requirements.txt
contourpy==1.2.1
cycler==0.12.1
joblib==1.4.2
matplotlib==3.8.4
numpy==1.26.4
pandas==2.2.2
scikit-learn==1.4.2
scipy==1.13.0
threadpoolctl==3.5.0

The crucial detail is the == operator: pip freeze pins every package to the exact version currently installed, including transitive dependencies you never asked for directly. That is what makes the file reproducible. Anyone — a teammate, a marker, a continuous-integration server, or you six months from now on a new laptop — can recreate the environment:

$ python3 -m venv ai-course-env
$ source ai-course-env/bin/activate
(ai-course-env) $ python -m pip install -r requirements.txt

This matters in AI work more than in most programming because numerical results are version-sensitive. A change in scikit-learn's default solver, a new random-number stream, or a different tie-breaking rule can shift accuracy figures between releases. Pinning versions means the numbers in your report can be regenerated by whoever reads it.

A useful refinement is to keep two files: a short hand-written requirements.in listing only your direct, top-level dependencies (readable by humans, easy to update), and the machine-generated requirements.txt with the full pinned closure. Tools such as pip-compile generate the latter from the former, but even maintaining both by hand clarifies intent.

Conda's equivalent captures the Python version and non-Python binaries too:

(ai-course) $ conda env export > environment.yml
$ conda env create -f environment.yml

A caveat: a raw conda env export includes platform-specific build strings, so a file exported on macOS may fail to solve on Linux. For a portable file, use conda env export --from-history, which records only the packages you explicitly requested.

Commit the requirements file (and your .gitignore) to your repository; do not commit the environment directory itself. The combination of pinned requirements file plus ignored environment directory is the standard, expected shape of a Python project repository, and it is what makes an assignment submission self-documenting.

Troubleshooting Common Setup Issues

Almost every setup failure you will meet is one of five patterns. Learning to recognise the symptom and map it to the cause saves hours.

  • 'python' is not recognized... / command not found: python. The interpreter is installed but not on PATH. On Windows, re-run the installer, choose Modify, and enable "Add Python to PATH" — or add the install directory and its Scripts subfolder manually via Environment Variables, then open a new terminal (PATH changes do not affect already-open shells). In the meantime, py --version often works because the launcher is installed separately. On macOS/Linux, try python3 rather than python; the unversioned name frequently does not exist.
  • ModuleNotFoundError: No module named 'sklearn' immediately after a successful install. The install succeeded — just not for the interpreter you are now running. Either you forgot to activate the environment in this terminal, or your editor/notebook is launching a different interpreter. Diagnose from inside the failing process: 
    >>> import sys
>>> sys.executable
>>> sys.path
    Compare sys.executable with the output of which python in the activated shell. If they differ, you have found the problem. In VS Code, use the Python: Select Interpreter command and choose the one inside ai-course-env; in Jupyter, register the environment as a kernel with python -m ipykernel install --user --name ai-course-env and then select that kernel in the notebook. A notebook quick check is to run !which python or import sys; print(sys.executable) in a cell.
  • Packages going to the wrong interpreter. Bare pip is just whichever pip executable PATH finds first, which may belong to a different Python. Always prefer python -m pip install .... This form says "run the pip module using this interpreter", so the package necessarily lands in that interpreter's site-packages. Make it a habit even when you are confident; it costs six characters and eliminates an entire failure mode.
  • PermissionError: [Errno 13] Permission denied or "Access is denied" during install. pip is trying to write into a system-owned directory, which means no virtual environment is active. The correct fix is to activate (or create) one and install there. Do not use sudo pip install: it writes root-owned files into the system Python, mixes distribution-managed and pip-managed packages, and is exactly the route to breaking OS utilities. On modern Python versions you may instead see an externally-managed-environment error — that is the interpreter deliberately protecting itself, and the intended response is, again, to use a virtual environment.
  • Compilation failures on scientific packages — long walls of C compiler output ending in error: command 'gcc' failed or Microsoft Visual C++ 14.0 or greater is required. This means pip could not find a pre-built wheel matching your platform, Python version and CPU architecture, so it fell back to building the package from source — and the machine lacks the toolchain to do so. Try these in order: 
    (ai-course-env) $ python -m pip install --upgrade pip setuptools wheel
    An old pip may not recognise newer wheel tags (for example, Apple Silicon or recent manylinux variants) and will needlessly compile. If upgrading does not help, check whether a wheel exists for your Python version at all — the newest Python releases often run ahead of the scientific stack by a few months, in which case installing one minor version behind is the pragmatic fix. Failing that, switch to conda, whose packages ship as compiled binaries complete with their BLAS/LAPACK and C++ runtime dependencies, so no local compiler is ever required.

Two further problems are worth naming because their error messages point away from the real cause. The first is the shadowing import: if you name a file random.py, queue.py, heapq.py or collections.py in your working directory, Python finds your file before the standard library module, and you get errors such as AttributeError: module 'random' has no attribute 'choice'. The __pycache__ directory beside the offending file is a giveaway. Rename the file and delete the cache. The second is the stale terminal: PATH changes, newly created environments and freshly installed launchers are picked up only by shells started afterwards, so "it still doesn't work" is frequently cured by closing the terminal and opening a new one.

Put together, the end-to-end sequence for starting the module's coursework on a fresh machine is short enough to memorise:

$ cd ~/projects/ai-coursework
$ python3 -m venv ai-course-env
$ source ai-course-env/bin/activate          # Windows: ai-course-env\Scripts\activate
(ai-course-env) $ python -m pip install --upgrade pip
(ai-course-env) $ python -m pip install numpy scipy pandas scikit-learn matplotlib jupyter
(ai-course-env) $ python -c "import sklearn, numpy, pandas; print(sklearn.__version__)"
(ai-course-env) $ pip freeze > requirements.txt
$ echo "ai-course-env/" >> .gitignore

Run it once, commit requirements.txt and .gitignore, and every subsequent import error in the module becomes a genuine question about your code rather than an accident of configuration.
