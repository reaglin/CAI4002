Introduction

Search algorithms are only as good as the data structures that hold their working state. Every uninformed or informed search you will write in this course — breadth-first, depth-first, uniform-cost, greedy, A* — needs some way to store the frontier of nodes still to be expanded, some way to remember which states have already been visited, and some way to represent a state so that it can be compared and looked up quickly. Python gives you these pieces in its built-in collections (lists, tuples, sets, dictionaries), in the heapq module for priority queues, and in the collections module for specialized containers like deque, Counter, and defaultdict.

The choices matter because they change the asymptotic behavior of your search. A visited set backed by a hash set gives roughly constant-time membership checks, while scanning a list for the same thing is linear and will quietly turn a workable search into one that never finishes. Popping from the front of a list is expensive; popping from the front of a deque is cheap. Pulling the lowest-cost node from an unsorted list requires a full scan, while a binary heap gives you that in logarithmic time. Hashability also matters: a state you want to put in a set or use as a dictionary key must be immutable, which is why tuples and frozensets show up so often in state encodings.

The videos below focus on two of the areas students most often find unfamiliar: how a heap actually works underneath heapq, and what the collections module offers beyond the built-in types. While watching, keep asking yourself which search role each structure would fill — frontier, visited set, cost table, or state encoding — and what the cost of each operation would be when the search tree grows large.
