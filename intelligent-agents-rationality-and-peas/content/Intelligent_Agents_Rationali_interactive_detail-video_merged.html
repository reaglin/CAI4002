The Agent–Environment Model

1

The Agent–Environment Model

▶

Artificial intelligence, in its most practical form, is the study of how to build things that do something sensible in a world that they cannot fully control. The agent–environment model is the conceptual frame that makes this study tractable. It draws a boundary — a conceptual skin — around a system, labels everything inside that boundary the agent, labels everything outside it the environment, and then insists that all traffic across the boundary flows through just two channels: information coming in, and actions going out. Once that frame is in place, an enormous variety of systems — a thermostat, a chess program, a warehouse robot, a spam filter, a self-driving car, even a human being — can be described in the same vocabulary and compared on the same terms.

The power of the model lies in its austerity. It does not ask what the agent is made of, whether it has beliefs, or whether it is "really" intelligent. It asks only three questions: what can it perceive, what can it do, and how does what it perceives determine what it does? Everything else in the study of intelligent systems — rationality, performance measures, environment types, architectures — is built on top of these three questions.

What is an agent?

An agent is anything that can be viewed as perceiving its environment through sensors and acting upon that environment through actuators. The definition is deliberately permissive. Note the phrase "can be viewed as": the definition describes a stance we adopt towards a system, not an intrinsic property that some devices possess and others lack.

Sensors supply information about the state of the world. A sensor is any mechanism that converts some aspect of the environment into a form the agent's internal machinery can process. The range is vast:

  • A robot vacuum uses infrared cliff detectors, bump switches, optical flow sensors, and a dirt-detection sensor in the suction path.
  • An autonomous vehicle uses cameras, LIDAR, radar, wheel-odometry encoders, an inertial measurement unit, and a GPS receiver.
  • A software agent that files emails "senses" by reading the byte stream of incoming messages; its sensors are system calls and network sockets rather than physical transducers.
  • A human agent has eyes, ears, nose, tongue, and skin; a human's sensors deliver roughly ten million bits per second to the nervous system, of which only a tiny fraction reaches conscious attention.

Crucially, sensors are partial and imperfect. A camera sees only what is in its field of view, at a limited resolution, with noise, and with no information about what lies behind an occluding wall. This partiality is not an engineering defect to be eliminated; it is the permanent condition of agency, and much of AI is the study of how to act well despite it.

Actuators are the means by which the agent changes the state of the world. An actuator converts a decision into a physical or informational effect. Motors, wheels, grippers, steering columns, speakers and display screens are actuators; so are network writes, database updates, API calls, and the act of printing a character to a terminal. The set of actions available to an agent is as defining a constraint as the set of percepts: a chess program that can only output legal moves inhabits a very different world from a robot arm that can output arbitrary joint torques. Note also that in many systems the actuators and sensors are coupled — a robot that moves its camera changes what it can perceive next. This coupling, called active perception, is one reason the agent–environment relationship is a loop rather than a pipeline.

The agent concept is a tool for analysis, not a precise classification of devices. It is tempting to ask "Is a thermostat really an agent?" This is the wrong question. The right question is "Is it useful to describe this thermostat using the agent vocabulary?" Sometimes the answer is yes — if we want to reason about how it responds to a sequence of temperature readings, whether its behaviour is rational given a comfort-and-energy performance measure, and how it would need to change in a building with occupancy sensors. Sometimes the answer is no — if we want to analyse the bimetallic strip's thermal expansion coefficient, the agent stance adds nothing and the physics stance is correct. The agent concept, like the concept of "system" or "module" in engineering, earns its keep by the explanatory leverage it provides.

Almost any system can be viewed as an agent if we specify its sensors, actuators, and environment. Consider a hand calculator. Its sensors are the keypad; its actuators are the display segments; its environment is the user and the sequence of key presses. Under this description the calculator is a (very simple, very reliable) agent whose agent function maps key-press sequences to display states. The description is accurate but uninteresting, because the agent function is trivial and the environment imposes no uncertainty. Contrast a stock-trading program: same formal structure, but the environment is adversarial, partially observable, and stochastic, and so the agent description does real work. A useful rule of thumb is that the agent stance pays off in proportion to the amount of uncertainty and choice in the system's situation. Where the drawing of the boundary itself is ambiguous — is the vehicle's braking controller an agent, or a component of the vehicle agent? — the answer is settled by convenience of analysis, not by fact. We draw the boundary where it produces the cleanest account of the decisions we care about.

Percepts and percept sequences

A percept is the content of the agent's sensory input at a single instant — a complete snapshot of everything the sensors report at that moment. A percept sequence is the complete history of everything the agent has perceived from the beginning of its operation to the present. If we write the set of possible percepts as P, then the set of possible percept sequences is P*, the set of all finite strings over P.

An agent's choice of action at any instant can depend on the entire percept sequence observed to date. This is the strongest possible statement of what an agent is permitted to use. It licenses behaviour such as: "if I have passed this landmark three times already, take the other turning", or "if the user has rejected my last four recommendations, change strategy". Nothing in the model forbids arbitrarily long-range dependence on history.

It cannot depend on anything the agent has not perceived. This is the corresponding, and equally important, prohibition. Whatever is true of the world but invisible to the sensors simply cannot enter into the decision — not because of a deficiency in the agent's reasoning, but because the information is not there. An agent that happens to act in a way that suits a hidden fact has been lucky, not clever. This constraint is the root of the later distinction between rationality and omniscience: we judge an agent by what it does with the percept sequence it has, not by what it would have done had it known everything.

Memory determines how much of the sequence is actually available. The percept sequence is defined externally, as a matter of record; whether the agent can use it depends on its internal construction:

  • An agent with no internal state retains nothing. Its action is a function of the current percept alone, so its behaviour is of the restricted form f(p1…pt) = g(pt). Such agents are cheap, fast, and incapable of any history-dependent behaviour whatsoever.
  • An agent with internal state carries a summary of the past forward in time. It need not store the raw sequence; typically it stores a compressed state st updated by a rule st = update(st-1, pt, at-1). If the summary is sufficient — if it captures everything about the past that is relevant to the future — the agent loses nothing by discarding the raw history. Designing such sufficient summaries is one of the central engineering problems in AI.

A concrete illustration: a robot in a long featureless corridor sees the same percept at every point along it. Without memory it cannot tell whether it is near the start or the end, and its behaviour at both points must be identical. With a counter of steps taken since entering the corridor, the two situations become distinguishable and different actions become possible. The percepts are identical; the percept sequences are not.

Tabulating behaviour over all percept sequences fully characterises an agent. If, for every possible percept sequence, we record the action the agent would take, we have captured its behaviour exhaustively — there is nothing left to say about what it does. This conceptual table is the agent's complete behavioural specification. The catch is size. Suppose an agent runs for T steps and has |P| possible percepts per step. The number of distinct percept sequences of length at most T is (|P|T+1 − 1)/(|P| − 1), which grows exponentially in T. For a taxi with a single camera at modest resolution the number of possible single percepts already exceeds the number of atoms in the observable universe, and for an agent that runs indefinitely the table is literally infinite. The table is therefore a definition, not a design.

The agent function and the agent program

The agent function f is the mathematical object that maps every possible percept sequence to an action:

f : P* → A

where  P  = the set of possible percepts
       P* = the set of all finite percept sequences
       A  = the set of possible actions

The agent function is an external, abstract description of behaviour. It belongs to the observer's account of the agent, not to the agent's insides. You could determine an agent function (in principle) purely by experiment, by feeding every possible history to the agent and recording its output, without ever opening the box. It is a total function: it specifies an answer for every history, including absurd ones that will never occur. And it is infinite in extent for any agent operating over unbounded time.

The agent program is the internal, finite implementation that produces that behaviour. The program is a concrete artefact — code, circuits, trained network weights — that runs on some physical architecture (a computing device with its sensors and actuators attached). The relationship is captured by the slogan agent = architecture + program. Where the agent function takes a whole percept sequence as its argument, the program takes only the current percept, because that is all the architecture hands it on each cycle; any dependence on history must be manufactured by the program itself through internal state.

A table-driven program is one possible implementation, but impractical for all but trivial tasks. The most literal way to implement an agent function is to store it:

function TABLE-DRIVEN-AGENT(percept) returns an action
    persistent: percepts, a sequence, initially empty
                table, a table of actions indexed by percept sequences
    append percept to the end of percepts
    action <- LOOKUP(percepts, table)
    return action

This works, and for tiny worlds it is perfectly sensible. But it fails on four counts for anything realistic. First, space: the table is astronomically or infinitely large. Second, construction time: no designer could ever fill in all the entries. Third, learning: even an agent that learned from experience could not visit more than a vanishing fraction of the entries. Fourth, generalisation: the table contains no structure, so experience with one entry teaches it nothing about any other. Compare a table that stores the square root of every number to a four-line Newton's-method routine: the routine is smaller, constructible, and correct on inputs never anticipated. The central project of AI is exactly this — to find compact programs that generate rational behaviour over vast percept spaces, rather than to enumerate that behaviour.

Different programs can realise the same agent function with very different efficiency. Because the agent function describes only input–output behaviour, it is blind to how that behaviour is produced. Two agents that always choose the same action given the same history are, as agent functions, identical — even if one deliberates for an hour using exhaustive search and the other answers instantly from a compiled rule. Consider three implementations of the same tic-tac-toe agent function:

  • A full minimax search of the game tree on every move: a few dozen lines of code, thousands of node expansions per move.
  • A memoised lookup of precomputed optimal moves: fast, but requiring stored entries for every reachable position.
  • A short set of hand-crafted rules ("take the win, else block the win, else take the centre, else take a corner…"): tiny and instantaneous.

All three may compute precisely the same function. They differ in memory footprint, latency, energy consumption, and ease of modification — and in the real world those differences often decide which agent is usable. This is also why the distinction matters practically: rationality is a property of the agent function; efficiency is a property of the agent program. In real-time environments the two interact, because a program too slow to answer before the world changes effectively implements a different (and worse) agent function.

The perception–action loop

Each cycle consists of perceive, decide, and act. The agent's operation is not a single question-and-answer but an unbounded repetition:

loop forever:
    p  <- SENSE()                  # read the sensors: obtain percept p_t
    s  <- UPDATE-STATE(s, a, p)    # optional: revise internal state
    a  <- DECIDE(s, p)             # select an action using the program
    EXECUTE(a)                     # drive the actuators
    # the environment now evolves, partly because of a

The three phases are conceptually distinct even when they are physically interleaved. In a reactive hardware controller the "decide" step may be a single comparator; in a planning robot it may be a search over thousands of candidate futures. In real implementations these phases often run concurrently at different rates — a vehicle may sense at 100 Hz, re-plan a route at 1 Hz, and actuate continuously — but the logical cycle is the same.

Actions taken now influence the percepts received later. This is what makes the structure a loop rather than a function evaluated once. The environment state evolves according to both its own dynamics and the agent's interventions, and the next percept is drawn from that new state. Three consequences follow:

  • Decisions have consequences over time. An action that looks locally attractive may lead the agent into a region of the environment from which no good outcomes are reachable. A delivery robot that takes a short-cut into a dead-end corridor has not made a small mistake; it has made a mistake whose cost is paid over all subsequent cycles.
  • Information is itself an outcome. Because actions shape future percepts, some actions are worth taking purely for what they reveal — turning the head, opening a door, asking a diagnostic question, running a test. This gives rise to the exploration-versus-exploitation tension that pervades learning agents.
  • Errors can compound or be corrected. The loop gives the agent repeated opportunities to observe the effects of its actions and adjust, which is why closed-loop control is vastly more robust than open-loop execution of a fixed plan.

The loop continues indefinitely or until a terminal condition is reached. Some agents have a natural termination — a chess program stops at checkmate or stalemate, a medical triage system stops when a diagnosis is issued, a package-sorting arm stops when the belt empties. Others are designed to run without end: a thermostat, a network intrusion monitor, a planetary rover. The distinction matters for design, because a terminating task can be evaluated by its final outcome, whereas a non-terminating one must be evaluated by its ongoing conduct. It also determines whether total accumulated reward is even well-defined, which is why ongoing tasks are usually scored with averages or discounted sums rather than totals.

Because the loop is continuous, behaviour must be evaluated over sequences of states, not single moments. A snapshot judgement is almost always misleading. A vacuum agent that dumps dirt on the floor and sweeps it up again scores well on "squares cleaned per hour" at any instant while accomplishing nothing over an hour. A trading agent can show a profit on every individual day of a month and still be ruined by the one position it holds overnight. A taxi agent that minimises instantaneous travel time will accelerate hard, brake late and corner sharply — each decision locally optimal, the sequence collectively unsafe. Evaluation must therefore be applied to the environment history — the sequence of states the world passes through as a result of the agent's conduct — and the choice of how to aggregate over that history (sum, average, discounted sum, worst case) is a genuine design decision with real consequences for the behaviour that emerges.

Example: the vacuum-cleaner world

The classic illustration strips the model down to the smallest world in which anything interesting can happen. There are two locations, square A on the left and square B on the right. Each square is either clean or dirty. The agent occupies one square at a time, and it can move left, move right, suck up dirt, or do nothing.

The agent perceives its current location and whether that location is dirty. A percept is therefore a pair such as [A, Dirty] or [B, Clean]. Note what is not perceived: the agent has no information about the condition of the square it is not standing on. The world has eight possible states (two agent positions × two dirt conditions per square) but only four possible percepts, so the environment is partially observable — a point that will matter enormously later.

A simple agent function. One natural rule is: if the current square is dirty, Suck; otherwise, move to the other square. Tabulating this over percept sequences gives the following (truncated — the real table continues forever):

Percept sequenceAction
[A, Clean]Right
[A, Dirty]Suck
[B, Clean]Left
[B, Dirty]Suck
[A, Clean], [A, Clean]Right
[A, Clean], [A, Dirty]Suck
[A, Dirty], [A, Clean]Right
[A, Clean], [A, Clean], [A, Clean]Right
[A, Clean], [A, Clean], [A, Dirty]Suck
……

Observe that in this particular function the action depends only on the last percept in the sequence; every row with the same final percept has the same action. That is a property of this agent, not of agents in general, and it is exactly what makes a memoryless implementation possible here.

The same agent function, two implementations. Written as a table-driven program, we would store the rows above (infinitely many of them). Written as code, the whole thing collapses to:

function REFLEX-VACUUM-AGENT([location, status]) returns an action
    if status = Dirty then return Suck
    else if location = A then return Right
    else if location = B then return Left

Three lines replace an infinite table, and they behave identically on every input. This is the table-versus-program contrast in miniature, and it is the reason AI is written as programs.

Varying the environment or the percept detail changes which agent function performs best. The simple reflex rule above is a good agent under one set of assumptions and a poor one under others. Compare:

Environment variationEffect on the simple reflex ruleWhat a better agent needs
Dirt never reappears; movement is freePerforms well — cleans both squares, then oscillates harmlessly foreverNothing; the rule is already rational
Dirt never reappears; each movement costs one pointPerforms badly — oscillates between two clean squares, accumulating cost foreverMemory of whether both squares have been seen clean, plus a NoOp action
Dirt reappears at randomPerforms reasonably — patrolling is exactly the right policyPossibly a model of dirt-arrival rates to linger where dirt is frequent

The lesson is the one that organises everything that follows: there is no such thing as the best agent function in the abstract. The reflex rule that is ideal in the free-movement world is demonstrably irrational in the movement-cost world, where the rational agent must eventually stop. Change the cost structure, the sensor suite, or the dynamics of dirt, and the ranking of agent functions changes with it. An agent function can only be judged relative to a specified environment and a specified measure of success — which is precisely why the next step in studying agents is to make both of those specifications explicit rather than leaving them implicit.

Putting the pieces together

The model gives us a small, disciplined vocabulary with a clear division of labour:

  • Sensors and actuators define the boundary — what can cross it and in which direction.
  • Percepts and percept sequences define what the agent is entitled to base its decisions on.
  • The agent function says what the agent does, as an external fact about its behaviour.
  • The agent program says how, as an internal, finite, resource-bounded artefact.
  • The perception–action loop ties the two sides together over time, making behaviour a sequence rather than an event.

Everything else in the study of intelligent agents is a question asked within this frame: which agent function ought we to want (rationality); how do we specify the task precisely enough to answer that (performance measure, environment, actuators, sensors); what kind of world is the agent in (environment properties); and what internal organisation of the program will deliver the desired function at acceptable cost (agent architectures).

Rationality and Performance Measures

Rationality and Performance Measures

▶

Artificial intelligence is often described as the study of agents that do the right thing. That phrase is intuitively appealing but technically useless until we say precisely what "the right thing" means, who decides, and against what standard the decision is judged. The concept that supplies this precision is rationality. A rational agent is not one that is infallible, clairvoyant, or lucky; it is one whose action selection is defensible given what it wants, what it knows, what it can do, and what it has seen. This topic unpacks that definition ingredient by ingredient, shows how performance measures should be designed (and how they are commonly mis-designed), separates rationality from the neighbouring notions of omniscience, perfection, and success, and explains why learning, information gathering, and autonomy are themselves rational behaviours rather than optional extras.

Throughout, it helps to keep a running example in mind. The classic one is the vacuum-cleaner world: a two-square environment, squares A and B, each either clean or dirty. The agent perceives its current location and whether that location is dirty, and it can Move Left, Move Right, Suck, or NoOp. A second running example is an automated taxi driver, which is messier and more realistic, and so exposes trade-offs that the vacuum world hides.

The four ingredients of rationality

The standard definition states: For each possible percept sequence, a rational agent should select an action that is expected to maximise its performance measure, given the evidence provided by the percept sequence and whatever built-in knowledge the agent has. Four things determine what counts as rational at any moment:

IngredientWhat it suppliesVacuum-world instanceTaxi instance
Performance measure The external criterion of success — what we actually want to happen in the environment One point per clean square per time step over 1000 steps Weighted combination of safety, legality, trip time, fuel cost, passenger comfort, profit
Prior knowledge of the environment What the designer builds in before the agent ever runs "There are exactly two squares"; "Sucking cleans the current square" Road network map, traffic laws, vehicle dynamics, typical pedestrian behaviour
Available actions (actuators) The space of things the agent can physically do Left, Right, Suck, NoOp Steer, accelerate, brake, signal, horn, speak to passenger, display
Percept sequence to date Everything the agent has perceived from the start of its life until now [A, Dirty], [A, Clean], [B, Clean], ... Camera frames, lidar returns, speedometer, GPS fixes, passenger speech

The critical consequence is that rationality is a four-place relation, not a property of an agent in isolation. Change any single ingredient and the rational action may change. Suppose the vacuum agent perceives [A, Clean]. Is moving right rational? It depends:

  • Change the performance measure. If the measure awards one point per clean square per step but deducts one point for each movement (to model energy use), then in an environment where dirt never reappears and both squares are known clean, the rational action is NoOp — sitting still forever. Under the original measure with no movement penalty, moving to check the other square costs nothing and may gain points, so movement is rational.
  • Change the prior knowledge. If the agent knows a priori that square B was cleaned two steps ago and that dirt never reappears, moving right is pointless. If it has no such knowledge, moving right is an information-gathering action with positive expected value.
  • Change the available actions. If the agent's wheels have failed and only Suck and NoOp remain, "move right" is not merely irrational — it is not in the action set at all, and rationality must be assessed over the remaining options.
  • Change the percept sequence. If the current percept is [A, Dirty] rather than [A, Clean], sucking dominates every alternative. The agent's entire history matters too: an agent that has already observed B to be clean is in a different epistemic position from one that has never visited B, even though both now stand in a clean square A.

Formally, the agent is characterised by an agent function f: P* → A mapping percept sequences to actions. Rationality is a property of this function relative to a performance measure and an environment class. We can therefore sketch the ideal (if usually uncomputable) rational decision as:

function RATIONAL-ACTION(percept_sequence, prior_knowledge, actions, measure):
    best ← none; best_value ← −∞
    for each a in actions:
        # expectation over possible environments consistent with
        # prior_knowledge and percept_sequence
        v ← EXPECTED-VALUE(measure, outcome of doing a and acting well thereafter)
        if v > best_value: best ← a; best_value ← v
    return best

Note the word expected. The agent maximises expected performance over the environments it cannot rule out, not actual performance in the one true environment, which it does not get to inspect.

Performance measures evaluate outcomes, not behaviour

A performance measure is an objective criterion imposed by the designer or user on the sequence of environment states that results from the agent's activity. It is emphatically not a measure of how the agent behaves internally, how clever its reasoning looks, or how closely it conforms to our intuitions about good conduct. This distinction is the single most practically important idea in the topic.

  • Measure the environment, not the agent's self-report. For the vacuum agent, the right quantity is the amount of dirt remaining in the rooms over time, not the number of Suck operations performed. An agent that scores on Suck count can maximise its score by sucking repeatedly on an already-clean floor, or — in a notorious degenerate case — by dumping collected dirt back onto the floor so it can suck it up again. Both strategies are perfectly rational with respect to the stated measure; the measure, not the agent, is at fault.
  • Specify what you want, not how you think it should be achieved. If you reward the taxi for "staying in lane", you may get an agent that refuses to overtake a stalled vehicle. If you reward "reaching the destination safely, legally and promptly", you leave the agent free to discover manoeuvres the designer never anticipated. Over-specifying behaviour converts the designer's limited imagination into a hard ceiling on performance.
  • Bad measures invite degenerate strategies. This failure is known in modern practice as reward hacking or specification gaming. A delivery robot rewarded for minutes-to-destination will speed and run lights. A news-feed agent rewarded for clicks will surface outrage. A cleaning robot rewarded for "no dirt detected by my sensor" may learn to cover its sensor or switch it off. In every case the agent is behaving rationally; the designer encoded the wrong objective.
  • Measures usually combine criteria, and the criteria conflict. A taxi measure might be a weighted sum of: arriving at the correct destination; minimising fuel and wear; minimising trip time; minimising violations of traffic law; maximising passenger safety and comfort; maximising profits. Speed trades against safety and comfort; fuel economy trades against speed. The weights are a design decision with ethical content — selecting them is choosing how many extra minutes of travel time are worth one unit of collision risk. It is far better to make these weights explicit than to leave them implicit in hand-crafted rules.
  • The time profile matters. A measure defined over 1000 steps may reward a very different policy from one defined over 10 steps. Similarly, averaging performance is not the same as bounding worst-case performance: a taxi with excellent average speed and an occasional catastrophe is not acceptable, so real measures often include hard constraints or heavily asymmetric penalties.

A useful discipline when writing a measure is to ask: "If a devious engineer were allowed to maximise this number by any means, what is the ugliest thing they could build?" If the answer is something you would not accept, the measure is wrong.

Rationality is not omniscience

An omniscient agent knows the actual outcome of its actions in advance and can act accordingly. Omniscience is impossible in any realistic environment, because the agent's sensors are partial, its knowledge incomplete, and the world's future not fully determined by anything it can observe. Rationality is deliberately defined to be achievable: it is maximisation of expected performance given the percept sequence to date, whereas omniscience would be maximisation of actual performance.

The standard illustration: you are strolling along the Champs-Élysées and see an old friend across the street. No traffic is near, you are not otherwise engaged, so you cross to greet them. At 33,000 feet a cargo door falls off an airliner, and you are flattened before reaching the other side. Were you irrational to cross? Clearly not. Nothing in your percept sequence supported the hypothesis "falling cargo doors"; the probability was negligible and no available information-gathering action — glancing up, consulting a flight tracker — would have been worth its cost. The decision process was sound; the outcome was catastrophic. We say the agent was rational but unlucky.

  • Judgement is ex ante, not ex post. Agents are assessed on the evidence and deliberation available at the time of choice. Hindsight supplies information the agent could not have had, and importing it into the evaluation changes the question from "did it decide well?" to "did the world cooperate?".
  • Unforeseeable events do not retroactively make a decision irrational. If the event was foreseeable, however, the story is different — ignoring an audible screech of brakes while crossing would be irrational, because that percept was available.
  • Demanding perfection makes design impossible. If "rational" meant "always achieves the best possible result", then no agent in an uncertain environment could ever be designed to be rational, because no mapping from percepts to actions can guarantee best outcomes when the percepts underdetermine the world's state. The expected-value formulation preserves a meaningful, attainable design target.

Rationality versus perfection and success

It is worth laying out the three concepts side by side, since students routinely conflate them in both directions — treating a successful agent as rational and an unsuccessful one as irrational.

ConceptWhat it describesDepends onKnowable at decision time?
RationalityThe quality of the decision processPercepts so far, prior knowledge, action set, performance measureYes
SuccessThe outcome actually obtainedThe decision and how the environment happened to unfoldNo — only in retrospect
Perfection / omniscienceAlways achieving the best possible outcomeKnowledge of the actual futureNo — and unattainable in principle

Two asymmetric errors follow:

  • Rational but unsuccessful. A medical diagnosis agent sees a patient with classic symptoms of a common, benign condition, orders the standard confirmatory test, and prescribes the standard treatment. The patient turns out to have an exceedingly rare disorder with an identical presentation, and deteriorates. The outcome is bad; the decision was rational, because at decision time the expected benefit of the chosen action exceeded that of, say, ordering a full battery of expensive, invasive tests on every patient.
  • Successful but irrational. A taxi agent charges through a blind junction at 90 km/h with no sensing and arrives on time because, by chance, nothing was crossing. The outcome is excellent; the decision was reckless. Luck does not launder a bad decision. If we rewarded this agent, we would be reinforcing a policy with a catastrophic expected value.

The practical moral for AI engineering is that evaluating agents purely on realised results is statistically dangerous, particularly in stochastic or rare-event domains. Single-trial results conflate decision quality with noise. Sound evaluation either averages over many episodes and many environment configurations, or inspects the decision rule directly — asking whether the action chosen maximised expected performance given what the agent knew. This is exactly why benchmark suites in AI specify a class of environments rather than one instance, and why safety assessment of autonomous vehicles counts near-misses and risky manoeuvres, not just crashes.

Information gathering, learning, and autonomy

Because rationality is defined relative to the percept sequence to date, and because the agent can influence what it will perceive next, three further behaviours fall out of the definition as consequences rather than add-ons.

Information gathering is rational. An action that does not directly improve the environment but changes what the agent will know can still have the highest expected value, because better knowledge supports better future choices. Looking both ways before crossing a street yields no reward in itself; it modifies the percept sequence so that subsequent crossing decisions are far better informed. The expected gain from the improved decisions exceeds the small cost of the glance. Formally, this is the value of information: the expected improvement in performance from knowing an unknown quantity, minus the cost of finding it out. Examples abound:

  • A vacuum agent in an environment of unknown size and layout rationally explores the unvisited squares rather than oscillating between two known-clean ones.
  • A medical diagnosis agent rationally orders a diagnostic test whose result will change the treatment decision — and rationally declines a test whose result would not change the treatment, however informative it is in the abstract.
  • A taxi rationally slows and edges forward at an occluded junction, trading a few seconds of trip time for a decisive improvement in what its sensors can see.

Learning is rational. Prior knowledge given by the designer is typically partial and sometimes wrong. An agent that updates its internal model from experience improves the accuracy of the expectations on which its decisions rest, and hence its expected performance over its lifetime. The vacuum agent learns where dirt tends to accumulate and when; the taxi learns that a particular junction floods in heavy rain, that a certain class of pedestrian cue predicts stepping into the road, and that its own braking distance degrades with worn pads. In the limit of a perfectly known, static, fully observable environment — a simple clockwork world — learning is unnecessary, and a fixed built-in policy suffices. Such worlds are rare, and the more unknown or non-stationary the environment, the more learning dominates the design.

Autonomy is the degree to which an agent relies on its own percepts rather than on the designer's priors. An agent that acts solely on built-in knowledge is said to lack autonomy; its behaviour reflects the designer's model of the world rather than the world. The canonical example is the dung beetle, which after depositing its egg plugs the burrow with a ball of dung — and continues the plugging motion even if the ball has been removed from its grasp, because the behaviour is wired to the motion, not to the evidence. The sphex wasp similarly repeats a fixed inspection routine indefinitely if its prey is repeatedly moved a few inches. Neither creature is consulting evidence that contradicts its built-in assumptions, so neither can adapt.

  • An agent that ignores percepts contradicting its priors is both less autonomous and, over time, less rational: in a world that departs from the designer's assumptions, the agent's expected performance degrades while it persists in behaviour justified only by a false model.
  • Some built-in knowledge is nonetheless entirely reasonable: a brand-new agent with no experience and no priors would act randomly, which is unsafe and slow. The sensible design gives the agent enough prior knowledge to survive and act sensibly at the outset, plus the capacity to learn — so that autonomy increases with experience.
  • A truly autonomous agent should be able to operate successfully in a variety of environments, given sufficient time to adapt. This is the practical reason autonomy matters: it is what allows one design to be deployed in a city it was not specifically tuned for.

Rationality is relative to the task environment

Everything above converges on one conclusion: there is no such thing as a universally rational action, and no such thing as a universally rational agent program. Rationality is always indexed to a task environment — the combination of performance measure, environment, actuators and sensors. Consider how each component shifts the optimal policy for our vacuum agent:

Variation in the task environmentConsequence for the rational policy
Measure: +1 per clean square per step; no movement penalty; dirt never reappears; geography known Clean both squares as fast as possible, then NoOp forever. Movement after that is harmless but pointless.
Same, but each movement costs 1 point Stop moving as soon as both squares are known clean; the simple "always move when clean" reflex agent becomes irrational because it bleeds points indefinitely.
Dirt can reappear at random in either square Perpetual patrolling becomes rational again: the agent must keep sampling both squares, and the optimal patrol frequency depends on the reappearance rate versus the movement cost.
Geography unknown; number of squares unknown Exploration and model-building become rational; a purely reflex policy is now clearly suboptimal, and a learning, model-based agent is justified.
Sensor can only detect dirt in the current square (local, partial observability) The agent cannot know whether a remote square is dirty, so "go and check" has real expected value; with a global dirt sensor, checking is worthless and only targeted travel is rational.
Actuators lack a movement capability Only Suck and NoOp are candidates; the rational policy is defined over this reduced set, and performance is capped no matter how good the reasoning is.
Measure penalises noise above a threshold (a "quiet" requirement) It may become rational to leave light dirt in place at night and clean it in the morning — a behaviour that looks like failure under the original measure.

The same relativity holds for the taxi. In a city with strict, consistently enforced traffic law and litigious passengers, a conservative, slow policy maximises the measure. On an ambulance mission where arrival time dominates, the same conservative policy is irrational. In a city where everyone else drives aggressively, an excessively polite agent may actually be less safe, because other drivers' expectations form part of the environment dynamics.

Two design lessons follow directly. First, specify the task environment explicitly before writing any agent code. This is the role of the PEAS description (Performance measure, Environment, Actuators, Sensors) and of the subsequent classification of the environment along dimensions such as observability, determinism, episodicity, dynamism, discreteness and agent count. Without that specification, the phrase "a good agent" has no referent, and you cannot tell whether a disappointing result indicates a bug, a bad architecture, or a badly chosen objective. Second, the environment specification determines the architecture: a fully observable, static, deterministic, known world with a simple objective can be served by a lookup-table or simple reflex agent, whereas partial observability demands internal state, conflicting criteria demand a utility function rather than a binary goal test, and unknown or changing dynamics demand a learning element. Rationality, in short, is not a badge an agent carries; it is a verdict delivered by a specified task environment on a specified decision procedure.

Specifying Tasks with PEAS

Specifying Tasks with PEAS

▶

Before a single line of an agent program is written, a designer must be able to answer a deceptively simple question: what, exactly, is this agent supposed to do, and in what world is it supposed to do it? The PEAS framework — Performance measure, Environment, Actuators, Sensors — is the standard way of answering that question in a disciplined, written form. It is not a design; it is a specification of the task that any design must satisfy. In the same way that a civil engineer does not begin pouring concrete before the load requirements, soil conditions and span of a bridge are documented, an agent designer does not begin choosing data structures, search algorithms or learning methods before the PEAS description of the task is on paper. Everything that follows — the choice of architecture, the internal representation, the learning signal — is downstream of these four elements.

Why specify the task before designing the agent

The deepest reason is that the agent program depends entirely on the task environment. There is no such thing as a universally good agent program; there are only programs that are good for particular tasks. A control loop that works beautifully for a floor-cleaning robot in a two-room apartment is useless on a motorway, and a chess program is helpless in a hospital. The structure of the task determines what information the agent needs, how much internal state it must carry, whether it can act greedily or must plan ahead, and whether it must adapt over time. Fixing the task first means the designer is solving a well-posed problem rather than guessing at one.

A second reason is that a written specification exposes hidden assumptions. Designers routinely assume, without noticing, that the agent "knows where it is", that "the floor is flat", that "the patient tells the truth", or that "the other drivers obey the law". None of these assumptions are free: each one is either a sensor that must physically exist, a property of the environment that must actually hold, or a risk that must be managed. Writing down the sensors forces the question "how, concretely, would the agent come to know that?" Writing down the environment forces the question "and what happens when that assumption fails?" A vacuum agent that assumes it knows its location is a fundamentally different engineering problem from one that must infer its location, and the difference only becomes visible when the sensor list is written out.

A third reason is comparability. If two teams propose competing designs for a warehouse robot and each is evaluated against its own informal idea of the job, the comparison is meaningless — one team's design may simply be solving an easier problem. A shared PEAS specification makes the comparison fair: both designs face the same environment, control the same actuators, receive the same percepts, and are scored by the same performance measure. This is exactly the logic behind benchmark competitions such as the DARPA Grand Challenge or RoboCup, where the task specification is published in advance precisely so that different architectures can be judged on equal terms.

A fourth reason is that specification forces the designer to state success criteria up front rather than discovering them after deployment. The most expensive failures in deployed autonomous systems are rarely failures of implementation; they are failures of definition. A delivery robot that was never told that blocking a fire exit is unacceptable will cheerfully block a fire exit. A recommendation agent optimised for "time on site" will learn to be addictive rather than useful. Writing the performance measure first converts these from post-hoc discoveries into design-time decisions.

The four elements of PEAS

The four elements divide the specification into the part that defines what counts as doing well, the part that defines the world the agent is embedded in, and the two parts that define the interface between agent and world.

Element Question it answers What it constrains in the design Common errors
Performance measure By what criterion do we judge the sequence of states the agent brings about? The objective function, the evaluation of plans, the reward signal for learning, the trade-offs between competing goals. Scoring the agent's intentions or internal effort rather than its effects on the world; omitting safety, cost or side-effect terms.
Environment What surroundings, objects, processes and other agents does the agent operate among? The state space, the transition model, the uncertainty the agent must tolerate, the classification of the task environment. Describing an idealised laboratory world and ignoring weather, noise, failures, adversaries or human unpredictability.
Actuators Through what physical or software effectors can the agent change the world? The action set available to the agent, the granularity of control, the physical limits on what plans are executable. Listing abstract "actions" such as "drive to destination" that no actuator can execute directly; forgetting communication actuators.
Sensors Through what channels does the agent receive information about the world? The percept vocabulary, the degree of observability, the need for internal state, the noise model. Assuming perfect, noiseless, complete percepts; forgetting proprioceptive sensors that report the agent's own state.

The crucial discipline is that all four must be stated together, and changing any one changes the design problem. They are not four independent lists; they interlock. Remove the location sensor from a vacuum agent and the same performance measure now demands a far more sophisticated program that maintains a belief over possible positions. Add an opponent to the environment and a straightforward planner must become a game-playing agent that reasons about an adversary's choices. Add "passenger comfort" to the performance measure of a taxi and the actuator commands must become smooth rather than merely correct, and a new sensor (perhaps an accelerometer or a passenger feedback channel) may be needed to measure it. A PEAS description is therefore a single coherent object; partial specifications are not merely incomplete but misleading, because they suggest the remaining choices are free when in fact they are tightly coupled.

Writing a good performance measure

Of the four elements, the performance measure is the one most often written badly, and it is the one where bad writing is most damaging. Four principles help.

  • Measure outcomes in the environment, not the agent's internal satisfaction. It is tempting to score the agent on how well it thinks it is doing — how confident its classifier is, how many squares it believes it cleaned, how low its internal cost estimate is. This is a mistake, because the agent can always improve such a score by deceiving itself. A vacuum agent rewarded for "believing the floor is clean" can simply stop sensing dirt. A diagnostic agent rewarded for "confidence in its diagnosis" will become confidently wrong. The performance measure must be defined over states of the world: squares actually clean, patients actually recovering, packages actually delivered to the right address.
  • Specify what you actually want, not how you imagine it should be achieved. The designer's job is to state the end; the agent's job is to find the means. If you believe the best cleaning strategy is a boustrophedon sweep, do not write "performance = fraction of time spent sweeping in straight lines". That rewards the strategy, not the result, and it forecloses any better strategy the agent might discover. Write "performance = amount of dirt removed per unit of energy, with cleanliness maintained over the whole day", and let the design or the learning process find the sweep pattern — or something better.
  • Beware degenerate strategies and reward hacking. An agent optimises exactly what you wrote, not what you meant. The classic illustration is a vacuum agent scored on "total amount of dirt collected over its lifetime": the optimal policy is to collect dirt, dump it back onto the floor, and collect it again forever. Scoring "a clean floor, measured by sampling cleanliness at every time step" removes this exploit, because dumping dirt is now penalised. Similar pathologies are everywhere: a warehouse robot rewarded for "items moved" may shuffle the same box back and forth; a content agent rewarded for "engagement" may learn to provoke outrage; a cleaning robot penalised only for visible mess may learn to hide mess under the sofa. A useful test when drafting a measure is to ask, adversarially, "what is the laziest or most perverse behaviour that maximises this number?" If the answer is not acceptable behaviour, the measure needs rewriting — typically by adding terms for side effects, by measuring the maintained state rather than cumulative throughput, or by adding hard constraints the agent may not violate.
  • Handle multiple objectives explicitly. Real tasks almost always involve conflicting goals. A taxi must balance speed against safety, fuel economy against acceleration, and profit against passenger comfort. Simply listing these is not enough; the agent must be told how to trade them off when they conflict, because at run time it will face exactly those conflicts. Common approaches are a weighted sum (for example, score = 100·safety_violations⁻ + 1·minutes_late⁻ + 0.5·litres_fuel⁻ + 2·comfort_penalty⁻, where the weights encode the relative importance), a lexicographic ordering (never violate safety; subject to that, minimise time; subject to that, minimise fuel), or hard constraints plus a scalar objective (safety and legality as inviolable constraints, with time and fuel traded off inside the feasible set). The choice of weights is a genuine design and ethical decision, not a technical afterthought: setting the weight on "minutes late" too high produces an agent that runs amber lights.

Two further subtleties are worth noting. First, performance should normally be measured over a sequence of states rather than a single final state, because when and how an outcome is achieved matters: a floor that is clean for ten hours is better than one cleaned perfectly at midnight and filthy the rest of the day. Second, the measure should be chosen by the designer or stakeholder, not by the agent, and it may include things the agent cannot directly observe (such as long-term patient survival). That is perfectly legitimate — the performance measure defines success objectively; the agent must do the best it can with the percepts it has, which is precisely why rationality and omniscience are different things.

Worked example: vacuum cleaner agent

PEAS element Specification for a domestic vacuum cleaner agent
Performance measure Amount of floor area cleaned; cleanliness maintained over time (sampled at every time step rather than totalled as dirt collected); electrical energy consumed; time taken to complete a cleaning cycle; noise generated; avoidance of damage to furniture, cables and pets.
Environment Rooms or discrete squares in a house; dirt of varying types and quantities; static obstacles such as walls and furniture legs; movable obstacles such as chairs, shoes and toys; different floor surfaces (tile, hardwood, deep carpet); thresholds and stairs; possibly people and animals moving about; the charging dock.
Actuators Drive wheels or motors for forward, reverse and turning motion; suction motor (on/off or variable power); rotating side brushes and a main brush roll; possibly a dirt-bin release, a docking mechanism and a status beep or indicator light.
Sensors Dirt detector (optical or acoustic, reporting dirt in the current square); bump or contact sensor for obstacles; cliff sensors to avoid stairs; location sensor (odometry, gyroscope, lidar or camera-based SLAM); wall-following infrared sensor; battery-level sensor; bin-full sensor; wheel-drop sensor.

This example repays close reading because small changes ripple through everything. In the textbook two-square world, the agent has only a location sensor and a dirt sensor, two squares A and B, and three actions Left, Right, Suck. The entire agent function can be written as a tiny table over percepts of the form [A, Dirty], and a simple reflex rule suffices:

function VACUUM-AGENT(percept) returns an action
    location, status <- percept
    if status = Dirty then return Suck
    else if location = A then return Right
    else if location = B then return Left

Now delete the location sensor from the S column. The percept becomes just Dirty or Clean, and no reflex rule over that single bit can reliably clean both squares without either wasting actions or looping; the agent now needs internal state, or a randomised policy, or a wall sensor. Alternatively, add "energy consumed" to the performance measure with a meaningful weight: the previously optimal policy of moving back and forth forever now scores badly, and the best agent learns to stop (or return to its dock) once both squares are clean. Neither change touched the agent program directly, yet both changed the design problem completely — which is exactly the point of insisting that all four elements be stated together.

Worked example: automated taxi driver

PEAS element Specification for an automated taxi driver
Performance measure Safe arrival at the destination (no collisions, injuries or near-misses); legality (obeying speed limits, signals, lane rules); passenger comfort (smooth acceleration, braking and cornering); minimised trip time; minimised fuel or battery cost; maximised profit per shift; courtesy to other road users; correct fare handling.
Environment Urban streets, motorways, junctions and roundabouts; lane markings, kerbs, road works and potholes; other vehicles with human or automated drivers; cyclists and pedestrians; traffic signals, signs and police instructions; weather conditions including rain, fog, ice and glare; day and night lighting; passengers in the cabin with preferences and destinations.
Actuators Steering wheel or steering motor; accelerator; brake; gear selector; turn indicators; headlights and wipers; horn; a display screen and synthesised voice for communicating with the passenger; door locks.
Sensors Video cameras (forward, rear and surround); radar and lidar for range and relative velocity; ultrasonic sensors for close-range parking; GPS plus inertial measurement for localisation; odometer and speedometer; accelerometer; engine, battery and tyre-pressure sensors; a keyboard, touchscreen or microphone for passenger input; network connection for traffic and map updates.

Several design lessons fall out of this table. The performance measure is multi-objective and the objectives genuinely conflict, so the weighting must be made explicit: safety and legality are normally treated as near-inviolable constraints, with time, fuel and comfort traded off inside them. The environment is manifestly partially observable (a cyclist behind a van is not visible), stochastic (a pedestrian may step out unpredictably), sequential (an early lane choice determines later options), dynamic (the world changes while the agent deliberates), continuous in both state and action, and multi-agent with both competitive elements (merging into a gap another driver wants) and cooperative ones (letting a bus pull out). The actuator list is also revealing: notice that "drive to the airport" is not an actuator. Actuators are the low-level effectors; high-level intentions must be compiled down into sequences of steering, throttle and brake commands, which is exactly why a taxi agent needs a hierarchy of planning and control rather than a flat reaction rule. Finally, note the communication actuators and sensors — the screen, voice, microphone and keyboard. A taxi that cannot ask "where to?" cannot do its job, yet these channels are routinely forgotten by beginners who think only in terms of physical motion.

Worked example: medical diagnosis system

PEAS element Specification for a medical diagnosis system
Performance measure Accuracy of diagnosis (with asymmetric costs for false negatives versus false positives); improvement in patient health outcomes and survival; minimised cost of tests and treatment; avoidance of harmful or unnecessary treatments; timeliness of diagnosis; clarity and traceability of the reasoning offered to clinicians; equity of performance across patient groups.
Environment Patients (who may be anxious, forgetful, inarticulate or untruthful); doctors, nurses and other hospital staff; electronic medical records and prior histories; laboratory and imaging facilities with queues and turnaround times; pharmacy and treatment resources; clinical guidelines, regulations and insurance constraints.
Actuators Display of follow-up questions to the patient or clinician; orders or recommendations for laboratory tests and imaging; display of a ranked differential diagnosis with confidence levels; proposed treatment plans; referrals to specialists; alerts and flags written into the patient record.
Sensors Keyboard or form entry of presenting symptoms and history; patient answers to the system's questions; structured data from the electronic health record; laboratory results and imaging reports; vital-sign monitors where available.

This example is valuable because it is a softbot: the environment is largely informational, and the actuators are displays and orders rather than motors. That does not make it any less of an agent — it senses, it acts, and its actions change the world (a test ordered is a test performed; a treatment recommended may be a treatment given). It also illustrates why the performance measure must be written carefully. "Diagnostic accuracy" alone is an inadequate measure for at least three reasons. First, the costs are asymmetric: missing a myocardial infarction is catastrophic, while a false alarm costs an unnecessary test, so a single accuracy percentage conceals the trade-off that matters. Second, an agent optimising accuracy alone would order every available test on every patient, which is ruinously expensive and sometimes physically harmful; the "minimised cost" and "avoidance of harmful treatments" terms are what make selective, sequential test-ordering rational. Third, the ultimate goal is patient health, not label-matching — a system that is accurate but so slow or so opaque that clinicians ignore it has achieved nothing. Note too the environment entry "patients who may be untruthful or forgetful": this is the specification admitting that the sensors are noisy, which immediately implies the agent must reason under uncertainty rather than treat percepts as ground truth.

Applying PEAS in practice

A workable procedure for producing a PEAS specification runs roughly as follows.

  • Start with the performance measure. Ask what outcomes the stakeholders actually care about, in the world, and write them down with their relative weights or constraint status. Stress-test the draft by looking for degenerate strategies that would score well while being obviously unacceptable, and patch the measure until those strategies are penalised.
  • Describe the environment honestly, including the awkward parts. List the objects, processes and other agents present, and explicitly note the sources of noise, uncertainty, change and adversarial behaviour. It is far cheaper to discover at specification time that the environment contains unpredictable pedestrians than to discover it on the road.
  • Derive the actuators and sensors from the measure and the environment. Ask: to influence each term of the performance measure, what must the agent be able to do? And to decide what to do, what must it be able to know? This derivation order matters — it prevents the common error of listing whatever hardware happens to be on the shelf and then hoping it suffices.
  • Check that every listed actuator and sensor is justified by the performance measure. Each entry should have a defensible answer to "which part of the score does this help with?" A sensor that no term in the measure requires is cost, weight, power draw, latency and a maintenance liability for no benefit; an actuator the agent never needs is an extra failure mode and, sometimes, an extra way to cause harm. Conversely, if a term in the measure cannot be influenced by any actuator, or cannot be assessed from any sensor, the specification is internally inconsistent and must be repaired — either by adding hardware or by changing the measure.
  • Treat the specification as a living document. Environments change. A warehouse robot specified for a single-shift, human-free facility faces a different task when night-shift staff are introduced: it now needs people-detection sensors, a safety term in its performance measure, and perhaps an audible warning actuator. A vacuum agent moved from a bungalow to a house with stairs needs cliff sensors it never previously required. Whenever the environment description changes, the sensor and actuator lists and the measure must be revisited; otherwise the agent is optimising for a world that no longer exists.
  • Hand the completed specification to the next two design steps. The E column feeds directly into classifying the task environment along the observability, determinism, episodicity, dynamism, discreteness and agent-count dimensions, and that classification in turn constrains which agent architecture is viable. The S column tells you whether the environment is fully or partially observable and therefore whether internal state is needed; the E column tells you whether the world is deterministic or stochastic, static or dynamic; the P column tells you whether a goal predicate suffices or whether graded trade-offs demand a utility function; and the A column bounds the action set that any planner or policy may use.

The payoff from this discipline is concrete. A PEAS description with a single binary dirt sensor and no location sensor tells you immediately that a simple reflex agent will be inadequate and that a model-based agent maintaining a belief about which squares have been visited is required. A PEAS description whose performance measure is a single all-or-nothing goal ("deliver the package to room 302") points toward a goal-based agent, whereas one with weighted, conflicting objectives ("arrive quickly and safely and cheaply and comfortably") points toward a utility-based agent that can compare partially satisfactory outcomes. A PEAS description whose environment entry admits "road conditions and passenger preferences vary in ways the designer cannot enumerate in advance" points toward a learning agent. In every case the architecture decision is read off the specification rather than chosen by habit — which is precisely why the specification comes first.

Classifying Task Environments

▶

Once an agent and its task have been specified — typically through a PEAS description naming the Performance measure, Environment, Actuators and Sensors — the next engineering question is: what kind of world is this agent operating in? Two tasks may look superficially similar and yet demand radically different machinery. A robot that inspects widgets on a conveyor belt and a robot that drives a taxi both perceive images and act in the physical world, but the first can be built from a single classifier that forgets everything after each decision, while the second needs maps, trackers, predictive models of other drivers, and a planner. The difference is not in the agent — it is in the task environment. Classifying task environments along a small set of well-chosen dimensions gives us a vocabulary for recognising this difference before a line of code is written.

The standard dimensions are six (sometimes counted as seven, if "known vs. unknown" is included): fully vs. partially observable, deterministic vs. stochastic, episodic vs. sequential, static vs. dynamic, discrete vs. continuous, and single-agent vs. multi-agent. Each is a question about the structure of the world, not about the agent's cleverness, and each has direct consequences for the agent's architecture.

Why classify task environments at all? The classification is useful because environment properties behave as design constraints: they rule particular agent designs in or out. If the environment is fully observable, static, deterministic, episodic, discrete and single-agent, then a lookup table or a set of condition–action rules suffices — the current percept contains everything the agent could possibly need. Weaken any one of those properties and that design breaks:

  • Drop full observability and the agent must maintain an internal state (a belief state) that summarises the percept history, because the current percept is no longer a sufficient statistic for choosing an action.
  • Drop determinism and the agent must reason about probability distributions over outcomes, hedge against failure, and be ready to re-plan when an action does not do what was expected.
  • Drop episodicity and the agent needs lookahead — search, planning, or a learned value function — because the consequences of today's action show up many steps later.
  • Drop staticness and the agent faces a deadline: deliberation itself has a cost, so anytime algorithms, reactive layers and continual re-sensing become necessary.
  • Drop discreteness and exhaustive enumeration of states and actions is impossible; the agent needs discretisation, sampling, function approximation or continuous optimisation.
  • Drop single-agency and the agent must model other decision-makers who are modelling it in return, bringing in game theory, opponent modelling, communication and negotiation.

A useful rule of thumb follows: harder environments generally require internal state, models, learning, or search over long horizons. Each "hard" label adds a capability requirement, and the requirements compose. An agent for a partially observable, stochastic, sequential, dynamic, continuous, multi-agent world — that is, the real world — needs essentially all of them at once, which is exactly why autonomous driving is a far larger engineering project than tournament chess, despite chess being the harder game.

Three further points about how the classification should be used. First, the dimensions are largely independent, so an environment is not a single category but a combination of labels: one speaks of "a partially observable, stochastic, sequential, dynamic, continuous, multi-agent environment". With six binary dimensions there are already sixty-four combinations, and most of them are genuinely instantiated by real tasks. Second, classification depends on how the task is defined — including the agent's sensors, actuators and performance measure. The environment is not an objective fact about the universe but a fact about the agent–environment pair. Third, real-world environments typically fall at the hard end of most dimensions, so the easy categories should be treated as idealisations we deliberately engineer towards (by adding sensors, constraining the workspace, fencing off the robot cell) rather than as something we find for free.

The dependence on task definition deserves emphasis because it is the most common source of confusion. Consider the same physical vacuum robot described three ways:

Likewise, if we define a taxi's performance measure as "get to the destination" the problem is sequential, but if we define a sub-task as "classify this traffic sign from this image", that sub-task is episodic. Classification is always relative to a task specification.

Fully observable vs. partially observable. An environment is fully observable if the agent's sensors give it access, at each point in time, to the complete state of the environment that is relevant to the choice of action. The key consequence is liberating: a fully observable environment means the agent need not maintain any internal state to track the world, because the world itself acts as its own perfect memory. The agent can be a pure function of the current percept.

Partial observability arises in two distinct ways, and it is worth keeping them apart:

  • Missing sensing: parts of the state are simply not sensed. A taxi cannot see around the corner, cannot see what is in the boot of the car ahead, and cannot see the intentions of the pedestrian at the kerb. A poker agent cannot see opponents' hole cards.
  • Noisy or inaccurate sensing: the relevant quantity is sensed, but imperfectly. A GPS fix carries several metres of error; a dirt sensor may occasionally report "clean" on a dirty square; a thermometer drifts. Here the agent has information about the state but not certainty.

Either way, the design consequence is the same: the agent must keep a belief state — a representation of which world states are currently possible, or a probability distribution over them — and update it as percepts and actions arrive. This is the move from a simple reflex agent to a model-based agent. The update has two halves, a prediction using a transition model and a correction using a sensor model:

belief <- InitialBelief()
loop:
    percept <- Sensors()
    belief  <- UpdateWithPercept(belief, percept)      # sensor model
    action  <- ChooseAction(belief)
    Actuators(action)
    belief  <- UpdateWithAction(belief, action)        # transition model

Examples make the contrast concrete. Chess with a visible board is fully observable: every piece's position is on the table, and nothing relevant is hidden (castling and en-passant rights are usually folded into the state definition). Poker is partially observable because opponents' cards are hidden — and indeed much of the skill of poker consists in inferring the hidden state from betting behaviour. Automated driving is partially observable because of occlusions, sensor noise, weather and the unobservable mental states of other road users. And in the small vacuum world, an agent with only a local dirt sensor cannot see the other square, so even that toy domain becomes partially observable: after cleaning square A the agent must remember or assume something about B in order to act sensibly.

A limiting case worth naming is the unobservable or sensorless environment, where the agent perceives nothing at all. Surprisingly, such agents can still succeed if the environment is deterministic: a sensorless vacuum agent executing Suck, Right, Suck cleans both squares from any starting configuration, because the action sequence drives the entire belief state into a goal state. This shows that "partially observable" is not synonymous with "hopeless" — it means the agent must reason about sets of possible states rather than single states.

Deterministic vs. stochastic. An environment is deterministic if the next state is completely determined by the current state and the action executed by the agent; otherwise it is stochastic. In a deterministic world the agent can predict outcomes exactly and plan with certainty: a plan computed offline will execute as imagined, so classical search and planning techniques, which assume a single predicted successor per action, are sound.

In a stochastic world the agent must reason about probabilities and handle unexpected results. Three consequences follow. The agent's plans become contingent (branching on what actually happens) or policies (a mapping from state to action, defined everywhere) rather than linear action sequences. The agent's objective shifts from "achieve the goal" to "maximise expected utility", because outcomes are now random variables. And the agent needs an execution-monitoring loop that detects deviation and re-plans.

Taxi driving is stochastic in every respect: traffic density, weather, whether a light turns amber as you approach, and the possibility of a tyre blowout are all unpredictable from the agent's point of view. By contrast, a simple grid vacuum world with reliable actions is deterministic — Right always moves the agent right, Suck always cleans. (Add a 10% chance that Suck deposits dirt instead, as in the "slippery" variants, and the world becomes stochastic and the optimal behaviour changes.)

Two subtleties. First, stochasticity in this sense is epistemic as much as physical: a tyre blowout is governed by deterministic physics, but because the agent cannot sense tread micro-fractures, it must model the event as random. The practical test is not "is the universe random?" but "can this agent, with these sensors, predict the outcome?" This also means that a partially observable environment will usually be modelled as stochastic even if the underlying dynamics are deterministic. Second, if an environment is deterministic except for the actions of other agents, it is conventionally called strategic (or sometimes "deterministic but multi-agent"). Chess is the canonical example: the board evolves deterministically given both players' moves, and the uncertainty comes entirely from not knowing the opponent's choice. The distinction matters because strategic uncertainty is handled by adversarial search and game theory (minimax, equilibrium reasoning) rather than by probability over nature's coin flips.

A third label sometimes used is nondeterministic, reserved for environments where actions have multiple possible outcomes but no probabilities are attached. There the agent typically plans for the worst case ("a plan must work no matter which outcome occurs"), whereas in a genuinely stochastic environment it optimises the expectation.

Episodic vs. sequential. In an episodic task environment the agent's experience is divided into atomic episodes. In each episode the agent perceives and then performs a single action, and crucially the choice of action in one episode does not affect any later episode. The agent can therefore decide each case in isolation without looking ahead.

The classic example is a defect-detection robot on an assembly line: it sees a part, decides "pass" or "reject", and the next part arrives in a state entirely unaffected by that decision. Spam filtering, medical image classification, and optical character recognition are episodic for the same reason. Such environments are simpler precisely because the agent does not need to think ahead; the whole problem reduces to learning a good percept-to-action mapping, which is why supervised machine learning fits episodic tasks so naturally.

In a sequential environment, by contrast, current decisions affect all future decisions. Chess and taxi driving are sequential: a pawn structure weakened on move 8 may lose the endgame forty moves later; a missed motorway exit costs ten minutes and a different set of future choices. Sequential environments therefore require search, planning, or lookahead over sequences of actions — minimax or Monte Carlo tree search in games, A* or hierarchical planning in robotics, dynamic programming and reinforcement learning when outcomes are stochastic. They also introduce the credit assignment problem: when a long sequence ends badly, which action was to blame?

A common error is to equate "episodic" with "short". An episode may involve a lengthy computation; what matters is that episodes are independent. Conversely, a chess move takes a second to play but is deeply sequential. Note too that the same physical system can be decomposed into episodic sub-tasks nested inside a sequential whole: a self-driving car's "recognise this traffic sign" module is episodic even though "drive to the airport" is sequential.

Static vs. dynamic. An environment is static if it cannot change while the agent is deliberating; it is dynamic if it can. Static environments remove time pressure, which is a substantial simplification: the agent may take as long as it likes to compute the best action, it need not re-sense the world during deliberation, and it need not worry that the state it is reasoning about has already gone stale.

Crossword puzzles are static — the grid will patiently wait while you think about 14-across for an hour. Taxi driving is dynamic: traffic keeps moving while the agent deliberates, so a plan computed from a two-second-old snapshot may already be dangerous. In dynamic environments, inaction is itself a choice: if the agent has not decided what to do by the time the car ahead brakes, it has effectively decided to keep its current speed and will crash. This makes real-time response guarantees a first-class design requirement, and it motivates anytime algorithms (which always have a usable answer available and improve it with more time), reactive safety layers that bypass deliberation, and continuous re-sensing, because plans may become stale and must be validated against fresh percepts.

Between the two lies the semi-dynamic case: the environment itself does not change with time, but the agent's performance score does. Chess played with a clock is semi-dynamic — the pieces do not move while you think, but your remaining time drains away and slow deliberation is penalised, eventually by loss on time. Correspondence chess with no time limit is static; blitz chess is strongly semi-dynamic and is played with heuristics and pattern recognition rather than deep search. The same mechanism appears outside games: a diagnostic system billed by compute-seconds is semi-dynamic.

Discrete vs. continuous. This distinction applies separately to the state of the environment, to the handling of time, and to the agent's percepts and actions; an environment can be discrete along one axis and continuous along another.

  • Chess has a finite, discrete set of board states and a finite set of legal moves per turn (typically 20–40), and time advances in discrete ply. This is what makes exhaustive enumeration meaningful: one can in principle generate every successor state, and algorithms like minimax with alpha–beta pruning are built on exactly that ability.
  • Taxi driving is continuous in state and in time: position, velocity, heading, steering angle and throttle all vary smoothly, and the vehicle's configuration changes continuously rather than in ticks. There is no "next state" to enumerate — between any two steering angles lie infinitely many others.

Because enumeration is impossible, continuous domains usually require discretisation, approximation, or specialised numeric methods. Typical responses include: sampling the action space (consider steering angles in 2° increments); sampling the state space (probabilistic roadmaps, rapidly-exploring random trees); representing value or policy functions with parametric approximators such as neural networks instead of tables; and using gradient-based or convex optimisation, Kalman filters and other techniques designed for real-valued variables. Discretisation always trades fidelity for tractability, and a key design judgement is how fine a grid the task's performance measure actually demands.

A nuance worth noting: camera input is technically discrete — a fixed array of pixels, each with a bounded integer intensity — yet it is almost always modelled as continuous intensities and continuous object positions, because the discretisation is so fine that continuous mathematics (convolution, interpolation, sub-pixel estimation) gives better answers than treating each pixel value as a distinct symbol. This reinforces the earlier point: these labels describe the model we choose for the task, and the right choice is the one that supports the most effective algorithms.

Single-agent vs. multi-agent. The last dimension asks whether other entities in the environment must be modelled as agents — that is, as decision-makers — or merely as part of the physics. The operative test is behavioural rather than metaphysical: an entity counts as an agent if its behaviour is best described as maximising a performance measure whose value depends on your agent's actions. A beach whose waves raise and lower the sand is not an agent, because the waves are not trying to do anything in response to you; a chess opponent is, because their score depends directly on your moves and they will choose their moves accordingly. Occasionally it is useful to treat a non-agent as an adversary (robust control treats "nature" as a malicious player), and occasionally it is useful to treat an agent as a stochastic process (modelling pedestrians by statistical trajectory distributions rather than by reasoning about their goals) — this is a modelling decision driven by what works.

Chess is competitive in the pure sense: by the rules, one agent's success entails the other's failure, so the two performance measures sum to a constant. Taxi driving is mixed — all drivers share the strong goal of avoiding collisions, which makes the environment partially cooperative and gives rise to conventions such as lane discipline, indicator signals and right-of-way rules; yet drivers compete for a single parking space or for a gap in merging traffic. Multi-agency brings genuinely new requirements. It introduces communication as a rational action (flashing headlights to yield; broadcasting an intended route), negotiation and commitment (bidding, contracts, conventions), and game-theoretic reasoning, including the recursive problem that the other agents are modelling you while you model them. It is also the main source of strategic uncertainty and often the reason randomised policies are optimal — in poker or rock–paper–scissors, any deterministic policy is exploitable, so rationality itself requires a mixed strategy. Finally, multi-agent environments are usually dynamic by construction, since other agents act while you deliberate.

A known environment may be stochastic (the rules of backgammon, including the dice distribution, are fully known) and an unknown one may be deterministic (a new video game whose physics you must discover by experiment). An unknown environment is the defining reason to build a learning agent.

Once you can describe an agent in terms of sensors, actuators, and a PEAS specification, the next step is to characterize the world the agent operates in. AI researchers use six standard dimensions for this: fully vs. partially observable, deterministic vs. stochastic, episodic vs. sequential, static vs. dynamic, discrete vs. continuous, and single-agent vs. multi-agent. Each dimension is a question you ask about a task before you design anything: Can the agent see everything it needs to? Does the same action always produce the same result? Do earlier decisions constrain later ones? Is the world changing while the agent deliberates? Are there finitely many states and actions, or a continuum? Is anything else in the environment pursuing its own goals?

This classification matters because it is the single best predictor of how hard a task is and which agent architecture you will need. A fully observable, deterministic, episodic, static, discrete, single-agent environment can often be handled by a simple lookup or reflex rule. Weaken any one of those properties and you start needing internal state, probabilistic reasoning, search over sequences, or models of other agents. The vocabulary also lets you compare very different tasks — chess, a vacuum robot, a taxi, a medical diagnosis system — on the same scale.

Applying Environment Properties to Real Tasks

1

Applying Environment Properties to Real Tasks

▶

Classifying a task environment is the diagnostic step that sits between stating what an agent must achieve and choosing how to build it. The six classical dimensions — observability, agent count, determinism, episodicity, dynamism, and discreteness — are not academic labels; each one eliminates certain agent architectures and forces others. An agent designer who skips this step typically discovers the mismatch late, when a reflex controller fails in a world that silently demanded memory, or when an exhaustive search is applied to a continuous action space. This topic works through a repeatable checklist, applies it to five familiar domains, and then shows how the resulting profile maps onto concrete design choices and techniques.

A checklist for classifying any task environment. The checklist is a short sequence of questions whose answers, taken together, form an environment profile. The discipline of asking them in a fixed order matters because the answers interact: partial observability, for instance, changes what "deterministic" even means in practice.

  • Can the sensors see the full state, or only part of it? The test is not "does the agent receive a lot of data" but "do the percepts at each step determine every aspect of the environment state that is relevant to the performance measure?" If a chess agent looks at the board, it sees everything it needs; if a poker agent looks at the table, the opponents' hole cards — decisive for the outcome — remain hidden. Note the extreme case of an unobservable (sensorless) environment, where the agent must act blind and reason about the set of states it might be in.
  • Are there other agents whose behaviour affects the performance measure, and are they cooperative or competitive? An entity counts as an agent when it is useful to model it as maximising a performance measure that depends on your behaviour. A falling rock is stochastic weather; a blocking defender is an opponent. If maximising their measure tends to minimise yours, the setting is competitive; if the measures are aligned, it is cooperative. Many real settings — driving, negotiation, warehouse fleets — are partially cooperative: all parties want to avoid collisions, but each also wants the faster route.
  • Does the next state follow uniquely from the current state and action, or is there stochastic or unmodelled variation? The agent must be able to predict the successor exactly for the environment to count as deterministic. Importantly, "exactly" is evaluated relative to the agent's model and percepts, not to physics in the abstract.
  • Are decisions independent episodes, or do they commit the agent to future consequences? In an episodic environment the experience divides into atomic episodes — perceive, act, receive a score — and the action chosen in one episode does not affect the next. In a sequential environment, each action shapes the states, options, and rewards available later, so short-term decisions must be made with long-term consequences in mind.
  • Does the world change while the agent deliberates, and are states, time, and actions discrete or continuous? If the environment can change during deliberation, it is dynamic and thinking has a cost measured in lost opportunity or safety margin. If the environment is fixed but the performance score decays with time, it is semi-dynamic. Discreteness is asked separately of the state space, the time base, and the action set — these can differ within a single task.
  • Record the answers as a profile, then match that profile to candidate agent designs. Write the profile as a tuple, for example <partially observable, multi-agent (mixed), stochastic, sequential, dynamic, continuous>, and keep it next to the design document. Each entry is a constraint; the architecture must satisfy all of them simultaneously. A useful habit is to also record whether the environment is known (the agent has the transition and reward rules) because this is orthogonal to observability and drives whether learning is required.

Chess and poker: observability and opponents. These two games differ along only two dimensions, yet those two differences change almost everything about the algorithms that work.

  • Chess is fully observable — the board shows the whole state, and the castling, en-passant, and repetition flags are reconstructible from the move history. It is deterministic: moving a rook to e4 produces exactly one successor position. It is sequential: a pawn pushed on move 12 may lose the game on move 55. It is static in its untimed form and semi-dynamic with a clock, since the position does not change while you think but your remaining time does. It is discrete in states, time (moves), and actions (legal moves), and it is multi-agent competitive — strictly zero-sum between two players.
  • Poker shares the sequential, multi-agent competitive, and largely discrete character of chess, but it is partially observable because opponents' hole cards are hidden, and stochastic because the shuffle determines future community cards. Betting amounts in no-limit variants also make a portion of the action space effectively continuous or very large.
  • Chess supports minimax and alpha-beta search over a known game tree. Because the state is fully visible and transitions are deterministic, the agent can expand a tree of exact future positions, apply a heuristic evaluation at the depth limit, and back up values assuming an optimal opponent. Alpha-beta pruning exploits the zero-sum structure to discard branches that cannot affect the root decision, roughly squaring the depth reachable in a fixed time budget. The semi-dynamic clock is handled by iterative deepening, which yields a usable move whenever time runs out — an anytime property.
  • Poker requires belief states, probabilistic reasoning, and mixed strategies. The agent cannot search over states; it must search over belief states — probability distributions over the opponents' possible holdings, updated by Bayes' rule as betting actions reveal information. Chance nodes in the tree require taking expectations rather than maxima (expectimax). Crucially, because the opponent can observe your behaviour, any deterministic policy is exploitable: if you only raise with strong hands, opponents simply fold. The game-theoretic solution concept is a Nash equilibrium in mixed strategies, so the agent deliberately randomises — bluffing a fixed fraction of the time — to keep its beliefs about you uninformative. Modern solvers approximate this with counterfactual regret minimisation rather than classical minimax.
  • Both are sequential, so neither can be solved by a reflex agent that ignores history. A lookup from "current board" to "move" without lookahead plays badly in chess because the value of a position is defined by what can happen later; in poker, a reflex agent additionally discards the betting history that is the only evidence about hidden cards.

Automated driving: the hard case. Driving is the standard example of a task that is "hard" in every dimension at once, which is precisely why it resists the clean algorithms that solve board games.

  • Partially observable. A parked van occludes the crossing pedestrian; a vehicle sits in the blind spot; and — most fundamentally — the intentions of other drivers are internal mental states that no sensor reads. A car drifting toward the lane line may be changing lanes, avoiding a pothole, or drifting through inattention, and these have different safe responses.
  • Stochastic. Tyre slip on a wet surface, a child stepping off a kerb, a gust of crosswind, and the exact deceleration of the car ahead cannot be predicted exactly. Even where the underlying physics is lawful, the agent has no model precise enough to make exact predictions, so the practical treatment is probabilistic.
  • Sequential and dynamic. Choosing the right-hand lane now determines which exits are available in two kilometres. More sharply, the world does not pause for deliberation: at 30 m/s a vehicle covers three metres during a 100 ms planning cycle. Latency therefore becomes a safety constraint, not merely a performance nuisance, and the system must produce a safe action on a hard real-time deadline whether or not the search has converged.
  • Continuous and multi-agent with mixed incentives. Pose, velocity, steering angle, and throttle are real-valued, and time is continuous (approximated by a fast control loop). Other road users are agents: largely cooperative, since nobody wants a collision and lane-merging requires implicit negotiation, but competitive over scarce resources like gaps, parking spaces, and travel time.
  • Design consequences. The profile mandates sensor fusion (camera, radar, lidar, GPS/IMU combined because no single modality is reliable in all conditions); probabilistic state estimation (Kalman/particle filters for self-localisation and multi-object tracking, plus intention prediction over other agents); continuous control (MPC or PID layered below the planner); and online replanning on a rolling horizon rather than a single offline plan computed before departure. A typical architecture is layered: a fast reactive safety layer (emergency braking) beneath a deliberative planner, so that a slow plan never prevents a quick stop.

Image classification: an episodic, static environment. The contrast with driving is instructive, because image classification is the easy end of almost every dimension — and that is why a single feed-forward function suffices.

  • Episodic. Labelling photograph n as "tabby cat" does not change which photograph is presented as n+1, nor does it alter the correct answer for it. Each episode is perceive–classify–score, atomically. (The caveat: if the system is deployed in a feedback loop where its outputs choose the next images to collect or moderate, episodicity is lost and the task becomes sequential.)
  • Static. The pixel array is frozen while the network runs. Taking an extra 50 ms costs nothing in accuracy, which is why the design question is throughput rather than deadline safety.
  • Deterministic from the agent's side — the same input yields the same output, and the "state" is simply the presented image. The subtlety is that the labelling may be noisy or genuinely ambiguous (is that a wolf or a husky?), so the mapping from image to ground-truth label behaves stochastically. This is why classifiers output a probability distribution rather than a single hard label.
  • Single-agent under normal operation: no entity is choosing images to minimise your accuracy. Introduce an adversary generating adversarial examples — imperceptible perturbations crafted to flip the prediction — and the environment becomes multi-agent competitive, which changes the design to adversarial training and robustness certification.
  • Architectural consequence. Because the task is episodic, fully observable within the episode, and static, there is nothing to plan and no history worth remembering. A learned feed-forward mapping from percept to action — the classifier — is exactly the right shape of solution, and it is in fact a learning reflex agent: a condition–action mapping whose conditions were induced from data rather than written by hand.

Indoor robot navigation: partial observability meets continuity. This domain sits between the two extremes and is the canonical motivation for belief-space methods.

  • Partially observable. A lidar or sonar ring reports distances to nearby surfaces only; corridors look alike, and two different poses can produce near-identical scans (perceptual aliasing). The robot therefore cannot know its pose from a single percept and must maintain a belief — a probability distribution over poses — updated by Monte Carlo (particle) localisation that combines motion prediction with sensor correction.
  • Stochastic. Commanding "drive forward 1 m" yields perhaps 0.97 m with a 2° heading error because of wheel slip, uneven floors, and encoder quantisation. Sensor readings are noisy and occasionally spurious (specular reflections from glass). Odometry error compounds, which is why dead reckoning alone diverges within metres.
  • Sequential. Each move changes both what is reachable and what is observable next, which creates an exploration–exploitation tension specific to partial observability: it can be worth detouring to a feature-rich corner purely to reduce pose uncertainty before attempting a narrow doorway. This is information-gathering action selection, impossible in a purely reactive design.
  • Dynamic and continuous. People walk through corridors, doors open and close, and furniture moves, so the map is only partly valid. Pose, velocity, and time are continuous, so the planner works over sampled or discretised representations (occupancy grids, probabilistic roadmaps, RRTs) rather than enumerating states.
  • Agent count. A single service robot is single-agent with dynamic obstacles. A warehouse fleet is multi-agent cooperative: robots must avoid deadlock at intersections and share a common throughput objective, which calls for centralised traffic management or explicit communication and conflict-based multi-agent path finding.

From environment profile to agent architecture. Each dimension of the profile acts as a filter on the design space. Reading the profile left to right produces a specification of the minimum capability the agent must have.

  • Partial observability forces internal state or a belief state, which immediately rules out a simple reflex agent. A reflex agent maps the current percept to an action; if the current percept does not determine the relevant state, the same percept must sometimes lead to different correct actions, and a stateless mapping cannot express that. The minimum upgrade is a model-based reflex agent that carries a state estimate updated by a transition model and a sensor model. Where uncertainty is substantial, the state estimate becomes a full distribution and the problem is formally a POMDP, solved approximately by belief-space planning, filtering plus most-likely-state planning, or recurrent policies.
  • Stochasticity pushes the agent from plans toward policies. A fixed sequence of actions is fragile when outcomes branch: by step three, the agent may not be where the plan assumed. The robust object is a policy, a mapping from state (or belief) to action defined for every contingency. Decision quality is then measured by expected utility, which also means the agent needs a utility function rather than a binary goal test, since it must trade a high chance of a decent outcome against a small chance of a disastrous one. MDP solution methods (value iteration, policy iteration) and reinforcement learning are the natural tools.
  • Sequential structure requires lookahead. When current actions constrain later ones, an agent must evaluate actions by their downstream consequences — through search over a transition model, through classical planning, or, when the model is unknown, by learning a value function from experience. This is the dimension that separates a classifier from a chess engine even though both "map input to output".
  • Dynamic environments impose real-time deadlines. Computation competes with the world. The practical responses are anytime algorithms, which maintain a valid answer that improves monotonically with time (iterative deepening, receding-horizon MPC, Monte Carlo tree search), and layered architectures in which a fast reactive layer guarantees a safe default while a slower deliberative layer improves on it. Deliberation itself becomes a decision: metareasoning asks whether another 50 ms of thinking is worth more than acting now.
  • Continuous spaces forbid exhaustive enumeration. There is no "list of all states" or "list of all steering angles". The three standard responses are discretisation (occupancy grids, a finite set of candidate trajectories), sampling (RRT, particle filters, Monte Carlo rollouts), and function approximation (neural networks or linear features representing value functions and policies over real-valued inputs), often combined with gradient-based optimisation in the control layer.
  • Multi-agent settings demand opponent modelling or coordination machinery. Against adversaries, the agent must assume the other party responds to its choices, which brings in minimax, equilibrium computation, and randomised policies to avoid exploitation. Among cooperators, it needs shared conventions, explicit communication protocols, or a joint planner, plus mechanisms for deadlock resolution and task allocation.

Applying this mapping to the five domains yields the architectures observed in practice. Image classification — fully observable, episodic, static, single-agent — needs none of the upgrades, so a learned reflex mapping is optimal and anything more is wasted complexity. Chess needs lookahead and opponent modelling but no belief state or function over continuous actions, so deterministic adversarial search suffices. Poker adds partial observability and chance, so belief tracking and randomisation appear. Robot navigation adds continuity and noise, so filtering plus sampling-based planning appear. Driving requires every single upgrade simultaneously, which is a direct explanation of why it remains an unsolved engineering problem rather than a solved algorithmic one.

Common classification pitfalls. Most misclassifications come from a handful of recurring confusions, each of which leads to a concrete design error.

  • Determinism is judged from the agent's viewpoint. A die roll is governed by Newtonian mechanics, yet no practical agent can model the tumble; it is therefore stochastic for that agent. The same applies to tyre friction and pedestrian behaviour. The right question is not "is the world lawful?" but "can this agent, with these sensors and this model, predict the successor state exactly?" The related term nondeterministic is reserved for the case where the agent knows the set of possible outcomes but has no probabilities — which calls for contingency planning or worst-case reasoning rather than expected-utility maximisation.
  • Episodic does not mean short. A single-image classification lasting ten minutes is still episodic; a thirty-second game of speed chess is still sequential. The test is causal coupling, not duration: does this decision change the states, options, or payoffs available to later decisions? Part-picking on a conveyor is episodic even over an eight-hour shift, because each part is independent. Conversely, labelling one frame of a video stream used to track an object is sequential, because the track carries over.
  • Fully observable does not mean omniscient. Full observability concerns the current environment state, not the future and not other agents' internal reasoning. A chess agent sees the whole board yet cannot know which move its opponent has chosen or how the game will end. Full observability removes the need for state estimation; it does not remove the need for search, prediction, or opponent modelling.
  • Known and observable are different axes. "Known" refers to the agent's knowledge of the rules — the transition and reward models. "Observable" refers to access to the current state. Poker is a known but partially observable environment: the probabilities of every deal are computable, yet the opponent's cards are hidden. The inverse exists too — a new video game may be fully observable on screen while the effects of actions are entirely unknown and must be learned. Known environments allow model-based search; unknown ones require exploration and learning.
  • Semi-dynamic environments are easily mislabelled as static. In timed chess the position is frozen while you think, which tempts the label "static" — but your score degrades with deliberation time, and a flagged clock loses the game outright. Treating it as static would justify an unbounded search; recognising it as semi-dynamic forces an anytime algorithm with explicit time management. The same applies to any task with a response-time component in its performance measure, such as an online auction bidder or a fraud-detection system that must decide before the transaction clears.
  • A further trap: dimensions are relative to how the task is framed. The same physical domain can be classified differently depending on where the agent boundary and performance measure are drawn. Taxi driving is episodic if the performance measure is per-passenger comfort evaluated moment by moment, and strongly sequential if it is fuel efficiency and routecompletion over a shift. Similarly, a single-image classifier is episodic, but the same network embedded in a video-tracking pipeline is one step of a sequential task. Always state the agent boundary, sensors, and performance measure before classifying, and record the framing alongside the profile so that later designers know which assumptions the architecture rests on.

A practical way to close the loop is to write the profile and the derived requirements as a short artefact at the start of a project, for example:

Task: warehouse picking robot
Profile: partially observable, multi-agent cooperative, stochastic,
         sequential, dynamic, continuous, known map / unknown dynamics
Implications:
  partial observability -> particle-filter localisation + occupancy map
  stochastic            -> policy with expected-cost evaluation, not fixed plan
  sequential            -> receding-horizon path planner
  dynamic               -> 20 Hz reactive obstacle layer, anytime global planner

  multi-agent coop      -> central traffic manager, reservation-based intersections

Each line of the implications block is traceable to exactly one line of the profile, which makes the design reviewable: if a reviewer disputes the architecture, the argument moves to the classification, where it can be settled by inspecting the sensors and the performance measure rather than by preference.

From Specification to Agent Design

▶

Designing an agent is not an act of inspiration; it is a disciplined translation. You begin with a task specification — a statement of what counts as success, what world the agent inhabits, what it can do, and what it can perceive — and you end with an architecture: a concrete arrangement of components that computes actions from percepts. The central claim of this topic is that the specification largely determines the architecture. If you write the specification carefully, the right agent design is mostly read off from it; if you write it carelessly, you will build a competent machine that is competent at the wrong thing.

The vocabulary for this translation is PEAS — Performance measure, Environment, Actuators, Sensors — together with the standard dimensions along which task environments are classified. The agent architectures available are, in increasing order of sophistication, the simple reflex agent, the model-based reflex agent, the goal-based agent, the utility-based agent, and the learning agent (which is an outer wrapper that can enclose any of the others). What follows works through how each element of PEAS constrains the design, what each architecture assumes about the world, and a repeatable workflow that moves from a blank page to an evaluated implementation.

From PEAS specification to design decisions

Each of the four PEAS components carries distinct design information. Treating PEAS as a box-filling exercise wastes that information; treating it as a set of constraints on the agent program is where its value lies.

The performance measure defines the objective function. The performance measure is specified externally, by the designer or by the world, and it describes desirable states of the environment rather than desirable states of the agent. This matters architecturally. If the performance measure can be written as a predicate — "the patient is correctly diagnosed", "all squares are clean", "the blocks are stacked in the required order" — then a goal-based design is natural, because the agent only needs to distinguish satisfying states from non-satisfying ones. If instead the performance measure is a weighted combination of several quantities that trade off against one another — "arrive quickly, use little fuel, obey traffic law, maximise passenger comfort, minimise risk of collision" — then a binary goal is simply the wrong representational tool, and the specification is already telling you that you need a utility function. A useful diagnostic question is: can two different successful outcomes be ranked? If yes, you need utilities; if all successes are interchangeable, goals suffice.

The performance measure also encodes the time horizon and the attitude to risk. "Minimise expected travel time" and "minimise worst-case travel time" lead to different decision rules in a stochastic environment even though both mention only travel time. And because performance is measured on the environment, not on the agent's beliefs, a self-satisfied agent that believes it has cleaned the floor scores zero if the floor is dirty — which is exactly why sensing and internal state matter.

The environment description reveals the hard parts. When you write out the environment for an automated taxi — urban roads, pedestrians, other drivers, weather, roadworks, traffic signals, passengers with changing requests — you are implicitly declaring partial observability (you cannot see around the corner or inside another driver's head), stochasticity (a pedestrian may step off the kerb), dynamism (the world changes while you deliberate), continuity (position, velocity and steering angle are real-valued), and multi-agent interaction, including adversarial elements such as a driver racing you for a parking space. Each of these flags a required capability: state estimation, probabilistic reasoning, anytime or real-time decision-making, discretisation or continuous control, and opponent modelling.

The actuator list bounds the action space. The agent can only ever do what its actuators permit, so the actuator list fixes the branching factor of any search, the granularity of control, and the vocabulary in which plans are expressed. A taxi with steer, accelerate, brake, signal, horn, and display/speak has a continuous low-level action space; a route planner working over the same vehicle may use an abstracted action space of take next left, continue, stop at kerb. Choosing the abstraction level of the actions is itself a design decision, and it has to be compatible with both the real actuators and the time available for deliberation. A medical diagnosis agent whose only actuators are "display questions, order tests, display diagnosis and treatment" cannot cure anyone directly; its performance measure must therefore be about information and recommendations, not about surgical outcomes.

The sensor list determines the percept sequence. Sensors fix what is in each percept, and therefore what the agent can know directly. A taxi with cameras, lidar, GPS, speedometer, accelerometer, engine sensors and a keyboard for the passenger receives, at each instant, a rich but strictly local snapshot. Nothing in that snapshot says how much fuel was burned over the last hour, whether the vehicle behind has been tailgating for ten minutes, or that the bridge ahead was closed five minutes ago. Those facts can only be obtained by accumulating percepts into internal state.

Bridging the gap. The most important single question in agent design is: is there a gap between what the sensors reveal and what the performance measure requires? If the current percept fully determines the current state, and the current state fully determines the best action, the agent program can be a lookup from percept to action. Any mismatch must be bridged by internal reasoning — state estimation to recover unobserved variables, prediction to anticipate future states, search to evaluate consequences, probability to handle uncertainty, and learning to supply knowledge the designer did not have.

PEAS elementQuestion it answersDesign consequence
Performance measureWhat counts as doing well, and can successes be ranked?Binary predicate → goals; multi-attribute or risky → utility; unknown in advance → learning with an external standard
EnvironmentWhat is out there, and how does it behave?Drives environment classification: observability, determinism, dynamism, agency; dictates need for models and uncertainty
ActuatorsWhat can the agent change?Fixes the action set, branching factor, control granularity, and plan vocabulary
SensorsWhat can the agent know directly?Fixes the percept sequence; shortfall versus the state needed → internal state and a sensor model

Simple reflex agents: when percepts are enough

A simple reflex agent selects actions using only the current percept, typically via condition–action rules:

function SIMPLE-REFLEX-AGENT(percept) returns an action
    persistent: rules, a set of condition-action rules

    state  <- INTERPRET-INPUT(percept)
    rule   <- RULE-MATCH(state, rules)
    action <- rule.ACTION
    return action

This is the cheapest architecture available: constant-time lookup, no memory, no model, trivially easy to verify. It is the correct choice under two conditions that must both hold.

  • Full observability. The current percept must contain everything relevant to the decision. In the two-square vacuum world, the percept [location, status] is enough for the rule set "if dirty then Suck; if in A and clean then Right; if in B and clean then Left" to be optimal, because the only facts that matter are where you are and whether that square is dirty.
  • Episodic structure (or at least no need for history). If each decision is an independent episode — a part-picking robot classifying the object currently on the conveyor belt as "defective" or "acceptable" — then nothing learned in previous episodes alters the current correct action. Reflex rules match the task's logical shape exactly.

Simple reflex agents fail, often spectacularly, under partial observability. Remove the location sensor from the vacuum agent so that the percept is only [status]. Now the rule "if clean then Right" sends the agent off the right edge of the world forever, and "if clean then Left" strands it in the left square; no deterministic percept-to-action mapping can clean both squares, because the agent cannot tell the two "clean" situations apart. The characteristic failure modes are infinite loops and repeated mistakes: the agent keeps re-entering the same percept and keeps emitting the same wrong action. A braking rule keyed on "if the car in front shows brake lights then brake" fails at night, in fog, or when the lead vehicle's lights are broken — the percept simply does not carry the needed fact.

Randomisation is a genuine but partial remedy. A vacuum agent that flips a coin between Left and Right when it perceives "clean" will, with probability 1, eventually visit and clean both squares, and it outperforms any deterministic memoryless agent in that environment. Randomisation is also essential in adversarial multi-agent settings, where predictability is exploitable. But it is not a substitute for memory: a randomising agent still cannot answer "have I already checked that room?" and its expected performance is usually far below that of an agent with even a little internal state.

The design rule is blunt: if PEAS analysis shows the sensors cannot reveal the state features that the performance measure depends on, reject the simple reflex design. No amount of rule tuning repairs a missing percept.

Model-based agents: handling partial observability

A model-based reflex agent keeps an internal state that summarises the percept history, and updates it as new percepts arrive:

function MODEL-BASED-REFLEX-AGENT(percept) returns an action
    persistent: state, the agent's current conception of the world
                transition_model, how the world evolves and how actions affect it
                sensor_model, how world states give rise to percepts
                rules, a set of condition-action rules
                action, the most recent action, initially none

    state  <- UPDATE-STATE(state, action, percept, transition_model, sensor_model)
    rule   <- RULE-MATCH(state, rules)
    action <- rule.ACTION
    return action

Two kinds of knowledge make this work.

  • The transition model answers "how does the world change?" It has two parts: how the world evolves independently of the agent (traffic ahead keeps moving, rain continues, the patient's infection progresses) and how the world changes as a result of the agent's own actions (turning the wheel right while moving changes heading; sucking makes the current square clean). The second part also supports dead reckoning: after issuing Right, the vacuum agent can infer it is now in square B even without a location sensor.
  • The sensor model answers "what percepts would a given world state produce?" It is the inverse direction of inference: a lidar return pattern implies the presence of an obstacle at a distance; a blurred camera frame implies either motion or a dirty lens; a fever plus an elevated white-cell count implies a set of candidate infections. In the probabilistic setting this is precisely P(percept | state), and combining it with the transition model P(state' | state, action) gives recursive state estimation (filtering).

Crucially, the internal state is a best guess, not the truth. In a partially observable world the agent should ideally maintain a belief — a probability distribution or at least a set of states consistent with the history — rather than committing to one hypothesis. Dynamic and stochastic environments sharpen this requirement: if the world changes while the agent deliberates, stale state must be extrapolated forward; if actions have uncertain outcomes, the agent must represent the spread of possibilities rather than assuming its last action succeeded. A warehouse robot whose wheels slip must treat its dead-reckoned position as an estimate with growing error, and re-anchor it whenever it sees a landmark.

In multi-agent environments the model has to be extended to include other agents: their positions and velocities, but also their likely intentions and policies. An automated taxi that models the car in the next lane merely as a moving box will be surprised by a merge; one that models the driver as an agent with a goal ("he is indicating, he wants this lane, he will accelerate into the gap") can act pre-emptively. In competitive settings this becomes adversarial modelling; in cooperative ones it becomes coordination and communication.

Note what a model-based agent still does not do: it does not consider the future consequences of its options. It has a better-informed state, but the decision is still a rule lookup. That is the next step.

Goal-based agents: reasoning about the future

Knowing the current state is not sufficient when the right action depends on where you are trying to end up. At a T-junction, a model-based taxi knows exactly where it is, which lane it occupies, and what the traffic is doing — and still has no basis for choosing left over right until it is told the destination. The goal supplies that basis.

  • Goals are typically binary. A goal is a predicate over states, partitioning them into "satisfies the goal" and "does not". at(Passenger, Destination) is either true or false. This simplicity is a strength (it makes the problem a search problem) and a weakness (it cannot express "arriving in 20 minutes is better than arriving in 40").
  • Sequential environments make goal reasoning necessary. In a sequential environment the current action affects all future options: entering a one-way street, committing to a motorway slip road, prescribing a drug that rules out another. Reflex rules cannot represent this coupling; the agent must look ahead.
  • Search and planning are the mechanisms. Using its transition model, the agent simulates hypothetical action sequences and examines the resulting states before acting. If a sequence reaches a goal state, its first action is executed. This is exactly what search algorithms and planners provide, and it is why a transition model is a prerequisite for goal-based behaviour — goal-based agents are model-based agents with lookahead.
  • Flexibility. The knowledge is explicit and declarative, so behaviour can be retargeted by changing data rather than code. Give the taxi a new destination and the whole route changes automatically; tell a reflex taxi about the new destination and you must rewrite every rule. Similarly, if the model is updated ("it is raining, braking distances double"), all relevant behaviour adapts at once, whereas a reflex agent would need many individual condition–action rules revised by hand.
  • Cost. Lookahead is computation, and computation is time. A reflex agent responds in microseconds; a planner may need seconds. In dynamic environments this is a real risk — the world may have moved on by the time the plan is ready. Practical designs therefore combine layers: reflexes for emergency braking, planning for route selection, with the planner's output treated as advice that the reflex layer can override.

Utility-based agents: trading off competing objectives

Goals say whether you succeeded; utilities say how well. Use a utility-based design whenever the specification exhibits any of the following.

  • Competing objectives in the performance measure. The taxi's measure mentions safety, speed, legality, comfort, fuel economy and profit. These conflict: the fastest route is rarely the most comfortable or the safest. A utility function U(state) — or more generally over histories — assigns a single real number that expresses the designer's preferred trade-off, so the agent can compare an option that is slightly slower but much safer against one that is quick and jerky.
  • Conflicting goals that cannot all be achieved. Utility allows a principled compromise rather than an arbitrary tie-break.
  • Stochastic environments. When outcomes are uncertain, no action guarantees the goal. The rational criterion becomes maximum expected utility: choose the action a maximising Σ P(outcome | a, state) × U(outcome). This also lets the agent express attitude to risk through the curvature of the utility function — a concave utility over money, for example, makes the agent prefer a certain £50 to a coin-flip for £100.
  • Many goal-satisfying paths. Dozens of routes deliver the passenger; utility is what lets the agent prefer the better ones instead of returning the first solution search happens to find.
function UTILITY-BASED-ACTION(state, actions, model, U) returns an action
    best <- none; best_value <- -infinity
    for each a in actions do
        value <- 0
        for each (s', p) in model.PREDICT(state, a) do
            value <- value + p * U(s')
        if value > best_value then best_value <- value; best <- a
    return best

The decisive design principle is that the utility function should be an internalisation of the external performance measure. The performance measure lives outside the agent and judges environment histories; the utility function lives inside the agent and guides choice. When they agree, a utility-maximising agent is rational by the external standard. When they diverge, you get an agent that scores brilliantly on its own books and badly in reality — the classic mis-specification failure. Examples are easy to generate and instructive:

  • A vacuum agent rewarded for "amount of dirt collected" learns to dump the dirt back on the floor and collect it again.
  • A taxi rewarded only for "minutes of travel time" drives recklessly, because the external penalties for danger and discomfort were never written into its utility.
  • A diagnosis agent rewarded for "proportion of tests that come back positive" stops ordering the cheap ruling-out tests that are clinically valuable.

These failures are not bugs in the optimiser; the optimiser worked perfectly. They are bugs in the specification, which is why the workflow below insists on writing the performance measure first and revisiting it after evaluation.

Learning agents: operating in unknown environments

All of the above presumes the designer knows enough to hand-build rules, models, goals or utilities. Often they do not: the environment may be unknown (the agent does not know the outcomes of its actions), too complex to model by hand, or liable to change after deployment. A learning agent addresses this by splitting into four conceptual components.

ComponentRoleTaxi example
Performance elementSelects external actions from percepts — this is the whole agent as described previously (reflex, model-based, goal-based or utility-based)Decides to brake, steer, choose a route
Learning elementMakes improvements to the performance element using feedback supplied by the criticAdjusts the braking-distance model after a near miss; refines the route-time estimates
CriticObserves percepts and judges the agent's behaviour against a fixed external performance standard, producing the feedback signalNotes that passengers tipped nothing and that the manoeuvre was rated uncomfortable
Problem generatorSuggests exploratory actions that are suboptimal in the short term but yield informative experienceTries braking on a wet surface in a quiet car park to calibrate the model

Two subtleties deserve emphasis. First, the critic is necessary because percepts alone do not say whether behaviour was good. The percept "a crash occurred" carries no evaluation; it is the external standard, held fixed and outside the agent's control, that labels this as very bad. The standard must be fixed precisely so the agent cannot "improve" by lowering its own bar — an agent able to rewrite its own standard would simply declare whatever it does to be excellent.

Second, the problem generator institutionalises the exploration–exploitation trade-off. An agent that always takes the action currently believed best will never discover that a different action is better; deliberate, bounded exploration is what makes long-run improvement possible. The art is in bounding it: exploration should happen where mistakes are cheap and reversible, never during a motorway merge.

Any component of any architecture can be learned: condition–action rules from supervised examples, the transition and sensor models from observed trajectories, state-estimation parameters from data, utility values from reinforcement signals or from observing expert behaviour. The design trigger is in the PEAS and environment analysis — unknown, highly complex, continuous, or non-stationary dynamic environments all point towards a learning design, while small, fully specified, static environments usually do not justify the extra machinery and the extra risk.

A workflow for designing rational agents

The following five steps turn the preceding ideas into a repeatable procedure.

  • Step 1 — Write the PEAS description, performance first. Force yourself to state the performance measure before thinking about mechanisms, and state it in terms of environment outcomes, not agent behaviour. "Clean floor" rather than "spend time sucking". Enumerate the environment's contents, the full actuator list, and the full sensor list. Resist the temptation to list the sensors you wish you had.
  • Step 2 — Classify the environment. Place the task on every standard dimension: fully or partially observable (and whether it is effectively unobservable); single-agent or multi-agent, and if multi-agent, cooperative or competitive; deterministic, stochastic or merely nondeterministic; episodic or sequential; static, dynamic or semidynamic; discrete or continuous in state, time, percepts and actions; known or unknown. Each answer is a requirement in disguise.
  • Step 3 — Choose the least complex agent type that meets the demands. Complexity is a cost: more components mean more code, more assumptions, more failure modes, more computation per decision, and more that can be mis-specified. Start at the bottom of the ladder and climb only when the classification forces you to. Partial observability forces internal state; sequentiality forces lookahead; conflicting or graded objectives and stochastic outcomes force utilities; unknown or shifting environments force learning.
  • Step 4 — Add components only where the task requires them. This is Step 3 applied at the level of individual capabilities rather than whole architectures. A hybrid design is normal: a hierarchical taxi controller may run a hard-coded reflex layer for collision avoidance, a model-based state estimator for tracking other vehicles, a planner for routes, a utility function for route selection and ride comfort, and a learning element that refines only the braking model. Do not add a planner where a table lookup suffices, and do not add learning where a known model is available.
  • Step 5 — Evaluate against the original performance measure and revise. Run the implemented agent in the real environment, or in a simulator sampled from the realistic distribution of environments, and score it with the external measure written in Step 1 — never with the agent's own internal utility, which would be circular. Measure average performance over many environment instances, not one lucky episode. Then diagnose: poor scores caused by missing information point back to sensors or state estimation; poor scores caused by good-looking but harmful behaviour point to a mis-specified utility; poor scores caused by late decisions point to excessive deliberation; and systematically poor scores across the board often point to a flawed performance measure itself.

A worked illustration ties the workflow together. Consider a medical diagnosis system. Step 1 gives the PEAS: performance — healthy patient, accurate and timely diagnosis, minimised cost and minimised harm from unnecessary tests; environment — patient, clinicians, hospital information systems, laboratory; actuators — display of questions, test orders, diagnoses and treatment recommendations; sensors — entry of symptoms, patient answers, laboratory results. Step 2: partially observable (the underlying disease is never directly perceived), stochastic (symptoms do not determine disease), sequential (ordering one test changes what is worth doing next), dynamic in the slow sense (the patient's condition evolves), largely discrete at the level of findings, multi-agent only weakly, and partially unknown (prevalence and test accuracy vary by population). Step 3 and 4: a reflex "symptom → diagnosis" table is immediately ruled out by partial observability and stochasticity; the agent needs internal state in the form of a belief distribution over diseases, a sensor model giving the likelihood of each finding under each disease, utilities that trade off diagnostic certainty against test cost and patient risk, and a learning element to update prevalence and likelihood estimates from outcomes. Step 5: evaluate on held-out patients using the externally defined measure — not on the internal confidence score, which a mis-specified system can inflate while missing cases.

Finally, the most common root cause of a bad agent is not a bad algorithm but a vague or incomplete PEAS specification. If the performance measure omits safety, the optimiser will trade safety away. If the sensor list is aspirational, the design will assume information it never receives. If the environment description quietly ignores other agents, the agent will be blindsided by them. Specification errors do not stay put: they propagate through environment classification into architecture selection and finally into an agent that is, often very efficiently, optimising the wrong thing. Writing the specification well is therefore not paperwork preceding the design — it is the first and most consequential part of the design.
