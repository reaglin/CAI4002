Designing Agent Programs for Sample Environments

▶

Designing an agent program is not an act of inspiration; it is an act of specification followed by elimination. You first pin down exactly what the agent is being judged on and what world it inhabits, and only then do you choose the simplest internal organisation that can plausibly score well on that judgement. The sequence matters: a design that begins with "let's use reinforcement learning" or "let's write a few if-then rules" has already committed to an architecture before anyone has checked whether the environment supplies the percepts that architecture needs. The material below walks through the design discipline — PEAS first, then architecture selection, then critique — and applies it to four progressively harder sample environments: a vacuum world, an autonomous navigation task, a trading agent, and a game-playing agent.

Starting with a PEAS Specification

PEAS stands for Performance measure, Environment, Actuators, Sensors. It is the design contract. Each of the four fields does a distinct job, and the most common beginner errors come from blurring them.

The performance measure must be a scalar or a ranked set of criteria, not a description of behaviour. A statement like "the agent should move efficiently and clean up dirt" is a behaviour sketch, not a measure: two designs can both satisfy it while producing different outcomes, and nothing in the sentence tells you which one won. A measure must be computable by an external observer from the sequence of environment states the agent produced. Compare:

  • Not a performance measure: "Vacuums the room thoroughly and does not waste time."
  • A performance measure: "Score = (1 point for each square that is clean at each of the 1000 time steps) − (1 point per movement action) − (50 points if the agent falls down the stairs)."

The second version is a scalar. It is also falsifiable: you can run two agent programs and read off which one is better. Where a single scalar is genuinely impossible — as is usually the case in navigation or trading — you state a ranked (lexicographic) set instead: "First, never violate a traffic law or collide; subject to that, minimise expected journey time; subject to that, minimise fuel use; subject to that, maximise comfort." Ranking is weaker than a scalar because it refuses to trade a tiny amount of safety for a large amount of speed, but it is honest about priorities and it is still objective.

Note also that the performance measure is defined over environment states, not over the agent's own beliefs. An agent that believes the floor is clean scores nothing; an agent whose actions made the floor clean scores. This distinction is what stops designers from accidentally rewarding self-deception.

Environment properties must be listed explicitly, because each property is the reason a particular architecture is needed or not needed. The six standard dimensions are:

PropertyQuestion it answersDesign consequence if the "hard" value holds

A useful discipline is to write each property down with a one-line justification, e.g. "Partially observable: the camera sees 60° ahead, so vehicles approaching from behind are not in the percept." That justification is what you will cite later when defending the architecture.

Enumerating actuators bounds the action space. The agent program is a function that returns an action; if you have not listed the legal actions, you have not defined the function's codomain. Writing "Actuators: wheels, brakes, steering" is too vague to code against. Write the action set: {Accelerate(a) | a ∈ [−4, +2] m/s²} × {Steer(δ) | δ ∈ [−30°, +30°]} ∪ {SignalLeft, SignalRight, Horn}. This immediately exposes design problems: if the performance measure penalises discomfort but the actuator list has no way to limit jerk, the measure cannot be optimised.

Enumerating sensors determines the percept delivered on each cycle — and, crucially, exposes the gap between what the agent needs and what it can observe. This is the single most productive step in the whole PEAS process. For each item of information the decision rule requires, ask: which sensor supplies it, and at what noise and latency? Anything required but unsupplied must be inferred, and inference needs internal state and a transition model. The sensor list is therefore the formal proof that a reflex agent is or is not sufficient.

Vacuum World: Reflex versus Model-Based Design

The two-square vacuum world is deliberately trivial, which is exactly why it is a good instrument: it lets you see architecture choice forced by a single environment property rather than by complexity.

The fully observable case. The percept is a pair (Location, Status) with Location ∈ {A, B} and Status ∈ {Clean, Dirty}. There are exactly four possible percepts, and therefore the complete percept-to-action table has four rows:

PerceptAction
[A, Dirty]Suck
[A, Clean]Right
[B, Dirty]Suck
[B, Clean]Left

Four rules — and in fact only two distinct decisions ("if dirty, suck; otherwise move to the other square"). The agent program is a two-line lookup:

function REFLEX-VACUUM-AGENT(percept) returns action
    (location, status) <- percept
    if status = Dirty then return Suck
    else if location = A then return Right
    else return Left

This is a simple reflex agent, and it is provably adequate here because the percept uniquely identifies everything the decision depends on. Note the honest caveat: with the "+1 per clean square per step, −1 per move" measure, this agent oscillates forever between clean squares and bleeds points. Under the simpler "+1 per clean square per step" measure with no movement penalty, it is optimal. The architecture is adequate; the policy is only optimal relative to the measure you wrote. This is already an argument for evaluating designs against the stated measure rather than against intuition.

Removing the location sensor. Now the percept is just Status. There are two possible percepts, so a reflex agent can implement only four possible policies (one action choice for each of two percepts). Examine them:

  • Always Suck when Dirty, always Right when Clean: the agent reaches square B, finds it clean, and keeps executing Right against the wall forever. If square A later becomes dirty, it is never revisited. Permanent failure.
  • Always Suck when Dirty, always Left when Clean: symmetric failure at square A.
  • Suck regardless of status: never moves; the other square is never cleaned.
  • Move regardless of status: never cleans anything.

There is no deterministic reflex policy that cleans both squares and stops wasting moves, because two different world states produce the identical percept [Clean] while demanding different actions ("go right" from A, "stay or stop" at B). This is the textbook demonstration that partial observability breaks simple reflex agents. A randomised reflex agent (flip a coin between Left and Right when Clean) does eventually clean everything, which is worth noting — randomisation can rescue reflex agents from infinite loops — but it is inefficient and its expected score is poor.

Restoring correct behaviour with internal state. A model-based reflex agent keeps a small amount of memory and a transition model, and uses the percept to update it:

persistent: belief = {A: Unknown, B: Unknown}   # believed cleanliness
            pos = A                              # believed position
            last_action = None

function MODEL-BASED-VACUUM-AGENT(status) returns action
    # 1. UPDATE-STATE: fold last_action and new percept into the model
    if last_action = Right and pos = A then pos <- B
    if last_action = Left  and pos = B then pos <- A
    belief[pos] <- status
    if last_action = Suck then belief[pos] <- Clean

    # 2. RULE-MATCH on the internal state, not on the raw percept
    if belief[pos] = Dirty then action <- Suck
    else if belief[other(pos)] ≠ Clean then action <- move-toward(other(pos))
    else action <- NoOp

    last_action <- action
    return action

Two things are doing the work here. The transition model ("Right from A lands me in B") lets the agent infer its position without a location sensor, by dead-reckoning from its own action history. The sensor model ("the dirt sensor reports the square I am standing on") lets it attribute the percept to the right square. Together they convert a percept sequence into a belief state, and the rules then fire on the belief state. Notice the NoOp branch: once both squares are believed clean, the agent stops moving, which is impossible for the sensorless reflex agent and which directly earns points under a movement-penalising measure. (If dirt can reappear, the model must decay Clean beliefs back to Unknown after some time — an assumption worth documenting.)

Scaling to an n-square grid. Now the asymmetry becomes decisive. If the agent is fully observable over the whole grid, the world state is "which of the n squares are dirty" × "where the agent is", i.e. n · 2ⁿ states, and a complete lookup table needs one row per state:

Squares (n)World states (n · 2ⁿ)Rows in a full percept-to-action tableSize of the model-based program
288~10 lines
46464~10 lines
1010,24010,240~10 lines
25 (5×5 room)≈ 8.4 × 10⁸≈ 8.4 × 10⁸~10 lines

The table grows exponentially in the number of squares; the model-based program does not grow at all, because it stores a compressed representation (an n-bit dirt map plus a position) and computes the action from it rather than looking it up. This is the general lesson: a reflex table enumerates the state space, while a model-based program factors it. Exponential blow-up in rule tables is the structural reason real agents carry models.

Motivating a utility-based variant. Introduce the movement penalty: "+1 per clean square per step, −2 per move, −0 for NoOp." Now actions are no longer simply right or wrong; they trade off. Suppose the agent sits on a clean square and believes square 7 (eight moves away) is dirty with probability 0.6, and square 2 (two moves away) is dirty with probability 0.3. A goal-based formulation ("make every square clean") cannot choose between them — both satisfy the goal eventually. A utility-based agent computes expected net gain: travelling to square 2 costs 4 points and yields, with probability 0.3, a stream of +1 per remaining step; travelling to square 7 costs 16 points for a 0.6 chance of the same stream. With 20 steps remaining, the near square wins; with 400 steps remaining, the far square wins. The utility function makes the horizon and the probabilities first-class inputs to the decision, which is precisely what the goal formulation discards.

Autonomous Navigation: Goal-Based Design

Navigation is the canonical case where the right action now depends on a destination that is not in the percept. That single fact rules out reflex architectures.

The goal as an explicit state. Specify the goal as a predicate over states: GOAL(s) ≡ (s.position ∈ dropoff_zone) ∧ (s.parcel_delivered = true). The agent then searches a state space whose nodes are (position, heading, time) and whose edges are actions with costs, using A* over a road graph with an admissible heuristic such as straight-line distance divided by maximum legal speed. The output is an action sequence — a plan — rather than a single action:

function GOAL-BASED-NAVIGATOR(percept) returns action
    state <- UPDATE-STATE(state, last_action, percept, transition_model, sensor_model)
    if plan is empty or not VALID(plan, state) then
        plan <- SEARCH(state, goal, model)          # e.g. A* over the road graph
    action <- FIRST(plan); plan <- REST(plan)
    last_action <- action
    return action

The key architectural feature is the goal variable. Change the destination and the behaviour changes completely with no edit to the program — which is the practical benefit of goal-based design over compiled-in rules.

Partial observability and dynamism force replanning. A vehicle sees perhaps 100 m of road; it cannot observe a lane closure two kilometres ahead, a pedestrian behind a parked van, or the intentions of the car in the next lane. The world also changes while the agent deliberates: a plan computed for the state 400 ms ago may already be invalid. Hence the VALID(plan, state) test and the continual UPDATE-STATE step: the agent maintains a world model (map + tracked obstacles + its own pose, typically via a Kalman or particle filter) and treats its plan as a hypothesis to be revised, not a commitment. In practice this appears as a layered design — a slow global planner (route over the road graph, replanned every few seconds), a medium local planner (trajectory over the next 5 seconds, replanned at 10 Hz), and a fast reactive safety layer (emergency braking, running at 100 Hz). The reactive layer is a genuine reflex agent, retained precisely because reflexes are fast; it is subordinated to, not replaced by, the deliberative layers.

Contrast with pure obstacle avoidance. A reflex rule set such as "if obstacle ahead, turn right; else go forward" produces behaviour that looks purposeful and is utterly unreliable for a destination task. It has no representation of where it is going, so it cannot fail to reach the goal — it was never trying. Worse, it exhibits classic reflex pathologies: limit cycles around convex obstacles, oscillation in corridors, and the inability to deliberately back out of a dead end (backing out is locally "wrong" and globally necessary). Reaching a specified address reliably requires a goal representation and lookahead; this is an architecture-level limitation, not a tuning problem.

Competing objectives expose the limits of goals. Many plans reach the destination. Which one should the agent execute? Consider three candidate routes:

RouteTime (min)Fuel (L)Comfort (jerk events)Legal riskGoal satisfied?
Motorway242.13noneYes
City shortcut211.619noneYes
Bus-lane dash171.412fine likelyYes

All three satisfy GOAL(s). Goal satisfaction is a binary predicate and therefore cannot rank them. The designer either smuggles the ranking into the search cost function (which is already a partial move to utility) or admits it openly.

Upgrading to a utility function. Define U = −(w_t · time + w_f · fuel + w_c · discomfort + w_l · E[legal penalty] + w_s · E[collision cost]), with weights expressed in a common currency (money, or "equivalent minutes"). The planner then minimises expected cost rather than testing a predicate, and the ranked route table above resolves automatically once the weights are set — and, importantly, resolves differently for an ambulance (high w_t) than for a passenger shuttle (high w_c), without changing the program. The added design cost is real and should be acknowledged: you must elicit and calibrate weights, you must estimate probabilitiesfor rare events from sparse data, and you must defend the resulting trade-offs to regulators and passengers. The justification is that the environment is stochastic and the objectives genuinely conflict: there is no ordering of actions available to a goal-based agent that is correct for all stakeholders, so the trade-off has to live somewhere explicit. A utility function puts it in one auditable place rather than scattering it through ad-hoc tie-breaking rules.

One honest caveat: lexicographic safety constraints are usually kept outside the utility sum. Collapsing "never run a red light" into a weighted term means that a sufficiently large time saving can buy a red light, which is unacceptable. The practical pattern is a constrained utility maximisation: hard constraints filter the action set, and the utility function ranks whatever survives.

Trading Agents: Utility and Uncertainty

A trading agent is the cleanest example of an environment in which no action guarantees anything. Every architecture below utility-based is structurally unable to express the problem.

Utility over outcomes, not over a binary goal. The outcome of a trading decision is not "succeeded/failed" but a distribution over portfolio states. A workable utility function scores an outcome on several axes at once:

  • Profit and loss — the realised and unrealised change in portfolio value, net of commissions, spread, slippage and financing costs.
  • Risk exposure — position size relative to limits, concentration in a single name or sector, leverage, and sensitivity (delta, duration) to a market factor.
  • Variance / drawdown — the dispersion of outcomes, not just the mean. Two strategies with identical expected profit are not equally good if one has twice the volatility.

A standard formulation is mean–variance utility: U(w) = E[r(w)] − (λ/2) · Var[r(w)], where w is the portfolio weight vector, r the return, and λ > 0 the risk-aversion coefficient. Equivalently one can use a concave utility of wealth such as U(W) = log W, whose concavity is risk aversion: the pain of losing £10,000 exceeds the pleasure of gaining £10,000, so the agent declines fair gambles. This is not a detail — it is the formal reason a utility-based trader behaves sensibly where an expected-profit maximiser would bet the firm.

Environment properties. Written out explicitly:

PropertyValueJustification
ObservabilityPartially observableThe agent sees prices and visible order-book depth, not other participants' intentions, hidden/iceberg orders, or pending news.
DeterminismStochasticThe same order placed in the same visible state yields different fills and different subsequent prices.
EpisodesSequentialA position taken now constrains capital, risk limits and tax treatment later; today's trade moves tomorrow's price.
ChangeDynamicThe book updates in microseconds whether or not the agent acts; deliberation time is itself a cost.
RepresentationContinuous (prices, quantities, time), though tick-quantisedRules out tabular policies; demands function approximation.
AgentsMulti-agent, partly adversarialOther traders — including those detecting and front-running your order flow — optimise measures that depend on your actions.

The multi-agent property has a specific consequence that single-agent reasoning misses: your own actions change the environment's response function. A large market order moves the price against you (market impact), and a predictable execution pattern invites exploitation. Hence real execution agents randomise order sizes and timing — a randomised policy is a rational response to an adversary, exactly as in game theory.

Expected utility maximisation as the decision rule. When no action guarantees the goal, the agent ranks actions by expected utility:

function UTILITY-TRADER(percept) returns action
    state  <- UPDATE-STATE(state, last_action, percept)      # prices, book, position, cash
    model  <- CURRENT-PROBABILITY-MODEL()                     # P(outcome | state, action)
    best   <- Hold; best_eu <- EU(Hold)
    for each action a in LEGAL-ACTIONS(state):                # includes size and limit price
        eu <- SUM over outcomes o of  P(o | state, a) * U(o)  # U includes risk/variance terms
        eu <- eu − TRANSACTION-COST(a) − EXPECTED-IMPACT(a)
        if eu > best_eu then best <- a; best_eu <- eu
    if VIOLATES-RISK-LIMITS(best, state) then best <- Hold
    last_action <- best
    return best

A concrete illustration. The model says a stock currently at £100 will, over the next hour, be at £102 with probability 0.55 and £97 with probability 0.45. Expected profit per share is 0.55(+2) + 0.45(−3) = +1.10 − 1.35 = −0.25 — negative, so even a risk-neutral agent holds. Change the probabilities to 0.65/0.35 and expected profit is +1.30 − 1.05 = +0.25 per share: a risk-neutral agent buys the maximum size. A mean–variance agent, however, also computes the variance of that payoff (≈ 5.7 per share) and sizes the position so that E[r] − (λ/2)Var[r] is maximised, which yields a small position. Notice that the architecture produces position sizing automatically; nowhere did anyone write a rule saying "trade smaller when uncertain."

Adding a learning element. The probabilities above were asserted; in reality they must be estimated, and the estimates decay as markets change (regime shift, new participants, altered microstructure). The agent therefore becomes a learning agent with the four standard components:

  • Performance element — the expected-utility trader above, which chooses orders.
  • Critic — compares realised outcomes against the model's predictions and against the performance measure: realised P&L net of costs, calibration error (did events predicted at 65% happen about 65% of the time?), and realised volatility versus forecast volatility.
  • Learning element — updates P(outcome | state, action), e.g. by Bayesian updating of a predictive model, refitting a return forecaster on a rolling window, or gradient updates to a neural estimator; it may also recalibrate the market-impact model from the agent's own fills.
  • Problem generator — deliberately places small exploratory orders in instruments or venues the current model rates poorly, so that the agent keeps collecting data outside its current comfort zone. Without it the agent suffers the classic feedback trap: it only ever observes fills for trades it chose to make, so it never learns that its pessimistic estimate for a neglected market was wrong.

The exploration cost here is literal money, which is why the problem generator must be budgeted: "no more than 0.5% of capital, and no more than 2% of expected daily loss budget, allocated to exploratory positions."

Critiquing the goal-based alternative. Suppose someone proposes a goal-based trader: "Goal = achieve a 15% return this year; act so as to reach that state." Three failures follow directly from the architecture:

  • It is indifferent among all plans that might reach the goal. Buying a diversified index on margin and putting the entire account on a single biotech binary event both "achieve 15%" in some reachable future. Goal predicates cannot rank by risk because risk is a property of the distribution, and a goal test looks only at individual states.
  • It induces perverse risk-seeking when behind. If the agent is down 10% in November, the only remaining plans that reach +15% are extremely high-variance ones, so goal satisfaction requires gambling. This is the well-documented "doubling down" pathology, and it is produced by the architecture, not by a bug.
  • It is indifferent to overshoot and to path. A +60% return scores the same as +15%, so profitable opportunities are declined once the target is met; and a path that dips to −40% before recovering is scored identically to a smooth one, even though the fund would have been liquidated by its investors en route.

The repair in every case is the same: replace the binary predicate with a utility function that is sensitive to the whole outcome distribution. That is precisely the definition of upgrading from a goal-based to a utility-based architecture.

Game-Playing Agents: Learning Architectures

Games are the standard laboratory for learning agents because the performance measure is unambiguous, the environment is cheap to simulate, and feedback is plentiful.

Mapping onto the four components. Take a self-play chess or Go program:

ComponentRole in generalInstantiation in a game-playing agent
Performance elementSelects actions given percepts; this is "the agent" in the non-learning senseSearch (alpha–beta or Monte Carlo tree search) guided by the current evaluation function and move-ordering policy
CriticJudges the agent's behaviour against a fixed external performance standard and emits a feedback signalScores positions and games: final result (win/draw/loss), or the difference between the predicted value of a position and the value backed up by deeper search
Learning elementModifies the performance element using the critic's feedbackGradient updates to evaluation-function weights or network parameters; tuning of search heuristics and move priors
Problem generatorProposes actions/experiences that are informative even if currently suboptimalExploration: temperature-based or ε-greedy move selection, Dirichlet noise at the root, randomised opening books, self-play against earlier/weaker versions

The division of labour is worth stating precisely: the performance element tries to win now; the problem generator deliberately sacrifices some of that to learn more; the critic supplies the standard; the learning element is the only component that writes to the performance element. Conflating critic and performance element is a common design error — if the agent grades itself using the same evaluation function it is trying to improve, it will happily confirm its own mistakes.

Defining the critic's feedback signal. Two sources, with different properties:

  • Terminal outcomes (+1 win, 0 draw, −1 loss) are unambiguous and perfectly aligned with the performance measure, but extremely sparse: one scalar per game of perhaps 80 moves. This creates the credit assignment problem — which of the 80 moves deserves blame? Monte Carlo methods solve it statistically by averaging over very many games.
  • Intermediate evaluation signals are dense and available every move. The classic device is temporal-difference learning, as in Samuel's checkers player and TD-Gammon: the critic's error signal is δ_t = V(s_{t+1}) − V(s_t) (with the true outcome substituting for V at the terminal state), i.e. the agent learns to make each position's value consistent with the value of the position that actually followed. Alternatively, the critic can compare the shallow static evaluation of a position with the value returned by a deep search from it, and train the evaluation to predict the deeper, more reliable number.

In both cases note what makes this a critic and not merely a reward: the standard is external and fixed (the rules of the game decide wins), and it is applied to the agent's own behaviour to produce a correction.

Why the problem generator must force suboptimal moves. A performance element that always plays its current best move is on-policy and self-confirming. Suppose the evaluation function wrongly assigns a low value to positions with doubled pawns. The agent will then never enter such positions, will never see their true outcomes, and will never receive the data needed to correct the error. The bad estimate is protected by the very fact that it is bad. The problem generator breaks the loop by occasionally choosing a move the performance element rates second- or third-best — sampling proportionally to visit counts with a temperature parameter, adding Dirichlet noise to root priors so that every legal move has some chance of being tried, or starting games from randomly chosen opening positions. The short-term cost is real (some games are lost that would have been won); the long-term payoff is an evaluation function that is accurate over a much wider region of the state space. This is the exploration–exploitation trade-off in its architectural form, and it is why the problem generator is drawn as a separate box rather than folded into the performance element.

Why hand-coded evaluation is brittle. A classical chess evaluation is a weighted sum of human-identified features: material (♙=1, ♘=♗=3, ♖=5, ♕=9), mobility, king safety, pawn structure, control of the centre. Writing one requires expert knowledge; tuning the weights by hand is slow; and the feature set itself encodes the designer's blind spots. In a state space of roughly 10⁴⁴ legal chess positions or 10¹⁷⁰ Go positions, no enumeration is possible and the evaluation function must generalise — it must give sensible values to positions no one has ever seen. Hand-coded functions generalise poorly at the boundaries: they misjudge long-term positional compensation for material, they are exploitable once an opponent discovers which feature is mis-weighted, and every rule added to patch one case tends to break another. Go was the decisive demonstration: decades of hand-crafted evaluation produced only amateur-level play, while learned value networks trained by self-play surpassed the best humans. The architectural lesson generalises beyond games — whenever the state space is too large to enumerate and too subtle to summarise in a few dozen hand-chosen features, learn the evaluation from outcomes.

The architectural consequence is sharp. Chess needs a model-based, utility-guided search agent with a learned evaluation; the internal state it must track is small. Poker needs all of that plus explicit belief-state maintenance, plus deliberate randomisation, plus information-theoretic care about what the agent's own actions reveal. Partial observability does not merely add noise; it changes the mathematical object the agent is optimising and the form of the policy it must output. Also note the critic becomes harder to build: in poker a single hand's result is a terrible feedback signal because luck dominates, so the critic must be redesigned to measure decision quality rather than outcome.

Critiquing and Justifying Architecture Choices

A design is not finished when the architecture is chosen; it is finished when the choice is defended from both sides. The discipline below produces a short, reviewable justification that survives contact with a sceptical colleague.

1. State why the next-simpler architecture fails, citing a concrete environment property. Vague claims ("a reflex agent isn't smart enough") are not arguments. The correct form names the property and exhibits the failure. Examples:

  • Simple reflex → model-based: "Partially observable: with the location sensor removed, the world states (at A, both clean) and (at B, both clean) generate the identical percept [Clean] but require different actions, so no deterministic function from percept to action is correct. Internal state is mathematically necessary, not merely convenient."
  • Model-based → goal-based: "The destination is not a function of the current percept, and the correct first action at a junction depends on where the vehicle is ultimately going. Without an explicit goal variable, a new destination requires rewriting rules."
  • Goal-based → utility-based: "Multiple plans satisfy the goal and the environment is stochastic, so the goal predicate cannot rank a 21-minute bus-lane route with a likely fine against a 24-minute legal route. A binary test has no expressive capacity for trade-offs."
  • Utility-based → learning: "The probability model is non-stationary — market microstructure and participants change — so any fixed P(outcome | state, action) degrades. Feedback is abundant and cheap (every fill and every closing price), so the conditions for learning are met."

2. State why the next-more-complex architecture is unnecessary, citing avoided cost. This half is skipped far more often and is where most over-engineering originates. The claim takes the form "the extra machinery would buy nothing measurable on the stated performance measure, and here is what it would cost":

  • "A learning element for the two-square vacuum is unnecessary: the environment is fully specified, stationary, and tiny, and the optimal policy is already known in closed form. Learning would add a training regime, an exploration budget that loses points, and a non-deterministic component that is harder to certify — for zero attainable score improvement, since the hand-written policy is optimal."
  • "A utility-based vacuum is unnecessary when the performance measure has no movement penalty, because every non-wasteful action is equally good; the trade-off the utility function would express does not exist in the measure."
  • "A full POMDP solver for the delivery vehicle is unnecessary: the receding-horizon replanner achieves the measure, while exact POMDP solution is intractable at this state-space size and would blow the 100 ms control deadline."

Costs worth naming explicitly are computation (per-cycle latency, memory, energy), data (labelled examples, simulator fidelity, exploration losses), design and maintenance effort (who tunes the weights, who retrains the model, who debugs non-deterministic behaviour), and verifiability (a 4-row table can be exhaustively tested; a learned network cannot).

3. Identify the percept or state information each upgrade requires, and confirm it is obtainable. Every architectural step has a data precondition. If the precondition is not met, the upgrade is a fantasy:

ArchitectureInformation it requiresCheck to perform
Simple reflexA percept that determines the correct action by itselfAre there two world states sharing a percept but needing different actions?
Model-based reflexTransition model (how the world evolves, effects of own actions) + sensor modelCan the model be written or learned? Does drift accumulate (dead reckoning without correction)?
Goal-basedAn explicit goal predicate and a searchable model of action consequencesIs the goal supplied externally and is the state space searchable within the time budget?
Utility-basedNumeric utilities on a common scale, plus outcome probabilitiesWho sets the weights, and can the probabilities be estimated with enough data?
LearningA feedback signal from a critic, and a safe way to exploreIs feedback observable, timely, and attributable? Is exploration affordable and safe?

Two examples of the check failing usefully. Autility-based medical triage agent requires utilities on a common scale across patients; if the institution cannot or will not state how it trades a 1% mortality increase against a four-hour wait, the weights do not exist and the "upgrade" would merely hide an arbitrary choice inside a constant. A learning agent for a rare-fault industrial inspector requires attributable feedback; if the ground truth about a missed fault only arrives eighteen months later as a warranty claim with no record of which inspection passed it, the critic cannot assign credit and the learning element has nothing to consume. In both cases the correct response is either to acquire the missing information (commission a clinical-preference study; instrument the inspection pipeline to log part IDs) or to stay at the simpler architecture and document why.

4. Evaluate the design against the stated performance measure, not against intuitive notions of intelligence. The temptation is to judge an agent by whether its behaviour looks clever. This is unreliable in both directions. The two-square reflex vacuum looks mindless and is optimal under the no-movement-penalty measure. A sophisticated planner that deliberates for 900 ms looks intelligent and scores terribly in a dynamic world with a 100 ms deadline, because by the time it acts the world has moved. Conversely, an agent that discovers an odd-looking but high-scoring behaviour — a trading agent that mostly holds, a navigation agent that takes a longer route to avoid an unprotected right turn — is performing correctly even though a human observer might call it timid.

The practical procedure is:

  • Instantiate the measure as an executable scoring function.
  • Define an environment generator that samples instances from the specified environment class (dirt distributions, traffic densities, market regimes, opponent pools), including adversarial and edge-case instances.
  • Run each candidate architecture over many instances and report the score distribution — mean and worst case, since a design with a good average and a catastrophic tail is usually unacceptable.
  • Compare against baselines: a random agent, the simplest reflex agent, and (where computable) an omniscient optimal agent, which bounds how much score is actually available.

This last point deserves emphasis. If the optimal policy scores 940 and the simple reflex agent scores 905, then the entire budget for model-based, goal-based, utility-based and learning machinery is 35 points. Measuring the headroom before building is the cheapest design decision available.

If the measure itself produces behaviour you find unacceptable — the agent exploits a loophole, or optimises a proxy at the expense of what you meant — the correct fix is to repair the performance measure, not to bolt a patch onto the agent program. An agent that scores well on a badly written measure has done its job; the specification is the defect.

5. Document assumptions so the design can be revisited. Every architecture choice rests on claims about the environment that may later become false. Record them as an explicit, dated list with the design decision each one supports, so that when the environment specification changes you can tell immediately which decisions are now unsupported. A usable format:

AssumptionDesign decision it supportsHow it could breakConsequence and response if broken

Assumptions should also be made testable at runtime wherever possible. An agent that monitors its own preconditions — "my predicted percept disagrees with my actual percept more often than the sensor model allows", "my realised variance is three times my forecast" — can detect that its design envelope has been exceeded and degrade safely (hand over to a human, revert to a conservative fallback policy, raise an alert) rather than continuing to act confidently on an invalid model. That self-monitoring is itself a small critic, and it is the cheapest form of robustness available to a non-learning agent.

This topic takes the agent concepts you have been building — percepts, agent functions, agent programs, and architecture — and puts them to work on concrete task environments. The starting move is always the same: write a PEAS specification (Performance measure, Environment, Actuators, Sensors) so that the design problem is stated precisely before any program is sketched. From that specification you can reason about which architecture the environment actually demands.

You will work through a deliberate progression. A vacuum world shows why a simple reflex agent fails once the environment is partially observable and why internal state produces a model-based reflex agent. Autonomous navigation introduces explicit goals and search over future states. Trading agents add uncertainty and competing outcomes, which forces a utility function rather than a binary goal test. Game-playing agents close the loop with learning architectures, where a critic and a learning element improve the performance element over repeated play. The final skill is critique: naming the trade-offs — complexity, feedback availability, maintainability, computational cost — that justify your choice and rule out the alternatives.
