Learning Agents

▶

Every agent architecture examined so far — the simple reflex agent with its condition–action rules, the model-based reflex agent with its internal state and transition model, the goal-based agent with its explicit description of desirable world states, and the utility-based agent with its numerical preference function — shares a single structural dependency: somebody had to supply the knowledge in advance. A designer wrote the rules, encoded the model of how the world evolves, enumerated the goals, or calibrated the utility function. The agent is then only as good as the designer's foresight. A learning agent removes that ceiling. It is not a sixth, rival architecture so much as a wrapper that can be placed around any of the others, adding machinery that modifies the agent's own decision-making components in the light of experience.

The classic statement of the idea is Turing's: rather than attempting to hand-program an intelligent machine, build a simpler machine and then teach it. The learning agent framework makes that proposal concrete by splitting an agent into four interacting parts — a performance element, a critic, a learning element, and a problem generator — and specifying precisely what information flows between them.

Why learning agents are needed. Three distinct pressures push a designer toward learning, and it is worth separating them because they imply different designs.

  • Unanticipated situations. Real environments are combinatorially vast. A delivery robot's designer cannot enumerate every floor surface, every lighting condition, every arrangement of furniture, every unusual way a human might block a corridor. A rule set written in advance will inevitably encounter states it does not cover, and will then either fail silently or fall back on a default that may be badly wrong. Learning allows coverage to be grown from the environment itself rather than imagined ahead of time.
  • Initially unknown environments. Sometimes the designer genuinely has no information to give. A Mars rover's designers do not know the traction properties of a particular regolith patch; an agent dropped into a new e-commerce marketplace does not know the demand curve. Here learning is not an optimisation — it is the only way the agent can acquire a usable policy at all. The agent must become more competent than its initial program, which is a stronger claim than merely becoming faster.
  • Repairing faulty assumptions. Even where the designer supplied knowledge, that knowledge may be wrong or may go stale. A transition model that says "braking reduces speed by 5 m/s²" is wrong on wet tarmac. A utility function that weights fuel cost against delivery speed with a fixed exchange rate becomes miscalibrated when fuel prices triple. Experience provides the corrective signal: the agent observes the discrepancy between predicted and actual outcomes and adjusts. Environments also change — a non-stationary environment guarantees that a fixed program degrades over time.

A useful way to see the generality of the idea: the thing being improved is always some component of a conventional agent. In a reflex agent, learning edits condition–action rules. In a model-based agent, learning refines the transition and sensor models. In a goal-based agent, learning improves knowledge about which action sequences achieve goals. In a utility-based agent, learning adjusts the utility estimates themselves. The learning wrapper is architecture-agnostic.

The four components. The following table summarises what each part does, what it consumes, and what it produces.

Component Role Input Output
Performance element Selects actions — this is the "whole agent" of the previous architectures Percepts (and internal state, goals, utilities) Actions
Critic Judges how well the agent is doing against a fixed external performance standard Percepts / percept history, plus the performance standard Feedback: an evaluation of recent behaviour
Learning element Makes improvements to the performance element Critic's feedback, plus knowledge of how the performance element is built Changes to rules, models, goals, or utility estimates
Problem generator Proposes exploratory actions that yield new, informative experience Current knowledge and its gaps, learning goals Suggested actions (possibly suboptimal in the short term)

The loop is continuous and can be stated in four words: act, evaluate, modify, explore. The performance element acts; the critic evaluates; the learning element modifies the performance element; the problem generator occasionally overrides the performance element's preferred action to generate experience the agent would otherwise never obtain. Note the direction of the arrows: the learning element writes into the performance element. The performance element does not know it is being taught; from its own perspective it is simply an agent whose rules happen to change.

A concrete illustration. Consider an automated taxi.

  • The performance element contains everything needed to drive: perception, route planning, steering and braking rules.
  • The taxi makes a quick left turn across three lanes of traffic. The critic observes the ensuing percepts — horns sounding, a passenger's shocked expression, a near-miss registered by the proximity sensors — and, against a performance standard that includes "avoid alarming passengers and other drivers", reports this as poor performance.
  • The learning element formulates a new or modified rule: a condition–action rule that forbids three-lane turns, or a downward revision of the utility estimate for that manoeuvre.
  • The problem generator might later propose trying braking on a wet road surface in a safe, low-speed setting, because the agent's model of stopping distance under those conditions is poorly determined. This action is not what the current policy would choose, but it produces information.

The critic and the performance standard. The critic exists because the agent's own percepts do not come labelled with "good" or "bad". A sequence of percepts is just data; converting it into an evaluation requires an interpretive layer, and that layer requires a yardstick.

The crucial design principle is that the performance standard is external to the agent and must not be modifiable by the agent. The reason is a degenerate-solution problem. If the agent could rewrite its own standard, the easiest route to "high performance" would be to lower the bar — the agent would learn to declare itself successful rather than to behave well. This is sometimes called reward hacking or specification gaming, and the external, fixed standard is the structural defence against the most blatant form of it. Humans face an analogue of this problem: it is far easier to redefine success than to achieve it.

It is worth being precise about a distinction that students frequently blur:

Aspect Performance measure (performance standard) Utility function
Whose it is The designer's / the outside world's The agent's own internal representation
Purpose To judge the agent's behaviour from outside To guide the agent's choice among available actions
Where it lives In the critic, fixed In the performance element, learnable
Scope Evaluates environment state sequences over time Evaluates states or state–action pairs for decision-making
Can the agent change it? No Yes — this is precisely what learning adjusts

The ideal case is that the agent's utility function converges on something that maximises the external performance measure. The two are related — the utility function is, in effect, the agent's internal hypothesis about what the performance standard rewards — but they are never identical, and learning is the process of narrowing the gap. In a vacuum-world example, the performance standard might be "one point per square cleaned per time step, minus one point per unit of electricity consumed." The agent's utility function may begin as a crude proxy ("prefer moving toward visible dirt") and be refined until it approximates the true standard, including the energy penalty it initially ignored.

The learning element: what can actually be learned. Because the learning element modifies the performance element, the design of the learning element depends entirely on the design of the performance element. There is no generic learner; the learner must know what kind of thing it is editing.

Performance element architecture Learnable component Example of an improvement
Simple reflex Condition–action rules: add, strengthen, weaken, delete A spam filter adds the rule "if subject contains 'wire transfer urgent' then quarantine" after repeated user corrections
Model-based reflex Transition model ("how the world evolves") and sensor model ("how percepts relate to state") A robot learns that its wheel odometry over-reports distance by 4% on carpet, and recalibrates
Goal-based Action outcome knowledge, operator preconditions and effects, heuristics for goal achievement A planner learns that "order part X" has a 10-day latency, so plans that assume 2 days fail
Utility-based Utility estimates for states or state–action pairs; weights on competing objectives A trading agent lowers the estimated utility of holding a position overnight after repeated gap-down losses

Cutting across this is a second classification — the kind of feedback available, which determines what family of learning algorithm is applicable:

  • Supervised learning. The agent is given input–output pairs: for each situation, the correct answer. A medical diagnosis agent shown thousands of labelled images learns a mapping from image to diagnosis. In the agent framework, this arises naturally when the agent can observe the actual outcome of a situation and compare it with its own prediction — the environment effectively labels the agent's percepts after the fact. A taxi that predicts "the car ahead will brake" and then perceives it braking has generated its own supervised training example.
  • Unsupervised learning. No correct outputs are supplied; the agent discovers structure. A taxi driving agent, without being told, clusters driving conditions into categories resembling "good traffic day" and "bad traffic day", which can then be used as internal state features. Unsupervised learning alone cannot tell the agent what to do, because no preference information is present — but the representations it discovers make other learning easier.
  • Reinforcement learning. The agent receives a scalar reward or penalty rather than a correct answer. The taxi receives no tips from passengers; it must work out for itself which aspects of its behaviour caused that. Reinforcement learning is the most general and the most difficult, because the feedback says "that was bad" without saying "here is what you should have done instead." It is also the natural fit for the learning agent architecture, because rewards are simply another percept that the critic interprets.

The problem generator, and exploration versus exploitation. If the performance element always chose the action it currently believed best, the agent would be trapped by its own ignorance. Actions it has never tried have no evidence in their favour, so they are never tried, so they never acquire evidence. The problem generator breaks this cycle by deliberately proposing actions whose informational value exceeds their immediate expected payoff.

  • Exploitation is choosing the action with the highest expected value under current knowledge. It maximises reward now, assuming current beliefs are correct.
  • Exploration is choosing an action with uncertain outcome in order to reduce that uncertainty and improve future decisions. It sacrifices expected reward now for better decisions later.

The canonical illustration is the multi-armed bandit. Imagine a row of slot machines with unknown and different payout rates. After a few pulls, one machine has paid out twice out of three. Pure exploitation says: pull that lever forever. But three samples is nearly no evidence; the apparently best machine may in fact be the worst, and the agent will never find out. Pure exploration — pulling levers uniformly at random forever — gathers excellent statistics but never cashes in on them, so average reward stays mediocre permanently.

The failure modes are symmetric and both serious:

  • Pure exploitation locks the agent into a local optimum. A delivery robot that finds one workable route will keep using it even if a corridor twice as fast exists one floor down. The agent is not aware it is missing anything, because evidence of the alternative never arrives.
  • Pure exploration never consolidates. Performance remains at the level of random behaviour, and the knowledge gained is never converted into value. In some domains it is also dangerous.

Practical schemes therefore blend the two, typically with a bias toward exploration early and exploitation later, since early knowledge is poor and the remaining time over which to profit from new knowledge is long. Common mechanisms include:

  • ε-greedy: with probability ε choose a random action, otherwise choose the best known. Often ε is annealed — decayed from, say, 0.3 toward 0.01 — so exploration fades as knowledge matures.
  • Optimism in the face of uncertainty: initialise unexplored options with high estimated value, so the agent is naturally drawn to try them, and the estimates fall to reality as evidence accumulates.
  • Confidence-bound methods: choose the action with the highest upper plausible value, which automatically favours options that are either genuinely good or genuinely under-sampled.
  • Offline or simulated exploration: perform the risky experiments in a simulator or sandbox, then deploy what was learned. This decouples the cost of exploration from the real environment.
loop forever:
    percept  := SENSE()
    feedback := CRITIC(percept, PERFORMANCE_STANDARD)   # standard is read-only
    LEARNING_ELEMENT.update(performance_element, feedback)

    if PROBLEM_GENERATOR.wants_to_explore(knowledge_gaps) and SAFE(candidate):
        action := PROBLEM_GENERATOR.suggest()           # informative, maybe suboptimal
    else:
        action := performance_element.decide(percept)   # best known action

    ACT(action)

Feedback signals and learning in unknown environments. The quality and timing of feedback shape what is learnable.

  • Immediate reward and penalty. The simplest case: an action is followed directly by a scalar signal. Credit assignment is trivial — the action just taken is clearly responsible. Pain and hunger in biological agents work like this; so do a chess engine's immediate material gains.
  • Delayed reward and the credit-assignment problem. Far harder. A chess agent receives a single signal — win, lose, draw — after perhaps sixty moves. Which move caused the loss? The blunder may have been move 14, with the final collapse merely its consequence. The agent must propagate credit backward through time. Techniques such as temporal-difference learning address this by using the agent's own later estimates to update earlier ones, in effect passing the evaluation signal back along the chain of states. A business analogue: a customer churns after eight months; was it the pricing change in month two, or the support interaction in month seven?
  • Noisy and partial feedback. If the environment is stochastic, a good action can produce a bad outcome by chance. An agent that updates strongly on single episodes will over-fit — it will conclude the action is bad on one unlucky sample. The remedies are statistical: average over many episodes, use small learning rates so no single observation dominates, and hold out data to check that an apparent pattern generalises. Partial feedback compounds this: a recommender system learns only about items users actually clicked, never about the counterfactual performance of items it chose not to show, producing a self-reinforcing bias in the data it collects.
  • Simultaneous model and policy learning. In a genuinely unknown environment, the agent does not have the luxury of learning the world first and then optimising within it. It must build the transition model and the policy concurrently, each informing the other — a chicken-and-egg problem, because a poor model produces poor exploration, which produces a poor model. This is why the problem generator is not an optional extra in unknown environments: it is the mechanism that keeps the model-building process fed with data from regions the current (poor) policy would avoid.
  • Safety and irreversibility. The decisive practical constraint. Exploration is defensible when mistakes are recoverable; it is indefensible when they are not. A self-driving car must not "explore" whether a pedestrian crossing can be taken at 60 km/h. A surgical robot must not experiment on a patient. A trading agent must not explore position sizes that could bankrupt the fund. The standard response is to encode hard constraints outside the learning loop: a set of actions that the problem generator may never propose and the performance element may never select, regardless of estimated value. These constraints are a form of designer-supplied knowledge that learning is explicitly forbidden to override — the same logic that makes the performance standard immutable. Where possible, irreversible decisions are also wrapped in human approval, or rehearsed in simulation first.

Designing and justifying a learning agent. Adding learning is a design decision with costs, and should be argued for rather than assumed. A workable design procedure runs as follows.

  • Identify the component that most needs improvement. Learning should be targeted, not diffuse. Ask: where does this agent's knowledge come from, and which part of it is most likely to be wrong or incomplete? If the physics of the domain are well understood but user preferences are not, learn the utility function and leave the transition model fixed. If the actuators are uncertain but the objective is crisp, learn the transition model. Learning everything at once multiplies data requirements and makes failures impossible to diagnose.
  • Specify the external performance standard. Write down explicitly what the critic will measure, in terms of environment states and sequences, not in terms of the agent's internal variables. Scrutinise it for gaming opportunities: a cleaning agent rewarded for "dirt collected" may learn to dump dirt on the floor and re-collect it. If the standard omits something you care about — energy, safety, user annoyance — the agent will treat that thing as free and will exploit it.
  • Choose a feedback mechanism suited to the environment. If ground-truth labels are obtainable cheaply (historical outcomes, human annotation), supervised learning is the efficient choice. If only a quality signal is available and the agent must discover its own actions, reinforcement learning is required. If the environment is partially observable, the agent must learn under uncertainty about its own state, which rules out the simplest methods. Match the technique to observability and to the reward structure, including its delay.
  • Decide how much exploration is affordable. This is a function of the cost of mistakes. In a simulator or a recommender system, mistakes cost almost nothing and aggressive exploration is correct. In aviation, medicine, or finance, the exploration budget is close to zero in the live environment and must be spent in simulation, in shadow mode (the learner proposes but a trusted system acts), or on a small controlled fraction of traffic.
  • Compare against a non-learning baseline. Learning adds real costs: data pipelines, training infrastructure, non-deterministic behaviour that complicates testing, drift that requires monitoring, and the risk that the agent gets worse on a bad batch of data. A fixed rule-based agent is auditable, reproducible, and cheap to maintain. Learning is justified when (a) the environment is genuinely unknown at design time, (b) the environment changes faster than you can push updates, or (c) the required behaviour is too complex or too individualised to specify by hand. If none of these holds, the rule-based design is the better engineering choice.

A worked comparison makes the trade-off concrete. Consider a warehouse pick-path agent. A non-learning version uses a fixed shortest-path algorithm over a static map: it is predictable, easy to verify, and requires no data infrastructure — but it cannot exploit the fact that aisle 7 is congested every weekday at 10:00, or that the map is stale after a re-racking. A learning version wraps the same planner in a loop where the critic measures actual pick times against a standard of "items per hour, with zero collisions", the learning element updates per-aisle traversal-cost estimates, and the problem generator occasionally routes through under-sampled aisles to keep the cost estimates fresh. Exploration is cheap here (a slightly longer route costs seconds), feedback is immediate and quantitative, and the environment changes weekly. Learning is clearly justified. Change the domain to a drug-dosing agent and every one of those judgements reverses: exploration is dangerous, feedback is delayed and noisy, and a non-learning protocol with human oversight becomes the defensible design.

NotesSuggested in-class activities: (1) give students a faulty performance standard — e.g. a cleaning robot rewarded for "dirt collected" — and ask them to predict the gaming behaviour and repair the standard; (2) have students take a previously specified reflex or utility-based agent and identify, component by component, what a learning wrapper would modify; (3) run a short multi-armed bandit simulation with ε fixed at 0, 1, and 0.1 to make the exploration/exploitation trade-off tangible. Common misconceptions to pre-empt: that the learning agent is a fifth alternative architecture rather than a wrapper; that the critic and the utility function are the same thing; and that more exploration is always better.
