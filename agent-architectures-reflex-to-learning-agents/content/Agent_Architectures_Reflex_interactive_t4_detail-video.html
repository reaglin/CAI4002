Goal-Based Agents

1

Goal-Based Agents

▶

A goal-based agent is the first architecture in the standard progression of agent designs that explicitly represents what it is trying to achieve, separately from what it currently knows and what it can do. Simple reflex agents map a percept directly to an action; model-based reflex agents add an internal state so that the mapping can account for unobservable parts of the world. Both, however, bury the agent's purpose inside the condition–action rules themselves. If you want a model-based reflex taxi to drive to the airport instead of the railway station, you must rewrite the rules. A goal-based agent instead keeps the world model and bolts on a declarative statement of the desired outcome, then reasons about which sequence of actions will transform the current state into one that satisfies that statement. This shift — from lookup to deliberation — is what gives goal-based agents their characteristic flexibility and their characteristic cost.

What makes an agent goal-based. Three features, taken together, define the architecture. First, it retains the internal world model inherited from the model-based reflex design. Because real environments are usually partially observable, the agent cannot read the full state off its sensors; it maintains a belief about the current state and updates that belief as new percepts arrive. A warehouse robot whose camera sees only the aisle in front of it still "knows" that a pallet was left in aisle 7 two minutes ago, because its internal state records it. Without this model, lookahead would be impossible — you cannot predict the consequences of an action if you do not know what state you are acting in.

Second, the agent holds a goal: a description of a state or, more usually, a set of states that count as success. Goals are normally written as a predicate over states rather than as a single enumerated state. "The robot is at the loading dock" is satisfied by any state in which the robot's position is the dock, regardless of battery level, gripper contents, or time of day. A goal test such as IsGoal(s) = (s.location == DOCK and s.carrying == nothing) partitions the state space into goal states and non-goal states. This is a binary notion — a state either satisfies the goal or it does not — and that binary character is both the source of the architecture's simplicity and, as we will see, the source of its main limitation.

Third, action selection becomes a reasoning problem rather than a lookup problem. A reflex agent answers "what rule matches this percept?" A goal-based agent answers "which of the action sequences available to me leads from my current believed state to a goal state?" That question is answered by simulating the future: what will happen if I do this? The agent applies its transition model to candidate actions, obtains predicted successor states, applies the model again to those, and so on, building a tree of hypothetical futures until one of them satisfies the goal test. Consider a taxi at a junction deciding whether to turn left. A reflex rule might say "if the light is green, go." A goal-based agent asks: if I turn left, I end up on Elm Street; from Elm Street can I still reach the airport, and at what cost? The decision at the junction is justified by events several steps downstream.

Finally, goals make the agent's purpose explicit and inspectable. You can print the goal, log it, change it at run time, and explain a decision by reference to it ("I turned left because the only route to the airport that avoids the closed bridge goes through Elm Street"). In a reflex agent the purpose is implicit — smeared across hundreds of rules — and therefore cannot be audited, swapped, or reasoned about by the agent itself or by a human reviewer.

Core components of the agent program. The goal-based agent program is conventionally decomposed into five cooperating parts, executed in a perceive–deliberate–act loop.

  • Sensors and state estimation. Each cycle, the sensors supply a percept. The agent combines the percept with its previous belief and its knowledge of what it just did to produce an updated belief about the current state. This is the same UPDATE-STATE step used by the model-based reflex agent, and its quality bounds everything downstream: plan on a wrong state and you will execute a wrong plan.
  • A model of how the world evolves. This captures change that happens independently of the agent — traffic builds up at rush hour, a conveyor belt advances, an opponent moves a piece. In deterministic, static domains this component may be trivial; in dynamic domains it is essential for predicting the state at the moment the agent's action will actually take effect.
  • A model of what my actions do. The transition function RESULT(s, a) = s' predicts the successor state. In a planning formalism this is usually written as preconditions and effects rather than as a lookup table, because the state space is far too large to enumerate.
  • An explicit goal representation. A goal test, a conjunction of literals, a target state, or a set of acceptable states. This is the component that is swapped when the task changes.
  • A search or planning procedure. This is the deliberation engine: it chains predicted states together to find a sequence [a1, a2, ..., an] such that applying the transition model to the current state in order yields a goal state.
  • Actuators. The agent executes the first action of the chosen sequence, then the loop repeats. Re-planning (or at least re-checking the plan) after each action is what keeps the agent robust when the world does not behave exactly as the model predicted.
function GOAL-BASED-AGENT(percept) returns an action
    persistent: state, the agent's current belief about the world
                model, how the world evolves and what my actions do
                goal,  a description of the desired set of states
                plan,  an action sequence, initially empty

    state <- UPDATE-STATE(state, last_action, percept, model)
    if plan is empty or not VALID(plan, state, model) then
        plan <- SEARCH(state, goal, model)      // deliberation
    if plan is empty then
        return NoOp                              // goal unreachable
    last_action <- FIRST(plan)
    plan <- REST(plan)
    return last_action

Notice two design details in this skeleton. The agent only re-plans when the stored plan is empty or has been invalidated — this amortises the cost of deliberation over many cycles, an important optimisation given how expensive search is. And the agent commits to only one action at a time, so a surprise in the next percept can trigger a fresh plan before much damage is done. An architecture that computed a 200-step plan and then executed it blindly would be brittle in any environment that is not perfectly deterministic and static.

Search and planning as decision making. Deliberation can be organised in two broad styles, which differ in how richly they represent actions.

Search treats states as atomic, opaque objects. The agent knows only that it has a start state, a successor function, and a goal test; it explores the space of action sequences by repeatedly expanding states. Breadth-first search, uniform-cost search, and A* are all instances. For route finding this is natural: a state is "the taxi is at junction 42," the successors are the junctions reachable by one road, and the goal test is "is this junction the airport?"

Planning keeps a structured, factored representation of states and actions. A state is a set of true facts, and an action is described by its preconditions and effects, for example:

Action(Load(crate, truck, loc),
  PRECOND: At(crate, loc) & At(truck, loc) & Empty(truck)
  EFFECT:  ~At(crate, loc) & In(crate, truck) & ~Empty(truck))

Goal: In(crate7, truckB) & At(truckB, depot)

Because the planner can see inside states and actions, it can reason about which action achieves which sub-goal, ignore irrelevant facts, and decompose the problem — things an atomic-state search cannot do. For large, structured domains such as logistics, spacecraft operations, or manufacturing scheduling, planning is dramatically more efficient than blind search over the same space.

The depth of lookahead required depends entirely on the task. A single-step lookahead suffices only when one action achieves the goal directly: a vacuum agent in a dirty square need only check that Suck produces a clean square. This degenerate case looks almost like a reflex agent, and indeed a goal-based agent in such a domain buys you little. The interesting cases need multi-step lookahead, and here the cost bites. If each state has branching factor b and the shallowest solution lies at depth d, an uninformed search may generate on the order of bd nodes. With b = 10 and d = 12 — a modest route-planning problem — that is of the order of 1012 nodes, which is already infeasible to enumerate one by one.

This is why heuristics matter. A heuristic h(s) estimates the remaining cost from state s to the nearest goal state, letting the search order its frontier so that promising branches are expanded first and hopeless ones are effectively pruned. Straight-line distance is the classic heuristic for route finding; the number of misplaced tiles or the sum of Manhattan distances serves the 8-puzzle; the count of unsatisfied goal literals, or the cost of a relaxed plan that ignores delete effects, serves classical planning. A heuristic that never overestimates the true remaining cost is called admissible, and A* with an admissible heuristic is guaranteed to return an optimal solution while typically expanding orders of magnitude fewer nodes than uninformed search. The heuristic is where domain knowledge re-enters a design that otherwise prides itself on being general.

Flexibility compared to reflex agents. The practical payoff of separating goal from model is modularity, and it shows up in four distinct ways.

  • New goals yield new behaviour for free. Tell the delivery robot At(dock) today and At(bay3) tomorrow and it produces entirely different action sequences from the same map and the same transition model. No code is rewritten; only data changes. A reflex agent would need a fresh rule set per destination.
  • Model improvements propagate to every goal. Add a newly opened corridor to the map, or correct the model of how long the lift takes, and every future plan — for every destination — benefits immediately. In a reflex design, the same correction would have to be applied by hand to every rule that implicitly encoded the old route.
  • Novel situations are handled without anticipation. Suppose a bridge closes. A goal-based taxi, told the edge no longer exists, simply searches again and finds a detour the designer never thought about. A reflex taxi has no rule for "bridge closed on the route to the airport" unless someone wrote one, and no mechanism for inventing a replacement.
  • Behaviour is explainable. Because the goal and the model are explicit objects, a decision can be justified: "I chose TurnLeft because, given my belief that the bridge is closed, the cheapest path satisfying At(airport) starts with TurnLeft." This transparency matters enormously for debugging, for certification in safety-critical domains, and for user trust.

Contrast this with the combinatorics facing a reflex designer. If there are S distinguishable situations and D possible destinations, condition–action rules must in principle cover S × D combinations. The goal-based agent needs one model of size roughly S plus a goal of size roughly 1, and it computes the cross-product on demand. The cost is paid in CPU time at run time rather than in designer effort at design time — which is precisely the trade-off the next section examines.

Computational cost and limitations. Deliberation is not free, and goal-based agents have several well-understood weaknesses.

  • Exponential blow-up. As noted, both time and memory can grow as bd. Breadth-first search stores the entire frontier, so memory usually fails before time does. Real systems mitigate this with heuristics, iterative deepening, pattern databases, hierarchical decomposition, or plan caching — but the worst case remains intractable, and classical planning is PSPACE-complete in general.
  • Latency versus reflexes. A reflex agent responds in effectively constant time: match a rule, emit an action. In a real-time domain — collision avoidance, a control loop running at 100 Hz, an industrial safety interlock — a planner that takes 300 ms to think is simply the wrong tool. Practical architectures therefore often layer a fast reflex "safety" level beneath a slower deliberative level, letting reflexes pre-empt the plan when something urgent happens.
  • Binary goals cannot rank successes. If two routes both reach the airport, one taking 20 minutes and one taking 90, the goal test says "success" to both. You can patch this by adding path costs and using uniform-cost search or A*, which optimises a single cost measure, but the goal itself still carries no notion of degree of satisfaction.
  • No trade-offs between competing goals. A taxi should be fast, safe, cheap, legal, and comfortable. These conflict: faster means less safe, cheaper means slower. A binary goal conjunction can only say "achieve all of them" — and if the conjunction is unsatisfiable, the agent simply reports failure rather than finding the best available compromise. Partially achievable goals ("deliver 8 of the 10 parcels") are likewise outside its natural vocabulary.
  • Model uncertainty breaks confident plans. Search assumes the transition model is correct. If actions are stochastic, if other agents interfere, or if the world model is stale, a plan that looked guaranteed can fail mid-execution. Partial remedies include re-planning every cycle, contingency planning that branches on observations, and conformant planning that works for all possible outcomes — all of which increase cost further.

These limitations are exactly the motivation for the utility-based agent, which replaces the binary goal test with a utility function mapping each state (or each sequence) to a real number. Utility lets the agent say "this outcome is somewhat better than that one," supports principled trade-offs between conflicting objectives, and — combined with probabilities from an uncertain model — supports maximising expected utility rather than hoping a plan succeeds. Goal-based agents can be seen as the special case in which utility is 1 at goal states and 0 elsewhere.

Choosing a goal-based architecture. Architecture selection should be argued from the properties of the task environment and the operational constraints, not from fashion. Four questions settle most cases.

  • Do the goals change often while the dynamics stay stable? This is the sweet spot. A warehouse robot's map and motion model are fixed for months, but its destination changes every few minutes. Encoding the stable part once (the model) and varying the volatile part (the goal) minimises maintenance effort — one of the strongest practical arguments for the design.
  • Does the correct action depend on consequences several steps ahead? If a locally attractive action can lead into a dead end — turning onto a one-way street, spending a resource that is needed later, taking a cul-de-sac in a maze — then lookahead is not optional. Reflex rules, which see only the present, systematically fall into such traps.
  • Are responses required immediately, over a small set of situations? Then prefer a reflex design, or a hybrid in which reflexes handle time-critical events and a planner handles the longer horizon. A thermostat, an anti-lock braking controller, and a packet-dropping firewall rule need microseconds, not a search tree.
  • Is a reliable transition model actually available? This is the precondition everyone forgets. Planning is only as good as RESULT(s, a). If the domain is poorly understood, highly stochastic, or populated by adversaries, a nominally brilliant plan will fail on contact with reality; you may need stochastic planning, online re-planning, or a learning agent that acquires the model from experience.

When you do commit to the architecture, make the justification concrete by naming three things: the goal representation ("goal test At(robot, bay3) & Carrying(nothing)"), the search method ("A* over the grid graph with a Manhattan-distance heuristic, re-planned on each obstacle detection"), and the expected cost ("branching factor 4, typical depth 60, under 5,000 node expansions, well inside the 100 ms control budget"). Stating the rejected alternatives strengthens the case: a simple reflex wall-follower was rejected because it cannot guarantee reaching an arbitrary bay; a utility-based design was rejected because all successful routes are acceptable and no trade-off between competing objectives is required, so the extra modelling effort would buy nothing. That pattern — goal, method, cost, rejected alternatives — is what turns an architectural preference into a defensible engineering decision.

Worked illustration. Consider a hospital delivery robot that must take a sample from Ward C to the Lab. Its sensors report corridor occupancy and its own position; its internal state records the floor plan plus the fact that the east lift has been out of service since 09:00 — information no current percept provides, which is exactly why the world model is needed. Its goal is At(robot, Lab) & Holding(nothing). Its transition model says a Move action succeeds unless a corridor is blocked, that UseLift requires the lift to be in service, and that Deposit requires being at the Lab counter. A* with a floor-aware distance heuristic returns the sequence [Move(C, junction1), Move(junction1, westLift), UseLift(3, 1), Move(liftLobby, Lab), Deposit]. The robot executes Move(C, junction1) only, then re-perceives. If a trolley now blocks junction1, the stored plan is invalidated and a new search finds a route via the south corridor — a response the designer never explicitly programmed. Had the task instead been "deliver all six samples in whatever order minimises total time while never letting any sample exceed its 30-minute stability window," the binary goal test would be inadequate: that problem needs a continuous measure over outcomes, and the appropriate architecture would be utility-based.

NotesSuggested classroom extensions: (1) have students hand-trace the GOAL-BASED-AGENT pseudocode on a 3x3 grid world with one blocked cell, recording state, plan, and action for each cycle; (2) ask them to re-run the same trace after changing only the goal, to see that behaviour changes without any rule being rewritten; (3) ask them to invalidate the model (close a corridor mid-execution) and observe the re-planning branch of the pseudocode firing. Common misconceptions worth pre-empting: students often assume a goal-based agent must compute a complete plan once and then execute it blindly — emphasise the one-action-then-re-perceive loop. They also frequently conflate "goal" with "performance measure"; stress that a goal is a binary predicate over states supplied to the agent, whereas a performance measure is an external, often continuous criterion used to judge the agent, and that closing the gap between the two is precisely what utility-based agents do. Assessment ideas: give a scenario (lift controller, chess engine opening book, parcel-sorting arm, autonomous lawnmower) and require a one-paragraph architecture justification naming goal representation, search method, expected node expansions or latency budget, and at least one rejected alternative with a reason. Terminology note for consistency with Russell & Norvig: "model-based, goal-based agent" is the full name used in the textbook for this design; the shorter "goal-based agent" is used throughout here, but the retained world model should never be presented as optional.

A goal-based agent goes beyond reacting to what it currently senses. It keeps an internal model of how the world works and how actions change it, and it also holds explicit information about the state it is trying to reach. Action selection becomes a reasoning problem: the agent projects possible futures, asks "what would happen if I did this?", and chooses a sequence of actions that leads toward the goal. This is where search and planning enter the picture as the machinery behind the decision.

This topic matters in the course because it marks the transition from condition-action rules to deliberation. A model-based reflex agent can tell you what the world is like; a goal-based agent can tell you what the world should become. That added flexibility is real — change the goal and the behavior changes without rewriting rules — but it is paid for in computation, model accuracy, and design effort. Knowing when that price is worth paying is a core design skill.

As you watch, keep three questions in front of you. First, what components does the agent program need (state, transition model, goal test, search procedure)? Second, exactly where does a goal-based agent succeed in a situation that defeats a reflex agent? Third, what does the deliberation cost, and at what point would you reject this architecture in favor of something simpler or something utility-based?
