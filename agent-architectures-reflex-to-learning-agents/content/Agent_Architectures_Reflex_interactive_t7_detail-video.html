Selecting and Justifying an Architecture

▶

Choosing an agent architecture is an engineering decision, not a matter of taste. Every architecture — simple reflex, model-based reflex, goal-based, utility-based, and learning — buys a particular capability at a particular cost. The capability is only worth buying if something in the task environment demands it. The discipline of architecture selection therefore runs in one direction: observe the environment, state the task requirements, derive the minimum architecture that satisfies the performance measure, and then justify why you stopped where you did. A justification that begins with the architecture ("we used a learning agent because machine learning is powerful") is not a justification at all; it is a preference dressed up as an argument. The sections below set out a repeatable procedure: profile the environment, map requirements to architectures, weigh performance against complexity, check the data and maintenance constraints, write a defensible argument, and test the procedure against worked scenarios.

Start with the environment profile. The task environment, not the designer's ambition, determines which capabilities an agent must possess. Before any design decision is made, the environment should be characterised along the standard dimensions — observability, determinism, episodic versus sequential structure, static versus dynamic, discrete versus continuous, single-agent versus multi-agent, and known versus unknown dynamics — and each judgement should be recorded with the evidence that supports it.

  • Observability drives the need for internal state. If the agent's sensors reveal every aspect of the environment that is relevant to the current decision, then the current percept alone is a sufficient basis for action, and a simple reflex agent with condition–action rules can be optimal. The qualifier "relevant" matters: an environment may be technically partially observable yet fully observable with respect to the decision at hand. A thermostat cannot see the room's occupancy, furniture, or weather forecast, but the only variable its performance measure depends on is temperature, which it senses directly — so it is effectively fully observable and a reflex rule suffices. Conversely, if any part of the relevant state is hidden — a room the robot cannot currently see, a card an opponent holds, a machine component whose wear is not directly measurable — the agent must infer that state from the percept sequence. That inference requires memory plus a model of how the world evolves and how actions affect it, which is precisely the definition of a model-based reflex agent. Partial observability does not merely suggest internal state; it forces it, because without state the agent cannot distinguish two situations that produce identical percepts but demand different actions.
  • Dynamism requires tracking change that the agent did not cause. In a static environment the world only changes when the agent acts, so a snapshot taken at decision time remains valid while the agent deliberates. In a dynamic environment — pedestrians moving, prices fluctuating, other robots repositioning stock — the world evolves independently. The agent's internal model must therefore contain two distinct kinds of knowledge: a transition model of how its own actions change the world ("if I move forward 1 m, my position advances"), and a world-evolution model of how the world changes on its own ("vehicles ahead continue at roughly their current velocity"). Semi-dynamic environments, where the world is static but the performance score degrades with elapsed time (as in chess with a clock), impose a related constraint: deliberation itself has a cost, which pushes back against expensive architectures.
  • Competing objectives and probabilistic outcomes signal utility. A goal is a binary predicate: a state either satisfies it or it does not. That representation is adequate when there is exactly one notion of success and all ways of achieving it are equally acceptable. It breaks down in two common situations. First, when outcomes are uncertain, the agent must compare a plan that reaches the goal with probability 0.95 and mild cost against one that reaches it with probability 0.6 and no cost — a comparison that binary goal satisfaction cannot express. Second, when several objectives conflict (speed versus fuel, throughput versus fairness, profit versus risk), there is no single goal predicate; there is a preference ordering over bundles of attributes. Both cases require a utility function that maps states or outcome distributions to a scalar, and a decision rule of maximising expected utility.
  • Unknown or shifting dynamics point to learning. If the designer cannot write down the transition model, the rule set, or the utility weights in advance — because the dynamics are unknown, because users' preferences drift, or because an adversary adapts — then the correct behaviour has to be discovered from experience. This requires a learning agent: a performance element that selects actions, a critic that evaluates outcomes against a fixed external performance standard, a learning element that modifies the performance element in response to the critic's feedback, and a problem generator that proposes exploratory actions so the agent does not stagnate on locally adequate behaviour. Note the precondition hidden in this: learning is only available if a usable feedback signal exists.
  • Document the profile explicitly. Record the property, the verdict, and the evidence, so the later architecture argument can be traced back to observations rather than assertions. A compact table is the most usable form:

Map task requirements to architectures. Once the environment is profiled, the mapping from requirement to architecture is largely mechanical. The guiding question for each candidate is: what can this architecture represent that the one below it cannot?

  • Condition–action responses with no history requirement → simple reflex agent. The agent program is a set of rules of the form if percept matches condition then do action. It is fast, trivially testable, and has no state to corrupt. It is appropriate when the correct action is a pure function of the current percept: an airbag controller, a thermostat, a spam filter applied to a single message in isolation, or the classic vacuum agent that senses both its location and the dirt status of the square it occupies.
  • Memory of unobserved state or action effects → model-based reflex agent. The same condition–action rules operate, but their conditions are evaluated against an estimated world state rather than the raw percept. The agent maintains state ← UPDATE-STATE(state, action, percept, transition_model, sensor_model). This is the right choice when the agent must remember where it has been, what it has already done, or what is probably true but currently unseen — for example a robot tracking which rooms it has cleaned, or a fault-monitoring agent tracking a machine's hidden wear level.
  • Desired end state reached via search or planning → goal-based agent. Here the agent is given an explicit goal predicate and uses the transition model to search for an action sequence that reaches a goal state. The architecture's defining capability is lookahead: considering the future consequences of candidate action sequences before committing. It is required whenever the right immediate action depends on a destination that is not encoded in any local rule — route finding, puzzle solving, assembly sequencing. It also brings flexibility: change the goal and the behaviour changes without rewriting any rules, whereas a reflex agent would need a new rule set.
  • Trade-offs, degrees of success, or risk → utility-based agent. The goal predicate is replaced (or supplemented) by a utility function U(state) or U(outcome), and the agent chooses the action maximising expected utility: a* = argmax_a Σ_s' P(s' | s, a) · U(s'). This is the only architecture in the family that can rationally resolve conflicts between objectives, compare partial successes, or trade probability of success against cost.
  • Behaviour that must be discovered or refined over time → learning agent. Learning is a wrapper, not a rival: a learning agent's performance element can itself be reflex, model-based, goal-based, or utility-based. The decision to learn is therefore orthogonal to the decision about what structure the performance element has, and both decisions must be justified separately.

Weighing performance against complexity. The mapping table tells you what each architecture can do; it does not tell you what the task needs. That determination comes from the performance measure, which must be stated first and stated precisely. "Clean the floor" is not a performance measure; "percentage of floor area with dirt level below threshold, averaged over an eight-hour shift, minus 0.1 per unit of energy consumed, minus 50 per collision with a human" is. Once written, it functions as a test: start from the simplest architecture and ask whether it can attain an acceptable score. Escalate only when you can name the specific deficiency that causes failure.

  • Per-decision latency is a real constraint. Reflex rule evaluation is effectively constant time. State estimation adds a per-cycle update whose cost grows with the state representation; particle filters and Bayesian updates can be expensive. Goal-based search is worse: uninformed search over a branching factor b to depth d costs on the order of bd node expansions, and even with good heuristics the cost is many orders of magnitude above a rule lookup. Expected-utility calculation adds a summation over outcomes for every candidate action, and when combined with lookahead it multiplies the search cost. In a semi-dynamic or safety-critical setting, an architecture that produces a better decision too late produces a worse outcome. An obstacle-avoidance response computed in 300 ms by a planner is inferior to a cruder one computed in 5 ms by a reflex rule.
  • Models and goal representations are artefacts that must be built and maintained. Choosing a model-based or goal-based design commits the team to authoring a transition model, keeping it synchronised with the real world (new aisle layout, new product categories, changed road network), and validating it. Model drift is a silent failure mode: the agent behaves confidently and wrongly because its model no longer matches reality. The total cost of a model-based design is therefore not the implementation cost but the lifetime maintenance cost.
  • Hybrid layering is usually the honest answer for physical systems. Rather than picking one architecture, layer them: a fast reflex layer handles safety-critical, short-horizon responses with hard latency guarantees and simple, auditable rules; above it a model-based layer maintains the world estimate; above that a goal- or utility-based deliberative layer plans over a longer horizon. The reflex layer is given override authority, so that a planner failure or a late plan cannot cause a collision. This is the standard structure of robotic control stacks and of the subsumption-style architectures that preceded them.
  • Do not choose learning for novelty. If the correct behaviour is known, writable as rules, and verifiable by inspection or testing, a deterministic rule set is superior on almost every axis that matters: it is cheaper, it is predictable, it can be formally checked, it needs no training data, and it fails in ways engineers can diagnose. A learned policy introduces data dependencies, distributional-shift risk, opacity, and a monitoring obligation. Learning earns its place when the correct behaviour is genuinely unknown or genuinely non-stationary — not when it merely sounds more sophisticated.

Data, feedback, and maintainability constraints. Architectures impose obligations on the organisation that operates them, and these obligations often decide the question when the technical analysis leaves two candidates close together.

  • Learning needs a critic and experience. The critic's job is to convert raw percepts into an evaluation against a fixed performance standard, and it can only do so if some observable consequence correlates with success. A recommendation agent has an excellent feedback signal (clicks, dwell time, purchases, returns). A medical triage agent may have a signal available only after weeks, for a small number of cases, and with severe consequences for exploratory actions. When feedback is absent, delayed beyond usefulness, biased by the agent's own past choices, or when exploration is ethically or physically unsafe, the learning architecture is simply unavailable regardless of its theoretical appeal. Quantify this before committing: how many labelled or rewarded episodes per day, with what delay, and what is the cost of a bad exploratory action?
  • Reflex rule sets scale badly. Rules are cheap at ten and brittle at a thousand. As conditions multiply, rules begin to overlap and conflict, priority schemes become opaque, and each new requirement risks regressions in unrelated behaviour. Combinatorial growth in the number of distinguishable percepts is the usual symptom that a declarative model plus a search or inference procedure would be cheaper to maintain than an ever-expanding rule table.
  • Utility functions must be elicited and calibrated, and are politically contested. Writing U = 0.5·speed − 0.3·fuel + 0.2·priority looks like engineering, but each coefficient encodes a value judgement: how many minutes of delay is one unit of fuel worth? How much risk of a late delivery is acceptable to save cost? Different stakeholders — operations, finance, safety, customers — will answer differently, and the weights may need periodic renegotiation. Plan for elicitation workshops, sensitivity analysis (does the chosen policy change if a weight moves by 20%?), and a documented owner for the weights.
  • Explainability and auditability can override raw performance. In regulated domains — lending, hiring, clinical decision support, public-sector eligibility — the ability to state why an action was taken may be a legal requirement. An explicit rule or an explicit goal-and-plan representation yields a natural explanation ("rule 17 fired because the account was 90 days overdue"; "this route was chosen because it was the shortest path satisfying the delivery-window constraint"). A learned policy may outperform both and still be unacceptable if its decisions cannot be justified to an auditor or appealed by an affected individual.
  • Ask who maintains it. An architecture that only its original author can modify is a liability. If the operating team are logistics supervisors, a goal-based agent whose goals they can edit through an interface is more maintainable than a utility-based agent whose weights interact in non-obvious ways, which is in turn far more maintainable than a learned policy requiring retraining pipelines, data versioning, and drift monitoring. Match the architecture to the competence and staffing of the people who will own it for the next five years.

Building a defensible justification. A justification is a short, structured argument that another engineer could check. It has five parts, in order.

  • Evidence first: PEAS and environment properties. State the Performance measure, Environment, Actuators, and Sensors, then the environment property table. These are the premises of the argument. For a delivery robot: P = parcels delivered on time, energy used, collisions, customer rating; E = campus pathways with pedestrians, lifts, weather; A = drive wheels, steering, lid actuator, speaker; S = GPS, lidar, cameras, wheel encoders, lid sensor, network link.
  • Chosen architecture and the necessary capability. Name the architecture and name the one capability that makes it necessary — the thing the next simpler design cannot represent. "Utility-based, because the performance measure combines punctuality, energy, and collision risk with explicit exchange rates, and no binary goal predicate can rank a plan that is two minutes slower but halves collision probability."
  • Rejected alternatives, both simpler and more complex. Naming a simpler alternative proves you did not over-engineer; naming a more complex one proves you did not under-engineer out of convenience. "A goal-based agent was rejected because it cannot trade punctuality against risk. A learning agent for route policy was rejected because the campus network is known and stable, feedback on route quality arrives only once per delivery, and an exploratory route near a stairwell carries unacceptable risk."
  • Residual risks and failure modes. Every choice leaves something uncovered. State it: "The utility weights are fixed and will not adapt to seasonal pedestrian density; the world-evolution model assumes constant pedestrian velocity, which fails in crowd surges; and the agent has no mechanism to detect that its map is stale."
  • Migration triggers, stated measurably. Specify in advance what observation would justify a different architecture, so the decision can be revisited on evidence rather than opinion. "Migrate to a learning agent for pedestrian prediction if constant-velocity prediction error exceeds 1.5 m at a 2 s horizon in more than 10% of encounters over a four-week window. Add a reflex override layer if emergency-stop latency exceeds 150 ms at the 99th percentile. Revisit utility weights if on-time delivery falls below 92% for two consecutive months."

Comparative worked scenarios. The procedure is best understood by watching the same analysis applied to variations of a task, where small changes in the environment profile flip the architectural verdict.

  • Vacuum cleaner with full dirt sensing. PEAS: P = squares cleaned per time step, penalty for movement; E = two squares A and B; A = Left, Right, Suck; S = location sensor, dirt sensor. The dirt sensor reports the status of the current square and the location sensor reports position, so the decision-relevant state is fully observable, the environment is static and deterministic, and each decision is effectively episodic. Three rules suffice: if dirty then Suck; if at A then Right; if at B then Left. A simple reflex agent is adequate and cheapest; a model-based design would add a state variable that provably never changes the chosen action, buying nothing. Rejected more complex alternative: goal-based planning, rejected because the plan it would produce is identical to the rule output at a far higher cost per decision.
  • Vacuum cleaner with limited sensing across many rooms. Change one premise: the robot has only a local dirt sensor, no global position sensor, and operates across twenty rooms. Now the environment is partially observable. A reflex agent cannot tell "room already cleaned" from "room not yet visited" — the percepts are identical — so it will wander, re-clean, and leave areas untouched; worse, a deterministic reflex agent can enter an infinite loop. The agent must maintain an occupancy and coverage map updated from odometry and percepts, i.e. state ← UPDATE-STATE(state, action, percept). A model-based reflex agent is required, and the necessary capability is coverage tracking. Residual risk: odometry drift corrupts the map, so a localisation correction mechanism (or periodic docking reset) is needed.
  • Route-finding delivery robot with a defined destination. PEAS: P = parcels delivered on time; E = a known campus path network; A = drive and steer; S = GPS, encoders, lidar. The environment is sequential: the correct turn at the current junction depends entirely on where the robot is ultimately going, and no local condition–action rule can encode that dependency for arbitrary destinations. The agent needs a goal predicate (at(destination)), a transition model of the path graph, and a search algorithm such as A* with a straight-line-distance heuristic. A goal-based agent is required, and the necessary capability is lookahead over action sequences. A model-based reflex agent was rejected because it would require a separate hand-written rule set per destination — an unmaintainable combinatorial explosion. A utility-based agent was rejected at this stage because the performance measure contains a single objective with no trade-offs to resolve.
  • Delivery robot balancing speed, fuel use, and parcel priority. Now the performance measure becomes multi-objective: minimise lateness, minimise energy, honour parcel priority, and avoid risky corridors. Two candidate routes can no longer be compared by a goal predicate, because both reach the destination — they differ in degree. The agent must score outcomes, for example U = −1.0·expected_lateness_minutes − 0.4·energy_kWh + 2.5·priority_served − 8.0·P(near-miss), and select the plan maximising expected utility over the path distribution. A utility-based agent is required; the necessary capability is commensurating conflicting objectives and handling stochastic travel times. The organisational cost is real: the four coefficients must be elicited from operations and safety stakeholders, documented, owned, and re-examined by sensitivity analysis.
  • Recommendation agent facing shifting user preferences. PEAS: P = long-run engagement and satisfaction, penalised for irrelevant or harmful suggestions; E = a catalogue and a population of users whose tastes drift seasonally and individually; A = present a ranked list; S = clicks, dwell time, purchases, ratings, returns. The environment's dynamics are unknown at design time and non-stationary thereafter: no fixed rule set or hand-written utility function stays accurate, because the preference model it encodes decays. The feedback signal, however, is abundant, fast, cheap, and low-risk to explore against. This is the textbook case for a learning agent: the performance element ranks items (often utility-based, scoring predicted relevance), the critic converts behavioural signals into an evaluation against the fixed standard of long-run satisfaction, the learning element updates the scoring model, and the problem generator deliberately injects exploratory recommendations so the agent discovers new preferences instead of exploiting a stale profile. Residual risks to acknowledge: feedback loops that narrow the catalogue, popularity bias, and the explainability gap — which is why many deployments wrap the learned scorer in explicit business rules for exclusions and compliance.
  • Autonomous vehicle: a hybrid stack. No single architecture satisfies this environment, which is partially observable, stochastic, sequential, dynamic, continuous, multi-agent, and safety-critical with hard real-time deadlines. The resolution is layering. A reflex layer implements emergency braking and lane-keeping limits as simple, auditable, formally checkable rules with guaranteed millisecond-scale latency and override authority. A model-based layer fuses lidar, radar, camera, and map data into a tracked world state including occluded objects and other vehicles' predicted trajectories. A utility-based deliberative layer plans over a several-second horizon, trading progress, comfort, legality, and collision risk under uncertainty. Learning appears inside specific components — perception, intent prediction — where the dynamics genuinely cannot be hand-specified, while the safety layer deliberately remains non-learned so that its behaviour can be verified. The justification writes itself from the profile: each layer exists because a named environment property makes the layer below insufficient, and the reflex layer exists because latency and verifiability make the layer above untrustworthy as a sole safeguard.

Once you can name the agent architectures — simple reflex, model-based reflex, goal-based, utility-based, and learning — the harder question becomes: which one should you actually build? This topic gives you a decision framework. You start from the environment profile (observable or partial, deterministic or stochastic, episodic or sequential, static or dynamic, discrete or continuous, single- or multi-agent), translate the task requirements into capabilities the agent must have, and then select the simplest architecture that meets those requirements.

The framework matters because the "most sophisticated" architecture is rarely the right answer. A learning agent needs training data, a feedback signal, and ongoing maintenance; a utility-based agent needs a defensible utility function; a model-based agent needs an internal state model somebody has to keep correct. Every added capability buys performance at the cost of complexity, data dependence, and long-term upkeep. A good justification names the alternatives you rejected and states, in terms of the environment profile, why they were rejected.

The videos below come from IBM Technology and are industry-facing rather than textbook-facing. Watch them with two questions in mind. First, when a speaker describes an agent type or system design, ask what environment properties are quietly being assumed. Second, notice where added autonomy or added machinery is presented as a trade-off rather than a free upgrade — that framing is exactly what you will reproduce when you defend an architecture choice in a worked scenario.
